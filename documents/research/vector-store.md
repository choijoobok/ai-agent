# 벡터 저장소 조사 — 별도 벡터 DB 를 둘 것인가

| 항목 | 내용 |
|---|---|
| 조사 시점 | **2026-09** — 문헌 접근 시점이다. 이 분야는 분기 단위로 지형이 바뀌므로 갱신 없이 인용하지 않는다 |
| 성격 | **기술 평가** — 실측이 아니다 |
| 근거로 쓰인 결정 | [`ADR-005`](../decisions/ADR-005-벡터-저장소.md) |
| 상위 | `CON-001`(AI 전용 DB · 별도 벡터 DB 를 두지 않는다) · `ARCH-060`(지식 검색 구성) · `ARCH-040`(임베딩 모델 추상화·재임베딩) · `CON-012`(폐쇄망 설치) |

> **비규범이다.** 여기의 어떤 서술도 설계 제약이 아니다 — 제약은 `documents/spec/` 이,
> 결정은 `documents/decisions/` 가 갖는다 ([산출물 지도 42행](../../aidd-guide/artifact/INDEX.md)).

## 1. 이 문서의 성격과 범위

`CON-001` 은 **별도 벡터 DB 를 두지 않는다** 를 단정하면서 근거로 *폐쇄망 운영 구성요소를
늘리지 않기 위함* 한 줄만 갖고 있었다. 되돌리기 비용이 큰 선택인데 **대안을 평가한 흔적이
없어** 게이트에서 그대로 물릴 자리였다. 이 문서는 그 빈자리를 채운다.

**답하려 한 것 셋.**

1. pgvector 로 어디까지 감당하나 — 한계가 시작되는 구간이 어디인가.
2. 전용 벡터 DB 를 뺐을 때 검색 품질에서 무엇을 포기하나.
3. 폐쇄망에서 구성요소 하나를 더 들이는 실제 비용이 얼마인가.

**답하지 않는 것 넷.** 여기 없는 답을 있는 것으로 읽지 않기 위해 먼저 적는다.

- **우리 데이터로 잰 값이 아니다.** 문헌 조사이며 PoC 가 아니다.
- **우리 지식 규모를 모른다.** 고객사가 없다(`OQ-002`). 그래서 이 문서는 *얼마까지 되나* 에
  숫자로 답하지 못하고, **재검토 신호를 무엇으로 잡을 것인가** 로 질문을 바꾼다.
  → **조사를 마친 뒤 2026-09-10 에 사용자가 규모 감을 줬다**(§4.2). **조사 자체는 그것
  없이 이뤄졌으며**, 뒤에 온 값이 결론을 바꾸지 않았다는 것이 이 문서의 쓸모다.
- **임베딩 모델·차원을 정하지 않는다.** `ARCH-040` 이 설정으로 열어 뒀고, 차원이 정해지기
  전에는 인덱스 메모리를 계산할 수 없다.
- **태그·벡터 병합 규칙을 정하지 않는다.** `ARCH-060` 이 상세 설계로 미뤄 둔 것이며,
  **어느 후보를 고르든 우리가 만들어야 하는 몫**이다.

## 2. 평가 축 — 우리 요건에서 유도한다

축 없이 후보를 나열하면 무엇을 비교했는지 알 수 없다. 다섯을 세운다.

| # | 축 | 어디서 왔나 | 왜 이것이 축인가 |
|---|---|---|---|
| 1 | **벡터 검색은 주 경로가 아니다** | `ARCH-060` | 태그 검색이 기본이고 벡터는 **켜면 함께 수행해 병합**한다. 벡터 단독 recall 이 아니라 **병합 후 기여**가 평가 대상이며, 벡터가 잠시 죽어도 지식 검색은 산다 |
| 2 | **끌 수 있어야 한다** | `ARCH-060` | 임베딩 off 가 **정식 구성**이다. 벡터 저장소가 별도 프로세스면 **임베딩을 끈 고객사도 그것을 설치·운영**하게 된다 — 쓰지 않는 구성요소를 유지보수하는 구조가 된다 |
| 3 | **구성요소 수가 곧 비용** | `CON-012`·`CON-013` | 고객사마다 직접 구축하고 개별 유지보수한다. 프로세스 하나가 늘면 설치·백업·버전 관리·보안 심사가 모두 하나씩 는다 |
| 4 | **규모가 미상이다** | `OQ-002` | 상한을 지어낼 수 없다. 그래서 정할 것은 *얼마까지 쓴다* 가 아니라 **무엇이 관측되면 재검토하는가** 다 |
| 5 | **재임베딩은 예정된 사건이다** | `ARCH-040` | 임베딩 모델을 교체하면 **기존 벡터를 전량 재생성**한다. 대량 삭제·재적재와 인덱스 재구축이 예외가 아니라 계획된 작업이다 |

## 3. 관측

후보 넷. **A 가 현행 전제**이고 나머지는 그것을 뒤집는 쪽이다.

| 후보 | 무엇인가 |
|---|---|
| **A. pgvector** | AI 전용 DB(PostgreSQL) 안의 확장. 벡터가 업무 데이터와 같은 트랜잭션·같은 백업 안에 있다 |
| **B. Qdrant** | 전용 벡터 DB. 단일 바이너리·단일 컨테이너로 뜬다 |
| **C. Milvus** | 전용 벡터 DB. 대규모·분산을 겨냥한다 |
| **D. pgvector + pgvectorscale** | A 에 StreamingDiskANN 인덱스를 더한 것. 그래프를 디스크에 두어 메모리를 묶는다 |

### 3.1 축별 관측

| 축 | A. pgvector | B. Qdrant | C. Milvus | D. +pgvectorscale |
|---|---|---|---|---|
| **규모** | 100만 안팎은 순조. **1,000만~2,000만부터** 양자화·파티셔닝·메모리 튜닝이 필요해진다 | 수천만 대 실용 | 수억 대까지 겨냥 | 수백만~수억. 47M 벡터 벤치에서 471 QPS@recall 99%(같은 시험의 Qdrant 41 QPS) |
| **메모리** | HNSW 가 메모리를 먹는다. **1536차원 1,000만 벡터에 80~120GB**. 메모리를 넘기면 그래프 순회가 디스크로 새고 질의가 밀리초에서 초 단위가 된다 | 양자화 내장 | 양자화·GPU 인덱스 | **디스크 상주** — 데이터가 커져도 메모리가 묶인다 |
| **필터링** | 필터 선택도가 높으면 후보가 전부 걸러져 **recall 이 떨어진다**. 0.8 의 iterative scan 이 부족하면 더 훑어 완화하지만 **CPU·지연이 는다** | **인덱스 레벨 필터링** — 구조적으로 유리하다 | 인덱스 레벨 필터링 | A 와 같은 문제, 완화 수단은 별개 |
| **하이브리드** | **네이티브 BM25 없음.** 전문 검색과 섞으려면 RRF 같은 순위 결합을 손으로 짜거나 별도 확장 | 내장 | 내장 | 〃 |
| **삭제·갱신** | HNSW 는 **삭제한 노드를 재빌드 전까지 회수하지 않는다**(툼스톤). 갱신이 잦으면 인덱스가 붓고 recall 이 떨어진다 | 세그먼트 회수 | 세그먼트 회수 | 〃 |
| **분산** | **샤딩 없음.** 한 인스턴스에 들어가는 동안만 유효 | 클러스터 | 클러스터 | 샤딩 없음 |
| **운영 구성요소** | **0 — 이미 있는 DB 의 확장이다** | 프로세스 1 | **standalone 도 etcd·MinIO 를 함께 띄운다.** 문헌에 따라 3컨테이너~10서비스 | 0 — 확장 하나 더 |

### 3.2 후보가 주지 않는 것 — 어느 쪽을 골라도 우리 몫이다

- **태그 검색과 벡터 검색의 병합 규칙** — 중복 제거·순위 결합·컨텍스트 주입 건수 상한.
  `ARCH-060` 이 미확정으로 남겼다. **검색 품질을 저장소 선택보다 크게 좌우할 수 있다.**
- **임베딩 on/off 전환 절차** — 껐다 켜면 기존 지식 전체의 임베딩이 필요하다(`ARCH-060`).
- **재임베딩과 인덱스 재구축의 운영 절차** — 축 5.
- **임베딩 비용의 귀속** — `NFR-015`.

### 3.3 두 저장소를 두는 값 — 규모와 무관한 비용

문헌이 일관되게 짚는 것은 성능이 아니라 **이중화 비용**이다. 저장소를 나누는 순간
**동기화 로직 · 이중 쓰기 처리 · 백업 정합 · 두 시스템 사이의 최종 일관성**이 생기며,
이것은 데이터가 100만이든 1만이든 **첫날부터** 든다. 반대로 pgvector 를 택하면 벡터가
업무 데이터와 **같은 트랜잭션·같은 백업·같은 복구 지점** 안에 있다.

같은 판단이 이 저장소에서 이미 한 번 내려져 있다 — `ARCH-070`(턴 실행 점유)이 분산 락
서버·메시지 브로커를 들이지 않고 **DB 의 조건부 갱신**으로 점유를 구현하며, 그 이유로
*별도 벡터 DB 를 두지 않기로 한 것과 같은 이유* 를 명시한다.

## 4. 판단

### 4.1 확인된 것

1. **pgvector 의 한계가 시작되는 구간은 1,000만 벡터 이상**이고, 그 아래에서는 튜닝
   범위의 문제다. 기업 지식 베이스의 청크 수는 통상 그보다 훨씬 아래다.
2. **전용 벡터 DB 의 운영 부담은 후보에 따라 크게 갈린다** — Qdrant 는 프로세스 하나,
   Milvus 는 standalone 이라도 etcd·MinIO 를 동반한다. **폐쇄망에서 Milvus 는 축 3 에
   정면으로 걸린다.**
3. **두 저장소의 비용은 규모와 무관하게 첫날 발생한다**(3.3).
4. **필터 선택도가 높은 질의가 pgvector 의 약점**이며, 0.8 의 iterative scan 이 완화하되
   CPU·지연을 대가로 낸다.
5. **HNSW 는 삭제 공간을 재빌드 전까지 회수하지 않는다** — 재임베딩(축 5)이 계획된
   작업인 우리에게는 **인덱스 재생성이 절차에 포함돼야 한다**는 뜻이다.
6. **임베딩을 끄는 구성이 정식인 한**(축 2), 별도 저장소는 *쓰지 않는 고객사도 설치하는
   구성요소* 가 된다. **이 축은 규모와 무관하며 문헌이 아니라 우리 요건에서 나온다.**

### 4.2 확인되지 않은 것

| 무엇 | 왜 남았나 | 언제 답할 수 있나 |
|---|---|---|
| ~~우리 지식 규모~~ **감이 생겼다(2026-09-10)** | 사용자 확정 — **1차 대상은 WMS·TMS**, 업무 테이블 **100~300개**, 지식 문서는 **수만 건 미만** 예상. 청크로 쪼개도 수십만 이하로 보는 것이 타당하며 문헌의 한계 시작 구간(1,000만)의 **3% 이하**다. **다만 실측이 아니라 추정이다** — 청크 분할 방식에 따라 몇 배 움직인다 | 실측은 계측이 선 뒤(`NFR-006`~`009`) |
| **임베딩 차원** | `ARCH-040` 이 설정으로 열어 뒀다. 차원 없이는 인덱스 메모리를 계산할 수 없다 | 모델 선정 시(P3~P4) |
| **실측값** | 이 문서는 문헌 조사다. 우리 데이터·우리 하드웨어로 잰 것이 하나도 없다 | 계측이 선 뒤(`NFR-006`~`009` · `@defer P4`) |
| **병합 후 검색 품질** | 병합 규칙 자체가 아직 없다(`ARCH-060` undecided) | 상세 설계에서 규칙을 정한 뒤 |
| ~~고객사의 확장 설치 정책~~ **해소됐다(2026-09-10)** | 사용자 확정 — **AI 전용 DB 는 우리가 설치해 제공한다**(완제품 납품). `CON-012` 에 명시했다. **확장 설치와 버전이 우리 손 안에 있다** | 답이 나왔다 |
