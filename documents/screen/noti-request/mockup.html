  1. 1요청일시 오름차순이다 — 로그 화면과 반대다. 64 의 이력 3종은 "방금 무슨 일이 있었나" 를 묻지만 처리함은 대기열이고, 대기열은 오래 기다린 것이 먼저다. 최신을 위에 두면 가장 오래 방치된 요청이 목록 맨 아래로 밀려 영원히 안 보인다. tie-breaker 는 REQ_ID ASC 다.
  2. 2유형과 상태는 공통코드가 아니다 — 값은 소스가 분기하고 라벨만 메시지 키(notiReq.type.* · notiReq.stat.*)다. 배지는 값이 아니라 display 를 그린다: 라벨로 저장하면 set 필터와 정렬이 라벨을 보게 된다.
  3. 3요청 내용은 VARCHAR(2000) 인데 긴 텍스트 뷰어로 연다(화면 2). largeText 다 — 처음에는 textModal 로 적었는데 그 어휘에는 구현이 없다(컬럼 계약 열한째 · notice.html §2 가 같은 정정을 담는다). 컬럼 계약이 "길이가 타입과 무관하다" 고 한 것이 반대 방향에서 확인되는 첫 자리다 — nclob 이 아니어도 셀 한 줄에 안 들어간다.
  4. 4편집 열이 통째로 없다. 지금까지의 화면을 통틀어 처음이며 그리드 표준 ("그리드가 목록이자 편집 화면")의 예외다. 이유가 셋이다 — 처리는 저장이 아니라 판정이고, 부수 효과가 있고(화면 3 · 4), 반려는 두 값을 함께 강제해야 하는데 셀 하나로는 안 된다.
  5. 550건씩이다 — 처리 대기를 훑는 화면이라 넘기며 보는 것보다 한눈에 보는 것이 낫다. notice.html 은 20건이다.
  6. 6②가 없다. E 액션이 없으므로 감춘다 — notice.html 과 함께 두 번째·세 번째 실물이다. 요청은 개인이 낸 글이라 내려받아 돌려 볼 업무 데이터가 아니다(메뉴 목록의 판단과 같은 방향).
  7. 조회조건 기본값이 접수 하나다. 전체를 기본으로 두면 처리된 것이 대기 중인 것을 덮는다 — notice.html 의 게시 상태 기본값과 방향이 같고 더 좁다.
  8. 삭제 컬럼이 없다. 요청은 이력이며 지우면 "그때 뭘 요청했었나" 의 답이 사라진다. 보존은 기간이 맡는다 — 그 기간이 아직 미정이다.

2. 요청 내용 — 읽기 전용이어도 열린다

요청 내용 — 박정산 · 2026-08-25 09:31✕
읽기 모드 — 고칠 수 없고 복사는 된다 1
  1. 1editable: false 가 못 본다 를 뜻하지 않는다. 긴 텍스트는 열어야만 보이므로 읽기 전용 컬럼도 에디터를 읽기 모드로 연다 — 그 절이 "거부 메시지가 나오지 않는 유일한 읽기 전용 컬럼" 이라고 한 그것이다. 편집·검증 규약의 "읽기 전용 셀입니다" 가 여기서는 나오지 않는다 — 거부할 것이 아니라 보여줄 것이기 때문이다.
  2. 처리 메모도 같다. 처리된 행의 HANDLE_MEMO 를 더블 클릭하면 같은 모달이 읽기 모드로 열린다.

3. 처리 — 메모가 선택이다

처리✕
요청 1건을 처리 완료로 표시합니다.
박정산 — 배치 실행 권한 신청 2026-08-25
비우면 기본 문구가 갑니다 — "요청이 처리되었습니다." 1
확인하면 요청자의 알림함에 행이 하나 생깁니다 — 같은 트랜잭션입니다. 2
  1. 1처리 메모는 선택이고 반려 사유는 필수다(화면 4). 비대칭이 의도다 — 파일·알림 데이터 모델이 REJECTED 에만 "HANDLE_MEMO 필수" 라고 적었고 이 화면이 그것을 집행한다. 처리는 결과 자체가 답이지만 반려는 이유가 없으면 답이 아니다.
  2. 2이 화면이 SYS_NOTI_INBOX 의 첫 생산자다. 셸 표준이 "상태가 바뀌면 그것이 내 알림으로 온다" 고 적은 알림을 여기서 넣는다. 같은 트랜잭션이며 — 파일·알림 데이터 모델의 "DB 에 행을 쓰는 것이 곧 도달" 그대로다. outbox 도 릴레이도 없다: 외부 채널이 없는 배포이므로 지나갈 곳이 없는 테이블이다.
  3. LINK_MENU_CD 는 NULL 이다 — 요청 결과를 보러 갈 메뉴가 요청자에게 없다. NOTI_REQUEST 는 관리자 메뉴이고 요청자가 보는 자리는 알림 모달의 탭인데 탭에는 MENU_CD 가 없다. 파일·알림 데이터 모델이 "NULL 이면 이동 없음" 으로 이미 열어 둔 자리다.

  3. 처리와 반려가 한 API 인 이유 — 쓰는 컬럼이 같고 트랜잭션이 같다. 둘로 가르면 알림 INSERT 코드가 두 벌이 되고 한쪽만 고치는 날이 온다.

  1. 1버튼이 비활성이다 — 눌러서 안내를 받지 않는다. batch-schedule 의 선택 없이 즉시 실행 과 같은 규칙이며, 여기는 선택이 있는데도 비활성인 경우다.
  2. 2섞이면 전부 막는다 — 처리 가능한 것만 골라 실행하지 않는다. 일부만 처리하면 알림이 일부에게만 나가고 사용자는 무엇이 처리됐는지 모른다. 되돌리는 길이 없으므로(아래) 부분 성공을 만들지 않는다.
  3. 되돌아가는 전이가 없다. DONE·REJECTED 에서 RECEIVED 로 가는 길을 두지 않는 이유는 알림이 이미 나갔기 때문이다 — 상태를 되돌려도 요청자가 받은 알림은 회수되지 않는다. 잘못 처리했으면 요청자가 다시 내고 그것이 새 행이다.
  4. 넷째 상태를 요구하는 목소리(검토 중 · 보류)는 컬럼이 아니라 범위의 문제다 . 그 이상이 필요하면 신청 메뉴와 승인 메뉴를 분리해 권한으로 표현한다.

7. 테스트 케이스 — 주석의 주장을 전부 덮는다

주석은 "왜 이렇게 그렸는가" 를 말하고, 여기는 "그것이 지켜졌는가" 를 묻는다. 근거가 빈 케이스는 지어낸 것이다 — 문서 절이나 이 파일의 주석 번호를 가리킨다. 되면 안 되는 것도 함께 넣는다.

8. 이 목업으로 확인할 것

이 화면이 규약에 되돌려 준 것
  • 읽기 전용 그리드의 첫 실물 — 편집 열이 통째로 없다. 판정에 부수 효과가 있으면 셀 편집이 아니다(§1 주석 4).
  • 긴 텍스트 뷰어가 nclob 밖에서 처음 쓰인다(쓰인 것은 largeText 다) — REQ_CONTENT 는 VARCHAR(2000) 이다. "길이가 타입과 무관하다" 가 반대 방향에서 확인된다(§1 주석 3).
  • 대기열 화면은 오름차순이다(로그 화면 설계와 반대) — 정렬 방향이 화면 성격에서 나온다(§1 주석 1).
  • confirm: string 의 두 번째 자리 — 반려는 사유가 상대에게 간다 를 말해야 한다(§4 주석 1).
  • SYS_NOTI_INBOX 의 첫 생산자 — 셸 표준이 "상태가 바뀌면 그것이 내 알림으로 온다" 고 적은 알림을 여기서 넣는다. outbox 없이 성립한다.
아직 답이 없는 것
  • SYS_NOTI_REQUEST 의 보존 기간 — 보관 정책의 정책 표에 없다. 요청은 개인이 낸 것이라 로그와 성격이 다르고, 짧으면 "작년에 낸 요청" 의 답이 사라진다.
  • 알림에서 알림 모달의 다른 탭으로 가는 링크 — LINK_MENU_CD 는 메뉴 코드라 모달 안을 가리킬 수 없다. 지금은 NULL 이다.
  • entryType = NOTIFICATION(noti-inbox.html NI-10) — MenuSelectRequest 가 entryType 자체를 받지 않는다. 메뉴 진입은 되고 경로 기록만 안 된다.
  • 요청을 내는 화면의 상세 — 알림 모달 내 요청 탭의 새 요청 버튼 (noti-inbox.html §4). 유형 셋 중 무엇을 사용자가 고를 수 있는지는 인증 화면 설계의 몫이다.
