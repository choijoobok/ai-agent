# 요건 정의서 — 비밀번호 강제 변경

## 개요

- **무엇을 하는 화면인가**: 만료되었거나 초기화된 비밀번호를 **셸에 들어가기 전에** 바꾸게 한다. 규칙 다섯을 **실시간으로 표시**해 제출해서야 알게 되는 재입력을 없앤다.
- **프로세스상 위치**: [로그인](../login/requirements.md) 응답이 `mustChangePassword=true` 이거나 비밀번호가 만료됐을 때 → **이 화면** → 셸.
- **바꾸면 어디가 흔들리나**: 여기 정한 **규칙 다섯**을 [내 프로필 모달](../profile/requirements.md)의 비밀번호 변경 탭과 재설정 ③이 그대로 쓴다 — **화면이 셋이지만 규칙은 하나다.**

> **이 문서는 `docs/design/60-screen-auth.md` §4 에서 옮겼다**(2026-09-04 · 그 폴더는 폐지됐다).

> **문서 상태: 미구현** — 화면이 아직 없다. 규칙과 계약은 확정돼 있다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증 — 규칙 다섯

| # | 규칙 | 기본값 | `SYS_CONFIG` 키 | 프론트 검증 |
|---|---|---|---|---|
| 1 | 최소 길이 | **9자** | `auth.password.min-length` | ✅ |
| 2 | 문자 조합 — 영대·영소·숫자·특수 **4계열 중 N종** | **3종** | `auth.password.require-charset-kinds` | ✅ |
| 3 | 같은 문자·연속된 문자 **N자 이상 금지** | **4자** | **키 없음**(§9) | ✅ |
| 4 | **로그인 ID 포함 금지** | — | **키 없음**(§9) | ✅ |
| 5 | **재사용 금지** — 최근 N개 | **3개** | `auth.password.reuse-block-count` | ❌ **서버 전용** |

**숫자를 화면 코드에 박지 않는다.** 전부 `SYS_CONFIG` 에서 받아 그린다(런타임 반영).

### 6-2. 프론트·백엔드 검증을 어긋나지 않게 하는 방법

**완전 일치는 불가능하고 목표도 아니다.** 규칙 5는 과거 해시를 프론트에 내려줄 수 없으므로 **원리상 서버 전용**이다. 목표는 *"같게"* 가 아니라 둘이다.

- **프론트 검증 ⊆ 서버 검증**(진부분집합)
- **같은 입력에 대해 두 쪽의 판정이 갈리지 않음**

이를 위해 **세 층을 각각 단일 원본으로** 둔다.

| 층 | 단일 원본 | 전파 방식 |
|---|---|---|
| **파라미터**(9 · 3 · 4 · 3) | **`SYS_CONFIG`** | **정책 API** 가 내려준다. 프론트는 코드에 박지 않는다 |
| **규칙 판정** | **서버의 규칙 구현** | 정책 API 가 **규칙 식별자 + 파라미터 + 프론트검증 가능 여부**를 함께 내려준다. 프론트는 `식별자 → zod refinement` 매핑만 갖는다 |
| **문구** | **`SYS_MESSAGE`** | **서버가 번역을 완성해 내려준다.** 프론트는 받은 문자열을 그대로 표시하며 **에러 메시지 카탈로그를 두지 않는다** |

**정책 API 가 문구까지 함께 내려준다.** 그러면 **즉시 검증 문구와 제출 후 서버 거부 문구가 같은 `SYS_MESSAGE` 행에서 나오므로 갈릴 수 없다.**

```json
{ "rules": [
  { "id": "MIN_LENGTH",    "params": { "min": 9 },   "clientCheckable": true,
    "message": "9자 이상이어야 합니다." },
  { "id": "CHARSET_KINDS", "params": { "kinds": 3 }, "clientCheckable": true,
    "message": "영대문자·영소문자·숫자·특수문자 중 3종 이상을 포함해야 합니다." },
  { "id": "NO_REPEAT",     "params": { "len": 4 },   "clientCheckable": true,
    "message": "같은 문자나 연속된 문자를 4자 이상 쓸 수 없습니다." },
  { "id": "NO_LOGIN_ID",   "params": {},             "clientCheckable": true,
    "message": "아이디를 포함할 수 없습니다." },
  { "id": "NO_REUSE",      "params": { "count": 3 }, "clientCheckable": false,
    "message": "최근 3개와 같은 비밀번호는 쓸 수 없습니다." }
] }
```

**프론트가 갖는 것은 판정 로직뿐이다** — 문구도, 파라미터의 기본값도 갖지 않는다.

**어긋남을 막는 장치**

| 장치 | 내용 |
|---|---|
| `clientCheckable: false` | 프론트가 **건너뛴다.** 서버가 잡는다 — **실패 방향이 안전한 쪽**이다 |
| **매핑 없는 식별자** | 프론트가 **건너뛴다.** 서버가 규칙을 추가하면 프론트는 조용히 통과시키고 서버가 거부한다. **반대는 성립할 수 없다** — 규칙 목록의 출처가 서버 하나다 |
| **문구 단일 출처** | 프론트가 문구를 만들지 않으므로 **어긋날 대상이 없다** |
| **황금 케이스 테이블** | 같은 입력 집합을 양쪽에 먹여 판정을 대조한다. **판정 불일치를 실제로 잡는 유일한 수단** |
| **CI 대조** | `프론트 매핑 키 ⊆ 서버 규칙 식별자` 를 빌드에서 확인 — `checkApiSeed` 와 같은 발상 |

> **이것은 비밀번호만의 문제가 아니다.** 모든 폼이 같은 구조를 갖는다. 일반화는 두 갈래다 — **정적 규칙**(필수·길이·형식)은 서버 DTO 의 Bean Validation 에서 도출할 수 있고, **동적 규칙**(`SYS_CONFIG` 값에 의존)은 위의 정책 API 형태가 된다. **비밀번호는 동적 규칙으로 확정한다**(2026-08-26) — 정책값이 런타임에 바뀌므로 애노테이션에 박을 수 없다.

### 6-3. 영향 테이블

`SYS_USER`(해시 · `PWD_CHG_DTM` · `PWD_INIT_YN`) + `SYS_USER_PWD_HIST` 적재. **한 트랜잭션**이다.

## 7. API

정책 조회 **`GET /api/public/auth/getPasswordPolicy`** + 변경 `POST /api/common/auth/changePassword`.
**인가 시드의 입력이 아니다.**

> **정책 API 는 이미 서 있다**(2026-09-04 · [로그인 §7-1](../login/requirements.md)). 경로가
> 미결이었던 자리를 재설정 3단계가 닫았고, 이 화면은 **같은 응답을 그대로 쓴다** — 규칙
> 목록의 출처가 서버 하나여야 세 화면이 갈리지 않는다.
>
> **지금 그 응답이 내는 규칙은 셋**(1 · 2 · 5)이다. 규칙 3·4 는 서버에 구현도 설정 키도 없다
> — 아래 §9 의 미결이 그것이며, 정하는 날 `PasswordPolicies` 에 두 줄이 늘고 프론트는
> **고칠 것이 없다**(모르는 식별자를 건너뛰므로).

---

## 8. 시드 · 데이터 전제

`SYS_CONFIG` 에 `auth.password.min-length` · `require-charset-kinds` · `reuse-block-count` 가
있어야 한다 — **셋 다 있다**. 규칙 3·4 의 키는 **아직 없다**(§9).

정책 문구 셋(`pwd.rule.*`)도 **있다** — `data/107`. 이 화면이 쓸 문구는 **새로 만들 것이 없고**
남은 것은 화면 자신의 라벨뿐이다.

## 9. 미결 · 확인 필요

| 항목 | 성격 |
|---|---|
| **규칙 3·4 의 설정 키** — 끄고 켤 수 있어야 하는지, 자릿수를 조정할 수 있어야 하는지. **정하기 전까지 그 둘은 존재하지 않는다**(§7) | 결정 |
| **폼 검증 규약의 일반화** — 정적 규칙을 서버 DTO 에서 도출하는 방식. **ADR 대상** | 결정 |
| **[내 프로필](../profile/requirements.md)의 변경 폼과 컴포넌트를 공유할지** — 규칙·체크리스트는 같고 출구와 배너만 다르다 | 결정 |
