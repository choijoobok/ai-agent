# 요건 정의서 — 알림 모달

## 개요

- **무엇을 하는 화면인가**: 헤더 벨을 눌러 여는 **게시판 형태의 탭 모달**. 공지사항 · 내 알림 · 내 요청 셋을 보고, 여기서 **관리자에게 요청을 낸다.**
- **프로세스상 위치**: (선행) 관리자가 `NOTICE_MGMT` 에 공지를 쓰거나 시스템이 알림을 넣는다 → **이 화면**(사용자가 읽는다) → (후행) 낸 요청은 `NOTI_REQUEST` 메뉴에서 처리된다.
- **바꾸면 어디가 흔들리나**: **배지가 세는 것은 *내 알림* 탭의 미읽음뿐**이다. 공지는 세지 않는다. 요청을 내면 `NOTI_REQUEST` 대기열에 뜬다.

> **이 문서는 `docs/design/60-screen-auth.md` §8 에서 옮겼다**(2026-09-04 · 그 폴더는 폐지됐다).

> **문서 상태: 구현됨** — `modules/system/public/notification/NotificationModal.tsx`.

## 1. 화면 구성

| 탭 | 방향 | 비고 |
|---|---|---|
| 공지사항 | 관리자 → 전체 | **읽기 전용.** 팝업이 최신 1건만 띄우므로 **공지 목록의 실질 자리가 이 탭**이다 |
| 내 알림 | 시스템 → 나 | **배지가 세는 것은 이 탭의 미읽음뿐** |
| 내 요청 | 나 → 관리자 | 처리는 `NOTI_REQUEST` 메뉴 |

### 1-1. 목록에 상한이 있다 — 화면이 말한다

`sys-config.ui.noti.list-size`(기본 50). **탭 셋이 한 값을 쓴다** — 같은 모달의 같은 자리라 길이가 갈릴 이유가 없다.

**넘치면 조용히 자르지 않는다.** 전건 수를 함께 받아 *"최근 N건"* 을 낸다 — 조용히 자르면 목록이 전부로 읽히고, 그러면 **없는 알림을 없다고 확신한다.**

> **미읽음 배지는 이 상한과 무관하게 전건을 센다.** 상한이 배지를 깎으면 *배지는 3인데 목록엔 2* 가 생기고, 그때 사용자는 **놓친 알림을 찾을 방법이 없다.**

각 탭은 제목 · 일시 · 상태를 보인다. 공지 목록은 **본문(`nclob`)을 싣지 않는다** — 상세를 따로 부른다.

## 5. 버튼 · 액션

| 버튼 | 무엇 |
|---|---|
| 항목 클릭 | 상세로 — **그 항목만** 읽음 처리 |
| 모두 읽음 | 명시적으로 전부 |
| 이동 | 알림이 가리키는 메뉴로 — §6-4 |
| 새 요청 | *내 요청* 탭에서 폼으로 바뀐다 — §6-3 |

**읽음 처리** — 항목을 열면 그 항목만. **목록을 열었다고 전체 읽음 처리하지 않는다.**

## 6. 규칙 — 저장 · 실행

### 6-1. 부르는 경로 — 전부 `common` 이다

메뉴 밖 화면이라 `MENU_CD` 가 없고 권한은 `(MENU_CD, ACTION_CD)` 쌍이다. 그래서 **판정을 걸 자리가 없고, 대신 범위가 좁다** — 넷 다 대상이 세션의 주인이며 `userId` 를 본문으로 받지 않는다.

| 경로 | 무엇 | 비고 |
|---|---|---|
| `GET /api/common/system/notice/getList?includeExpired=` | 공지 탭 | 조건이 **서버 코드에 박혀 있다** |
| `GET /api/common/system/notice/getOne` | 공지 상세 | 목록이 본문을 싣지 않는다 |
| `GET /api/common/system/notice/getPopup` | 팝업 | 대상 1건 + **나머지 수** |
| `GET /api/common/system/noti/getList` | 내 알림 | 목록 · 미읽음 · 전건을 **함께** 준다 |
| `GET /api/common/system/noti/getUnreadCount` | 배지만 | 모달을 열지 않아도 벨은 숫자를 보여야 한다 |
| `POST /api/common/system/noti/saveRead` | 그 항목만 | 남의 번호는 **없는 것**이다(403 이 아니다 — **있다는 사실이 정보다**) |
| `POST /api/common/system/noti/saveAllRead` | 전부 | 본문이 없다 |
| `GET /api/common/system/notiRequest/getMyList` | 내 요청 | **최신이 위**다 — 대기열이 아니라 이력이다 |
| `POST /api/common/system/notiRequest/save` | 새 요청 | §6-3 |

### 6-2. 검증

| 규칙 | 왜 |
|---|---|
| 내용 **필수** | 유형만으로는 무엇을 원하는지 알 수 없고 **되묻는 단계가 없다** |
| **같은 유형이 `RECEIVED` 면 거부** | §6-3 |
| 상태를 **받지 않는다** | 받으면 스스로 `DONE` 인 요청을 만들 수 있고, 그러면 **요청함이 기록으로만 쓰인다** |

### 6-3. 새 요청 — 같은 유형을 두 번 열지 않는다

*내 요청* 탭의 **새 요청** 버튼이 **같은 모달 안에서** 폼으로 바뀐다(새 모달을 겹치지 않는다). 입력은 **유형과 내용 둘뿐**이며 나머지는 서버가 정한다 — 요청자는 세션, 상태는 `RECEIVED`, 시각은 주입받은 `Clock`.

**여벌을 막는 이유가 둘이다.** 워크플로가 없으므로 요청은 한 번 내면 답이 올 때까지 그대로이고, 같은 것을 또 내도 **진행이 빨라지지 않는다.** 그리고 관리자는 그 여벌을 **하나씩 반려**해야 하는데 **반려마다 요청자에게 알림이 나간다** — 더블클릭 한 번이 그것을 만든다.

**막는 것은 같은 유형뿐이다.** 권한 신청과 잠금 해제는 **서로 다른 답을 기다리는 것**이라 함께 열려 있어야 한다. 화면이 폼에서 먼저 막고(버튼 비활성 + 이유) 서버가 다시 거부한다.

### 6-4. 이동 버튼은 메뉴 트리로 판정한다

알림의 `LINK_MENU_CD` 는 URL 이 아니라 **메뉴 코드**다. 이동 가능 여부는 **내 메뉴 트리에 그 코드가 있는가** 하나로 판정한다 — 트리는 유효 권한으로 이미 걸러져 오므로 **권한을 다시 묻지 않는다.** 없으면 **버튼이 비활성**이고 문구가 이유를 말한다 — 눌러서 403 을 보는 것보다 낫고, **알림이 권한을 주지 않는다.**

`LINK_PARAM` 은 **넘겨주기 채널**(`handoffStore`)로 간다 — *화면 → 화면* 건네주기와 같은 채널이며 **알림이 그 셋째 입구**다. 다만 그 채널은 **화면당 값 하나이고 종류를 모른다.** 그래서 알림은 **받는 쪽이 기대하는 종류**를 실어야 하며, 배치 실패 알림이 실행 번호가 아니라 **배치 ID** 를 싣는 이유가 그것이다.

### 6-5. 낸 사람에게도 관리자에게도 알림을 넣지 않는다

접수는 **내가 방금 한 일**이다 — 알림이 답하는 물음은 *"내가 하지 않은 무슨 일이 있었나"* 이고, 내 행동을 나에게 알리면 **배지가 내 클릭을 센다.** 접수 사실은 *내 요청* 탭에 그 줄이 생기는 것으로 이미 보인다.

**관리자에게도 보내지 않는다.** 대기열은 `NOTI_REQUEST` 화면이 보는 것이고, 알림으로도 보내면 **같은 사실을 두 곳이 말한다.** 그리고 받을 사람을 정하려면 *어느 역할이 요청을 처리하는가* 라는 **설정이 하나 더** 필요해진다.

## 9. 테스트 케이스

> **요건이 지켜졌는지 묻는 표다.** 위의 절들이 *무엇을* 정했다면 여기는 *그것이 지켜졌는가* 다.
> **되면 안 되는 것**을 함께 담는다 — 그것이 빠지면 케이스가 그림 검사로 줄어든다.
>
> **목업(`mockup.html`)은 이 표와 위의 절들로부터 생성되는 파생물이다** — 케이스를 목업에서
> 고치지 않는다. 고칠 곳은 여기고, 고친 뒤 `/mockup` 이 목업을 다시 만든다.

### 공지사항 탭

| # | 조작 · 상황 | 기대 |
|---|---|---|
| `NI-01` | 공지를 작성·수정하려 한다 | **불가** — `NOTICE_MGMT` 메뉴의 일이다. **모달에는 권한을 걸 자리가 없다** |
| `NI-02` | 읽지 않은 공지가 있는 상태 | **미읽음 배지가 늘지 않는다** — 로그인 팝업으로 이미 도달했다 **(되면 안 되는 것)** |
| `NI-03` | 공지 목록의 미읽음 강조 | **쓰지 않는다** — 강조도 읽음 저장도 없다 |
| `NI-04` | 게시 기간이 끝난 공지 | **흐리게 + `종료` 배지**. 기본은 감추고 *"지난 공지 포함"* 으로 켠다 |
| `NI-04b` | **내려진** 공지(`USE_YN='N'`) | **어느 쪽에서도 안 보인다** — *지난 공지 포함* 을 켜도 오지 않는다 **(되면 안 되는 것)** |
| `NI-04c` | **예정**인 공지(게시 시작 전) | **안 보인다** — 예약 게시가 성립하는 자리다 **(되면 안 되는 것)** |
| `NI-04d` | 게시중인 공지의 배지 | **없다** — 전부에 배지를 붙이면 정상 상태가 경고처럼 보인다 |
| `NI-04e` | 공지 상세를 연다 | **읽음이 생기지 않는다** — 공지에는 읽음 상태가 없다 **(되면 안 되는 것)** |

### 내 알림 탭

| # | 조작 · 상황 | 기대 |
|---|---|---|
| `NI-05` | 배지 숫자와 목록 대조 | **배지는 이 탭의 미읽음만** 센다 — 셋 중 하나만 |
| `NI-06` | 목록을 열고 훑어만 본다 | **배지가 그대로다** — 전체 읽음 처리하지 않는다 **(되면 안 되는 것)** |
| `NI-07` | 항목 하나를 연다 | **그 항목만** 읽음이 된다 |
| `NI-08` | "모두 읽음" 을 누른다 | **비워진다** — 의도적으로 비우는 경로는 있어야 한다 |
| `NI-09` | 항목을 고른다 | **같은 모달 안에서 상세로 바뀐다** — 새 탭을 열지 않는다 |
| `NI-10` | 알림의 이동 버튼을 누른다 | `MENU_CD` + `LINK_PARAM` 으로 **메뉴에 진입**하고 **모달이 닫힌다.** `entryType` 은 **아직 없다** — 이동은 되고 **경로 기록만** 안 된다(§7) |
| `NI-11` | **권한이 없어진** 메뉴로 가는 알림 | **이동 버튼이 비활성**이고 **이유를 말한다** — *"알림이 권한을 주지는 않습니다"* **(되면 안 되는 것)** |
| `NI-16` | 이동 버튼을 누른다 — `LINK_PARAM` 이 있다 | 그 화면이 **그 값으로 조회조건이 채워진 채** 열린다 |
| `NI-17` | 목록이 상한(50)을 넘는다 | **"최근 50건" 이라고 말한다** — 조용히 자르지 않는다 |
| `NI-18` | 배지가 3인데 목록엔 2 | **일어나지 않는다** — 배지는 상한과 무관하게 전건을 센다 **(되면 안 되는 것)** |
| `NI-19` | 모달을 열지 않은 채 새 알림이 온다 | **배지가 낡는다** — 폴링하지 않는다. 탭을 열거나 새로고침하면 맞는다 |
| `NI-20` | 이미 읽은 항목을 다시 연다 | **받은 시각이 바뀌지 않는다** — `READ_DTM` 은 *언제 처음 봤나* 다 **(되면 안 되는 것)** |

### 내 요청 탭

| # | 조작 · 상황 | 기대 |
|---|---|---|
| `NI-12` | 요청 상태 값 | **접수 · 처리 · 반려 셋**에서 닫힌다 — 워크플로가 아니다 |
| `NI-13` | 요청을 처리하려 한다 | **불가** — `NOTI_REQUEST` 메뉴의 일이다 **(되면 안 되는 것)** |
| `NI-14` | 요청의 진행이 바뀐다 | **내 알림**으로 알려지고, 이 탭은 **이력**을 본다 |
| `NI-15` | 내 요청의 미읽음 | **성립하지 않는다** — 내가 보낸 것이다 |
| `NI-21` | 새 요청을 낸다 | **내 알림함에 아무것도 안 들어온다** — 내가 방금 한 일이다 **(되면 안 되는 것)** |
| `NI-22` | 같은 유형이 **접수 상태**인데 새 요청 | **보내기가 막히고 이유를 말한다.** 서버도 거부한다 |
| `NI-23` | **다른 유형**으로 새 요청 | **보낼 수 있다** — 서로 다른 답을 기다리는 것이다 |
| `NI-24` | 요청 내용을 비우고 보낸다 | **비활성이라 눌리지 않는다** — 되묻는 단계가 없다 |
| `NI-25` | **처리된** 요청의 처리 메모 | 라벨이 ***처리 메모*** 다 — *사유* 를 붙이면 처리가 반려처럼 읽힌다 |
| `NI-26` | 정렬 | **최신이 위**다 — `NOTI_REQUEST` 의 오름차순과 반대이며 그것이 의도다 |

## 10. 미결 · 확인 필요
