# 요건 정의서 — 내 프로필 모달

## 개요

- **무엇을 하는 화면인가**: 자기 정보를 보고 고치고, 비밀번호를 스스로 바꾸고, **내** 로그인 이력과 **내** 역할을 확인한다. 탭 넷.
- **프로세스상 위치**: (선행) 관리자가 `USER_MGMT` 에서 계정과 역할을 만든다 → **이 화면**(본인이 확인·수정) → (후행) 바꾼 비밀번호로 다음 로그인.
- **바꾸면 어디가 흔들리나**: 비밀번호 변경 탭은 [강제 변경](../pwd-change/requirements.md)**과 규칙이 같다** — 한쪽만 고치면 갈린다. 역할 탭은 **읽기 전용**이라 여기서 권한이 바뀌지 않는다.

> **이 문서는 `docs/design/60-screen-auth.md` §6 에서 옮겼다**(2026-09-04 · 그 폴더는 폐지됐다).

> **문서 상태: 구현됨** — `modules/system/public/profile/ProfileModal.tsx`.

## 1. 화면 구성

| 탭 | 내용 | 쓰기 |
|---|---|---|
| 내 정보 | 기본 정보 — **조회와 수정을 한 화면에서** | `PUT /api/common/system/auth/getMe`(경로 미확정 — §10) |
| 비밀번호 변경 | 현재 + 새 비밀번호. **입력 제한은 강제 변경과 같다** | `SYS_USER`(`PWD_CHG_DTM` · `PWD_INIT_YN`) · `SYS_USER_PWD_HIST` |
| 내 로그인 이력 | 최근 N건 — 일시 · IP · User-Agent · 성공/실패. **본인 것만** | 읽기 전용 `SYS_LO_LOGIN` |
| 내 역할 | 보유 역할 · 유효기간 · 개인 예외. **읽기 전용** | — |

**모달 하단에 버전 · 환경을 표시한다** — 셸에서 푸터를 없애며 옮긴 자리이고, **서버 정보 화면을 따로 만들지 않은 근거**이기도 하다.

---

## 2. 조회조건

**해당 없음** — 대상이 언제나 나 자신이다. `userId` 를 본문으로 받지 않는다.

---

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

| 테이블 | 읽기 | 쓰기 |
|---|---|---|
| `SYS_USER` | 기본 정보 · 해시 | 기본 정보 · `PWD_CHG_DTM` · `PWD_INIT_YN` |
| `SYS_USER_PWD_HIST` | 재사용 검사 | 변경 시 적재 |
| `SYS_LO_LOGIN` | **본인 최근 N건** | — |
| `SYS_USER_ROLE` · `SYS_USER_MENU_AUTH` | 보유 역할 · 개인 예외 | — |

### 3-2. 고정 조건

**세션의 주인으로 고정**된다. 화면이 대상을 고를 수 없다.

---

## 4. 컬럼

### 4-1. 내 로그인 이력 탭

일시 · IP · User-Agent · 결과. **최근 N건**이며 `N` 은 미결(§10).

### 4-2. 내 역할 탭

역할명 · 유효기간(시작·종료) · 개인 예외. **전부 읽기 전용**이다.

---

## 5. 버튼 · 액션

내 정보 저장 · 비밀번호 변경. 나머지 두 탭은 버튼이 없다.

---

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

비밀번호 규칙은 [강제 변경 §6-1](../pwd-change/requirements.md) **과 같다.**

> **강제 변경과 다른 점은 출구다.** 규칙 다섯은 같고, 강제는 셸 밖이라 출구가 로그아웃뿐인데 **여기는 탭을 옮기거나 모달을 닫으면 그만**이다. 동시 세션이 계정당 하나이므로 **다른 세션을 끊을 필요도 없다.** 진입 사유 배너도 없다 — **사용자가 스스로 온 것이라 설명할 것이 없다.**

### 6-2. 영향 테이블

비밀번호를 바꾸면 `SYS_USER` + `SYS_USER_PWD_HIST` 가 **한 트랜잭션**으로 간다.

---

## 7. API

전부 `/api/common/**` — 대상이 세션의 주인이라 인가 판정을 걸 자리가 없다. **인가 시드의 입력이 아니다.**

---

## 8. 시드 · 데이터 전제

비밀번호 정책이 `SYS_CONFIG` 에 있어야 한다.

---

## 9. 테스트 케이스

> **요건이 지켜졌는지 묻는 표다.** 위의 절들이 *무엇을* 정했다면 여기는 *그것이 지켜졌는가* 다.
> **되면 안 되는 것**을 함께 담는다 — 그것이 빠지면 케이스가 그림 검사로 줄어든다.
>
> **목업(`mockup.html`)은 이 표와 위의 절들로부터 생성되는 파생물이다** — 케이스를 목업에서
> 고치지 않는다. 고칠 곳은 여기고, 고친 뒤 `/mockup` 이 목업을 다시 만든다.

| # | 조작 · 상황 | 기대 |
|---|---|---|
| `PF-01` | 조회 전용 탭을 찾는다 | **없다** — 한 탭에서 보고 고친다 |
| `PF-02` | 언어를 바꾼다 | **서버에 저장**된다 — 메일·알림 언어를 서버가 정한다 |
| `PF-03` | 모달 하단 | **버전·환경**이 있다 — 푸터를 없애며 옮긴 자리 |

| # | 조작 · 상황 | 기대 |
|---|---|---|
| `PF-04` | 규칙 목록을 `pwd-change` 와 대조 | **목록이 완전히 같다** — 같은 정책 API. 건수를 세지 않는다 |
| `PF-05` | 진입 사유 배너를 찾는다 | **없다** — 스스로 온 것이라 설명할 것이 없다 |

## 10. 미결 · 확인 필요

| 항목 | 성격 |
|---|---|
| **`/api/common/system/auth/getMe` 의 쓰기 경로** — 같은 경로의 `PUT` 인지 별도 경로인지 | 결정 |
| **내 로그인 이력 표시 건수 `N`** | 실측 |
| **비밀번호 변경 폼을 [강제 변경](../pwd-change/requirements.md)과 컴포넌트로 공유할지** — 공유하면 규칙 표시가 한 곳이지만 **강제/자발 분기가 컴포넌트 안으로 들어온다** | 결정 |
