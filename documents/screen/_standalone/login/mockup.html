① 로 돌아가기
/login · 재설정 ③ 새 비밀번호
  • 9자 이상
  • 영대문자 · 영소문자 · 숫자 · 특수문자 중 3종 이상
  • 같은 문자 · 연속된 문자 4자 이상 금지
  • 아이디를 포함할 수 없습니다
  • 최근 3개 와 같은 비밀번호는 쓸 수 없습니다 — 서버에서 확인

숫자는 전부 SYS_CONFIG 에서 받아 그린다. 코드에 박지 않는다. 7

  1. 4메일 주소를 입력받지 않는다. 서버가 SYS_USER 에서 찾는다 — SYS_USER_PWD_RESET 에 메일 컬럼이 없는 것도 같은 이유다. 받으면 ID·메일이 어긋날 때 무엇을 보여줄지가 "응답은 항상 동일" 원칙과 충돌한다.
  2. 5발송 응답은 계정 존재 여부와 무관하게 항상 동일하다. 마스킹된 메일 주소도 보여주지 않는다 — 그것 자체가 계정 존재 확인이다.
  3. 6쿨다운은 SYS_USER_PWD_RESET.ISSUE_DTM 이 판정한다. 다만 서버가 "잠시 후 다시" 를 알려주면 존재하는 계정에만 쿨다운이 걸려 ID 열거 단서가 된다. 서버는 같은 응답을 주고 타이머는 클라이언트가 표시한다.
  4. 7규칙은 셋이고 그중 둘만 프론트가 판정할 수 있다. 재사용 금지는 과거 해시를 내려줄 수 없으므로 서버 전용이다 — 회색 항목이 그것이다. 프론트 검증은 서버 검증의 진부분집합이다.
    연속 문자·아이디 포함은 목록에 없다 — 서버에 구현도 설정 키도 없고 그 키는 강제 변경 요건서 §9 의 미결이다. 없는 규칙을 그리면 지키지 않아도 통과하는 규칙이 생긴다(요건서 §7-1).
    위 문구도 프론트가 만든 것이 아니다. 정책 API 가 규칙·파라미터와 함께 완성된 문구를 내려준다 — 즉시 검증 문구와 제출 후 서버 거부 문구가 같은 SYS_MESSAGE 행에서 나오므로 갈릴 수 없다.
  5. 잠금은 ③ 완료 시점에 풀린다 — 발송만으로 풀리면 실패 5회 → 재설정 요청 → 리셋 → 다시 5회 가 무한 반복된다.
  6. 메일 연동이 없는 배포에서는 관리자 발급이 유일한 복구 수단이다 (auth.password.admin-reset-enabled 기본 켬).

4. 테스트 케이스 — 주석의 주장을 전부 덮는다

주석은 "왜 이렇게 그렸는가" 를 말하고, 여기는 "그것이 지켜졌는가" 를 묻는다. 근거가 빈 케이스는 지어낸 것이다 — 문서 절이나 이 파일의 주석 번호를 가리킨다. 되면 안 되는 것도 함께 넣는다.

5. 이 목업으로 확인할 것

미결이 없다(2026-09-04). 여섯이 닫혔고 결론은 전부 requirements.md 가 갖는다 — 이 목록은 무엇이 어디서 닫혔는지만 가리킨다.
  • /api/public/** 재설정 3종 경로 → sendResetCode · verifyResetCode · saveResetPassword. reset 으로 묶어 관리자 발급(/service/user/savePasswordReset)과 이름이 겹치지 않게 했다 (요건서 §7)
  • 비밀번호 정책 API → GET /api/public/auth/getPasswordPolicy. 규칙 식별자 · 파라미터 · 문구를 함께 내려주며 강제 변경 · 프로필도 같은 응답을 쓴다 (요건서 §7-1)
  • 재발송 쿨다운 → 60초. 이미 닫혀 있었다 — sys-config.auth.password.reset.request-cooldown-seconds 가 소스에 있다. 목업이 그린 60초가 맞았다 (요건서 §6-1)
  • 언어 선택기 → 두지 않는다. 언어는 localStorage → 브라우저 언어 두 순위로 끝나고 지원 언어가 둘이라 그것이 모든 경우를 닫는다. 바꾸는 자리는 설정 모달이다 (요건서 §4-3)
  • 잠김 안내의 재설정 링크 → 경고 배너 본문 안에 링크. 새 버튼을 만들지 않는다 — 만들면 잠긴 사용자만 보는 버튼이 생기고 그 상태를 따로 그려야 한다 (요건서 §6-4)
  • 로고 · 서비스명 교체 → 서비스명은 SYS_MESSAGE 값, 로고는 sources/frontend/src/assets/ 파일 교체. 소스를 고치지 않는다 — 고치면 프로젝트마다 포크가 되어 템플릿 업데이트를 받을 수 없다 (요건서 §1-1)
화면이 다 섰다(2026-09-04 — 승인 뒤 개발). 표 · 메일 · API 넷 · 3단계 화면이 실물이며 이 목업은 이제 만들 것이 아니라 확인할 것을 그린다 — 위 테스트 케이스 열여섯이 ⑤ 사용자 테스트의 목록이다. 메일은 spring.mail.host 를 두어야 실제로 나간다 — 두지 않은 배포에서는 응답이 같고 서버 로그에만 남는다(요건서 §6-3).
