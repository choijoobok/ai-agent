# 요건 정의서 — 로그인

## 개요

- **무엇을 하는 화면인가**: 아이디와 비밀번호로 인증하고 셸로 들여보낸다. 실패·잠금·휴면을 안내하고, **본인 비밀번호 재설정 3단계**(요청 → 검증 → 완료)의 입구가 된다.
- **프로세스상 위치**: (선행) 관리자가 계정을 만든다(`USER_MGMT`) → **이 화면** → (후행) `mustChangePassword` 면 [비밀번호 강제 변경](../pwd-change/requirements.md), 아니면 셸.
- **바꾸면 어디가 흔들리나**: 결과 코드가 `SYS_LO_LOGIN` 한 행이 되고 그것이 **로그인 이력 화면**(`/log/login`)에 그대로 보인다. 잠금·휴면 해제 경로가 `USER_MGMT` 와 짝이다.

> **이 문서는 `docs/design/60-screen-auth.md` §3 에서 옮겼다**(2026-09-04 · 그 폴더는 폐지됐다). 승인 이력은 그 문서의 것을 잇는다.

> **문서 상태: 구현됨**(2026-09-04 — 승인 뒤 ④ 개발 완료 · §11).
> 로그인도 **재설정 3단계도 서 있다** — `sources/frontend/src/features/auth/`(`LoginPage` ·
> `PasswordResetFlow` · `passwordRules`) · `AuthController` · `PasswordResetService`.
>
> **⑤ 사용자 테스트가 남았다.** 게이트 초록이 그것을 갈음하지 않는다(AGENTS.md §6.3).

## 1. 화면 구성

로그인 폼 하나. 실패 안내는 **폼 상단 한 곳**에 낸다 — 필드마다 흩어 놓지 않는다.

재설정은 **같은 라우트의 단계 전환**이며 로그인 폼의 *비밀번호를 잊으셨나요* 링크가 ①로 보낸다(§6-3).

### 1-1. 로고 · 서비스명은 **교체 지점이다**

이 템플릿을 받은 프로젝트가 **가장 먼저 바꾸는 자리**이므로 어디를 고치는지 문서가 말한다.

| 무엇 | 어디 | 방법 |
|---|---|---|
| 서비스명 | `MSG.LOGIN_*` 메시지 키 | **소스가 아니라 `SYS_MESSAGE` 값**을 바꾼다 — 다국어가 따라온다 |
| 로고 이미지 | `sources/frontend/src/assets/` 의 파일 | **파일을 교체한다.** 컴포넌트를 고치지 않는다 |
| 배경 · 색 | `shared/theme/` 토큰 | 화면이 색을 박지 않는다 |

> **문구를 소스에 박지 않는 규칙이 여기서 값을 한다.** 서비스명이 코드에 있으면 프로젝트마다
> 소스를 포크하게 되고, 그러면 **템플릿 업데이트를 받을 수 없다.**

## 4. 컬럼

### 4-1. 로그인 폼

| 필드 | 라벨 | 타입 | 필수 | 비고 |
|---|---|---|---|---|
| `loginId` | 로그인 ID | `text` | Y | `autocomplete="username"` |
| `password` | 비밀번호 | `password` | Y | `autocomplete="current-password"` |
| — | *비밀번호를 잊으셨나요* | 링크 | — | 재설정 ①로 — §6-3 |

### 4-2. 재설정 단계별 입력

| 단계 | 입력 | 비고 |
|---|---|---|
| ① 요청 | **로그인 ID 하나** | **메일 주소를 받지 않는다** — §6-3 |
| ② 검증 | 인증번호 **6자리** | 재발송 버튼 + 남은 시간 |
| ③ 완료 | 새 비밀번호 · 확인 | 규칙은 [강제 변경 §6-1](../pwd-change/requirements.md) 과 **같다** |

### 4-3. 언어 선택기 — **두지 않는다**

`resolveLang()` 이 **`localStorage` → `navigator.language`** 두 순위로 언어를 정하고
**그 둘이 모든 경우를 닫는다** — 지원 언어가 `ko`·`en` 둘이라 *"ko 로 시작하면 ko, 그 밖은
전부 en"* 이다.

> **처음 접속한 사용자도 자기 브라우저 언어로 본다.** 선택기를 두면 *브라우저가 이미 맞게
> 골라 준 것* 을 다시 묻게 되고, 로그인 뒤에는 `SYS_USER.LOCALE_CD` 가 정본이라 **그 선택이
> 한 번 쓰이고 버려진다.** 언어를 바꾸는 자리는 [설정 모달](../settings/requirements.md)이다.
>
> **지원 언어가 셋 이상이 되면 다시 본다** — 그때는 브라우저 언어가 모든 경우를 닫지 못한다.

## 5. 버튼 · 액션

| 버튼 | API | 비고 |
|---|---|---|
| 로그인 | `POST /api/public/auth/login` | 응답 `{ user, mustChangePassword, menus, permissions }` |
| 인증번호 받기 (①) | `POST /api/public/auth/sendResetCode` | 입력은 **로그인 ID 하나** |
| 인증번호 확인 (②) | `POST /api/public/auth/verifyResetCode` | 미만료 · 미사용 · 시도 한도 내 |
| 변경하고 로그인 (③) | `POST /api/public/auth/saveResetPassword` | **여기서** `LOCK_YN='N'` · `LOGIN_FAIL_CNT=0` |
| (자동) 정책 로드 | `GET /api/public/auth/getPasswordPolicy` | **재설정 진입 시 한 번** — ②의 유효 시간과 ③의 규칙을 같은 응답이 나른다(§7-1) |

**`SYS_API` 시드 대상이 아니다** — `/api/public/**` 은 인가 판정을 받지 않으므로
`generateApiSeed` 가 스캔하지 않는다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

새 비밀번호의 입력 제한은 [비밀번호 강제 변경 §6-1](../pwd-change/requirements.md) **과 같다** —
화면이 셋이지만 규칙은 하나다. 파라미터는 전부 `getPasswordPolicy` 가 내려주며
**화면 코드에 숫자를 박지 않는다.**

| 재설정 고유 검증 | 값 | 설정 키 |
|---|---|---|
| 코드 유효 시간 | **10분** | `sys-config.auth.password.reset.token-valid-minutes` |
| 코드 입력 시도 한도 | **5회** | `sys-config.auth.password.reset.try-limit` |
| 재발송 최소 간격 | **60초** | `sys-config.auth.password.reset.request-cooldown-seconds` |

> **셋 다 이미 `AuthPasswordProps.Reset` 에 있고 `application.yml` 에 값이 있다.**
> 화면이 새로 정할 것이 없다 — **읽어 쓴다.**
>
> **앞의 둘은 화면도 알아야 한다** — ②가 *"10분 동안 유효합니다"* 를 그리고 재발송 타이머를
> 직접 세기 때문이다(§6-3). 그래서 정책 API 가 그 둘을 함께 내려준다(§7-1) — **화면 코드에
> 숫자를 박지 않는다**는 규약이 그 통로를 요구한다.

### 6-2. 영향 테이블

| 언제 | 무엇 |
|---|---|
| 로그인 성공 | `LAST_LOGIN_DTM` 갱신 + `LOGIN_FAIL_CNT=0` |
| 로그인 실패 | `LOGIN_FAIL_CNT` 증가, 임계값에서 `LOCK_YN='Y'` · `LOCK_DTM` |
| **결과가 무엇이든** | `SYS_LO_LOGIN` 에 **한 행** |
| 재설정 ① | `SYS_USER_PWD_RESET` 발급(토큰 **해시**) |
| 재설정 ③ | `SYS_USER` 해시·`PWD_CHG_DTM` + `SYS_USER_PWD_HIST` 적재 + `LOCK_YN='N'`·`LOGIN_FAIL_CNT=0` + 토큰 사용 표시 — **한 트랜잭션** |

### 6-3. 재설정은 3단계다

| 화면 | 입력 | 하는 일 |
|---|---|---|
| **① 요청** | **로그인 ID 하나** | 토큰 생성 · **해시 저장** · 메일 발송. `LOCK_YN` 등을 건드리지 않는다 |
| **② 검증** | 인증번호 6자리 | 해시 일치 · 미만료 · 미사용 · 시도 한도 내 |
| **③ 완료** | 새 비밀번호 | **여기서** `LOCK_YN='N'` · `LOGIN_FAIL_CNT=0` |

**메일 주소를 입력받지 않는다.** 서버가 `SYS_USER` 에서 찾는다 — `SYS_USER_PWD_RESET` 에
메일 컬럼을 두지 않는 것도 같은 이유다. 받으면 ID·메일이 어긋날 때 무엇을 보여줄지가
*"응답은 항상 동일"* 원칙과 충돌한다.

| 항목 | 처리 |
|---|---|
| 발송 응답 | **계정 존재 여부와 무관하게 항상 동일.** 마스킹된 메일 주소도 보여주지 않는다 |
| **시도 횟수** | 틀린 횟수는 **거절과 다른 트랜잭션**에서 센다(`PasswordResetAttempts`) — 같은 트랜잭션에서 세면 거절의 롤백이 그 숫자를 함께 지워 **한도가 조용히 무한**이 된다 |
| 재발송 | **서버는 같은 응답을 주고 타이머는 클라이언트가 표시**한다 — 서버가 *"잠시 후"* 를 알려주면 **존재하는 계정에만 쿨다운이 걸려 ID 열거 단서**가 된다 |
| 잠금 해제 | **③ 완료 시점.** 발송만으로 풀리면 *실패 5회 → 요청 → 리셋 → 다시 5회* 가 무한 반복된다 |
| **메일 발송 실패** | 사용자에게는 **성공과 같은 응답**을 준다(열거 방지). 실패는 **서버 로그에 남기고** 토큰은 **발급된 채 만료를 기다린다** — 지우면 재발송 쿨다운이 무의미해진다 |

### 6-4. 잠김 안내 — **복구 경로를 배너 안에 둔다**

`FAIL_LOCKED` · `FAIL_DORMANT` 는 **경고 배너 본문에 재설정 링크를 넣는다.** 폼 아래의
평소 링크에만 의존하지 않는다.

> **복구 경로가 안 보이면 전부 문의로 간다.** 그리고 문의가 유일한 경로가 되면 **관리자
> 발급이 정상 경로**가 되는데, 그것은 *메일 불가 환경의 유일한 복구 경로* 로 만든 것이지
> 일상 경로가 아니다.
>
> **새 버튼을 만들지 않는다** — 배너 안의 링크다. 버튼을 만들면 *잠긴 사용자만 보는 버튼* 이
> 생기고 그 상태를 따로 그려야 한다.

### 6-5. 예외 화면

| 상황 | 처리 |
|---|---|
| 서버 무응답 · 5xx | 폼 상단 에러 배너. 입력값은 유지하고 **비밀번호만 비운다** |
| 세션이 이미 있는데 `/login` 진입 | 셸로 리다이렉트 |
| 재설정 ② 시도 한도 초과 | **토큰을 즉시 만료**시키고 ①로 되돌린다 |
| 권한 없음 | **해당 없음** — 인증 전 화면이다 |

### 6-6. 상태 전이 — 결과 코드가 화면 문구를 정한다

접근 제어 체인이 **먼저 걸린 코드 하나만** 남긴다. 화면은 그 코드로 안내를 고른다.
**소스의 결과 코드는 열하나다**(`SUCCESS` + `FAIL_*` 열).

| `SYS_LO_LOGIN` 결과 코드 | 화면이 보여주는 것 |
|---|---|
| `SUCCESS` | `mustChangePassword` 면 강제 변경으로, 아니면 셸로 |
| `FAIL_NO_USER` · `FAIL_PWD` | **같은 문구.** 계정 존재 여부를 드러내지 않는다. **남은 횟수를 알려주지 않는다** |
| `FAIL_LOCKED` | 잠김 안내 + **배너 안 재설정 링크**(§6-4) |
| `FAIL_DISABLED` · `FAIL_EXPIRED` | 관리자 문의 안내 |
| `FAIL_DORMANT` | 휴면 안내 + **배너 안 재설정 링크** — 그 흐름이 곧 본인 재인증이며 마치면 휴면이 풀린다 |
| `FAIL_IP` | 허용되지 않은 접속 위치 안내 |
| `FAIL_NO_AUTHORITY` | **권한이 없어 로그인할 수 없다** — 빈 셸로 들여보내지 않는다 |
| `FAIL_TEMP_EXPIRED` | 임시 비밀번호 만료 — 재발급 안내 |
| `FAIL_CONCURRENT` | 동시 접속 제어에 걸렸다 |

> **`FAIL_NO_USER` 와 `FAIL_PWD` 를 같은 문구로 내는 것이 이 화면의 핵심 제약이다.**
> 문구가 갈리면 계정 열거가 가능해진다.
>
> **문구는 서버가 완성해 내려준다.** 화면은 `code` 로 분기하지 않고 받은 `message` 를 그대로
> 배너에 넣는다 — 두 코드를 같은 문구로 유지하는 책임이 **화면이 아니라 서버 한 곳**에
> 있어야 한다. **프론트가 조립하면 언젠가 갈린다.**
>
> **§6-4 의 링크는 예외다** — 문구가 아니라 **배치**이므로 화면이 `code` 로 판단한다.

## 7. API

| 경로 | 메서드 | 무엇 | 지금 |
|---|---|---|---|
| `/api/public/auth/login` | POST | 인증 | **있다** |
| `/api/public/auth/getPasswordPolicy` | **GET** | 규칙 식별자 + 파라미터 + 문구 + 재설정 값 둘 | **있다** |
| `/api/public/auth/sendResetCode` | POST | ① 발송 | **있다** |
| `/api/public/auth/verifyResetCode` | POST | ② 검증 | **있다** |
| `/api/public/auth/saveResetPassword` | POST | ③ 완료 | **있다** |

**이름을 `reset` 으로 묶는다.** 셋이 한 묶음임이 경로만 봐도 보이고, 이미 있는
`/api/service/user/savePasswordReset`(**관리자 임시 비밀번호 발급**)과 **이름이 겹치지 않는다** —
둘은 다른 일이며 겹치면 로그에서 구분되지 않는다.

**정책만 `GET` 인 것이 규약이다** — `common`·`public` 의 조회는 GET, 나머지는 POST.

> **접두 액션 규칙(`get*`→READ · `save*`→SAVE)의 대상이 아니다.** `public` 은 인가 판정을
> 받지 않아 `SYS_API` 시드에 들어가지 않으므로 접두가 권한을 정하지 않는다. **그래도 같은
> 접두를 쓴다** — 규칙이 둘이 되면 어느 쪽인지 매번 확인해야 한다.

### 7-1. 정책 API 응답

```json
{ "rules": [
  { "id": "MIN_LENGTH",    "params": { "min": 9 },   "clientCheckable": true,
    "message": "9자 이상이어야 합니다." },
  { "id": "CHARSET_KINDS", "params": { "kinds": 3 }, "clientCheckable": true,
    "message": "영대문자·영소문자·숫자·특수문자 중 3종 이상을 포함해야 합니다." },
  { "id": "NO_REUSE",      "params": { "count": 3 }, "clientCheckable": false,
    "message": "최근 3개와 같은 비밀번호는 쓸 수 없습니다." }
],
  "reset": { "tokenValidMinutes": 10, "resendCooldownSeconds": 60 } }
```

**같은 응답을 [강제 변경](../pwd-change/requirements.md)과 [프로필](../profile/requirements.md)도
쓴다** — 규칙 목록의 출처가 서버 하나여야 세 화면이 갈리지 않는다. 계약의 상세는
강제 변경 §6-2 가 갖는다.

> **규칙이 셋이다 — 다섯이 아니다.** 강제 변경 §6-1 이 그린 다섯 중 `NO_REPEAT`(연속 문자)와
> `NO_LOGIN_ID`(아이디 포함)는 **서버에 구현도 설정 키도 없고**, 그 설정 키는 강제 변경 §10 에
> **아직 미결**로 남아 있다. `PasswordRules` 가 *"정책이 가진 축은 길이와 문자 종류 둘뿐이며,
> 여기에만 있는 규칙을 더하면 설정으로 끌 수 없는 규칙이 생긴다"* 고 못박은 그 자리다.
>
> **없는 규칙을 목록에 넣는 것이 최악이다.** 화면이 그것으로 체크리스트를 그리면 사용자는
> *지키지 않아도 통과하는 규칙*을 지키게 되고, 서버가 잡아 주지 않으므로 그 사실은 어디서도
> 드러나지 않는다. 규칙이 늘어나는 날 `PasswordPolicies` 에 한 줄이 늘며, **프론트는 모르는
> 식별자를 건너뛰므로** 그 순서로 배포해도 안전하다(강제 변경 §6-2).
>
> **`reset` 두 값이 함께 실린다.** 화면이 ②의 유효 시간을 말하고 재발송 타이머를 직접 세야
> 하는데(§6-3) 숫자를 코드에 박을 수 없기 때문이다. 별도 API 를 두면 재설정 화면 하나가
> 왕복 둘로 열린다.

## 8. 시드 · 데이터 전제

| 무엇 | 지금 |
|---|---|
| `sys-config.auth.password.*`(정책 · `reset.*` 셋) | **있다** — `application.yml` |
| `LOGIN_RESULT` 공통코드 | 있다 |
| 로그인 화면 문구(`MSG` 키) | 있다 |
| **재설정 3단계 문구 + 메일 본문(다국어)** | **있다** — 키는 `008`(생성물), 값 30개×2언어는 `data/107`. **메일 본문도 `SYS_MESSAGE` 키다**(파일 템플릿을 만들지 않았다 — 다국어와 운영 중 수정이 공짜로 따라온다) |
| **`SYS_USER_PWD_RESET` 테이블** | **있다** — `schema/029` |
| **메일 발송 의존성 · 설정** | **있다** — `spring-boot-starter-mail`(bootstrap `runtimeOnly`) · `app.mail.from`. `spring.mail.*` 은 **주석으로 둔다**: 두면 켜지고 두지 않으면 발송만 실패한다(§6-3) |

> **`SYS_USER_PWD_RESET` 을 미리 만들어 두지 않은 것이 규약이다** — *쓰지 않는 DDL 을 미리
> 넣으면 "됐다" 로 보이는데 한 번도 돌아 본 적이 없다.* 이 화면을 만드는 슬라이스가 만든다.

## 9. 테스트 케이스

> **요건이 지켜졌는지 묻는 표다.** 위의 절들이 *무엇을* 정했다면 여기는 *그것이 지켜졌는가* 다.
> **되면 안 되는 것**을 함께 담는다 — 그것이 빠지면 케이스가 그림 검사로 줄어든다.
>
> **목업(`mockup.html`)은 이 표와 위의 절들로부터 생성되는 파생물이다** — 케이스를 목업에서
> 고치지 않는다. 고칠 곳은 여기고, 고친 뒤 `/mockup` 이 목업을 다시 만든다.

### 기본 상태

| # | 조작 · 상황 | 기대 |
|---|---|---|
| `L-01` | 화면 진입 | 입력 필드가 **둘뿐**이다 — **"로그인 상태 유지" 체크박스가 없다** |
| `L-02` | 브라우저 비밀번호 관리자로 자동 채움 | 두 필드가 채워진다 — `autocomplete` 가 명시돼 있다 |
| `L-03` | 로그인 성공 | **API 한 번**으로 `user·mustChangePassword·menus·permissions` 를 받는다. **`/auth/me` 를 뒤이어 부르지 않는다** |
| `L-04` | **잠기지 않은** 기본 상태 | **비밀번호 재설정 링크가 이미 보인다** |

### 실패 상태

| # | 조작 · 상황 | 기대 |
|---|---|---|
| `L-05` | 잠김 + 비활성이 동시에 참인 계정으로 로그인 | **배너가 하나만** 뜬다 — 체인에 **먼저 걸린 코드** |
| `L-06` | 서버 5xx · 무응답 | **별도 문구**. **ID 는 남고 비밀번호만 비워진다** |

| # | 조작 · 상황 | 기대 |

| # | 조작 · 상황 | 기대 |
|---|---|---|
