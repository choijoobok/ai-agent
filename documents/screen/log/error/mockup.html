  1. 15xx 만 이 이 화면의 가장 흔한 조회다. 403 이 압도적으로 많고 그것은 대개 정상 동작이다(권한 없는 사람이 눌렀다) — "고쳐야 할 것" 만 보려면 5xx 다. login-log 의 결과 묶음 과 같은 파생 조건이며 세 번째 사례다(72). number 범위로 두지 않는 이유: 400~499 를 사람이 입력하면 경계를 틀린다.
  2. 2붉은 헤더 셋은 이 화면을 그리다 없는 것이 드러났다(화면 2). 로그 데이터 모델은 "사용 이력과 동일 + ROOT_CAUSE_STACK" 이라고만 적고 있었다 — 2026-08-28 에 로그 데이터 모델으로 들어갔다.
  3. 3[보기] 하나가 탭 둘을 연다(화면 5). PARAMETERS 와 ROOT_CAUSE_STACK 이 둘 다 nclob 이라 목록에 실을 수 없고, 컬럼마다 링크를 두면 사용자가 어느 쪽을 눌러야 하는지 매번 판단한다.
  4. 메뉴 · IP · 순번은 기본 숨김이다(visible: false) — ⚙ 에서 켠다. hidden 컬럼은 없다.

2. 모델이 바뀌었다 — 배타를 없애고 컬럼 셋을 넣는다

  • 로그 데이터 모델의 그림과 백엔드 구현이 서로 다른 모델이었다 — 그림은 한 요청 = ACCESS 1행 + (예외 시) EXCEPTION 1행, 구현은 둘 중 하나 2
  • 중복의 정체가 PARAMETERS(1MB nclob) 하나였다 — 그것만 사용 이력에 두면 중복 회피의 목적이 달성되고 배타가 필요 없어진다
  • HTTP_STAT 이 없으면 403 홍수 속에서 500 을 찾을 수 없다 — 가르는 컬럼이 없으면 드문 쪽이 흔한 쪽에 묻힌다
  • ERR_CD 가 없으면 "같은 오류가 몇 건인가" 를 물을 수 없다 — nclob 스택으로는 정렬도 그룹도 벤더가 막는다(22)
  • ERR_MSG 가 없으면 목록에서 무슨 오류인지 볼 수 없다 — 지금은 스택 안에 묻혀 있다
  • 셋 다 응답이 이미 갖고 있는 값이다 — ApiResponse 의 code · message 와 HTTP 상태
백엔드 구조가 이미 적었다 — "예외의 getMessage() 가 그대로 SYS_LO_EXCEPTION 과 애플리케이션 로그에 남는다 … 코드와 완성된 문구가 함께 남는 것이 운영 대응의 값이다". 적었는데 담을 컬럼이 없었다 1
컬럼타입없으면 무엇을 못 하나
HTTP_STATsmallint 4xx 와 5xx 를 가를 수 없다. 403 과 무관하게 이미 필요했다 — 백엔드 구조가 검증 실패를 400 으로 정했으므로 이 테이블에는 오늘도 4xx 가 있다
ERR_CDVARCHAR(50) 같은 오류를 묶을 수 없다. 403 의 세 갈래도 여기 실린다(화면 3)
ERR_MSGVARCHAR(1000) 목록 컬럼이 되지 않는다. nclob 으로 두면 의 제약을 또 하나 만든다
  1. 1새로 만드는 것이 아니라 버리고 있던 것을 적는다. 셋 다 응답에 이미 있는 값이며, 모델을 고치기 전에는 응답으로만 나가고 이력에 남지 않았다.
  2. 2그림이 옳았고 구현이 따라오지 못한 것이다. 배타였을 때 "이 에러 요청의 전문을 보자" 는 언제나 0건이었고 사용자는 그것을 로그 유실로 읽었다. 대가는 하나 — 전문이 사용 이력에만 있어 보존이 90일 / 180일로 어긋난다(화면 5).
  3. ERR_MSG 를 VARCHAR 로 두는 이유 — 서버가 번역을 완성해 담으므로 파라미터가 치환된 문장이 들어온다. nclob 으로 두면 정렬 불가 · 목록 미적재가 따라온다 — 목록 컬럼으로 쓰려면 VARCHAR 여야 한다. 초과분은 절단한다.
  4. 예외 클래스명 컬럼은 두지 않는다. ERR_CD 가 같은 일을 하며, 클래스명은 리팩터링으로 바뀐다 — 과거 이력과 현재 코드가 어긋난다. 백엔드 구조가 code 를 문자열 상수로 둔 것이 그 대비다.
  5. DDL 이 바뀐다 — 2026-08-28 에 로그 데이터 모델에 반영됐다. 65~67 이 이 테이블을 건드리지 않아 더 모을 사례가 없어 지금 닫았다.

3. 403 이 여기 있다 — 보안 설계가 "구분해 기록한다" 고만 적었다

  • 인가 인터셉터의 거부는 예외로 던져 @RestControllerAdvice 가 받는다
  • 403 은 양쪽 에 남는다 — 사용 이력에 일어난 요청(HTTP_STAT=403 · 전문), 에러 로그에 ERR_CD 로 구분된 원인. 고를 필요가 없어졌다 2
  • 로깅 인터셉터를 인가 인터셉터보다 앞에 등록한다 — preHandle 이 거부해도 이미 true 를 반환한 인터셉터의 afterCompletion 은 호출된다 3
  • 401 은 기록하지 않는다 — 세션 만료는 정상 흐름이고 하트비트마다 쌓이면 에러 로그가 만료 로그가 된다 1

  6. HTTP_STAT 을 공통코드로 두지 않는다 — HTTP 상태 코드는 표준이고 관리자가 늘릴 것이 아니다. 인프라 · 기준정보 데이터 모델과 같은 판단이다.

  1. 1탭 둘을 한 번에 가져온다. 둘 다 nclob 이고, 스택을 보다가 전문을 보는 것이 진단의 기본 동선이다. 탭마다 부르면 왕복이 둘이 되고 두 번째가 실패하면 절반만 열린 모달이 된다.
  2. 24xx 는 스택 탭이 비활성이다 — 비어 있는 것이 아니라 저장하지 않은 것이며 화면이 그 차이를 말한다. 말하지 않으면 "스택이 유실됐다" 로 읽힌다.
  3. 3전문 탭이 로그 화면 설계의 대가를 그대로 받는다. PARAMETERS 는 사용 이력에만 있고 두 테이블의 보존이 90일 / 180일로 다르다. 받아들이는 이유 — ERR_CD · ERR_MSG · 스택이 자기 테이블에 있어 진단이 자립한다. 180일 된 오류에서 필요한 것은 "무엇이 몇 번 났나" 이지 그때 보낸 body 가 아니다. 두 기간을 맞출지는 로그 데이터 모델 미결이다(보관 정책에도 적었다).
  4. 컬럼 계약의 textModal 은 컬럼 하나에 모달 하나를 전제한다 — 여기는 한 행에 둘이다. 컬럼마다 [보기] 를 두면 그리드에 링크 컬럼이 둘 생기고 사용자는 어느 쪽을 눌러야 하는지 매번 판단한다. 로그 화면 설계가 이 사례를 54 로 되돌려 준다.
    그래서 이 모달은 그리드 어휘가 아니다(2026-08-31 정정) — 탭 둘을 담는 화면 컴포넌트이며, textModal 은 아직 자체 구현 대상이다(컬럼 계약 열한째). 이 화면은 그것을 기다리지 않는다.
  5. 읽기 전용이어도 열린다 — "editable: false 가 못 본다를 뜻하지 않는다". 이것이 편집·검증 규약의 거부 메시지가 나오지 않는 유일한 읽기 전용 컬럼이다.

8. 이 목업으로 확인할 것

이 화면이 규약에 되돌려 준 것 — 전부 반영됐다 (2026-08-28)
  • 사용 이력과 에러 로그의 배타를 없앴다 — 로그 데이터 모델의 그림과 백엔드 구현이 서로 다른 모델이었고, 그림이 옳았다. 중복의 정체가 PARAMETERS 하나였으므로 그것만 사용 이력에 두고 배타를 풀었다.
  • SYS_LO_EXCEPTION 에 컬럼 셋이 들어갔다 — HTTP_STAT · ERR_CD · ERR_MSG. HTTP_STAT 은 403 과 무관하게 이미 필요했다(백엔드 구조가 검증 실패를 400 으로 정했다).
  • 403 은 양쪽에 남는다 — 보안 설계의 "구분해 기록한다" 가 ERR_CD 라는 기록처를 얻었고, 셋째 갈래(err.no-authority)가 그 표에 새로 들어갔다.
  • 401 을 빼고 SESSION_TIMEOUT 을 더했다 — 코드 13 → 14. 둘은 한 결정이었다.
  • 로깅 인터셉터가 인가 인터셉터보다 앞이라는 등록 순서가 규약이 됐다.
  • 컬럼 계약에 한 행에 둘 이 더해진다 — 모달 하나 + 탭. 게다가 둘 중 하나는 다른 테이블에 있다(화면 5).
  • 컬럼 계약이 생겼다 — badge 의 색을 정하는 축이 코드 · 묶음 둘이 됐다. 사례 셋이 같은 방향으로 벗어나 있었다(상태 4xx/5xx · 결과 14→3 · 메뉴·권한 화면 설계의 미매핑) — 규약이 좁았던 것이다. 화면은 tone 맵으로 선언하고 맵에 없는 값은 칠하지 않는다.
아직 답이 없는 것
  • 전 요청 기록으로 사용 이력이 얼마나 커지나 — 4xx·5xx 가 더해진다. 2xx 가 압도적이라 미미하다고 보지만 403 이 잦은 조직에서는 다를 수 있다. Docker 필요.
