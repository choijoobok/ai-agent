  1. 1일시가 필수이고 상한이 31일이다. 비워 두면 첫 조회가 90일 전량을 향한다. 상한은 두 층이다 — 시스템 ui.log.range-days.max(92)를 이 화면이 31 로 덮는다. 셋 중 유일하게 행마다 nclob 이 달려 있고 보존이 가장 짧다 — 가장 큰 테이블에 가장 짧은 창.
  2. 2추적 ID 를 넣으면 일시가 선택이 된다. TRACE_ID 에 별도 인덱스가 있어 기간 없이도 인덱스를 탄다. 조건 하나가 다른 조건의 필수 여부를 바꾸는 첫 사례이며 사용자 화면 설계의 파생 조건과 함께 72 프로토콜의 입력이다.
  3. 3쓰는 버튼이 없다 — api.save 도 addRow 도 선언하지 않으므로 저장 · 행 추가 · 상태 컬럼 · 삭제 컬럼이 전부 없다(§4). ⤓ 와 ⚙ 는 남는다 — 하나는 쓰기가 아니고 하나는 개인화다. ⤓ 가 곧 LOG-08 이다(화면 6).
  4. 4USER_ID 가 빌 수 있다 — 미인증 요청은 NULL 이다. 빈칸으로 두지 않는다 — 수집이 안 된 것 과 구분되지 않는다. (익명) 으로 그린다.
  5. 5MENU_CD 도 빌 수 있다(메뉴 목록 미결을 닫는다). 로그인은 셸 진입 전이라 현재 메뉴가 존재하지 않는다. 빈 문자열은 쓸 수 없고 (Oracle 은 '' = NULL) 특수값도 두지 않는다(조인이 비어 같은 처리를 부른다). NULL 을 허용하고 화면이 (메뉴 없음) 으로 그린다. 화면 3.
  6. 6총 건수가 없다(그리드 표준 미결을 닫는다). COUNT 가 한 번 더 나가는데 수천만 행에서 비싸다. 상한 · 근사 · 생략 중 생략을 골랐다 — 상한은 "1000+" 라서 어차피 번호를 못 만들고, 근사는 벤더별 통계 뷰가 달라 무수정 기동이 깨진다(22). 다음 페이지는 size+1 건을 읽어 판정한다.
  7. 8이 화면은 이제 실패한 요청도 보여준다. 이전에는 "성공한 요청 목록"(2xx 만)이었고 지금은 "일어난 요청 전부"다. 요청 전문 로깅 결정이 감사 이력을 요청 전문 로깅으로 대체했는데, 그 대체는 요청 로그가 완전할 때만 성립한다 — "이 사용자가 무엇을 했나" 에 실패한 시도가 빠지면 감사가 되지 않는다. 화면 이름은 바꾸지 않는다 — 사용 이력 은 원래 성공을 뜻하지 않았다.
  8. 9배지는 색 둘이다 — 2xx 는 칠하지 않고 4xx 는 주의색 · 5xx 는 오류색이다. 그리드 표준과 같은 규칙("편집 가능은 칠하지 않는다") — 정상이 압도적인 목록에서는 칠하지 않는 것이 기본값이고 칠한 것만 눈에 남는다. 색은 tone 맵으로 선언한다 — 범위형이며 맵에 없는 값은 칠하지 않는다. 403 행이 여기 있는 것이 요점이다 — 같은 추적 ID(1f9e…-5c08)가 error-log 화면 1 의 넷째 행이며 거기서는 err.no-authority 를 달고 있다. 한 요청이 두 테이블에 한 행씩이고, 그것이 로그 데이터 모델의 그림이다.
  9. 7화면 기본 페이지 사이즈가 100 이다 — 그리드 표준이 "로그는 100" 이라고 예고한 것의 첫 실물이다. 3층(시스템 20 → 화면 100 → 개인 설정) 중 가운데다.

2. 전문은 목록에 없다 — 셀은 값이 아니라 [보기] 다

  • 목록 조회에서 전문 컬럼을 SELECT 하지 않는다 — Oracle LOB 성능(S-2)
  • 앞 N자만 잘라 오는 것은 벤더 중립이 아니다 — SUBSTR · SUBSTRING · DBMS_LOB.SUBSTR
  • 100행 × 1MB = 100MB — 전문 절단 상한이 1MB 다
  • 그래서 미리보기를 두지 않는다 — 파생 컬럼 + link 렌더러 + getDetail

컬럼 필터의 덧붙임 문구는 남는다 — 총 건수가 없어도 이 페이지 안의 분모는 안다: "이 페이지 100건 중 12건"
  1. PK tie-breaker 가 필수다. 여기에는 이유가 하나 더 있다 — allocationSize = 1000 이라 노드마다 다른 블록을 쥔다(세션 스토어 선택형 결정 다중화). PK 순서가 시간 순서가 아니다. 그래서 시각이 먼저고 PK 는 동률만 가른다.
  2. 정렬을 끈 것이 기능을 뺀 것으로 읽히면 안 된다. "사용자별로 정렬해 보고 싶다" 는 조회조건 사용자 가 답한다 — 정렬이 아니라 거르기가 맞는 도구다.
  3. 총 건수와 정렬은 한 결정이다(로그 화면 설계 미결) — 운영에서 다른 컬럼 정렬을 요구하면 커서형을 포기하고 총 건수와 함께 되돌린다. 둘 중 하나만 되돌릴 수 없다.

7. 테스트 케이스 — 주석의 주장을 전부 덮는다

8. 이 목업으로 확인할 것

이 화면이 규약에 되돌려 준 것
  • 그리드 표준의 COUNT 미결이 닫혔다 — 생략이며, 그 대가로 정렬이 일시 하나로 좁혀진다. 푸터 3분할의 예외를 화면이 선언한다(countMode).
  • 메뉴 목록의 MENU_CD NULL 미결이 닫혔다 — 허용하고 (메뉴 없음) 으로 그린다. 백엔드 구조와 로그 데이터 모델에 한 줄씩 들어간다.
  • 로그 데이터 모델의 기본 조회 기간 미결이 닫혔다 — 기간이 필수이고 이 화면만 1일 / 31일이다. ui.log.range-days.default · .max 두 키가 기준정보 데이터 모델에 들어간다.
  • 컬럼 계약에 값이 손에 없는 경우 가 더해진다 — link 렌더러 + getDetail. 그 절은 값이 손에 있다 를 전제했다.
  • 이 테이블이 전 요청을 받게 됐다 — HTTP_STAT 신설. 요청 전문 로깅 결정의 감사 대체 전제가 회복된다 — 실패한 시도가 빠진 요청 로그는 감사가 되지 않는다.
아직 답이 없는 것
  • 기본값 1 · 31 · 92 의 근거가 없다 — 실제 행 수에서 조회가 몇 초인지. Docker 필요.
  • 인덱스를 더 둘지 — 지금은 CRE_DTM · TRACE_ID 둘뿐이다. 읽기는 하루 몇 번, 쓰기는 초당 수십 건이라 균형이 쓰기 쪽에 있다.
  • 전문 모달에 검색을 둘지 — 1MB JSON 에서 키 하나를 찾는다. Ctrl+F 는 가상 스크롤이면 안 걸린다.
  • 다운로드 이력 행을 걸러 낼지 — /api/common/excel/log 가 이 화면에 쌓인다.
  • 전 요청 기록으로 이 테이블이 얼마나 커지나 — 4xx·5xx 가 더해진다. 2xx 가 압도적이라 미미하다고 보지만 403 이 잦은 조직에서는 다를 수 있다.
