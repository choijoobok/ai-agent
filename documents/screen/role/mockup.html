  1. 1기본정보 탭이 컬럼이 되었다 — 그리드 표준이 편집 폼을 두지 않기로 했으므로 역할명·설명·사용 여부가 전부 마스터 그리드의 셀이다. 메뉴 목록이 "62 착수 시 함께 정리한다" 며 남긴 자리를 이것이 닫는다.
  2. 2하단은 탭이 아니라 pane 하나다 — 메뉴 목록의 탭 셋이 하나로 준다(§2). 탭 하나짜리 탭바는 누를 곳이 없는 크롬이며, 사용자 화면 설계가 예외 목록을 하단 pane 으로 둔 것과 같은 판단이다.
  3. 3하단은 읽기 전용이다 — 부여를 고치는 곳은 USER_MGMT 의 보유 역할 탭(사용자 화면 설계 탭 1)이다. 메뉴·권한 화면 설계의 영향 인원과 같은 컴포넌트이고 API 도 같다(§6).
  4. 4②(엑셀)이 없다 — 메뉴 목록의 액션 열이 R S 다. EXPORT 가 없는 두 번째 화면이며 첫째는 role-auth 다.
  5. 5USE_YN 은 스위치다 — 값이 둘인 데이터 칸은 전부 스위치다. 끄면 보유자 전원이 바뀌므로 저장 확인이 세 줄이 된다(§5).
  6. 6축은 상하다(그리드 표준의 기본값) — 마스터 컬럼이 일곱이라 좌우로 나누면 가로가 모자란다. role-auth 가 좌우인 것은 트리가 좁기 때문이며, 축은 데이터가 정하지 취향이 정하지 않는다.
  7. 7파생 컬럼 셋 — 나열은 못 해도 세는 것은 된다. 사용자 화면 설계가 역할 나열 컬럼을 기각한 것은 문자열 집계가 벤더마다 다르기 때문이다(LISTAGG · GROUP_CONCAT · string_agg). COUNT 에는 그 문제가 없어 컬럼으로 둔다.
  8. 8삭제 컬럼이 있다 — 사용자 화면 설계의 사용자 그리드와 갈리는 자리다. SYS_USER 는 물리 삭제를 하지 않지만 역할은 지울 수 있다(§4).
  9. 9조회조건 사용 여부 기본값이 전체 다 — 끈 역할을 감추면 같은 것을 또 만들고, 그때 ROLE_ID 가 PK 라 저장이 실패한다. 운영자는 "왜 저장이 안 되나" 만 본다.
  10. 10순서를 사람이 정하지 않는다 — SYS_ROLE 에 SORT_NO 가 없다(2026-08-27). 소비처가 이 그리드 하나였는데 그리드는 헤더 정렬을 이미 갖는다.
    SYS_MENU 는 순서가 곧 구조라 드래그로 정하고, SYS_CODE 는 콤보에 의미 순서가 있어 정한다. 역할의 자연스러운 순서 는 권한 범위 순인데 그것이 정확히 보안 설계가 금지한 오해다 — 그래서 정하지 않는다.
    기본 정렬은 ORDER BY ROLE_NM, ROLE_ID 다(tie-breaker).
  11. 11ROLE_ID 는 저장 후 편집할 수 없다 — 기존 행에서는 읽기 전용이고 신규 행에서만 편집 가능하다(§3). 그래서 헤더는 필수(*) 인데 셀은 회색이며 어긋나는 것이 정상이다 — 헤더는 컬럼 선언을, 셀 배경은 그 행의 실제 상태를 말한다.
  12. 부여 상태 셋을 구분 표시한다 — 예정 · 유효 · 만료(AUTHZ-13). 만료도 보여준다 — 지금은 영향이 없지만 다시 유효해질 수 있다.
  13. 브레드크럼 줄의 오른쪽은 화면이 채운다. [조건 ▾] 은 저장된 조회조건 (UX-07) — 열면 조회, 고르면 적용, ✕ 가 삭제, 맨 아래가 저장이다. 넷을 버튼 넷으로 두지 않는다 — 조회·적용은 이미 제스처다. [⌃ 조회조건] 은 검색 폼 접기 토글(UX-15)이며 폼 밖에 있어야 한다 — 숨기는 버튼이 폼 안에 있으면 숨긴 뒤 되돌릴 수 없다. 리프 목업이 셸 크롬을 그리지 않는 규약의 유일한 예외가 이 줄이다.
  14. 검색 폼에 조회·검색 버튼이 없다. 그리드 ①이 이미 조회를 갖는다 — 폼에도 두면 같은 조회를 부르는 버튼이 둘이 된다. 남는 것은 초기화 하나이며 컬럼 필터도 함께 지운다. Enter 는 남는다 — 버튼을 없앤 것이지 제스처를 없앤 것이 아니다.
  15. 그리드 헤더의 버튼은 전부 오른쪽이다 — 왼쪽은 제목뿐이고 도구 둘(⤓ ⚙)은 맨 오른쪽 고정이다.

  1. 1셋째가 둘째와 같다 — 나누면 같은 조회를 두 번 하고 두 탭이 항상 같은 내용을 보여준다. 사용자는 둘의 차이를 찾느라 시간을 쓴다.
  2. 2제목만 다르다. 보는 시점이 다를 뿐 질문은 하나다 — "이 역할을 가진 사람이 누구인가". 그것이 AUTHZ-13 역방향 권한 조회다.
  3. 3API 를 새로 만들지 않는다 — role/getUserList 를 따로 두면 같은 질문에 답이 둘이 된다. SYS_MENU_API 에 ROLE_MGMT 행이 하나 더 붙을 뿐이다(매핑은 다대다다).
  4. 4탭이 하나면 탭 크롬을 두지 않는다. 사용자 화면 설계가 예외 목록을 "탭이 아니라 하단 pane" 으로 둔 것과 같다 — 규칙이 하나면 기억할 것이 없다.

  1. 1defaults 만 선언한다. canAdd 는 막을 이유가 없어 적지 않았다 — 건수 상한도, 선행 저장도, 상태 의존도 없다. onAdd 도 없다 — 편집 진입은 컴포넌트가 한다. 옵션 넷을 다 쓰는 것이 기본이 아니다 — 필요 없는 화면이 적지 않는 것이 선언이 곧 허용 이라는 뜻을 지킨다.
  2. 2defaults 는 하나뿐이다 — useYn:'Y'(켜 두는 것이 정상이다). 순서는 사람이 정하지 않으므로 채울 것이 이것뿐이다(§1 주석 10). 옵션을 적게 쓰는 것이 흠이 아니다.
  3. 3ROLE_ID · ROLE_NM 은 채우지 않는다 — 사람이 정해야 하는 값에 기본값을 넣으면 "그대로 저장" 이 된다.
  4. 4ROLE_ID 는 신규 행에서만 편집 가능하다 — 그래서 여기서만 필수 바탕(--req-bg)이 아니라 편집 중으로 열려 있다. 저장된 행에서는 읽기 전용이다(§1).
  5. 5새 행은 맨 위에 붙고 정렬·필터를 타지 않는다 — 값이 비어 있어 필터에 걸리면 방금 만든 행이 사라지는데 그것이 사고다.
  6. 6신규 행을 고르면 하단이 잠긴다 — SYS_USER_ROLE 이 SYS_ROLE 을 FK 로 참조하므로 부모가 저장되기 전에는 자식이 있을 수 없다. 사용자 화면 설계와 같은 구조다. 비활성되는 것은 버튼이지 pane 이 아니다 — 자리는 남고 안내가 뜬다.
  7. 7신규 행의 삭제는 항상 가능하다 — 서버에 없으므로 즉시 제거이며 FK 게이트(§4)를 타지 않는다.
  8. 8건수 컬럼 셋은 — 다 — 읽기 전용이고 서버가 센다. 0 으로 채우면 "세어 보니 0" 과 구분되지 않는다.
  9. 9SAVE 권한이 없으면 셋이 함께 사라진다 — 행 추가 · 저장 · 삭제 컬럼. 추가한 행은 저장으로만 서버에 가므로 나갈 곳이 없는 버튼이다. 감추지 비활성으로 남기지 않는다.

  1. 1마스터의 건수 컬럼이 디테일의 자리를 대신한다 — 자식이 화면에 없어도 게이트가 닫힌다. 조회 응답이 이미 갖고 있으므로 왕복이 늘지 않는다. 이 줄을 그리드 표준으로 올렸다.
  2. 2막는 것은 보유 인원이지 유효 인원이 아니다. 만료된 부여도 SYS_USER_ROLE 행이며 FK 는 날짜를 보지 않는다. ROLE_TEMP_2025 는 유효 0 인데 막히고, 그것이 정상이다 — 그래서 컬럼을 둘 다 둔다.
  3. 3왜 막히는지 말한다. 회색 버튼은 이유를 말하지 못하고 사용자는 화면이 고장난 줄 안다 canAdd 와 같은 방향이다. 대안까지 말한다 — "사용 여부를 끄세요"(§5).
  4. 4다중 선택 삭제가 없다 — 하단은 선택된 한 행에 대해서만 조회되므로 나머지 행은 자식 유무를 모른다.
  5. 5동시성으로 뚫릴 수 있다. 게이트가 앞서 막지만 판정과 저장 사이에 누가 부여를 만들 수 있다 — 그때는 저장 실패 모달이다. 화면이 미리 막는 것은 저장 시점의 실패를 조회 시점에 알리는 일이지 보증이 아니다.
  6. 6게이트를 통과하는 역할은 한 번도 쓰이지 않은 것뿐이다 — 그것이 정확히 "잘못 만든 역할" 이다. 쓰인 역할을 지우는 길은 없고 그것이 의도다 — 지우면 누가 무슨 역할을 가졌었나 가 사라진다.

5. USE_YN 을 끄면 — 확인이 세 줄이 된다

저장 확인✕

역할 1건을 수정합니다.

'운영자' 를 미사용으로 바꾸면 47명의 유효 권한에서 이 역할의 권한 34건이 빠집니다.

그중 2명은 유효 권한이 공집합이 되어 다음 로그인부터 차단됩니다.

부여 행과 권한 행은 지워지지 않는다 — 다시 켜면 살아난다

권한 행 (SYS_ROLE_MENU_AUTH)남는다〃

언제 쓰나거의 항상 이쪽한 번도 쓰이지 않은 역할
  1. 1메뉴·권한 화면 설계와 같은 컴포넌트다. 거기서는 권한을 고칠 때 나오고 여기서는 스위치 하나가 낸다. screen/README.md 의 AUTHZ-02 가 "비활성화는 보유자 전원의 유효 권한을 바꾼다 — 영향 인원 표시 필수" 라고 요구한 것이다.
  2. 2셋째 줄이 보안 설계가 요구한 것이다 — "공집합이 되는 인원은 다음 로그인부터 차단되므로 관리자가 모르고 지나가면 안 된다." 공집합 인원이 0 이면 그 줄을 내지 않는다 — 항상 보이면 읽히지 않는다.
  3. 3끄는 변경이 있을 때만 둘째·셋째 줄이 붙는다. 이름만 고친 저장은 한 줄이다(그리드 API 계약의 기본 문구).
  4. 4켜는 방향에는 경고가 없다 — 권한이 늘어나는 것은 되돌릴 수 있다. 경고를 양쪽에 두면 읽지 않게 된다.
  5. 5USE_YN 은 입력 필터다 — 유효 권한 계산 순서 ②에서 걸러진다. 메뉴의 USE_YN 은 최종 게이트여서 자리가 다르다(AUTHZ-01).
  6. 6역할에는 기간이 없다 — 계정을 못 쓰게 하는 축이 넷인 것과 달리 여기는 USE_YN 하나다. 기간은 부여에 있지 역할에 있지 않다.

8. 이 목업으로 확인할 것

결정된 것이 아니라 미결이다. 결정은 메뉴·권한 화면 설계의 표에 있다.
  • ROLE_ID 를 사람이 정한다 — PK 가 손으로 입력하는 문자열이다. 관례(ROLE_*)를 검증으로 강제할지 안내만 할지. 강제하면 기존 시스템에서 넘어온 코드를 넣을 수 없다
  • 건수 컬럼의 비용 — 목록 조회마다 자식 둘을 센다. 역할이 수십 건이라 문제없다고 보지만 인원이 수만 명일 때 어떤지 — 실측
  • 최후의 관리자 보호 — 관리자 역할을 끄면 아무도 들어올 수 없게 될 수 있다. 사용자 · 메뉴·권한 화면 설계의 같은 미결과 한 결정이며, 여기서는 스위치 하나가 그 경로를 연다는 것이 새로 드러난 부분이다
  • 하단 pane 의 규모 — 보유 사용자가 수천 명인 역할에서 페이징이 버티는지 (메뉴·권한 화면 설계의 영향 인원의 규모 와 같은 실측이다)
결정하면 문서 표에 적는다. 이 파일이 아니라.
