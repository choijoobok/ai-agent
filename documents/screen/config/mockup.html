  1. 1분류 컬럼이 없으니 검색으로 찾는다. CFG_GRP_CD 를 두지 않은 이유는 "설정 하나는 한 영역에만 속한다" 가 참이 아니기 때문이다 — deny-empty-authority 는 인증이면서 랜딩 정책이다. 한 칸이 키와 설명을 함께 건다.
  2. 2적용값이 이 화면의 유일한 입력 칸이다. SYS_CONFIG 행이 없으면 기본값을 복사해 보여주고, 고치면 그때 행이 생긴다. 값이 다르면 굵게 + 변경됨.
  3. 3값이 기본값과 같은데 배지가 붙은 행이 있다. 배지의 근거는 값이 다른가 가 아니라 SYS_CONFIG 행이 있는가다 — 같은 값으로 저장해 두면 다음 배포가 yml 기본값을 올려도 그 키만 옛 값에 묶인다. 눈으로는 구분되지 않으므로 배지가 유일한 신호다.
  4. 4행 추가가 없다. 아우터 조인의 왼쪽에 없는 키를 넣으면 아무 데도 읽히지 않는 행이 생긴다 — 저장은 되고 동작하지 않는 가장 나쁜 실패다. addRow 를 선언하지 않는다.
  5. 5삭제 컬럼의 헤더가 되돌리기 다. 행을 지우면 값이 사라지는 것이 아니라 yml 이 드러난다 — 라벨이 삭제 면 값이 사라질 것을 기대하고, 같은 키가 남으면 버그로 읽힌다. 변경됨 인 행만 체크할 수 있다.
  6. 60 이 끔 인 키가 있다. 설명이 그것을 말하고 화면이 0 을 막지 않는다 — 상한도 강제하지 않는다 (3회를 원하는 조직이 막힌다 — 01 P9).
  7. 7끄면 잠긴 계정을 풀 수 없는 키가 있다. 저장 전 확인을 띄운다 — 되돌릴 수는 있지만 되돌릴 사람이 못 들어올 수 있다(화면 5).
  8. 유형도 설명도 읽기 전용이다 — 유형은 필드 타입, 설명은 필드 Javadoc 이다. 설명을 편집하게 두면 값을 안 바꿨는데 오버라이드 행이 생긴다 — 화면 3.
  9. 기본값 컬럼을 숨기지 않는다. 되돌리면 무엇이 되는지가 행마다 보여야 화면 4 의 확인이 놀라움을 주지 않는다.

2. 층은 둘, 메커니즘도 둘 — 목록은 아우터 조인

yml 이 정한 키 목록   LEFT OUTER JOIN   SYS_CONFIG   ON key

기본값 = yml 값                                ← 언제나 있다
적용값 = COALESCE(SYS_CONFIG.CFG_VAL, 기본값)   ← 행이 없으면 기본값을 복사한다
행 수는 설정 키 수로 고정이며 SYS_CONFIG 의 행 수와 무관하다. 오른쪽이 비어 있는 것이 정상이고, 그 비어 있음은 값이 없다 가 아니라 아무도 안 바꿨다 를 뜻한다
층어디역할
yml배포 산출물 (프로필 포함) 기본값. 모든 설정 키가 여기에 값을 갖는다
SYS_CONFIGDB 적용값의 오버라이드. 행이 있으면 이 값이 이긴다
 
기동   : yml → @ConfigurationProperties 바인딩 → 검증   ← SYS_CONFIG 가 없다
런타임 : 유틸이 그 위에 SYS_CONFIG 를 덮어 다시 바인딩      ← 유틸만 안다
층이 둘이면 메커니즘도 둘이다. SYS_CONFIG 는 프로퍼티 소스가 아니다 — 섞으면 yml 누락이 DB 행에 가려지고, 읽는 시점이 기동 한 번이라 런타임 변경(MASTER-08)이 성립하지 않는다 3
  1. 1이전 판은 층이 셋이었다(필드 초기값 → yml → SYS_CONFIG). 셋째 층의 명분은 "yml·DB 가 모두 비어도 동작한다" 였는데 그렇게 동작하는 것이 문제였다 — 키를 추가하고 yml 을 빠뜨려도 아무 일도 일어나지 않고 하드코딩 값이 쓰인다. 층을 줄이면 그 누락이 기동 실패가 된다(원칙 P1 · 2026-08-28 개정).
  2. 원시 타입을 쓰지 않는다. int 는 yml 이 비면 조용히 0, boolean 은 false 가 된다 — admin-reset-enabled 가 그렇게 꺼지면 사고가 소리 없이 난다. 래퍼 타입 + @NotNull 이라야 전부 기동에서 걸린다.
  3. 3환경변수가 있어도 화면에서 바꾼 값이 이긴다 — 근거는 프로퍼티 소스 순서 가 아니라 유틸이 마지막에 덮는다 는 것이다. 순서로 지켜야 했을 것을 구조가 지킨다.
  4. 고아 키는 읽을 경로가 없다. 유틸의 키 집합이 곧 필드 집합이므로, 필드를 지운 뒤 남은 행은 무시된다 — 정리 배치도 경고도 두지 않는다. 롤백하면 무시되고 롤포워드하면 되살아난다.
  5. yml 은 루트 키 sys-config 아래에 모은다. CFG_KEY 는 루트를 뺀 나머지이며 화면에 보이는 키가 그것이다 — 루트를 넣으면 접두사 콤보의 첫 마디가 전부 같아진다(§6). 루트의 값은 빌드 검사의 범위를 확정하는 것이다 — "sys-config 아래 모든 yml 키는 필드가 있어야 한다", 없으면 빌드 실패.
  6. 메뉴·권한 화면 설계의 미등록 과 같은 구조인데 답이 다르다. API 카탈로그는 없는 행을 낼 수 없어 빈 상태가 진단이 됐다. 여기는 왼쪽 테이블이 코드에 있어서 낼 수 있다 — 차이는 후보 집합을 아는가다.

직접 주입 막는다. props 클래스를 빈으로 등록하지 않으므로 @Autowired 가 기동에서 죽는다 4
  1. 1경계는 요청이 아니라 작업이다. 캐시 전략 결정이 요청을 든 것은 요청이 특별해서가 아니라 "한 덩어리 일 안에서 값이 바뀌면 안 된다" 를 말하려던 것이며, 배치가 10만 건을 도는 도중에 바뀌어도 같은 사고다. 가장 오래 도는 일은 요청이 아니다.
  2. 2오래 도는 작업이 낡은 값에 묶이는 것은 버그가 아니라 의도다 — 캐시 전략 결정이 원한 일관성이 그것이다. 반영하려면 작업을 다시 돌린다.
  3. 3대가는 화면을 안 거친 값이 검증을 만나는 것이다. UPDATE … SET CFG_VAL='-1' 은 @Min(0) 위반인데 화면을 안 거쳤으니 아무도 안 막았고, 터지는 것은 넣은 순간이 아니라 다음 작업이며 죽는 것은 넣은 사람이 아니다. 그래서 기동 시 예행 바인딩으로 전량을 한 번 얹어 보고, 런타임 실패는 예외로 낸다 — 그 키만 yml 로 되돌리면 화면은 변경됨 인데 동작은 기본값인, 이 설계가 닫으려는 바로 그 실패가 된다. 이 테이블의 쓰기 경로는 관리 화면 하나이며 SQL 직접 수정은 비지원이다.
  4. 4유틸을 안 거치면 yml 값이 나온다 — 화면은 변경됨 이라 말하는데 동작은 안 바뀐다. 주입할 빈이 없으면 그 경로가 아예 없다.

3. 왼쪽 테이블은 어떻게 나오나 — 키 · 유형 · 설명

private Integer failLimit; 만 보면 키를 알 수 없다 — 앞 절반은 클래스에 있다
@ConfigurationProperties(prefix = "sys-config.auth.login")  ← 키의 앞 절반
@Validated
public class AuthLoginProps {
    /** 로그인 연속 실패 허용 횟수. 0 이면 잠금을 끈다. */  ← 설명
    @NotNull @Min(0) private Integer failLimit;   ← 뒷 절반 · 초기화식이 없다
}
CFG_KEY 는 루트를 뺀 auth.login.fail-limit
sys-config:            ← 시스템 설정은 전부 이 루트 아래
  auth:
    login:
      fail-limit: 5    ← 기본값은 여기에만 있다
화면의 무엇어디서 나오나
키 목록 · 유형 @ConfigurationProperties 클래스 스캔 — prefix + 필드명에서 루트를 뺀 것 → auth.login.fail-limit. camelCase → kebab-case 는 완화 바인딩의 정규 표기다. 중첩 객체는 재귀한다 1
설명META-INF/spring-configuration-metadata.json — 필드 Javadoc 2
기본값Environment 유효값 — 프로필 yml·환경변수까지 포함한 배포가 정한 값. SYS_CONFIG 가 프로퍼티 소스가 아니므로 뺄 것이 없다
적용값SYS_CONFIG 행이 있으면 그 값, 없으면 기본값
  1. 1빈 목록에서 찾지 않는다. props 클래스는 빈으로 등록되지 않으므로(§2) getBeansWithAnnotation 이 아무것도 돌려주지 않는다. 애노테이션 스캔이며, 그래서 등록 목록을 따로 관리하지 않는다 — 빠뜨릴 목록이 없다. 화면은 인스턴스를 만들지 않는다 — 층이 셋이던 판은 기본값을 읽으려고 new AuthLoginProps() 를 만들었고 그 때문에 JavaBean 바인딩을 강제해야 했다. 층이 둘이 되면서 그 제약이 통째로 사라진다 — record 로 써도 된다. 값을 실제로 쓰는 쪽은 유틸이 Binder 로 만든다(§2).
  2. 2설명은 CFG_DESC 에서 올 수 없다. 오른쪽이 비어 있는 것이 정상이라 안 바꾼 키는 설명도 없고, 채우려고 편집하면 값을 안 바꿨는데 그 키가 변경됨 이 된다. spring-boot-configuration-processor 가 필드 Javadoc 을 컴파일 시점에 뽑아 둔다(20) — 접두 액션 · 시드 생성 결정이 @Operation 을 재사용한 것과 같은 모양이다.
  3. 메타데이터의 defaultValue 는 쓰지 않는다 — 기본값의 원천은 yml 하나이고, 프로세서의 추출은 best-effort 이며 프로필을 반영하지 못한다.
  4. 그래서 SYS_CONFIG 에 남는 것은 오버라이드뿐이다 — CFG_TYPE_CD(필드 타입) · CFG_DESC(Javadoc) · SYS_YN(두 층 폴백)이 전부 지킬 것을 잃는다. 남는 것은 CFG_KEY · CFG_VAL · 감사 4컬럼. 컬럼을 지우는 것은 기준정보 데이터 모델의 일이라 기준정보 화면 설계 미결로 올렸다.
  5. 스칼라만 목록에 낸다. Map · List 프로퍼티는 맵의 키가 곧 프로퍼티 이름이라 키가 하나로 고정되지 않는다. 컬렉션이 필요하면 JSON 문자열 한 칸으로 선언한다(인프라 데이터 모델이 쓰는 방식).

  2. 2상호 제약은 화면이 알 수 없다 — 다른 행의 값을 봐야 판정된다. 메뉴·권한 화면 설계가 "둘 다 다른 행을 봐야 판정되므로 DB 제약이 아니다" 라고 한 것과 같은 모양이며, 여기서는 서버가 받는다.
  3. 3되돌릴 수는 있지만 되돌릴 사람이 못 들어올 수 있다. 메뉴·권한 화면 설계가 "되돌리기가 안 되니까 묻는다" 고 한 것의 변형이다 — 여기서는 되돌리기가 안 되는 것이 아니라 닿을 수 없는 것이다.

9. 이 목업으로 확인할 것

이 화면이 정한 것
  • 층을 둘로 줄였다(2026-08-28) — yml 이 기본값이고 필드 초기화식을 쓰지 않는다. 셋째 층의 명분이던 "yml 이 비어도 동작한다" 가 누락을 조용하게 만드는 것이었고, 층을 줄이니 그 누락이 기동 실패가 된다.
  • 화면이 아우터 조인이 된다(§2) — 컬럼 둘(기본값 · 적용값)로 족하고 출처 라는 개념이 사라졌다. 남은 신호는 변경됨 하나다.
  • 인스턴스를 만들 필요가 없어졌다(§3 주석 1) — record 를 금지하던 JavaBean 바인딩 제약이 통째로 사라졌다.
  • SYS_CONFIG 를 프로퍼티 소스에서 뺐다(§2 · 2026-08-28) — 층이 둘이면 메커니즘도 둘이다. 겹쳐 두면 yml 누락이 DB 행에 가려지고, 읽는 시점이 기동 한 번이라 런타임 변경이 성립하지 않는다. 고아 키는 읽을 경로가 없어져 정리 배치도 경고도 필요 없다.
  • 경계는 요청이 아니라 작업이다(캐시 전략 결정 개정) — 스케줄러·비동기까지 한 유틸로 덮고, 경계는 MDC 가 이미 붙는 자리 셋에서 연다.
  • 루트 키 sys-config — 빌드 검사의 범위를 확정한다. CFG_KEY 는 루트를 뺀 나머지다.
  • 삭제가 아니라 되돌리기(§4) — 행이 사라지지 않고 yml 이 드러난다.
아직 답이 없는 것
  • SYS_CONFIG 에서 컬럼 셋이 죽는다 — CFG_TYPE_CD(필드 타입) · CFG_DESC(필드 Javadoc)는 원천이 코드로 옮겨갔고(§3), SYS_YN 은 두 층 폴백 때문에 지킬 것이 없다. 남는 것은 CFG_KEY · CFG_VAL · 감사 4컬럼 — 컬럼을 지우는 것은 기준정보 데이터 모델의 일이다.
  • 런타임 반영의 시점은 정해졌다 — 다음 작업부터다. 남은 것은 오래 도는 작업이다 — 몇 시간짜리 배치는 끝까지 옛 값을 쓰고, 반영하려면 작업을 다시 돌려야 한다. 그것으로 충분한지는 실물에서 본다.
  • 재바인딩 비용의 실측 — 작업마다 클래스를 다시 만들고 검증을 다시 돈다. 키가 19개인 지금은 문제가 아니지만 어디부터 문제인지는 재보지 않았다.
  • JSON 유형의 편집 — 1000자 문자열을 한 줄 입력으로 두면 못 쓴다. largeText 로 갈지 미정이다.
