# 요건 정의서 — 실행 제한·운영 설정

## 개요

- **무엇을 하는 화면인가**: REQ-614의 운영 설정에서 REQ-601에 정의한 업무별 관리 승인 절차 사용 여부를 독립 설정한다. 현재 값·변경 전후·사유·처리자·시각과 각 처리에 적용한 설정 버전을 조회한다. 화면 요건서·목업은 P3에서 정의한다
- **프로세스상 위치**: 관련 자산·정책 확인 → 이 화면의 조회·입력 → 소유 업무의 검증·반영 또는 전용 요청 화면.
- **이 데이터를 누가 쓰나**: 연결된 관리 업무와 agent의 현재 권한 검증 및 실행 기록.
- **바꾸면 어디가 흔들리나**: REQ-614·REQ-601와 연결된 참조·승인·이력. 정본은 documents/spec이며 이 문서는 화면 검토 초안이다.

## 1. 화면 구성

조회조건 → 상단 실행 제한·운영 설정 목록 → 상하 스플리터 → 하단 업무별 승인 설정·배포 설정 조회·적용 관측.
1:1 값은 상단 컬럼, 1:N 집합은 하단 탭으로 표시한다. 장문은 셀 뷰어를 쓴다.
제목·건수는 왼쪽, 작업 버튼은 오른쪽에 정렬한다. 초기 화면의 모든 탭은 실제 전환되며 같은 대상의 입력·선택을 유지한다.
초기 목업은 한 대상 선택 예시이며 실제 목록 조회 후 행은 자동 선택하지 않는다.
상태별 버튼: 허용 목록

### 1-1. 마스터-디테일 연동

- 대상 안정 식별자와 읽은 문맥/기준 버전으로 전체 구성을 확보한다. 탭의 행과 상위 대상을 섞지 않는다.
- 다른 대상 선택·재조회·화면 이탈은 미저장 입력 확인 후 수행하며 같은 대상 탭 이동은 입력을 유지한다.
- 조회 실패·부분 목록·접힌 탭을 삭제나 빈 전체 집합으로 해석하지 않는다. 처리 중 중복 명령을 막고 결과 불명은 원 키로 확인한다.

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

현재 적용된 최종 관리 구성과 현재 권한 범위를 조회한다. 초안·제출·반려본을 운영 목록에 섞지 않는다.
물리 테이블·결합 키의 신규 상세 설계는 후속이다. 다른 소유의 관측·역참조는 읽기 전용이며 저장 사본에 포함하지 않는다.

### 3-2. 고정 조건 · 기본 정렬

현재 유효 조회 권한과 대상 범위를 적용한다. 표시명과 안정 식별자로 동일 이름을 구별한다. 정확 정렬/페이징 계약은 후속 상세 설계한다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

- system 저장소를 복제하지 않는다. 이 화면은 admin 운영 설정의 허용 편집과 읽기 전용 원천 참조 경계를 따른다.
- 턴 전체 시간·누적 토큰 강제 종료 상한을 설정으로 추가하지 않는다. 스텝·개별 호출·동시 턴 한도와 구별한다.
- 승인 설정 읽기 실패는 사용으로 판정한다. 현재 권한·참조·요청/감사 저장도 실패하면 접수하지 않는다. 설정 복구/미사용 전환으로 대기 요청 자동 승인 금지.
- 설정마다 적용 시점이 다르며 저장값을 진행 중 턴/고정 호출에 일괄 덮어쓰지 않는다. 미지원 키·자료형·범위·상호 제약 위반은 반영하지 않는다.

### 6-2. 영향 테이블

물리 테이블을 새로 확정하지 않는다. 소유 업무 구성·처리 근거·적용 이력을 기존 정본의 같은 반영 단위로 다룬다. 실패 시 부분 반영·부분 권한 변경을 남기지 않는다. 조회 전용 동작은 변경 없음.

### 6-3. 상태 전이

조회 전용은 상태 변경 없음. 관리 변경은 해당 요구사항의 적용 시점과 상태 전이를 따르며 저장 성공과 외부 실행·배포 성공을 혼동하지 않는다.

## 7. API

신규 물리/API 상세 설계는 이번 범위 밖이다. 이미 정해진 기능·화면·공통 승인 계약을 참조하고 새로운 경로·메서드·요청 DTO는 정하지 않는다. 실행 당시 정확 버전 기록과 현재 권한 검사는 유지한다.

## 8. 시드 · 데이터 전제

메뉴/경로는 화면 정본의 검토안이다. 이번 작업에서 메뉴·메시지·공통코드 시드나 제품 sources/를 변경하지 않는다. 미정 코드/메시지 키는 화면 합의 후 상세 설계한다.
