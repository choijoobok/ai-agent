# 요건 정의서 — 업무 도구 변경 요청

## 개요

- **무엇을 하는 화면인가**: 조회조건·상단 요청 마스터 그리드·선택 요청의 하단 탭으로 구성한다. 원 관리 화면의 소유 업무 컬럼/탭을 재사용하고 요청번호·요청자/일시·상태·처리자/일시·사유·자기 기준/결과 리비전과 처리 영역을 추가한다. 요청일시 범위·처리 상태·요청자 조건을 제공하고 원 관리 화면의 업무 조건도 요청 스냅샷 값에 적용한다. 제출본은 읽기 전용이며 초안만 허용 상태/권한에서 보완한다. 원 관리 화면이 단일 그리드이면 업무 컬럼과 요청정보를 요청 목록에서 확인하며 존재하지 않는 하단 탭을 추가하지 않는다. 원 화면이 마스터/탭형이면 요청 마스터와 당시 소유 자식 탭을 재사용한다.
- **프로세스상 위치**: 관련 자산·정책 확인 → 이 화면의 조회·입력 → 소유 업무의 검증·반영 또는 전용 요청 화면.
- **이 데이터를 누가 쓰나**: 연결된 관리 업무와 agent의 현재 권한 검증 및 실행 기록.
- **바꾸면 어디가 흔들리나**: REQ-601·REQ-305·REQ-306와 연결된 참조·승인·이력. 정본은 documents/spec이며 이 문서는 화면 검토 초안이다.

## 1. 화면 구성

조회조건 → 상단 업무 도구 변경 요청 목록 → 상하 스플리터 → 하단 전체 변경 대상·요청 처리·연결 지식.
1:1 값은 상단 컬럼, 1:N 집합은 하단 탭으로 표시한다. 장문은 셀 뷰어를 쓴다.
제목·건수는 왼쪽, 작업 버튼은 오른쪽에 정렬한다. 초기 화면의 모든 탭은 실제 전환되며 같은 대상의 입력·선택을 유지한다.
초기 목업은 한 대상 선택 예시이며 실제 목록 조회 후 행은 자동 선택하지 않는다.
상태별 버튼: 허용 목록
행 추가 탭: 허용 그룹

### 1-1. 마스터-디테일 연동

- 대상 안정 식별자와 읽은 문맥/기준 버전으로 전체 구성을 확보한다. 탭의 행과 상위 대상을 섞지 않는다.
- 다른 대상 선택·재조회·화면 이탈은 미저장 입력 확인 후 수행하며 같은 대상 탭 이동은 입력을 유지한다.
- 조회 실패·부분 목록·접힌 탭을 삭제나 빈 전체 집합으로 해석하지 않는다. 처리 중 중복 명령을 막고 결과 불명은 원 키로 확인한다.

### 요청 업무 구성 상속

원 관리 요건서의 지정 영역 컬럼·검증·설명을 그대로 사용하되 같은 요청의 업무 스냅샷 문맥으로 표시한다. 제출 이후 편집하지 않는다. 원 화면의 저장/실행 버튼과 실시간 관측은 상속하지 않는다. 상속 영역의 목록은 §0, 각 영역의 작업·저장 단위는 공통 요청 경계를 따른다.

### 편집·선택·기본값

§1의 상태와 현재 권한이 허용할 때만 입력한다. 선택 후보의 취소·조회 실패는 원 입력을 보존한다. 새 참조는 안정 식별자를 선택하며 동명·미확인 대상을 자동 대체하지 않는다. 신규의 필수값·미확인 상태를 임의 기본값으로 채우지 않는다. 서버 등록 근거·현재 기준 버전은 숨은 전달 문맥이며 사용자가 수정하지 않는다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

- 관리 목록·상세는 최종 적용본만 표시하며 승인 설정 사용이면 승인 요청, 미사용이면 저장이다. 전체 대상의 설정을 서버에서 재판정한다.
- 자기 기준 리비전 충돌·현재 권한·필수 참조 유효성·SQL/API 기술 검증은 유지한다. 요청 대기 중 운영본을 덮어쓰지 않는다.
- 지식은 외부 자산의 안정 ID를 매핑한다. 외부 리비전 상승만으로 자동 반려·매핑 동기화·지식 재승인을 강제하지 않는다.
- 자산 요청에서 적용/승인 대기 지식의 본문·사용 설명·영향/보완 필요 여부와 근거·보완 요청을 연결한다. 읽지 못한 내용을 영향 없음으로 표시하지 않는다.
- 실제 실행에 사용한 정확 계약·가이드 버전은 실행 당시 기록한다. 관리 승인과 사용자의 실제 업무 실행 승인은 다르다.
- 복합 요청은 같은 요청번호의 모든 대상에 현재 권한·선행 상태·자기 기준본·참조/기술 검증을 확인하고 전체를 한 번 판정한다. 일부 권한만으로 부분 판정/반영하지 않는다.
- 제출 업무 스냅샷은 읽기 전용이다. 초안 보완만 허용하며 반려/취소 뒤에는 이전 요청을 연결한 새 요청을 만든다.
- 자산별 요청6개는 별도 문서/목업 대상이다. 통합 조회 SCR-036은 검색·이동만 하며 판정하지 않는다.
- 별도 관리 이력은 원 화면 상속이다. 이 요청 원장을 관리 이력으로 복제하지 않는다.
- 지식 영향의 새 제출 연결·권한 제한·조회 실패·진짜 연결 없음과 요청 시점/현재 목록 차이를 구별한다. 외부 리비전 상승만으로 재승인·동기화하지 않는다.

### 6-2. 영향 테이블

물리 테이블을 새로 확정하지 않는다. 소유 업무 구성·처리 근거·적용 이력을 기존 정본의 같은 반영 단위로 다룬다. 실패 시 부분 반영·부분 권한 변경을 남기지 않는다. 조회 전용 동작은 변경 없음.

### 6-3. 상태 전이

초안 작성 → 제출(내용 고정) → 기술 검토 → 최종 승인/반려 → 실제 전체 적용 결과. 취소·반려 뒤 보완은 이전 요청을 연결한 새 요청이다. 승인 미사용은 실제 저장자 전결 결과를 기록하고 하지 않은 기술 검토를 완료로 꾸미지 않는다. 실패·결과 불명은 원 요청으로 확인하며 실제 반영 성공 전 결과 리비전을 채우지 않는다.

## 7. API

신규 물리/API 상세 설계는 이번 범위 밖이다. 이미 정해진 기능·화면·공통 승인 계약을 참조하고 새로운 경로·메서드·요청 DTO는 정하지 않는다. 실행 당시 정확 버전 기록과 현재 권한 검사는 유지한다.

## 8. 시드 · 데이터 전제

메뉴/경로는 화면 정본의 검토안이다. 이번 작업에서 메뉴·메시지·공통코드 시드나 제품 sources/를 변경하지 않는다. 미정 코드/메시지 키는 화면 합의 후 상세 설계한다.
