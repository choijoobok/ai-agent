# 요건 정의서 — 사용자 그룹 추가 승인

## 개요

- **무엇을 하는 화면인가**: Portal 사용자의 그룹 추가/재부여 요청을 승인·반려한다. 데이터소스·대상 시스템의 사용자 아이디는 Portal 사용자 관리에서 승인 없이 직접 설정하므로 이 화면의 대상이 아니다.
- **프로세스상 위치**: Portal 사용자 관리/사용자 그룹의 추가 요청 → 이 화면의 동일 요청 검토·판정 → 유효 소속 확인.
- **이 데이터를 누가 쓰나**: 현재 사용자 그룹 승인 액션 권한자와 접근 판정 업무.
- **바꾸면 어디가 흔들리나**: REQ-609의 그룹 부여·REQ-103의 최소 그룹·REQ-601의 요청 무결성.

### 1-1. 마스터-디테일 연동

- 요청번호로 사용자·그룹·제출 버전을 고정하고 요청/탭별 입력·선택을 유지한다.
- 신원 요청을 그룹 요청으로 자동 전환하지 않는다. 기존 신원 이력은 원 업무에서 보존하며 이 화면에서 신규/지연 승인하지 않는다.

## 3. 조회 — 테이블과 범위

### 3-1. 사용 테이블 · 결합

사용자 그룹 추가 요청의 고정 제출본·현재 사용자/그룹·현재 소속과 원 처리 이력을 소유 정본에서 조회한다. 신원 매핑/비밀값은 승인 자료에 포함하지 않는다. 물리 테이블·키는 후속 상세 설계다.

### 3-2. 고정 조건 · 기본 정렬

그룹 요청만 현재 조회 권한 범위에서 조회한다. 실패·권한 없음·성공 0건을 구분하고 현재 적용 소속과 요청 상태를 혼합하지 않는다.

## 6. 규칙 — 저장 · 실행

### 6-1. 검증

- 이 화면은 그룹 추가/재부여만 처리한다. 데이터소스/대상 시스템 아이디 저장·교체·중지에는 승인/전결/기술 검토를 요구하지 않는다.
- 그룹 승인 설정 사용 시만 새 요청을 접수하고 미사용 시 기존 저장자 전결을 따른다. 설정 변경으로 기존 대기 요청을 자동 승인하지 않는다.
- 현재 그룹 요청 권한과 승인/반려 권한은 별개다. 같은 사람이 각 권한을 가지면 단계별 근거를 남겨 요청/승인할 수 있다.
- 동일 사용자·그룹·요청 버전만 승인한다. 제출 내용을 교체하려면 기존 요청의 미반영 종결 후 새 요청을 제출한다. 그룹 요청 상태는 유효 소속이 아니다.
- 취소·반려·회수된 그룹을 늦은 승인으로 되살리지 않는다. 그룹 중지는 Portal 사용자 관리/사용자 그룹의 직접 회수 경로이며 이 화면에서 기다리지 않는다.

### 6-2. 영향 테이블

그룹 요청 상태·판정 근거와 현재 사용자-그룹 소속을 같은 소유 반영 단위로 처리한다. 기존 신원 요청의 자동 전환이나 신원 현재값 변경은 하지 않는다.

### 6-3. 상태 전이

승인 대기 → 승인과 소속 활성화 또는 반려/취소. 판정/활성화 일부 실패는 전체 실패이며 기존 유효 소속을 유지한다.

## 7. API

그룹 요청 조회·승인·반려·취소 공개 계약은 화면/업무 흐름 합의 후 상세 설계한다. 신원 승인 계약은 신규 설계에서 제외한다.

## 8. 시드 · 데이터 전제

메뉴 표시명은 사용자 그룹 추가 승인으로 변경한다. 현재 설계 SCR/메뉴 코드/경로를 유지하며 제품 sources/·메뉴/메시지/권한 시드는 화면 승인 뒤 갱신한다.
