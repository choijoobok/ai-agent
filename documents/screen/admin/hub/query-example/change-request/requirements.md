# 요건 정의서 — 인증 예제 변경 요청

## 개요

- **무엇을 하는 화면인가**: 검수된 업무 질문·SQL·파라미터와 실행 데이터소스·참조 카탈로그의 최종 적용본을 관리한다. 이 화면은 최종 적용본 대신 선택 요청의 고정 제출본·초안·처리 원장을 다룬다.
- **프로세스상 위치**: SCR-012에서 변경 작성 → 이 전용 요청의 검토·전체 판정 → 실제 전체 반영 → 원 화면 적용본·상속 이력
- **이 데이터를 누가 쓰나**: 권한 있는 관리자와 연결 업무의 담당자가 현재 적용값 또는 업무 처리 근거로 사용한다.
- **바꾸면 어디가 흔들리나**: 소유 기능의 요청·권한·참조 및 이력/감사 연결을 함께 확인한다.

> 미구현 화면 초안이며 사용자 화면 합의·제품 구현·G3(설계 승인 게이트) 승인이 아니다. [화면 정본](../../../../../spec/60-screens/_index.yaml)과 [기능 정본](../../../../../spec/31-features/002-admin.yaml)을 따른다. 표시 예시는 실제 데이터·물리명·운영 기본값이 아니다.

## 1. 화면 구성

상단 조회조건 → 변경 요청 목록 → 파라미터 · 참조 카탈로그 · 관계 참고 · 노출 그룹 · 연결 지식 · 변경·복원 근거 · 변경 비교 · 요청 전체 대상 · 영향 판단 · 처리 근거 · 처리 원장 순서다. 제목·건수는 왼쪽, 작업 버튼은 상단·그리드 툴바·모달 하단에서 우측 정렬한다. 초기 화면의 모든 탭은 실제 전환하며 같은 상위 대상의 입력·선택·추가/제거 행을 유지한다.

## 8. 시드 · 데이터 전제

- 코드그룹·메시지 키·물리 테이블·필드·신규 API 경로는 미정이다. A 담당 공통 정본 확정 후 연결하며 이번 작업에서 시드·제품 소스를 변경하지 않는다.

## 10. 미결 · 확인 필요

- A 공통 요청 영역은 REQ-601·SCR-056~061의 정본과 기존 scaffold 선언 기능으로 재사용한다. 공통 상태/메시지·실제 명령 및 결과 확인 계약·전역 TC의 본 화면 사례 연결을 A가 통합해야 한다.
- A 공통 생성기 보완 필요: mockup-controls.js의 명령 입력 확인 문구가 카탈로그 전용으로 고정되어 있다. 모든 자산/업무 명령에 맞게 업무 데이터를 변경하지 않았다는 공통 문구로 바꿀 필요가 있다. B는 수정하지 않았다.
- 목업의 초안/제출/재요청 버튼은 상태 예시 이동, 판정 버튼은 공통 사유 입력창의 입력 확인을 시연한다. 실제 서버 승인/반영·권한·경합 검증은 제품 구현 뒤 시험한다.
- A 공통 생성기 보완: 일반 그리드 제거 버튼의 실제 행 제거/행수·선택 갱신과 미저장 입력 유지는 현재 미지원이다. declared-layout.mjs의 버튼 속성과 mockup-controls.js 대응 처리를 A가 추가해야 한다. B 검증은 제거 실행을 통과로 주장하지 않는다.
- @defer 화면 합의 후 소유 상세 설계 — DB 물리명·와이어 필드·API·공통코드·메시지 키·길이/개수/기간/보존·운영값을 확정한다. 화면 작업은 해당 계약을 추정하지 않는다.
- A 공통 변경 필요: 소유 FEAT의 공개 계약·전역 TC에서 본 화면 사례 연결과 메시지 키를 확정한다. 공통 spec·메뉴·상태·생성기·스타일은 이 B 작업에서 수정하지 않는다.
