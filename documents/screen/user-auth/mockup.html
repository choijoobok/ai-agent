1. 기본 상태 — 셋으로 나뉘고 스플리터가 둘이다

  1. 1조회 버튼은 그리드마다 있다 — 검색 폼은 하나지만 누르는 조회 버튼에 따라 다시 부르는 것이 다르다. 사용자를 다시 조회하면 선택이 풀려 트리·목록이 빈 상태가 되지만, 메뉴명만 바꿔 트리의 조회를 누르면 선택은 그대로다. 폼 하나에 조건 셋을 두고도 "메뉴명 하나 고쳤는데 사용자 선택이 날아가는" 일이 없는 이유가 이것이다.
  2. 2부여 상태를 조회조건에 두지 않는다 — 만료 행도 함께 온다.
    초안은 예정+유효 를 기본값으로 두고 만료를 감췄는데 뺐다. 트리는 전건을 본다 — 만료 배지를 그려야 하기 때문이다. 목록만 걸러져 있으면 "둘은 같은 데이터의 두 표시"(§4)가 성립하지 않고, 만료된 조합을 다시 체크했을 때 고쳐야 할 행이 목록에 없다.
    감추고 싶으면 컬럼 필터로 건다 — 결과 내 필터라 재조회 없이 켜고 끈다. 기본으로 걸어 두지 않는 이유는 컬럼 계약 그대로다.
  3. 3좌 pane 은 팝업이 아니라 목록 그리드다. 사용자 화면 설계가 <UserPicker> 로 적었는데 그것은 팝업 참조용 컴포넌트이며, pane 과 스플리터가 있는 자리에 팝업을 둘 이유가 없다. 사용자 화면 설계를 고쳤다.
  4. 4권한 트리는 그리드가 아니다. AG Grid 의 Tree Data 는 Enterprise 이고 우리 어휘 밖이라 감싸지 않는다. AntD Table 의 트리 행으로 만든다 — "AG Grid = 데이터 그리드 전용"의 적용이다. → §6
  5. 5구조 노드는 체크박스가 없다 — MENU_URL IS NULL 이라 가리킬 화면이 없다. 권한의 단위는 (MENU_CD, ACTION_CD) 인데 구조 노드에는 부를 API 가 없다.
  6. 6역할로 이미 갖고 있는 것은 역할명으로 말한다 — 회색 배경을 쓰지 않는다. 이 화면에도 읽기 전용 셀(회색)이 함께 있어 같은 회색이 두 뜻이 되면 "못 고치는 칸" 으로 읽힌다. → §3
  7. 7— 는 액션 미정의다 — 그 메뉴에 그 액션의 API 가 없다. 권한의 단위는 (MENU_CD, ACTION_CD) 이고 그것이 뜻하는 바는 "이 메뉴에서 이 액션의 API 를 부를 수 있다" 인데, 부를 API 가 없으면 부여할 것이 없다.
    이 행(USER_AUTH_MGMT)은 R S E 뿐이다 — EXECUTE 로 떨어지는 API 가 이 화면에 없다. 공통코드 행도 같은 이유로 실행이 — 다. 빈 체크박스로 두면 "줄 수 있는데 안 준 것" 으로 읽힌다 — 아무리 눌러도 안 되는 칸이 된다.
    고정이 아니다 — 그 화면에 EXECUTE 로 떨어지는 API 가 하나 생기면(접두 액션 · 시드 생성 결정 접두 규칙) 시드가 재생성되면서 — 가 스위치로 바뀐다. → §8
  8. 8기간과 사유가 전부 필수다(AUTHZ-07) — 역할 부여(사용자 화면 설계 탭 1)는 기간이 선택인데 여기는 필수다. 개인 예외는 임시 조치라는 것이 그 차이의 전부이며, 그래서 만료 행이 쌓이는 대가를 진다(주석 2).
  9. 9삭제 컬럼은 오등록 정정용이다 — 회수는 삭제가 아니라 종료일을 어제로 하는 것이다(§5). 지우면 "누구에게 왜 무엇을 언제까지 줬는가" 가 사라진다 — 변경 이력 테이블을 두지 않았으므로 이 행이 그 기록이다.
  10. 10상태 셋은 조회 시 계산한다 — 배치가 컬럼을 갱신하지 않는다 . 읽기 전용이며 정렬도 끈다 — 파생값이라 SQL ORDER BY 대상이 아니다.
  11. 12체크박스는 "지금 유효한가", 배지는 "행이 있는가" 를 말한다. 만료를 켜진 스위치로 두면 "이 사람 지금 이거 되나" 에 거짓으로 답한다. 역할 경유를 배지로 말하는 것과 같은 규칙이다(주석 6).
    배지가 붙은 꺼진 스위치를 켜면 새 행이 아니라 있는 행이다 — PK 가 (USER_ID, MENU_CD, ACTION_CD) 라 한 조합에 행은 하나뿐이다. → §4
  12. 11하단에 탭이 없다. 역할 후보 리포트(AUTHZ-12)를 두려 했으나 기능에서 뺐다. 탭이 하나면 탭이 아니다 — 그리드 크롬만 남긴다.
    그래서 그리드 표준의 예외도 사라졌다 — 이 화면의 하단은 전부 선택된 사용자에 종속된다. → §6
  13. 브레드크럼 줄의 오른쪽은 화면이 채운다. [조건 ▾] 은 저장된 조회조건 (UX-07) — 열면 조회, 고르면 적용, ✕ 가 삭제, 맨 아래가 저장이다. 넷을 버튼 넷으로 두지 않는다 — 조회·적용은 이미 제스처다. [⌃ 조회조건] 은 검색 폼 접기 토글(UX-15)이며 폼 밖에 있어야 한다 — 숨기는 버튼이 폼 안에 있으면 숨긴 뒤 되돌릴 수 없다. 리프 목업이 셸 크롬을 그리지 않는 규약의 유일한 예외가 이 줄이다.
  14. 검색 폼에 조회·검색 버튼이 없다. 그리드 ①이 이미 조회를 갖는다 — 폼에도 두면 같은 조회를 부르는 버튼이 둘이 된다. 남는 것은 초기화 하나이며 컬럼 필터도 함께 지운다. Enter 는 남는다 — 버튼을 없앤 것이지 제스처를 없앤 것이 아니다.
  15. 그리드 헤더의 버튼은 전부 오른쪽이다 — 왼쪽은 제목뿐이고 도구 둘(⤓ ⚙)은 맨 오른쪽 고정이다.

2. 트리 셀의 상태 일곱 — 62 가 이것을 참조한다

AUTHZ-07 이 "역할 화면과 동일 컴포넌트" 라고 했고 역할 쪽은 62 다. 먼저 쓰는 문서가 정의하고 뒤가 참조한다 — 개인 예외가 제약이 더 많으므로 (기간·사유 필수, 허용만) 여기서 정의하면 62 는 빼는 쪽이 된다. 반대로 하면 62 에 없던 제약을 여기서 더하게 되고, 그때 컴포넌트가 갈린다.

액션 미정의—불가메뉴 목록의 액션 열에 없는 조합
구조 노드체크박스 없음불가MENU_URL IS NULL
  1. 액션은 넷에서 닫힌다 — READ · SAVE · EXPORT · EXECUTE. 이 네 열 헤더의 조회 · 저장 · 내보내기 · 실행 은 action.{ACTION_CD} 메시지이며 API 목록 그리드의 액션 셀도 같은 키를 읽는다 — 공통코드가 아니다. 넷이 헤더로 박혀 있으니 데이터로 두면 코드를 바꿀 때마다 소스를 함께 고쳐야 한다. 열이 늘지 않으므로 트리의 폭이 예측 가능하다 — 그래서 좌우 배치가 성립한다.
  2. 허용만 있고 거부는 없다 — 개인 예외는 더하는 것뿐이다. 역할이 준 것을 개인 단위로 빼는 수단을 두면 "유효 권한이 왜 이런가" 를 두 방향으로 추적해야 한다( 합집합). 빼려면 역할에서 빼거나 역할을 회수한다.
  3. 체크박스가 아니라 스위치다 — 그리드의 ynFlag 와 같은 것을 쓴다. 읽기 전용일 때가 이유의 절반이다: 회색 체크박스는 "꺼진 것" 인지 "못 켜는 것" 인지 구분되지 않지만 비활성 스위치는 상태 표시로 읽힌다. 켜짐은 위치 + 색이라 메뉴 × 액션 4열이 촘촘한 트리에서 멀리서도 보인다.
    클릭 한 번이 곧 확정이며 편집 모드가 없다 — 값이 둘뿐이라 중간 상태가 없다(편집·검증 규약의 예외). 스위치가 즉시 저장을 뜻하지는 않는다 — 켜면 행 상태가 ✎ 가 되고 저장 버튼을 눌러야 나간다.
  4. 여럿을 고르는 자리는 여전히 체크박스다 — 행 선택 · set 필터 목록 · 그리드 설정 창의 컬럼 표시. 스위치는 값이 둘인 데이터 셀이고 체크박스는 목록에서 고르는 것이다.
  5. 조회 권한은 나머지 셋의 전제다 — 다른 액션이 하나라도 켜져 있으면 READ 가 켜져 있다. READ 없이 SAVE 만 가지면 메뉴는 보이는데 첫 조회가 403 이라 아무것도 못 한다 — 모든 액션은 그 화면 안에서 발동되기 때문이다.
    조회를 끄면 나머지 셋도 함께 꺼지고, 다른 액션을 켜면 조회가 함께 켜진다. 둘 다 조용히 하지 않는다. 남겨 두면 나중에 조회 하나를 켜는 순간 저장·실행이 함께 부활해 권한 확장이 리뷰 없이 일어난다. → role-auth §7
  6. 트리에는 페이징이 없다 — 계층이 잘리면 부모 없는 자식이 보인다. 그래서 하단 .pg 가 없고, 그리드 표준의 푸터 셋 중 이 화면의 트리만 예외다. → §6

역할로 이미 갖고 있습니다 — 운영자. 개인 예외를 더해도 됩니다. 4
  1. 1역할명은 배지로 붙는다. 사용자 화면 설계 초안은 회색 배경이었는데 이 화면에 읽기 전용 셀(회색)이 함께 있다(예외 목록의 메뉴·상태·부여자). 같은 회색이 "못 고치는 칸" 과 "역할로 이미 있는 칸" 두 뜻이 되면 편집할 수 있는 칸을 편집할 수 없다고 읽는다. 그리드 표준의 "색만으로 말하지 않는다" 를 여기서는 색을 아예 쓰지 않는 것으로 지킨다. 사용자 화면 설계를 고쳤다.
  2. 2역할 보유분에 개인 예외를 더하는 것을 막지 않는다. 합집합이라 중복은 무해하고("중복은 사라진다"), 막으면 역할 부여가 곧 만료되는 경우를 처리할 수 없다 — 역할이 빠질 때 권한도 함께 사라진다. 회색으로 "지금은 역할로도 갖고 있다" 를 알려주는 것까지가 화면의 몫이다.
  3. 3역할이 여럿이면 배지가 여럿이다 — "어느 역할이 이걸 줬나" 가 회수 판단의 재료다. 역할 목록을 서버가 문자열로 이어 붙이지 않는다 — 4벤더에서 이식 가능한 문자열 집계 함수가 없다. 배열로 내려 화면이 그린다.
  4. 4안내는 토스트가 아니라 배너다 — 흐름을 멈출 일은 아니지만 체크를 누르는 동안 계속 보여야 한다. 토스트는 사라진다.

4. 트리와 목록은 한 데이터다 — 목록이 원본이고 트리는 그 투영이다

둘 다 SYS_USER_MENU_AUTH 다. 트리는 "무엇을", 목록은 "언제까지 · 왜" 를 받는다 — 기간과 사유가 필수인데 트리 셀에는 넣을 자리가 없다.

  2. 2행 상태가 추가(＋)가 아니라 수정(✎)이다. 있는 행을 고치는 것이므로 저장은 UPDATE 로 나간다. 추가로 두면 INSERT 가 나가 실패한다 — 행 상태가 곧 SQL 이다.
  3. 3종료일을 "지우는" 것이 아니라 다시 받는다. 역할 부여는 NULL 이 무기한이지만 개인 예외는 기간이 필수다(AUTHZ-07). 무기한이라는 선택지가 없으므로 비워 두면 검증에 걸린다. 시작일만 오늘로 채운다 — 거의 항상 오늘이다.
  4. 4사유도 비운다 — 새 판단이다. 이전 사유를 남겨 두면 "그대로 저장" 이 되고, 사유를 필수로 둔 의미가 사라진다(§1 주석 8).
  5. 5덮어쓰기 전에 보여준다. 이전 기간과 사유가 대체되며 되돌릴 수 없다.
    §5 의 "행을 남기는 것이 기록" 과 어긋나 보이지만 아니다 — 그것은 회수에 대한 것이다. 재부여는 그 기록을 대체하는 별개의 결정이며, 대체된 내용은 요청 전문 로그에 있다 (변경 이력 테이블 대신 요청 body 를 통째로 남기기로 한 판단이 여기서 값을 한다).

9. 이 목업으로 확인할 것

결정하면 문서 표에 적는다. 이 파일이 아니라.
  • 역할 신설 검토 안내의 임계치 — 한 번에 몇 개를 체크하면 물을지. 막지 않고 묻기만 한다 — 막으면 저장을 두 번 나눠 규칙을 피한다. 배너 문구도 함께
  • 트리의 규모 — 메뉴가 수백 개면 전건 렌더가 버티는지. 가상 스크롤이 필요하면 AntD Table 로 되는지 실측이 필요하다
  • 트리 조회의 응답 크기 — 메뉴 × 액션 4 × 역할 보유분을 한 번에 내려준다. 역할이 많은 사용자에서 얼마나 커지는지
  • 스플리터 둘의 기본 비율 — 좌 pane 은 고정 폭이 나은지 비율이 나은지. 그리드 표준은 비율만 정했다
  • 메뉴명 검색이 트리를 어떻게 접는가 — 맞는 노드만 남기고 조상을 펼칠지, 전체를 두고 강조만 할지. 조상이 없으면 어디의 메뉴인지 알 수 없다
  • 액션 미정의(—)의 출처 — 메뉴 목록의 액션 열은 문서다. 런타임에는 SYS_MENU_API ⋈ SYS_API 를 ACTION_CD 로 접으면 나온다 — 트리 조회가 매번 계산할지 캐시할지
  • 고아 배지의 모양 — 행을 남기는 것은 정해졌다 — 시드는 전체 동기화라 API 가 사라지면 SYS_API 행도 사라지지만, 사람이 부여한 행은 남는다. 배포가 운영 결정을 지우지 않는다. 목록에서 어떻게 표시하고 일괄 정리를 줄지가 남았다
  • 만료 행의 정리 — 기간이 필수라 계속 쌓인다. 보관 기간을 두고 배치로 지울지, 영구 보관할지. 지우면 사유가 사라진다(§1 주석 9)
  • 일괄 부여 — 여러 사용자에게 같은 예외를 한 번에 주는 수단이 없다. 그것이 필요해지는 순간이 곧 역할을 만들 순간이라 두지 않은 것인데, 운영에서 버티는지
