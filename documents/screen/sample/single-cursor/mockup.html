푸터 셋이 응답의 mode 하나로 갈린다. 화면은 선언하지 않는다

5. 주석

  1. 1기간이 필수이고 상한이 있다. 편의가 아니라 부하다 — 비우면 첫 조회가 전량을 향한다. 화면 층(rangeDays)은 시스템 값을 좁히기만 한다 — 화면이 32를 적어도 시스템이 31이면 31이다. 서버도 같은 것을 다시 본다: 화면만 막으면 도구·스크립트가 그대로 지나간다.
  2. 2같은 테이블인데 저장이 없다. 이 화면이 보이려는 것은 대용량 이력을 어떻게 넘기나 이고, 편집을 얹으면 커서가 바뀌는 동안 편집이 살아 있는 문제를 함께 떠안는다 — 그것은 이 화면의 주제가 아니다.
  3. 3footerNote 가 총 건수의 자리를 메운다. 무엇을 물어서 나온 N건인지 가 함께 있어야 "전부가 100건" 으로 읽히지 않는다.
  4. 4‹ 이전 도 커서다. page > 0 으로 첫 장인지 알 수 없고, 서버가 prevCursor 를 주었는가 로만 안다 — 화면은 두 방향을 구분하지 않고 받은 토큰을 그대로 되돌려준다.
  5. 5모드로 판정하면 동작이 데이터 양에 흔들리지 않는다. 사용자가 "정렬해도 편집이 안 날아간다" 를 배운 뒤 데이터가 늘어난 날 작업을 잃는 일이 없다.
  6. 6토큰은 불투명하고 유효기간이 없다. 클라이언트가 해석하면 정렬 키가 노출되고, 형태를 바꿀 때 프론트가 깨진다. 서버가 상태를 갖지 않으므로 다중화에서도 안전하다.
  7. 7필수는 폼이 막는다 — 그리드는 값을 요청할 뿐이다.
  8. 8커서형에는 마지막 장 이 없다. size + 1 건을 읽어 hasNext 만 안다 — 지금 다음이 없다 와 영영 없다 는 다르다.

7. 이 목업으로 확인할 것

이 화면이 정한 것
  • 페이징 모드는 테이블의 성질이 아니다 — 같은 SMPL_ORDER 에 모드가 다른 엔드포인트 둘을 둔다. 테이블을 하나 더 만들면 모드가 데이터의 성질처럼 읽힌다.
  • 커서형은 오히려 벤더 중립적이다 — 오프셋 페이징이 벤더 분기를 요구하는 유일한 자리인데 커서형은 보통의 WHERE + 상위 N 이다.
  • 모드 셋의 푸터가 한 화면에 나란히 있다(화면 2) — 문서 표가 처음으로 그림이 됐다.
아직 답이 없는 것
  • 자동 새로고침의 주기 — toggle 을 켰을 때 몇 초인가. 켜 둔 채 편집이 없는 화면이라 잃을 것이 없지만, 커서를 유지할지 첫 장으로 갈지가 미정이다.
  • 커서형에서 N건 조회됨 의 N — 이번 장의 건수인가 지금까지 누적인가. 누적이면 뒤로 갔을 때 줄어드는 숫자가 된다.
  • 사이즈 콤보를 바꾸면 커서를 버리고 첫 장으로 가야 한다 — 규약은 정해졌으나 사용자가 위치를 잃는 체감은 재 보지 않았다.
목업 규약 — 정적 HTML, 프레임워크 없음, 픽셀 충실도는 목표가 아니다. 결정은 requirements.md 가 갖고 이 파일은 확인용이다 — 여기에만 있고 요건서에 없는 정보는 유실된 것으로 친다.
