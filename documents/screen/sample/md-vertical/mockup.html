6. 주석

  1. 1디테일 제목에 부모 이름이 붙는다(2026-08-31). 마스터의 선택 행이 스크롤 밖으로 나가거나 조회조건을 펼치면 지금 보고 있는 것이 누구의 것인지가 화면 어디에도 없다. 문자열을 화면이 만들지 않는다 — 부모 컨트롤러와 컬럼 이름만 주면 titleSuffix 가 조립한다.
  2. 2디테일도 조회 버튼을 갖는다. 마스터 선택이 바뀌면 스스로 조회하지만, 자동 조회와 수동 재조회는 다른 일이다 — 남이 고친 것을 다시 읽거나, 저장 실패 뒤 서버 상태를 확인하거나, 실행이 서버에서 바꾼 값을 되받을 때 마스터를 건드리지 않고 이쪽만 읽는다. 마스터 조회로 대신할 수 없다: 그쪽은 목록을 통째로 바꾸고 디테일을 리셋하므로 고른 행을 잃는다. 대상은 여전히 마스터의 선택이고(부모 키는 searchParams) 버튼이 그 값을 바꾸지 않는다.
  3. 3품목이 있는 주문은 삭제 체크가 열리지 않는다(화면 4).
  4. 4계산은 디테일에서 일어난다 — 수량 또는 단가를 고치면 afterEdit 가 금액을 채운다. 마스터의 합계는 화면이 갱신하지 않는다: 미저장 편집이 마스터에 물들면 마스터만 저장했을 때 존재하지 않는 품목의 금액이 DB 에 들어간다. 합산은 저장 시 서버가 한다.
  5. 5onSelect 가 false 를 돌려주면 판의 선택이 되돌아간다(기준정보 화면 설계가 처음 요구했다). void 를 돌려주면 언제나 통과이며, 잃을 것이 없는 화면은 묻지 않는다.
  6. 6화면 게이트와 DB 제약이 같은 것을 두 번 본다. 화면만 막으면 API 를 직접 부르는 경로가 열리고, DB 만 걸면 사용자가 저장을 눌러 봐야 안 되는 줄 안다.
  7. 7접힘의 규칙이 하나여야 배울 것도 하나다. 상하·좌우·탭 하단이 전부 제목 줄 클릭으로 되돌린다 로 같다.

8. 이 목업으로 확인할 것

이 화면이 정한 것
  • 저장 단위가 둘이라는 것을 화면이 말한다 — 상태 컬럼·삭제 컬럼·저장 버튼이 위아래에 각각 있다. 디테일이 마스터의 일부 였다면 저장 버튼이 하나여야 한다.
  • 마스터 합계를 화면이 갱신하지 않는다(주석 4) — 미저장 값이 다른 저장 단위로 새는 것을 막는다. 이 규칙은 지금까지 어디에도 적혀 있지 않았다.
  • 삭제 게이트가 화면과 DB 양쪽에 있다(주석 6) — 어느 한쪽만으로는 부족하다.
아직 답이 없는 것
  • 마스터 재조회 후 선택이 유지되는가 — 같은 ORD_NO 행이 결과에 남아 있으면 다시 고를지, 선택을 비울지. 유지하면 디테일이 다시 읽히는지가 따라온다.
  • 디테일이 페이징을 갖는가 — 지금은 all 로 그렸다. 품목이 수백 건인 주문이 생기면 모드가 갈려야 하고, 그때 디테일 푸터가 처음 네비를 갖는다.
  • 기본 비율 — defaultRatio 0.55 로 그렸다. 마스터가 아홉 컬럼이라 위가 더 넓어야 할 수도 있다. 재 보지 않았다.
목업 규약 — 정적 HTML, 프레임워크 없음, 픽셀 충실도는 목표가 아니다. 결정은 requirements.md 가 갖고 이 파일은 확인용이다 — 여기에만 있고 요건서에 없는 정보는 유실된 것으로 친다.
