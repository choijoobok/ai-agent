2. 조회조건 열둘 — op × type 이 컨트롤을 정한다

조회조건을 펼친 상태. 같은 type 이라도 연산자가 바뀌면 칸의 모양이 바뀐다
popupRef 필드 ~ ~ 이상 gt · lt = 정기 ×9월 × 태그 입력 — 값 칸이 사라진다 3
저장된 조회조건은 폼 안 오른쪽 아래
  • 연산자를 바꾸면 컨트롤이 바뀐다 — 범위는 칸 둘, 여럿은 다중 선택, 있음/없음은 칸이 사라진다
  • 긴급(ynFlag)에는 연산자 셀렉터가 없다 — 허용이 eq 하나뿐
  • 소요시간은 초로 받아 ms 로 보낸다 — scale:1000. 사람이 600000 을 치지 않는다
  • 컬럼 필터를 서버로 보내지 않는다 — 헤더의 필터는 조회 결과 안에서 거른다
  • 정렬 필드를 폼에 두지 않는다 — 정렬은 헤더 클릭이다
  • 빈 칸은 보내지 않는다. 기본값과 같은 칸은 저장하지 않는다

8. 주석 — 무엇을 왜 이렇게 그렸나

  1. 1기본 상태에서는 조회조건을 세 칸만 보인다. 열둘을 항상 펼쳐 두면 그리드가 화면 아래로 밀린다 — 접기 토글은 브레드크럼 줄의 슬롯이다(UX-15).
  2. 2컬럼 서른을 줄이지 않는다. 이 화면이 어휘의 유일한 실물이므로 하나를 빼면 그 어휘의 예가 템플릿에서 사라진다. 가로 스크롤은 좌우 고정으로 견딘다 — 왼쪽에 주문번호·주문명, 오른쪽에 삭제.
  3. 3isNull·isNotNull 을 고르면 값 칸이 사라진다. 값을 받지 않는 연산자이며, 칸을 남겨 두면 "값을 넣었는데 안 걸린다" 가 된다.
  4. 4완료(DON) 주문의 스위치가 잠겼다 — editable 함수가 {ok:false, message} 를 돌려준다. 거부에는 메시지가 필수이며 없으면 사용자는 화면이 고장난 줄 안다.
  5. 5삭제 체크가 아니라 — 다. 완료 주문은 삭제 대상이 아니며 DeleteColumnSpec.enabled 가 그것을 정하고 reason 이 툴팁으로 이유를 댄다.
  6. 6변경 건수를 헤더가 말한다. 일괄 저장이라 무엇이 나가는지 가 눌러 보기 전에 보여야 한다.
  7. 7실패는 배너와 셀 둘 다에 있다. 배너만 있으면 어느 행인지 찾아야 하고, 셀만 있으면 스크롤 밖의 오류를 못 본다.
  8. 8계산은 한 곳에서 셋 다. 수량의 afterEdit 가 금액과 부가세를 함께 채운다 — 연쇄는 한 단계에서 멈춘다. 서로를 부르면 어느 컬럼이 먼저 도느냐로 결과가 갈린다.
  9. 9삭제는 상태이지 실행이 아니다. 체크한 행은 취소선으로 남고 저장을 눌러야 사라진다 — 배경이 아니라 글자다.
  10. 10거부 메시지는 토스트다. 편집 모드가 아니라 셀에 붙일 자리가 없다. 판정 시점은 편집 진입 직전이며, 렌더 시점에 한 번만 하면 같은 행의 다른 셀을 고쳐 조건이 바뀌었을 때 낡은 판정이 남는다.
  11. 11popupRef 는 타입이지 에디터만이 아니다. 값이 하나가 아니라 여러 칸을 함께 채우므로 컬럼 타입 축에 있다. 채워진 칸을 손으로 고칠 수 있으면 참조가 깨지므로 읽기 전용이다.
  12. 12viewer 와 editor 는 다른 축이다. 저것은 고치는 방법, 이것은 읽는 방법 이며 한 이름으로 묶으면 "읽기 전용인데 편집기가 열린다" 가 되어 사용자가 타이핑한다.
  13. 13순서는 검증 → 파라미터다. 어차피 막힐 실행에 값을 묻지 않는다. 그리고 이 모달이 확인을 겸한다 — confirm 을 따로 띄우면 두 번 묻는 꼴이다.
  14. 14STEP_MSG 를 보인다. 퍼센트만 있으면 멈춘 것과 느린 것을 구별할 수 없다. TOT_CNT 가 NULL 이면 불확정 막대다.
  15. 15모달을 닫아도 작업은 돈다. 사용자를 붙잡아 두지 않는다 — jobId 는 화면이 들고 있고, 세션이 만료돼 재인증해도 다음 폴링이 그냥 나간다.
  16. 16실패는 모달에 남는다. 토스트로 내면 자리를 뜬 사이 사라지고, 어디까지 됐는지가 함께 사라진다 — 오래 걸리는 작업의 실패는 재시도 범위가 정보다.
  17. 17visible:false 는 편의다 — 목록에 있고 사용자가 켠다.
  18. 18hidden:true 는 통제다 — 목록에 없다. 편집 대상도 아니다. 둘이 엇갈리면 hidden 이 이긴다.

10. 이 목업으로 확인할 것

이 화면이 정한 것
  • 어휘가 화면을 요구한다 — 컬럼 서른은 업무가 아니라 컬럼 계약의 칸에서 나왔다. 지우면 예가 사라지는 어휘가 열둘이다.
  • 실행이 둘로 갈린다(§6-1) — 같은 X 인데 하나는 응답이 곧 끝이고 하나는 jobId 다. 그 갈림이 화면에서 어떻게 보이는지 는 지금까지 실물이 없었다.
  • params 모달이 확인을 겸한다 — 예고된 "처음 인자를 요구하는 실행" 이 왔고, 두 번 묻지 않는 것이 그 규약이다.
  • 숨김 두 층이 설정 창에서 갈린다(§7) — visible 은 목록에 있고 hidden 은 없다. 문서의 두 단어가 화면에서 두 모양이 됐다.
  • gt·lt 를 숫자 컬럼에서만 연다 — 날짜의 초과·미만 은 경계 하루로 사람이 잘못 읽는다.
아직 답이 없는 것
  • progress 렌더러의 셀 높이 — 행 높이 설정을 따라야 하는가 고정인가. 따라가면 촘촘 에서 막대가 실선이 된다.
  • icon 아이콘 집합 — 메뉴 아이콘 집합을 재사용할지 별도로 둘지. 임의 문자열을 받지 않는다는 것만 정해졌다.
  • 진행률 모달을 닫은 뒤 다시 여는 길 — 화면 어딘가에 진행 중 표시가 남아야 하는가. 없으면 닫는 순간 작업이 사라진 것처럼 보인다.
  • 첫 진입에서 조회를 자동으로 할지 — 기준정보 화면 설계는 탭을 열면 조회가 나간다. 여기는 2,000건이라 같은 판단인지 확인이 필요하다.
  • 컬럼 서른의 가로 스크롤이 실제로 견디는가 — 좌우 고정으로 버틴다고 적었지만 재 보지 않았다. 컬럼 계약의 동적 컬럼 개수 상한 과 같은 자리다.
