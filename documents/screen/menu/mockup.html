총 2건
  1. 1검색은 거르지 않는다 — 찾아간다. 조건에 맞는 노드만 남기면 부모가 사라져 트리가 아니게 된다. 일치 노드를 강조하고 경로를 펼치며, n / m 과 이전·다음이 없으면 화면 밖의 일치를 찾을 수 없다. 컬럼 필터도 전부 끈다 — 헤더 필터가 행을 감추면 같은 문제다.
  2. 2행 추가가 아니라 버튼 둘이다. 즉시 저장 그리드에는 미저장 행이 없으므로 addRow를 선언하지 않는다. 최상위 메뉴 추가는 항상 활성이고(부모 NULL — 모듈이 된다), 하위 메뉴 추가는 선택 노드가 부모이며 선택이 없으면 비활성이다. 하나로 두고 라벨을 바꾸지 않는다 — 누르기 전에 무엇이 만들어질지 알아야 한다(화면 4 주석 7).
  3. 3삭제가 비활성이다 — 선택된 에러 로그 는 매핑 API 2 · 접근 인원 14 · 매핑 역할 3 이다. 누르면 왜 막히는지 말한다(화면 6).
  4. 4엑셀은 드롭다운이 아니라 아이콘 하나다. 페이지가 없어 현재 페이지 와 전체 가 같은 것이다 — 항목이 둘일 때만 드롭다운이었다.
  5. 5푸터가 한 칸이다. 그리드 표준의 셋 중 네비게이션과 페이지 사이즈가 사라진다 — 트리를 페이징하면 부모 없는 자식 페이지가 생긴다.
  6. 6최상위는 모듈이다. 템플릿 메뉴는 전부 SYSTEM 아래이며 DASHBOARD 만 예외로 최상위 리프다 — 셸의 고정 탭이라 조상이 없다. 구조 노드의 스위치도 열려 있다 — 놓으면 자기 + 자손 전체에 같은 값을 쓴다. 전체 사용 안 함 이 그렇게 된다(화면 5).
  7. 7미연결 과 미매핑 은 다른 것이다. 미연결 = 프론트 라우트 정적 맵에 없다(클릭이 404), 미매핑 = SYS_MENU_API 0건 (아무도 기능을 쓸 수 없다). 고치는 곳이 라우트와 시드로 갈린다. 미연결은 경고이지 저장 거부가 아니다 — 라우트 맵은 프론트만 아는 사실이라 서버가 판정할 수 없다.
  8. 8깊이는 리프 포함 5단이 상한이다. 주문 은 사용 프로젝트의 업무 모듈 예시이며 주문 › 출고 › 출고 지시 › 지시 등록 › 신규 등록 으로 상한을 채운 모습이다. 앞의 넷은 전부 구조 노드이고 URL 은 5단 리프에만 있다 — URL 과 자식은 배타이기 때문이다(주석 12). 업무 모듈은 SYSTEM 의 형제로 붙는다 — 템플릿이 올라가도 업무 트리가 섞이지 않는다.
  9. 11구조 노드의 URL 칸은 잠겨 있다 — URL 과 자식은 배타이기 때문이다 . 칸에 자식 수를 보여 왜 잠겼는지 를 그 자리에서 말한다. 화면 2 참조.
  10. 124단인데 URL 이 없는 이유 — 지시 등록 은 자식(신규 등록 · 일괄 등록)이 있으므로 구조 노드다. 깊이가 얕아서가 아니라 자식이 있어서 URL 이 없다. 파생 셋(매핑 API · 접근 인원 · 매핑 역할)도 리프에만 값이 있다 — 권한 대상이 리프뿐이기 때문이다.
  11. 9매핑 API 탭은 조회 전용이다 — 매핑 행 추가가 곧 접근 범위 확장이라 시드로만 바뀐다. AUTHZ-14 가 조회 전용인 것과 같은 이유다.
    액션 셀은 조회 · 저장 · 내보내기 · 실행 이다 — READ 가 아니다. 권한 화면의 액션 4열 헤더와 같은 메시지 키(action.{ACTION_CD})를 읽는다.
  12. 10모두 접기 · 모두 펼치기는 Ⓑ 다(도구 앞, controls 선언). 드래그의 전제이며(화면 3) 토글 하나로 두지 않는다 — 일부만 펼친 중간 상태에서 토글이 무엇을 가리키는지 말할 수 없다. 기본은 전부 펼침이고 저장하지 않는다 — 접힘은 그 순간의 작업 상태이지 개인화가 아니다(그리드 표준의 저장 항목에 없다).
  13. 상태 컬럼도 삭제 컬럼도 없다(그리드 표준의 양끝이 둘 다 비었다). 즉시 저장 그리드이기 때문이며 이 화면이 그 첫 실물이다 — 화면 2.
  14. 메뉴명과 메뉴 코드가 읽기 전용이다(회색 셀). 메뉴명은 서버가 만드는 메시지 키 (menu.{MENU_CD})이며 고치는 곳은 MESSAGE_MGMT 하나다. 코드는 PK 다.
  15. UP_MENU_CD 와 SORT_NO 컬럼이 없다. 트리의 모양이 곧 그 두 값이다 — 컬럼으로 두면 인가 데이터 모델이 저장 DTO 에서 빼 버린 두 필드를 화면이 되살린다.
  16. 브레드크럼 줄의 오른쪽은 화면이 채운다. [조건 ▾] 은 저장된 조회조건 (UX-07) — 열면 조회, 고르면 적용, ✕ 가 삭제, 맨 아래가 저장이다. 넷을 버튼 넷으로 두지 않는다 — 조회·적용은 이미 제스처다. [⌃ 조회조건] 은 검색 폼 접기 토글(UX-15)이며 폼 밖에 있어야 한다 — 숨기는 버튼이 폼 안에 있으면 숨긴 뒤 되돌릴 수 없다. 리프 목업이 셸 크롬을 그리지 않는 규약의 유일한 예외가 이 줄이다.
  17. 검색 폼에 조회·검색 버튼이 없다. 그리드 ①이 이미 조회를 갖는다 — 폼에도 두면 같은 조회를 부르는 버튼이 둘이 된다. 남는 것은 초기화 하나이며 컬럼 필터도 함께 지운다. Enter 는 남는다 — 버튼을 없앤 것이지 제스처를 없앤 것이 아니다.
  18. 그리드 헤더의 버튼은 전부 오른쪽이다 — 왼쪽은 제목뿐이고 도구는 맨 오른쪽 고정이다. 이 화면의 도구는 ⤓ 하나다 — 트리는 그리드 설정 창을 갖지 않는다 .

기본은 일괄 저장전부 즉시 위치 변경은 즉시일 수밖에 없다 — 형제 전체 재작성 + @CustomLock(WAIT). 그리고 이 한 그리드 안에서 섞는 것을 금지한다. 두 줄을 함께 놓으면 답이 하나로 정해진다

마스터-디테일의 잠긴 상태없다미저장 신규 행이 없으므로 상태가 셋이 아니라 둘이다
  1. 섞으면 무엇이 깨지나 — 드래그는 이미 저장됐는데 셀 편집은 아직인 상태가 같은 화면에 있게 된다. 저장 버튼이 무엇을 저장하는지 알 수 없고, 되돌릴 수 있는 편집과 없는 편집이 한 그리드에 섞인다.
  2. 대가는 요청 수다. 셀 하나에 요청 하나이며 메뉴는 드물게 바뀌는 마스터라 받아들인다 — 인가 데이터 모델이 형제 N건 쓰기를 받아들인 것과 같은 판단이다.
  3. 실패하면 셀이 되돌아간다. 되돌리기 수단이 없는 화면에서 화면과 DB 가 어긋나면 고칠 방법이 없다. 연타는 그리드 API 계약 그대로 막는다 — 응답 전에 같은 셀을 다시 고칠 수 없다.
  4. api.save 선언은 남는다. 그리드 API 계약이 그것으로 저장 버튼을 만드는 것을 이 화면만 끄고, 선언 자체는 권한 판정과 시드에 여전히 필요하다.
  5. 6URL 은 라우트 목록에서 고른다. 프론트가 MENU_URL → Component 정적 맵을 갖고 있으니 그 키가 곧 고를 수 있는 전부다 — 손으로 치게 두면 오타가 곧 404 이고, 목록이 이미 있는데 자유 입력을 두는 것은 근거가 없다. 서버 왕복이 없고 배포와 언제나 일치한다. 다른 메뉴가 이미 쓰는 URL 은 목록에서 뺀다 — 라우트 ↔ 메뉴는 1:1 이다.
  6. 7타이핑은 필터이지 입력이 아니다. 후보가 하나로 좁혀지면 자동 확정하고, 고르지 않고 벗어나면 편집 전 값으로 되돌린다 — 취소는 비우기 가 아니라 되돌리기 다. 편집을 취소했는데 값이 사라지면 취소가 데이터를 바꾼 것이 된다. 비우는 것은 고르는 행위여야 해서 (없음) 이 목록에 있다.
  7. 8URL 과 자식은 배타다. 구조 노드는 경로, 리프는 화면이며 그 사이가 없다 — 자식이 있으면 URL 칸이 잠기고, URL 이 있으면 하위 메뉴 추가와 드롭 가운데 구역이 죽는다(화면 3·4). 섹션 랜딩 화면을 포기한 것이며 그 패턴은 자식 리프로 둔다 (주문 › 주문 현황). 얻는 것은 "이 줄을 누르면 펼쳐지나 열리나" 가 트리 전체에서 하나로 정해지는 것이다.
  8. 둘 다 다른 행을 봐야 판정되므로 DB 제약이 아니다 — 저장 서비스가 막고 시드는 CI 가 검사한다. 화면의 잠금은 보조 수단이다(화면에서 숨기는 것은 UX 이지 방어가 아니다).
  9. 미연결 은 입력 방지에서 사후 진단으로 바뀐다. 콤보로 고르므로 만드는 순간에는 생기지 않고, 배포로 라우트가 사라졌거나 시드로 직접 넣은 경우에만 남는다. 여전히 저장을 막지는 않는다 — 라우트 맵은 프론트만 아는 사실이라 서버가 판정할 수 없다.
  10. 권한이 없으면 트리가 통째로 읽기 전용이 된다. 즉시 저장이라 "편집은 되는데 저장이 안 되는" 상태가 아예 없다.

기본 포커스는 취소 8
  • 요청은 형제 목록이다 — { upMenuCd, [menuCd…] }. 배열 인덱스가 곧 SORT_NO
  • 부모가 바뀌면 두 부모가 다시 쓰인다 — 뺀 쪽과 넣은 쪽을 한 요청에 담는다
  • 금지 대상은 끄는 동안 회색이 된다 — 놓아 본 뒤 에러를 내는 것보다 낫다
  • 막는 범위가 자식이다 — 자식만 막으면 손자로 끌 수 있다. 자손 전체다
  • 순서를 숫자로 입력한다 — 인가 데이터 모델이 저장 DTO 에서 뺐다. 중복·구멍·순환이 곧바로 들어온다
  • 서버가 같은 검사를 다시 한다 — 화면의 방어는 UX 이지 방어가 아니다. 네 층 중 첫 층일 뿐이다
  • 깊이 상한은 리프 포함 5단 — 서브트리를 통째로 끌면 그 높이까지 더해 판정한다
  • 락은 @CustomLock(WAIT) — 트리 전체에 불변식이 걸려 잠글 행이 없다
  1. 집합 검증이 낙관적 덮어쓰기를 막는다. 보낸 목록이 그 부모의 현재 자식 집합과 정확히 일치하지 않으면 거부하고 "트리가 변경되었습니다. 다시 불러오세요." 를 낸다 — 조용한 유실을 시끄러운 실패로 바꾸는 것이며 복구는 조회 버튼이다.
  2. 락과 집합 검증은 역할이 다르다. 락은 순환 불변식을 지키고, 검증은 "당신이 보던 트리는 낡았다" 를 알린다. WAIT 라 두 번째 저장은 기다렸다가 검증에서 걸러진다 — 화면은 스피너를 보인다(즉시실패가 아니다).
  3. 4접기가 드래그의 전제다. 24행이 전부 펼쳐진 트리에서 목적지가 화면 밖이면 끌면서 스크롤해야 하고 지나가는 행이 많을수록 엉뚱한 자리에 놓을 확률이 는다. 깊이가 5단이 되면서 더 커진 문제다.
  4. 5접힌 트리에서도 드래그가 성립해야 한다. 접힌 폴더 위에 잠시 머무르면 펼쳐지고(hover 자동 펼침), 그대로 놓으면 그 폴더의 자식 맨 끝으로 간다 — 신규 노드가 가는 자리와 같다(화면 4). 자동으로 펼친 것은 되돌리지 않는다 — 되돌리면 방금 놓은 노드가 눈앞에서 사라진다.
  5. 6가로선은 화면에 보이는 두 행 사이를 뜻한다. 그래서 펼친 폴더 아래의 선은 첫 자식 앞이고, 접힌 폴더 아래의 선은 다음 형제다. 펼친 폴더의 다음 형제 자리에 놓으려면 그 폴더를 접는다 — 접기가 보기 좋으라고 있는 것이 아니라 놓을 수 있는 자리를 바꾼다.
  6. 7마우스의 좌우 위치는 읽지 않는다. 선의 들여쓰기를 손으로 맞추게 하면 한 픽셀 차이로 부모가 바뀌고 그 실수는 놓기 전에 보이지 않는다. 깊이를 고르는 수단은 접기 하나다. 자식을 가질 수 없는 행(5단)은 가운데 구역이 죽고 위·아래는 살아 있다.
  7. 8드롭이 곧 저장이라 놓으면 묻는다. 셀은 다시 고치고 스위치는 다시 누르면 되지만 드래그는 원래 자리를 사람이 기억해야 되돌릴 수 있다 — 형제가 스무 개인 폴더에서 몇 번째였는지 기억하는 사람은 없다. 지금 과 이동 을 나란히 내는 것이 되돌릴 근거다. ‘다시 묻지 않기’ 를 두지 않는다 — 되돌릴 수 없는 작업에 두면 그 체크가 켜진 채로 사고가 난다. 취소하면 놓기 전 상태로 돌아가고 요청은 나가지 않는다.
  8. 순환과 깊이 위반은 확인까지 오지 않는다 — 애초에 놓이지 않는다. 확인은 판정이 아니라 마지막 되물음이다. 집합 검증 실패는 확인 뒤에 온다 — 확인은 클라이언트가 하고 판정은 서버가 한다(편집·검증 규약과 같은 구조).

버튼이 둘인 이유는 주석 7
  1. 이것이 그리드 표준이 없앤 편집 폼인가 — 아니다. 그 절이 없앤 것은 행을 편집하는 폼 이고 여기는 createNode(upMenuCd, menuCd) 라는 한 연산의 인자를 받는다. 그리드 표준이 "파라미터 모달은 이 규칙 밖" 이라고 적어 둔 자리이며, 칸이 하나뿐인 것이 그 증거다.
  2. 부모는 고를 수 없다 — 선택 노드다. 다른 위치에 만들려면 만든 뒤 드래그한다. 경로가 하나뿐인 대가이며 두 경로를 두는 것보다 낫다.
  3. 맨 위가 아니라 맨 끝이다. 최상위도 하위도 형제의 끝에 붙는다 — 맨 앞에 넣으면 방금 만든 노드 하나 때문에 형제 전체의 SORT_NO 를 다시 써야 한다. 추가 직후 그 행을 선택하고 스크롤한다 — 맨 끝이라 화면 밖에 생길 수 있고 만든 사람은 곧바로 URL·아이콘을 채운다.
  4. 제자리로 옮기는 것은 드래그다 — 그래서 모두 접기가 추가와 짝이다(화면 3). 맨 끝에 만들어 놓고 접은 트리에서 끈다.
  5. 메뉴명 칸이 없다. MENU_NM 은 메시지 키이고 서버가 MENU_CD 로 조립한다 — 저장 DTO 에 아예 두지 않으므로 조작할 경로가 구조적으로 없다(원칙 P1).
  6. MENU_CD 중복은 서버 검증이다 — 다른 사람이 방금 만든 것을 클라이언트가 알 수 없다.
  7. 7버튼이 둘인 이유 — 하나로 두고 라벨을 바꾸지 않는다. 선택 여부에 따라 최상위 와 하위 를 오가면 누르기 전에는 무엇이 만들어질지 모른다. 최상위 모듈은 드물게 만들고 하위는 자주 만드는데, 같은 버튼이면 잘못 눌러 최상위에 모듈이 하나 더 생기고 되돌리려면 메뉴·권한 화면 설계의 삭제 게이트를 지나야 한다. 하위 메뉴 추가는 선택이 없으면 비활성이며 사유가 붙는다.
  8. 깊이 5단에 닿은 노드는 하위 메뉴 추가 가 비활성이다 — 드롭을 막는 것과 같은 상한이며 판정도 같은 곳이다(화면 3).

  2. 즐겨찾기를 막아 두면 막다른 골목이 된다. 관리자는 남의 즐겨찾기를 볼 수도 지울 수도 없는데 메시지는 "3명이 즐겨찾기에 등록했습니다" 가 된다 — 운영자가 할 수 있는 일이 없는 거부는 거부가 아니라 고장이다. ON DELETE CASCADE 는 쓰지 않는다 — 서비스가 같은 트랜잭션에서 지운다.
  3. 매핑 API 가 막는 이유는 FK 가 아니라 다음 배포다. 시드는 전체 동기화이므로 코드에 그 화면이 살아 있으면 generateApiSeed 가 SYS_MENU_API 행을 다시 넣고, MENU_CD 가 없으면 FK 로 배포가 깨진다. 메뉴를 지우는 것은 화면을 지우는 것이며 순서는 엔드포인트 선언 제거 → 시드 재생성 → 배포 → 메뉴 삭제 다.
  4. 왜 막히는지 말한다 — 회색 버튼은 이유를 말하지 못한다(메뉴·권한 화면 설계와 같은 규약). 다중 선택 삭제는 없다.
  5. 게이트의 근거가 조회 응답에 이미 있다 — 파생 셋(매핑 API · 접근 인원 · 매핑 역할)이 마스터 컬럼이라 왕복이 늘지 않는다. 자식 노드 수는 트리 자신이 안다.

  1. 역할 화면에서는 탭 셋이 pane 하나가 됐다(둘째와 셋째가 같은 그리드였다). 여기서는 셋이 서로 다른 것을 본다 — 접지 않는다.
  2. 영향 인원 컴포넌트와 같아 보이는데 열이 둘 는다. 경유(역할명 또는 개인 예외)와 액션 4열이다 — 권한은 (메뉴, 액션) 단위라 "쓸 수 있다" 가 액션마다 갈린다.
  3. 그래서 API 를 공유하지 않는다. 메뉴·권한 화면 설계는 "같은 그리드이므로 경로도 같아야 한다" 고 했는데 여기는 같은 그리드가 아니다 — "이 역할을 가진 사람" 과 "이 메뉴에 닿는 사람" 은 조인이 다르다. 같아 보인다고 합치면 두 질문에 같은 답을 내는 API 가 생긴다.
  4. 계정 상태를 함께 보여준다 — 잠김 인 사용자는 권한은 있으나 로그인할 수 없다.
  5. 구조 노드를 선택하면 탭 셋이 0건이고 이유를 낸다 — "구조 노드는 권한 대상이 아닙니다".
  6. USE_YN='N' 인 역할도 탭 3 에 나온다 — 권한 행은 살아 있고 FK 도 살아 있다. 게이트가 막는 것은 행의 존재이지 역할의 상태가 아니다.

9. 테스트 케이스 — 주석의 주장을 전부 덮는다

주석은 "왜 이렇게 그렸는가" 를 말하고, 여기는 "그것이 지켜졌는가" 를 묻는다. 근거가 빈 케이스는 지어낸 것이다 — 문서 절이나 이 파일의 화면 번호를 가리킨다. 되면 안 되는 것도 함께 넣는다.

10. 이 목업으로 확인할 것

이 화면이 규약에 되돌려 준 것
  • 그리드 표준의 첫 실물 — "즉시 저장은 예외이며 화면이 선언한다" 가 실제로 무엇을 지우는지가 여기서 목록이 됐다(화면 2 의 표). 그리드 표준의 삭제 컬럼 표에 SYS_MENU 행이 붙었다.
  • 인가 데이터 모델의 USE_YN 은 리프의 것이다 — 구조 노드에서는 판정에 관여하지 않는다는 줄이 그 표로 올라갔다.
  • 메뉴 목록이 남긴 기본정보 탭 정리가 하나 줄었다 — 남은 것은 API_CATALOG 하나다.
아직 답이 없는 것
  • 라우트 맵을 서버가 알아야 하는가 — 지금 미연결 은 프론트만 아는 경고다. 시드로 올리면 서버가 검증할 수 있지만 화면 배포와 시드가 또 한 번 묶인다.
  • 즉시 저장의 되돌리기 — 셀은 다시 고치면 되지만 드래그는 원래 자리를 기억해야 되돌릴 수 있다.
  • 트리 전건의 상한 — 사용 프로젝트가 메뉴를 수백 건으로 늘렸을 때 드래그가 버티는지.
  • 삭제와 함께 즐겨찾기를 지우는 것을 알릴지 — 지금은 알리지 않는다.
