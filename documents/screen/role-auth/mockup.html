1. 기본 상태 — 하단이 편집 그리드가 아니다

SYS_ROLE_MENU_AUTH 에는 기간도 사유도 없다(감사 4컬럼뿐). user-auth 가 "트리만 두면 기간과 사유를 넣을 자리가 없다" 며 하단에 편집 그리드를 둔 것인데, 여기는 넣을 것이 없으므로 트리가 전부다. 하단은 영향 인원이며 읽기 전용이다.

  1. 1조회조건에 부여 상태가 없다 — user-auth 는 예정·유효·만료가 있어 그것을 뺐다 넣었다 했는데, 여기는 상태 자체가 없다. SYS_ROLE_MENU_AUTH 에 기간 컬럼이 없기 때문이다.
  2. 2역할 목록은 읽기 전용이다 — 생성·비활성화·삭제는 ROLE_MGMT 의 일이다(role.html). 고르기만 하는 목록이라 삭제 컬럼도 행 추가 버튼도 없다.
  3. 3비활성 역할도 보인다 — 권한 구성은 켜기 전에 해 두는 것이 정상이다. 비활성 역할의 권한을 고치는 것은 아무에게도 영향이 없으므로 가장 안전한 편집이다.
  4. 4트리의 정의는 사용자 화면 설계 다. 이 화면은 거기서 셋을 빼고 하나를 더한다(§2 · §3). <DataGrid> 가 아니다 — AG Grid Tree Data 는 Enterprise 이자 어휘 밖이라 AntD Table 의 트리 행이다.
  5. 5엑셀 다운로드 버튼(②)이 없다 — 이 화면의 액션이 R S 이고 EXPORT 가 없다. 사용자 화면 설계의 "액션 미정의" 가 화면 단위로 나타난 것이다 — §6.
  6. 6폴더는 파생 3-state 다(AUTHZ-03) — 전체 · 부분 · 없음. 저장하지 않는다 — 구조 노드에는 행이 생기지 않는다. 액션 열마다 따로다. → §3
  7. 7— 는 액션 미정의 — 그 메뉴에 그 액션의 API 가 없다. 이 화면 자신의 행(역할 권한 관리)이 그 실물이다 — 내보내기·실행이 — 다.
  8. 8하단은 편집 그리드가 아니다. user-auth 의 예외 목록은 트리와 같은 데이터였지만, 여기 영향 인원은 다른 데이터이며 읽기 전용이다. 저장 대상은 트리뿐이라 "목록이 원본이고 트리는 그 투영" 이 여기서는 성립하지 않는다.
  9. 9역할 부여에는 기간이 있다 — 권한에는 없지만 부여에는 있다. 예정·유효·만료를 구분 표시하는 것이 AUTHZ-13 의 요구다.
    만료된 부여도 보여준다 — 지금은 영향이 없지만 다시 유효해질 수 있다. 감추면 "영향 없다고 해서 지웠는데 다음 달에 문제가 생겼다" 가 된다.
  10. 10개인 예외 보유 열이 있는 이유 — 권한을 빼도 개인 예외로 여전히 가진 사람이 있다. 유효 권한은 합집합이므로 그 사람에게는 이 변경이 영향이 없다. 공집합 판정의 입력이 이 열이다 — §4.
  11. 브레드크럼 줄의 오른쪽은 화면이 채운다. [조건 ▾] 은 저장된 조회조건 (UX-07) — 열면 조회, 고르면 적용, ✕ 가 삭제, 맨 아래가 저장이다. 넷을 버튼 넷으로 두지 않는다 — 조회·적용은 이미 제스처다. [⌃ 조회조건] 은 검색 폼 접기 토글(UX-15)이며 폼 밖에 있어야 한다 — 숨기는 버튼이 폼 안에 있으면 숨긴 뒤 되돌릴 수 없다. 리프 목업이 셸 크롬을 그리지 않는 규약의 유일한 예외가 이 줄이다.
  12. 검색 폼에 조회·검색 버튼이 없다. 그리드 ①이 이미 조회를 갖는다 — 폼에도 두면 같은 조회를 부르는 버튼이 둘이 된다. 남는 것은 초기화 하나이며 컬럼 필터도 함께 지운다. Enter 는 남는다 — 버튼을 없앤 것이지 제스처를 없앤 것이 아니다.
  13. 그리드 헤더의 버튼은 전부 오른쪽이다 — 왼쪽은 제목뿐이고 도구 둘(⤓ ⚙)은 맨 오른쪽 고정이다.

2. 셀 상태 — 사용자 화면 설계의 일곱에서 셋을 뺀다

정의는 user-auth가 갖고 여기는 덜어 내기만 한다. 사용자 화면 설계가 "먼저 쓰는 쪽이 정의하고 뒤가 뺀다" 고 한 것이 실제로 그렇게 됐다 — 제약이 많은 쪽에서 정의했으므로 컴포넌트의 데이터 계약이 갈리지 않는다.

  2. 재부여라는 개념이 없다 — 만료 상태가 없으므로 끄면 회수, 켜면 부여 둘뿐이다. 기간·사유를 다시 받을 일도 없다.

3. 폴더 파생 3-state — 표시뿐이다 (AUTHZ-03)

구조 노드는 권한을 갖지 않는다(MENU_URL IS NULL 이면 거부). 대신 그 아래를 얼마나 줬는지를 요약해 보여준다. 누르는 것이 아니다 — 일괄 토글은 두지 않는다(주석 3).

  1. 1전체 · 부분 · 없음 셋이다. 저장되지 않는다 — 구조 노드에는 행이 생기지 않는다. 색만으로 말하지 않으므로 글자를 함께 둔다.
  2. 2파생이다 — 자식을 하나 끄면 폴더가 전체 → 부분 이 된다. 반대 방향(폴더를 저장)은 없다. 액션 열마다 따로이며 조회 열이 전체 라고 저장 열이 그런 것은 아니다.
  3. 3일괄 토글을 두지 않는다 — 어느 화면에도. 3-state 를 그리면 "누르면 자식 전부가 켜지는 것" 이 자연스러워 보이지만 뺐다.
    개인 예외는 보안 설계가 이미 막았다 — "폴더 단위로 확장하면 제2의 역할 체계가 된다".
    역할은 이유가 다르다 — ① 실수의 범위가 크다(폴더 하나가 리프 열댓 개이고 그것이 곧 보유자 전원의 유효 권한 변경이다 — §4) ② 되돌리기 규칙을 정해야 한다 (원래 켜져 있던 것만 복원할지) ③ 연쇄가 겹친다 — 액션 미정의를 건너뛰고 READ 불변식도 함께 도는데(§7), 클릭 한 번에 세 규칙이 동시에 돌면 결과를 예측할 수 없다.
    두 화면의 트리가 이로써 완전히 같아진다 — 갈리는 것이 없다.
  4. 4액션이 없는 자식(—)은 요약에서 뺀다 — 줄 수 없는 것을 안 줬다 로 세면 폴더가 영영 전체 가 되지 않는다. 내보내기 열의 없음 은 셀 수 있는 둘 중 하나도 안 줬다는 뜻이다.
  5. 표시는 양쪽 공통이다 — "이 폴더 아래를 얼마나 줬나" 는 개인 예외에서도 알아야 하는 사실이고 읽는 것은 마찰의 대상이 아니다. 그래서 사용자 화면 설계에 표시를 더했다.
  6. 필요해지면 그때 연다 — 권한을 묶어서 주고 싶은 요구는 역할 자체가 이미 그 답이며 이 화면이 그 역할을 만드는 자리다. 폴더 단위 편의가 실제로 아쉬운지는 운영에서 드러난다(§9).

4. 저장 — 확인 문구가 세 줄이다

저장 확인 ✕

권한 12건을 추가하고 3건을 삭제합니다. 1

이 역할을 가진 47명에게 적용됩니다. 2

  1. 1첫 줄은 그리드 표준이다 — 추가·수정·삭제 건수. 여기는 수정이 없다 — 권한은 있거나 없거나 둘뿐이라 켜면 추가, 끄면 삭제다.
  2. 2둘째 줄이 이 화면의 것이다 — 역할 권한을 고치는 것은 그 역할을 가진 모든 사용자의 유효 권한을 바꾼다. 건수를 모르고 누르면 안 된다.
  3. 3셋째 줄은 보안 설계가 명시적으로 요구한 것이다 — "영향 인원과 그중 유효 권한이 공집합이 되는 인원을 보여준다. 후자는 다음 로그인부터 차단되므로 관리자가 모르고 지나가면 안 된다."
    공집합이면 로그인이 차단된다 — 기준은 "역할 미부여" 가 아니라 유효 권한 공집합이다. 개인 예외만으로 일하는 사용자가 정당하게 존재하므로.
  4. 4공집합 인원이 0 이면 이 줄을 내지 않는다. 항상 보이면 읽히지 않는다.
  5. 이름을 함께 보여준다 — 건수만 알려주면 "그 2명이 누구지" 를 찾으러 다른 화면에 가야 한다. 사유(다른 역할 없음 · 개인 예외 없음)까지 붙여야 판단이 그 자리에서 끝난다.
  6. 계산의 입력이 §1 의 하단 그리드다 — 개인 예외 보유 열(주석 10)이 그것이다. 유효 권한은 합집합이므로 개인 예외가 있으면 공집합이 되지 않는다.
  7. ROLE_MGMT 이 같은 컴포넌트를 쓴다(role.html §5) — 거기서는 스위치 하나가 이 세 줄을 낸다. 역할을 끄는 것도 보유자 전원의 유효 권한을 바꾸기 때문이다. 둘이 다른 문구를 내면 같은 사고를 두 번 배운다.

  1. 1불변식은 하나다 — "다른 액션이 하나라도 켜져 있으면 READ 가 켜져 있다." 규칙 둘이 아니라 불변식 하나이고 양방향이 거기서 나온다.
    모든 액션은 그 화면 안에서 발동된다 — 버튼은 그리드 헤더가 그리고 그리드는 화면 안에 있다. 화면에 못 들어가면 어느 버튼도 누를 수 없다. READ 는 편의가 아니라 구조상의 전제다.
  2. 2남기지 않고 지운다. 도달할 수 없는 권한을 남기면 인가 데이터가 거짓말을 한다 — 감사에서 "이 역할은 저장 권한이 있다" 로 읽히는데 아무도 저장할 수 없다.
    더 위험한 것은 되살아나는 것이다 — 나중에 READ 하나를 켜는 순간 저장·실행이 함께 부활한다. 권한 확장이 리뷰 없이 일어난다.
    시드 전체 동기화 결정의 고아 행과 다르다 — 거기는 코드 변경이 사람의 결정을 지우면 안 된다는 것이었고, 여기는 사람이 같은 화면에서 하는 조작이다.
  3. 3조용히 하지 않는다. 무엇이 함께 꺼졌는지 건수를 낸다 — 저장 확인의 삭제 건수에도 그대로 반영된다.
  4. 4자동은 줄이는 쪽으로만 연쇄한다. READ 를 켠다고 나머지가 켜지지는 않는다 — 끄는 것은 축소라 안전하고 켜는 것은 확장이라 명시해야 한다.
    다른 액션을 켤 때 READ 가 따라 켜지는 것은 그 조작 자체가 이미 확장의 의사표시이기 때문이다. 이것도 알린다.
  5. 서버도 같은 검증을 한다 — 프론트는 UX 다. MENU_URL IS NULL 거부와 같은 자리이며 원칙 P1 이다.
  6. 이미 깨진 데이터가 조회되면 그대로 보여주고 경고한다. 자동으로 고치지 않는다 — 조회가 데이터를 바꾸면 안 된다. 저장할 때 정리된다.
  7. 3-state 가 그 결과를 따라 다시 계산된다(§3) — SAVE 를 켜서 READ 가 함께 켜지면 READ 열의 요약이 바뀐다. 파생이므로 자연스럽다.
    일괄 토글이 없어서 여기가 단순하다 — 있었다면 클릭 한 번에 세 규칙(토글 · 액션 미정의 건너뛰기 · READ 불변식)이 동시에 돌았을 것이다(§3 주석 3).
  8. READ 가 — 인 리프는 없다 — 화면이 있으면 그것을 그리는 조회 API 가 있고 접두 규칙상 그것이 READ 다. 그런 리프가 생겼다면 화면 설계의 오류이며 시드 리뷰에서 걸린다.

8. 테스트 케이스 — 주석의 주장을 전부 덮는다

주석은 "왜 이렇게 그렸는가" 를 말하고, 여기는 "그것이 지켜졌는가" 를 묻는다. 근거가 빈 케이스는 지어낸 것이다. 되면 안 되는 것도 함께 넣는다.

9. 이 목업으로 확인할 것

결정하면 문서 표에 적는다. 이 파일이 아니라.
  • 최후의 관리자 보호 — 관리자 역할에서 권한을 빼면 아무도 들어올 수 없게 될 수 있다. 사용자 화면 설계의 같은 미결과 한 결정이며 보안 설계의 부트스트랩 함정과 같은 구조다
  • 공집합 인원 계산의 비용 — 저장 확인마다 역할 경유 ∪ 개인 예외 를 전원에 대해 계산한다. 보유 인원이 많은 역할에서 얼마나 걸리는지
  • 폴더 단위 편의가 실제로 아쉬운가 — 일괄 토글을 뺐다(§3 주석 3). 리프가 많은 폴더에서 한 칸씩 켜는 것이 운영에서 버티는지. 아쉬우면 그때 열되 되돌리기 규칙을 함께 정한다
  • 영향 인원의 규모 — 수천 명인 역할에서 하단 그리드가 버티는지. 저장 확인의 공집합 목록도 같은 문제다(몇 명까지 이름을 보여줄지)
  • 권한 트리의 규모 — 사용자 화면 설계와 같은 미결이다. 메뉴가 수백이면 전건 렌더가 버티는지
  • READ 불변식 알림의 분량 — 여러 리프를 연달아 끄면 문구가 쌓인다. 줄이되 건수는 남긴다가 초안이다
