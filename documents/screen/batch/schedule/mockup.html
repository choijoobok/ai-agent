최근 10건 — 더블 클릭하면 실행 이력을 그 배치로 연다 9
  1. 1SORT_NO 는 사람이 정하고 드래그가 아니다. 메뉴·권한 화면 설계는 역할 목록에서 SORT_NO 를 두지 않기로 했지만 배치는 실행 순서가 의미를 갖는 묶음이 있다(마감 → 집계 → 발송). 메뉴·권한 화면 설계의 트리 드래그는 계층을 바꾸는 조작이라 드래그가 유일한 수단이었고, 여기는 평평한 목록이라 숫자 셀 편집이면 된다. 기본 정렬은 ORDER BY SORT_NO, BATCH_ID — tie-breaker 는 DB 이식성 규약이 요구한다.
  2. 2설명이 필수이고 목록에 보인다. 그 절이 "SORT_NO 와 함께 관리 화면이 목록만으로 판단 가능하게 만드는 것이 목적" 이라고 적었고 여기가 그 화면이다. 끄는 순간은 대개 장애 대응 중이라 소스를 열 시간이 없다. 한 줄로 잘리고 전체는 셀 위 팝업(largeText) — 화면 5 가 이 문장을 다시 읽어 준다.
  3. 3즉시 실행은 X 이며 쿨다운을 우회하고 락은 잡는다. 선택 0건이면 비활성. 진행률 모달은 뜨지 않는다 — 배치는 락을 잡은 다른 노드에서 돌 수 있어 ProgressHelper 의 전제가 깨진다. 던지고 끝내며, 진행 상황은 하단 pane 의 RUNNING 행이 보여준다. 화면 4.
  4. 4⤓ 가 없다 — 이 문서군에서 엑셀 버튼이 사라지는 첫 화면이다. 그리드 표준이 "E 가 없으면 ②도 감춘다" 고 정한 것의 실물이며 메뉴 목록의 액션 열이 R S X 인 것과 맞는다. 등록이 수십 건이고 원본이 화면(시드가 아니다)이라 내려받아 할 일이 없다. ⚙ 는 남는다 — 개인화다.
  5. 5PARAM_JSON 은 nclob 이 아니다(VARCHAR(2000)). 값이 손에 있으므로 배치 화면 설계의 [보기] 규약이 아니라 컬럼 계약의 긴 텍스트 에디터다 — 셀은 한 줄로 자르고 툴팁에 전체. 화면 2.
    textModal 로 적었다가 largeText 로 고쳤다(2026-08-31) — 그 어휘에는 구현이 없다(컬럼 계약 열한째). 실물은 셀 위 팝업이고 글자 수가 없다. 여기서는 손실이 작다: 값이 VARCHAR(2000) 이고 대개 한 줄이다.
  6. 6BEAN_ID 가 같은 등록이 여럿이다(인프라 데이터 모델 창고 10개). PK 가 BATCH_ID 라 가능하고, 부수 효과가 더 크다 — 락 키가 갈린다. 중복을 막지 않는다. 에디터는 richSelect 이며 목록은 스프링 컨텍스트의 BatchJob 구현에서 온다 — 메뉴·권한 화면 설계가 메뉴 URL 을 라우트 목록에서 고르게 한 것과 같은 판단이다.
  7. 7화면 기본 페이지 사이즈가 50 이다 — 등록이 수십 건이라 한 화면에 다 들어오는 것이 목적이다. 실행 이력은 100 이다.
  8. 8탭이 아니라 pane 하나다 — 메뉴·권한 화면 설계와 같은 판단이며 탭 하나짜리 탭바는 누를 곳이 없는 크롬이다. 최근 10건만 내고 페이징이 없다 — 전량은 BATCH_HISTORY 가 답한다. 하단에 ②가 없다. 마스터의 최근 결과 컬럼이 이 pane 의 첫 행과 같은 값이다.
  9. 9더블 클릭이 실행 이력을 그 배치로 연다(UX-02 멀티탭). 반대 방향도 있다 — 실행 이력의 BATCH_ID 셀 더블 클릭이 이 화면을 연다 (batch-history 화면 5). 두 화면이 왕복을 만든다.
  10. SKIP 이 둘로 갈렸다 — 건너뜀(락) 과 건너뜀(쿨다운). 하나는 정상이고 하나는 결함인데 인프라 데이터 모델은 같은 코드였다. 위 pane 의 app-02 행이 락이 제대로 동작한 증거다.

  3. 3JSON 포맷터를 두지 않는다 — 모달 안에 정렬 버튼을 넣으면 그것도 규약이 된다. 값은 2000자 상한이고 대개 한 줄이다.

쿨다운(300초)이 크론 최소 간격(60초)보다 깁니다. 실행이 건너뛰어집니다. — SETTLE_DAILY 1
관계분산 락화면
쿨다운 ≥ 크론 최소 간격등록 거부 저장이 실패한다. 두 셀에 오류 표시
쿨다운 ≥ 최소 간격 × 0.5WARN 저장 확인에 경고를 얹는다 — 막지 않는다(화면 5)
그 외통과—
  1. 1오류가 두 셀에 걸린다. 어느 쪽이 틀렸는지 서버가 말할 수 없다 — 관계가 틀린 것이다. 둘 다 표시하고 문구가 관계를 말한다. 판정은 서버다 — 크론 최소 간격은 "고정 기준시각에서 다음 실행 N개를 뽑아 인접 간격의 최솟값" 이라 크론 파서가 필요하고 기술 스택에 없다. 서버 검증이 없어지는 것은 아니다 — 그 자리다. 편집·검증 규약의 세 층 중 컬럼 검증이다 — 같은 행의 두 값 비교이며, 그 절이 "컬럼 검증이 값이 아니라 행 전체를 받는 이유" 로 든 경우가 정확히 이것이다.
  2. 2다음 실행 파생 컬럼이 크론을 눈으로 확인시킨다. 서버가 목록 조회에서 계산해 내려주므로 API 를 늘리지 않는다 — 저장 후 재조회에서 새 값이 온다. 검증에 걸린 행은 이 칸이 빈다(위 첫 행).
  3. 기동 시 전건 재검증도 있다 — 화면 밖이다. 그때 걸린 배치는 다음 실행 이 비고 최근 결과 가 건너뜀(쿨다운) 으로 드러난다(화면 1).
  4. 배치 빈에 @CustomLock 이 붙어 있으면 기동이 거부된다 — 스케줄러 래퍼의 락과 이중으로 걸리고 키도 다르다. 화면 밖이지만 같은 원칙 P1 이다.

안판단
스위치를 즉시 저장 기각 — 토글하는 순간 저장되면 확인을 낼 자리가 없다. 컬럼 계약이 "스위치가 즉시 저장을 뜻하지 않는다" 고 적은 이유가 이것이다
일괄 저장 + 확인채택 — BATCH_DESC 를 그대로 읽어 준다
  1. 1켜는 것은 확인하지 않는다 — 축이 다르다. 켜는 것은 되돌릴 수 있고 끄는 것은 시간이 간다. 여러 건을 함께 끄면 목록으로 낸다 — 메뉴·권한 화면 설계의 영향 인원 확인과 같은 컴포넌트다.
  2. 2인프라 데이터 모델의 셋째 항목이 여기서 값을 한다 — "껐다 켜면 저절로 따라잡는 배치와 건너뛴 구간이 영영 비는 배치는 끄는 결정의 무게가 다르다." 그 문장을 끄는 순간에 보여주지 않으면 적어 둔 의미가 없다. 그래서 BATCH_DESC 가 필수다(화면 1 주석 2).
  3. 3쿨다운 WARN 도 이 확인에 함께 실린다(화면 3). 확인이 하나여야 사용자가 한 번 읽는다 — 두 번 뜨면 두 번째를 넘긴다.
  4. USE_YN='N' 인 배치는 스케줄러가 등록조차 하지 않는다 — 크론이 남아 있어도 돌지 않으며 SKIP 이력도 남지 않는다. "안 돈다" 와 "건너뛰었다" 는 다른 사건이며, 실행 이력에서 행이 없으면 꺼져 있는 것이다(batch-history 화면 3).

  1. 1이력이 게이트가 아닌 이유 — 이력에는 FK 가 없다. 등록을 지워도 SYS_BATCH_HISTORY 행은 그대로 남으며 남아야 한다 — 로그 데이터 모델이 "존재하지 않는 주체의 기록도 남아야 한다" 고 한 것과 같은 규칙이다. 이력이 게이트가 되면 오래된 배치는 영영 못 지운다.
  2. 2대신 고아가 생긴다 — 배치명이 조인되지 않는다. 실행 이력 화면이 (삭제된 배치) 로 그리고 BATCH_ID 는 그대로 보인다. 로그 화면 설계가 로그인 이력에서 없는 계정에 이름을 붙이지 않기로 한 것과 같은 판단이다 — 빈칸으로 두면 조회가 덜 된 것으로 읽힌다.
  3. 삭제 컬럼이 있다 — 물리 삭제를 하므로 오른쪽 끝 시스템 컬럼이 붙는다. SYS_USER와 다르다.

7. BATCH-06(실패 알림)은 이 화면에 자리가 없다

  • 메뉴 목록은 BATCH-06 을 이 메뉴에 배정했는데 인프라 데이터 모델의 컬럼 표에 알림 설정이 없다
  • 배치별 on/off 를 두면 — 꺼 둔 것을 잊는다. 배치 실패는 전부 알려야 하는 사건이다
  • 전역 설정 하나 — 수신 대상과 채널. 배치별 예외를 두지 않는다
  • 키 이름과 저장처는 66(공지 · 알림) 이 채널을 정할 때 함께 — 배치 화면 설계 미결
컬럼을 두지 않기로 한 것도 결정이다 — 두었다면 인프라 데이터 모델에 NOTI_YN 이 생기고, 끈 채로 잊힌 배치가 생겼을 것이다

8. 테스트 케이스 — 주석의 주장을 전부 덮는다

주석은 "왜 이렇게 그렸는가" 를 말하고, 여기는 "그것이 지켜졌는가" 를 묻는다. 근거가 빈 케이스는 지어낸 것이다. 되면 안 되는 것도 함께 넣는다.

9. 이 목업으로 확인할 것

이 화면이 규약에 되돌려 준 것
  • 인프라 데이터 모델의 BATCH_DESC 가 화면을 얻었다 — 그 절이 "목록만으로 판단 가능하게" 를 목적으로 적었고, 필수 + 목록 표시 + 끌 때 재확인 셋이 그것을 실현한다(화면 1 · 5).
  • 분산 락 규약의 SYS-19 검증이 실물이 됐다 — 거부는 두 셀 오류, WARN 은 저장 확인. 판정은 서버이고 화면은 표시만 한다(화면 3).
  • E 없는 화면의 첫 실물 — 그리드 표준의 "E 가 없으면 ②도 감춘다" 가 처음 쓰인다(화면 1 주석 4).
  • 스위치가 즉시 저장이 아닌 이유가 실물로 나왔다 — 즉시 저장이면 확인을 낼 자리가 없다(화면 5).
아직 답이 없는 것
  • BatchJob 의 취소 계약 — batch-history 화면 4 와 한 항목이다.
  • 파라미터 키 검증 — 훅이 있으면 화면이 키까지 막을 수 있다.
  • BATCH-06 의 설정 자리 — 전역 하나로 정했고 키 이름과 저장처가 남았다. 66 이 채널을 정할 때 함께.
  • 등록이 수백 건이 됐을 때 — PARAM_JSON 으로 검색할 수 없다는 인프라 데이터 모델의 대가가 그때 아프다.
