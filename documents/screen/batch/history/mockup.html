  1. 1duration 렌더러가 필요하다 — ELAPSED_MS 는 밀리초이고 3725000 을 사람이 읽지 않는다. 서버가 포맷한 문자열 컬럼은 기각이다 — 정렬이 문자열 정렬이 된다(9분 > 10분). 화면이 셀에서 계산하는 것도 기각이다 — 컬럼 계약이 닫아 둔 렌더 함수다. 값은 원본 ms, 표시만 사람 단위이며 정렬 · 필터 · 엑셀이 전부 ms 를 본다. 컬럼 계약의 "렌더러가 충분한가" 에 첫 사례이며 어휘가 일곱이 됐다.
  2. 2정렬이 열려 있다 — 64 를 상속하지 않는다. 인프라 데이터 모델이 ELAPSED_MS 를 저장하기로 한 이유가 "오래 걸린 배치 정렬이 인덱스를 못 탄다" 였다 — 정렬을 끄면 그 컬럼을 저장할 이유가 사라진다. 로그 화면 설계가 "정렬이 아니라 거르기가 맞는 도구" 라고 한 것의 반대 사례다. 총 건수도 함께 센다(주석 9) — 둘은 한 결정이다. 소요 이상 조건으로 좁힌 뒤 소요 정렬로 훑는 것이 성능 진단 동선이다.
  3. 3S 가 없는데 X 가 있다. 저장 버튼도 행 추가도 없고 전 컬럼이 읽기 전용이라 상태 컬럼도 삭제 컬럼도 붙지 않는다(§4) — 메뉴·권한 화면 설계의 조회 전용 모양에 중단 하나가 더 있는 형태다. 화면 4.
  4. 4⤓ 가 있다 — 스케줄 관리와 반대다(batch-schedule 화면 1 주석 4). "지난달 실패 목록" 을 개발팀에 넘기는 일이 실제로 있다. 메뉴·권한 화면 설계의 "조회 전용은 쓰기에 관한 말이지 내보내기에 관한 말이 아니다" 가 그대로 온다. 가장 쓸모 있는 조합은 실패만 + 기간 + 전체 다.
  5. 5BATCH_ID 셀 더블 클릭 → BATCH_SCHEDULE 을 그 배치로 연다(UX-02 멀티탭). 로그 화면 설계가 요청 URI 에 둔 것, 메뉴·권한 화면 설계가 하단 pane 에 둔 것과 같은 어휘다. 반대 방향은 batch-schedule 하단 pane 이며 둘이 왕복을 만든다.
  6. 6nclob 둘을 목록에 싣지 않는다 — ERR_MSG(예외 스택)와 RSLT_DTL_MSG(처리한 대상 목록)이다. 로그 화면 설계의 규약을 상속하는 유일한 항목이며 파생 컬럼 + link + getDetail. [보기] 는 실패 전용이 아니다 — 성공 행에도 대상 목록이 있으면 붙는다. 모달은 탭 둘이며 로그 화면 설계와 같은 모양이다. 화면 2.
  7. 7SKIP 이 둘로 갈렸다(인프라 데이터 모델을 고친다). 같은 코드에 정상과 결함이 함께 있어 화면이 색을 줄 수 없었다. 건너뜀(락) 은 회색 — 노드 3대면 매 주기 2건이 쌓이는데 빨강으로 두면 목록의 3분의 2가 경고가 되고 진짜 문제가 묻힌다. 건너뜀(쿨다운) 은 주의색 — 분산 락 규약이 막으려던 사고다. 화면 3.
  8. 8등록이 지워지면 배치명이 빈다. 이력에는 FK 가 없어 행이 남으며 남아야 한다. 빈칸으로 두지 않는다 — (삭제된 배치) 로 그리고 BATCH_ID 는 보인다. 로그 화면 설계가 없는 계정에 이름을 붙이지 않은 것과 같은 판단이다.
  9. 9총 건수를 센다 — 로그 화면 설계를 상속하지 않는다. 등록 수십 건 × 하루 수십 회라 수천만 행이 되지 않는다. 번호 있는 페이징이 있어야 임의 컬럼 정렬이 성립한다(주석 2). 기간도 필수가 아니다 — 기본값만 둔다.

이미 중단 요청됨 (09:17) — 버튼이 비활성이다
  1. 1실패만 인데 0건이면 진단이다 — access-log · login-log · error-log 와 같은 규칙이며 메뉴·권한 화면 설계에서 온 것이다. 0건에는 언제나 이유가 있고, 화면이 아는 이유는 화면이 말한다.
  2. 2중단은 선택 행 중 진행 중 인 것만 대상이다. 아니면 버튼이 비활성이다 — "눌렀는데 안내가 뜨는 것보다 누를 수 없는 것이 먼저 보이는 편이 낫다".
  3. 기간이 필수가 아니다 — 비우고 조회하면 전량이며 1년치가 수십만 행이라 느려진다. 막지는 않는다 — 64 와 다른 점이다.

7. 테스트 케이스 — 주석의 주장을 전부 덮는다

주석은 "왜 이렇게 그렸는가" 를 말하고, 여기는 "그것이 지켜졌는가" 를 묻는다. 근거가 빈 케이스는 지어낸 것이다. 되면 안 되는 것도 함께 넣는다.

8. 이 목업으로 확인할 것

이 화면이 규약에 되돌려 준 것
  • RSLT_CD 가 넷에서 여섯이 된다 — SKIP → SKIP_LOCK · SKIP_COOLDOWN, CANCELED 추가. 하나는 정상이고 하나는 결함인데 같은 코드였다(화면 3).
  • CANCEL_REQ_DTM 신설 — 인프라 데이터 모델이 "둘 중 하나" 로 물었는데 답은 둘 다이고 축이 다르다. 요청과 결과다(화면 4).
  • renderer: 'duration' — 컬럼 계약의 "렌더러가 충분한가" 에 첫 사례. 어휘가 일곱이 된다(화면 1 주석 1).
  • 로그 화면 설계의 넘김이 정확하지 않았다 — "규약 셋을 상속하지 않는다" 였는데 nclob 미적재는 상속한다.
  • 파생 조건의 네 번째 사례 — 결과 묶음(72).
  • RSLT_MSG 를 요약과 상세로 가른다(RSLT_DTL_MSG 신설) — 배치가 처리한 대상 목록을 남기려니 1000자가 모자랐다. 통째로 nclob 이면 요약이 목록 컬럼 자격을 잃는다. 모달이 탭 둘이 된다(화면 2).
아직 답이 없는 것
  • BatchJob 의 취소 계약 — "체크포인트마다 확인한다" 를 인터페이스에 어떻게 넣고, 확인하지 않는 구현을 빌드가 막을 수 있는지.
  • duration 의 표시 단위 — 1시간 2분 5초 인지 01:02:05 인지. 다국어에서 갈린다.
  • 유령 판정의 임계값 — LOCK_EXPIRY_SEC 를 그대로 쓴다. 배수를 둘지 — 만료 직후를 죽었다고 부르면 오탐이 난다.
  • SKIP_LOCK 이 얼마나 쌓이나 — 노드 3대 × 5분 주기면 하루 576건이다. 1년 보존에서 이력의 대부분이 될 수 있다.
  • 상세 결과의 절단 상한 — RSLT_DTL_MSG 에 얼마나 적을지는 배치가 정한다. 요청 전문의 1MB 절단을 그대로 쓸지, 1년 보존에 맞는 상한을 따로 둘지.
