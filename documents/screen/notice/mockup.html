  4. 4게시 상태는 파생이며 서버가 판정한다. 클라이언트가 계산하면 PC 시계가 틀린 사람에게 다른 배지가 뜨고, 기준 시각은 브라우저가 아니라 app.business-timezone 이다. 배지 색이 셋이다 — 예정 은 아직 아니다, 게시중 은 지금 보인다, 종료 와 내림 은 더 안 보인다 라서 같은 회색이다. 내림 은 기간과 무관하게 이긴다 — 축이 다르기 때문이다(USE_YN).

  6. 620건씩이다 — 행마다 nclob 이 달려 있다. 목록에서 읽지는 않지만 행 수를 늘릴 이유도 없다.

  8. 게시 기간 조회조건이 비어 있다. 판의 시스템 기본값이 최근 7일인데 그것을 그대로 두면 지난달에 올린 게시중 공지가 기본 조회에서 사라진다 — 공지는 이력이 아니라 지금 무엇이 걸려 있는가 를 보는 목록이다. 화면 선언이 기본값을 빈 값으로 덮는다.
  9. 다중 선택을 연다. 하단 pane 이 없으므로 그리드 표준의 제약이 걸리지 않는다 (batch-schedule 은 pane 이 있어 단일이었다). 여러 건을 한 번에 지우는 일이 실제로 있다(화면 4).

컬럼 계약의 editor 넷이 화면왜
text — 셀 안 한 줄—수천 자가 들어온다
largeText — 셀 위 팝업채택 판이 내장으로 준다(agLargeTextCellEditor) — 어휘에 있고 구현이 있는 유일한 긴 텍스트 에디터다

richText — 리치 에디터—라이브러리 미정. 프론트 스택이 범위에서 제외했다
  1. 1셀은 한 줄로 자른다 — 말줄임 + 툴팁 미리보기. 정렬을 끈다: Oracle 이 CLOB 의 ORDER BY 를 막아 4벤더 무수정 기동이 깨진다(22). 필터도 끈다 — 값이 길어 set 필터가 되지 않고, 부분 일치는 조회조건이 아니라 결과 내 필터라 오해를 부른다.
  2. 2감수한 것이 둘이다. 글자 수 표시가 없고(본문은 nclob 이라 상한이 사실상 없어 손실이 작다 — 500자 제한이 있는 TITLE 과 갈리는 자리다), 팝업이 셀 위라 모달보다 좁다. 그 둘로 화면이 못 서는 것은 아니며 없는 어휘를 쓰는 것보다 있는 어휘로 서는 편이 낫다 — 어휘에 있는데 어댑터가 모르면 조용히 무시된다(컬럼 계약의 주의). textModal 이 서는 날 바꿀 자리는 이 컬럼의 editor 한 줄이다.
  3. 3서식 도구를 그리지 않는다. 굵게·목록·링크 버튼을 하나라도 두면 그것이 곧 HTML 저장이고, 저장 시 sanitize 가 필수가 된다 — 공지는 전 사용자에게 렌더링되므로 XSS 의 이상적인 통로다.
  4. editable: false 가 못 본다 를 뜻하지 않는다. 긴 텍스트는 열어야만 보이므로 읽기 전용 컬럼도 읽기 모드로 연다 — 그 자리가 viewer 이며 값은 역시 largeText 다. noti-request.html 화면 2 가 그 실물이다.
  5. 에디터를 붙이는 프로젝트가 할 일 — CONTENT_TYPE_CD 를 HTML 로 저장하고 editor 를 richText 로 바꾼다. 표시 측도 함께 바꾼다: 팝업과 공지 탭이 지금은 텍스트로 그리므로, 분기 없이 HTML 을 저장하면 태그가 글자로 보인다.

6. 테스트 케이스 — 주석의 주장을 전부 덮는다

주석은 "왜 이렇게 그렸는가" 를 말하고, 여기는 "그것이 지켜졌는가" 를 묻는다. 근거가 빈 케이스는 지어낸 것이다 — 문서 절이나 이 파일의 주석 번호를 가리킨다. 되면 안 되는 것도 함께 넣는다.

7. 되돌려 준 것 · 실물이 이 파일을 고친 것 · 남은 것

이 화면이 규약에 되돌려 준 것
  • 파일·알림 데이터 모델에 게시 기간 컬럼 둘이 는다 — NOTICE_FROM_DTM · NOTICE_TO_DTM. noti-inbox.html 의 게시중/종료 배지가 그때까지 근거 없이 떠 있었다.
  • 인증 화면 설계의 공지 미결 넷이 닫힌다 — 대상 · 읽음 · 게시 기간 · 팝업 조건. 넷이 한 물음의 갈래였다.
  • E 없는 화면의 두 번째 실물 — 근거가 batch-schedule 과 다르다: 저쪽은 원본이 화면, 여기는 nclob 이 엑셀에서 잘린다(§1 주석 5).
  • 파생 조건의 다섯째 사례 — 게시 상태 는 컬럼이 아니라 USE_YN + 기간 둘의 조합이다(72).
실물이 이 파일을 고친 자리 셋(2026-08-31) — 목업이 틀렸던 것이 아니라 그려 볼 수 없던 것이다.
  1. 본문 에디터를 textModal 로 그렸다. 컬럼 계약의 표에 그 이름이 있고 큰 textarea + 글자 수 라고 쓰여 있어 골랐는데 구현이 없는 어휘였다 (같은 문서 의 열한째). 실물은 셀 위 팝업이고 글자 수가 없다 — 화면 2 를 그렸고 컬럼 계약과 공지·알림 화면 설계도 함께 고쳤다.
  2. 기본 조회 결과에 내림 을 그렸다. 조회조건은 예정 · 게시중 · 종료 셋인데 결과에 넷째가 있는 그림이었다 — 그 줄을 뺐다(§1 주석 9).
  3. 번호 컬럼을 bigint 으로 적었다. 그 어휘는 구현 목록에 없다 — number 다.
아직 답이 없는 것
  • 공지 첨부 — 파일·알림 데이터 모델이 SYS_FILE_REF 로 붙이기로 했고 파일 업로드가 미뤄져 있다. 붙는 날 삭제가 참조를 함께 지운다(화면 4 주석 2).
  • textModal 자체 구현(컬럼 계약 열한째) — 이 화면이 그것을 기다리지 않는다. 서는 날 바꿀 자리는 본문 컬럼의 editor 한 줄이고, 요청함의 viewer 가 함께 온다.
  • richText 에디터 라이브러리 — 이 화면은 largeText 로 서므로 막지 않는다. 붙이는 프로젝트가 고른다.
  • 공지가 몇 건까지 쌓이나 — 제목 contains 에 인덱스를 두지 않았다.
  • 팝업 dismiss 키가 localStorage 를 얼마나 먹나 — 공지마다 키 하나이고 청소가 팝업 렌더 때만 돈다.
