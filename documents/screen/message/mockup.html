지원 언어 2 · 값이 있는 1
  1. 1값으로 키를 찾는 조건이 이 화면의 핵심이다. 운영자는 "화면에 보이는 이 문구" 를 들고 오지 키를 들고 오지 않는다. 어느 언어의 값이든 걸려야 하며, 그래서 하단 조건이 마스터를 거른다.
  2. 2사용처는 읽기 전용이다. generateMessageSeed 가 프론트 MSG 와 백엔드 MsgKey 상수를 스캔해 전건 재계산한다 — 화면의 저장 DTO 에 필드가 없다(기준정보 데이터 모델이 DTL_NM 에 쓴 방식).
  3. 3데이터 는 시드가 건드리지 않는다. code.* · menu.* 는 소스 상수가 아니라 데이터에서 조립된 키이고 CODE_MGMT와 메뉴 저장이 그 행을 만든다. 이 예외를 잊으면 그 키 전부가 죽은 키로 잡힌다.
  4. 4미번역은 경고이지 결함이 아니다. 메뉴·권한 화면 설계의 미매핑 과 같은 어휘를 쓰되 색이 한 단계 낮다 — 값이 없어도 기준정보 데이터 모델의 폴백이 받아 화면은 동작한다. 번역 컬럼은 list 에서 계산한다.
  5. 5미사용 이 죽은 키다. 양쪽 상수에서 못 찾았다는 뜻이며 고치는 곳은 "지우거나, 쓰기 시작한다" 다. 막지는 않는다 — 번역을 엑셀로 먼저 넣거나 배포 예정 화면의 키가 먼저 들어오는 정상 경로가 있다.
  6. 6하단에 버튼이 하나도 없다. 감춘 것이 아니라 api 선언이 없는 것이다 — 그리드 표준의 ①은 그 선언이 채운다. 조회가 있으면 list 의 미저장 편집이 날아가고, 저장이 있으면 저장 단위가 둘이 된다.
  7. 7행 추가가 없다(2026-08-30 개정 · 화면 3). 키를 만드는 화면이 아니다 — 키의 원본은 소스 상수이거나 데이터 파생(code.* · menu.*)이고 이 화면은 그 어느 쪽도 아니다. 감춘 것이 아니라 addRow 선언이 없다.
  8. 8엑셀 다운로드가 아직 없다(화면 8). 정해진 것은 ②가 아니라 ①이고 서버 POI(엑셀 세 갈래 결정의 셋째)라는 것까지다 — 화면은 키 단위로 접혀 있는데 엑셀은 (MSG_KEY, LANG_CD) 원 테이블 모양이어야 하기 때문이다. 경로가 아직 없어 버튼도 없다.
  9. MSG_GRP_CD 가 없다. 분류와 번들 경계 둘을 지고 있었고 MSG_KEY 에만 종속인데 PK 에 LANG_CD 가 있어 부분 함수 종속이었다. 번들 컬럼은 사용처의 파생이며 저장하지 않는다 — 화면 흐름이 "프론트가 쓰는 것 전체" 로 경계를 정했으므로 경계가 곧 사용처다.

2. 저장 단위는 마스터 하나다 — 하단은 list 컬럼이다

조회      → 마스터 행마다 values: [{langCd, msgVal}, …] 를 함께 받는다
행 클릭   → 하단이 그 list 를 그린다              (서버 호출 없음)
하단 편집 → 마스터 행의 list 가 바뀌고 상태가 ✎  
저장      → 마스터 저장 하나. 백엔드가 list 를 루프한다
컬럼 계약이 이 경로를 이미 적어 뒀다 — "화면의 다른 그리드: 하단 그리드에서 행을 쌓고, 화면이 그것을 추려 마스터 행의 필드에 넣는다". 이 화면이 그 첫 실물이다 1
하단에 없는 버튼있으면 무엇이 깨지나
조회다시 조회하면 list 의 미저장 편집이 날아간다. 하단은 서버가 아니라 마스터 행을 원본으로 삼는다
저장저장 단위가 둘이 되어 "키는 저장됐는데 값은 안 됐다" 가 생긴다
행 추가행 수는 지원 언어 수로 고정이다 — 더할 것이 없다
그리드 설정컬럼이 둘이고 개인화할 것이 없다
  1. 1테이블은 둘, 화면도 둘, 저장은 하나다. 기준정보 데이터 모델이 SYS_MESSAGE_KEY(코드 소유)와 SYS_MESSAGE(사람 소유)로 쪼갰고, 컬럼 계약의 list 가 그 둘을 화면에서 한 행으로 묶는다 — "배열은 전송 형태이지 저장 형태가 아니다".
  2. 그리드 표준의 UX-10 확인이 필요 없어진다. 그 절은 "디테일에 미저장 편집이 있는 채로 다른 마스터 행을 클릭하면 확인 다이얼로그를 띄운다 — 리셋은 되돌릴 수 없다" 고 했는데 여기서는 리셋이 없다. 다른 행에 갔다 돌아오면 편집이 그대로 있다 — 잃을 것이 없으면 물을 것도 없다.
  3. list 컬럼은 정렬·필터를 둘 다 끈다 — 배열은 비교 대상이 아니다. 그래서 미번역 찾기가 컬럼 필터일 수 없고 서버 조건이다(화면 6).

3. 행을 더할 수 없다 — 키를 만드는 화면이 아니다 (2026-08-30 개정)

이 절은 뒤집혔다. 전에는 "신규 키도 같은 경로다 — 하단이 리셋되지 않는다" 였고 그 시연이 행 추가 버튼이었다. 지금은 addRow 선언이 없다 — 손으로 더한 키는 태어날 때부터 사용처 없음 이고 다음 시드 생성도 그것을 알지 못하므로, 이 화면이 스스로 죽은 키로 표시하는 행을 만드는 셈이 된다. 지우라고 만드는 행이다.

  1. 1감춘 것이 아니라 선언이 없다. addRow 를 적지 않았으므로 버튼이 나오지 않는다 — 메뉴·권한 화면 설계의 "이 화면의 절반은 선언하지 않은 것으로 이루어져 있다" 를 여기서도 쓴다.
  2. 2메시지 키 가 열리지 않는다. 여기서 고친 키는 다음 생성이 되돌린다 — 원본이 소스 상수이거나 데이터이기 때문이다. required: true 가 적혀 있었는데 이미 죽은 선언이었다: 편집할 수 없는 칸은 검증이 필수로 보지 않는다.
  3. 3미사용 이 죽은 키다. 양쪽 상수에서 못 찾았다는 뜻이며 사용처는 시드가 소유한다 — 저장 DTO 에 필드가 없다. 정상이 압도적인 목록에서는 칠하지 않는 것이 기본이고 죽은 키만 눈에 남는다.
  4. 4지우기는 남는다. 죽은 키를 걷어내는 것이 이 화면의 두 일 중 하나다 — 게이트가 없다: SYS_MESSAGE_KEY 는 물리 삭제이며 값 → 키 순서라 FK 가 막을 것이 없다(화면 4).
  5. MSG_KEY 를 비우는 경로가 사라졌다. 칸이 열리지 않으므로 "키가 없으면 하단이 잠긴다" 는 상태도 도달할 수 없다.

4. 저장이 백엔드에서 무엇이 되나 — list 를 루프한다

POST /api/service/message/save
{ "rows": [

values 는 그 키의 전량이다 — 델타가 아니다. 화면이 지원 언어 전부를 들고 있으므로 부분만 보낼 이유가 없고, 전량이면 서버가 상태를 추론하지 않는다 1
마스터 상태백엔드가 values 를 루프하며
C SYS_MESSAGE_KEY 행 INSERT(USE_SCOPE='NONE') → 값이 있는 항목만 SYS_MESSAGE INSERT
U 항목마다 upsert. msgVal 이 null 이면 그 행을 DELETE
D 값 → 키 순서로 DELETE — 게이트가 필요 없는 이유다 3
막는 것어디서문구
LANG_CD 가 지원 언어가 아니다서버 ERR_MESSAGE_LANG_UNKNOWN — 지원 언어는 설정이 갖는다
고치려는 키가 이미 지워졌다서버 ERR_MESSAGE_KEY_MISSING
MSG_KEY 중복화면 + 서버 화면에서는 도달할 수 없다 — 신규 행이 없다(화면 3). 서버는 그래도 본다: 요청 본문은 조작할 수 있고, 두 번째 C 의 존재 확인이 첫 번째의 flush 를 만나지 못해 조용히 덮인다
  1. 1한 트랜잭션이다. 키와 값이 같은 요청에 있어야 FK 순서를 서버가 정할 수 있다. SYS_CACHE_VERSION.message 는 저장 한 번에 +1 — 행 수만큼 올리지 않는다.
  2. 2USE_SCOPE 를 화면이 보내지 않는다. 시드가 소유한다 — 저장 DTO 에 필드를 두지 않으므로 받을 경로가 구조적으로 없다(원칙 P1).
  3. 3삭제에 게이트가 없다. 그리드 표준의 게이트는 DB 가 거부할 것을 조회 시점에 미리 알리는 장치인데, 삭제 서비스가 값 → 키 순서로 지우므로 거부되지 않는다. 대신 확인이 건수를 말한다 — "ko·en 2건이 함께 삭제됩니다."
  4. 빈 값은 null 로 보낸다. 빈 문자열을 저장하면 기준정보 데이터 모델의 폴백이 죽는다 — NULL 은 아직 안 채웠다, 빈 문자열은 의도적으로 비웠다 이고 후자의 요구가 없다.
  5. 그리드 API 계약의 확인 건수는 키 단위로 센다 — "추가 1 · 수정 2 · 삭제 1건". 하단 편집은 그 키의 수정으로 묶인다.

  1. 1리터럴을 금지한다. ESLint · ArchUnit 이 막으며, 접두 액션 · 시드 생성 결정이 endpoints 상수에 대해 "URL 문자열 리터럴을 금지하고 상수만 쓰게 한다" 고 한 같은 장치다. 그러면 선언 = 사용이 구조적으로 보장되고 상수 목록이 곧 "누가 이 키를 쓰는가" 가 된다.
  2. 2미분류 배지가 사라졌다. 이전 판은 MSG_GRP_CD 가 공통코드라 관리자가 코드가 모르는 그룹을 추가할 수 있었고 그것을 표시할 배지가 필요했다. 키의 원천이 소스가 되면서 그 상태 자체가 없어진다.
  3. 행은 추가만, USE_SCOPE 는 전건 재계산이다. 시드 전체 동기화 결정의 전건 동기화와 갈리는 자리이며 이유는 하나 — 번역이 딸려 있다. 코드에서 사라진 키의 행을 지우면 사람이 쓴 것이 사라진다. 그래서 지우지 않고 미사용 으로 표시만 한다.
  4. checkMessageSeed 가 CI 에서 재생성 결과와 커밋본을 비교한다(25). 시드가 키와 사용처만 담으므로 비교가 성립한다 — 값은 파일에 없다.
  5. 미사용 을 CI 경고로 올릴지는 기준정보 화면 설계 미결이다 — 메뉴·권한 화면 설계가 미매핑에 대해 남긴 것과 같은 성격이고 정상 경로가 있어 오탐이 난다.

그래도 엑셀 세 갈래 결정이 셋째 경로를 만든 이유는 그대로 맞는다 — "화면 구조와 엑셀 구조가 일치하지 않기 때문이다 … 사용자는 합친 엑셀 하나를 원한다." 화면은 키 단위로 접혀 있고 번역자는 키 × 언어 표를 원한다 2

  5. 기준정보 데이터 모델의 "키 충돌 처리" 결정은 살아 있다 — 폐기가 아니라 흡수됐다. 신규·변경·동일은 rowState C · U · 없음이고(동일은 그리드 표준이 보내지 않는다), 오류는 편집·검증 규약의 검증 표시이며, 전건 한 트랜잭션 은 일괄 저장(UX-14)이 원래 그렇다. 사라진 것은 결정이 아니라 별도 규약이다.

이 화면이 닫은 것
  • 키의 원천이 정해졌다 — 프론트·백엔드 전역 상수에서 동기화한다. 접두 액션 · 시드 생성 결정이 API 에 대해 한 것과 같은 모양이고, 다른 점은 행을 지우지 않는다는 것이다 — 번역이 딸려 있기 때문이다.
  • MSG_GRP_CD 가 지고 있던 두 역할이 갈라졌다 — 번들 경계는 사용처의 파생이 되고 분류는 사라졌다(분류로 찾지 않고 검색으로 찾는다). 미분류 배지가 개념째로 없어졌다.
  • 부분 함수 종속이 사라졌다 — 테이블을 키(코드 소유) · 값(사람 소유) 으로 쪼갰다. 소유가 테이블 경계가 된 것이며 시드 전체 동기화 결정의 축이 그렇게 표현된다.
  • 쪼개기의 대가로 걱정했던 둘이 치러지지 않았다 — 다만 앞엣것은 이유가 바뀌었다: 등록이 아예 화면의 일이 아니게 됐고(화면 3 — 2026-08-30), 삭제는 서비스가 순서대로 지워 게이트가 필요 없다(화면 4 주석 3).
  • 컬럼 계약의 "화면의 다른 그리드" 경로가 첫 실물을 얻었다(화면 2) — 하단에 버튼이 하나도 없는 형태가 그 결과다.
  • 엑셀 세 갈래 결정의 셋째 경로(서버 POI)가 처음 쓰일 자리가 정해졌다(화면 8) — 화면 구조와 엑셀 구조가 다르다는 그 절의 이유가 그대로 맞는다. 다만 아직 붙이지 않았다: 다운로드 이력·상한이 함께 와야 한다.
  • 엑셀 업로드가 이 화면에서 빠졌다 — 같은 이유다. 구조가 다르다는 것이 다운로드에서는 서버 POI 로 간다 였고 업로드에서는 여기 붙이지 않는다 였다. 기준정보 데이터 모델의 충돌 규약은 rowState 로 흡수됐다.
아직 답이 없는 것
  • 미사용(죽은 키)을 CI 경고로 올릴지 — 메뉴·권한 화면 설계가 미매핑에 대해 남긴 것과 같은 성격이고 정상 경로가 있어 오탐이 난다.
  • 서버 POI 파일의 보관과 다운로드 URL 규약 — 이제 하나다 (엑셀 다운로드). 47 과 함께 정해져야 하며, 그것이 정해지기 전에는 버튼도 없다(화면 8).
  • MSG_VAL 2000자 상한 — 약관·안내문이 들어오면 nclob + textModal 이 필요하고, 그 에디터부터 만들어야 한다(컬럼 계약 열한째).
  • 메시지 키 명명 규약 — 상수 이름이 키를 대신 부르게 되어 급함이 줄었다. 그래도 MSG.USER_LIST_TITLE 과 'user.list.title' 의 대응을 누가 검사하는지는 정해지지 않았다.
  • 치환 변수 규약(화면 7) — {{orderNo}} 의 검증·미리보기는 47(알림)이 갖는다.
목업 규약 — 정적 HTML, 프레임워크 없음, 픽셀 충실도는 목표가 아니다. 결정은 requirements.md 가 갖고 이 파일은 확인용이다 — 여기에만 있고 요건서에 없는 정보는 유실된 것으로 친다.
