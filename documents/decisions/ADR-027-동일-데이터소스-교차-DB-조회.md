# ADR-027 — 동일 데이터소스 연결이 허용하는 교차 DB 조회

| 항목 | 내용 |
|---|---|
| 일자·상태 | 2026-10-27 · accepted · 사용자 명시 결정 |
| 등급 | High — 조회 범위와 물리 객체 식별 |
| 적용 차수 | RM-P1 |
| 정본 | [REQ-603](../spec/10-requirements/011-reference-integration.yaml), [REQ-301·302](../spec/10-requirements/007-knowledge-catalog.yaml), [ARCH-030](../spec/20-architecture/009-datasource.yaml) |
| 승인 근거 | 사용자가 하나의 데이터소스로 접근할 수 있다면 다른 DB 조회도 허용하고, 실제 접속 권한은 DB가 부여하므로 Hub에서 별도로 DB 범위를 제한할 필요가 없다고 결정했다 |

## 1. 맥락

REQ-603은 데이터소스를 연결 단위로 정의하지만 같은 연결의 다른 DB 조회는 P2 결정으로 남아 있었다.
DBMS마다 DB와 스키마의 경계가 다르므로, 데이터소스를 스키마 또는 단일 DB와 동일시하면 지원 가능한 조회를 불필요하게 나누게 된다.
예를 들어 SQL Server는 같은 인스턴스의 다른 DB 객체를 `database.schema.object`로 참조할 수 있다. PostgreSQL의 일반 연결은 하나의 DB에 연결하고 그 안의 여러 스키마를 사용한다.
근거: [SQL Server FROM](https://learn.microsoft.com/en-us/sql/t-sql/queries/from-transact-sql?view=sql-server-ver17), [PostgreSQL Schemas](https://www.postgresql.org/docs/current/ddl-schemas.html).

## 2. 고려한 대안

| 대안 | 장점 | 단점·비용 | 판단 |
|---|---|---|---|
| A. 접속 대상 DB 하나로 제한 | 식별·검증 범위가 단순함 | 같은 연결로 가능한 DB 간 조인도 나누고 결과를 결합해야 함 | 제외 |
| B. 다른 DB를 Hub 허용 목록에 별도 등록 | 운영자가 DB 범위를 추가로 통제함 | DB 권한·공개 객체 등록 외에 별도 목록과 변경 절차가 생김 | 초기 AI 권고였으나 제외 |
| C. 기존 연결이 접근 가능한 DB 허용 | DB의 접속 권한을 사용하고 중복 관리가 없음 | 전체 객체 식별과 DBMS별 파서 검증이 필요함 | 사용자 선택 |

## 3. 결정

동일 데이터소스의 기존 연결로 접근 가능한 다른 DB/카탈로그 조회를 허용하며, 별도의 DB 허용 목록을 두지 않는다.
실행 조건과 물리 식별의 정본은 REQ-603·301이다. 공개 객체 등록과 Hub 사용자 권한을 없애는 결정은 아니다.

## 4. 근거

데이터소스의 연결 경계를 유지하면서 DB가 이미 제공하는 기능과 권한을 사용한다.
카탈로그에는 DB/카탈로그와 스키마를 구분해 동명 객체의 잘못된 대체를 막는다.
서로 다른 데이터소스를 한 SQL에 섞는 동작이나 Hub가 추가 연결을 만드는 동작은 이 결정에 포함되지 않는다.

## 5. 포기한 것과 위험

별도 DB 목록으로 공개 객체 등록보다 상위의 범위를 다시 제한하는 기능은 두지 않는다.
대신 등록·수집·SQL 검증·행 스코프·컬럼 추적이 같은 전체 식별을 사용해야 한다.
DB의 권한이 바뀌어 조회가 실패할 수 있으며, 이를 Hub가 다른 연결로 우회하지 않는다.

## 6. 되돌리기

구현 전에는 REQ-301·302·603과 ARCH-030을 변경하면 된다.
구현 후에는 카탈로그 참조·예제·지식·저장 조회의 영향 조사와 데이터 이행이 필요하므로 비용이 높다.
DB 간 동명 객체를 잘못 식별하거나 파서가 전체 참조를 보존하지 못하면 해당 구문의 지원을 보완하고 영향 실행을 차단한다. 이를 DB 허용 목록을 도입한 것으로 간주하지 않는다.

## 7. 영향과 후속

REQ-021·301·302·603, ARCH-030, FEAT-002·003, SCR-002·003의 후속 설계에 반영한다.
P3에서 DBMS별 이름 해석·메타데이터·쿼리 검증의 계약 시험을 구체화한다. 이 ADR의 승인으로 admin G2 또는 구현 게이트가 통과되지는 않는다.

## 8. 사용자 결정 (AI 권고와 상이)

- AI 권고안: 검증된 DBMS·파서에서 별도로 등록한 DB만 허용한다.
- 사용자 선택: 동일 연결이 접근할 수 있다면 DB별 추가 제한을 두지 않는다.
- 예상 리스크: DB명을 누락한 카탈로그 비교가 동명 객체의 정책을 잘못 적용할 수 있다.
- 발생 신호: 다른 DB의 객체가 현재 DB의 권한·행 스코프로 판정되거나 이력에서 구분되지 않는다. REQ-301의 전체 물리 식별과 거부 시험으로 검증한다.
