# ADR-014 — 저장 사본은 항상 마스킹한다

| 항목 | 내용 |
|---|---|
| 결정 일자 | **2026-09-28** — 사용자 결정(AI 권고 B안과 같음) |
| 상태 | **accepted** — High. 감사·재현·보안의 저장 원칙이며 데이터 모델 전체에 걸린다 |
| 적용 범위 | Hub에 남는 모든 저장 사본 — 감사 이력·재개 상태·품질 증거 묶음·애플리케이션 로그·결과 캐시 |
| 관련 결정 | PRN-07 개정, ADR-003(상태 원천 단일화), ASM-008 |

## 1. 맥락

PRN-07과 REQ-107은 "조회 결과 원문은 **기본 미보존**"을 정해 두었다. 레거시의 평문 개인정보를
AI 전용 DB에 무기한 복제하지 않기 위해서다. 그런데 REQ-101~107 정련 카드를 쓰며 저장 경로를
전수 대조하자, 원문을 보존하지 않아도 **다른 경로로 평문 업무 데이터가 남는** 자리가 드러났다.

- 외부 모델 전송분은 항상 저장한다(REQ-106·107) — 평문 전송이 허용된 개인정보 컬럼도 그대로 남는다
- **실행 API 요청 파라미터에는 마스킹 규칙이 없었다** — 응답은 REQ-111이 "수신 직후 마스킹
  사본만 저장"으로 막았지만 요청은 비어 있어, 배송지·연락처가 실행 이력·승인 이력·재개 상태에 평문으로 남았다
- 실행으로 이어진 턴은 조회 결과 **원문**을 항상 보존했다(REQ-107)
- 품질 신고·오류 증거 묶음은 모든 스텝의 입력·출력을 불변 복사한다(REQ-110·115, ASM-008)
- 재개 상태(체크포인트)는 턴 동안 조회 결과 원문을 들고 있다(REQ-109)
- 저장된 조회의 결과 캐시는 저장 위치가 정해지지 않았다(NFR-005)

"기본 미보존"이 약속하는 것보다 실제로는 더 많이 저장되고 있었다.

## 2. 고려한 대안

### 대안 A — 업무 데이터 값을 저장하지 않는다
- 내용: 조회 결과·모델 전송분·파라미터는 메타데이터(SQL·행 수·컬럼 목록)와 결과 지문만 남긴다
- 장점: 가장 안전하고 저장량이 가장 작다
- 단점: "무엇을 보고 실행했나", "외부 모델에 무엇을 보냈나"에 답할 수 없다. 품질 신고의 재현이 어렵다
- 왜 선택하지 않았나: 감사(INV-01)와 외부 전송 통제(REQ-106)의 근거가 사라진다

### 대안 B — 저장 사본은 항상 마스킹한다 — **선택**
- 내용: REQ-111의 "평문은 사용자 응답 경로에만, 저장 사본은 수신 직후 마스킹"을 API 응답만이 아니라
  조회 결과·요청 파라미터·모델 전송분·증거 묶음 **전체로 넓힌다**
- 장점: 감사와 재현이 가능하면서 평문 개인정보가 저장소에 남지 않는다
- 단점: 마스킹 대상을 정확히 알아야 한다(카탈로그 컬럼·API 응답 경로·요청 파라미터의 개인정보 표시).
  가려진 값으로는 재현이 불완전한 경우가 있다
- 비용/난이도: 개인정보 표시를 등록하는 운영 부담과, 저장 직전 마스킹 분기의 구현

### 대안 C — 현행 유지
- 내용: 원문만 기본 미보존으로 두고 나머지 경로는 그대로 둔다
- 왜 선택하지 않았나: 위 §1의 평문 저장 경로가 그대로 남는다

## 3. 결정

**Hub에 남는 모든 저장 사본은 업무 데이터 값을 생성·수신 직후 마스킹한 것만 만든다.** 평문은 사용자
응답 경로와 허용된 외부 모델 전송 경로에만 흐르고, 마스킹 사본을 만들 수 없으면 값 없이 메타데이터와
지문만 남긴다.

## 4. 근거

1. **사고의 비용이 비대칭이다** — 여러 시스템의 데이터가 한곳에 모이는 구조에서 평문 복제는 도입의
   전제를 깬다(ECO-05). 가려진 값 때문에 재현이 불완전한 비용은 그보다 작다.
2. **이미 검증된 규칙을 넓힌 것이다** — REQ-111이 API 응답에서 쓰던 분기를 같은 이유로 나머지 경로에 적용했다.
   규칙이 하나라 운영자가 하나만 배운다.
3. **지문은 원본 값으로 계산한다** — 마스킹 사본만 있어도 "그때 결과와 같은가"를 대조할 수 있어,
   감사 질문의 대부분에 답이 남는다.

## 5. 포기한 것

- **재개된 턴은 개인정보 값이 가려진 채 이어진다**(REQ-109). 재개 뒤 원래 값이 필요하면 다시 조회해야 한다
- **품질 신고를 원래 값으로 재현할 수 없다** — 원문이 보존되지 않은 턴은 SQL·메타데이터·지문으로만 재현한다
- 평문 전송이 허용된 개인정보 컬럼이라도, 이력에서 "정확히 어떤 값이 나갔는가"는 지문으로만 확인한다
- 사용자 질의·모델 응답 같은 **자유 문장**은 이번 결정으로 가리지 못한다 — 자동 판별이 필요해
  Hub 개발 뒤 별도 기능으로 미뤘다(REQ-107에 P6으로 미뤄 둠)

## 6. 되돌리기

- 되돌릴 수 있는가: 지금은 쉽다 — admin·agent의 데이터 모델이 아직 없다(G3 전)
- 되돌리는 방법: PRN-07과 아래 §7의 REQ·FEAT에서 "마스킹 사본" 표현을 걷어 낸다
- 예상 비용: 구현 뒤에는 **이미 저장된 사본을 평문으로 되돌릴 수 없다** — 되돌리기는 앞으로 쌓일 것에만 걸린다
- 되돌려야 한다는 신호: 품질 신고의 재현 실패가 반복되고 원인이 "가려진 값"으로 모일 때,
  또는 고객사 감사가 평문 보존을 요구할 때. 이때도 먼저 **보존 정책을 켠 데이터소스만 평문**으로
  여는 좁은 예외를 검토한다

  - 자유 문장과 system 사용 이력 파라미터의 개인정보 자동 판별·마스킹(REQ-107에 P6으로 미뤄 둠, CR-007)
  - 저장 직전 마스킹 분기의 구현 위치 — agent·admin 데이터 모델 설계(P3)
