# ADR-012 — 단일 main 통합과 후속 검증을 분리한다

| 항목 | 내용 |
|---|---|
| 결정 일자 | **2026-09-17** — 사용자 승인 |
| 상태 | **accepted** |
| 적용 범위 | 사람과 AI가 여러 PC에서 동시에 작업하는 이 저장소 |
| 관련 결정 | ADR-006의 작업흐름·슬라이스 축을 유지하고 형상 통합 규칙을 보완한다 |

## 1. 맥락

여러 작업자가 같은 `project.state.yaml`과 공통 소스·분석·설계 문서를 동시에 고치면 마지막
통합자가 충돌을 해결한다. 충돌 해결이 기존 기능이나 문서 의미에 영향을 줄 수 있지만, 구현
완료나 게이트 전체를 되돌리면 같은 테스트가 반복되고 프로젝트가 멈춘다. 장기 개인 브랜치는
최종 일괄 병합 비용 때문에 기본 운영으로 쓰지 않는다.

## 2. 고려한 대안

### 대안 A — 작업자별 장기 브랜치
- 장점: 작업 중 격리가 분명하다.
- 단점: 뒤늦은 대량 병합과 통합 검증 비용이 커진다.
- 왜 선택하지 않았나: 소규모 팀의 짧은 변경에는 병합 비용이 더 크다.

### 대안 B — 마지막 통합자가 모든 검증을 끝낸 뒤에만 push
- 장점: main이 항상 검증 완료 상태다.
- 단점: 다른 기능의 문맥과 실행환경이 없으면 통합자가 모든 작업을 대신해야 하고 병목이 된다.
- 왜 선택하지 않았나: 테스트를 다른 팀원에게 넘길 수 없고 부재 시 통합이 멈춘다.

### 대안 C — 단일 main과 후속 검증 상태를 함께 사용 — **선택**
- 내용: 충돌 통합은 오프라인 확인 뒤 push할 수 있고, 미실시 검증은 `pending_rechecks`로 넘긴다.
- 장점: 브랜치 일괄 병합 없이 현재 위험과 후속 작업이 모든 세션의 브리핑에 보인다.
- 단점: main이 일시적으로 미검증 상태일 수 있고 커밋 기록 규율이 필요하다.
- 비용/난이도: 중간. 프로세스·상태 템플릿·스킬·훅·CI를 함께 맞춘다.

## 3. 결정

**팀 기본 형상 전략은 단일 `main`이며, 충돌 통합 이력은 커밋에, 현재 미실시 검증은
`project.state.yaml`의 `pending_rechecks`에 둔다.** 누구나 후속 검증을 수행할 수 있다.

## 4. 근거

1. 커밋은 과거 사실을, 상태 파일은 지금 해야 할 일을 맡아 정본이 겹치지 않는다.
2. 구현 완료와 검증 유효성을 분리해 관련 없는 변경의 재시험을 막는다.
3. 마지막 통합자가 의미 결정을 독점하지 않고 원 작업자에게 오프라인으로 확인할 수 있다.
4. 미검증 main을 허용하는 대신 해당 범위의 완료·게이트·배포만 막아 복구 경로를 열어 둔다.

## 5. 포기한 것

- 모든 순간 main이 검증 완료 상태라는 보장.
- Git 충돌만으로 업무 영향까지 자동 판정하는 방식.
- 개인·계정 ID에 고정된 결정 권한과 테스트 소유권.

## 6. 되돌리기

- 되돌릴 수 있는가: 가능하다.
- 되돌리는 방법: `pending_rechecks`를 닫고 PR·작업자별 브랜치·merge queue 정책으로 전환한다.
- 예상 비용: 협업 프로세스, 상태 템플릿, 통합 스킬·훅·CI 재작성으로 Medium.
- 재검토 신호: 미해결 검증이 계속 누적되거나 미검증 main 때문에 다른 작업의 실패가 반복될 때.

## 7. 영향

- `aidd-guide/process/14-collaboration.md`가 공통 절차의 정본이다.
- 기존 완료 슬라이스와 과거 충돌 이력은 소급 재구성하지 않는다.
- 승인된 spec의 의미 변경은 계속 CR을 사용한다.
- Claude와 Codex는 같은 스킬 원본과 훅 계약을 사용한다.
