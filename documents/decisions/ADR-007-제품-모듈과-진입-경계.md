# ADR-007 — 제품 모듈과 진입 경계를 분리한다

| 항목 | 내용 |
|---|---|
| 결정 일자 | **2026-09-12** — 사용자 승인 |
| 상태 | **accepted.** 되돌리기 비용 High인 모듈러 모놀리스 경계와 인가 진입 방식을 함께 확정했다 |
| 적용 범위 | 기존 백오피스와 Agentic AI Hub의 프론트엔드·백엔드·API·화면 문서·인가 |
| 관련 결정 | ADR-006의 작업흐름 축은 유지하되, 세 Hub 모듈 고정과 공통 Entity 경계는 이 결정이 대체한다 |

## 1. 맥락

현재 소스에는 사용자·메뉴·권한·공통코드·다국어 메시지 등 백오피스 시스템 관리 기능이
이미 구현되어 있지만, 제품 명세의 모듈은 `admin`·`portal`·`agent` 셋뿐이다. 그 결과 기존
시스템 관리와 AI 관리가 `admin` 하나에 섞이고, 프론트 `features`, 백엔드 `api`·`domain`,
화면 문서와 API 경로에서 소유 모듈을 식별할 수 없다(ARCH-003, ARCH-010~014, ARCH-018).

portal은 도메인 루트 `/`에서 독립된 사용자 화면을 제공하고, 기존 백오피스와 AI 관리는
`/admin` 관리 콘솔에서 함께 제공해야 한다. 로그인 뒤 이동과 메뉴 없는 내부 시험 화면도
기존의 역할명 직접 비교가 아니라 하나의 유효 권한 판정을 따라야 한다(ARCH-012, ARCH-020).

## 2. 고려한 대안

### 대안 A — 기존 3모듈을 유지하고 백오피스를 admin 내부에 둔다

- 장점: 파일 이동과 API·시드 마이그레이션이 가장 적다.
- 단점: 기존 시스템 관리와 AI 관리의 수명주기·소유권이 계속 섞인다.
- 왜 선택하지 않았나: 폴더 이름만 정리해도 실제 캡슐화가 생기지 않고, 고객사 업무 확장을
  붙일 때 같은 충돌이 반복된다.

### 대안 B — 4개 제품 모듈을 한 배포 안에서 캡슐화한다 — **선택**

- 내용: `system`·`admin`·`agent`·`portal`을 제품 모듈로 두고, 기술 기반은 `platform`과
  `shared`에 둔다. 프론트는 하나의 SPA 안에서 portal과 관리 콘솔 화면 영역을 나눈다.
- 장점: 한 번의 배포와 공통 인증을 유지하면서 코드·문서·API·DB 쓰기 소유권을 모듈별로
  식별하고 의존성 검사로 강제할 수 있다.
- 단점: 기존 소스·문서·시드 경로를 단계적으로 이행하고 호환 구간을 운영해야 한다.
- 비용/난이도: 높음. 현재 구현의 경로·패키지·인가 시드를 함께 옮겨야 한다.

### 대안 C — portal과 각 백엔드 모듈을 별도 애플리케이션으로 분리한다

- 장점: 배포·확장·장애 격리가 가장 강하다.
- 단점: 폐쇄망 설치 단위, 인증 세션, 다국어 메시지, 공통 UI와 계약 버전 운영이 늘어난다.
- 왜 선택하지 않았나: 현재 필요한 것은 독립된 화면과 코드 경계이지 독립 운영 단위가 아니다.

## 3. 결정

**단일 배포의 모듈러 모놀리스 안에 `system`·`admin`·`agent`·`portal` 네 제품 모듈을 두고,
portal과 관리 콘솔은 하나의 SPA에서 서로 다른 진입 영역으로 분리한다.**

다음 규칙을 함께 적용한다.

1. `system`은 사용자·메뉴·권한·공통코드·다국어 메시지와 기존 백오피스 기반을 소유한다.
2. `admin`은 AI 지식·정책·설정·운영 기능을 소유하고 관리 콘솔 메뉴에 기여한다.
3. `agent`는 UI가 없는 실행 모듈이며 대화·추론 LLM과 업무 DB·API의 유일한 접점이다.
4. `portal`은 `/`에서 시작하는 독립 사용자 화면이며 agent가 내놓은 계약만 소비한다.
5. 브라우저 경로는 화면 영역을 먼저 표현한다: `/`, `/portal/**`, `/admin`,
   `/admin/system/**`, `/admin/hub/**`, `/internal/**`.
6. API 경로는 보안 계층을 먼저 표현한다:
   `/api/{public|common|service}/{module}/{domain}/{action}`. `/api/service/**`만 기존
   `SYS_API`·`SYS_MENU_API` 완전 일치 권한 판정을 받는다.
7. 로그인 뒤 이동은 역할명이 아니라 유효 권한과 안전한 원래 목적지로 결정한다.
8. 메뉴 없는 내부 시험 화면도 서버 권한 대상이다. 역할은 권한 묶음일 뿐 판정 근거가 아니며,
   메뉴 노출 여부와 접근 가능 여부를 분리한다.
9. 모듈 소유 소스와 화면 문서는 모듈 경로를 갖는다. 전역·통합 정본과 기술 공통물은 네 모듈
   중 하나로 가장하지 않고 `integration`·`platform`·`shared`에 한 번만 둔다.

## 4. 근거

1. **현재 구현된 시스템 관리가 독립된 제품 책임이다.** AI 관리와 같은 메뉴 셸을 쓰더라도
   사용자·권한·코드·메시지의 변경 이유와 데이터 소유권은 다르다.
2. **보안 계층 접두사를 보존해야 한다.** 현재 인가 인터셉터와 시드 생성기는
   `/api/service/`를 기준으로 동작하므로 모듈은 그 뒤에 와야 실패 폐쇄 규칙이 유지된다.
3. **화면 분리는 배포 분리와 다르다.** 하나의 `index.html`과 인증 부팅을 재사용하면서 React
   라우터와 지연 로딩으로 portal과 관리 콘솔을 충분히 격리할 수 있다.
4. **역할명 직접 비교는 두 번째 인가 체계를 만든다.** 시작 화면과 내부 시험 화면 모두 서버가
   계산한 유효 권한을 사용해야 역할 추가·개인 권한 변경에도 결과가 어긋나지 않는다.
5. **폴더만 나누지 않는다.** 프론트 import 규칙과 백엔드 빌드·ArchUnit 규칙, 테이블 쓰기
   소유권이 함께 있어야 캡슐화가 실제로 유지된다.

## 5. 포기한 것

- 모든 화면 URL·API URL·코드 경로를 문자 그대로 같은 모양으로 만드는 단순함. `/api`와
  `/admin`은 각각 보안 계층과 화면 영역을 먼저 표현한다.
- portal을 지금 즉시 독립 배포하는 선택.
- 모든 Entity와 Repository를 모듈 구분 없이 직접 참조하는 편의.
- `ADMIN`·`TESTER` 같은 역할명만 보고 화면과 API 접근을 결정하는 구현.
- 기존 북마크와 API 경로를 호환 절차 없이 한 번에 제거하는 빅뱅 이행.

## 6. 되돌리기

- 되돌릴 수 있는가: 가능하지만 High 비용이다.
- 되돌리는 방법: 모듈별 패키지와 빌드를 다시 기술 계층 중심으로 합치고, 라우트·API·시드·
  화면 문서를 이전 경로로 이행한다.
- 예상 비용: 프론트 화면과 백엔드 컨트롤러·서비스의 대규모 이동, Liquibase 신규 변경 세트,
  권한 시드 재생성, 문서·생성기·테스트 재수정.
- 되돌려야 한다는 신호: 모듈 경계를 지키기 위해 대부분의 변경이 `shared`로 빠지거나,
  module 간 호출 어댑터가 실제 업무 코드보다 많아지고, 독립 변경률이 개선되지 않을 때.

- `documents/spec/20-architecture.yaml`: C4 구성, 모듈 경계, DB 쓰기 소유권, 라우팅·인가 규칙.
- `documents/spec/22-authz.yaml`: 시작 화면 권한과 메뉴 없는 권한 자원.
- `documents/spec/50-api.yaml`: `/api/{계층}/{모듈}/{도메인}/{동작}`.
- `documents/spec/60-screens.yaml`: portal·관리 콘솔·내부 시험 화면의 진입 영역.
- `documents/project.state.yaml`: `system` 작업흐름 추가, integration G2와 전역 G2 재검증.
- `aidd-guide/`와 생성기: 모듈 경로를 선택적으로 지원하고 기존 프로젝트의 단일 모듈 구조는
  깨뜨리지 않도록 하네스 동기화.
- 소스와 DB 변경은 영향받는 작업흐름 G3 승인 뒤 별도 슬라이스로 수행한다.
