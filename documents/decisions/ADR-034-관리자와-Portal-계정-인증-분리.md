# ADR-034 — 관리자와 Portal의 계정·인증을 분리한다

| 항목 | 내용 |
|---|---|
| 결정 일자 | 2026-10-29 — 사용자 명시 결정 |
| 상태 | accepted — 방향 승인. 상세 설계·화면·G3·구현 승인은 별도 |
| 관련 요구 | REQ-501·616·609·041, ARCH-012·021·050, AUTHZ-090 |
| 대체 범위 | CR-027의 공통 계정 방향 및 ADR-007의 공통 인증/인증 부팅 재사용 부분. 네 제품 모듈·단일 배포·SPA·화면 진입 경로는 유지 |

## 1. 맥락

관리 콘솔은 자체 관리자 계정으로 시스템과 Hub를 운영하며 고객사의 ITO 조직이 운영할 수도 있다.
Portal은 일반 업무 이용자의 PC·모바일 접점이며 SSO·대상 시스템 계정 연동 또는 자체 계정 모드가 필요하다.
같은 사람이 두 영역을 사용할 수 있지만 등록 원천·인증 방식·운영 책임과 계정 생애주기는 다르다.
CR-027의 공통 계정 참조와 직전 AI의 세 관리 메뉴 제안은 이 차이에 비해 계정·자격 연결과 변경 영향 관리가 복잡하다.

## 2. 고려한 대안

### 대안 A — 공통 계정 하나와 영역별 이용 자격

- 장점: 계정·인증정보 중복을 줄이고 한 사람의 신원을 연결할 수 있다.
- 단점: 공통 계정 상태·인증 원천 변경이 양쪽에 영향을 주며 자격·세션·부분 실패의 경계가 필요하다.
- 선택하지 않은 이유: 사용자가 공통 계정 요구를 철회했다. 관리자와 Portal의 원천·운영 주체·인증 요구가 다르다.

### 대안 B — 별도 계정 원장·인증·세션 — 선택

- 내용: system은 관리자 자체 계정/인증, admin은 별도 Portal 계정 등록/관리, portal은 Portal 인증/세션을 소유한다.
- 장점: ITO 관리자와 업무 이용자의 등록·인증·상태 관리가 독립적이고 계정 동기화가 필요하지 않다.
- 단점: 겸임자는 별도 계정을 발급받아 각각 로그인하며 인증 흐름과 운영/시험을 두 영역에 제공해야 한다.
- 비용/난이도: 높음. 기존 관리자 구현은 보존하되 별도 Portal 원장·SSO/자체 인증과 경계 계약이 필요하다.

## 3. 결정

**공통 Hub 계정 등록 요구를 철회하고 관리자와 Portal의 계정·로그인 인증·세션·권한 수락을 분리한다.**
제품 사실의 정본은 [ARCH-050](../spec/20-architecture/011-identity.yaml)이다.
관리자는 Portal 이용 시 별도 Portal 계정을 발급받으며 공통 사용자 목록에서 선택 등록하지 않는다.
SSO·대상 시스템 인증 연동은 Portal 범위이고 관리자에게 확대 적용하지 않는다.

## 4. 근거

관리 콘솔과 업무 Portal은 이미 진입 화면과 권한 책임이 다르다.
계정과 인증을 나누면 공통 원장과 양방향 상태 동기화 없이 각 운영 책임에서 등록·중지할 수 있다.
단일 배포·공유 기술 유틸을 유지해도 계정·인증 수락과 세션을 분리할 수 있으므로 배포 단위를 늘릴 필요는 없다.

## 5. 포기한 것

- 관리자 로그인 한 번으로 Portal을 사용하는 편의와 공통 개인 계정 관리.
- 관리자/Portal의 비밀번호·잠금·활성 상태·로그아웃을 자동 일치시키는 동작.
- Portal이 기존 SYS_USER FK·관리자 auth 상태·알림/개인 설정을 그대로 사용하는 구현 편의.

## 6. 되돌리기

- 공통 계정으로 돌아가려면 새 변경 요청과 사용자 승인이 필요하다.
- 외부 원천·실제 소유 근거를 검증해 두 계정을 명시적으로 연결하고 세션·권한·감사/보존을 이행해야 한다.
- 이름·이메일·같은 로그인 ID로 자동 병합할 수 없다. 실제 데이터가 쌓인 뒤에는 High 비용이다.
- 두 계정 발급·회수 누락이 반복되거나 고객사의 통합 신원 요구가 생기면 재검토하되 이번 결정의 자동 예외로 취급하지 않는다.

## 7. 영향과 후속

- CR-028이 REQ-501·616, UC-501·023, FEAT-501·005·301·305와 ARCH-011·012·021·022·024·025·050, AUTHZ-090의 경계를 정합화한다.
- SCR-501은 관리자 자체 계정 관리로 유지하고 SCR-005는 Portal 별도 계정을 등록한다. 공통 사용자 관리라는 세 번째 메뉴는 두지 않는다.
- Portal 공통 인증 화면 SCR-113~115를 system 화면 재사용과 분리한다. 상세 요건·목업·로그인 URL/세션·API는 소유 P3에서 작성한다.
- 같은 문자열 ID의 주체·이력·명령 결과·알림·개인 설정 혼동과 양방향 인증 수락을 거부하는 시험을 설계한다.
- 기존 관리자 테이블·비밀번호·소스와 데이터는 변경하지 않았다. 실제 분리 구현·이행/롤백·DB/외부 인증 시험은 후속이다.

## 8. 사용자 결정과 직전 AI 권고

- 직전 AI는 공통 계정을 세 관리 화면으로 분리하는 안을 권고했다.
- 사용자는 계정 연결과 동기화의 복잡성, ITO 운영과 Portal 외부 인증의 차이를 근거로 독립 계정을 명시 선택했다.
- 예상 비용은 겸임자의 두 계정 운영과 인증별 회복 절차다. 계정 오인·한쪽 발급/회수 누락이 증상이다.
- 이를 계정 자동 통합으로 해결하지 않고 영역 표시·독립 발급/회수·경계 시험으로 다룬다.
