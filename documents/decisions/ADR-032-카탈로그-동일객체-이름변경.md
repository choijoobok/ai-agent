## 1. 맥락

카탈로그·컬럼 이름은 원천 변경으로 달라질 수 있지만 지식·관계·정책과 과거 내용은 안정 식별자를 참조한다.
이름 변경 때마다 새 항목을 만들거나 이름이 같은 객체에 자동 승계하면 각각 불필요한 연결 재작성 또는 잘못된 동일시가 발생한다.
제품 규칙은 [REQ-301.identity_change](../spec/10-requirements/007-knowledge-catalog.yaml)에 둔다.

## 2. 대안

| 대안 | 장점 | 대가 |
|---|---|---|
| A. 동일 객체 확인 근거와 후보 반영을 거쳐 식별자 유지 | 기존 연결과 변경 이력을 이어갈 수 있음 | 동일성 검수·이름 충돌·참조 영향 검증 필요 |
| B. 항상 새 항목으로 등록 | 이름별 등록 절차가 단순함 | 관계·지식·정책 연결 재작성과 이력 단절 비용 |

## 3. 결정과 근거

사용자가 2026-10-29 A를 선택했다. 동일 객체의 이름 변경임을 관리자가 확인한 근거를 남기고
기존 카탈로그 변경 후보의 검토·승인 또는 전결·실제 반영을 거쳐 안정 식별자를 유지한다.
제출된 과거 리비전의 물리 이름과 참조 판은 바꾸지 않는다. 기존 연결의 안정 식별자 유지가
과거·제출 참조를 최신 내용으로 자동 치환하거나 검증을 면제한다는 뜻은 아니다.

## 4. 포기한 것

이름 변경의 자동 확정·전체 참조의 자동 최신판 치환과 삭제 후 동명 객체 재생성의 자동 승계를 제공하지 않는다.
이 결정은 다른 데이터소스·다른 물리 실체로 기존 항목을 이전하는 승인도 아니다.

## 5. 되돌리기

항상 신규 등록으로 바꾸려면 기존 카탈로그·컬럼의 이름 변경 이력과 지식·관계·정책 참조를 구분해
이행해야 하므로 구현 후 비용이 높다. 과거 리비전을 다시 쓰지 않고 별도 변경 요청으로 처리한다.

## 6. 영향과 후속

REQ-301, FEAT-003·011, UC-007·008, ENT-005~009와 SCR-003에 연결한다.
전체 물리 식별·중복 검사·현재 포인터 전환·이름 변경 근거를 물리/API 계약에 구체화한다.
원천 객체의 변경 사실을 스스로 추정하지 않으며 제품 구현·G3 승인은 별도다.
