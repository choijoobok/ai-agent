# ADR-013 — RM-P1 최소 모듈 간 공개 계약

| 항목 | 내용 |
|---|---|
| 결정 일자 | **2026-09-20** — CR-023 영향 분석에 따른 AI 결정 |
| 상태 | **accepted** — Medium. 모듈러 모놀리스 방식은 ADR-007을 유지하고, 공개 계약 허용 목록만 정밀화한다 |
| 적용 범위 | RM-P1의 실행 API·저장된 조회·이번 달 추가 토큰 신청·승인과 그 운영 조회 |
| 관련 결정 | ADR-007, CR-023 |

## 1. 맥락

CR-023은 RM-P1에서 조회 전용 선출시를 하지 않고, 등록 REST 업무 API의 명시적 승인 실행,
저장된 조회의 현재 권한 재판정 실행, 이번 달 추가 토큰 사용 신청·승인을 함께 준비하도록
확정했다. 그러나 기존 ARCH-011은 system의 인증 계약과 portal → agent 계약만 허용한다.
admin이 소유한 실행 구성·쿼터·승인 상태를 agent와 portal이 사용하고, agent가 소유한 저장된
조회 실행 상태를 admin이 운영 조회하는 흐름을 내부 Repository 참조로 만들면 모듈 경계가 깨진다.

## 2. 고려한 대안

### 대안 A — 업무 목적별 최소 공개 계약만 추가한다 — 선택

- 내용: 다음 다섯 계약만 허용한다. system의 인증·유효 권한 계약, portal → agent 사용자 처리,
  portal → admin 추가 토큰 신청·본인 처리 결과, admin → agent 실행 구성·유효 쿼터 조회,
  agent → admin 실행 통계·저장된 조회 상태 조회. 계약은 공개 포트와 DTO만 노출하고 내부
  서비스·Entity·Repository는 노출하지 않는다.
- 장점: RM-P1 전체 흐름에 필요한 상태 소유권은 보존하면서, 모듈 간 참조와 계약 시험 범위를
  작게 고정한다.
- 단점: 계약별 버전·권한·소유 시험을 별도로 관리해야 한다.
- 비용/난이도: 중간. P3에서 API·DTO·ENT와 계약 시험을 각각 연결해야 한다.

### 대안 B — agent를 모든 사용자 업무의 단일 중계자로 둔다

- 내용: portal의 추가 토큰 신청도 agent가 받은 뒤 admin으로 전달하고, admin 운영 조회도 agent를
  거치게 한다.
- 장점: portal의 외부 의존 방향은 하나로 유지된다.
- 단점: 실행 모듈인 agent가 쿼터 신청·승인 전달의 불필요한 중계 책임을 지며, admin 승인 상태의
  변경 경계와 오류 책임이 흐려진다.
- 왜 선택하지 않았나: API 실행·LLM·업무 DB의 유일한 접점이라는 agent의 보안 경계와 무관한
  업무를 agent에 넣어, 다음 변경 때 더 넓은 모듈을 동시에 바꾸게 만든다.

### 대안 C — 공유 DB의 admin·agent Repository를 직접 참조한다

- 장점: 초기 구현이 짧고 별도 DTO가 필요 없다.
- 단점: 테이블 변경이 즉시 다른 모듈의 컴파일·업무 규칙에 영향을 주고, 호출 권한과 상태 전이
  책임을 소스에서 구분할 수 없다.
- 왜 선택하지 않았나: ARCH-010·011 및 쓰기 소유권 원칙을 직접 위반한다.

## 3. 결정

**RM-P1에는 업무 목적이 고정된 최소 공개 계약 다섯 개만 허용한다.**

추가 토큰 신청·승인 상태는 admin이, 저장된 조회의 실행 정의와 실행 이력은 agent가 소유한다.
portal은 즐겨찾기·대시보드 배치만 소유하며, 저장된 조회 실행 정의를 직접 보유하지 않는다.

## 4. 근거

1. 실행 API와 업무 DB·LLM의 접점은 계속 agent 하나여야 한다(ARCH-013).
2. 쿼터 계획과 승인 이력은 비용·운영 정책이므로 admin 한 곳의 상태 전이가 필요하다(REQ-119).
3. 저장된 조회는 SQL·현재 권한 재판정·마스킹을 매 실행에 수행하므로, 실행 정의와 함께 agent가
   소유해야 한다(REQ-201~207).
4. 공개 DTO를 통과시키면 P3에서 권한·버전·계약 시험의 대상을 한정할 수 있다.

## 5. 포기한 것

- portal이 agent 하나만 의존하는 단순한 모양.
- 공유 DB를 편의상 직접 조회·갱신하는 초기 구현 속도.

## 6. 되돌리기

- 되돌릴 수 있는가: 가능하나 중간.
- 되돌리는 방법: 공개 계약과 소비자를 제거하거나 agent 단일 중계 경로로 이행하고,
  ARCH-011·토폴로지·P3 API/DTO·계약 시험을 함께 바꾼다.
- 예상 비용: admin·agent·portal·integration P3 산출물과 모듈 의존성 시험을 한 차례 재설계한다.
- 되돌려야 한다는 신호: 추가 토큰 신청 또는 저장된 조회 흐름 때문에 새 범용 모듈 간 계약이
  반복적으로 늘어나, 현재 다섯 계약으로 변경 격리가 유지되지 않는 경우.

## 7. 영향

- 산출물: ARCH-011, ARCH-001 토폴로지, 쓰기 소유권, admin·agent·portal·integration의 P3 API·DTO·ENT·계약 시험.
- 후속으로 정해야 할 것: P3에서 각 공개 계약의 주소·요청/응답·버전·권한과 테이블별 키·무결성,
  그리고 통합 계약 시험의 책임을 확정한다.
- `@defer P3` 추가 토큰 신청 명령의 멱등 키·중복 제출 처리와 승인 행의 동시 판정 규칙을 정한다.
- `@defer P3` 승인 직후 유효 쿼터 조회와 agent 토큰 사용량 차감의 원자성·버전·경합 거부 규칙을 정한다.
- `@defer P3` admin 운영 조회가 저장 SQL·파라미터 값·결과 원문을 불필요하게 노출하지 않도록
  agent → admin 통계 계약의 허용 필드와 감사 권한을 정한다.
