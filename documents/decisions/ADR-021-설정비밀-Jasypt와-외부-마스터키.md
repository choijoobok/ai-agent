## 1. 맥락

CON-011에는 Jasypt 기본 전략이 있었으나 REQ-402·602·603·608의 비밀 관리 경계가 분산돼 있었다. 현재 소스는 DB·메일 등에 환경 변수 바인딩을 제공하지만 Jasypt 해석은 구현되지 않았다. 비밀 종류마다 환경 변수나 외부 저장소 주입을 요구하면 고객사 운영 부담이 커진다는 사용자 판단으로 기본 정책을 명확히 한다.

## 2. 고려한 대안

### 대안 A — Jasypt 암호화 yml + 외부 마스터 키 하나 (채택)

비밀 설정값을 yml의 `ENC(...)`로 관리하고 설정 암복호화 키만 외부에 둔다. 별도 설정 서버 없이 기존 yml 관리 흐름을 유지하고 외부 관리 항목 수를 줄인다. 반면 키 유출의 영향이 같은 환경의 전체 암호값에 미치며 키 교체에는 일괄 재암호화가 필요하다. Spring Boot 연동 라이브러리의 호환성을 검증해야 한다.

### 대안 B — 모든 비밀을 개별 환경 변수 또는 외부 비밀 저장소로 주입

비밀별 권한·교체·감사 체계를 활용할 수 있지만 변수·참조·외부 도구 운영 부담이 증가한다. 사용자가 관리 복잡도를 이유로 기본 방식에서 제외했다.

### 대안 C — Spring Security Crypto 기반 설정 해석 어댑터

Spring 공식 암호화 기능을 사용하되 yml 암호값 감지·조기 해석·오류 처리와 암호화 도구는 별도로 구성한다. 서버를 추가할 필요는 없지만 Jasypt처럼 설정값을 자동 해석하는 완성된 대체 라이브러리는 아니며 자체 어댑터의 유지 비용이 생긴다. Jasypt의 호환성 검증 실패 시 사용자와 비교할 후보로 남긴다. [공식 Crypto 문서](https://docs.spring.io/spring-security/reference/features/integrations/cryptography.html)

### 대안 D — Spring Cloud Config 또는 SOPS

Spring Cloud Config는 설정 서버의 암복호화 경로를, SOPS는 YAML 등 파일 암호화 도구를 제공한다. 전자는 설정 서버 운영이, 후자는 배포 시 복호화·설정 로딩 연결이 필요하므로 현재의 단일 애플리케이션과 최소 운영 부담 목표에는 기본안으로 선택하지 않는다. [Config 암호화](https://docs.spring.io/spring-cloud-config/reference/server/encryption-and-decryption.html), [SOPS 공식 저장소](https://github.com/getsops/sops)

## 3. 결정

2026-10-02 사용자가 대안 A를 명시 채택했다. 제품 규칙의 정본은 [REQ-403](../spec/10-requirements/008-derived.yaml)이다. 비밀 설정값을 Jasypt 암호화 yml로 관리하고 환경별 활성 설정 마스터 키 하나만 OS 환경 변수 등 외부에서 관리한다. 개별 비밀의 외부 주입을 기본 운영 방식으로 요구하지 않는다.

정책 채택은 현재 소스의 구현 완료나 특정 starter 버전의 호환성 승인과 별개다. 운영·개발 및 고객사 간 키를 공유하지 않으며, 설정 보호 키를 업무 데이터 암호화 키로 직접 재사용하는 결정도 아니다. 인증서 개인키 파일과 외부 운영 도구의 비밀을 모두 Hub yml에 넣는 결정은 아니다.

## 4. 근거

기존 CON-011의 전략을 유지하면서 외부 관리 대상을 줄인다. 연결 메타데이터를 관리하는 admin과 실제 비밀을 사용하는 서버·배포 담당자의 책임도 유지한다. 별도 설정 서버나 비밀 저장소를 기본 인프라로 추가하지 않는다.

## 5. 포기한 것과 위험

- 기본안에서는 비밀별 외부 저장소 접근 제어·자동 교체의 장점을 얻지 않는다.
- 마스터 키가 유출되면 해당 환경의 모든 암호값이 영향을 받는다. 키와 암호문을 함께 보관하지 않고 키 유출 시 실제 자격증명 교체까지 판단해야 한다.
- 키를 잃으면 암호화된 설정을 복구할 수 없다. 별도 안전 보관과 키/yml 버전이 일치하는 교체·복구 절차가 필요하다.
- 공식 저장소의 최신 공개 릴리스는 확인 시점에 4.0.4이다. Boot 4.0.0에서 오류가 보고됐고 Boot 4 지원 요청도 열려 있으므로 현재 Spring Boot 4·JDK 25 조합의 호환성을 보장했다고 볼 수 없다. [릴리스](https://github.com/ulisesbocchio/jasypt-spring-boot/releases), [오류 보고 #425](https://github.com/ulisesbocchio/jasypt-spring-boot/issues/425), [지원 요청 #429](https://github.com/ulisesbocchio/jasypt-spring-boot/issues/429)

## 6. 되돌리기

- 가능 여부: 가능하나 여러 설정과 운영 절차에 영향이 있어 비용은 Medium이다.
- 방법: 새 ADR로 대체 정책을 정하고 암호문 형식·해석 어댑터·암호화 도구·키 교체/복구 절차를 이행한다. 실제 비밀을 소스나 로그로 출력하며 변환하지 않는다.
- 범위: REQ-403·CON-011·FEAT-302와 REQ-602·603·604·608의 참조, 배포 안내, 이후 작성할 계약 시험이다. 현재는 구현 전이므로 소스 재작업은 없다.
- 재검토 신호: Boot 4/JDK 25 기동·DB 초기화·Liquibase·로그 초기화에서 호환 실패, 유지보수/보안 문제, 고객사가 비밀별 권한·자동 교체를 필수로 요구하는 경우다. 기본 운영 원칙을 유지할 수 있는 대안부터 비교하고 사용자 승인 없이 라이브러리를 대체하지 않는다.

## 7. 영향과 후속

REQ-403에 관리 대상 목록·비밀 비노출·키 분리·교체 규칙을 모으고 개별 연결 카드는 이를 참조한다. 현재 system의 인증·일반 설정 허용 목록과 소스를 변경하지 않는다. REQ-403 카드 전체와 REQ-604·608의 확정은 이번 기술 정책 채택과 별개로 순차 검토한다.

P2에서는 호환성과 조기 설정 해석 경로, 암호 파라미터, 암호화 도구, 외부 키 주입·교체·복구 계약을 확인한다. P3에서는 합성 비밀로 누출·오키·누락·교체 실패를 검증할 시험을 정의한다. 구현은 소유 작업흐름의 G3 승인 이후 수행한다.
