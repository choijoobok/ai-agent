## 1. 맥락

REQ-601·603·604의 대상 시스템/데이터소스는 같은 관리 명령으로 현재 정의와 전체 집합을 변경한다.
변경 직전 구성만 기록하면 그룹 10개를 8개로 줄인 이력 행 자체에는 8개가 보이지 않고 다음 변경이나 현재값을 따라가야 한다.
사용자는 변경 시점의 확정 결과를 그대로 스냅샷에 남기도록 결정했다. 현재 범위는 미구현 설계다.

## 2. 대안

| 대안 | 장점 | 대가 |
|---|---|---|
| A. 변경 전 전체 구성만 저장 | 직전 상태 조회에 직접 대응 | 이력 행만으로 이번 반영 결과를 알 수 없고 최초 상태 이력이 없음 |
| B. 반영 후 확정된 전체 구성 저장 | 각 버전이 독립적이며 10→8 변경 행에 8개가 저장됨 | 이전값 비교는 직전 버전을 함께 조회해야 함 |
| C. 변경 전·후 전체 구성을 모두 저장 | 한 행에서 전후를 바로 비교 | 동일 구성이 반복 저장되고 계약·용량이 늘어남 |

## 3. 결정

사용자가 2026-10-29 B를 선택했다. FEAT-001·002 직접 관리의 생성·수정·참조 정정에 반영 후 확정된 전체 구성을 저장한다.
최초 등록도 버전 1의 스냅샷을 만들며 성공한 명령 결과는 항상 해당 이력을 가리킨다.
삭제는 마지막 구성을 보존한 삭제 상태 스냅샷으로 기록한다. 삭제 표시를 현재 유효 구성으로 해석하지 않는다.
제품 계약의 정본은 [FEAT-001.shared_write_contract](../spec/50-api/003-admin-integration-contracts.yaml)다.

## 4. 근거

각 이력 행이 그 시점의 결과를 자급하므로 현재값·후속 이력의 존재와 무관하게 8개 상태를 재현할 수 있다.
그룹은 안정 ID 목록으로 저장하며 이름을 작은 VARCHAR에 이어 붙이지 않는다. 기존 SNAPSHOT의 PostgreSQL text·JPA NCLOB 대응을 유지한다.
이력·현재값/집합·명령 성공 결과는 같은 트랜잭션으로 확정하고 재수신은 기존 이력을 재사용한다.

## 5. 포기한 것

한 이력 행에 전·후 구성 두 벌을 중복 저장하지 않는다. 전후 비교는 직전 버전과 해당 버전으로 수행한다.
현재 그룹명·배포 관측을 과거 구성에 합성하지 않는다. 그룹의 당시 표시 근거 계약은 소유 access_policy에서 연결한다.

## 6. 되돌리기

구현 전에는 ENT-003/004·019, FEAT-001/002·033, API 계약·화면·TC를 함께 되돌릴 수 있다.
이력 데이터 적재 후에는 의미가 다른 스냅샷을 구별하는 형식/이행이 필요하므로 비용이 높다.
전후 비교가 실제로 단일 행 원문을 요구하는지 확인되면 별도 결정으로 재검토한다.

## 7. 영향

- ENT-003/004의 PREVIOUS_VERSION을 RESULT_VERSION으로 바꾸고 생성 이력·버전별 유일성·순서를 정합화한다.
- ENT-019와 AssetMutationResult의 historyId는 신규를 포함해 항상 필수다.
- SCR-001/002 이력 컬럼·최초 등록/10→8/삭제/재수신·원자성 시험을 새 의미로 맞춘다.
- 카탈로그/API·도구의 승인 후보·고정 내용 판과 구현된 system 이력은 이번 결정의 대상이 아니다. 보존·파기·그룹 과거 표시 소유는 유지한다.

## 8. 기존 AI 제안과의 차이

직전 AI 제안은 전·후 그룹 목록을 함께 보존하는 방식이었다. 사용자 선택은 반영 후 전체 스냅샷 한 벌이다.
전후 비교가 필요하면 이전 버전을 읽어야 한다는 대가를 기록하며 저장 정책을 다시 혼합하지 않는다.
