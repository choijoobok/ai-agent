## 1. 맥락

REQ-610의 전사 공통 프롬프트 변경에서 의미 모순을 검토하되 ARCH-013의 admin 직접 대화·추론 호출 금지를 유지해야 한다. 관리자 검토에 Portal 이용 등급을 요구할 이유는 없지만 사용량은 추적해야 한다. 운영자가 자연어 지침을 바꾸는 것과 모듈 간 통신 스키마를 바꾸는 것은 영향이 다르다.

## 2. 고려한 대안

### 대안 A — agent 경유 운영 호출과 소스 계약 분리 (채택)

관리자 운영 호출은 별도 모델·effort 설정과 사용자별 사용량 기록을 사용하고 쿼터는 적용하지 않는다. 데이터 포맷·스키마는 소스 계약으로 정의하고 agent가 스텝 유형별 프롬프트를 조합한다. 호출 책임과 계약 검증이 일관되지만 운영용 인가·집계 구분이 필요하다.

### 대안 B — 관리자도 Portal 등급·제한과 같은 프롬프트 편집 체계 사용

기존 개인 쿼터를 재사용할 수 있지만 운영 검토를 개인 잔여량이 막고, 시스템 통신 계약이 운영 문구 수정으로 흔들릴 수 있다. 사용자가 원한 운영 경계와 맞지 않아 기각했다.

### 대안 C — admin에서 직접 LLM 호출

연결 단계는 줄지만 대화·추론 호출 책임과 모델·추적 처리가 중복되고 ARCH-013을 변경해야 하므로 기각했다.

## 3. 결정

2026-10-01 사용자가 대안 A를 명시 승인했다. 제품 규칙의 정본은 REQ-610(prompt_contract), REQ-602(운영용 모델·effort), REQ-116(관리자 집계와 Portal 쿼터 분리)이며 ARCH-040과 REQ-031이 이를 참조한다.

운영 반영 전 LLM 검토를 실행하되 최종 결정은 관리자가 한다. 형식·통신 계약 오류는 서버가 차단한다. 의미 경고·검토 실패는 사유를 남겨 판단하고 실패를 통과로 기록하지 않는다. 검토 뒤 변경한 문구에는 기존 검토 결과를 재사용하지 않는다.

## 4. 포기한 것과 위험

- 무모순을 자동 보증하지 않는다. LLM의 누락·오탐 가능성과 관리자 최종 판단 책임이 남는다.
- 관리자 운영 호출에는 개인 쿼터 비용 상한이 없다. 실제 토큰·비용은 기록하며 기존 호출 제한·인가를 제거하지 않는다.
- 통신 스키마 수정에는 코드 변경·시험·배포가 필요하다. 운영 문구만으로 계약을 바꾸는 편의는 포기한다.
- 내용 리비전 유지와 현재 접근 권한 판정은 별개다. 동적 조합의 재현 근거는 영속 버전/스냅샷으로 확보하고 메모리 캐시에 의존하지 않는다.

## 5. 되돌리기

되돌리기 비용은 높다. 운영 호출을 개인 쿼터와 합치면 과거 집계 의미·한도 적용을 다시 정해야 한다. 통신 스키마를 운영 편집 대상으로 열면 모듈 호환·인가·검증 계약을 재설계해야 한다. 변경 시 별도 사용자 결정과 영향 검증을 거친다.

## 6. 후속

REQ-610의 P2/P3 후속에서 운영 검토 요청·인가·결과 계약, 스텝 유형별 입력·출력·조합과 버전 보존 구조를 상세화한다. 현재는 요구사항 결정이며 구현이나 단계 게이트 승인으로 간주하지 않는다.
