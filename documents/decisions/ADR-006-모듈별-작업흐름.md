# ADR-006 — 로드맵·작업흐름·슬라이스를 독립 축으로 관리한다

| 항목 | 내용 |
|---|---|
| 결정 일자 | **2026-09-11** — 사용자 승인 |
| 상태 | **accepted.** 되돌리기 비용 High 라 승인받았다. 뒤집을 때는 새 ADR 로 대체한다 |
| 적용 범위 | 제품 표준 소스의 admin·agent·portal 및 고객사 업무 확장 |
| 반영 위치 | `project.state.yaml` · 프로세스 규칙 · 모듈별 소스 쓰기 게이트 · portal/agent 계약 |
| 부분 대체 | **ADR-007.** 작업흐름 축은 유지하고, Hub 모듈 셋 고정과 공통 Entity 경계만 대체한다 |

## 1. 맥락

admin 은 기준 정보·지식·정책을 만들고 agent 는 그것을 사용한다. 따라서 admin 을 먼저
설계·개발하되 agent 구현에서 드러난 결손을 admin 으로 되돌려 고칠 수 있어야 한다.
portal 은 처음에는 agent 에 질의를 보내고 **정책 적용이 끝난 응답 계약을 그대로 보여 주는
시험 화면**만 필요하다. 채팅 이력·개인화·그리드·차트·지도 같은 제품 화면은 admin 과 agent
핵심이 안정된 뒤 상세 설계한다.

현재 방식은 한 차수에 단계와 게이트가 한 벌뿐이다. 이 구조에서는 portal 상세 설계가
끝나기 전 admin 소스를 열 수 없거나, 반대로 admin 때문에 열린 전역 게이트로 아직 설계되지
않은 portal 소스까지 열리는 두 실패 중 하나가 생긴다. 또한 고객사 WMS·TMS·OMS·HR·ERP를
같은 빌드에 넣는 `SHAPE-02`(업무 시스템과 Hub를 함께 구축하는 형태)를 독립적으로 설계하고
검증할 상태 자리도 없다.

## 2. 고려한 대안

### 대안 A — 차수마다 전역 단계·게이트 하나만 유지

- 장점: 상태가 단순하고 기존 훅을 고치지 않는다.
- 단점: 가장 늦은 모듈이 모든 모듈을 막거나, 한 번 열린 문이 미설계 모듈까지 연다.
- 왜 선택하지 않았나: 세 모듈의 의존 순서와 상세 설계 시점이 실제로 다르다.

### 대안 B — 모듈마다 저장소·로드맵·배포를 완전히 분리

- 장점: 일정과 형상 관리가 완전히 독립한다.
- 단점: 세 모듈이 공유하는 Entity·DB·권한 판정·배포 단위와 충돌하며 계약 변경을 여러
  저장소에 동기화해야 한다. 업무 확장이 Hub와 한 빌드로 나가는 목적도 약해진다.
- 왜 선택하지 않았나: 개발 순서가 다르다는 사실을 런타임·배포 분리로 과대 해석한다.

### 대안 C — 전역 릴리스 게이트와 작업흐름 게이트를 함께 둔다 — **선택**

- 내용: 로드맵은 출시 범위, 작업흐름은 모듈별 성숙도, 슬라이스는 기능 변경 단위로 둔다.
- 장점: 한 저장소와 통합 제품을 유지하면서 승인된 모듈만 구현할 수 있다. 계약은 별도
  `integration` 작업흐름에서 잠가 양쪽 모듈이 각자 해석하지 않게 한다.
- 단점: 상태와 훅이 어느 작업흐름의 게이트인지 판별해야 한다.
- 비용/난이도: 중간. 문서 구조와 훅을 한 번 바꾸지만 소스 모듈이나 배포 단위는 바꾸지 않는다.

## 3. 결정

**로드맵·작업흐름·슬라이스를 독립 축으로 관리한다.** 전역 게이트는 차수의 통합·인도를
판정하고, 작업흐름 게이트는 해당 모듈 또는 계약의 설계·구현·검증을 연다.

## 4. 근거

1. **의존성과 일정은 다르다.** admin → agent 의 의미 의존은 선행 순서를 만들지만 portal
   상세 UX까지 같은 시점에 확정할 이유는 없다.
2. **게이트의 보호 범위와 쓰기 권한을 맞춘다.** 작업흐름 `G3`(해당 설계를 동결하고 구현을
   여는 관문)가 승인된 기능만 소스를 쓸 수 있어, 다른 모듈의 승인을 빌려 구현하지 못한다.
3. **계약을 제3의 소유권으로 둔다.** portal↔agent, admin↔agent, 업무 확장↔Hub 계약은
   어느 한쪽 모듈의 내부 설계가 아니다. `integration` 작업흐름이 버전·호환성·계약 시험을
   소유해야 변경 영향이 양쪽에 보인다.
4. **미래 portal 요구를 버리지 않고 상세 결정을 미룰 수 있다.** 요구는 먼저 식별하고 핵심
   계약 영향만 검사한다. 시각화 라이브러리·화면 배치는 portal 작업흐름 설계 때 정한다.
5. **고객사 업무 시스템도 같은 규율을 재사용한다.** 업무 확장은 네 번째 Hub 모듈이 아니라
   이름 있는 별도 작업흐름이며, 자체 DB·메뉴·Hub 연동 계약을 설계한 뒤 같은 슬라이스로 만든다.

## 5. 포기한 것

- 상태 파일의 단일 `current.phase` 만 보고 전체 진행을 설명하는 단순함.
- 한 번의 전역 `G3` 승인으로 저장소의 모든 소스를 여는 방식.
- portal 시각화 도구와 응답 블록을 agent 핵심 설계와 동시에 확정하는 방식.
- 모듈 일정이 다르다는 이유만으로 독립 배포·독립 저장소를 얻는 선택.

## 6. 되돌리기

- 되돌릴 수 있는가: 가능하지만 High 비용이다.
- 되돌리는 방법: 모든 작업흐름을 같은 단계로 합치고, 모듈별 베이스라인과 소스 게이트를
  전역 게이트로 환원한다.
- 예상 비용: 상태 이력 재구성, 승인 범위 재판정, 훅·스킬 변경, 진행 중 슬라이스 재분류.
- 재검토 신호: 작업흐름 간 계약 변경이 매 슬라이스마다 전역 재설계를 일으키거나, 모듈별
  상태가 실제 승인·배포 판단에 쓰이지 않고 지속적으로 같은 값만 복제할 때.

## 7. 영향

- `admin`, `agent`, `portal`, `integration` 작업흐름을 둔다. `common` 기능과 모듈 간 계약은
  `integration` 이 소유한다.
- P0/G0(제품 목적·범위)와 G6(통합 인도)는 전역이다. P1~P5는 전역 상태와 작업흐름 상태를
  함께 가지며, 작업흐름 `G3` 승인만 해당 기능의 소스 쓰기를 연다.
- portal 초기 시험 화면은 제품 채팅 화면과 다른 기능·화면 ID를 갖고 `integration`
  작업흐름에서 계약 시험용으로 만든다. 상세 portal은 별도 작업흐름에서 뒤에 진행한다.
- 승인된 작업흐름의 기능 추가·수정은 변경 요청으로 영향 범위를 판정한 뒤, 별도 슬라이스가
  설계 확인 → 테스트 우선 구현 → 검증을 돈다.
- 업무 확장은 `extension:<이름>` 작업흐름으로 등록한다. **제품 모듈은 ADR-007에 따라
  system·admin·agent·portal 넷이며**, 업무 확장은 그 수에 포함하지 않는다.
- portal↔agent 응답 계약은 표현 도구의 설정 객체가 아니라 의미 블록과 버전을 제공한다.
  구체 스키마와 호환 규칙은 `integration` 작업흐름 G3에서 확정한다.
