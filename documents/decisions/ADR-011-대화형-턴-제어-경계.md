# ADR-011 — 대화형 턴 제어는 스트리밍·영속 입력함·실행 경계로 나눈다

| 항목 | 내용 |
|---|---|
| 결정 일자 | 2026-09-16 (사용자 결정) |
| 상태 | accepted |
| 근거 자료 | 사용자 요구사항 검토 · Amazon Bedrock 공식 API 문서(2026-09-16 확인) |
| 반영 위치 | 영향 목록 §7 — 별도 사용자 확인 뒤 정본 요구사항에 반영 |

## 1. 맥락

portal의 추가 입력은 처리 중인 agent 인스턴스와 다른 HTTP 요청·다른 인스턴스로 들어올 수 있다. LLM 호출을 하나의 동기 블로킹 코드 경로로만 두면 그 입력을 처리할 수 없고, 공급 경로마다 스트리밍·원격 취소·양방향 입력 지원도 다르다. 특히 대상 시스템 실행 API를 전송한 뒤에는 Hub가 사용자 중단으로 그 업무 처리를 취소할 수 없다.

Amazon Bedrock은 모델별 응답 스트리밍(`InvokeModelWithResponseStream`·`ConverseStream`)을 제공하지만, 양방향 스트림은 현재 Nova Sonic 음성 계열에 한정된다. 일반 텍스트 대화에서 웹소켓 양방향 입력을 공통 전제로 둘 수 없다.

## 2. 고려한 대안

### 대안 A — 스트리밍을 최소선으로, 영속 입력함과 실행 경계를 둔다 — 채택

- 내용: portal은 모든 중단·추가 입력을 DB의 append-only 입력 이벤트로 먼저 접수한다. LLM 호출은 독립 작업으로 실행하고, 점유한 agent 워커만 입력 이벤트를 읽어 제어한다. 운영 대화형 공급 경로는 최소 응답 스트리밍을 지원해야 하며, 웹소켓·원격 취소·실행 중 입력은 capability로만 사용한다.
- 장점: 다중 인스턴스에서 화면 세션과 무관하게 동작한다. DB가 정합성 원본이므로 알림 유실·워커 재기동에도 입력을 잃지 않는다. 비스트리밍 모델을 대화형 기본 경로에 넣어 중단 가능하다고 오해시키지 않는다.
- 단점: 공급 경로 선정 때 스트리밍 검증이 필요하며, 분류·입력 이벤트·점유의 상태 모델이 늘어난다.
- 비용/난이도: P2~P3에서 턴 입력 이벤트·공급 경로 capability·상태 표시·계약 시험을 설계·구현한다.

### 대안 B — 웹소켓 양방향 통신을 운영 최소선으로 강제한다

- 내용: 모든 대화형 공급 경로가 실시간 양방향 세션에서 추가 입력을 즉시 수신해야 한다.
- 장점: 가장 짧은 수정 반영 지연을 기대할 수 있다.
- 왜 선택하지 않았나: 일반 텍스트 LLM 공급 경로에 공통으로 성립하지 않는다. Amazon Bedrock의 양방향 스트림도 현 시점에는 Nova Sonic 음성 계열에 한정된다. 공급사 선택을 불필요하게 좁히고, 외부 업무 API의 비가역성도 해결하지 못한다.

### 대안 C — 단건 응답형 공급 경로도 대화형 기본 경로로 허용한다

- 내용: LLM 응답이 끝난 뒤에만 중단·수정 입력을 확인한다.
- 장점: 어댑터 구현과 공급사 선정이 단순하다.
- 왜 선택하지 않았나: 사용자 중단이 사실상 지연되고, 수정 입력이 이미 생성된 결과 뒤에만 반영된다. 긴 응답의 비용·대기 문제를 해결하지 못하며 REQ-018의 진행 상태 근거도 약하다.

## 3. 결정

**운영 대화형 LLM 공급 경로는 최소 응답 스트리밍을 지원해야 한다. portal의 제어 입력은 DB 영속 입력함을 정본으로 하고, P1에서는 주기 확인으로 정합성을 보장하며 DB 알림은 지연을 줄이는 선택 최적화로만 둔다. 텍스트 생성 중 중단은 즉시 시도하되, 수정·보강은 현재 응답을 종료한 뒤 새 회차에서 처리하고, 대상 시스템 실행 API가 전송된 뒤에는 중단 불가 사실과 결과 확인 상태를 사용자에게 알린다.**

## 4. 근거

- 다중 인스턴스에서 portal의 HTTP 세션·로컬 메모리 큐는 공유된 사실이 아니다. DB 입력 이벤트와 점유 펜스가 인스턴스 경계를 넘는 유일한 정합성 근거다.
- DB 알림은 연결 단절·재기동 중 유실될 수 있으므로 업무 입력의 원본이 될 수 없다. 주기 확인을 남기면 알림이 없어도 결국 처리한다.
- 스트리밍은 텍스트 생성 중 사용자 중단을 빠르게 감지하고 클라이언트 측 취소를 시도할 기회를 준다. 그러나 원격 취소·양방향 입력은 공급 경로별 capability이며 공통 약속이 아니다.
- 대상 시스템 실행 API는 전송 순간부터 업무 효과가 발생할 수 있다. Hub의 연결 취소를 업무 취소로 표시하면 사용자가 잘못 판단한다.

## 5. 포기한 것

- 단건 응답형 모델을 portal의 대화형 기본 경로로 사용하는 선택을 포기한다. 해당 모델은 배치·비대화형 경로 또는 개발 검증용으로 한정한다.
- 웹소켓 양방향 모델에서 가능한 즉시 입력 주입을 공통 UX로 약속하지 않는다.
- DB 알림만으로 즉시성을 보장하지 않는다. 주기 확인만큼의 지연은 남으며, 정확한 주기는 부하 시험으로 정한다.
- 이미 대상 시스템에 전송된 실행 요청을 Hub의 중단 버튼으로 되돌릴 수 있다고 약속하지 않는다.

## 6. 되돌리기

- 되돌릴 수 있는가: 예. 구현 전이다.
- 방법: 운영 대화형 최소 capability를 단건 응답까지 낮추거나, 실시간 양방향을 필수 capability로 올린다. 입력함의 정본을 별도 메시지 브로커로 바꾸려면 전달 보장·재처리·감사 경계를 다시 설계한다.
- 예상 비용: REQ-030~035·037, NFR-023, FEAT-215~216, ARCH-070 및 공급 경로 계약·턴 상태·API/TC 설계의 재작업. 구현 후에는 데이터 이행과 다중 인스턴스 회귀 시험이 추가된다.
- 되돌려야 한다는 신호: 스트리밍 지원 공급 경로가 고객사의 사용 조건을 충족하지 못하거나, 주기 확인 지연이 사용자 응답성 목표를 계속 위반하거나, 대상 시스템이 승인된 업무 취소 API를 제공해 별도 취소 흐름이 요구될 때.

## 7. 영향

- 영향 산출물(자동 수정하지 않음): `REQ-030`~`REQ-035` · 신규 실행 API 전송 경계 요구사항 · `NFR-023` · `FEAT-215`~`FEAT-216` · `ARCH-070` · 공급 경로 계약(IF-003) · 관련 API·테스트 설계.
- 후속으로 정해야 할 것:
  - 자연어 추가 입력의 묶음 기간, 한 턴당 분류 호출 상한, 제어용 LLM 용량 예약값
  - DB 알림 사용 여부와 주기 확인 상한의 부하 시험 기준
  - 공급 경로별 `STREAM_OUTPUT`·`REMOTE_CANCEL`·`MID_TURN_INPUT` capability 검증표
  - 대상 시스템의 업무 취소 API를 별도 실행 액션으로 등록할 기준
