# ADR-009 — 모듈별 기준선과 로컬 샘플 배포를 분리한다

| 항목 | 내용 |
|---|---|
| 결정 일자 | **2026-09-13** — 사용자 승인 |
| 상태 | **accepted** |
| 적용 범위 | RM-P1 system의 Liquibase, sample 참조 구현, 로컬 개발과 제품 배포 |
| 관련 결정 | ARCH-027, CR-018, CR-019 |

## 1. 맥락

현재 Liquibase master는 스키마·시드·sample 파일을 한 목록으로 151개 포함한다. 신규 설치에는
정확하지만, 누적 이력이 길고 sample이 제품 배포물에도 항상 실린다. 사용자는 현재 최종 상태를
새 설치 기준선으로 합치고, sample은 local에서만 사용하도록 결정했다.

## 2. 고려한 대안

### 대안 A — 모듈별 기준선과 local 전용 sample을 함께 도입한다 — 사용자 선택

- 내용: 루트 master는 모듈 master를 명시 순서로 포함한다. 제품 빌드는 sample 백엔드·프런트·시드를
  제외하고 local 배포 변형만 함께 넣는다. 기존 로컬 DB는 삭제 후 새 기준선으로 다시 만든다.
- 장점: 신규 설치가 짧고, 고객 전달물에 참조 구현과 `SMPL_*` 데이터가 남지 않는다.
- 단점: 기존 DB는 기준선으로 자동 전환되지 않으며, local과 제품 두 변형을 계속 시험해야 한다.
- 비용/난이도: 높음. Gradle·Vite·Liquibase·시드·문서·검증 계약을 함께 고친다.

### 대안 B — 누적 changeset과 현재 sample 포함 배포를 유지한다

- 장점: 기존 DB와 빌드 절차를 바꾸지 않는다.
- 단점: 신규 설치 이력과 고객 전달물의 불필요한 sample이 계속 늘어난다.
- 왜 선택하지 않았나: 사용자가 초기 설치 단순화와 local 전용 sample을 명시했다.

## 3. 결정

**현재 최종 상태의 모듈별 기준선을 새 빈 DB의 유일한 설치 경로로 삼고, sample은 local 배포
변형에서만 백엔드·프런트·Liquibase 시드와 함께 포함한다.**

## 4. 근거

1. 새 빈 DB는 기존 이력을 보존할 이유가 없고, 최종 상태 한 번으로 재현하는 편이 설치 오류를 줄인다.
2. Spring 프로파일은 실행 뒤에 적용되므로 제품 산출물에서 코드를 빼려면 Gradle·Vite의 빌드 경계가 필요하다.
3. sample의 코드·메뉴·시드는 한 조각으로 포함하거나 제외해야 소스와 DB가 어긋나지 않는다.

## 5. 포기한 것

- 기존 DB에 `DATABASECHANGELOG`만 비워 기준선으로 자동 전환하는 간편한 방법.
- local과 제품이 같은 단일 산출물을 쓰는 단순함.

## 6. 되돌리기

- 되돌릴 수 있는가: 가능하나 높음.
- 되돌리는 방법: 이전 changeset master와 sample 포함 빌드 변형을 복원하고, 새 빈 DB를 다시 만든다.
- 예상 비용: CR-019의 Gradle·Vite·Liquibase·시드·문서·두 배포 변형 검증을 재작업한다.
- 되돌려야 한다는 신호: 제품 배포가 sample API를 공식 지원해야 하거나 모듈 기준선이 신규 DB를 재현하지 못하는 경우.

## 7. 영향

- 산출물: ARCH-027, CR-018, changelog 표준·playbook, build/deploy 안내, sample 화면 문서.
- 후속으로 정해야 할 것: 공유·운영 DB가 생긴 뒤 기준선 전환이 필요하면 별도 데이터 마이그레이션 계획을 승인한다.
