# AI Agent Hub 구축 가속 패키지

기업의 여러 레거시 업무 시스템을 하나의 대화 창구로 연결해, 사용자가 자연어로 **조회·실행·자동화**할 수 있게 하는 Agentic AI Hub입니다.

이 저장소는 처음부터 개발하는 SI 프로젝트의 빈 골격도, 설치만 하면 끝나는 완제품도 아닙니다. 인증·권한·관리 화면·AI 운영 규칙·연동 구조·개발 표준을 갖춘 기준 제품을 바탕으로, 고객사의 사용자·업무 지식·스키마 카탈로그·실행 API를 채워 빠르게 구축하는 **구축 가속 패키지(Solution Accelerator)**입니다.

> 내부에서 간단히 “템플릿”이라고 부를 수는 있지만, 고객 제안과 수행 문서에는 **AI Agent Hub 구축 가속 패키지**를 권장합니다. “재사용 가능한 기준 제품 + 고객별 설정·데이터 구축 + 필요한 범위의 확장”이라는 성격을 가장 정확히 전합니다.

이 문서는 프로젝트 수행 팀이 이 패키지로 고객사 구축을 시작할 때, 무엇을 가져가고 무엇을 고객사와 함께 만들어야 하는지 빠르게 파악하도록 돕습니다.

## 1. AI Agent Hub 시스템 개요

### 무엇을 해결하는가

현업 사용자는 시스템마다 화면을 찾아다니거나 데이터를 내려받아 수작업으로 조합하지 않고, 목적을 자연어로 말합니다. Hub는 허용된 업무 지식과 카탈로그를 바탕으로 조회 계획을 제시하고, 권한·마스킹·승인·감사를 거쳐 결과를 보여 주거나 업무 API를 실행합니다.

이 시스템의 기본 방향은 “AI가 모든 것을 알아서 실행한다”가 아닙니다. **고객사가 등록·검토한 업무 의미와 권한 안에서, 사람이 확인 가능한 방식으로 AI를 업무에 연결한다**는 것입니다.

| 영역 | 기준 제품에 포함되는 역할 | 고객사 구축에서 주로 하는 일 |
|---|---|---|
| `system` | 인증, 메뉴, 역할·개인 권한, 코드, 메시지, 공통 사용 이력 | 사용자·조직·역할·권한 기준과 운영 계정 정책 반영 |
| `admin` | 연동·업무 지식·AI 정책·품질·비용·감사 관리 | 지식 베이스, 스키마 카탈로그, API 목록, 승인·운영 정책 등록 |
| `agent` | 자연어 처리, 조회·실행 계획, 정책 적용, 상태·이력 처리 | 대상 시스템 API·DB·DW와의 실제 조회·실행 경로, 고객 업무 용어·지식 기반 응답 품질 검증 |
| `portal` | 현업 사용자의 질의, 결과 확인, 승인·알림 경험 | 사용자 집단별 사용 흐름과 필요한 표현 방식을 검증 |
| 업무 확장 (`extension:<이름>`, 선택) | Hub와 한 빌드로 함께 구축하는 고객 업무 시스템 | 업무 DB·메뉴·업무 기능을 자체 소유하고 Hub와의 계약을 구현 |

### 고객사마다 달라지는 것과 유지하는 것

구축의 중심은 기존 소스를 대규모로 다시 만드는 일이 아니라, 고객사의 업무 맥락을 안전하게 입력하고 검증하는 일입니다.

| 구분 | 고객사에 맞춰 구축하는 내용 | 기준 제품으로 유지하는 내용 |
|---|---|---|
| 사용자·권한 | 사용자, 조직, 역할, 메뉴·행위 권한, 승인 책임 | 인증·인가 방식과 공통 이력 구조 |
| 업무 지식 | 업무 용어, 규정·매뉴얼, FAQ, 최신성·검토 책임자 | 지식 등록·검토·검색·품질 관리 흐름 |
| 데이터 의미 | 스키마 카탈로그, 테이블·컬럼의 업무 의미, 민감정보·마스킹 규칙 | 카탈로그 기반 조회 계획·권한 검사 구조 |
| 실행 연결 | 실행 API, 파라미터, 승인 조건, 대상 시스템 계약 | 승인·만료·감사·오류 처리 원칙 |
| 운영 정책 | 모델 사용 범위, 쿼터, 비용, 품질 신고·개선 절차 | 정책 적용과 운영 현황 관리 기반 |
| 화면·기능 확장 | 고객 고유 업무와 패키지 범위를 벗어난 기능 | 공통 모듈 경계, 표준, 자동 검증 규칙 |

따라서 고객사 구축의 일반적인 우선순위는 다음과 같습니다.

```text
사용자·권한 기준 확정
        ↓
업무 지식 · 스키마 카탈로그 · 실행 API 등록
        ↓
권한·마스킹·승인·감사 조건 검증
        ↓
대표 업무에서 현업 사용성·응답 품질 검증
        ↓
정말 필요한 고객 고유 기능만 확장
```

### 두 가지 구축 형태

Hub는 특정 업무 시스템에 고정되지 않습니다. 고객 상황에 따라 다음 두 형태를 수용합니다.

1. **독립 운영** — 이미 운영 중인 여러 업무 시스템을 Hub에 연동합니다. 여러 시스템에 흩어진 조회·실행 업무를 하나의 창구로 묶는 경우에 적합합니다.
2. **통합 구축** — 새 업무 시스템 구축과 함께 Hub를 업무 확장으로 포함합니다. 이때도 업무 시스템의 데이터·수명주기는 해당 확장이 소유하고, Hub는 AI 사용 경험과 운영 통제를 제공합니다.

`integration`은 별도의 제품·업무 시스템 모듈 이름이 아니라, `portal`·`agent`·업무 확장 사이의 **API 계약 버전·호환성·계약 시험을 관리하는 작업흐름**입니다. 따라서 고객 업무 시스템을 Hub와 함께 만들 때는 `integration`이 아니라 **업무 확장**으로 등록합니다.

### 기준 제품을 다룰 때의 원칙

- 고객 데이터와 정책을 먼저 구성합니다. 공통 코드를 고치기 전에 기존 설정·관리 기능으로 해결 가능한지 확인합니다.
- AI가 참조하거나 실행하는 모든 대상은 카탈로그·권한·승인·감사의 대상이어야 합니다.
- 고객 고유 변경은 모듈 경계와 추적성을 유지한 기능 단위로 설계·승인·구현합니다. 편의상 공통 제품 코드를 복사하거나 직접 우회하지 않습니다.
- 현재 구현 범위와 남은 제품 성숙도는 항상 [`documents/project.state.yaml`](documents/project.state.yaml)과 [`documents/spec/`](documents/spec/)을 기준으로 확인합니다. README의 설명은 제품 약속이나 최신 진척의 정본이 아닙니다.

## 2. AI 주도 개발 방법을 적용한 프로젝트 수행 흐름

이 패키지는 코드뿐 아니라, AI가 요구사항을 빠뜨리거나 독단으로 구현하지 않도록 하는 수행 방법을 함께 제공합니다. AI는 PM·BA·아키텍트·개발자·테스터의 반복 작업을 돕고, 고객과 수행 팀은 업무 사실·우선순위·승인 판단을 맡습니다.

### 수행의 기본 원리

1. **업무 흐름을 기능보다 먼저 확인합니다.** 현행 업무의 문제와 예외를 듣고 To-Be 프로세스를 만든 뒤 요구사항을 뽑습니다.
2. **정본은 하나로 유지합니다.** `documents/spec/`이 요구사항·설계·테스트 연결의 유일한 진실이며, 생성 문서는 정본을 대신하지 않습니다.
3. **단계마다 사람이 승인합니다.** AI가 초안을 만들고 기계 검사를 실행해도, 게이트를 넘는 결정은 고객·의사결정자의 명시 승인 없이는 하지 않습니다.
4. **기능은 작은 수직 단위로 만듭니다.** 하나의 업무 흐름에 필요한 화면·API·데이터·테스트를 함께 완성해 검증합니다.
5. **변경은 흔적을 남깁니다.** 이미 승인한 설계나 요구사항을 바꾸면 영향·대안·되돌리기 비용을 확인한 뒤 변경 요청으로 처리합니다.

### 고객사 구축의 권장 흐름

| 단계 | 고객사·수행 팀이 함께 결정할 것 | AI와 패키지가 만드는 것 | 완료 판단 |
|---|---|---|---|
| 0. 착수 | 목표, 범위, 이해관계자, 제약, 성공 기준 | 프로젝트 헌장·용어 초안·질문 목록 | 착수 게이트 승인 |
| 1. 발견·요구사항 | 1차 적용 업무, 현행 문제, 예외, 담당자, 우선순위 | To-Be 프로세스, 요구사항, 비기능 요구, 추적성 초안 | 요구사항 게이트 승인 |
| 2. 아키텍처 | 연동 경계, 데이터 소유권, 보안·운영 제약, 되돌리기 비싼 선택 | 모듈·데이터·인터페이스 설계, ADR(아키텍처 의사결정 기록) | 아키텍처 게이트 승인 |
| 3. 상세 설계 | 화면 동작, 승인 규칙, 예외 처리, 고객 고유 확장 범위 | 유즈케이스, API·화면·테스트 명세, 목업 | 설계 게이트 승인 |
| 4. 구현 | 우선순위가 높은 기능의 수용 기준 | 테스트 우선 수직 슬라이스, 시드·마이그레이션·코드 | 기능별 미니 게이트 |
| 5. 검증 | 실제 사용자 시나리오, 권한·보안·운영 수용 기준 | 자동 시험, 계약·통합 시험, 결함 근거 | 검증 게이트 승인 |
| 6. 인수·운영 전환 | 운영 책임, 교육, 장애·백업·모니터링 절차 | 사용자 안내, 운영 런북, 인수 근거 | 납품 게이트 승인 |

각 단계는 다음의 짧은 고리를 반복합니다.

```text
고객 업무 사실 확인 → AI 초안·추적성 생성 → 팀 검토·기계 검사
                     → 위험·예외 반박 → 고객의 명시 승인 → 다음 단계
```

### 고객사 데이터를 다루는 실무 순서

첫 번째 적용 업무를 정한 뒤에는 아래 순서가 가장 안정적입니다.

1. **대표 업무를 하나 고릅니다.** 시스템 경계를 넘고, 반복 수작업이 많으며, 담당자와 데이터 접근 근거를 확보할 수 있는 업무가 적합합니다.
2. **현재 처리 시간·건수와 실패 사례를 기록합니다.** 도입 효과는 추정치가 아니라 적용 전·후 비교로 판단합니다.
3. **사용자·권한과 업무 자산의 책임자를 확정합니다.** 누가 어떤 데이터·API를 읽고 실행할 수 있는지, 누가 지식의 최신성을 검토하는지 정합니다.
4. **지식 베이스와 카탈로그를 입력·검토합니다.** 문서를 많이 넣는 것보다 업무 용어·출처·최신성·민감정보 규칙을 명확히 하는 편이 중요합니다.
5. **조회·실행을 계약 시험으로 검증합니다.** 정상 경로뿐 아니라 권한 부족, 마스킹, 승인 거절·만료, 연동 오류를 함께 확인합니다.
6. **사용자 테스트 후 확장 여부를 결정합니다.** 설정으로 해결되지 않는 요구만 영향 분석을 거쳐 제품 확장 또는 고객 확장으로 분리합니다.

## 시작하기 전에 확인할 질문

고객사 프로젝트를 실제로 시작할 때 다음 질문의 답이 있어야 패키지를 빠르게 적용할 수 있습니다.

- 첫 번째로 검증할 실제 업무는 무엇이며, 현재 처리 시간·건수는 얼마인가?
- 어떤 업무 시스템·DB·API·문서에 접근할 수 있으며, 각각의 데이터 소유자는 누구인가?
- 사용자·역할·승인 책임과 개인정보·민감정보 처리 기준은 무엇인가?
- 지식 베이스와 스키마 카탈로그를 누가 등록·검토·최신화할 것인가?
- 고객사 표준 인프라·인증·모니터링·망 분리 제약은 무엇인가?
