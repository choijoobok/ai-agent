# 레드팀과 뮤테이션 — 테스트가 진짜 검증하는가

## 3. 레드팀 패스 — AI의 자기반박 (게이트마다 필수)

AI의 최대 실패 모드는 **자기 산출물에 대한 무비판**이다. 절차로 강제한다.

### 실행 방법
`[QA-레드팀]` 모자로 전환하고, **작성자가 아니라 인수 심사자의 입장에서** 아래 4개를 산출한다.

```markdown
### [QA-레드팀] G3 자기반박

**1) 이 설계가 틀렸다면, 가장 가능성 높은 이유 3가지**
   (추상적 우려 금지. "무엇이 어떻게 잘못되는지" 구체적으로)
   1. 재고 차감 시점을 출고확정으로 잡았는데 현장은 피킹 시점을 기대할 수 있음
      → 실제 결과: 피킹~확정 사이 이중 할당 발생, 재고 마이너스
   2. ...

**2) 다루지 않은 예외·경계**
   - 반품 후 재입고 시 로트 정책 미정의
   - 마감된 회계기간에 소급 입력 시도

**3) 사용자가 나중에 "이거 아닌데" 할 지점**
   - 엑셀 일괄 업로드를 범위 밖으로 뒀음 (현업은 당연히 있다고 볼 것)

**4) 지금 결정을 미루면 나중에 얼마나 비싼가**
   - 재고 차감 시점: 구현 후 변경 시 슬라이스 5개 재작업 (High)
```

### 레드팀 규칙
- **"문제 없습니다"는 유효한 결과가 아니다.** 최소 3개를 반드시 낸다. 없으면 아직 안 들여다본 것이다.
- 지적한 것은 반드시 처리한다: 수정 / `ASM-###` 등록 / 사용자 결정 요청 중 하나.
- 레드팀 결과를 게이트 승인 요청에 **그대로 포함**한다. 숨기지 않는다.

## 4. 테스트가 진짜 검증하는지 확인 — 뮤테이션 검사 (필수)

### 왜 필요한가

2026년 실증이 지목한 AI 코드의 핵심 실패 모드는 이것이다.

> **AI가 만든 변경 대부분은 테스트를 통과하고 합리적으로 보이면서도,
> 지켜야 할 규칙에서 표류한다.**

원인은 명확하다. **AI가 코드를 먼저 쓰면 그 코드에 맞는 테스트를 쓴다.**
TEST-FIRST(`aidd-guide/process/07-slice.md` §3-③)로 절반은 막지만, TC 자체가 약하면 여전히 헛돈다.
"테스트 통과"를 완료 조건으로 삼는 한, 테스트의 강도를 따로 검증해야 한다.

Thoughtworks Technology Radar Vol.34는 뮤테이션 테스트를 코딩 에이전트의
**feedback control**(사람 리뷰 전에 자기교정을 유발하는 장치)로 명시 지목했다.

### 방법 1 — 규칙 뒤집기 (모든 트랙 필수, 언어 무관)

슬라이스마다, 해당 UC의 `business_rules` 각각에 대해:

```
1. 규칙을 코드에서 의도적으로 뒤집는다
   예) "예정 수량 ≤ 발주 잔량"  →  부등호를 반대로, 또는 검사 자체를 주석 처리
2. 테스트를 돌린다
3. 최소 1개가 실패해야 한다
4. 실패하면 되돌리고 다음 규칙으로
5. ★ 아무 테스트도 실패하지 않으면, 그 규칙은 검증되지 않고 있다 ★
   → TC를 추가하고 다시 확인한다
```

보고 형식:

```markdown
### 규칙 뒤집기 검사 — SLICE-007

| 업무 규칙 | 뒤집은 방식 | 실패한 테스트 | 판정 |
|---|---|---|---|
| 예정 수량 ≤ 발주 잔량 | `<=` → `>=` | TC-0122 | 검증됨 |
| 예정일은 오늘 이후 | 검사 제거 | **없음** | **미검증 → TC-0124 추가** |
| 중복 예정번호 거부 | unique 검사 제거 | TC-0123 | 검증됨 |
```

**미검증 규칙이 하나라도 남으면 G4를 통과할 수 없다.**
느리지 않다. 규칙 3~5개면 슬라이스당 몇 분이다.

### 방법 2 — 자동 뮤테이션 테스트 (Standard/Full 트랙)

| 언어 | 도구 |
|---|---|
| Java / Kotlin | PIT (pitest) |
| JavaScript / TypeScript | Stryker Mutator |
| Python | mutmut, cosmic-ray |
| C# | Stryker.NET |
| Go | go-mutesting |
| Ruby | mutant |

**뮤테이션 스코어 임계값**

| 트랙 | 대상 | 임계 |
|---|---|---|
| Lite | — (방법 1로 대체) | — |
| Standard | 도메인·서비스 계층 | ≥ 60% |
| Full | 도메인·서비스 계층 | ≥ 75% |

전체 코드에 돌리지 않는다. **업무 규칙이 사는 계층만** 대상으로 한다.
컨트롤러·DTO·설정에 뮤테이션을 돌리면 시간만 쓰고 얻는 게 없다.
