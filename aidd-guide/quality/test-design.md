# 테스트 케이스 설계 — 최소 세트와 비기능 TC

## 1. 테스트 케이스 설계 (P3에서 작성, 구현 전에 존재해야 함)

### 최소 세트 — 모든 FEAT는 아래를 갖는다
| 유형 | 필수 | 내용 |
|---|---|---|
| 정상 (Happy) | ● | UC 기본 흐름대로 성공 |
| 입력 검증 | ● | 필수 누락, 형식 오류, 길이/범위 초과 |
| 업무 예외 | ● | UC 예외 흐름 각각 (권한 없음, 중복, 상태 불일치 등) |
| 권한 | ● | 권한 없는 액터의 접근 차단 |
| 경계값 | ○ | 0, 1, 최대값, 최대값+1, 음수, 빈 목록 |
| 동시성 | △ | 같은 자원 동시 수정 (해당되는 FEAT만) |
| 멱등성 | △ | 같은 요청 2회 (결제·확정 등 되돌릴 수 없는 액션) |

### TC 작성 형식 (`documents/spec/70-testcases.yaml`)
```yaml
- id: TC-0122
  feature: FEAT-012
  usecase: UC-004
  type: business_exception
  title: 동일 예정번호 중복 등록 거부
  precondition: "예정번호 IP-20260101-001 이 이미 존재"
  actor: ACT-003
  steps:
    - "카탈로그등록 화면에서 이미 등록된 테이블 HR.EMPLOYEE 선택"
    - "저장 클릭"
  expected: "'이미 등록된 테이블입니다' 오류. 저장되지 않음. 기존 데이터 불변."
  priority: high
```

## 2. 화면 케이스는 무엇으로 잠그나 — **선언을 읽는다**

요건서 §9 의 케이스 절반이 *화면을 봐야* 판정되는 것처럼 보인다 — 헤더에 버튼이 셋인가,
배지 색이 셋인가, 그 컬럼이 기본 숨김인가. **그런데 이 프로젝트의 화면은 선언형이다.**
그것들은 전부 컬럼·버튼 선언 객체에 적혀 있고, **브라우저도 렌더링 라이브러리도 없이 읽힌다.**

| 케이스가 묻는 것 | 무엇을 읽나 | 잠기나 |
|---|---|---|
| 버튼이 셋뿐이다 · 저장 버튼이 없다 | `api` 선언에 `save` 키가 없다 | **기계** |
| 정렬이 한 컬럼만 열린다 | `sortable` 이 붙은 컬럼 수 | **기계** |
| 배지 색이 셋 · 글자가 열다섯 | `tone` 맵의 값 집합 크기 | **기계** |
| 그 컬럼이 기본 숨김이다 | `hidden` | **기계** |
| 그 컬럼이 아예 없다 | 컬럼 배열 | **기계** |
| 조회조건 콤보가 둘로 갈려 있다 | `searchFields` 배열 | **기계** |
| 배지가 실제로 그려진다 · 툴팁에 전체 값이 뜬다 | 렌더링 결과 | 사람 |
| 레이아웃이 접히지 않는다 | 브라우저 | 사람 |

- **선언 검사는 단위 테스트다.** `buildColumns()` 를 부르고 배열을 검사하면 끝난다 —
  컴포넌트를 마운트하지 않으므로 빠르고 깨지지 않는다.
- **`되면 안 되는 것` 은 대개 선언의 부재로 이룬다**(감추는 코드가 아니라). 그래서
  *"없다"* 를 검사하는 것이 곧 그 케이스를 잠그는 것이다.
- **잠글 수 없는 것을 잠금으로 적지 않는다.** 요건서의 케이스 표에 *기계 / 사람* 을
  표시하고, 사람 몫은 §6.3 ⑤ 사용자 테스트로 넘긴다 — **AI 의 게이트 초록이 그것을
  갈음하지 않는다**(CLAUDE.md §6.3).

## 3. 열거형을 나눈 묶음 — **전수 커버를 테스트가 잠근다**

코드 열다섯을 *실패 · 종료 · 성공* 셋으로 접는 것 같은 묶음이 있다. **새 코드를 더하면서
묶음을 안 정하면 그 코드는 어느 묶음에도 안 걸려, 그 조회를 하는 사람의 목록에서
말없이 빠진다.** 조용한 누락이 틀린 값보다 나쁘다.

**테스트가 주 방어선이다.**

```java
for (LoginResultCode code : LoginResultCode.values()) {
    assertThat(어느_묶음에_들었나(code)).as("%s 가 어느 묶음에도 없다", code).isNotNull();
}
```

- **정적 초기화에 기대지 않는다.** 그것이 기동에 도는지는 *누가 그 클래스를 먼저
  건드리나* 에 달렸고, **아무것도 그 의존을 선언하지 않는다** — 투영 목록을 메서드 안으로
  옮기는 흔한 리팩터 하나로 검사가 조용히 첫 조회로 밀린다. 남겨 두는 것은 좋으나
  **이중 방어이지 방어선이 아니다.**
- **기동에서 터지는 것도 늦다.** 운영에서 발견되지만 빌드는 개발자 자리에서 끝난다.
- **접두로 판정하지 않는다**(`startsWith("FAIL_")`). 열거형에 이름을 더하는 순간
  **묶음이 조용히 바뀐다** — 집합을 적어야 안 정한 코드가 드러난다.
- 실물: `domain/auth/LoginResultGroup` · `LoginLogSpecTest`.

## 4. 비기능 테스트 (NFR별로 반드시 하나)

측정하지 않은 NFR은 존재하지 않는 것으로 본다. G5에서 실측값 없으면 미충족.

| NFR 유형 | 측정 방법 예 |
|---|---|
| 응답시간 | 대표 트랜잭션 3종, 목표 데이터량 상태에서 p50/p95/p99 |
| 처리량 | 동시 사용자 N명 시나리오, 초당 처리 건수 |
| 가용성 | 장애 주입 후 복구 시간 측정 |
| 보안 | 인증 우회, 권한 상승, SQL 인젝션, 민감정보 노출 점검 |
| 데이터 정합성 | 동시 질의 후 토큰 쿼터 합계 일치 검증 |
| 운영성 | 로그로 장애 원인 추적 가능한지 실제로 해보기 |
