# ADR-0008. 개인정보 분리보관(PII Vault) 패턴 채택

- 상태: **채택 — 단, 설계 개요 에서 재검증**
- 일자: 2026-08-23 (2026-08-26 개정: 적용 시점을 Phase 12 로 미루고 **테이블 설계를 처음부터 다시 한다.** 분리보관이라는 방향은 유지하되 스키마는 재설계 대상이다)

## 맥락

개인정보를 원본 테이블에 암호화해 저장하는 방식(컬럼 암호화)과,
참조키만 남기고 별도 저장소에 모으는 방식(vault) 중 선택이 필요했다.

## 결정

**PII Vault 패턴**을 채택한다.

- PII 컬럼은 원본 테이블에 **`CHAR(36)` 참조키(UUID)** 만 저장
- 실제 값은 `SYS_PII_VAULT` 에 AES-256-GCM 암호화 저장
- 대상 컬럼과 마스킹 규칙은 `SYS_PII_DEF` 로 **화면에서 관리** (코드 배포 없이 추가)
- 저장은 Hibernate 이벤트 리스너로 **완전 자동**
- 조회는 **API 응답 직렬화 계층**에서 일괄 복호화·마스킹

상세: [27-pii-vault.md](../../standard/backend/pii-vault.md)

## 근거

- 개인정보가 한 테이블에 모여 **접근 이력·파기·키 롤링을 한 곳에서** 처리할 수 있다.
- 원본 테이블 스키마에 암호문 길이를 고려한 컬럼 확장이 불필요하다.
- 대상 컬럼 추가가 **DDL 없이 데이터 등록만으로** 가능하다.

## 조회 자동화 — 대안 비교

요구는 "JPA·QueryDSL·MyBatis 조회 시 자동 감지 복호화" 였다. 검토 결과 ORM 계층 자동화는 실패한다.

| 대안 | 판정 |
|---|---|
| Hibernate `PostLoadEventListener` | ❌ **QueryDSL DTO 프로젝션에서 이벤트 미발생.** 목록 화면 대부분이 이 경로. 엔티티 조회도 행마다 vault 조회로 N+1 |
| MyBatis `Interceptor` + `ResultSetMetaData.getTableName()` | ❌ PostgreSQL JDBC 는 **설계상 빈 문자열** 반환, Oracle 도 동일 사례. 벤더 전용 API 캐스팅은 DB 중립성 위반 |
| JPA `AttributeConverter` | ❌ 컬럼마다 수동 지정 필요 — "자동 감지" 요구 미충족. 복호화 시점에 사용자 권한을 알 수 없어 마스킹 불가 |
| **응답 직렬화 계층 일괄 처리 (채택)** | ✅ ORM 무관 · N+1 없음 · 권한 반영 가능 · 이력 일원화 · DB 중립 |

응답 경계는 **요청자 권한을 알 수 있는 유일한 지점**이라, 마스킹과 접근 이력이 자연스럽게 붙는다.

## 결과

### 감수하는 제약

- **부분 일치 검색이 불가능하다.** 완전 일치만 해시로 지원된다.
  "이름에 '김' 포함" 같은 조건은 성립하지 않는다 → Phase 5 에서 컬럼별 판단 필요
- PII 컬럼 정렬·그룹핑·집계 불가
- PII 컬럼 타입이 전부 `CHAR(36)` 이 된다
- **MyBatis 로 PII 테이블에 쓰기 금지** — 이벤트 리스너를 우회한다
- 응답 경계를 거치지 않는 경로(배치·엑셀·메일)는 `PiiSupport` 유틸 **명시 호출** 필요
- 조회 시 대상 식별은 DTO `@Pii` 애노테이션 기반 **반자동** — 완전 자동은 불가

### 필요한 장치

- `@Pii` 애노테이션 누락 탐지 (참조키 형태 값이 마스킹 없이 응답에 나가는지 검사)
- `SYS_PII_DEF` 전체 캐시 — 저장 경로마다 DB 조회 금지
- vault 고아 행 정리 배치
- 키 버전별 재암호화 배치
