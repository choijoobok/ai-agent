# ADR-0017. 캐시는 대상별로 전략이 다르다 — 공유 캐시 없는 다중화

- 상태: 채택 (**§3 개정 2026-08-28** — 요청 스코프 → **작업 스코프**, [ADR-0026](./0026-config-lookup-util-and-work-scope-snapshot.md))
- 일자: 2026-08-26
- 관련: 비기능 요건 §2.1 · [23-security-design](../../standard/backend/_study/security-design.md) §2·§4 · [24-frontend-stack](../../standard/frontend/_study/frontend-stack.md) §8 · [30-async-and-concurrency](../../standard/backend/crosscutting.md) §3·§6 · [43-data-model-master](../../knowledge/sys/code.md) §8 · [ADR-0002](./0002-selectable-session-store.md) · [ADR-0026](./0026-config-lookup-util-and-work-scope-snapshot.md)

## 맥락

비기능 요건 §2.1 은 *"다중 노드면 Redis"* 로 정했다. 그런데 Redis 를 제대로 운영하려면
센티넬·이중화가 따라오고, 이 비용을 치를 의사가 없는 고객사가 실재한다. 노드를 2대로
늘렸다는 이유만으로 캐시 인프라 하나가 통째로 들어오는 구조다.

**세션은 이미 이 문제를 풀었다**([ADR-0002](./0002-selectable-session-store.md)). 캐시에도 같은 판단을 적용할 수 있는지가
이 문서의 질문이다.

### 먼저 — 캐시를 한 덩어리로 보고 있었다

기존 설계는 `code`·`message`·`config`·`userAuth` 를 한 표에 묶어 **같은 저장소, 같은
무효화 전략**을 적용했다. 그런데 이들은 캐싱하는 **이유가 서로 다르다.**

| 층 | 목적 | 고려해야 하는 것 |
|---|---|---|
| **백엔드 캐시** | 서버 부하 감소 | **다중 노드 간 일관성** |
| **프론트 캐시** | 화면 렌더링 속도 | **사용자마다 갱신 시점이 다르다** |

목적이 다르면 무효화 전략도 달라야 한다. 한 덩어리로 다루면 **가장 비싼 요구에 전부가
맞춰진다** — 권한의 일관성 요구 때문에 코드·메시지까지 공유 캐시가 필요해지는 식이다.

## 결정

**대상별로 전략을 나눈다. 그 결과 노드 간 공유가 필요한 백엔드 캐시가 하나도 남지 않는다.**

| 대상 | 백엔드 | 프론트 | 왜 |
|---|---|---|---|
| 메뉴 트리 | **캐싱 없음** | 메모리(`authStore`) | 로그인 후 1회 로드. 조회가 많지 않다 |
| **유효 권한** | **세션에 담는다** | 메모리(`authStore`) | 매 요청 필요하지만 **낡으면 보안 결함** — §1 |
| 공통 코드 | **캐싱 없음** | **버전 확인 후 캐싱** | 서버 부하는 문제가 아니다. 문제는 화면 렌더링 — §2 |
| 시스템 설정 | **작업 스코프** | **버전 확인 후 캐싱** | **한 덩어리 일 안에서 값이 바뀌면 안 된다** — §3 |
| 다국어 메시지 | **TTL 30~60분** | **버전 확인 후 캐싱** | 건수가 많다(수천~수만) — §4 |
| PII 정의 | 애플리케이션 캐시 | — | 응답 직렬화마다 참조 — §5 |

**공유 캐시(Redis)를 요구하는 항목이 없다.** 다중 노드 무효화 폴링도 필요 없다.

## 1. 유효 권한 — 세션에 담는다

인가 인터셉터는 **매 요청** 유효 권한을 본다([23](../../standard/backend/_study/security-design.md) §4 접근 제어 체인 6번). 그러나 이
데이터는 낡으면 *"회수된 권한이 아직 통과한다"* 가 되므로, 코드·메시지와 같은 지연 허용
전략을 쓸 수 없다.

**세션이 정답인 이유는 셋이다.**

| | |
|---|---|
| 추가 왕복 0 | 세션은 어차피 매 요청 조회된다. [23](../../standard/backend/_study/security-design.md) §4 의 *"요청당 추가 쿼리 0"* 이 유지된다 |
| 다중 노드 일관성 자동 | 세션 스토어가 공유다. 노드마다 다른 값을 가질 수 없다 |
| 즉시 무효화 | 그 사용자의 세션만 건드리면 된다. 폴링 지연이 없다 |

### 담는 것은 계산 결과다

유효 권한은 `{ (MENU_CD, ACTION_CD) }` 쌍의 **평면 집합**이다([23](../../standard/backend/_study/security-design.md) §4). 역할 목록이
아니다 — 역할·개인 예외·유효기간·메뉴 게이트는 전부 **계산 입력**이며 세션에 담지 않는다.
입력을 담으면 매 요청 재계산해야 하므로 담는 의미가 사라진다.

액션 4종을 비트마스크로 접으면 `Map<MENU_CD, byte>` 다. 메뉴 200개에 권한을 가진
사용자여도 **6KB 수준**이다.

### 무효화는 플래그로 한다

권한이 바뀌면 대상 사용자의 세션에 **`authzDirty` 플래그만 세운다.** 권한 집합을 다시
계산해 넣지 않는다.

```
역할 권한 변경 → SYS_USER_ROLE 역방향 조회로 보유자 전원
              → findByPrincipalName(userId) 로 각 세션에 authzDirty=true
              → 각 사용자의 다음 요청에서 인터셉터가 재계산 후 세션 갱신
```

관리자가 역할 하나를 바꾸면 보유자가 100명일 수 있다. 그때 권한 집합 100개를 계산해
쓰는 것보다 **플래그 하나씩 세우는 편이 훨씬 가볍고**, 로그인하지 않은 사용자는 계산조차
하지 않는다.

**세션 검색 능력은 이미 있다.** [23](../../standard/backend/_study/security-design.md) §4-1 이 `SpringSessionBackedSessionRegistry` 를
채택했고, 이는 `FindByIndexNameSessionRepository` 를 요구한다 — AUTH-09(동시 접속 제어)와
AUTH-10(강제 로그아웃)이 이미 쓰는 인터페이스다. 새로 들이는 부품이 아니다.

| 세션 스토어 | 인덱스 |
|---|---|
| `jdbc` | `JdbcIndexedSessionRepository` — 그대로 동작 |
| `redis` | **`RedisIndexedSessionRepository`** 여야 한다. 기본 `RedisSessionRepository` 는 인덱스가 없다 |
| `none` | `MapSessionRepository` — 인덱스 없음. AUTH-09/10 이 이미 갖고 있던 로컬 개발 제약 |

### 날짜 경과는 계산 날짜로 잡는다

[23](../../standard/backend/_study/security-design.md) §4 는 *"기간이 있는 부여는 시간이 캐시를 낡게 만든다"* 를 이미 다뤘고, 판정
단위가 **날짜**(양끝 포함)이므로 값이 바뀔 수 있는 순간은 **업무 시간대의 자정 한 번**뿐임을
확정했다. 해법은 **자정 전체 무효화**였다.

세션 방식에서는 이것이 더 단순해진다. 전체를 순회할 필요가 없다.

```
세션에 authzCalcDate (계산한 업무 시간대 날짜) 를 함께 담는다
인터셉터: authzDirty == true  또는  authzCalcDate != 업무시간대_오늘  → 재계산
```

각 사용자가 **자정 이후 첫 요청에서** 스스로 재계산한다. 자정에 깨어 있는 세션을 찾아
순회하는 작업이 사라진다 — Spring Session 은 principal 별 조회는 제공하지만 전체 순회는
스토어마다 다르다.

> **AUTHZ-08 배치가 하는 일이 셋에서 둘로 준다.** [23](../../standard/backend/_study/security-design.md) §4 가 배치의 역할을 *"캐시
> 무효화 · 이력 기록 · 만료 예정 통보"* 로 정의했는데, 첫째가 필요 없어진다. 이력 기록과
> 통보는 그대로 남는다 — 그것은 캐시 문제가 아니다.
>
> **개정(2026-08-31) — 둘에서 하나가 됐다.** [23](../../standard/backend/_study/security-design.md) §4 가 **이력 기록을 물렸다**:
> 적을 테이블을 [ADR-0010](./0010-request-logging-without-audit-trail.md) 이 만들지 않기로 했고 [42](../../knowledge/sys/menu.md) §3.1 이
> `VALID_TO_DT` 컬럼을 그 자리로 정했다. **여기서 뺀 것과 근거가 다르다** — 이쪽은
> *필요 없어졌다* 이고 그쪽은 *처음부터 배치의 일이 아니었다* 다(자동 만료는 저장이
> 일어나지 않으므로 배치가 쓸 행이 없다). 남는 것은 통보 하나다.

## 2. 공통 코드 — 백엔드는 캐싱하지 않는다

캐싱이 필요한 이유가 **서버 부하가 아니라 화면 렌더링**이다. 한 화면이 콤보 여러 개를
띄우면 코드 그룹을 여러 번 요청하고, 그 왕복이 렌더링을 늦춘다. 서버 쪽 조회 자체는
인덱스 조회 한 번이라 부하로 잡을 수준이 아니다.

**프론트가 그룹 단위로 캐싱한다.** 필요한데 캐시에 없으면 받아서 넣고, 이후에는 캐시를
본다. 유효성 판단은 §6.

> **업무 데이터 콤보는 캐싱 대상이 아니다.** 거래처·담당자처럼 실시간 조회로 채우는
> 콤보는 같은 컴포넌트를 쓰더라도 캐싱하지 않는다. **컴포넌트 차원에서 갈라야 한다** —
> 공통코드용과 업무 데이터용이 한 컴포넌트면 캐싱이 따라 붙는다([24](../../standard/frontend/_study/frontend-stack.md) §7).

백엔드가 코드값을 필요로 하는 지점은 캐시 없이도 성립한다 — `CODE_REF_KEY` 화이트리스트
검증은 코드 저장 시점에만 일어난다.

> **액션 4종은 애초에 공통코드가 아니다**(2026-08-27 — [43](../../knowledge/sys/code.md) §4.3.1). 기동 시 적재되는 것은
> `SYS_API` 이고([23](../../standard/backend/_study/security-design.md) §4), 값 넷은 **소스가 갖는다.** 이전 판이 이 줄을 공통코드의 예로
> 든 것이 **공통코드일 필요가 없다는 증거**였다.

## 3. 시스템 설정 — 백엔드는 작업 스코프

대량 목록을 루프로 처리하는 도중에 설정이 바뀌면 **앞의 1000건과 뒤의 1000건이 다른
규칙으로 처리된다.** 결과만 봐서는 알 수 없는 조용한 사고다.

**작업 스코프 스냅샷**으로 그 작업 동안의 일관성을 보장한다. 작업은 한 노드에서만
처리되므로 다중 노드 문제가 **원천적으로 없다.**

> **이전 판은 이것을 *요청 스코프* 라고 적었다**(2026-08-28 개정 — [ADR-0026](./0026-config-lookup-util-and-work-scope-snapshot.md) §2).
> 요청이 특별해서가 아니라 *"한 덩어리 일 안에서 값이 바뀌면 안 된다"* 를 말하려던
> 것이었고, **배치가 10만 건을 도는 도중에 바뀌어도 같은 사고**다. 요청은 작업의
> 한 종류이며, **가장 오래 도는 일은 요청이 아니다.**

| 작업 | 경계를 여는 곳 |
|---|---|
| HTTP 요청 | 요청 필터 — `requestId` 를 넣는 그 자리([28](../../standard/backend/_study/system-logging.md) §3.3) |
| `@Async` | `ContextCopyingTaskDecorator` — MDC·Locale 을 옮기는 그 자리([30](../../standard/backend/crosscutting.md) §4) |
| `@Scheduled` | 스케줄러 진입 래퍼 — `job`·`requestId` 를 넣는 그 자리([30](../../standard/backend/crosscutting.md) §8) |

- **lazy 로 채운다** — 작업 시작 시 전량을 뜨면 설정을 쓰지 않는 작업까지 쿼리를 낸다.
  처음 필요할 때 읽고 그 작업 동안 재사용한다
- 대량 루프도 조회는 **1회**다 — 루프가 길수록 이 방식이 유리하다
- **비동기는 부모 스냅샷을 복사해 물려받는다**([30](../../standard/backend/crosscutting.md) §3.2) — 스냅샷은 불변 값 묶음이라
  *살아 있는 객체를 전파하지 말라* 는 그 절의 이유가 걸리지 않는다. **스케줄러는 새로 뜬다**
- **경계 밖 호출은 예외로 죽인다** — 조용히 허용하면 위의 사고가 그대로 되돌아온다

**값을 읽는 것은 조회 유틸이며 `SYS_CONFIG` 는 프로퍼티 소스가 아니다** — [ADR-0026](./0026-config-lookup-util-and-work-scope-snapshot.md).
프로퍼티 소스면 읽는 시점이 **기동 한 번**이라 이 절의 스냅샷과 양립하지 않는다.

프론트는 코드와 같다(§2·§6) — 렌더링에 쓰는 표시 형식·자릿수 같은 값이다.

## 4. 다국어 메시지 — 양쪽 다 캐싱한다

수천~수만 건이 될 수 있다. 프론트 번들 API 가 전량을 내려주므로 **백엔드도 캐싱해야
한다** — 로그인마다 수천 행을 조회할 수는 없다.

**TTL 30~60분으로 만료시킨다.** 무효화 신호를 두지 않는다.

| | |
|---|---|
| 왜 TTL 로 충분한가 | 문구가 30분 낡은 것은 옛 문구가 보일 뿐이다. 권한처럼 오작동이 되지 않는다 |
| 다중 노드는 | 노드마다 만료 시점이 다르지만, 위 이유로 문제가 되지 않는다 |
| 즉시 확인이 필요하면 | 메시지 관리 화면이 저장 후 **자기 노드의 캐시를 비운다.** 고친 사람은 바로 본다 |

MASTER-02 의 *"수정 즉시 반영"* 은 **공통 코드에 대한 요구**이며, 코드는 백엔드 캐싱을
하지 않으므로 그 요구가 구조적으로 충족된다.

## 5. PII 정의 — 여기는 캐싱해야 한다

`SYS_PII_DEF`(마스킹 규칙)는 **응답 직렬화마다** 참조된다([23](../../standard/backend/_study/security-design.md) §4 체인 7번,
[27](../../standard/backend/pii-vault.md) §2). 매 요청이고, 변경은 극히 드물다 — 캐싱의 전형적인 대상이다.

애플리케이션 캐시(Caffeine)에 두고, 변경 시 그 노드가 비운다. 다중 노드에서는 다른
노드가 낡을 수 있으나 **마스킹 규칙 변경은 배포에 준하는 사건**이므로 재기동으로 반영한다 —
운영 중 실시간 변경을 요구하지 않는다.

## 6. 프론트 캐시의 유효성 — 로그인 시 버전을 비교한다

프론트 캐시는 **사용자마다 갱신 시점이 다르다.** 서버에서 코드가 바뀌어도 이미 로그인해
있는 사람과 새로 로그인한 사람이 다른 콤보를 볼 수 있다. 코드·설정·메시지는 변경이 드물어
이 어긋남이 실질적 문제가 되지 않는다.

**로그인할 때 버전을 비교해 필요한 것만 버린다.** 무조건 비우지 않는다.

```
SYS_CACHE_VERSION (CACHE_NAME PK, VERSION, MOD_DTM)
```

로그인 응답에 현재 버전들을 실어 보내고, 프론트는 `localStorage` 에 든 버전과 비교해
**달라진 것만** 폐기한다. 같으면 그대로 쓴다 — 로그인할 때마다 수천 건을 다시 받지 않는다.

**폴링이 아니다.** 이 표는 백엔드 노드끼리 주고받는 신호가 아니라, **프론트가 자기 캐시의
유효성을 판단하는 기준**이다. 읽는 시점은 로그인 한 번이다.

## 결과

| 구성 | 세션 | 백엔드 캐시 | 진행률 | 중복방어 |
|---|---|---|---|---|
| 단일 노드 | JDBC | 메시지 TTL · PII | caffeine | JDBC |
| **다중 노드 · Redis 없음** | **JDBC** | **같음 — 공유 불필요** | **JDBC** | **JDBC** |
| 다중 노드 · 고부하 | Redis | 같음 (Redis 로 교체 가능) | Redis | Redis |

- **Redis 는 다중화의 전제가 아니다.** 세션([ADR-0002](./0002-selectable-session-store.md))·중복방어([29](../../standard/backend/crosscutting.md) §5)·분산
  락([31](../../standard/backend/persistence.md))은 이미 DB 로 동작하고, 캐시는 **공유가 필요한 항목 자체가 없어졌다**
- 대표 서버 한 대에 Redis 를 얹는 절충은 다중화로 없애려던 단일 장애점을 되살리는데,
  이제 그 절충을 할 이유가 사라진다
- 진행률은 `jdbc` store 로 간다([30](../../standard/backend/crosscutting.md) §6.2) — 건별이 아니라 throttle 된 UPDATE 다

## 기각한 대안

| 안 | 문제 |
|---|---|
| **모든 캐시를 `SYS_CACHE_VERSION` 폴링으로 무효화** | 이 문서의 초안이었다. 대상별 요구가 다른데 한 장치로 묶으면 **가장 비싼 요구에 전부가 맞춰진다.** 게다가 폴링 주기만큼 권한이 낡아 **회수된 권한이 통과하는 구간**이 생긴다 |
| 다중 노드 + 로컬 캐시를 기동 시 거부 | 문제를 푸는 대신 금지한다 — 고객사는 여전히 Redis 를 사야 한다 |
| 유효 권한을 매 요청 DB 조회 | 가장 정확하지만 조인 4단계가 매 요청 돈다. [23](../../standard/backend/_study/security-design.md) §4 의 *"요청당 추가 쿼리 0"* 을 포기하게 된다 |
| DB `LISTEN`/`NOTIFY` | PostgreSQL 전용. 4벤더 무수정 기동이 깨진다([22](../../standard/backend/_study/db-portability.md)) |
| 캐시 자체를 DB 테이블로 | 매 조회가 DB 왕복이 되어 캐시를 두는 목적이 사라진다 |
