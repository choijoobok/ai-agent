# ADR-0014. 분산 락 — 만료 안전망과 쿨다운의 분리

- 상태: 채택
- 일자: 2026-08-23

## 맥락

다중화 서버에서 스케줄 배치가 모든 노드에서 동시에 깨어난다. DB PK INSERT 기반 분산 락으로
상호 배제를 걸어도, **작업이 수 밀리초 만에 끝나면 락이 무용지물**이 된다.

```
[노드 A] INSERT → 실행 → DELETE   (3ms)
[노드 B] INSERT 성공 ← 락이 이미 없다 → 또 실행
```

락은 정상 동작했다. B 가 시도한 시점에 락이 존재하지 않았을 뿐이다.
노드 간 시계 오차가 있으면 창은 더 벌어진다.

결과는 실행 이력에 같은 배치가 연달아 2~3건 남는 것이고, **유지보수 담당자가 결함으로
오인**한다. 그리고 실제로도 중복 실행이 맞다.

요구는 "한 번만 실행"이 아니라 **"정해진 기간 내에 한 번만 실행"** 이다.

## 결정

락 보유 시간을 결정하는 값을 **두 필드로 분리**한다.

| 필드 | 성격 | 기본값 |
|---|---|---|
| `expirySeconds` | **장애 안전망** — 프로세스 사망 등으로 해제 실패 시 회수 시한 | `300` |
| `minIntervalSeconds` | **업무 규칙** — 같은 키의 최소 재실행 간격(쿨다운) | `0` |

`minIntervalSeconds = 0` 이면 작업 종료 즉시 해제한다(기존 동작).
`> 0` 이면 종료 후에도 해당 시각까지 락을 유지한다.

선언 위치는 대상에 따라 갈린다.

| 대상 | 쿨다운 선언 | 근거 |
|---|---|---|
| 스케줄 배치 | `SYS_SCHEDULE_BATCH` **컬럼** | 락을 거는 주체가 스케줄러 래퍼다 |
| 일반 서비스 메서드 | `@CustomLock` | 비교할 주기가 없다 |

부수 결정 세 가지.

- `onConflict = WAIT` 와 `minIntervalSeconds > 0` 은 **상호 배타** — 기동 시점에 거부한다.
- 배치 등록 시·기동 시 **쿨다운과 크론 최소 간격의 정합성을 검증**한다 (SYS-19).
- **수동 실행(즉시 실행)은 쿨다운을 우회**한다. 상호 배제 락은 그대로 적용한다.
- **락 구간에 트랜잭션이 걸쳐 있지 않게 한다.** AOP 순서를 맞추는 것이 아니라
  트랜잭션이 락을 가로지르지 않게 하는 것이 해법이다 — 권장 패턴은 **전용 락 트리거 빈**.
  런타임 `isActualTransactionActive()` 검사로 위반을 즉시 실패시킨다.

### 비관적 락과의 역할 분담

`@CustomLock` 은 만능이 아니다. **기본은 비관적 락**이고, 외부 락은 그것이 닿지 않는 곳에 쓴다.

| 상황 | 수단 |
|---|---|
| 집계 상태 파생 계산 (잠글 부모 행 존재) | **비관적 락** — 해제가 곧 커밋 |
| 총량 제한, 잠글 행 없음 (팬텀) | `@CustomLock` |
| 트랜잭션 경계를 넘음 (비동기 분리) | `@CustomLock` — 비관적 락은 원리적 불가 |
| 스케줄 배치 | 스케줄러 래퍼 |

상세: [31-distributed-lock](../../standard/backend/persistence.md)

## 근거

### 왜 불린 옵션이 아닌가

"종료 시 자동 삭제" 같은 불린 하나로 이 동작을 켜는 설계가 가능하고, 실제로 흔하다.
그러나 그 값에 따라 **`expirySeconds` 의 의미 자체가 바뀐다.**

| 불린 | `expirySeconds` 의 뜻 |
|---|---|
| 자동삭제 ON | 장애 안전망 |
| 자동삭제 OFF | 최소 재실행 간격 |

성격이 다른 두 개념이 한 필드를 공유하므로, 기본값 300초를 둔 채 옵션만 끄면
**같은 키가 5분에 한 번만 실행된다.** 주석으로 경고해야 하는 설계는 설계가 잘못됐다는 신호다.

필드를 나누면 경고가 필요 없어지고, 기존 설계로는 표현할 수 없던
"안전망 5분 + 재실행 간격 5초" 조합이 자연스럽게 나온다.

### 선례

ShedLock 의 `lockAtLeastFor` 가 같은 문제를 같은 방식으로 푼다 — 짧은 작업과 노드 간
시계 오차로 인한 중복 실행을 최소 보유 시간으로 막는다. **알려진 패턴**이며 독자 발명이 아니다.

### 왜 배치는 컬럼이고 어노테이션이 아닌가

빈 이름으로 대상 빈을 찾아 `@CustomLock` 을 리플렉션으로 읽는 방법이 가능하다.
그러나 어노테이션이 `execute` 가 아니라 **안쪽 서비스 메서드에 붙어 있으면 찾지 못하고**,
검증기는 "쿨다운 없음" 과 "찾지 못함" 을 구분할 수 없다. 결과는 **조용한 통과** —
막으려던 사고가 그대로 난다.

게다가 화면에서 크론을 고치는 사람에게 그 값이 보이지 않는다.
소스를 열어야 아는 값 때문에 저장이 거부되는 셈이다.

스케줄 배치는 애초에 락을 거는 주체가 배치 구현체가 아니라 **스케줄러 래퍼**다.
래퍼가 등록 행을 읽어 선점하면 배치 구현체에는 어노테이션이 아예 필요 없고,
검증은 **같은 행의 두 값 비교**가 된다.

### 왜 수동 실행은 우회하는가

쿨다운은 여러 노드가 같은 크론에 동시에 깨어나는 상황을 막는 장치다.
사람이 누른 즉시 실행에는 그 상황이 없다. 막으면 "버튼이 안 먹는다" 는 문의가 오는데,
이는 쿨다운을 도입한 원래 이유와 **같은 종류의 혼란**이다.

상호 배제 락은 그대로 적용하므로 자동 실행이 진행 중이면 여전히 막힌다.

### 왜 순서가 아니라 구조로 푸는가

락 해제가 커밋보다 먼저면 틈이 생긴다. JPA 는 커밋 시점에 flush 하므로 노출 구간은
flush+commit 시간뿐이다 — 락이 무력화되는 것은 아니고 **넓은 경합이 좁은 경합으로** 줄어든다.
그러나 그 좁은 창에서 SELECT 한 번만 걸리면 뒤 트랜잭션의 작업 전체가 잘못된 전제 위에서 돌고,
증상은 락이 없을 때와 같으면서 빈도만 낮아 재현이 어렵다.

본질은 **락 해제와 영속성 결정이 원자적이어야 하는데 둘로 갈려 있다**는 것이다.
2PC 가 필요한 이유와 같은 구조다. 비관적 락에 이 문제가 없는 이유도 같다 — 해제가 곧 커밋이다.

AOP 순서로 풀려 하면 두 가지가 걸린다.

첫째, **`@Transactional` 의 위치(클래스 / 메서드)는 순서와 무관하다.** 순서는 어드바이저의
`order` 값으로만 결정된다. 그리고 트랜잭션 어드바이저와 `@Order` 없는 커스텀 애스펙트는
기본값이 **같아** 어드바이저 빈 등록 순서가 결과를 정한다 — 명세되지 않은 우연이다.

둘째, 순서를 맞춰놔도 **나중에 누가 클래스 레벨 `@Transactional` 을 추가하면 조용히 깨진다.**
클래스 레벨은 그 클래스의 모든 public 메서드에 적용되므로 락 메서드에는 아무 변화가 보이지 않는다.

그래서 순서를 맞추는 대신 **트랜잭션이 락을 가로지르지 않게** 한다. 락 메서드가 트랜잭션을
열지 않으면 안쪽 로직이 커밋한 뒤에 락이 풀리므로 순서가 저절로 맞고, 어드바이저 순서는
무관해진다. 전용 락 트리거 빈은 **self-invocation 으로 락이 통째로 건너뛰어지는 문제**까지 막는다.

정적 스캔은 보조 수단이다 — 호출자가 이미 트랜잭션을 열고 들어오는 경로는 정적으로 잡을 수 없다.
런타임 검사가 유일하게 빈틈이 없다. 스캔을 할 때도 어노테이션을 직접 뒤지지 말고 Spring 의
`TransactionAttributeSource` 를 재사용해야 클래스·상위클래스·메타 어노테이션(`@DefaultTx`)까지 걸린다.

### 왜 크론 정합성을 검증하는가

쿨다운이 크론 주기보다 길면 **실행이 조용히 누락된다.** 5초를 의도하고 300초를 넣는 실수가
정확히 이 형태로 나타나며, 아무 오류도 나지 않으므로 발견이 늦다.
원칙 P1(규칙이 아니라 메커니즘으로 강제)에 따라 등록 자체를 막는다.

## 대안

| 대안 | 기각 사유 |
|---|---|
| 불린 `autoDelete` 옵션 | 하나의 필드가 두 의미를 가진다. 기본값과 조합 시 사고 |
| 쿨다운 없이 락만 | **문제를 풀지 못한다.** 짧은 작업에서 상호 배제가 실패한다 |
| 리더 선출로 단일 노드만 스케줄링 | 코디네이터 의존성 추가. 리더 전환 중 공백. 배치 외 용도에 적용 불가 |
| 작업 시작 시 인위적 지연 | 락 보유를 늘리려 실행을 늦추는 것 — 원인이 아니라 증상을 건드린다 |
| 배치도 `@CustomLock` 으로 통일 + 리플렉션 검증 | 어노테이션 위치를 못 찾으면 조용히 통과한다. 화면에서 값이 안 보인다 |
| 수동 실행에도 쿨다운 적용 | 즉시 실행이 이유 없이 막힌다. 도입 목적과 무관한 상황이다 |
| AOP `@Order` 만으로 트랜잭션 경계 보장 | 클래스 레벨 `@Transactional` 이 나중에 추가되면 조용히 깨진다. 호출자 경유 경로도 못 막는다 |
| 중복 실행을 허용하고 이력만 병합 | 실제로 두 번 실행된다. 멱등하지 않은 배치에서 데이터가 깨진다 |
| 모든 상호 배제를 `@CustomLock` 으로 통일 | 비관적 락으로 되는 곳에서 안전성이 내려간다 — 누수·데드락 미감지·AOP 순서 부담 |
| MQ 로 직렬화 | 비동기가 되어 즉시 피드백을 잃는다. 백오피스는 경합이 낮고 즉시성의 가치가 크다 |

## 결과

### 감수하는 것

- **쿨다운은 실행을 누락시킬 수 있다.** 크론 기반은 [31](../../standard/backend/persistence.md) §7 검증이 막지만, 이벤트 기반 호출에는
  검증할 주기가 없어 값 선정이 전적으로 개발자 책임이다.
- 필드가 하나 늘어 **API 표면이 넓어진다.** 기본값 `0` 으로 두어 쓰지 않는 쪽이 기본이다.
- 저장소 장애 시 **fail-closed** — [ADR-0012](./0012-request-dedup.md) 의 dedup(fail-open)과
  반대 방향이다. 의도적이다. 상호 배제는 정확성이 목적이므로 판정 불가 시 실행하지 않는다.

### 반드시 지킬 것

| # | 항목 |
|---|---|
| 1 | 락 INSERT·DELETE 는 **업무 트랜잭션과 분리**(`NOT_SUPPORTED`). 롤백이 선점을 되돌리면 안 된다 |
| 2 | 만료 락 회수는 **조건부 DELETE 후 재INSERT**. 검사 후 삭제 금지 |
| 3 | 해제는 반드시 `finally` |
| 4 | 실행 이력에 **노드 식별자**를 남긴다 (BATCH-03) — 없으면 중복 원인 추적이 추측이 된다 |
| 5 | 만료 락 **정리 배치를 처음부터 포함**한다 |
| 6 | 배치 빈에 `@CustomLock` 이 붙으면 **이중 락** — 기동 시 스캔해 거부한다 |
| 7 | 크론 최소 간격은 **고정 기준시각**에서 계산한다. `now` 를 쓰면 저장 시마다 결과가 달라진다 |
| 8 | 락 구간에 트랜잭션 **금지**. 런타임 `isActualTransactionActive()` 로 거부 |
| 9 | 스캔은 `TransactionAttributeSource` 재사용. 어노테이션 직접 조회 금지 (클래스·상위·메타를 놓친다) |
| 10 | `@CustomLock` 메서드를 **self-invocation 하지 않는다** — 프록시를 지나지 않아 락이 걸리지 않는다 |
| 11 | `WAIT` 대기는 커넥션을 점유한다. **동시성 상한**과 함께 쓴다 |
