# ADR-0010. 감사 이력 미구현 + 요청 전문 로깅 채택

- 상태: 채택
- 일자: 2026-08-23

## 맥락

데이터 변경 이력(before/after) 을 남기는 감사 이력(audit trail) 을 템플릿에 포함할지,
포함한다면 Hibernate Envers 를 쓸지 직접 구현할지 검토했다.
동시에 사용 이력·에러 로그의 기록 방식도 정해야 했다.

## 결정

### 1) 감사 이력은 만들지 않는다

데이터 변경 before/after 추적 기능을 템플릿에서 **제외**한다. 필요한 프로젝트가 직접 구현한다.

### 2) 사용 이력·에러 로그는 요청 전문을 통째로 저장한다

`ContentCachingRequestWrapper` 기반 **request cache filter** 로 body 를 캐싱하고,
**쿼리스트링 + 헤더 + body** 를 직렬화해 한 컬럼에 저장한다.

| | `SYS_LO_ACCESS` | `SYS_LO_EXCEPTION` |
|---|---|---|
| 조건 | 2xx 응답만 | 예외 발생 시 |
| 차이 | — | **`ROOT_CAUSE_STACK` 추가** |

상세: [21-backend-architecture](../../standard/backend/_study/architecture.md) §6

## 근거

### 감사 이력 제외

- **데이터가 폭증한다.** 컬럼 단위 기록 시 배치 한 번에 수십만 행이 쌓이고,
  감사 이력은 성격상 함부로 지울 수도 없다.
- **요구가 프로젝트마다 다르다.** 대상 테이블·보존 기간·조회 화면 형태가 전부 다르다.
  범용 구현은 어느 쪽에도 맞지 않는다.
- **Envers 는 우리 구조와 충돌한다.** 엔티티마다 `xxx_AUD` 테이블이 생겨
  스키마와 Liquibase changelog 가 2배가 되고, **멀티 DB 검증 대상도 2배**가 된다.
- 설계 원칙 P2(삭제하기 쉬운 템플릿) — 안 쓰는 무거운 기능을
  넣는 것보다 필요한 팀이 추가하는 편이 낫다.

### 요청 전문 저장

- **구현이 단순하고 누락이 없다.** 어떤 필드를 기록할지 화면마다 정의할 필요가 없다.
- 사고 조사 시 **요청 그대로**를 볼 수 있어 재현이 쉽다.
- 사용 이력과 에러 로그가 **같은 직렬화 로직**을 공유한다.

## 대안

| 대안 | 기각 사유 |
|---|---|
| Hibernate Envers | 스키마·changelog·멀티 DB 검증 대상 2배. 통합 조회 화면 구성 곤란. QueryDSL/MyBatis 변경 미포착 |
| 단일 `SYS_AUDIT_LOG` 직접 구현 | 감사 이력 자체를 범위에서 뺐으므로 불필요 |
| 화면별로 기록 필드 정의 | 정의 누락이 조용히 발생. 유지보수 비용이 화면 수에 비례 |
| 응답 body 도 저장 | 목록 응답이 수 MB. 용량 대비 가치가 낮다 |

## 결과

### 감수하는 것

- **"이 값이 언제 누구에 의해 바뀌었나" 를 값 단위로 추적할 수 없다.**
  요청 전문에서 역추적은 가능하지만 조회 편의성은 떨어진다.
- 컴플라이언스 감사에서 변경 이력을 요구하면 프로젝트가 직접 구현해야 한다.

### 반드시 필요한 장치

| # | 장치 | 사유 |
|---|---|---|
| 1 | **마스킹** — 비밀번호·토큰·헤더 + **`SYS_PII_DEF` 등록 컬럼 자동 연동** | 전문 저장은 마스킹이 없으면 **로그가 최대 취약점**이 된다. 등록·수정 요청 body 에는 개인정보가 **평문**으로 들어온다 |
| 2 | `multipart/` 제외 | 파일 바이너리 버퍼링 시 OOM |
| 3 | body 캐시 상한 (1MB) | 대용량 요청 방어 |
| 4 | 텍스트 Content-Type 화이트리스트 | 바이너리는 `[binary: N bytes]` 로 표기 |
| 5 | `REQUIRES_NEW` + 실패 삼킴 | 로그 저장 실패가 원본 응답에 영향을 주면 안 된다 |
| 6 | **아카이브 배치 (LOG-07 을 M 으로 승격)** | 전문 저장이라 비대화가 빠르다 |
| 7 | `TRACE_ID` 컬럼 | P7 원칙 — 사용 이력·에러 로그·개인정보 접근 이력 상호 연결 |
| 8 | 로그 조회 화면 접근 권한 | 전문에 접근 가능하므로 일반 사용자에게 열면 안 된다 |

> **1번이 가장 중요하다.** [27-pii-vault](../../standard/backend/pii-vault.md) 로 원본을 분리 암호화해도,
> 요청 전문이 평문으로 로그에 남으면 그 노력이 무의미해진다.
> 개인정보 파기 요구 시 로그 테이블까지 뒤져야 하는 상황도 피해야 한다.
