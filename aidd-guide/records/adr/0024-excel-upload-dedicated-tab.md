# ADR-0024. 엑셀 업로드는 **전용 탭**이고, **저장 경로를 새로 만들지 않는다**

- 상태: 채택
- 일자: 2026-08-28
- 관련: [ADR-0019](./0019-excel-download-three-paths.md) · [ADR-0020](./0020-path-prefix-action-and-seed-generation.md) · [53-grid-standard](../../standard/frontend/_study/grid-standard.md) §1.1 · §3.1 · [56-grid-edit-validation](../../standard/frontend/_study/grid-edit-validation.md) §3 · [10-feature-inventory](../../knowledge/features.md) MASTER-07 · FILE-06 · SMPL-05

## 맥락

엑셀 업로드를 **기준정보 화면에 붙이기로** 했었다. [52](../../knowledge/sys/menu.md) §4.5 가 USER-06(사용자 일괄 등록)을
빼면서 *"엑셀 업로드 자체가 사라지는 것은 아니다 — MASTER-07 이 `CODE_MGMT`·`MESSAGE_MGMT`
에 남는다"* 고 적었고, [63](../../../documents/screen/code/requirements.md) §2.7 · §3.6 이 그 규약을 정했다.

**목업을 그려 보니 두 화면이 업로드에 맞지 않았다.**

| 화면 | 왜 |
|---|---|
| `CODE_MGMT` | **단계가 둘**이다(그룹 → 코드). 평면 엑셀 한 장으로 두 레벨을 담으려면 **그룹 속성이 행마다 반복**된다 |
| `MESSAGE_MGMT` | 마스터가 `list` 컬럼으로 접혀 있다([54](../../standard/frontend/_study/grid-column-contract.md) §5.6). [63](../../../documents/screen/code/requirements.md) §3.6 이 이미 *"화면의 `list` 모양으로는 쓸 수 없다"* 고 적었다 |

**그리고 규약 쪽에 더 무거운 것이 있었다.** 63 §2.7 · §3.6 이 API 를 둘 새로 만들었다 —
`saveExcelPreview` · `saveExcelImport`. 그러면 **같은 테이블에 저장 경로가 둘**이 되는데,
[53](../../standard/frontend/_study/grid-standard.md) §1.1 이 등록/수정 모달을 없앤 이유가 **정확히 그것**이다.

> **증상이 하나 더 있었다.** 접두가 `import*` 면 `EXECUTE` 로 떨어져([ADR-0020](./0020-path-prefix-action-and-seed-generation.md)) 화면 액션이
> `R S E` 인데 `X` 가 필요해진다. 63 §2.7 이 경로를 `saveExcelImport` 로 고쳐 맞췄다 —
> **맞는 답이지만, 없어도 될 문제에 답한 것**이었다.

## 결정

**다섯을 함께 정한다.**

### 1. 업로드는 화면 안 **탭**이다

업무 데이터 탭과 **엑셀 업로드 탭**을 나란히 둔다. 업로드 탭은 그리드 하나이며
[53](../../standard/frontend/_study/grid-standard.md) §2 의 크롬(제목 · ① · ② · ③)을 그대로 갖는다 — 새 어휘가 아니다.

```
[ 업무 데이터 ] [ 엑셀 업로드 ]          ← 화면 안 탭
──────────────────────────────
 파일 선택 → 그리드 적재 → 확인·수정 → 검증 → 저장
```

| 기각 | 이유 |
|---|---|
| **업로드 모달** | 파일을 올린 뒤 **고칠 자리가 없다.** 모달 안에 그리드를 또 넣으면 크롬이 두 겹이 된다 |
| **업무 그리드에 직접 붓기** | 손으로 편집 중인 행과 파일에서 온 행이 **섞이고** 되돌릴 방법이 없다 |
| **별도 메뉴** | 메뉴가 화면 수만큼 는다. 권한도 갈려 *"업무는 되는데 업로드가 안 된다"* 를 두 곳에서 봐야 한다 |

### 2. **저장 경로를 새로 만들지 않는다** — 업무 탭의 `save` 를 부른다

`saveExcelPreview` · `saveExcelImport` 를 **두지 않는다.** 업로드 탭의 저장 버튼은 업무 탭과
**같은 `api.save`** 를 선언한다. 다른 것은 **행이 어디서 왔는가**(파일 vs 손입력)뿐이다.

| 그러면 사라지는 것 | 왜 |
|---|---|
| **`import*` 접두 문제** | **업로드 API 가 없다.** [ADR-0020](./0020-path-prefix-action-and-seed-generation.md) §1 의 규칙은 그대로 남는다 |
| **전건 롤백 별도 규약** | 일괄 저장(UX-14)이 원래 **한 트랜잭션**이다 |
| **미리보기 API** | §4 가 그리드로 대신한다 |
| **`READ` 권한자가 업로드 창을 여는 문제** | 저장 액션이 하나뿐이라 [55](../../standard/frontend/_study/grid-api-contract.md) §3.6 이 이미 거른다 |

**[53](../../standard/frontend/_study/grid-standard.md) §1.1 을 위반하지 않는다** — 저장 경로가 여전히 **하나**다. [55](../../standard/frontend/_study/grid-api-contract.md) §8 이 파라미터
모달에 대해 쓴 판별과 같은 자리이며, 기준은 *"같은 테이블에 저장 API 가 둘이 되는가"* 다.

### 3. 파싱은 **프론트**가 한다 — 파일이 서버에 올라가지 않는다

`exceljs`([20](../../standard/stack.md) §2)는 쓰기만이 아니라 **읽기도 한다.** 업로드 탭이 파일을 읽어 행 배열로 바꾼다.

| | |
|---|---|
| 업로드 엔드포인트 | **없다** |
| 파일 저장 | **없다** — [47](../../knowledge/sys/notification.md) 의 파일 테이블과 비기능 요건 §3 의 업로드 검증이 이 경로에 **관여하지 않는다** |
| 서버 POI | **다운로드 전용으로 남는다**([ADR-0019](./0019-excel-download-three-paths.md) 의 셋째) |

**어차피 브라우저에 데이터가 있어야 한다.** 그리드에서 확인·수정하는 것이 이 패턴의
요점이므로, 서버에서 파싱하면 **왕복이 하나 늘고 그 응답이 결국 같은 배열**이다.
[ADR-0019](./0019-excel-download-three-paths.md) 가 *"이미 브라우저에 있는 데이터를 서버 POI 로 만들지 않는다"* 고 한 것의
**반대 방향이며 같은 논리**다.

### 4. 미리보기는 **그리드의 상태 컬럼**이다

[43](../../knowledge/sys/code.md) §9 가 2026-08-27 에 정한 *"덮어쓴다 + 미리보기(신규·변경·동일·오류) + 전건 롤백"* 은
**폐기되지 않는다.** 별도 화면 없이 **이미 있는 어휘**로 표현된다.

| 미리보기 분류 | 무엇으로 표현되나 |
|---|---|
| **신규** | `rowState: 'C'` — [53](../../standard/frontend/_study/grid-standard.md) §3.5 의 상태 컬럼 |
| **변경** | `rowState: 'U'` — ***덮어쓴다* 가 이것이다** |
| **동일** | **상태가 없다** → [53](../../standard/frontend/_study/grid-standard.md) §3.1 이 변경 행만 보내므로 **저장 대상에서 자동으로 빠진다** |
| **오류** | [56](../../standard/frontend/_study/grid-edit-validation.md) §3 의 검증 실패 표시. 저장 전 검증이 막으므로 *"오류가 있으면 반영이 잠긴다"* 가 그대로다 |

**그래서 상태를 붙이려면 기존 행을 알아야 한다.** 업로드 탭은 파일을 읽은 직후 **업무 탭과
같은 조회 API** 를 한 번 부르고 **키로 대조**한다. 이것이 이 패턴이 요구하는 유일한 추가
동작이며, **새 API 가 아니다.**

- **엑셀은 삭제 수단이 아니다** — DB 에만 있는 행은 업로드 탭에 **나타나지 않고**
  `rowState: 'D'` 도 생기지 않는다. **파일에서 줄을 지운 것과 *"지워라"* 를 구별할 방법이 없다**
- **오류 목록을 따로 내리지 않는다** — 그리드가 오류를 표시하고 ②의 엑셀 다운로드가
  그 그리드를 그대로 내린다([53](../../standard/frontend/_study/grid-standard.md) §2.2). 서버 POI 로 오류 파일을 만들 이유가 없어진다
- **미리보기의 *부가 집계* 도 컬럼이 된다.** 이전 판이 건수로 세던 것(예: 메시지의
  *`미사용` 신규*)은 **읽기 전용 파생 컬럼**이 그리드에 그대로 나오므로 **행마다** 보인다.
  건수보다 낫다 — *"3건"* 은 어느 행인지 말하지 않는다

### 5. **기준정보 화면에서 업로드를 뺀다** — 다운로드만 남는다

MASTER-07 은 **다운로드**만 남는다. 업로드의 실물은 **SMPL-05**(샘플 엑셀 업로드, M등급)이며
설계 개요 페이즈 8 의 *샘플 메뉴 5종* 에 이미 자리가 있다 — **원래 그쪽이 집이었다.**

**단일 그리드 화면이 이 패턴의 전제다.** 탭 하나에 그리드가 둘 필요해지는 화면
(마스터-디테일)에는 붙이지 않는다. 붙이려면 엑셀을 시트 둘로 나눠야 하고, 그러면
**파싱·검증·저장이 셋 다 갈린다.**

## 기각한 대안

| 기각 | 이유 |
|---|---|
| **63 을 고쳐 업로드를 남긴다** | 평면 엑셀 ↔ 2단계 · `list` 의 불일치가 남는다. 63 §3.6 이 스스로 자백한 그대로다 |
| **업로드 전용 API 를 유지한다** | 저장 경로가 둘이 된다. 충돌 규약 · 검증 · 롤백이 두 곳에서 갈리고 **한쪽만 고치는 일**이 생긴다 |
| **서버가 파싱한다** | 왕복 하나 + 파일 업로드 검증 체계(비기능 요건 §3) + **임시 파일 수명** 문제를 끌고 온다. 그리드가 데이터를 가져야 하므로 얻는 것이 없다 |
| **미리보기를 별도 화면·모달로** | `rowState` 와 검증이 **이미 같은 것을 말한다.** 둘을 두면 어긋나고, 어긋나면 어느 쪽이 맞는지 알 수 없다 |
| **엑셀로 삭제까지 한다** | 파일에서 지운 줄과 **애초에 안 넣은 줄**을 구별할 수 없다. 삭제는 업무 탭의 삭제 컬럼이다([53](../../standard/frontend/_study/grid-standard.md) §3.5) |
| **업로드 양식을 별도 파일로 배포** | ②의 **전체 다운로드가 곧 양식**이다([53](../../standard/frontend/_study/grid-standard.md) §2.2) — 컬럼이 화면과 같으므로 양식이 갈릴 수 없다 |

## 결과

- **[63](../../../documents/screen/code/requirements.md) §2.7 이 사라진다.** 그 절이 갚던 접두 문제는 **해소가 아니라 소멸**이다 — 업로드
  API 가 없다. 규칙은 [ADR-0020](./0020-path-prefix-action-and-seed-generation.md) §1 에 남고 [61](../../../documents/screen/user/requirements.md) §3.4 의 각주도
  *"이 화면에 없다"* 로 유지된다
- **[52](../../knowledge/sys/menu.md) §4.5 의 문장이 개정된다** — MASTER-07 이 두 기준정보 화면에 *남지* 않는다.
  USER-06 을 뺀 판단 자체는 유지된다
- **[43](../../knowledge/sys/code.md) §9 의 키 충돌 결정은 흡수된다** — 폐기가 아니라 `rowState` + [56](../../standard/frontend/_study/grid-edit-validation.md) 검증으로
  표현된다. **결정이 살아 있는 채로 별도 규약이 사라지는 것**이 이 ADR 의 값어치다
- **FILE-06 이 좁아진다** — *검증 결과 리포트* 가 별도 산출물이 아니라 **그리드**다.
  컴포넌트 하나(`<ExcelUploadTab>` — [24](../../standard/frontend/_study/frontend-stack.md) §7)로 닫힌다
- **[56](../../standard/frontend/_study/grid-edit-validation.md) §4 의 붙여넣기 미결이 답을 얻는다** — 일괄 입력 요구는 이 탭으로 받는다.
  Enterprise 의 Range Selection · Clipboard 를 살 이유가 없어진다
- **새 화면 형태가 하나 늘어난다** — [52](../../knowledge/sys/menu.md) §3.5 에 등재한다. **셸 탭바**([51](../../standard/frontend/_study/main-shell.md))
  바로 아래에 탭 줄이 둘이 되므로 **모양을 갈라야 한다** — 세그먼트 컨트롤로 두는 쪽을
  권하며 51 에서 정한다. **미결**이다
- ~~**프론트 파싱의 실질 상한이 미결이다**~~ → **`ui.excel.max-upload-rows` = 5,000**
  (2026-09-02 실측 — [48](../../playbook/INDEX.md) §8). 같은 자리에 두었으나 **같은 키는 아니다**: 이 절의
  초안은 `ui.excel.max-rows` 를 그대로 쓰자고 했는데, 재 보니 **비싼 쪽이 파싱이 아니었다**
  — 5만 행 파싱이 1.5초인 반면 저장은 **한 트랜잭션**이라 2만 행이 12.5초다. 내려받기는
  브라우저가 만드는 파일의 크기이고 올리기는 서버의 쓰기라, 한 값으로 두면 **멀쩡한
  내려받기를 깎거나 사용자를 30초 기다리게** 한다. 상한을 넘으면 **이 패턴이 아니라
  배치**라는 것은 그대로이며, 화면이 그 문장을 그대로 말한다 —
  *"10000건은 5000건을 넘습니다. 이 화면이 아니라 배치로 처리하세요."*
