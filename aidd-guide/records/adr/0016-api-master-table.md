# ADR-0016. API 마스터 테이블 분리 — 액션은 API 의 속성이다

- 상태: 채택
- 일자: 2026-08-26
- 관련: [23-security-design](../../standard/backend/_study/security-design.md) §4 · [42-data-model-authz](../../knowledge/sys/menu.md) §5

## 맥락

[23](../../standard/backend/_study/security-design.md) §4 는 인가 사실 전체를 데이터에 두기로 하고, API 하나를
인가하는 데 필요한 사실을 둘로 분해했다.

1. 이 API 가 어떤 **액션**인가 (`READ`·`SAVE`·`EXPORT`·`EXECUTE`)
2. 어느 **메뉴들**에 속하는가

그리고 둘을 `SYS_MENU_API` 한 테이블에 담았다 — `MENU_CD · HTTP_METHOD · API_URL · ACTION_CD`,
PK 는 앞 세 컬럼.

**PK 가 메뉴를 포함하므로 같은 API 가 메뉴마다 다른 액션을 갖는 행이 저장될 수 있다.**

```
(USER_MGMT, POST, /api/service/user/save, SAVE)
(ORDER_MGMT, POST, /api/service/user/save, READ)   ← 모순. 저장이 막히지 않는다
```

액션은 **API 의 성질**이지 (API, 메뉴) 조합의 성질이 아니다. 위 두 행이 공존하면 인가
판정이 **어느 행을 읽느냐에 따라 갈린다** — `SAVE` 권한만 가진 사용자와 `READ` 권한만 가진
사용자가 같은 저장 API 를 통과할 수 있다.

표준 SQL 제약으로는 막을 수 없다. 같은 `API_URL` 그룹 안에서 `ACTION_CD` 가 유일해야
한다는 규칙은 UNIQUE·CHECK 로 표현되지 않는다. [42](../../knowledge/sys/menu.md) §10 은 이것을
*"Phase 3 즉시"* 미결로 들고 있었고, 대응 후보 셋을 두고 있었다.

| 후보 | 내용 | 평가 |
|---|---|---|
| A | 관리 화면에서 기존 `ACTION_CD` 를 읽어 잠금 | 화면 밖 경로(시드, 직접 INSERT)를 막지 못한다 |
| B | 시드 검증 테스트로 CI 에서 유일성 검사 | 원칙 P1 에 부합하나 운영 중 입력은 못 막는다 |
| C | **테이블 분리** | 모순이 구조적으로 불가능. 단 23 의 "단일 원본" 형태를 바꾼다 |

당시 결론은 *"C 가 가장 깨끗하지만 확정 결정을 되돌리므로 B + A 를 권한다"* 였다.

여기에 요구 하나가 더 붙었다 — **매핑 작업자가 API 를 이름과 설명으로 찾을 수 있어야
한다.** 지금 구조에는 API 를 설명할 자리가 없다. URL 문자열만 보고 무슨 일을 하는 API 인지
판단해 메뉴에 매핑하는 것은 실수를 부른다.

## 결정

**`SYS_API` 마스터를 신설하고 `SYS_MENU_API` 를 순수 매핑으로 축소한다.** 후보 C 다.

| 테이블 | 컬럼 | 담는 사실 |
|---|---|---|
| **`SYS_API`** | `API_URL`(PK) · `API_NM` · `API_DESC` · `ACTION_CD` | **API 의 속성** |
| `SYS_MENU_API` | `MENU_CD`·`API_URL`(PK) | **정책** — 어느 메뉴가 쓰는가 |

`ACTION_CD` 가 URL 당 **한 번만** 존재하므로 모순이 저장될 수 없다. 표준 제약으로 표현할 수
없던 규칙이 PK 하나로 해결된다 — 검증을 사람의 리뷰에서 구조로 옮긴 것이며 원칙 P1 그대로다.

**`HTTP_METHOD` 는 제거한다.** 키는 `API_URL` 단독이다.

## `HTTP_METHOD` 를 버리는 근거

| 판단 | 근거 |
|---|---|
| 경로가 곧 오퍼레이션이다 | [23](../../standard/backend/_study/security-design.md) §4 가 경로 변수·와일드카드를 금지하고 조회도 POST + body 로 정했다. 그 규약 아래서 경로는 이미 `/user/list` · `/user/save` 처럼 **행위별로 갈려 있다** |
| 액션은 메서드에서 유추하지 않는다 | `ACTION_CD` 가 선언한다 — 23 이 이미 확정한 것이다 |
| 잘못된 메서드는 프레임워크가 막는다 | 핸들러가 없는 메서드는 Spring MVC 가 405 로 거부하며 인가 인터셉터에 닿지 않는다 |
| 검증하지 않는 컬럼은 표류한다 | 정보용으로만 남기면 컨트롤러와 어긋나도 아무도 모른다 — 코드에 액션 어노테이션을 얹지 않은 결정과 같은 논리 |

**규약이 깨지는 경로는 구조가 막는다.** 한 경로에 두 오퍼레이션(예: `POST` 와 `DELETE`)을
두려면 `SYS_API` 에 같은 `API_URL` 행을 또 넣어야 하고 **PK 충돌로 시드 배포가 실패한다.**
[23](../../standard/backend/_study/security-design.md) §4 에서 기각한 기동 시 핸들러 전수 스캔을 도입하지 않고도 fail-closed 가 유지된다.

## 23 의 "단일 원본" 은 깨지지 않는다

되돌리는 것으로 보였던 부분을 분명히 한다. 23 이 지키려 한 것은 *"인가 사실이 코드가 아니라
데이터에 있다"* 이며, **테이블이 하나라는 것이 아니었다.** 23 자신이 사실을 둘로 분해해 놓았고,
이 결정은 그 둘을 각자의 테이블에 두는 것이다. 코드에는 여전히 아무 선언도 없다.

바뀌는 문장은 하나다 — *"둘 다 `SYS_MENU_API` 매핑 행에만 둔다"*.

판정 비용도 같다. 기동 시 두 테이블을 합쳐 `URL → (ACTION_CD, [MENU_CD…])` 맵으로 적재하므로
런타임은 해시 조회 한 번이다([23](../../standard/backend/_study/security-design.md) §4 권한 캐싱).

## 결과

### 얻는 것

- **모순이 저장될 수 없다.** 시드 리뷰가 볼 항목이 하나 줄었다 — *"같은 URL 행들의 액션이
  같은가"* 를 사람이 확인할 필요가 없다
- **API 를 이름·설명으로 찾을 수 있다.** 매핑 작업자가 URL 문자열만 보고 판단하지 않는다
- **403 의 원인이 갈라진다.** `SYS_API` 미등록(API 자체가 없다)과 `SYS_MENU_API` 0건
  (등록됐으나 아무 메뉴도 쓰지 않는다)은 고치는 곳이 다르다. 이전에는 둘이 같은 상태였다
- FK(`SYS_MENU_API` → `SYS_API`)가 존재하지 않는 API 에 대한 매핑을 막는다. 그런 행은
  영원히 403 이 되면서 원인이 보이지 않는다

### 대가

- 테이블이 하나 늘고 조회가 둘로 나뉜다 — 기동 시 1회 적재이므로 런타임 비용은 없다
- **`SYS_API` 도 시드다.** 어떤 URL 이 존재하고 그것이 어떤 액션인지는 코드가 결정하는
  사실이므로 운영 화면의 편집 대상이 아니다. 관리 화면(AUTHZ-14)은 조회와 매핑 작성 보조를
  맡는 것을 권하며, 편집 허용 여부는 [42](../../knowledge/sys/menu.md) §10 미결이다
- 컨트롤러를 추가할 때 시드 행을 **두 개**(마스터 + 매핑) 넣어야 한다. 잊으면 403 이므로
  fail-closed 는 유지된다

### 두지 않는 것

**`SYS_API.USE_YN` 을 두지 않는다.** API 의 존재는 코드가 결정하는 사실이며 데이터로 끄는
대상이 아니다. 전면 차단이 필요하면 매핑을 지우거나 배포로 푼다 — 메뉴·역할의 `USE_YN`
(유효 권한의 필터·게이트)과 축이 다르다([23](../../standard/backend/_study/security-design.md) §4).
