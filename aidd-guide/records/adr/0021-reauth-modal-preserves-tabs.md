# ADR-0021. 만료는 로그아웃이 아니다 — 재인증 모달로 복구하고 탭을 유지한다

- 상태: 채택
- 일자: 2026-08-26
- 관련: 화면 흐름 §7.1 · §9 · [24-frontend-stack](../../standard/frontend/_study/frontend-stack.md) §9 · [23-security-design](../../standard/backend/_study/security-design.md) §4-1 · [ADR-0005](./0005-multi-tab-workspace.md)

## 맥락

화면 흐름 §9 는 로그아웃에 이르는 네 경로를 두고 *"넷 다 같은 정리 함수로 수렴한다"* 로
정했다. 그 넷에 **401** 이 들어 있었다 — 유휴 만료든 강제 로그아웃이든 401 을 받으면
`authStore` 를 비우고 탭을 초기화하고 로그인 화면으로 갔다.

**멀티탭 워크스페이스([ADR-0005](./0005-multi-tab-workspace.md))에서 이 처리의 비용이 크다.** 탭 상한이 20 이고
사용자는 실제로 여러 개를 열어 놓고 일한다. 회의·자리 이동으로 유휴 타임아웃이 지나면
열려 있던 탭 전부와 **입력 중이던 값**이 사라진다.

**자리를 잠깐 비운 것과 업무를 끝낸 것은 다르다.** 유휴 만료는 대개 전자인데 후자와
같게 처리하고 있었다.

## 결정

**401 을 받으면 먼저 재인증을 시도한다.** 로그아웃은 재인증이 불가능하거나 사용자가
포기했을 때만 한다.

| 항목 | 규칙 |
|---|---|
| 트리거 | **401 전부** — 유휴 만료 · 강제 로그아웃(AUTH-10) · 동시 접속으로 밀림 |
| 화면 | **탭과 입력값을 그대로 두고** 셸 위에 모달. **배경은 블러** |
| 입력 | **비밀번호만.** 로그인 ID 는 읽기 전용 |
| 성공 | **모달만 닫는다.** 새 `menus`·`permissions` 로 화면 흐름 §8.2 탭 정리를 한 번 돌린다 |
| 닫기(✕) | **두지 않는다.** 출구는 재인증 · 다른 계정 · (불가 시) 로그아웃 셋 |
| 401 을 받은 요청 | **자동 재시도하지 않는다** |
| API | **로그인 API 를 그대로 쓴다** — 전용 엔드포인트를 두지 않는다 |

### 로그인 ID 를 어디서 얻는가

**`authStore`(메모리)에 남아 있다.** 만료는 이제 로그아웃이 아니므로 `authStore` 를
비우지 않는다.

**`localStorage` 에 넣지 않는다.** 화면 흐름 §5.1 이 권한·메뉴를 메모리에 둔 이유가
*"로그아웃한 뒤에도 그 PC 에 이전 사용자의 정보가 남는다 — 공용 PC 에서 앞사람이 무슨
업무를 하는지 보인다"* 였다. 재인증 모달을 채우려고 ID 를 `localStorage` 로 옮기면
그 경계를 넘는다.

> **메모리에 두는 것은 괜찮다.** 로그인 ID 는 비밀이 아니다 — 사내 직원 식별자이며
> 이름·회사 메일을 평문으로 두기로 이미 정했다([41](../../knowledge/sys/user-role.md) §4.1). 헤더의 프로필에도
> 사용자가 표시된다([51](../../standard/frontend/_study/main-shell.md) §3). 메모리는 탭을 닫으면 사라지므로 §5.1 의 경계를
> 넘지 않는다.

### 새로고침(F5) 후에는 재인증 모달을 띄우지 않는다

`authStore` 가 메모리이므로 F5 하면 ID 를 잃는다. 그러면 모달을 채울 수 없다.

**그런데 그 경우 유지할 탭도 없다.** [24](../../standard/frontend/_study/frontend-stack.md) §4.1 이 *"새로고침 시 탭을 복원하지
않는다"* 로 이미 정했기 때문이다. 그래서 **F5 후 401 은 정식 로그인 화면**으로 간다.

| 상태 | 탭 | `authStore` | 처리 |
|---|---|---|---|
| 세션만 만료 | 살아 있다 | 살아 있다 | **재인증 모달** |
| F5 후 세션 만료 | 없다 | 없다 | **로그인 화면** |

**두 조건이 항상 함께 움직인다** — 탭 스토어와 `authStore` 가 같은 메모리 수명을 갖기
때문이다. 우연이 아니라 구조적이며, 그래서 판정에 별도 플래그가 필요 없다.

### 왜 비밀번호만 받는가

**ID 가 다르면 탭을 유지할 수 없다.** 열린 탭은 이전 사용자의 유효 권한으로 열린 화면이고,
새 사용자가 그 권한을 갖는다는 보장이 없다. ID 를 고정하면 이 모달의 의미가
*"같은 사람의 세션 복구"* 로 좁혀지고 **탭 유지가 정당해진다.**

다른 계정으로 들어가려면 모달의 *"다른 계정으로 로그인"* 을 쓴다 — 그것은 **정식
로그아웃 정리를 거친 뒤** 로그인 화면으로 가는 경로다(화면 흐름 §9).

> **개발도구로 다른 ID 를 보낼 수 있다.** 막지 않는다 — 그렇게 하는 사람은 **이미 그 PC
> 앞에 앉아 화면을 보고 있는** 사람이고, 얻는 것은 자기 계정 로그인뿐이다(권한 상승이
> 아니다). 화면의 이전 데이터는 조작 없이도 블러 뒤에 있다. **새로운 공격면이 아니다.**
>
> 다만 성공 응답의 `user.userId` 가 만료 전 값과 다르면 **전체 재로드**한다. 값싸고
> 실수를 잡는다.

### 왜 자동 재시도하지 않는가

401 을 받은 요청이 저장이었으면 재시도가 **중복 실행**이 된다. 중복 요청 방어(SYS-11)는
**기본 꺼짐**이므로([29](../../standard/backend/crosscutting.md) §7) 프레임워크가 받쳐 주지 않는다. 입력값이 그대로 남아
있어 사용자가 다시 누르는 비용이 작다 — 실패 방향이 안전한 쪽을 택한다.

## 보안 판단 — 무엇을 감수하는가

**만료된 화면이 블러 뒤에 남는다.** 화면 흐름 §5.1 이 경계한 *"공용 PC 의 잔존 노출"* 과
같은 축이다.

| 대상 | 블러로 | 비고 |
|---|---|---|
| 그리드 데이터 · 폼 입력값 · 사이더 | 가려진다 | |
| **탭 제목(메뉴명)** | **남는다** | *"무슨 업무를 하는지"* 는 보인다 |

**완전한 방어는 OS 잠금의 몫이며 백오피스가 대신할 수 없다.** 유휴 타임아웃의 목적은
세션을 끊는 것이지 화면을 가리는 것이 아니다 — 세션이 살아 있는 동안에도 화면은 그대로
보인다. 그 이상이 필요한 배포는 **유휴 타임아웃을 짧게** 잡는 것이 답이다.

**얻는 것과 감수하는 것을 나란히 두면** — 탭 20개와 입력값을 지키는 대가로 블러 뒤의
데이터가 남는다. 유휴 만료가 실제로 *"자리를 비운 것"* 인 빈도를 생각하면 교환이 맞다고
본다.

## 기각한 대안

| 기각 | 이유 |
|---|---|
| **401 = 곧바로 로그아웃** (기존) | 유휴 만료의 실제 성격과 어긋난다. 탭 20개를 다시 여는 비용을 사용자가 전부 진다 |
| 만료 시 탭만 유지하고 **로그인 화면 전체 전환** | 로그인 화면이 셸을 덮으면 탭 상태를 어디에 보관하는지가 생긴다. 모달이면 셸이 살아 있어 보관 문제가 없다 |
| 재인증 모달에 **ID 입력란도 두기** | 탭 유지의 정당성이 사라진다 — 다른 사용자가 이전 사용자의 화면을 이어받는다 |
| **자동 연장**(유휴에도 세션 유지) | 화면 흐름 §7 이 이미 기각했다. 자리를 비운 화면이 무한히 살아 있으면 유휴 타임아웃의 목적 자체가 사라진다 |
| 재인증 **전용 엔드포인트** 신설 | 로그인과 판정이 같다(접근 제어 체인 전체를 지나야 한다). 엔드포인트를 나누면 체인이 두 곳에 생긴다 |
| `localStorage` 에 ID 보관 | 화면 흐름 §5.1 의 경계를 넘는다. 그리고 F5 후에는 필요하지도 않다(위) |

## 결과

- **화면 흐름 §9 의 로그아웃 경로가 재정의된다** — 401 이 빠지고 *"재인증 포기"* 가 들어온다.
  넷이 같은 정리 함수로 수렴하는 원칙은 유지된다
- [24](../../standard/frontend/_study/frontend-stack.md) §9 axios 인터셉터의 401 처리가 **로그아웃에서 모달 표시로** 바뀐다
- **재인증 성공 후 화면 흐름 §8.2 탭 정리를 재사용한다** — 자리를 비운 사이 권한이 바뀌었을 수
  있다. 권한 변경 시 탭 정리 로직이 이미 있으므로 새로 만들 것이 없다
- `mustChangePassword=true` 가 재인증 응답에 오면(재인증 시점에 비밀번호가 만료) **비밀번호
  강제 변경 화면**으로 간다 — 그 화면은 셸 밖이므로 탭은 정리된다([60](../../../documents/screen/_standalone/README.md) §4)
- **여러 브라우저 탭에 각각 모달이 뜬다.** 한 곳에서 재인증하면 나머지가 닫혀야 하며,
  탭 간 통신 수단이 필요하다 — [51](../../standard/frontend/_study/main-shell.md) §12 미결
- 동시 접속 제어(AUTH-09)와 겹치면 **핑퐁이 가능하다** — 계정당 1세션·후승 우선이므로
  두 자리에서 번갈아 재인증하면 서로를 밀어낸다([23](../../standard/backend/_study/security-design.md) §4-1). 원래 설계의 성질이며
  재인증 모달이 새로 만드는 문제가 아니다
