# ADR-0012. request-id 기반 중복 요청 방어 (at-most-once)

- 상태: 채택
- 일자: 2026-08-23

## 맥락

프록시·로드밸런서가 타임아웃 시 재전송하면 **동일한 요청이 백엔드에 두 번 이상** 들어온다.
사용자는 한 번 클릭했고 브라우저도 한 번만 보냈는데 중복 저장이 발생한다.

프론트 버튼 가드로는 막을 수 없다 — 재전송은 브라우저를 거치지 않기 때문이다.
서버에서 "같은 요청인가" 를 판정할 수단이 필요하다.

## 결정

**클라이언트 발급 `request-id` 기반 at-most-once 방어**를 도입한다.
**기본 비활성**(`app.request-dedup.enabled: false`)이며 설정으로 켠다.

| 항목 | 결정 |
|---|---|
| 의미론 | **at-most-once** — 같은 id 는 최대 한 번 실행. 응답 재생 없음 |
| 키 채널 | **헤더 `X-Request-Id` + 쿼리 `_rid` 이중화** |
| 키 정체 | **추적 ID 와 통합** — 같은 값이 MDC·사용 이력·dedup 키로 쓰인다 |
| 중복 응답 | HTTP **200** + `{success:false, code:"err.duplicate-request"}` → 프론트가 **무음 처리** |
| 저장소 | `auto`(Redis→JDBC) / `redis` / `jdbc` / `local`(명시 시만) |
| 비활성 시 | `@ConditionalOnProperty` 로 빈 미등록 → 성능 영향 0 |

상세: [29-request-dedup](../../standard/backend/crosscutting.md)

## 근거

### 헤더 단일 채널이 실전에서 유실된다

nginx 의 언더스코어 헤더 폐기, 게이트웨이의 request-id 덮어쓰기, 헤더 화이트리스트 정책으로
헤더가 사라진다. **중간 레이어가 비교적 잘 보존하는 쿼리 파라미터에 같은 값을 이중으로** 싣는다.
두 채널 중 하나라도 저장소에 있으면 중복으로 판정한다.

### 추적 ID 와 통합하는 이유

서버가 생성하는 추적 ID 는 **재전송마다 값이 달라** 중복 판정에 쓸 수 없다.
클라이언트 발급 ID 를 서버가 이어받아 MDC 에 넣으면 **로그만 보고 진단이 된다.**

| 로그 | 해석 |
|---|---|
| 같은 requestId 2회 | 인프라 재전송 |
| 다른 requestId | 사용자의 실제 재요청 |

키를 두 개로 나누면(추적용·멱등용) 이 대조가 불가능하다.

### at-most-once + 무음 처리를 택한 이유

응답 재생(replay)은 응답 본문 저장·크기 상한·요청 해시 대조가 모두 필요하다.
목록 응답이 수 MB 인 백오피스에서 **복잡도 대비 이득이 낮다.**

중복에 에러 토스트를 띄우면 사용자가 "다른 작업자가 처리했나?" 로 오해한다.
전용 코드(`err.duplicate-request`)로 **레이스 컨디션 에러와 구분**해 무음 처리한다.

### 폴백이 `local` 이 아니라 `jdbc` 인 이유

멀티 인스턴스 + 비스티키 환경에서 로컬 캐시를 쓰면 다른 노드로 간 복제본을 못 잡아
**방어가 조용히 무력화**된다. 중복 방어는 정확성이 목적이므로 자동 폴백 대상이 아니다.
`local` 은 단일 인스턴스임을 **명시**했을 때만 선택된다.

## 대안

| 대안 | 기각 사유 |
|---|---|
| 프론트 버튼 가드만 | **다른 문제를 푼다.** 프록시 재전송은 브라우저를 거치지 않는다 |
| 헤더 단일 채널 | nginx·게이트웨이에서 유실된다 |
| 별도 멱등 키(`X-Idempotency-Key`)를 추적 ID 와 분리 | 로그에서 "인프라 재전송 vs 사용자 재요청" 대조가 불가능해진다 |
| 응답 재생(Stripe 류) | 응답 저장·크기 상한·요청 해시 대조 필요. 복잡도 대비 이득 낮음 |
| HTTP 409 반환 | 우리 API 는 모든 응답이 `ApiResponse<T>` 다. 200 + `success:false` 가 프론트 처리에 일관적 |
| 요청 본문 해시로 판정 | 정당한 동일 내용 재등록(같은 값 2건 입력)을 막아버린다 |
| 항상 활성화 | 요구상 기본 OFF. 비활성 시 빈 미등록으로 영향 0 |

## 결과

### 감수하는 것

- **더블클릭은 막지 못한다.** 키가 다르다. 프론트 재진입 가드가 담당한다.
- **두 채널을 모두 지우는 중간 레이어가 있으면 무력**하다. 도입 전 확인이 필요하다.
- **성공 피드백이 유실될 수 있다.** 프록시가 첫 연결을 버리고 재전송 응답만 중계하면
  브라우저는 중복 코드만 받는다 — 저장은 됐지만 그리드 갱신·토스트가 없다.
- 첫 시도가 실패해도 같은 id 재전송은 거부된다(정당한 재시도는 새 id 로 온다).

### 반드시 지킬 것

| # | 항목 |
|---|---|
| 1 | `tryAcquire` 는 **원자적 선점**(`SET NX` / `UNIQUE INSERT`). 검사 후 기록 금지 |
| 2 | JDBC INSERT 는 **`NOT_SUPPORTED` 전파**로 즉시 오토커밋. 비즈니스 트랜잭션에 묶이면 롤백 시 선점이 사라진다 |
| 3 | `SAFE_ID` 정규식(`^[A-Za-z0-9-]{8,64}$`) 검증. MDC 필터와 **공유**. 로그 인젝션·키 오염 방어 |
| 4 | `MDC.remove()` 를 `finally` 에서. 스레드풀 재사용으로 다음 요청 로그에 샌다 |
| 5 | **`crypto.randomUUID` 폴백 필수.** secure context 전용이라 사내망 HTTP 배포에서는 없다 |
| 6 | 프론트 응답 인터셉터에서 중복 코드를 **일반 실패 처리보다 먼저** 걸러 무음 처리 |
| 7 | **JDBC store 정리 배치를 처음부터 포함.** 무한 누적된다. 나중으로 미루면 잊힌다 |
| 8 | 저장소 장애 시 **fail-open** — 막지 않고 통과 |
| 9 | 헤더 값과 쿼리 값이 다르면 **WARN 로그** (중간 레이어 변조 신호) |
