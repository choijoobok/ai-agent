# 작업흐름 — 모듈별로 설계·구현·검증하는 법

## 1. 세 축은 서로 대신하지 않는다

| 축 | 답하는 질문 | 상태 자리 |
|---|---|---|
| 로드맵 차수 | 이번 출시에 무엇을 내는가 | `current.roadmap` · spec의 `roadmap:` |
| 작업흐름 | 어느 모듈·계약이 어디까지 성숙했는가 | `workstreams.<키>` |
| 슬라이스 | 지금 끝까지 만드는 기능 변경 하나는 무엇인가 | `slices[]` |

차수 하나가 P0~P6을 돈다는 기존 규칙은 유지한다. 다만 같은 차수 안에서 모듈의 속도가
다르면 `workstreams`가 그 차이를 갖는다. `current.phase`는 차수 전체의 통합 상태이지
모든 모듈이 같은 단계라는 주장이 아니다.

## 2. 작업흐름 키와 소유 범위

기본 키는 다음과 같다.

| 키 | 소유하는 것 |
|---|---|
| `admin` | admin 기능·화면과 그 내부 설계 |
| `agent` | agent 기능과 턴 실행·검색·정책 집행 내부 설계 |
| `portal` | 최종 사용자 portal 기능·화면과 표현 어댑터 |
| `integration` | `common` 기능, 모듈 간 API·이벤트·DB 계약, 계약 시험 |
| `extension:<이름>` | 고객사 업무 확장 하나와 Hub 접점 |

기능의 `module:`이 기본 작업흐름이다. 예외는 기능의 `workstream:`에 명시한다. 예를 들어
portal에 보이는 계약 시험 화면이라도 제품 UX가 아니라 계약 검증용이면 `integration`이
소유할 수 있다. **경로가 아니라 기능 ID의 소유권이 게이트를 정한다.**

업무 확장은 네 번째 Hub 모듈이 아니다. `extension:wms`처럼 별도 작업흐름으로 등록하지만
아키텍처 경계·DB 소유권은 프로젝트 spec이 정한다.

## 3. 전역 게이트와 작업흐름 게이트

P0/G0은 제품 목적·범위라 전역으로 한 번 정한다. G6은 통합 산출물·배포·인수라 전역이다.
P1~P5는 차수 전역 게이트와 작업흐름 게이트를 함께 가진다.

- **작업흐름 게이트**: 해당 모듈 또는 계약만 다음 단계로 보낸다.
- **전역 게이트**: 이번 차수에 내기로 한 모든 작업흐름의 결과가 함께 성립하는지 판정한다.
- 전역 G3는 출시 범위 전체의 통합 베이스라인이다. **소스 쓰기를 여는 직접 조건은 각
  기능을 소유한 작업흐름 G3 승인**이다.
- 전역 G3가 먼저 승인되는 상태는 허용하지 않는다. 출시 범위의 필수 작업흐름 G3가 모두
  승인돼야 전역 G3를 청구할 수 있다.

작업흐름 상태 형식은 다음과 같다.

```yaml
workstreams:
  admin:
    phase: P3
    blocked_by: []
    gates:
      P1_discovery: { status: approved, approved_at: "..." }
      P2_architecture: { status: approved, approved_at: "..." }
      P3_design: { status: approved, approved_at: "..." }
      P4_build: { status: in_progress, approved_at: null }
      P5_verify: { status: not_started, approved_at: null }
```

상태 값은 기존과 같은 `not_started | in_progress | self_verified | approved`다. 선행 작업흐름이
끝나기를 기다리는 것은 `blocked_by`가 아니라 `deferred_until`로 쓴다. **외부 사실이 없어
못 가는 것과, 의도적으로 나중에 하는 것을 구분하기 위해서다.**

작업흐름 G1은 소유 요구사항에 우선순위와 근거가 있는지를 판정하되 **Must 70% 상한을
작업흐름마다 강제하지 않는다.** 기반·보안처럼 작은 작업흐름은 전부 필수일 수 있어 비율을
맞추려고 거짓으로 낮추게 되기 때문이다. 상한은 현재 차수의 모든 작업흐름을 모은 **전역
G1에서 적용**한다. 작업흐름이 필수라고 판정한 것들도 전역 우선순위 조정에서는 다시 비교한다.

## 4. 작업흐름 G3가 잠그는 범위

작업흐름 G3는 다음만 동결한다.

1. 그 작업흐름이 소유한 현재 차수 기능과 그 기능에 연결된 UC·ENT·API·SCR·TC.
2. 그 작업흐름이 소유한 계약과 호환성 규칙.
3. G3 승인 요청에 명시한 공통 산출물 조각.

다른 작업흐름의 미완성 설계를 동결하지 않는다. 따라서 admin G3 이후 agent 설계를 계속할
수 있고, portal의 식별된 요구를 상세 설계 전 상태로 남길 수 있다.

소스 쓰기는 다음 순서로 판정한다.

1. 변경 파일의 `@feat FEAT-###`를 읽는다.
2. 기능의 `workstream:` 또는 `module:`로 소유 작업흐름을 찾는다.
3. 그 작업흐름의 `P3_design.status == approved`인지 확인한다.
4. 공통 기반처럼 기능 태그가 면제된 소스는 `integration` G3가 소유한다.

전역 G3 승인은 기존 프로젝트와의 호환을 위해 전체 소스를 열 수 있지만, 새 프로젝트는
작업흐름 상태를 먼저 둔다. 기능 태그가 필요하지만 소유권을 판정할 수 없으면 쓰기를 막는다.

## 5. 슬라이스는 기능별 한 바퀴다

슬라이스는 작업흐름 안에서 **설계 확인 → 테스트 우선 구현 → 통합 검증**을 끝내는 기능 변경
하나다. `slices[]`의 각 항목은 `workstream`, `features`, `stage`를 갖는다.

- 작업흐름 최초 G3 전: P3에서 슬라이스 후보와 테스트를 설계하고, G3 승인 뒤 구현한다.
- 작업흐름 G3 후 새 기능·변경: 변경 요청이 영향 범위를 정하고, 승인된 미니 설계를 붙인
  새 슬라이스로 구현한다.
- 한 슬라이스가 여러 작업흐름을 동시에 소유하지 않는다. 계약 변경이 필요하면
  `integration` 계약 슬라이스를 먼저 만들고 소비자 슬라이스가 그 버전을 따른다.

UI가 없는 agent 기능은 DB→API→UI를 억지로 채우지 않는다. 그 기능에 실제로 존재하는
층만 관통하되, 외부에서 관찰 가능한 계약과 테스트까지 닫아야 한다. 화면만 있는 어댑터도
같다. 세부 순서는 [슬라이스 규약](07-slice.md)이 갖는다.

## 6. portal의 두 시점

portal 요구는 다음 두 묶음으로 관리한다.

1. **계약 시험 시점**: 질의를 접수하고, 권한·보안·쿼터·감사를 거친 agent의 최종 계약
   응답을 가공 없이 확인한다. 제품 UX의 완료로 세지 않는다.
2. **제품 portal 시점**: 이력·개인화·그리드·차트·지도 등 사용자 편의를 상세 설계한다.

제품 portal 요구는 먼저 식별하고 `impact_screened`까지 진행할 수 있다. 이 상태에서는
agent 핵심에 미치는 영향과 필요한 계약 확장점만 정하고, 화면 배치·시각화 제품·세부 옵션은
portal 작업흐름 P3로 미룬다. **미룬 것은 요구가 아니라 상세 설계다.**

계약은 표현 라이브러리의 옵션을 직접 노출하지 않는다. agent는 의미와 데이터, 버전이 있는
표현 블록을 반환하고 portal 어댑터가 AG Grid·차트·지도 도구로 변환한다. 새 블록이 기존
소비자를 깨뜨리면 새 계약 버전과 병행 기간이 필요하다.

## 7. 되돌리기와 재작업 경계

| 변화 | 기본 처리 |
|---|---|
| 한 작업흐름 내부 설계·코드 | 그 작업흐름과 슬라이스만 되돌린다 |
| 모듈 간 계약의 호환 확장 | `integration` 계약 슬라이스 후 소비자별 슬라이스 |
| 계약의 호환 불가 변경 | 영향받는 작업흐름 G3 재개방 + 변경 요청 |
| 제품 목적·공통 보안 불변식 변경 | 전역 게이트 재개방 |
| 실험 전체 폐기 | 해당 작업흐름 상태와 슬라이스를 폐기하되 승인 이력은 남긴다 |

전체 설계를 뒤집는 것은 마지막 수단이다. 영향 분석이 계약 경계를 넘지 않으면 국소
재작업으로 끝내고, 공통 불변식이나 제품 목적이 바뀔 때만 전역으로 승격한다.

## 8. 브리핑과 게이트 보고

3줄 브리핑의 `지금 여기`에는 전역 단계와 **현재 작업흐름**을 함께 쓴다. 상태 보고는 최소한
다음을 보여 준다.

- 이번 차수와 전역 게이트.
- admin·agent·portal·integration의 단계, 막힘 또는 의도적 대기.
- 진행 중 슬라이스와 그 소유 작업흐름.
- 다음으로 청구할 작업흐름 게이트 또는 전역 게이트.

게이트 승인 요청은 “전역인지, 어느 작업흐름인지, 무엇만 동결되는지”를 첫 문단에 명시한다.
