# 워크스루 — 실제로 어떻게 굴러가는가

사용자가 한 문장을 던진 순간부터 인수까지, 대화가 어떤 모양인지 보여준다.
(💬 = 사용자, 🤖 = AI)

---

## 세션 1 — 착수

> 💬 **여러 시스템에 흩어진 데이터를 자연어로 조회하는 걸 만들고 싶어.**

🤖 `[PM]`
> 이해한 것: 업무 시스템 여럿에 흩어진 데이터를 사람이 화면을 돌아다니지 않고
> 자연어로 한 번에 얻으려는 것으로 보입니다.
>
> 이런 시스템은 보통 ①연동 기반(스키마 카탈로그·계정·권한) ②조회(계획·SQL 생성·검증·실행)
> ③가공(그리드·차트·다운로드) ④실행(승인 필요 액션) ⑤자동화(워크플로우)
> ⑥운영(감사·비용·품질) 으로 구성됩니다.
> **이 중 필요 없는 영역, 또는 빠진 영역**을 먼저 알려 주세요.
>
> ## [P0] 착수 — 질문 7개 (예상 5분)
> "기본값"이라고만 주셔도 됩니다.
>
> **Q1. [필수] 지금 이 일 때문에 누가 무엇 때문에 불편하신가요?**
> …
> **Q5. [필수] 이번에는 안 할 것을 정해 주세요.**
> - 배경: 범위를 안 자르면 아무것도 못 끝냅니다.
> - 전부 만들면 대략 A개월입니다. **절반 기간에 먼저 쓸 수 있게 한다면 무엇부터** 있어야 할까요?
> - 영향: 전체 일정과 이후 모든 산출물
> - 되돌리기 비용: 높음

> 💬 **한 건 확인하려고 시스템 셋을 열어서 엑셀로 붙여 맞춰. 건당 20분씩 걸려.
> 쓸 사람 120명, 붙일 시스템 3개. 연말까지. 기능 실행은 2차로 미뤄도 돼.**

🤖 `[PM]` `documents/spec/00-charter.yaml` `01-actors.yaml` `02-constraints.yaml` 작성
> 반영했습니다. 성공기준 SC-01(자연어 조회 성공률), SC-02(조회 1건 소요 시간 20분→2분).
> **범위 밖**: 기능 실행(2차), 워크플로우 자동화(3차), 모바일 앱.
>
> 남은 질문 2개: 운영 주체 / 사내 기술 표준 유무
>
> `/phase-gate G0` 로 넘어가겠습니다.

🤖 `[QA-레드팀]`
> **틀렸을 가능성 3가지**
> 1. 스키마 카탈로그를 관리 기능으로만 보셨는데, **이것 없이는 조회가 서지 않습니다.**
>    테이블 뜻을 모르면 AI 가 계획을 못 세웁니다. → **카탈로그 등록·검수는 1차 필수입니다.**
> 2. 붙일 시스템 3곳이 읽기 계정을 내줄지 불확실합니다. 안 내주면 결국 사람이 엑셀을 씁니다.
> 3. 조회 결과에 개인정보가 섞일 때의 처리 범위가 미정입니다.

> 💬 **아, 맞네. 카탈로그는 1차에 넣자. 시스템은 ERP 먼저 붙이고 나머지는 뒤에.**

🤖 헌장 갱신 → **G0 승인 요청** → 💬 **승인** → `phase: P1`

## 세션 2~3 — 발견

🤖 `[BA]` 용어사전 → To-Be 프로세스 → 요구사항 순으로.

프로세스를 그리면서 단계마다 예외를 캐묻는다:
> "카탈로그에 없는 테이블을 물으면요?" / "계획이 틀리면?" / "실행 중에 권한이 회수되면?"
> "두 사람이 같은 카탈로그를 동시에 고치면?" / "잘못 실행한 걸 되돌릴 수 있어야 하나요?"

REQ 47개 도출. 품질 검사에서 모순 하나 발견:
> ⚠️ **REQ-023** "모든 조회 이력을 영구 보존" ↔ **REQ-041** "개인정보는 3년 후 파기"
> 조회 결과에 담긴 개인정보가 이력에 남습니다. 어떻게 할까요?
> (A) 이력의 개인정보만 마스킹 후 보존 ← 권장 (B) 이력 전체 3년 (C) 개인정보를 이력에 안 남김

→ **G1 승인** → `phase: P2`

## 세션 4 — 아키텍처

🤖 `[AA]` 결정 순서대로 ADR 10건 작성. 대부분 AI가 제안하고 사용자는 승인만.

> **ADR-002 아키텍처 스타일 — 모듈러 모놀리식 (권장)**
> 대안: MSA / 모놀리식 / **모듈러 모놀리식**
> 근거: 운영 인력 2명. MSA는 운영 부담이 인력 대비 과도합니다.
> 포기한 것: 모듈별 독립 배포·독립 스케일링.
> 되돌리기: 모듈 경계를 지켜 두면 나중에 분리 가능. 비용 중간.

권한 모델에서 중요한 확인:
> **[필수] 현업 담당자가 다른 부서 데이터를 볼 수 있어야 하나요?**
> - 안 된다면 **모든 테이블에 `org_unit_id` 가 필요**합니다. ERD 전에 정해야 합니다.
> - 영향: 전 엔티티, 전 API, 전 조회 화면

→ **G2 승인** → `phase: P3`

## 세션 5~9 — 설계 (가장 김. 영역별로 쪼개 부분 승인)

순서 고정: UC → FEAT/메뉴 → ERD → API → 화면 → 시퀀스 → TC → 슬라이스 백로그

중간에 훅이 개입:
```
⚠️ 추적성 오류 3건이 남아 있습니다 (게이트 통과 불가):
  [T2] REQ-018: 미실현 요구사항 — UC/FEAT 연결 없음
  [T5] FEAT-044: 테스트 케이스 없음
  [UC] UC-009: 예외 흐름 없음
```

🤖 `[PM]`
> REQ-018(조회 결과 오류 신고 반영)이 어떤 기능으로도 실현되지 않았습니다.
> 놓친 것인지, 범위 밖인지 확인이 필요합니다.

**G3 승인 요청** — 레드팀이 4건 지적, 그중 2건은 사용자 결정으로 반영.
> 💬 **승인**

🤖 `documents/spec/` 베이스라인 동결. 슬라이스 24개 정렬 완료. 이후 변경은 CR.

## 세션 10~ — 구현

🤖 `/slice` — 첫 슬라이스는 **골격**(로그인→권한→화면→DB→로그→테스트→배포).
여기서 기술 리스크가 한 번에 드러난다.

이후 슬라이스마다:
```
① spec 재확인 → ② 설계 확인 → ③ TC를 테스트 코드로 (실패 확인)
→ ④ DB → ⑤ API → ⑥ UI → ⑦ 전체 통과 → ⑧ 미니게이트 → ⑨ 다음
```

> 💬 **스키마 카탈로그를 엑셀로 한 번에 올릴 수 있게 해줘.**

🤖 `[PM]` `/change-request`
> 베이스라인 이후 변경이라 CR로 처리합니다.
> **CR-003** 영향: FEAT +1, API +1, SCR 수정 1, TC +4 / 재작업: 슬라이스 1.5개
> (A) 지금 반영 ← 권장 (B) P5 이후 2차 (C) 안 함(수기 등록 유지)
>
> 참고: G3 대비 FEAT 62 → 71 (+14.5%). 15%에 근접했습니다.

## 사용자가 실제로 한 일

전체를 통틀어 사용자가 한 것은 **질문에 답하고, 게이트에서 승인/보류를 고르고,
CR에서 A/B/C를 선택한 것**이 전부다.
산출물 32종, 코드, 테스트, 문서는 전부 AI가 만들었다.

그리고 AI가 **혼자 결정하지 않은 것**들이 이 방법론의 값이다.
마스킹 적용 시점, 권한 범위 축, 개인정보 보존 정책, 카탈로그를 1차에 넣을지 —
이것들을 AI가 조용히 정했다면 시스템은 완성되었어도 쓸 수 없었을 것이다.
