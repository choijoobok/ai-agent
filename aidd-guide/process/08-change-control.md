# 변경 관리 — 베이스라인 이후의 유연함

## 1. 언제부터 CR인가

**해당 산출물의 소유 작업흐름 G3 승인 전까지는 CR이 없다.** 자유롭게 고친다.
작업흐름 G3 승인 순간 그 범위가 동결되고, 이후 그 범위의 spec 변경은 CR 절차를 탄다.
전역 G3만 있는 기존 프로젝트는 전역 G3를 같은 기준으로 쓴다.

이 경계가 중요한 이유: 동결이 너무 이르면 경직되고, 없으면 AI가 사용자 한마디에
설계를 통째로 바꿔 버려서 이미 만든 것과 어긋난다.

새 기능도 승인된 작업흐름에 들어가면 CR 대상이다. CR이 영향 범위와 미니 설계를 승인하고,
새 슬라이스가 설계 확인 → 테스트 우선 구현 → 검증을 돈다. 계약을 건드리면 `integration`
작업흐름을 먼저 영향 범위에 넣는다([13-workstreams.md](13-workstreams.md)).

## 2. CR 절차 (가볍게, 그러나 빠짐없이)

```
① 접수     사용자 요청 / 구현 중 발견 / 결함 원인분석에서 발생
② 분류     추가(Add) · 변경(Modify) · 삭제(Remove) · 오류정정(Fix)
③ 영향분석 추적성 체인을 타고 영향 산출물 전부 나열 + 재작업 규모
④ 판정     사용자에게 3가지 옵션 제시 → 사용자 선택
⑤ 반영     spec 수정 → 영향 문서 재생성 → 영향 슬라이스 재작업
⑥ 기록     documents/decisions/CHANGES.md 에 CR-### 확정
```

### ④ 판정 시 반드시 3옵션으로 제시

```markdown
## CR-003 — 스키마 카탈로그에 엑셀 일괄 업로드 추가 요청

**영향**: FEAT 신규 1개, ENT 변경 0, API 신규 1, SCR 변경 1, TC 신규 4
**재작업**: SLICE-007 부분 수정 + SLICE-025 신규
**규모**: 중 (슬라이스 1.5개 분량)

**옵션**
- (A) **지금 반영** — 현재 슬라이스 끝내고 바로. 다른 일정 영향 없음. ← 권장
- (B) **P5 이후 2차로** — 지금은 넘어가고 검증 후 별도로. 리스크: 화면 재설계 필요할 수 있음
- (C) **범위 밖 유지** — 수기 등록으로 운영. 현업 반발 예상

어느 쪽으로 갈까요?
```

**옵션 C(안 함)를 항상 포함한다.** AI는 요청을 거절할 줄 모르므로, 거절을 선택지로 만들어 준다.

## 4. 범위 증가 감지 (Scope Creep Guard)

`[PM]` 은 매 게이트에서 아래를 계산해 보고한다.

```
G3 대비 현재:  FEAT 62 → 71 (+9, +14.5%)
                누적 CR: Add 7 / Modify 3 / Remove 1
⚠️ 기능 수가 베이스라인 대비 15%에 근접했습니다.
   추가된 9개 중 Must가 아닌 것: FEAT-065, FEAT-068, FEAT-070
   범위 재조정을 검토하시겠습니까?
```

**AI는 사용자가 요청한 것을 자동으로 다 받아들이면 안 된다.** 누적 증가를 보여 주는 것이
AI가 할 수 있는 유일한 범위 통제다.

## 5. 되돌리기 불가능한 지점 이후의 변경

이미 배포되어 실데이터가 쌓인 뒤의 변경은 추가로 아래를 요구한다.
- 기존 데이터 마이그레이션 계획
- 하위 호환성 유지 여부 (API 버저닝)
- 롤백 시나리오
- 사용자 공지 필요 여부

이 4개가 없는 CR은 접수하지 않는다.
