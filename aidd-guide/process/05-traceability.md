# 추적성 — ID 체계와 연결 규칙

## 1. 왜 강제하는가

AI는 세션이 바뀌면 "이 코드가 왜 여기 있는지"를 모른다. 추적성 체인은 **AI의 외장 기억**이자
변경 영향 분석의 유일한 수단이다. 체인이 끊기면 AI는 안전하게 고칠 수도, 지울 수도 없다.

## 2. ID 체계

| Prefix | 대상 | 발번 단계 | 예 |
|---|---|---|---|
| `ACT-` | 액터(사용자 유형/외부 시스템) | P0 | ACT-003 업무 지식 관리자 |
| `CON-` | 제약사항 | P0 | CON-002 예산 상한 |
| `PRC-` | 업무 프로세스 / 단계 | P1 | PRC-01-02 SQL 검증·실행 |
| `REQ-` | 요구사항 (FR/NFR) | P1 | REQ-011 |
| `TRM-` | 용어 | P1 | TRM-004 스키마 카탈로그 |
| `ADR-` | 아키텍처 결정 | P2~ | ADR-004 인증방식 |
| `NFR-` | 비기능 목표치 | P2 | NFR-002 응답시간 |
| `UC-` | 유즈케이스 | P3 | UC-004 스키마 카탈로그 등록 |
| `FEAT-` | 기능 (메뉴 단위 실현체) | P3 | FEAT-012 |
| `ENT-` | 엔티티/테이블 | P3 | ENT-004 스키마 카탈로그 |
| `API-` | API 엔드포인트 | P3 | API-031 |
| `SCR-` | 화면 | P3 | SCR-008 |
| `IF-` | 외부 인터페이스 | P3 | IF-002 ERP 스키마 읽기 |
| `TC-` | 테스트 케이스 | P3~ | TC-0121 |
| `SLICE-` | 구현 슬라이스 | P4 | SLICE-007 |
| `DEF-` | 결함 | P4~ | DEF-013 |
| `ASM-` | 가정 | 상시 | ASM-007 |
| `CR-` | 변경 요청 | P3~ | CR-002 |

**발번 규칙**: 3자리 연번, 재사용 금지(삭제해도 번호를 비워 둔다), `documents/project.state.yaml` 의 `counters:` 로 관리.

## 3. 필수 연결 체인

```
                    ┌─────────────── ADR-### (근거)
                    │
ACT-###  ─┐         │
          ├──▶ REQ-### ──▶ UC-### ──▶ FEAT-### ──┬──▶ ENT-### ──▶ (DDL)
PRC-###  ─┘                                       ├──▶ API-### ──▶ (sources/)
                                                  ├──▶ SCR-### ──▶ (sources/)
                                                  └──▶ TC-###  ──▶ (tests/) ──▶ DEF-###
NFR-### ──────────────────────────────────────────────────────────▶ TC-###(비기능)
```

### 검사 규칙 (`/trace` 스킬 및 훅이 자동 검사)

| # | 규칙 | 위반 시 |
|---|---|---|
| T1 | 모든 `REQ` 는 최소 1개 `ACT` 와 연결 | 오류 |
| T2 | 모든 FR `REQ` 는 최소 1개 `UC` 또는 `FEAT` 로 실현 | 오류 (미실현 요구사항) |
| T3 | 모든 `UC` 는 최소 1개 `REQ` 로 역추적 | 오류 (근거 없는 유즈케이스) |
| T4 | 모든 `FEAT` 는 최소 1개 `UC` · `REQ` · **`NFR`** 로 역추적 | 오류 (고아 기능) |
| T5 | 모든 `FEAT` 는 최소 1개 `TC` 보유 | 오류 |
| T6 | 모든 `TC` 는 정상 1건 + 예외 1건 이상 짝을 이룸 | 경고 |
| T7 | 모든 `NFR` 은 측정 방법과 `TC` 보유 | 오류 (G2 이후) |
| T8 | 모든 `ENT` 는 최소 1개 `FEAT` 에서 사용됨 | 경고 (미사용 테이블) |
| T9 | 모든 `API`/`SCR` 은 `FEAT` 에 소속 | 오류 |
| T10 | `sources/` 파일은 헤더에 `@feat FEAT-###` 태그 보유 | 경고 |
| T11 | 참조된 ID가 실제로 존재함 (dangling reference) | 오류 |
| T12 | ID 중복 없음 | 오류 |

### T4 가 `NFR` 도 받는 이유

**비기능 목표만 실현하는 기능이 실재한다** — 모델 단가 관리 · 전사 예산 계획 · 토큰 집계 ·
스케줄러는 어느 기능 요구사항의 실현체도 아니고 **비용·안정성 목표의 실현체**다.
그것을 고아로 부르면 **없는 `REQ` 를 만들어 붙이게 되고**, 그 `REQ` 는 추적성을 위해서만
존재하는 거짓 항목이 된다 — **검사를 통과시키기 위해 spec 을 오염시키는 것**이다.

### T10 은 언제부터 적용되나

**이 프로젝트의 프로세스 아래에서 쓰인 코드에만 적용된다.** `sources/` 에 먼저 들어온
백오피스 템플릿은 이 추적성 체계보다 앞서 만들어졌고, **템플릿의 기능을 실현하는 코드에
Hub 의 `FEAT-###` 를 붙이는 것은 거짓 연결이다.**

그래서 그 817 파일을 [`.claude/hooks/feat-baseline.txt`](../../.claude/hooks/feat-baseline.txt)
에 **명단으로 고정하고 T10 은 명단 밖만 센다.** 건수로 집계하기만 하던 것을 2026-09-05 에
바꿨다 — **영구히 켜진 경고는 사람에게 경고를 무시하는 법을 가르치기** 때문이다. 실제로
재현 실험의 두 재현이 *"헌법은 요구하는데 실물에 0건이라 어느 쪽을 따를지 모르겠다"* 를
같은 말로 짚었다.

**명단은 줄어들기만 해야 한다.** 태그를 단 파일은 명단에서 지운다. 새 파일을 명단에
더하는 것은 **규칙을 끄는 것**이며, 그럴 이유가 있으면 커밋 메시지에 적는다.

## 4. 코드 태깅

소스 파일 상단에 기계가 읽을 수 있는 태그를 남긴다.

```java
/**
 * @feat FEAT-012 스키마 카탈로그 등록
 * @uc   UC-004
 * @api  API-031, API-032
 */
```
```typescript
// @feat FEAT-012  @scr SCR-008
```
```sql
-- @ent ENT-004 스키마 카탈로그
```

훅이 `sources/` 쓰기를 감지하면 이 태그를 확인하고, 없으면 경고한다.

## 5. 변경 영향 분석

spec의 어떤 ID가 바뀌면 AI는 **먼저 영향 목록을 보고**하고, 자동 수정하지 않는다.

```markdown
## ⚠️ 변경 영향 분석 — REQ-011 수정

REQ-011 (마스킹 적용 시점) 변경 시 영향:

**직접 영향 (반드시 수정)**
- UC-007 자연어 조회 실행 — 기본 흐름 4단계
- FEAT-021, FEAT-022, FEAT-023
- ENT-004 스키마 카탈로그 / ENT-009 조회 이력 — 컬럼 추가 필요
- API-045 POST /api/portal/query/execute
- TC-0451, TC-0452, TC-0455

**간접 영향 (검토 필요)**
- ADR-006 (마스킹 구현 위치) — 적용 지점 재검토
- SCR-014 조회 결과 화면 — 안내 문구
- 이미 구현된 SLICE-014 — 재작업 필요

**예상 재작업**: 슬라이스 3개 부분 재작업
진행할까요? 또는 CR-### 로 정식 등록할까요?
```
