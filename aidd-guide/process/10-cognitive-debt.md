# 인지 부채 — 사용자가 이해하지 못한 채 승인하는 문제

> **여기는 *승인을 어떻게 받나* 다.** *게이트가 언제 열리나* 는
> [process/04-gates.md](./04-gates.md) 가 갖는다 — 게이트 일곱과 Exit Criteria, 되돌리기.
> 아래 장치 넷은 저쪽 §3 의 승인 요청 봉투 안에서 쓰인다.

## 1. 무엇이 문제인가

Thoughtworks Technology Radar Vol.34(2026)가 이름 붙인 **cognitive debt**:

> AI가 인간이 이해할 수 있는 속도보다 빠르게 코드를 생산해서,
> 개발자와 자신이 만든 시스템 사이의 간극이 벌어진다.

이 방법론은 이 문제를 **악화시킬 구조적 위험**을 안고 있다. 산출물을 32종이나 만들고,
게이트마다 "승인/보류"를 묻기 때문이다. 사용자가 읽지 않고 승인을 누르는 순간
게이트는 **품질 장치가 아니라 책임 이전 장치**가 된다.

증상은 프로젝트 후반에 나타난다.
- "이거 제가 승인한 거예요? 이런 줄 몰랐는데요"
- 인수 후 운영을 못 해서 결국 AI에게 계속 물어봐야 함
- 결함이 나도 원인을 판단할 수 없어 AI 말을 믿는 수밖에 없음

## 2. 설계 원칙

| 원칙 | 이유 |
|---|---|
| **시험 보게 하지 않는다** | 사용자는 고객이지 학생이 아니다. 퀴즈는 모욕적이고 협조를 잃는다 |
| **AI의 불확실성으로 포장한다** | "확인 좀"이 아니라 "제가 이 부분 확신이 없습니다"로 묻는다 |
| **실패는 산출물 탓으로 돌린다** | 사용자가 답 못 하면 사용자가 아니라 **문서가 부족한 것**이다 |
| **읽으라고 하지 않는다** | "문서 보세요"는 금지. AI가 요약해서 제시한다 |
| **이해를 강제하지 않는다** | 사용자가 위임을 택할 권리가 있다. 단 기록은 남긴다 |

## 3. 장치 A — 결정 카드 (모든 게이트)

승인을 요청하기 **전에**, 이번 단계에서 **사용자가 실제로 결정한 것**만 뽑아 제시한다.
산출물 목록이 아니다. 사용자가 소유한 판단만이다. 3~5개, 업무 언어로 한 줄씩.

```markdown
### 이번 단계에서 확정되는 것 (읽어주셔야 할 5줄)

1. **마스킹은 결과를 화면에 보이는 시점에 겁니다** — SQL 은 원본을 읽습니다
   → 되돌리기: 어려움 (슬라이스 5개 재작업)
2. **현업 담당자는 자기 조직 데이터만 봅니다** — 다른 부서 데이터는 조회 불가
   → 되돌리기: 매우 어려움 (전 테이블 구조 영향)
3. **조회 이력의 개인정보는 3년 후 자동 파기됩니다** — 단 열람 사실 기록은 마스킹 후 5년 보존
   → 되돌리기: 보통
4. **엑셀 일괄 업로드는 이번 범위에 없습니다** — 건별 수기 등록만
   → 되돌리기: 쉬움 (2차 추가 가능)
5. **로그인은 사내 SSO를 씁니다** — 퇴사자 접근이 자동 차단됩니다
   → 되돌리기: 어려움
```

**규칙**
- 기술 용어를 쓰면 실패다. "SAML 연동" ✗ → "퇴사하면 자동으로 접근이 막힙니다" ✓
- 되돌리기 비용을 반드시 붙인다. 사용자가 어디에 집중할지 판단하는 근거다
- 5개를 넘기지 않는다. 넘으면 그 단계를 쪼개야 한다는 뜻이다

## 4. 장치 B — 역질문 (게이트마다 1~2개)

AI가 **자기 불확실성**을 근거로 묻는다. 도메인을 이해한 사람만 답할 수 있는 질문이어야 한다.
`/redteam` 결과에서 가장 불안한 항목을 가져오면 대개 좋은 역질문이 된다.

```markdown
### 제가 확신이 없는 부분 (2개만 답해주세요)

**Q1.** 마스킹을 "결과 표시" 시점으로 잡았습니다. 그런데 보안팀은 SQL 실행 전에
물건을 빼는 순간 이미 없는 것으로 치실 것 같기도 합니다.
**계획에 개인정보 컬럼이 섞였을 때, 실행을 막아야 하나요 마스킹해서 실행해야 하나요?**

**Q2.** 카탈로그에 없는 테이블을 묻는 일이 실제로 얼마나 자주 있나요?
드물면 예외 처리로 두고, 잦으면 정식 흐름으로 만들어야 합니다.
```

**좋은 역질문 / 나쁜 역질문**

| 나쁨 | 좋음 |
|---|---|
| "ERD 확인하셨나요?" (확인 요구) | "이 두 테이블을 나눈 게 맞을까요? 실무에서 같이 관리하신다면 합쳐야 합니다" |
| "REQ-011이 무슨 뜻인지 아시나요?" (시험) | "차이 사유를 필수로 했는데, 바쁠 때 형식적으로 아무거나 넣게 되지 않을까요?" |
| "설계에 동의하십니까?" (공허함) | "승인자가 휴가면 어떻게 되나요? 지금은 대기 상태로 멈추게 해뒀습니다" |

**답이 안 오면**: 그 자체가 신호다. `ASM-###`으로 등록하고 진행하되, 침묵 카운터를 올린다.

## 5. 장치 C — 침묵 승인 카운터

`documents/project.state.yaml`의 `cognitive_debt:`에 기록한다.

```yaml
cognitive_debt:
  silent_approvals: 0        # 질문·반박·역질문 답변 없이 통과시킨 게이트 연속 횟수
  last_walkthrough: null     # 마지막 시스템 설명 일자
  deferred_by_user: false    # 사용자가 "이해 확인 생략"을 명시적으로 택함
  unanswered_reverse_q: []   # 답 못 받은 역질문 ID
```

**판정과 대응**

| 연속 침묵 승인 | AI의 대응 |
|---|---|
| 1회 | 아무것도 안 한다 (바빴을 수 있다) |
| 2회 | 다음 게이트에서 결정 카드를 **3줄로 더 줄이고**, 역질문을 1개로 좁힌다 |
| 3회 이상 | **워크스루를 먼저 제안한다** (아래) |

```markdown
게이트 3개를 연속으로 바로 승인해 주셨습니다. 진행은 빠른데,
나중에 "이런 줄 몰랐다"가 나오면 그때는 되돌리기가 비쌉니다.

10줄로 지금까지 만든 시스템을 설명드리겠습니다. 3분이면 됩니다.
읽으시고 **가장 이상해 보이는 것 하나만** 짚어주세요.

(설명 10줄)

이상해 보이는 게 없으면 "없음"이라고만 주셔도 됩니다. 그대로 진행하겠습니다.
```

## 6. 장치 D — 운영 인수 시험 (P6, 생략 불가)

인수의 목적은 서명이 아니라 **AI 없이 운영 가능한 상태**다. G6에서 세 가지를 확인한다.

```markdown
### 인수 확인 — 아래 3개에 답하실 수 있으면 인수 준비가 된 것입니다

1. 내일 아침 사용자가 "로그인이 안 된다"고 하면, **어디를 먼저 보시겠습니까?**
2. 어제 데이터를 실수로 지웠습니다. **되살리는 절차가 어떻게 되나요?**
3. 신규 입사자에게 조회 권한을 주려면 **무엇을 하시나요?**
```

**중요: 답을 못 하시면 그것은 사용자의 문제가 아니라 런북과 매뉴얼의 결함이다.**
해당 문서를 보강하고 다시 묻는다. 이 문답을 통과하지 못하면 G6를 통과할 수 없다.

이 세 질문은 각각 `documents/generated/80-운영런북.md`의 장애 대응 · 백업/복구 · 정기 작업 절에 대응한다.
사용자가 문서를 보고 답을 찾을 수 있으면 통과다. **외우는 게 아니라 찾을 수 있으면 된다.**

## 7. 사용자가 위임을 택할 때

"난 잘 모르니 알아서 해줘"는 정당한 선택이다. 단 이렇게 처리한다.

1. 한 번만 리스크를 알린다 (2~3문장). 반복하지 않는다
2. `cognitive_debt.deferred_by_user: true` 로 기록
3. 결정 카드는 계속 만든다. 읽든 안 읽든 **기록은 남아야** 나중에 근거가 된다
4. **P6 운영 인수 시험은 면제되지 않는다** — 이건 이해의 문제가 아니라 시스템이
   운영 가능한지의 문제다. 사용자가 답 못 하면 문서를 고친다

## 8. 하지 말아야 할 것

- 사용자를 가르치려 들기, "이해하셨나요?" 반복
- 게이트를 인질로 잡기 ("답 안 하시면 진행 못 합니다") — 역질문 무응답은 ASM으로 처리하고 진행
- 결정 카드에 기술 용어 쓰기
- "자세한 내용은 `documents/generated/40-ERD.md`를 참고하세요" — **AI가 요약해야 한다**
- 침묵 카운터를 사용자에게 비난조로 언급하기 ("또 그냥 승인하셨네요")
