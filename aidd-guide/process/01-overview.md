# 방법론 총론 — 왜 이렇게 설계했는가

## 1. 문제 정의

기존 방법론은 세 가지 인간의 제약을 전제로 만들어졌다.

| 전제 | 전통 방법론의 대응 | AI 시대의 실제 |
|---|---|---|
| 문서 작성 비용이 크다 | 애자일: 문서를 줄인다 | **비용 ≈ 0. 문서를 줄일 이유가 없다** |
| 의사소통이 손실된다 | 대면 협업, 짧은 반복 | 여전히 손실된다. 오히려 **AI는 잘못 이해해도 자신 있게 진행**한다 |
| 재작업 비용이 크다 | 폭포수: 앞단을 두껍게 | 코드 재작업은 싸졌지만 **결정 재작업은 여전히 비싸다** |

그래서 AI-SDLC의 병목은 **개발 속도가 아니라 (a) 사용자의 의사결정 대역폭, (b) AI의 맥락 유실과 표류**다.
방법론은 이 둘을 방어하는 구조여야 한다.

## 2. 설계 원칙 7가지

### 원칙 1. 문서는 폭포수처럼 두껍게, 리듬은 애자일처럼 짧게
산출물 목록은 SI 폭포수 수준(요건정의서·유즈케이스·ERD·시퀀스·테스트결과서·매뉴얼)으로 유지한다.
AI에게 문서는 비용이 아니라 **자기 자신의 장기 기억**이기 때문이다.
단 만드는 리듬은 기능 단위 수직 슬라이스로 짧게 돈다.

### 원칙 2. SSOT — 명세는 데이터, 문서는 뷰
`documents/spec/*.yaml` 이 유일한 진실이다. `documents/generated/*.md` (요건정의서, 설계서 등)는 여기서 **생성**된다.
문서 간 불일치(가장 흔한 SI 실패 원인)를 구조적으로 제거한다. 사람이 documents/generated/를 고치면 훅이 경고한다.

### 원칙 3. 추적성은 선택이 아니라 강제
`REQ → UC → FEAT → (ENT|API|SCR) → TC → DEF` 체인이 끊기면 훅이 막는다.
"이 코드는 왜 존재하는가"에 항상 답할 수 있어야 AI가 나중에 지우거나 고칠 수 있다.

### 원칙 4. 결정은 원장에, 미확인은 가정 원장에
되돌리기 비용이 큰 선택은 `ADR-###`. 확인 못 한 전제는 `ASM-###`.
AI가 "일단 이렇게 가정하고 진행"하는 것을 **금지하는 대신 기록하게** 한다. 진행은 멈추지 않되 흔적은 남는다.

### 원칙 5. 질문 예산 — 사용자의 시간이 가장 비싼 자원
질문은 배치로, 권장안과 함께, 영향 범위를 붙여서. "기본값으로" 한 마디로 7개가 처리되어야 한다.
`[필수]` 표시는 되돌리기 비용 High인 것에만 쓴다. 남발하면 사용자가 게이트를 형식적으로 통과시킨다.

### 원칙 6. 게이트 — AI의 과속 방지턱
AI는 요구사항 정의 중에 코드를 쓰고 싶어 한다. 각 단계는 **Exit Criteria + 자기검증 + 레드팀 반박 + 사용자 승인**
네 단계를 거쳐야 닫힌다. 승인 없이 다음 단계 산출물을 만드는 것은 절대 규칙 위반이다.

### 원칙 7. 레드팀 자기반박
게이트 직전 AI는 `[QA-레드팀]` 모자로 자기 산출물을 공격한다.
"이 설계가 실패하는 시나리오 3개", "이 요구사항이 모순되는 지점", "빠진 예외 흐름".
AI의 최대 약점은 자기 산출물에 대한 무비판이므로, 이것을 절차로 강제한다.

### 원칙 8. 기계가 셀 수 있는 것은 기계가 센다
2026년 실증(GitClear 6.23억 건 분석)이 특정한 AI 코드의 확실한 열화 지표 —
**중복 +81%, 리팩터링 -74%, 재사용 -70%, 원인 미평가 에러 처리 +47%** — 는
사람 눈으로 보는 체크리스트로 안 잡힌다. `quality-check.mjs` 가 슬라이스마다 센다.
그리고 "테스트 통과"를 믿지 않는다. **규칙을 뒤집어 테스트가 실패하는지** 확인한다.

### 원칙 9. 사용자가 이해하지 못한 승인은 승인이 아니다
산출물이 많을수록 사용자는 읽지 않고 승인한다. 그러면 게이트는 품질 장치가 아니라
**책임 이전 장치**가 된다. 게이트마다 결정 카드(업무 언어 3~5줄)와 역질문으로
실제 이해를 확인한다. → `11-cognitive-debt.md`

### 원칙 10. 검증 비용을 숨기지 않는다
DORA가 관측한 **J-커브** — AI 도입은 가치를 내기 전에 생산성이 먼저 떨어진다.
원인은 학습 비용과 **verification tax**(AI 코드가 믿을 만한지 확인하는 추가 노력)다.
이 방법론은 그 하락을 없앨 수 없다. 대신 **P0에서 미리 알리고, 지금이 어느 구간인지
계속 보고하고, 압박이 왔을 때 무엇을 줄여도 되는지 미리 정해 둔다.**
바닥 구간에서 즉흥적으로 절차를 깎으면 반드시 지켜야 할 것부터 깎인다.
→ `12-verification-cost.md`

## 3. 참고한 방법론과 채택 지점

| 출처 | 가져온 것 | 버린 것 |
|---|---|---|
| **Waterfall / V-Model** | 단계 게이트, 산출물 목록, 요구사항↔테스트 대응(V자) | 되돌릴 수 없는 단방향 진행 |
| **RUP / Unified Process** | 아키텍처 우선(P2), 유즈케이스 중심 분석, 반복 | 무거운 4단계 9워크플로우 매트릭스 |
| **Agile / Scrum** | 수직 슬라이스, 백로그, 데모-피드백 루프 | 문서 경시, 고정 스프린트 길이(AI는 시간이 아니라 슬라이스로 센다) |
| **XP** | 테스트 우선, 지속 통합, 작은 릴리스 | 페어 프로그래밍(AI 자체가 페어) |
| **DDD** | 유비쿼터스 언어(용어사전), 도메인 모델, 바운디드 컨텍스트 | 전술 패턴 강제 |
| **ADR (Nygard)** | 의사결정 기록 포맷 | - |
| **C4 Model** | 아키텍처 4계층 문서화 | - |
| **Shape Up** | Appetite(투입 상한 먼저 고정), 범위 조절 가능한 슬라이스 | 6주 사이클 |
| **ISO/IEC 29148, IEEE 830** | 요구사항 기술 문법 (`~해야 한다`, 검증 가능성) | 문서 서식 강박 |
| **Spec-Driven Development** (Spec Kit, Kiro, BMAD, OpenSpec) | 명세=진실의 원천, constitution(불변 규칙), 역할별 에이전트 | 3단계(요구사항–설계–태스크)만으로 끝내는 얕은 흐름 |
| **DORA 2025/2026** | J-커브(초기 생산성 하락), verification tax, "AI는 증폭기" | 딥의 깊이·기간 수치 (DORA도 제시하지 않음) |
| **GitClear 2026** | 중복·재사용·에러삼킴을 기계로 측정 | — |
| **Thoughtworks Radar v34** | cognitive debt, feedforward/feedback control, 뮤테이션 테스트 | — |

## 4. 전체 흐름 한눈에

```
P0 착수 ──▶ P1 발견 ──▶ P2 아키텍처 ──▶ P3 설계 ══▶ P4 구현 ──▶ P5 검증 ──▶ P6 인도
   목적       요구사항      기술결정        상세설계   (슬라이스     통합/시나리오   배포/매뉴얼
   범위       프로세스      인프라          ERD/API     반복)         테스트결과서    인수
   성공기준    용어사전      NFR목표         화면/시퀀스
    │           │             │              │            │             │            │
    ▼           ▼             ▼              ▼            ▼             ▼            ▼
  [게이트]   [게이트]      [게이트]       [베이스라인]  [슬라이스별]   [게이트]     [게이트]
                                          ★여기서 동결   미니게이트

  ═══ 상시 진행 ═══
  documents/decisions/ADR·ASM 원장 │ 추적성 매트릭스 │ 변경관리(CR) │ documents/project.state.yaml
```

**P3 이후 spec은 베이스라인(동결)된다.** 이후 변경은 반드시 변경요청(CR) 절차를 탄다.
이것이 "견고함"의 핵심이고, CR 절차가 가벼운 것이 "유연함"의 핵심이다.

## 5. 규모에 따른 재단 (Tailoring)

모든 프로젝트에 전부 적용하지 않는다. P0에서 트랙을 먼저 정한다.

| 트랙 | 기준 | 생략 가능 산출물 |
|---|---|---|
| **Lite** | 화면 20개 미만, 단일 팀 사용, 외부 연동 없음 | 시퀀스 다이어그램(핵심 3개만), 상세 유즈케이스(요약형으로 대체) |
| **Standard** | 화면 20~100개, 부서 간 사용, 연동 2~5개 | - (기본) |
| **Full** | 화면 100개+, 대외 서비스, 감사/규제 대상 | 추가: 보안설계서, 성능시험계획, 데이터 이행 계획 |

트랙은 `documents/spec/00-charter.yaml` 의 `track:` 에 기록하고, 각 단계 가이드가 이 값을 참조한다.
