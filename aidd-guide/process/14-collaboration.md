# 공동 작업 — 단일 main 통합과 후속 검증

## 1. 기준

작업자는 같은 `main`을 쓸 수 있다. 사용자·PC를 식별해 절차를 나누지 않고, 최종 통합 결과를
푸시하는 사람이 최신 원격을 반영한다. 충돌이 없고 담당 범위 영향도 없으면 기존 상태와 검증을
그대로 유지한다. `pull` 자체는 상태 전이가 아니다.

Git 충돌과 기능 영향은 다르다. 충돌이 없어도 공통 API·DB·공통 소스가 바뀌어 기존 기능에
영향을 줄 수 있고, 충돌이 있어도 문장 순서처럼 의미가 그대로일 수 있다.

## 2. 통합 절차

1. 깨끗한 트리에서 `fetch`하고, 뒤처지기만 했으면 fast-forward한다.
2. 로컬과 원격이 갈렸으면 `merge --no-commit`으로 합친다. 자동 merge commit은 만들지 않는다.
3. 의미 선택이 필요하면 해당 내용을 작업한 팀원에게 오프라인으로 확인받는다.
4. 충돌을 해결하고 영향받은 FEAT·TC 또는 REQ·API·SCR를 적는다. 모르면 모듈 전체로 넓힌다.
5. 통합자가 검증하거나 `pending_rechecks`로 넘긴다.
6. 충돌 통합 커밋과 필요한 상태 커밋을 한 번의 push로 올린다. 푸시는 사용자 요청 때만 한다.

개인 브랜치를 쓴 작업자도 최종 `main` 후보를 위 순서로 검증한다. squash나 rebase로 충돌
기록을 없애지 않고, 최종 main 커밋에 아래 블록을 남긴다.

## 3. 기록과 현재 상태

충돌이 있었던 최종 커밋 본문에는 다음을 남긴다.

```text
[충돌 통합]
영향: FEAT-501, TC-5076
확인: 개발자 A 오프라인 확인
검증: 완료 | 후속 필요
```

과거 이력은 커밋이 갖고, 현재 열려 있는 일만 `project.state.yaml`의 `pending_rechecks`가 갖는다.
기존 슬라이스의 `done`이나 승인된 게이트를 단순 충돌 때문에 되돌리지 않는다.

```yaml
pending_rechecks:
  SLICE-510:
    kind: code_test
    introduced_by: abc1234
    affected: [FEAT-507, TC-5076]
    reason: "공통 오류 처리 충돌 통합"
```

문서는 `kind: document_review`로 기록한다. 승인된 spec의 의미가 바뀌면 이 상태로 대신하지
않고 CR을 먼저 밟는다. 생성물 충돌은 병합하지 않고 정본에서 다시 생성한다.

## 4. 넘긴 검증

후속 검증에는 개인 소유자를 고정하지 않는다. 팀원 누구나 실행할 수 있으며, 실행 명령·결과와
영향 범위를 상태 커밋 본문에 남기고 항목을 제거한다. 실패하면 항목을 유지하고 실패 근거를
갱신한다. 미해결 항목은 일반 개발을 막지 않지만 해당 범위의 완료 선언·게이트 승인·배포를 막는다.

브리핑은 미해결 항목 전부와 최근 `[충돌 통합]` 커밋 세 건을 보여 준다. 도입일 이전의 충돌과
검증 이력은 복원하지 않는다.

## 5. 실패 시 안전한 기본값

- 영향 범위를 모르면 테스트 케이스 → 기능 → 모듈 순으로 넓힌다.
- 같은 `pending_rechecks` 키가 이미 있으면 `affected`와 사유를 합치고 최초 `introduced_by`를 보존한다.
- 오프라인 확인을 아직 못 받았고 의미가 갈리면 정본을 추정해 푸시하지 않는다.
- 상태 파일 자체가 충돌하면 양쪽의 서로 다른 현재 항목을 보존하고 같은 키만 판단한다.
- main이 미검증 상태일 수 있다는 사실을 숨기지 않는다. `pending_rechecks`가 그 경고다.
