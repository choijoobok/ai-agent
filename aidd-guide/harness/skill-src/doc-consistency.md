# 문서 정합성·일관성 점검

`trace`는 ID 연결을, `redteam`은 실패 경로를 찾는다. 이 스킬은 **한 문서 안 또는 서로 다른 정본이 같은 사실을 다르게 말하는지**와, 사실의 정의 자리가 둘 이상인지 점검한다. 자동 훅으로 돌리지 않는다. 문맥과 업무 의미를 판단해야 하므로 사람이 시작하는 반복 점검이다.

## 범위와 기준

- 기본 범위는 `documents/spec/`, `documents/decisions/`, `documents/project.state.yaml` 및 연결된 화면 정본(`documents/screen/**/requirements.md`, `manual.md`)이다. 사용자가 범위를 좁히면 그 범위와 직접 참조 대상만 본다.
- 구현된 현재 사실은 소스가, 미구현 범위의 정본은 `documents/spec/`이 이긴다. `documents/generated/`와 `build/`는 파생물이므로 사실 판정 근거로 쓰지 않고, 어긋나면 재생성 대상으로만 보고한다.
- `project.state.yaml`은 현재 상태, ADR·결정 문서는 선택의 이유, spec은 제품 사실을 맡는다. 역할이 다른 문서에 같은 표현이 있어도 즉시 모순으로 세지 않는다.

## 점검 절차

1. 먼저 기계적으로 확인 가능한 결손을 분리한다.

   ```bash
   node aidd-guide/harness/runtime/harness-check.mjs
   node aidd-guide/meta/_meta/lint.mjs
   node .claude/hooks/trace-check.mjs --all
   ```

   ID 누락·깨진 링크·추적성 오류는 이 결과를 그대로 보고하며, 의미 모순으로 중복 집계하지 않는다.

2. 범위 안의 사실을 다음 축으로 비교한다. 먼저 각 문서 안에서 제목·본문·표·규칙·예외·수용 기준이 같은 사실을 다르게 말하지 않는지 읽고, 이어서 문서 사이를 비교한다. 모든 파일을 같은 깊이로 읽지 말고 ID·용어·참조를 검색해 후보를 좁힌다.

   | 축 | 대조하는 사실 |
   |---|---|
   | 범위·책임 | roadmap, workstream, In/Out, 액터·소유자 |
   | 업무 규칙 | REQ의 조건·예외·우선순위·수용 기준과 PRC/UC/FEAT의 흐름 |
   | 업무 흐름 연결 | 이전 단계의 산출물·상태·권한이 다음 단계의 입력·전제와 맞는지, 인계·대기·재시도·취소가 어디로 가는지 |
   | 계약 | 데이터 소유권·보존·권한, API 요청/응답·오류, 화면 액션·권한 |
   | 비기능·운영 | NFR 목표·측정·보안·감사·운영 책임 |
   | 결정·상태 | ADR/ASM/OQ의 결정 상태, 베이스라인·게이트·`pending_rechecks` |

3. 발견 항목을 아래 중 하나로 판정한다.

   - **모순**: 한 문서 안 또는 여러 문서에서 동일 사실의 값·주체·시점·범위가 둘 이상으로 양립할 수 없다. 일반 규칙과 예외 규칙이 실제 적용 조건 없이 서로 부정하는 경우도 포함한다.
   - **낡음**: 신뢰 순서가 높은 현재 사실과 하위 문서가 다르다.
   - **정의 중복**: 한 사실이 역할이 같은 문서 둘에 정의되어 이후 갈릴 위험이 있다.
   - **경계 불명확**: 서로 충돌하지는 않지만 책임·예외·우선순위가 비어 있어 둘 이상의 해석이 가능하다.
   - **흐름 단절**: 단계의 입력·산출물·상태 전이·담당 권한이 다음 단계와 이어지지 않거나, 예외 뒤의 경로가 없다.

   업무 흐름은 순서대로 읽는다. 정상 흐름뿐 아니라 승인 대기·거절·시간 초과·재시도·취소·부분 실패에서 누가 무엇을 결정하고 어느 단계로 돌아가는지 대조한다. 예를 들어 “승인 후 실행” 요구가 있는데 승인 결과를 보관하거나 실행에 전달하는 단계·API·권한이 없으면, ID 연결이 온전해도 흐름 단절로 보고한다.

4. 수정하지 않고 먼저 문제를 보고한다. 각 항목에 사실·근거 경로·영향 ID·판정·권장 처리를 붙인다. 문제가 없으면 “확인한 범위”와 “확인할 수 없었던 전제”를 함께 쓴다.

   ```markdown
   ## 문서 정합성 점검

   | 등급 | 사실 | 근거 | 영향 | 처리 |
   |---|---|---|---|---|
   | 모순 | API-…의 승인 주체가 둘로 정의됨 | spec/… · screen/… | REQ-… · TC-… | 정본 한 곳을 사용자와 확정 |
   | 흐름 단절 | 승인 결과가 실행 단계의 입력으로 전달되지 않음 | PRC-… · UC-… · API-… | REQ-… · FEAT-… | 상태·권한·예외 경로 확정 |
   ```

5. 처리 경로를 지킨다.

   - 구현된 소스와 문서가 다르면 소스를 현재 사실로 보고 문서 현행화 필요를 알린다.
   - G3 이후 승인된 spec의 의미가 바뀌면 `change-request`를 먼저 사용한다. 정합성 점검으로 조용히 덮지 않는다.
   - 확인할 수 없는 업무 사실은 `ASM-###` 또는 `OQ-###`로 남긴다.
   - 파생물 불일치는 정본을 고친 뒤 해당 생성기를 다시 실행한다.
   - 영향 범위를 확정해야 하면 `trace --impact ID`를, 산출물의 실패 가능성을 공격해야 하면 `redteam`을 이어서 사용한다.

## 사용 시점

- 여러 문서 묶음의 통합 직후 또는 외부 도구로 merge를 끝낸 뒤
- P1~P6 게이트 자체검증 전. 단계별로 요구·프로세스(P1), 경계·소유권(P2), 설계·예외(P3), 구현과 정본의 현행성(P4), 시험·NFR 근거(P5), 운영·인도 문서(P6)에 초점을 둔다.
- 문서 구조·용어·책임 경계를 크게 바꾼 뒤
- 사용자가 정한 정기 품질 점검 주기

이 점검은 문제를 **발견하고 분류**할 뿐, 게이트·상태·정본을 자동으로 바꾸지 않는다. 게이트에서 발견된 해당 범위의 모순은 해소 또는 명시적 결정 없이는 통과로 보고하지 않는다.
