# Sub-Agent Architecture 정책

> 메인 컨텍스트를 보호하기 위해 **탐색·계획·검토** 작업을 서브에이전트에 위임. AI 가 자기 컨텍스트를 직접 부풀리지 않게 한다.

## 위임 결정 트리

```
새 작업이 들어왔다 — 직접? 위임?
  ├─ 결과만 필요하고 과정 노이즈가 큼 (탐색·검색)
  │    → provider의 탐색용 서브에이전트
  ├─ 설계가 필요하고 다양한 대안 검토
  │    → provider의 계획용 서브에이전트
  ├─ 1~3 파일 단순 수정
  │    → 직접
  ├─ 사용자와 대화하며 점진 진행
  │    → 직접
  └─ 4파일 이상 또는 키워드 모를 때
       → 범용 서브에이전트
```

## 사용 가능한 서브에이전트

> 이름과 제공 여부는 Claude Code와 Codex 버전에 따라 다르다. 프로젝트는 특정 이름을 계약으로
> 삼지 않는다. 코드 검토의 최종 판정은 서브에이전트가 아니라 **게이트**(AGENTS.md §8·§7)가 맡는다.

| 역할 | 용도 | 트리거 |
|---|---|---|
| 탐색 | 코드 위치 탐색 | "어디에 있지", "X를 어떻게 사용하는지" |
| 계획 | 구현 전략 설계 | "어떻게 구현해야 할까" |
| 범용 | 복잡한 다단계 조사 | 모호한 검색·다중 도구 필요 |
| 제품 도움말 | AI runtime의 최신 동작 확인 | "hooks가 어떻게 동작하나" |

## 모델·effort 자율 위임과 승인 게이트

주 에이전트는 위임할 때 **어떤 서브에이전트를 쓸지**뿐 아니라 **어떤 모델·effort로 실행할지**도
스스로 판단한다(2026-09-14, AGENTS.md 위임 정책). 역할은 두 갈래다.

- **자율 사용** — 각 provider 전용 설정에 등록된 역할. 사용자 승인 없이 바로 위임한다. 다만
  위임 직전 목적·역할을 한 문장으로 알린다.
- **승인 전용** — 등록은 됐지만 자율 사용이 아닌 역할(예: 최상위 고비용 모델). 이번 호출에 대한
  사용자의 명시적 승인 없이는 쓰지 않는다. 등록되지 않은 새 모델도 같은 취급이다.

완료 뒤에는 주 에이전트가 결과를 직접 검토·통합해 보고한다(아래 "결과 검증"과 동일한 원칙).

provider별 구체적 역할 이름·모델명·effort는 여기 두지 않는다 — 위 "사용 가능한 서브에이전트"의
계약 원칙과 같다. 실물은 각 provider 전용 설정에 있다.

| provider | 전용 설정 |
|---|---|
| Claude Code | `.claude/agents/*.md` frontmatter(`model`·`effort`) — [providers/claude-code.md](./providers/claude-code.md) |
| Codex | `.codex/agents/*.toml`(`model`·`model_reasoning_effort`) + `.codex/config.toml`의 `[agents]` 기본값 |

## 위임 vs 직접 비용 분석

| 측면 | 직접 | 위임 |
|------|------|------|
| 메인 컨텍스트 점유 | 큼 | 결과 요약만 |
| 토큰 비용 | 단일 | 서브가 추가 |
| 응답 속도 | 빠름 | 지연 발생 |
| 정확도 (탐색 류) | 낮을 수 있음 | 격리된 컨텍스트로 향상 |
| 격리 (실패 시) | 메인 오염 | 서브에서 격리 |

> 사용량 추정치만으로 위임하지 않는다. 독립적으로 끝낼 수 있고 결과 요약만 필요할 때 위임한다.

## 위임 잘 하는 법 (프롬프트 작성)

1. **자기완결적 입력** — 서브는 본 대화 모름. 파일 경로·맥락·범위 명시.
2. **응답 형식 강제** — "200자 이내로 보고", "punch list 만" 같이.
3. **이해 위임 금지** — "분석한 결과로 알아서 수정해줘" 금지. 동작 명시 필수.
4. **병렬 호출** — 서로 쓰는 파일이 겹치지 않는 독립 작업만 동시에 실행.

## Claude Code와 Codex를 병행할 때

- 두 AI가 쓰기 작업을 병행하면 각각 별도 Git worktree와 branch를 쓴다.
- 같은 working tree의 index와 파일을 동시에 공유하지 않는다.
- 공통 명세 변경은 먼저 하나의 작은 커밋으로 합친 뒤 각 adapter 구현을 올린다.
- 최종 통합자는 diff와 gate를 직접 확인한다. 다른 AI의 완료 문장을 검증으로 쓰지 않는다.

## 결과 검증

서브에이전트는 **자기가 한 일을 요약**하지만, 실제로 한 게 그것이라는 보장은 없다. 코드 변경한 경우 직접 diff 확인.

## 안티 패턴

- "에이전트한테 다 시키고 결과만 받으면 됨" → 검증 없이 신뢰. 잘못된 결과 수용.
- 같은 검색을 메인 + 서브에서 중복 → 토큰 낭비.
- 단순 1파일 수정에 에이전트 호출 → 오버헤드만.
