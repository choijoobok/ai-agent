# 23. 보안 설계 (인증 · 인가 · 개인정보)

- 상태: 확정
- 최종수정일: 2026-08-28
- 관련 ADR: [0002](../../../records/adr/0002-selectable-session-store.md), [0009](../../../records/adr/0009-role-based-authz-without-org.md)
- **읽어야 할 때**: 인증·인가 흐름을 구현할 때 · 접근 제어 지점을 추가할 때

## 1. 인증 방식

**세션 기반 인증** (JWT 아님). 근거:
- 강제 로그아웃(AUTH-10), 동시 접속 제어(AUTH-09), 세션 만료 예고(AUTH-03)가 요구사항에 있고,
  이들은 stateless 토큰으로는 별도 블랙리스트 저장소가 있어야 한다. 결국 서버 상태가 생긴다.
- 백오피스는 브라우저 단일 클라이언트이며 CORS 없는 동일 오리진 배포([25](../../build-deploy.md))이므로
  세션 쿠키가 가장 단순하고 안전하다.

## 2. 세션 스토어 — 설정으로 선택

서버 다중화 대응을 위해 세션을 외부화하되, **Redis 필수 인프라를 강제하지 않는다.**

#### `store-type` 은 Spring Boot 4 에 없다 (2026-08-28 개정)

**이전 판은 `spring.session.store-type: jdbc` 였다.** 로그인 슬라이스에서 띄워 보니
**그 프로퍼티가 사라졌고, 적어도 아무 일이 일어나지 않았다** — 알 수 없는 프로퍼티는
오류가 아니다. 스토어는 **클래스패스에 있는 자동설정**이 정하며 둘 다 있으면 **Redis 가
이긴다.** `jdbc` 라고 적어 둔 채 Redis 로 붙었고, *"Unable to connect to Redis"* 가 나기
전까지 아무도 몰랐다.

**선택은 자동설정 제외로 표현한다.** 여전히 설정이며 코드 분기가 아니다.

```yaml
spring:
  autoconfigure:
    exclude:
      # jdbc (기본) : Redis 세션 자동설정을 뺀다
      # redis       : 아래를 JdbcSessionAutoConfiguration 으로 바꾼다
      # none        : 둘 다 뺀다 — 서블릿 컨테이너 세션으로 떨어진다
      - org.springframework.boot.session.data.redis.autoconfigure.SessionDataRedisAutoConfiguration
  session:
    timeout: 30m
    jdbc:
      table-name: SPRING_SESSION
      initialize-schema: never    # Liquibase 가 관리
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
```

| 선택 | 용도 | 주의 |
|---|---|---|
| `none` (둘 다 제외) | 단일 노드 로컬 개발 | 재기동 시 세션 소멸 |
| **jdbc** (Redis 제외) | **기본값.** Redis 없이 다중화 | 세션 조회 부하가 DB 로. 만료 세션 정리 배치 필요 |
| redis (JDBC 제외) | 트래픽 큰 환경 | Redis 가용성이 로그인 가용성이 됨 |

> **ADR-0002 의 결정은 그대로다** — 선택형이고, 두 구현체가 클래스패스에 있고, 코드에
> 분기가 없다. **바뀐 것은 선택을 표현하는 프로퍼티 이름뿐**이다.
>
> **다만 대가가 하나 는다.** 클래스 이름을 `yml` 에 적으므로 Spring Boot 가 그 클래스를
> 옮기면 제외가 조용히 무효가 된다 — 오타나 이름 변경은 오류가 아니라 *무시*다.
> 세션 스토어가 무엇인지 **기동 로그로 확인하는 것**을 배포 점검 항목에 둔다.

### 구현 시 유의점
1. **스타터를 쓴다** — `spring-boot-starter-session-jdbc` · `-session-data-redis`.
   라이브러리(`spring-session-jdbc`)만 넣으면 Boot 4 는 자동설정을 붙이지 않는다
   ([20](../../stack.md) §1.2.1). 둘 다 클래스패스에 두는 것은 그대로다.
2. Redis 미사용 환경에서 Redis 자동설정이 기동을 막지 않도록 확인한다
   (`store-type: jdbc` 인데 Redis 헬스체크가 fail 하면 안 됨 → `management.health.redis.enabled: false`).
3. `SPRING_SESSION` 테이블 DDL 은 Spring Session 제공 벤더별 스크립트를
   Liquibase `dbms=` 분기로 포함한다. 직접 작성하지 않는다.
4. **세션 직렬화**: 세션에 담는 principal 객체는 최소 필드만(사용자ID, 로그인ID)
   유지하고 `serialVersionUID` 를 고정한다. 무중단 배포 시 역직렬화 실패를 막기 위함이다.
   세션에는 이 밖에 **유효 권한 계산 결과**와 계정 상태를 둔다(§4 *"권한 캐싱"*) — 계산
   **입력**인 역할 목록·개인 예외·유효기간은 담지 않는다. **메뉴 트리는 세션에도 서버
   캐시에도 두지 않는다** — 로그인 후 프론트 메모리로 1회 내려간다([ADR-0017](../../../records/adr/0017-cache-strategy-per-target.md)).

### 캐시도 같은 방식
```yaml
app:
  cache:
    type: caffeine      # caffeine | redis
```
**Caffeine 은 노드별 로컬 캐시**이므로 다중화하면 한 노드의 수정이 다른 노드에 보이지
않는다. 그래서 원래는 *"다중화 = Redis"* 였다.

**[ADR-0017](../../../records/adr/0017-cache-strategy-per-target.md) 이 이것을 뒤집었다** — 캐시를 한 덩어리로 보지 않고 대상별로 나누면,
**노드 간 공유가 필요한 백엔드 캐시가 하나도 남지 않는다.**

| 대상 | 백엔드 | 근거 |
|---|---|---|
| 유효 권한 | **세션** | 매 요청 필요하지만 낡으면 보안 결함 — §4 권한 캐싱 |
| 공통 코드 · 메뉴 트리 | **캐싱 없음** | 서버 부하가 문제가 아니다. 프론트가 캐싱한다 |
| 시스템 설정 | **작업 스코프** | 한 덩어리 일 안에서 값이 바뀌면 안 된다 |
| 다국어 메시지 | **TTL 30~60분** | 건수가 많다. 낡아도 옛 문구가 보일 뿐이다 |
| PII 정의 | 애플리케이션 캐시 | 응답 직렬화마다 참조. 변경은 배포에 준한다 |

따라서 `type: redis` 는 **고부하 배포의 선택지**이지 다중화의 전제가 아니다(비기능 요건 §2.1).
사용처는 `@Cacheable` 만 본다.

## 3. 인증 흐름

```
[로그인]
POST /api/public/auth/login  {loginId, password}
  → 계정 조회 (활성/잠금/휴면 확인)
  → 비밀번호 검증 (BCrypt)
     실패 → 실패횟수 +1 → 임계치 초과 시 잠금 → 로그인 이력(실패) → 401
  → 성공 → 실패횟수 초기화 → 세션 생성 → 로그인 이력(성공)
  → 비밀번호 변경 필요 여부 판단 (최초 로그인 / 변경주기 경과)
  → 200 { user, mustChangePassword, menus, permissions }

[세션 확인]  GET /api/common/auth/getMe     — 새로고침 시 복원
[연장]      POST /api/common/auth/heartbeat — 만료 예고 모달에서 호출
[로그아웃]  POST /api/common/auth/logout   — 세션 무효화 + 이력
```

### 만료 처리
- 서버: 세션 타임아웃 30분(설정)
- 프론트: 만료 5분 전 모달 표시 → "연장" 시 heartbeat, 미응답 시 자동 로그아웃
- API 가 **401** 반환 시 axios 인터셉터가 전역 로그아웃 처리 → 로그인 화면

## 4. 인가 모델

**조직/부서 계층은 두지 않는다.** 권한은 역할 기반이며, 개인별 예외를 허용한다.
근거: [ADR-0009](../../../records/adr/0009-role-based-authz-without-org.md)

```
SYS_USER ──< SYS_USER_ROLE >── SYS_ROLE ──< SYS_ROLE_MENU_AUTH >── SYS_MENU ──< SYS_MENU_API >── SYS_API
    │                                              │                             (메뉴↔API 매핑, AUTHZ-11)
    └──────< SYS_USER_MENU_AUTH >───────────────────┘   ← 개인별 예외 권한
                                          (조회/저장/출력/실행)
```

- 권한의 단위는 **(주체 × 메뉴 × 액션)**. 주체는 역할 또는 사용자.
- 액션은 공통 코드로 관리: `READ`, `SAVE`, `EXPORT`, `EXECUTE`.
- **유효 권한 = 역할 권한 합집합 ∪ 개인 예외 권한**

### 역할이 여러 개면 합집합이다 — 선택하지 않는다

한 사용자가 역할 N 개를 가질 수 있으므로 *"로그인 후 어느 역할로 동작하는가"* 가 문제가
된다. **선택하지 않는다.** 가진 역할 전부의 권한을 합쳐 하나의 유효 권한으로 만든다.

```
유효 권한 = ⋃( USE_YN='Y' 인 보유 역할의 권한 ) ∪ ( 유효기간 내 개인 예외 권한 )
```

| 규칙 | 내용 |
|---|---|
| **합집합의 단위는 (메뉴, 액션)** | 메뉴 단위가 아니다. 역할 A=(주문,`READ`) · 역할 B=(주문,`SAVE`) 면 사용자는 주문 화면에서 조회·저장을 둘 다 갖는다 — **어느 역할에도 없던 조합이 만들어진다** |
| 중복은 사라진다 | 집합이므로 두 역할이 같은 (메뉴, 액션) 을 주는 것은 무해하다. 우선순위·순서가 개입할 여지가 없다 |
| **비활성 역할은 제외** | `SYS_ROLE.USE_YN='N'` — 아래 |
| 메뉴 트리도 같다 | 합집합을 먼저 구하고 그 리프 집합에서 조상을 **한 번** 역산한다(AUTHZ-04). 역할별로 트리를 만들어 병합하지 않는다 |
| **`USE_YN` 은 머지하지 않는다** | 셋 다 축이 다르고 필터·게이트로 쓰인다 — 아래 |

**프론트에는 평탄화된 (메뉴, 액션) 집합만 내린다.** 역할명은 표시용으로만 쓴다 —
`if (roles.includes('ADMIN'))` 식의 분기가 생기면 역할을 신설할 때마다 프론트를 고쳐야 하고,
인가 사실의 원본이 데이터 하나라는 규칙이 깨진다(아래 서버측 인가와 같은 논리).

#### 머지의 단위는 (메뉴, 액션) 쌍이다 — 컬럼별로 합치지 않는다

`MENU_CD` 집합과 `ACTION_CD` 집합을 **각각** 합치면 안 된다. 권한 **행**을 합친다.

| 역할 | 권한 행 |
|---|---|
| A | (주문관리, `READ`) |
| B | (사용자관리, `SAVE`) |

컬럼별로 합치면 메뉴 `{주문관리, 사용자관리}` × 액션 `{READ, SAVE}` 의 곱집합이 되어
**아무 역할도 주지 않은 (주문관리, `SAVE`) · (사용자관리, `READ`) 가 생긴다.** 권한 상승이다.

```
유효 권한 = { (MENU_CD, ACTION_CD) } 의 집합 합집합      ← 쌍이 원소다
          ≠ {MENU_CD} × {ACTION_CD}                     ← 곱집합. 금지
```

같은 (메뉴, 액션) 을 두 역할이 주는 것은 무해하다 — 집합이므로 원소 하나다. 그래서
판정은 `contains((menuCd, actionCd))` 한 번이고 **어느 역할에서 왔는지는 판정에 쓰이지
않는다.** 출처는 권한 화면의 표시용으로만 필요하다(위).

#### `USE_YN` 은 셋이고, 어느 것도 머지 대상이 아니다

머지되는 것은 권한 행뿐이다. `USE_YN` 은 **행을 낼 자격**과 **대상의 생존**을 정하는
필터이며 합집합에 들어가지 않는다. 같은 이름의 컬럼이 셋 있고 축이 전부 다르다.

| 컬럼 | 축 | 머지에서의 역할 |
|---|---|---|
| `SYS_USER.USE_YN` | 계정 | **무관** — 로그인 자체가 막힌다. 체인 #2([41](../../../knowledge/sys/user-role.md) §4.2) |
| `SYS_ROLE.USE_YN` | 권한의 **출처** | **입력 필터** — `'N'` 인 역할은 행을 내지 않는다 |
| `SYS_MENU.USE_YN` | 권한의 **대상** | **최종 게이트(AND)** — `'N'` 인 메뉴는 결과에서 제거된다 |

`SYS_ROLE_MENU_AUTH` · `SYS_USER_MENU_AUTH` 에는 `USE_YN` 이 **없다.** 행의 존재가 곧
허용이므로([42](../../../knowledge/sys/menu.md) §6) 부여 행을 끄는 수단을 두지 않는다 — 두면
`'N'` 이 "거부" 인지 "미부여" 인지 정해야 하고, 합집합 위에서 그 구분은 DENY 와 같은
우선순위 문제가 된다.

#### 역할 `USE_YN` — "하나라도 Y" 는 결과로 성립한다. 플래그를 OR 하는 것이 아니다

*"가진 역할 중 하나라도 `Y` 면 사용 가능"* 은 **결과적으로 맞다.** 역할 A 가 꺼져도 역할 B 가
살아 있으면 B 의 권한으로 계속 일한다. 다만 거기에 도달하는 방식이 다르고, 차이가 구멍을 만든다.

| 읽는 방식 | 동작 | 결과 |
|---|---|---|
| **플래그 OR** — "하나라도 Y 면 전부 유효" | A(`N`)+B(`Y`) 이므로 A 의 권한도 살아난다 | **역할 비활성화가 무의미해진다** |
| **행 필터**(채택) — 역할별로 자격을 따로 본다 | A 는 행을 내지 않고 B 만 낸다 | A 를 끈 효과가 정확히 나타난다 |

| 역할 | `USE_YN` | 권한 행 | 합집합 기여 |
|---|---|---|---|
| 관리자 | `N` | (사용자관리, `SAVE`) | **없음** |
| 일반 | `Y` | (주문조회, `READ`) | (주문조회, `READ`) |

플래그 OR 로 읽으면 이 사용자는 관리자 역할이 꺼졌는데도 `사용자관리` 를 저장할 수 있다.
`USE_YN` 은 **역할이 주는 권한 묶음 전체의 스위치**이지 사용자의 속성이 아니다.

#### 메뉴 `USE_YN` — 역할이 몇 개든 되살릴 수 없다

`SYS_MENU.USE_YN='N'` 은 *"이 화면을 아무도 쓰지 않는다"* 는 조직의 결정이므로 합집합
**결과에서** 제거한다. 역할 하나가 권한을 갖고 있다고 되살아나면 메뉴를 끄는 수단이
존재하지 않는 것과 같다. 여기만 OR 이 아니라 **AND** 다.

`MENU_URL IS NULL` 인 순수 구조 노드도 같은 자리에서 제거된다 — 권한 대상이 아니기 때문이다(위).

> **여기서도 공집합이 될 수 있다.** 메뉴 하나를 끄는 것이 어떤 사용자의 마지막 권한을
> 없앨 수 있고, 그러면 그 사용자는 다음 로그인부터 차단된다(아래). 역할을 끌 때와 같은
> 함정이므로 메뉴 관리 화면도 영향 인원을 보여줘야 한다(AUTHZ-01).

> **`DISP_YN` 은 두지 않는다.** 트리는 권한에서 파생되므로 별도의 표시 스위치를 얹으면
> 원본이 둘이 된다. 그리고 가능한 두 해석 어느 쪽도 성립하지 않는다.
>
> | 해석 | 문제 |
> |---|---|
> | 트리에서만 숨기고 권한은 유효 | 딥링크·즐겨찾기(UX-03)·커맨드 팔레트(UX-04)로 여전히 접근된다 — 관리자는 감췄다고 믿는데 실제로는 열려 있다. **조용한 실패**다 |
> | 권한까지 무효 | `USE_YN` 과 같은 일이다. 컬럼 둘이 한 일을 하면 어느 것을 봐야 하는지 알 수 없다 |
>
> 특정 사용자에게 감추려면 **권한을 주지 않는다**(개발 중인 화면이면 개발자 역할에만 준다).
> 아무도 쓰지 않으면 `USE_YN='N'` 이다. 폴더 체크 상태를 저장하지 않는 결정과 같은 논리다 —
> **파생값에 별도 저장을 두지 않는다.**

#### 계산 순서 — 필터 · 합집합 · 게이트

```
① 수집   보유 역할 N 개 + 개인 예외가 각각 (MENU_CD, ACTION_CD) 행을 낸다
② 필터   역할     : SYS_ROLE.USE_YN='Y' AND 부여가 유효기간 내         ← 출처 자격
         개인 예외 : 업무 시간대의 오늘이 유효기간 안인 행만
③ 합집합  살아남은 행을 (MENU_CD, ACTION_CD) 집합으로 합친다          ← 유일한 머지
④ 게이트  SYS_MENU.USE_YN='N' · MENU_URL IS NULL 인 메뉴를 제거       ← 대상 생존
         = 유효 권한.  ∅ 이면 로그인 차단(아래)
```

②와 ④를 나눠 두는 이유는 **방향이 반대**이기 때문이다 — ②는 *누가 주는가*, ④는 *대상이
살아 있는가* 다. 하나로 합치면 "역할을 켜면 되는 문제" 와 "메뉴를 켜야 하는 문제" 가
구분되지 않아 관리자가 무엇을 고쳐야 할지 알 수 없다.

**세션에는 ④ 의 결과만** 담는다(아래 권한 캐싱). 중간 산출물을 담으면 매 요청 게이트를
다시 계산해야 한다. 대신 재계산 트리거가 넷이다.

| 변경 | 무효화 범위 |
|---|---|
| 역할 부여(`SYS_USER_ROLE`) · 개인 예외 | 그 사용자 |
| 역할 권한 · 역할 `USE_YN` | 그 역할 **보유자 전원** — `SYS_USER_ROLE` 역방향 조회 |
| 메뉴 `USE_YN` · `MENU_URL` | **전체** — 메뉴는 전역이다 |
| **날짜 경과** (역할 부여·개인 예외의 기간) | 각 사용자가 **자정 이후 첫 요청에서** 스스로 — 아래 |

##### 기간이 있는 부여는 시간이 캐시를 낡게 만든다

②의 필터에 날짜가 들어가므로 **아무도 아무것도 바꾸지 않아도 캐시가 틀려진다** —
어제 만료된 부여가 캐시에 살아 있다. 데이터 변경만 트리거로 두면 이 경로가 새어 나간다.

판정 단위가 **날짜**(date, 양끝 포함)이므로 값이 바뀔 수 있는 순간은 **업무 시간대의 자정
한 번**뿐이다. 따라서 TTL 을 쓰지 않는다 — TTL 은 "언제 반영되나" 를 흐리고 날짜가 안
바뀌는 동안에도 재계산을 만든다.

**세션에 계산 날짜를 함께 담아 해결한다**(아래 권한 캐싱).

```
authzDirty == true  또는  authzCalcDate != 업무시간대_오늘  → 재계산
```

각 사용자가 **자정 이후 첫 요청에서** 스스로 재계산하므로, 자정에 활성 세션을 찾아
순회하는 작업이 필요 없다([ADR-0017](../../../records/adr/0017-cache-strategy-per-target.md)).

> **AUTHZ-08 의 범위가 좁아졌다.** 기존에는 *"개인 예외 권한 만료 처리 배치"* 였는데,

##### 이력 기록을 물린다 — 그 자리는 컬럼이다 (2026-08-31)

**이 문서가 배치에 얹었던 둘째 일을 되돌린다.** 적을 테이블을 만들어야 성립하는
요구였는데, 그 테이블을 만들지 않기로 한 결정이 **둘** 있다.

| 결정 | 무엇 |
|---|---|
| [ADR-0010](../../../records/adr/0010-request-logging-without-audit-trail.md) | **감사 이력을 만들지 않는다** — 데이터가 폭증하고 요구가 프로젝트마다 다르며 Envers 는 스키마·changelog·멀티DB 검증을 2배로 만든다 |
| [42](../../../knowledge/sys/menu.md) §3.1 | **`VALID_TO_DT` 가 그 이력이다** — 회수는 삭제가 아니라 이 컬럼이며, *누가 언제까지 무슨 역할을 가졌는지* 를 남기는 것이 이 컬럼의 용도다 |

**그래서 컬럼이 이미 답한다.** *"이 권한이 언제 자동으로 빠졌나"* 는 `VALID_TO_DT` 그
날짜이고, 만료된 부여는 **목록에서 지워지지 않는다**([61](../../../../documents/screen/user/requirements.md) §3.8 탭 1 이 기간으로 거르지
않는 이유가 그것이다 — *만료된 부여야말로 보여줘야 할 답*). 곧 만료될 것은 조회조건
(`역할 만료 예정 N일` · [61](../../../../documents/screen/user/requirements.md) §3.3)과 이 배치의 알림이 함께 답한다.

**컬럼이 답하지 못하는 것은 하나다 — 반복 부여의 앞 기간.** PK 가
`(USER_ID, ROLE_ID)` 라 **한 쌍에 행이 하나**이며, 3월에 줬다 빼고 6월에 다시 주면 같은
행을 덮는다. *"작년에 이 사람이 이 권한을 가진 적이 있나"* 에는 답할 데이터가 없다.

**그것을 템플릿이 메우지 않는다.** [ADR-0010](../../../records/adr/0010-request-logging-without-audit-trail.md) 이 감사 이력을 뺀 근거가 그대로
적용된다 — *보존 기간·조회 화면·대상 범위가 프로젝트마다 다르고*, 설계 원칙 P2 대로
**필요한 팀이 좁은 표를 더하는 편**이 안 쓰는 무거운 기능을 넣는 것보다 낫다.
그때 더할 것은 **범용 before/after 가 아니라** `(주체, 대상, 기간, 사유, 끝난 방식)` 한
표이며, 이 배치가 아니라 **부여·회수 저장 경로**가 그 행을 쓴다(자동 만료는 저장이
일어나지 않으므로 배치가 쓸 것이 없다 — 그것이 이 요구가 처음부터 배치의 일이 아니었던
이유다).

| 쓰이는 곳 | 어떻게 | 판정 주체 |

**트리에 들어가는 것은 `URL` 이 있는 메뉴 = 트리의 리프다.** URL 과 자식이 배타이므로(아래)

> **API 판정에는 "지금 보고 있는 메뉴" 가 쓰이지 않는다.** 프론트의 버튼 판정은 현재 화면의

> **하나라도** 유효 권한에 있으면 통과시킨다(OR). `X-Menu-Code` 는 이력용이다(아래 서버측 인가).

> 만 가졌다면 **A 화면의 저장 버튼은 숨겨지지만 그 API 호출 자체는 서버가 허용한다.** 의도된
> 결과다 — 사용자가 얻는 것은 화면이 아니라 **API 능력**이고 능력은 호출 경로와 무관하다.
> 화면마다 허용 범위가 달라야 한다면 그것은 공유 API 가 아니라 **분리해야 할 두 API** 다(아래).

### 역방향 조회 — "이 메뉴를 누가 쓸 수 있나" (AUTHZ-13)

위 파이프라인은 **사용자 → 권한** 방향이다. 관리 화면이 물어보는 것은 반대 방향이다.

| 화면 | 질문 | 원천 |
|---|---|---|
| 역할 관리(AUTHZ-02) | 이 역할을 가진 사용자는 누구인가 | `SYS_USER_ROLE` 단순 조회 |
| 메뉴 관리(AUTHZ-01) · 역할별 메뉴(AUTHZ-03) | **이 메뉴를 쓸 수 있는 사용자는 누구인가** | 파이프라인의 역산 |

두 번째는 단순 조회가 아니다. **역할 경유와 개인 예외를 모두 합치고 같은 필터를 적용해야
한다** — 하나라도 빠지면 화면이 거짓을 말한다.

```
메뉴 → 사용자 = ( SYS_ROLE_MENU_AUTH ⋈ SYS_ROLE(USE_YN='Y') ⋈ SYS_USER_ROLE )
              ∪ ( SYS_USER_MENU_AUTH 중 업무 시간대 오늘이 유효기간 내인 행 )
```

- **출처를 구분해 표시한다** — 역할 경유면 어느 역할인지, 개인 예외면 기간·사유. 출처가
  보이지 않으면 관리자가 무엇을 고쳐야 할지 알 수 없다(권한 화면의 역할 보유분 표시와 같은 요구)
- **계정 상태를 함께 보여준다** — `USE_YN` · 기간 · 잠금. 권한은 있으나 로그인할 수 없는
  사용자가 섞이며, 그것을 구분하지 못하면 "왜 이 사람이 목록에 있나" 를 설명할 수 없다
- **미리 계산해 둘 수 없다.** 세션에 담긴 유효 권한은 사용자 → 권한 방향이고, 이 조회는
  그 역방향이다. 실시간 쿼리이며 결과가 크면 페이징한다

이 조회 하나가 둘을 해결한다 — 감사 대응(*"이 화면을 누가 볼 수 있나"*)과 역할·메뉴를 끌 때의
**영향 인원 표시**(위)다.

#### 역할 전환 UI 를 두지 않는다

"현재 역할" 을 세션에 두고 사용자가 고르게 하는 방식을 기각한다.

| 이유 | 내용 |
|---|---|
| 판정이 문맥에 의존하게 된다 | 판정 원본이 (사용자) 에서 (사용자, 현재 역할) 로 바뀌고 세션에 담을 집합이 역할 수만큼 늘어난다. **어느 화면에서 호출했는지를 인가에 쓰지 않는다**는 결정과 같은 논리다 |
| 선택에 동기가 없다 | 사용자가 자기 권한을 스스로 낮출 이유가 없다. 항상 최대 권한을 고르므로 선택 UI 는 클릭 한 번을 추가하고 아무것도 바꾸지 않는다 |
| 최소 권한은 부여로 달성한다 | 필요한 것만 가진 역할을 주는 것이 답이다. 넓게 주고 사용자가 좁혀 쓰기를 기대하는 것은 통제가 아니다 |

> **~~AUTHZ-09 권한 시뮬레이션~~ 은 제외됐다(2026-08-26).** 역할 하나를 미리 보는 것으로는
> *"이 사용자가 왜 못 보나"* 에 답할 수 없다 — 사용자는 역할 N개 ∪ 개인 예외 ∪ 계정
> 상태의 합이기 때문이다([10](../../../knowledge/features.md) §C). 대체할 **사용자 기준 진단**은
> [52](../../../knowledge/sys/menu.md) §8 미결이다.
>
> 도입한다면 **역할 전환이 아니어야 한다** — 관리자 자신의 세션 권한을 바꾸지 않고,
> 그 중 발생하는 API 요청도 관리자 본인의 권한으로 인가되어야 한다. 그렇지 않으면
> 미리보기가 권한 상승 경로가 된다.

#### 부여 행은 남기고, 대신 영향 인원을 보여준다

**`SYS_USER_ROLE` 행은 지우지 않는다.** 역할을 다시 켜면 원래 부여가 그대로 살아나야 한다 —
계정 상태 플래그가 서로 덮지 않는 것과 같은 구조다([41](../../../knowledge/sys/user-role.md) §4.2).
그래서 비활성화가 바꾸는 것은 `SYS_ROLE.USE_YN` 한 컬럼뿐이다.

역할 하나를 끄는 것은 **그 역할을 가진 모든 사용자의 유효 권한을 바꾼다.** 캐시 무효화
범위는 위 표에 있고, 화면이 해야 할 일이 하나 더 있다.

관리 화면은 저장 전에 **영향 인원**과 그중 **유효 권한이 공집합이 되는 인원**을 보여준다.
후자는 다음 로그인부터 차단되므로(아래) 관리자가 모르고 지나가면 안 된다.

### 유효 권한이 공집합이면 로그인을 차단한다

**기준은 "역할 미부여" 가 아니라 "유효 권한 공집합" 이다.** 역할이 하나도 없어도 개인 예외
권한(AUTHZ-07)만으로 일하는 사용자가 정당하게 존재할 수 있다 — 개인 예외는 합집합의 독립
항이므로 역할 유무로 판정하면 그 사용자가 부당하게 막힌다.

| 왜 빈 메뉴로 들여보내지 않는가 | 내용 |
|---|---|
| 공격면이 0 이 아니다 | 로그인 성공은 세션 발급이다. 권한 0 인 세션도 `/api/common/**`(공통코드 조회·사용자 검색 팝업·`auth/me`)에 접근한다 |
| 원인을 알려주지 못한다 | *"로그인은 되는데 아무것도 없다"* 는 사용자가 스스로 해결할 수 없고 전량 문의로 이어진다. 차단하고 사유를 주는 편이 낫다 |
| 실패 방향이 맞다 | 권한 부여를 잊은 것이 **로그인 단계에서** 드러난다 — `deny by default` 와 같은 방향이다 |

- 구현 위치는 **AUTH-14 로그인 후처리 핸들러 체인**이다. `UserDetails` 4개 플래그에 대응이
  없다 — 휴면·허용 IP 와 같은 자리다([41](../../../knowledge/sys/user-role.md) §4.4)
- 판정 순서는 **휴면·IP 다음**이다. 권한 계산은 조인이 필요하므로 값싼 검사를 먼저 한다.
  이력에는 먼저 걸린 코드 하나만 남는다([45](../../../knowledge/sys/logs.md) §5.1)
- `auth.login.deny-empty-authority`(기본 `true`)로 끌 수 있다 — [43](../../../knowledge/sys/code.md) §6.3.
  끄면 UX-11 의 권한 없음 화면이 랜딩이 된다. 로그인 후 권한을 신청하는 흐름을 두는
  프로젝트를 위한 것이며 템플릿의 기본 동작은 차단이다

> **부트스트랩 함정 — 시드에 역할 부여 행이 없으면 아무도 들어올 수 없다.** 최초 관리자
> 계정에 `SYS_USER_ROLE` 이 없으면 유효 권한이 공집합이라 로그인이 차단되고, 관리 화면에
> 들어갈 수 없으므로 **복구 경로가 남지 않는다.** 시드 changelog 는 `SYS_USER` · `SYS_ROLE` ·
> `SYS_USER_ROLE` · `SYS_ROLE_MENU_AUTH` 를 **한 묶음으로** 넣고 그 정합성을 검증 테스트로
> 지킨다(원칙 P1) — 메뉴 URL 규칙을 시드 테스트로 지키는 것과 같은 방식이다.

> **직무 분리(SoD)는 이 모델로 표현할 수 없다.** 합집합이므로 기안자 역할과 승인자 역할을
> 함께 가지면 자기 기안을 자기가 승인한다. 역할 배타(mutually exclusive) 개념을 넣으면
> 우선순위 규칙과 *"왜 권한이 없나"* 추적 곤란이 따라오는데, 그것은 DENY 를 기각한 이유와
> 같다. **권한 모델이 아니라 업무 규칙으로 막는다** — 승인 화면에서 기안자=본인 행을 제외하는
> 식이다. 부여 화면의 배타 조합 경고는 프로젝트 몫으로 둔다([42](../../../knowledge/sys/menu.md) §10).

### 액션은 4종에서 닫는다

| 액션 | 의미 | 화면의 예 |
|---|---|---|
| `READ` | 조회 | 화면 진입, 목록·상세 조회 |
| `SAVE` | 저장 — **추가·수정·삭제 포함** | 저장 버튼, 모달 등록/수정, 행 삭제, 셀 편집 |
| `EXPORT` | 출력 | 엑셀 다운로드 |
| `EXECUTE` | 절차 발동 | 배치 수동 실행, 승인/반려, 발송, 마감·재계산, 강제 로그아웃 |

**등록/수정/삭제로 쪼개지 않는 이유** — 그리드 저장 표준이 리스트 CUD 일괄 처리(UX-14)다.
행별 추가/수정/삭제 구분은 URL 이 아니라 **페이로드(행 상태 필드) 안에** 있으므로, 일괄
저장 API 하나를 셋으로 쪼개 판정하려면 서비스 코드가 페이로드를 열어 행 상태별로 권한을
검사해야 한다 — 판정을 인터셉터 한 곳에 두는 원칙이 깨진다. 서버가 API 경계에서 집행할
수 없는 세분 권한은 권한 화면의 장식일 뿐이다. 액션은 **집행 가능한 단위**로만 둔다.

`SAVE` 통합으로 인가 모델은 화면의 저장 패턴 선택과 독립이다 — 셀 편집 즉시 동기화든,
모달 CRUD 든, 일괄 저장이든 전부 (메뉴, `SAVE`). 화면이 패턴을 바꿔도 매핑·부여 데이터의
재분류가 없다.

`EXECUTE` 는 CRUD 도 출력도 아닌 절차 발동을 위한 유형이다. 이것이 없으면 위험한 버튼이
`SAVE` 에 섞여 "저장 권한을 주면 배치 실행도 된다"가 된다. 실무에서 필요한 권한 비대칭은
"수정 vs 삭제"가 아니라 **"일상 저장 vs 위험한 절차"**이고, 그것은 `SAVE`/`EXECUTE` 가
담당한다. 그래도 남는 비대칭(같은 데이터에 역할별로 다른 조작)은 메뉴를 분리해 푼다 —
신청/승인 메뉴 분리와 같은 형태다.

집합은 이 4종에서 닫는다. 화면별 커스텀 액션을 허용하면 권한 화면이 메뉴마다 다른
컬럼을 갖게 되어 (주체 × 메뉴 × 액션) 의 균일함이 깨진다.

#### `EXPORT` 하나만 **집행되지 않는 경우가 있다** (2026-08-30 · [ADR-0027](../../../records/adr/0027-menu-declared-export-action.md))

바로 위 문단이 *"서버가 API 경계에서 집행할 수 없는 세분 권한은 장식"* 이라고 했다.
**`EXPORT` 가 그 경계에 걸친다** — 그러나 액션을 쪼갠 것이 아니라 **엑셀을 만드는 자리가
둘**이기 때문이다([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md)).

| 엑셀 경로 | 요청 | `SYS_API` 행 | 인터셉터가 |
|---|---|---|---|
| 임의 API (서버 POI) | **있다** | 있다(`export` 접두) | **집행한다** |
| 현재 페이지 · 전체 (프론트 생성) | **없다** | **없다** | 막을 것이 없다 |

**아래쪽에서 `EXPORT` 를 집행하는 것은 버튼을 그릴지 정하는 프론트뿐이다.** 화면에서
감추는 것은 UX 이지 방어가 아니라고 이 문서가 여러 번 말했고, 여기서도 그대로다 —
그러니 **그 권한을 봉쇄로 읽으면 안 된다.**

| | |
|---|---|
| **실제 경계** | **`READ`** 다. 조회할 수 있는 사람은 화면에 뜬 것을 옮겨 적을 수 있다 |
| `EXPORT` 가 남기는 것 | *"이 사람에게 내려받기를 허용했는가"* 라는 **운영 사실** |
| 짝이 되는 것 | **다운로드 기록** — 프론트 생성도 서버에 알린다([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) · `SYS_LO_ACCESS`) |

**그래도 장식이 아닌 이유가 그 마지막 줄이다.** 부여와 기록이 짝을 이루면 *정한 대로
운영되고 있는가* 를 물을 수 있다. 진짜 봉쇄가 필요한 데이터라면 답은 `EXPORT` 를 끄는
것이 아니라 **`READ` 를 주지 않는 것**이며, 그 판단을 흐리지 않으려고 여기 적어 둔다.

> **부여할 수 있는 액션의 정의도 여기서 갈린다.** 나머지 셋은 매핑된 API 가 말하지만
> (`SYS_MENU_API ⋈ SYS_API` — [ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)) 프론트 생성 엑셀에는 말해 줄 API 가 없어
> **메뉴가 직접 선언한다**(`SYS_MENU.EXPORT_YN` — [42](../../../knowledge/sys/menu.md) §4). 그때도 **`READ` 가 정의된
> 메뉴에만** 붙는다 — 위 표의 *실제 경계* 가 그 조건의 근거이기도 하다.

### 경로 결합은 없다 — 리프 단독 판정

**조상 메뉴의 권한은 판정에 관여하지 않는다.** 메뉴 접근 가능 여부는 그 메뉴 자신의
(역할 ∪ 개인) 권한만으로 결정된다.

> **권한은 URL 이 있는 메뉴에만 부여한다.** URL 없는 노드는 순수 구조다.

이 규칙으로 "조상 권한이 없다" 는 상태가 **구조적으로 존재할 수 없게** 된다 — 조상이
권한의 대상이 아니기 때문이다. `SYS_ROLE_MENU_AUTH` / `SYS_USER_MENU_AUTH` 에
URL 없는 메뉴가 들어오면 **거부**한다 (원칙 P1).

**URL 과 자식은 배타다**(2026-08-27 개정). 자식이 있으면 URL 을 가질 수 없고, URL 이
있으면 자식을 가질 수 없다 — *구조 노드는 경로, 리프는 화면* 이 **1:1** 이 된다.
`MENU_URL IS NULL` 과 *자식이 있다* 가 **같은 사실**이 되므로 판정이 볼 것도 하나다.

> **섹션 랜딩 화면을 포기한 것이다.** 폴더를 눌렀을 때 요약 화면이 뜨는 패턴은
> **자식 리프로 둔다**(`주문 › 주문 현황`). 대시보드가 이미 그 모양이다 — [52](../../../knowledge/sys/menu.md) §3.2.
> **제약으로 표현할 수 없으므로 저장 서비스가 검증한다**([42](../../../knowledge/sys/menu.md) §4 · 원칙 P1).

메뉴 트리(AUTHZ-04)는 **역산**한다.

```
권한 있는 메뉴 집합 → 각 메뉴의 조상 경로를 자동 포함 → 트리
```

조상은 **언제나** 표시만 되고 클릭 대상이 아니다 — 자식이 있으면 URL 이 없기 때문이며, 이제 예외가 없다. 개인 예외로 리프 하나만 받은
사용자도 그 경로가 트리에 자연스럽게 나타난다.

#### 왜 경로 결합을 기각하는가

| 이유 | 내용 |
|---|---|
| **개인 예외가 무력화된다** | 예외를 주려면 역할의 조상 권한도 열어야 하고, 그러면 그 역할의 다른 사용자 전원에게 영향이 간다. 개별 부여라는 목적이 성립하지 않는다. 게다가 **실패가 조용하다** |
| **암묵적 DENY 와 동형** | 리프에 GRANT 가 있는데 접근이 안 되고 원인은 다른 행에 있다. DENY 를 두지 않는 이유와 같은 문제다 |
| 웹앱에 "경로 통과" 가 없다 | 트리는 **내비게이션이지 게이트가 아니다.** 멀티탭(UX-02)·즐겨찾기(UX-03)·커맨드 팔레트(UX-04)는 모두 조상을 지나지 않는다 |
| 방어에 기여하지 않는다 | 실질 게이트는 메뉴 권한 + 메뉴↔API 매핑(AUTHZ-11) 이다 |

#### 폴더 단위 일괄 부여는 화면에서 푼다

"폴더 하나 끄면 하위 전체" 는 정당한 요구지만 **판정 모델이 아니라 UI 의 문제**다.
트리 체크박스의 연동 모드로 캐스케이드하고, **폴더 체크 상태는 저장하지 않는다.**

| 폴더 표시 | 의미 |
|---|---|
| ☑ 체크 | 하위 **전부** 권한 있음 |
| ⊟ 부분 | 하위 **일부만** 권한 있음 |
| ☐ 해제 | 하위 **전무** |

폴더 상태는 **저장값이 아니라 하위에서 파생된 값**이다. 그래서 "폴더는 꺼져 있는데
하위는 켜져 있다" 는 화면이 **표시될 수 없다** — `⊟ 부분` 으로 렌더된다.
사람마다 다르게 읽히는 상태가 애초에 만들어지지 않는다.

관리자 클릭은 1번, 서버 전송은 리프 키만, 저장은 리프 행 수만큼이다.
리프 단위 저장이 폴더 단위보다 나은 이유가 둘 더 있다.

| 이유 | 내용 |
|---|---|
| 메뉴 재편에 안전 | 폴더 권한이면 리프를 다른 폴더로 옮기는 순간 접근 가능자가 조용히 바뀐다 |
| 신규 메뉴가 자동 노출되지 않음 | 폴더 권한이면 그 아래 새 메뉴가 기존 권한자 전원에게 열린다. `deny by default` 와 어긋난다 |

### 개인별 예외 권한

| 항목 | 규칙 |
|---|---|
| 용도 | 역할로 표현하기 어려운 일시적·개별적 권한 |
| 부여 유형 | **허용(GRANT) 만.** 차단(DENY) 은 두지 않는다 |
| 기간 | `VALID_FROM_DT` / `VALID_TO_DT` — **기간 한정이 기본.** 업무 시간대의 날짜 → [40](../../../knowledge/sys/INDEX.md) §4.3 |
| 사유 | `GRANT_RSN` 필수 — 감사 대응 |
| 만료 처리 | **판정은 조회 시 계산.** 배치(AUTHZ-08)는 **만료 예정 통보만** 한다(§4 — 이력 기록은 2026-08-31 에 물렸다) |

> **DENY 를 두지 않는 이유**: 허용과 차단이 섞이면 우선순위 규칙이 필요해지고,
> "왜 권한이 없는지" 를 추적하기 어려워진다. 특정 사용자만 빼야 하면 역할을 분리한다.

#### 화면은 역할 권한 화면과 같은 컴포넌트

권한의 단위가 `(주체 × 메뉴 × 액션)` 이므로 **주체 선택만 역할↔사용자로 바뀌는
같은 컴포넌트**를 쓴다. 별도 매핑 화면을 새로 만들지 않는다. 트리도 그대로 쓰므로
부모 클릭 한 번으로 하위 전체가 선택된다.

**반드시 있어야 하는 것 — 역할 보유분 구분 표시.**

| 상태 | 표시 |
|---|---|
| 역할로 이미 보유 | **읽기 전용**(체크 고정·비활성) + 어느 역할에서 왔는지 |
| 개인 예외로 보유 | 편집 가능 + 기간·사유 |
| 없음 | 편집 가능 |

"지금 내가 무엇을 추가하는 중인가" 가 보이지 않으면 이 화면은 쓸 수 없다.
이미 있는 권한을 중복 부여하게 된다.

기간·사유는 **행마다가 아니라 부여 작업 단위**로 한 번 입력받아 선택 행 전체에 복사한다.
10 행에 사유를 10 번 쓰게 하면 아무도 쓰지 않는다. 회수는 행 단위로 개별 가능하게 둔다.

#### 마찰을 유지한다

한 경로의 리프 10 개를 한 사람에게 통째로 줘야 하는 상황이면, 그것은 개인 예외가 아니라
**역할**이다. 10 개 묶음은 일시적이지도 개별적이지도 않다.

마찰을 없애려고 개인 예외를 폴더 단위로 확장하면 개인 예외가 **제2의 역할 체계**가 되고
"이 사용자가 왜 이 권한을 갖는가" 추적이 불가능해진다. 대신 화면이 안내한다.

- 선택 건수가 임계치를 넘으면 **"역할 신설을 검토하세요"** 안내 — [61](../../../../documents/screen/user/requirements.md) §4.4

> **탐지 리포트를 두지 않는다(2026-08-27).** 같은 예외 조합이 반복되는 사용자를 모아
> 보여주는 화면(AUTHZ-12)을 두려 했으나 **기능에서 뺐다**([52](../../../knowledge/sys/menu.md) §4.5). 개인 예외는 말
> 그대로 예외라 **반복을 탐지할 만큼 쌓이지 않고**, *"조합을 어떻게 묶는가"* 라는 무거운
> 결정을 끌고 온다. **남는 장치는 위의 부여 시점 안내 하나**이며, 그것이 마찰을 남겨 두는
> 이 결정의 취지에 오히려 가깝다 — 쌓인 뒤에 걷어내는 것보다 **쌓이기 전에 묻는 편**이 낫다.

### 결재/승인이 필요한 경우

결재선·조직 계층 기반의 워크플로는 만들지 않는다. 대신 **신청 메뉴와 승인 메뉴를 분리**하고,
각 메뉴에 서로 다른 역할을 부여해 절차를 표현한다. → 설계 원칙 §2

### 접근 제어 체인 — 모든 메뉴·API 접근에 적용

권한 검사 하나만으로는 부족하다. 모든 요청은 아래 순서로 검사하며,
검사마다 **로그인 시점**과 **세션 중(매 요청)** 의 실행 지점이 다르다.

| # | 검사 | 실패 시 | 로그인 시 | 세션 중 (매 요청) |
|---|---|---|---|---|
| 1 | 로그인 여부 | 401 → 로그인 화면 | 인증 그 자체 | Security 필터 체인 — 세션 복원 실패 시 401 |
| 2 | 계정 활성화 여부 | 401 + 사유 | `isEnabled()` 자동 | 인가 인터셉터 — 사용자 상태 캐시 재검사 |
| 3 | 계정 사용 기간 만료 여부 | 401 + 사유 | `isAccountNonExpired()` 자동 | 〃 |
| 4 | 계정 잠금 여부 | 401 + 사유 | `isAccountNonLocked()` 자동 | 〃 |
| 5 | **비밀번호 만료 여부** | **차단이 아니라 강제 변경 유도** | `isCredentialsNonExpired()` 자동 → 제한 세션 전환 | 인가 인터셉터 — 제한 세션이면 변경 API 외 403 |
| 6 | 메뉴·액션 권한 (역할 ∪ 개인) | 403 → 권한 없음 화면 | 유효 권한 캐시 적재 — **공집합이면 차단**(위) | 인가 인터셉터 — 아래 서버측 인가 절 |
| 7 | 개인정보 접근 권한 (해당 시) | 마스킹 유지 | — | 응답 직렬화 계층 → [27-pii-vault](../pii-vault.md) §2, 해제 보기는 §7 |

**로그인 시점의 2~5 는 Spring Security 의 `UserDetails` 4개 플래그와 정확히 대응**하므로
`AccountStatusUserDetailsChecker` 가 자동 검사한다. 직접 구현하지 않는다.

> **5번만 별도 처리가 필요하다.** 비밀번호 만료는 "접근 차단"이 아니라
> "비밀번호 변경 화면으로 유도"여야 한다. `CredentialsExpiredException` 을 잡아
> 비밀번호 변경 API 만 허용하는 제한 세션 상태로 전환한다.
> 변경 완료 전까지 다른 모든 API 는 403 + `PASSWORD_CHANGE_REQUIRED` 코드를 반환한다.

세션 중 재검사가 필요한 이유: 세션 유지 중 상태가 바뀔 수 있다(관리자가 계정 비활성화).
그래서 2~6 은 **인가 인터셉터 하나**가 매 요청 수행한다 — 캐시 조회 두 번
(사용자 상태 + 유효 권한, 아래 권한 캐싱 절)이면 끝난다. 파이프라인 내 위치는
[21-backend-architecture](./architecture.md) §5.

### 비밀번호 초기화와 계정 잠금 (AUTH-04 · AUTH-07)

경로가 둘이며 **성격이 다르다.**

| 경로 | 성격 | 전제 |
|---|---|---|
| **자기 재설정** (본인 이메일) | 기본 경로 | 메일 발송이 동작한다 |
| **관리자 발급** | **대체 경로** | 메일 서버 장애 · 메일 연동 미구성 |

관리자 발급은 편의 기능이 아니라 **메일 경로가 없을 때의 유일한 계정 복구 수단**이다.
따라서 기본으로 켜 둔다 — 끄면 메일 연동이 없는 배포에서 잠긴 계정을 풀 방법이 사라진다.

#### 잠금 전이

| 사건 | 전이 |
|---|---|
| 비밀번호 불일치 | `LOGIN_FAIL_CNT` +1. 임계값 도달 시 `LOCK_YN='Y'` · `LOCK_DTM=now` |
| 로그인 성공 | `LOGIN_FAIL_CNT=0` · `LOCK_YN='N'` (경과분 정리) |
| 잠금 시간 경과 | **컬럼을 갱신하지 않는다** — 조회 시 계산해 플래그를 만든다 |
| **관리자 임시 비밀번호 발급** | `LOCK_YN='N'` · `LOGIN_FAIL_CNT=0` · `PWD_INIT_YN='Y'` — **발급 시점에 푼다** |

`auth.login.fail-limit = 0` 은 **잠금 기능을 끈다**(개발 환경용).
`lock-release-minutes = 0` 은 관리자 해제만 허용한다.

> **자동 해제를 배치로 하지 않는다.** 배치는 지연이 있어 *"30분 지났는데 아직 잠김"* 이
> 생긴다. `isAccountNonLocked()` 는 `LOCK_YN='Y' AND LOCK_DTM + release > now` 를
> **조회 시 계산**한 결과다 — 컬럼은 원시 데이터, 플래그는 파생이다.

#### 자기 재설정 흐름

```
① 요청   토큰(6자리 숫자) 생성 → 해시만 저장 → 메일 발송
         LOCK_YN · PWD_INIT_YN · LOGIN_FAIL_CNT 를 건드리지 않는다
         응답은 항상 동일 — "입력한 메일로 안내를 보냈습니다"

② 검증   TOKEN_HASH 일치 + 미만료(10분) + USED_YN='N' + TRY_CNT 한도(5회) 내

③ 완료   PWD 갱신 · PWD_CHG_DTM=now · PWD_INIT_YN='N'
         LOCK_YN='N' · LOGIN_FAIL_CNT=0        ← 잠금은 여기서 푼다
         USED_YN='Y' · SYS_USER_PWD_HIST 적재
```

> **관리자 발급은 발급 시점에 풀어도 된다.** 자기 재설정 ①과 달리 **관리자가 신원을
> 확인하고 수행하는 행위**이며, 잠긴 계정을 푸는 것이 이 경로의 목적 자체다. 발급하고도
> 잠긴 채로 두면 관리자가 잠금 해제를 따로 눌러야 하고, 그 두 단계를 이어 붙이는 것은
> 실수를 부른다.

> **①에서 잠금을 풀면 잠금이 무력화된다.** 초기화 요청은 ID 만 알면 누구나 트리거할 수
> 있다. 요청만으로 풀리면 *실패 5회 → 초기화 요청 → 리셋 → 다시 5회* 가 무한 반복된다.
> 공격자에게 메일이 가는 것은 방해가 되지 않는다 — 목표는 잠금 리셋이다.
> **인증번호를 받은 사람만 풀 수 있어야 한다.**

> **①의 응답을 항상 같게 하는 이유**는 존재하지 않는 ID 를 알려주면 ID 열거가 되기
> 때문이다 — 로그인 실패 응답과 같은 논리다([45](../../../knowledge/sys/logs.md) §5.2).
>
> **인증번호는 해시로만 저장한다.** 평문으로 두면 DB 유출이 곧 계정 탈취가 되고,
> 비밀번호를 해시하는 이유가 무의미해진다.

#### 관리자 발급 흐름

```
관리자   임시 비밀번호를 시스템이 생성 → 화면에 1회 표시(재조회 불가)
         PWD_INIT_YN='Y' · PWD_CHG_DTM=now
         LOCK_YN='N' · LOGIN_FAIL_CNT=0        ← 관리자는 즉시 풀 수 있다
         SYS_USER_PWD_HIST 적재 (REG_ID = 관리자)
사용자   로그인 → 강제 변경 화면 → 변경 완료 시 PWD_INIT_YN='N'
```

- **관리자가 문자열을 직접 입력하지 않는다.** 시스템이 정책(길이·문자조합)을 만족하는
  값을 생성한다 — 관리자가 아는 패턴을 쓰는 것을 막는다
- 저장은 해시이므로 **재조회가 구조적으로 불가능**하다. 1회 표시가 자연스럽다
- **사유 입력을 필수로** 한다. 이 경로가 상시 편의 수단이 되는 것을 억제한다
- 메일이 동작하면 사용자에게 *"관리자가 비밀번호를 초기화했습니다"* 를 통지한다

> **임시 비밀번호에는 별도 만료가 필요하다.** `PWD_INIT_YN='Y'` 상태가 90일 유지되면
> 발급받고 방치한 계정이 그만큼 취약해진다. `auth.password.temp-valid-hours`(기본 24)를
> 넘으면 로그인 자체를 막고 재발급을 요구한다.

#### 체인 #5 는 두 조건의 OR 이다

```
비밀번호 변경 필요 = PWD_INIT_YN='Y'  OR  PWD_CHG_DTM + expire-days 경과
```

임시 비밀번호에 정상 유효기간(90일)을 주면 안 되므로 `PWD_INIT_YN` 이 독립 조건이다.

> 별도 이력 테이블을 두지 않는다. 초기화 요청·완료는 API 호출이므로 사용 이력
> (`SYS_LO_ACCESS`)에 남고, 비밀번호 변경 사실은 `SYS_USER_PWD_HIST` 에 행위자와 함께
> 남는다 — 관리자가 남의 비밀번호를 바꾼 경우가 `REG_ID` 로 구분된다([45](../../../knowledge/sys/logs.md) §2.1).

### 서버측 인가 (필수)

프론트에서 메뉴·버튼을 숨기는 것은 UX 이지 보안이 아니다. 프론트가 든 권한 사본은
재조회 전까지 낡을 수 있다 — 방금 회수된 권한의 버튼이 아직 보일 수 있고, 그 클릭을
막는 것은 서버다. 판정의 원본은 항상 서버쪽 유효 권한이다.

SPA 이므로 **"화면 로드"라는 서버 요청은 존재하지 않는다.** 화면 접근은 서버가 내려준
권한 메뉴 목록(AUTHZ-04)으로 프론트 라우터가 제한하고([24-frontend-stack](../../frontend/_study/frontend-stack.md) §5),
서버가 실제로 지키는 것은 그 화면이 호출하는 **API** 다. JS 청크는 정적 리소스라 막지
않는다 — 보호 대상은 화면(코드)이 아니라 데이터다.

#### 인가 사실의 원본은 데이터이며, 두 테이블로 나뉜다

API 하나를 인가하는 데 필요한 사실은 둘 — 이 API 가 어떤 **액션**인가, 어느 **메뉴들**에
속하는가. **성격이 다르므로 각자의 테이블에 둔다.** 코드에는 아무 선언도 없다.

| 사실 | 테이블 | 성격 |
|---|---|---|
| 이 URL 은 어떤 액션인가 · 무슨 일을 하는가 | **`SYS_API`** (마스터) | **API 의 속성** — 메뉴와 무관하다 |
| 이 URL 을 어느 메뉴가 쓰는가 | `SYS_MENU_API` (매핑) | **정책** — 1 : N |

컬럼 상세는 [42](../../../knowledge/sys/menu.md) §5 다. 한 테이블에 두었을 때의 문제는
**같은 API 가 메뉴마다 다른 `ACTION_CD` 를 갖는 모순이 저장될 수 있다**는 것이었고,
그러면 인가 판정이 어느 행을 읽느냐에 따라 갈렸다 — [ADR-0016](../../../records/adr/0016-api-master-table.md).

**`HTTP_METHOD` 는 두지 않는다.** 업무 API 는 경로가 곧 오퍼레이션이므로(아래) 메서드는
식별에 기여하지 않고, 검증하지 않는 정보 컬럼은 표류한다. **키는 `API_URL` 단독**이며,
한 경로에 두 오퍼레이션을 두려는 시도는 `SYS_API` PK 충돌로 시드 배포에서 막힌다(원칙 P1).

**업무 API 의 경로는 고정 문자열이다** — 경로 변수(`{id}`)와 와일드카드(`*`/`**`)를 쓰지
않는다. 행위 주체(userId)는 세션에서 얻고, 대상 식별자와 조회 조건(마스터-디테일의 부모
PK 포함)은 body 에 담는다 — 조회도 대부분 POST + body 다. 조회가 POST 인 것은 문제가
아니다: 액션은 HTTP 메서드에서 유추하지 않고 `ACTION_CD` 가 선언한다. 쿼리스트링은
자유지만 **매칭에 참여하지 않는다.**

따라서 매칭은 패턴 매칭이 아니라 **경로 완전 일치** — 해시 조회 한 번이다.

- 겹침이 구조적으로 불가능하다 — 같은 키의 행 N 개는 의도된 다중 메뉴 매핑뿐이다
- 새 API 가 기존의 넓은 패턴에 자동으로 덮이는 일이 없다 — 새 API 는 반드시 새 행이다
- 시드 행과 컨트롤러의 매핑 문자열이 1:1 이라 대조 리뷰가 기계적이다

경로 변수가 자연스러운 API(파일 다운로드 등)는 애초에 메뉴 소속이 아니라 공통 API 다.
공통·공개·외부 계층은 매핑에 참여하지 않으므로 이 제약과 무관하다.

메뉴를 코드에 박으면(`@PreAuthorize("hasMenuAuth('USER_MGMT','SAVE')")` 식) 두 번째
화면이 그 API 를 재사용하는 순간 코드 수정·배포가 필요하고, 나열을 잊으면 그 화면
사용자만 **조용히 403** 을 받는다 — API 재사용에 벌금을 물리는 구조다. 같은 API 를
여러 화면이 쓰는 것은 정상이므로(API 1 : 메뉴 N), 인가 사실은 데이터여야 한다.

모든 `/api/**` 는 **경로 프리픽스로** 셋 중 정확히 하나에 속한다. 분류가 URL 에
새겨지므로 별도 상수 목록이 없고, 컨트롤러의 경로가 곧 보안 등급 선언이다.

| 분류 | 프리픽스 | 통과 조건 |
|---|---|---|
| 공개 | `/api/public/**` | 익명(`permitAll`). 로그인, 비밀번호 재설정(분실) 등 최소한 |
| 공통 API | `/api/common/**` | 인증만. 특정 메뉴에 소속시킬 수 없는 것 — 공통코드 조회, 사용자 검색 팝업, `auth/me`, **메뉴 선택 기록**([42](../../../knowledge/sys/menu.md) §8), **진행률 폴링**(`common/progress/{jobId}` — [30](../crosscutting.md) §6), **파일 다운로드**(`common/file/**` — [47](../../../knowledge/sys/notification.md) §3) 류 |
| 업무 API | `/api/service/**` | 인증 + `SYS_API` 에 행이 있고, 그 URL 의 `SYS_MENU_API` 메뉴 1~N 중 **하나라도** (메뉴, 액션) 권한 보유 — OR |

- **세 프리픽스 밖의 `/api/**` 는 무조건 403** — 미분류가 경로 차원에서 fail-closed 다.
- **버전 프리픽스(`/v1`)는 두지 않는다.** 프론트가 서버 JAR 에 임베드되어 원자적으로 함께
  배포되므로([ADR-0001](../../../records/adr/0001-repository-layout.md)) 뒤처질 구버전 클라이언트가 없고,
  v1/v2 공존이라는 상황이 성립하지 않는다. 배포 중 열려 있던 탭의 구버전 번들만 남는
  문제인데, 그것은 URL 버전이 아니라 빌드 버전 핸드셰이크로 푼다([24](../../frontend/_study/frontend-stack.md) §10).
- 외부 시스템 연동이 생기면 네 번째 프리픽스로 추가한다 — `/api/ext/**` + 비인간 주체
  인증(API 키/mTLS), 버전이 필요하면 **그 계층만** 갖는다. 지금은 구현도 훅도 두지 않는다.
- 오배치 위험 한 곳: 업무 API 를 `/api/common` 아래 두면 조용히 열린다. URL 에 보이므로
  **코드 리뷰가 지키는 지점**이다.

판별 신호: 매핑하려니 **메뉴를 전부 나열하게 되는** API 는 업무 API 가 아니라 공통 API 다.

#### 판정은 인가 인터셉터 한 곳에서 한다

```
요청 → /api/public 익명 통과 · /api/common 인증만 확인
    → /api/service 는 경로 완전 일치로 SYS_API 조회 → ACTION_CD 1개
    → 같은 경로의 SYS_MENU_API 조회 → MENU_CD N개
    → (메뉴, 액션) 조합 중 하나라도 유효 권한(역할 ∪ 개인)에 있는가 → 없으면 403
    → SYS_API 미등록도 403 · 메뉴 매핑 0건도 403 · 세 프리픽스 밖 /api/** 도 403
```

**403 이 되는 두 경우를 구분해 기록한다.** 원인이 다르고 고치는 곳이 다르다.

**기록처는 `SYS_LO_EXCEPTION.ERR_CD` 다**(2026-08-28 확정 — [45](../../../knowledge/sys/logs.md) §4.2 · [21](./architecture.md) §6.3).
이 절은 오래 *"구분해 기록한다"* 고만 적고 **어디인지를 비워 두었다.**

| `ERR_CD` | 상태 | 뜻 | 고치는 곳 |
|---|---|---|---|
| **`err.api-not-registered`** | `SYS_API` 에 행이 없다 | API 자체가 등록되지 않았다 | API 마스터 시드 |
| **`err.api-not-mapped`** | 행은 있으나 `SYS_MENU_API` 가 0건 | 등록됐지만 어느 메뉴도 쓰지 않는다 → 아무도 권한을 가질 수 없다 | 매핑 시드 |
| **`err.no-authority`** | 매핑은 있으나 유효 권한에 쌍이 없다 | **API 는 정상이고 사람에게 권한이 없다** | 역할 권한 · 개인 예외 |

구분하지 않으면 *"권한을 줬는데 403"* 문의에서 어디를 봐야 할지 알 수 없다.

**셋째 줄이 이 표에 새로 들어왔다** — 원래 둘은 *설정 결함*이고 셋째는 *정상 동작*이라
가르지 않았는데, **운영자가 받는 것은 셋 다 403 하나**다. 셋을 코드로 갈라야
[62](../../../../documents/screen/menu/requirements.md) §5.2 의 진단 동선이 성립한다. 403 은 **`SYS_LO_ACCESS` 에도 일어난 요청으로
남는다** — 사용 이력이 전 요청을 받기 때문이다([21](./architecture.md) §6.3).

판정 원본을 하나로 유지하기 위해 **기각한 것 둘**:

| 기각 | 이유 |
|---|---|
| `@PreAuthorize` 메서드 시큐리티 병행 | 같은 사실을 두 곳이 각자 판정하면 어긋났을 때 실효 규칙이 둘의 AND 가 되어 "권한 화면엔 체크돼 있는데 403" 이 생기고 원인은 다른 곳에 있다 — DENY·경로 결합을 기각한 것과 같은 이유 |
| 액션 코드 어노테이션 + 기동 정합 검증 | 원본이 데이터 하나면 표류할 상대가 없다. 코드 선언을 얹으면 데이터와의 정합 검증 인프라까지 따라와야 하는데, 그 유지비가 코드 가시성이라는 효익을 넘는다 |

공유 API 의 OR 판정이 정당한 이유: 사용자가 얻는 것은 화면이 아니라 **API 능력**이고,
능력은 호출 경로와 무관하다. 어느 화면에서 호출했는지는 인가에 쓰지 않는다 — 클라이언트가
매 요청 부착하는 현재 메뉴 코드(`X-Menu-Code`)는 사용 이력(LOG-01)에만 기록된다
([21-backend-architecture](./architecture.md) §6). 화면마다 허용 **범위**가 달라야
한다면 그것은 공유 API 가 아니라 **분리해야 할 두 API** 다.

> **405 는 저절로 나오지 않았다**(2026-08-29 실측). [42](../../../knowledge/sys/menu.md) §5 는 *"잘못된 메서드는 Spring MVC 가
> 405 로 거부하며 인터셉터에 닿지 않는다"* 를 전제로 `HTTP_METHOD` 컬럼을 뺐다. **앞 절반은
> 맞다** — `HttpRequestMethodNotSupportedException` 이 디스패처에서 던져지고 인터셉터에 닿지
> 않는다. 그런데 **아무도 그것을 잡지 않아** 포괄 예외 핸들러가 받았고 결과가 **500 +
> ERROR 로그**였다. 인가 판정의 403 을 확인하다 `GET /api/public/auth/login` 에서 드러났다.
>
> 그냥 지저분한 것이 아니다. **500 은 서버가 고장났다는 뜻**이고 그 로그는 사람을 깨운다 —
> 클라이언트가 메서드를 틀린 것이 그것과 같은 신호를 내면 안 된다. `GlobalExceptionHandler` 에
> 405(`err.method-not-allowed`)와 깨진 본문 400(`err.malformed-body`)을 명시적으로 더했다.
> `HTTP_METHOD` 를 두지 않는 결정 자체는 그대로다.

#### deny by default — 런타임 403 이 전부다

세 프리픽스 어디에도 해당하지 않는 `/api/**` 요청은 **403** 이다. 이 한 줄이 정책 전부다.

매핑 등록을 잊으면 그 화면을 처음 열어 보는 순간 403 으로 드러난다. 실패 방향이
"조용히 뚫림"(미매핑을 인증만으로 통과)이 아니라 "조용히 잠김"이므로, 누락은 보안
사고가 아니라 개발 중 발견되는 버그다. 허용은 언제나 명시적 매핑의 결과다.

기동 시 핸들러 전수 스캔 같은 사전 검증은 **두지 않는다.** fail-closed 런타임이 이미
미매핑을 잡으므로 스캔이 앞당기는 것은 발견 시점뿐인데, 그 대가로 커스텀 검증 인프라를
유지해야 한다. 단, 이 판단은 **fail-closed 가 전제**다 — 미매핑을 통과시키는 쪽으로
바꾸는 순간 이 절은 성립하지 않는다.

#### 매핑은 시드로만 바뀐다

인가 사실 전체가 데이터이므로 `SYS_MENU_API` 행 추가가 곧 **접근 범위 확장**이다.
매핑은 운영 화면에서 편집하는 데이터가 아니라 화면 코드와 함께 **코드 리뷰를 거쳐
배포되는 Liquibase 시드**다(첫 실물은 샘플 화면 — [10-feature-inventory](../../../knowledge/features.md) §L).
메뉴 관리 화면(AUTHZ-01)은 트리·표시 속성만 다루고 매핑은 다루지 않는다.

`SYS_API` 도 시드다. 어떤 URL 이 존재하고 그것이 어떤 액션인지는 **코드가 결정하는 사실**
이므로 운영 중 편집 대상이 아니다. 관리 화면은 **조회 전용**이다(AUTHZ-14).

**그 시드는 손으로 쓰지 않고 생성한다** — `./gradlew generateApiSeed` 가 컨트롤러 스캔과
프론트 `endpoints` 선언에서 두 changelog 를 만들고, 개발자가 그것을 커밋한다.
액션은 **경로 접두**가 정하며 `@ApiActionType` 이 예외를 선언한다. 생성물을 커밋하지 않으면
CI 의 `checkApiSeed` 가 빌드를 세운다 — 리뷰는 유지하면서 누락만 막는다
([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md) 에 작업 순서가 있다).

시드 리뷰가 볼 것 둘:

- **`SYS_API` 행의 `ACTION_CD` 가 맞는가** — 이 값 하나가 그 API 의 인가 등급이다
- **이 API 를 이 메뉴들에 여는 것이 맞는가** — 매핑 행 추가 = 접근 확장

> **테이블을 나눈 뒤로 리뷰가 지킬 항목이 하나 줄었다.** 이전에는 *"같은 URL 행들의 액션이
> 같은가"* 를 사람이 봐야 했다. 이제 `ACTION_CD` 가 `SYS_API` 에 한 번만 존재하므로
> **모순이 저장될 수 없다** — 검증을 사람에서 구조로 옮긴 것이다(원칙 P1).

### 권한 캐싱 — 유효 권한은 세션에 둔다

인가 인터셉터가 매 요청 참조하는 것은 전부 미리 적재된 것이다. **요청당 추가 쿼리 0** 이
기본이다.

| 자리 | 내용 | 갱신 |
|---|---|---|
| **세션** | 사용자별 **유효 권한** (역할 ∪ 개인) + `authzCalcDate` (계산한 업무 시간대 날짜) | 아래 |
| **세션** | 계정 활성/기간/잠금 상태 | 사용자 상태 변경 시 같은 방식 |
| API 인가 사실 | `SYS_API` + `SYS_MENU_API` 를 합쳐 `URL → (ACTION_CD, [MENU_CD…])` 맵으로 기동 시 적재 | 불변. 시드 배포 = 재기동 |

**공유 캐시(Redis)가 아니라 세션인 이유** — 세션은 어차피 매 요청 조회되므로 추가 왕복이
없고, 세션 스토어가 공유라 다중 노드에서 노드마다 다른 값을 가질 수 없다. 그리고 그
사용자의 세션만 건드리면 되므로 **폴링 지연 없이 즉시** 반영된다([ADR-0017](../../../records/adr/0017-cache-strategy-per-target.md)).

담는 것은 **계산 결과**(`{(MENU_CD, ACTION_CD)}` 집합)이지 역할 목록이 아니다. 역할·개인
예외·유효기간은 계산 입력이며 세션에 담지 않는다 — 담으면 매 요청 재계산해야 한다.

#### 체인 #2~#4 재검사는 재계산에 얹는다 (2026-08-29 구현)

체인 표는 *"세션 중 (매 요청)"* 열에 **인가 인터셉터 — 사용자 상태 캐시 재검사**라고만
적어 두었고 **언제 다시 읽는지**가 비어 있었다. 두 극단은 둘 다 틀렸다.

| 안 | 문제 |
|---|---|
| 매 요청 계정 조회 | **요청당 추가 쿼리 0** 이라는 이 절의 전제가 깨진다 |
| 하지 않음 | 비활성화된 계정이 **세션 만료까지 계속 일한다** |

**답은 재계산과 같은 순간이다.** 유효 권한을 다시 계산하는 트리거가 계정 상태를 다시 봐야
하는 순간과 정확히 겹친다.

| 트리거 | 잡는 것 | 지금 동작하나 |
|---|---|---|
| `authzCalcDate` 불일치 | 계정 사용 기간 만료(#3) · 부여 만료 | **동작한다** |
| `authzDirty` | 관리자의 `USE_YN` 해제 · 강제 잠금(#2 · #4) | **플래그를 세우는 화면이 아직 없다** |

- 실패하면 **세션 무효화 + 401** 이다. 403 이 아닌 이유 — 권한의 문제가 아니라 그 사람이
  더는 로그인 상태일 수 없다는 뜻이고, 프론트는 401 에 재인증 모달을 띄운다([24](../../frontend/_study/frontend-stack.md) §9)
- **남는 창이 하나다**: 관리자가 계정을 비활성화해도 그 사용자의 세션은 **자정까지** 살아
  있다. 사용자 관리 슬라이스가 `markDirty` 를 부르면 닫힌다. 강제 로그아웃(AUTH-10)은 세션
  자체를 지우므로 이 경로와 무관하다

#### 갱신은 플래그로 한다

```
역할 권한·역할 USE_YN 변경 → SYS_USER_ROLE 역방향 조회로 보유자 전원 (위)
                          → findByPrincipalName(userId) 로 각 세션에 authzDirty=true
                          → 각 사용자의 다음 요청에서 인터셉터가 재계산 후 세션 갱신
```

권한 집합을 미리 계산해 넣지 않는다. 역할 하나를 바꾸면 보유자가 100명일 수 있고,
**플래그를 세우는 편이 훨씬 가벼우며** 로그인하지 않은 사용자는 계산조차 하지 않는다.

세션 검색은 §4-1 이 채택한 `SpringSessionBackedSessionRegistry` 가 이미 요구하는
`FindByIndexNameSessionRepository` 를 쓴다 — AUTH-09·AUTH-10 과 같은 부품이다.

> **날짜 경과도 갱신 신호다.** `VALID_TO_DT` 가 오늘까지인 사용자는 자정을 넘겨도 아무도
> 값을 바꾸지 않았으므로 `authzDirty` 가 서지 않는다. 인터셉터는 플래그와 `authzCalcDate`
> 를 **함께** 본다 — 위 *"기간이 있는 부여는 시간이 캐시를 낡게 만든다"*.

## 4-1. 동시 접속 제어

**방침: 동시 세션은 계정당 1개.** 다른 IP(다른 자리)에서든 같은 자리에서든 두 번째 세션을
허용하지 않는다. IP 를 비교해 막는 방식이 아니라 **세션 개수 제한**으로 달성한다 — IP 비교는
Spring Security 가 제공하지 않는 커스텀인 데다, 사무실 NAT(전원이 같은 공인 IP)에서는 못
잡고 모바일 망(IP 수시 변동)에서는 오탐한다. 개수 제한은 IP 구분 없이 두 번째 세션 자체를
막으므로 요구를 포괄한다.

Spring Security 의 세션 관리 기능을 쓰고 **yml 로 옵션화**한다. 직접 구현하지 않는다.

> **스토어에 principal 인덱스가 있어야 성립한다**(2026-08-30 · [ADR-0002](../../../records/adr/0002-selectable-session-store.md)).
> 레지스트리는 `SpringSessionBackedSessionRegistry` 이고 그것은
> `FindByIndexNameSessionRepository` 를 요구한다. **Spring Session 의 Redis 구현은 둘이고
> 인덱스를 가진 것은 하나**인데(`RedisIndexedSessionRepository`),
> `spring.session.data.redis.repository-type` 의 **기본값이 인덱스 없는 쪽**이다.
>
> 그래서 **스토어를 골라 놓고 인덱스가 없으면 기동을 실패시킨다** — 이전에는 조용히
> `SessionRegistryImpl`(JVM 힙의 맵)로 떨어졌고, 그 상태는 **제어가 걸려 있다고 믿는
> 무제한 배포**다. 증상이 *"계정당 1세션인데 두 곳에서 로그인된다"* 라 원인을 짐작하기
> 어렵다. 스토어가 **아예 없는 것**(`none` · 컨테이너 세션)은 선택된 동작이라 그대로 둔다.

```yaml
app:
  security:
    concurrent-session:
      enabled: true
      max-sessions: 1          # 동시 허용 세션 수
      prevent-login: false     # true=신규 로그인 차단, false=기존 세션 만료
```

| 설정 | 동작 |
|---|---|
| `enabled: false` | 제한 없음 |
| `prevent-login: false` (기본) | 신규 로그인 성공, **기존 세션 강제 만료** |
| `prevent-login: true` | 기존 세션 유지, **신규 로그인 거부** |

**기본값 확정 (2026-08-23)**: 위 yml 값 그대로 — `enabled: true` · `max-sessions: 1` ·
`prevent-login: false`(후승 우선). `prevent-login: true` 를 기본으로 두지 않는 이유:
브라우저 비정상 종료로 남은 유령 세션이 재로그인을 세션 타임아웃(최대 30분)까지 막는다.

### 구현 시 유의점

- 세션이 외부 스토어(JDBC/Redis)에 있으므로 기본 `SessionRegistry` 로는 다중 노드에서 동작하지 않는다.
  **`SpringSessionBackedSessionRegistry`** 를 사용해야 JDBC·Redis 양쪽에서 정상 동작한다.
- 강제 만료된 세션의 사용자는 다음 요청에서 401 을 받는다. 프론트가 사유를 구분해 안내한다
  (`SESSION_EXPIRED` vs `CONCURRENT_LOGIN`).
- 강제 만료도 로그인 이력(LOG-02)에 기록한다.

#### 구현하며 채운 것 (2026-08-29)

| 무엇 | 내용 |
|---|---|
| **`ConcurrentSessionFilter` 가 필수다** | `expireNow()` 는 세션을 <b>지우지 않고 표시만</b> 한다. 그것을 읽어 끊는 필터가 없으면 밀려난 사용자의 `SecurityContext` 가 세션에 그대로 남아 **계속 일할 수 있다** — 제어가 조용히 무력해진다. 기본 동작(로그인 페이지 리다이렉트)은 SPA 에 쓸 수 없으므로 401 JSON 을 쓰는 전략을 함께 둔다 |
| **전략 순서가 규약이다** | 밀어내기(`ConcurrentSessionControl`)가 <b>먼저</b>, 세션 ID 교체(`ChangeSessionId`)가 뒤다. 뒤바뀌면 방금 만든 새 세션을 기존 세션으로 세어 <b>자기가 자기를 밀어낸다</b> |
| **`RegisterSessionAuthenticationStrategy` 를 넣지 않는다** | 등록은 Spring Session 의 principal 인덱스가 이미 하고 있고, `SpringSessionBackedSessionRegistry` 의 등록 메서드는 의도적으로 아무 일도 하지 않는다 |
| **`prevent-login: true` 의 실패 코드가 없었다** | 신규 로그인 거부에 대응하는 이력 코드와 화면 문구가 비어 있었다 — `FAIL_CONCURRENT` · `err.login.concurrent` 를 신설했다([45](../../../knowledge/sys/logs.md) §5.1) |
| **거부는 성공 기록보다 앞이다** | 세션 수립이 실패 횟수 초기화(`recordLoginSuccess`)보다 <b>먼저</b> 일어나야 한다. 순서가 뒤바뀌면 거부된 로그인이 잠금 카운터를 지운다 |
| **`app.security.concurrent-session` 은 `SYS_CONFIG` 가 아니다** | 기동 시 필터 체인의 모양을 정하므로 런타임에 바꿔도 반영될 자리가 없다 — 배포 설정이며 관리 화면에 나타나지 않는다([43](../../../knowledge/sys/code.md) §6.1 의 경계 밖) |

> **켜 두었는데 세지 못하는 상태**가 가능하다 — 세션 스토어가 `none` 이면 principal
> 인덱스가 없어 레지스트리가 비어 있고, 그러면 <b>제한이 걸린 줄 알지만 실제로는 무제한</b>
> 이다. 기동 시 경고를 남긴다.

|---|---|

| 마스킹 | 서버에서 수행. 규칙은 `SYS_PII_DEF.MASK_RULE_CD` |

### 키 관리

`CryptoKeyProvider` 인터페이스로 추상화하고 구현 2개를 내장한다.

| 구현 | 용도 |
|---|---|
| `file` | **운영 기본.** 설정에는 키 파일 경로만 (`app.crypto.key-file`) — 경로는 비밀이 아니다 |
| `env` | 로컬/개발 (`APP_CRYPTO_KEY`) |

클라우드 KMS(AWS KMS · GCP Cloud KMS · Azure Key Vault)는 어댑터 예시만 문서화하고
의존성은 포함하지 않는다. 자체 구축형(Vault)은 고가용 시스템을 하나 더 운영하는 일이라
템플릿 범위에 과하다.

#### 키 파일

**평문 텍스트 파일이 맞다.** 보호는 파일 내용 암호화가 아니라 접근 통제에서 나온다 —
keystore 로 감싸면 그 비밀번호가 또 필요해져 비밀이 한 겹 밀릴 뿐이고, K8s·Docker 의
secret 도 컨테이너 안에서는 결국 평문 파일 마운트다.

```
# 버전당 한 줄. 최고 버전 = 암호화용, 전 버전 = 복호화용 (KEY_VER 롤링과 대응)
v1=Base64(32바이트 무작위)
v2=Base64(32바이트 무작위)
```

| 환경 | 위치 |
|---|---|
| 온프렘/VM | 배포 디렉터리 **밖** 고정 경로 (`/etc/{app}/crypto.keys`). 소유=서비스 계정, 권한 600 |
| Docker | secret → `/run/secrets/crypto_keys` 마운트. 이미지에 굽지 않는다 |
| Kubernetes | Secret 을 **볼륨 마운트** (env 주입 아님). etcd encryption at rest 권장 |

- 금지 장소: git · 이미지 레이어 · 로그 · CI(Jenkins) 변수
- 기동 시 키 **지문**(해시 앞자리)만 로그에 남긴다 — "지금 어떤 키로 도는지" 대조용
- 환경변수 대비 실익: 프로세스 환경에 뜨지 않아 자식 프로세스 상속·덤프 노출이 없고,
  파일 재읽기로 **재기동 없이 새 키 버전 추가**가 가능하다
- **분실 대비는 기술이 아니라 절차다.** 이 파일 내용이 백업 대상 — 생성 시 2인 분리 보관
  또는 조직 비밀 관리 시스템에 이중 백업. 키를 잃으면 PII 전체가 영구 복호 불가다

#### 롤링·재암호화

| 항목 | 방침 |
|---|---|
| 롤링 | 암호문에 키 버전 프리픽스(`v1:`) + `SYS_PII_VAULT.KEY_VER`. 복호화는 버전별 키, 암호화는 최신 키 |
| 재암호화 | 키 버전별 배치 (온라인 무중단) |

## 8. 보안 헤더 / 기타

| 항목 | 설정 |
|---|---|
| 쿠키 | `HttpOnly`, `Secure`(운영), `SameSite=Lax` |
| CSP | `default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:`. **인라인 스크립트는 그대로 금지**이고, 인라인 **스타일**과 `data:` **이미지**만 연다 — §8.2 |
| 기타 헤더 | `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY` |
| CORS | 동일 오리진 배포이므로 **비활성**. 개발 시에만 Vite 프록시로 우회(→ [25](../../build-deploy.md) §4) |
| Actuator | 운영에서 `health`, `info` 만. 별도 포트 + 인증 |
| 에러 응답 | 스택트레이스 노출 금지. `traceId` 만 반환하고 상세는 에러 로그 테이블에 |
| **접속 IP** | `getRemoteAddr()` 만 본다. `X-Forwarded-For` 를 손으로 읽지 않는다 — §8.1 |

### 8.2 CSP 는 `style-src` 와 `img-src` 만 연다

**`default-src 'self'` 하나로는 화면이 뜨지 않았다**(2026-08-30 실측 — 단일 JAR 로 띄우니
로그인 화면부터 스타일 없이 떴다). AntD 와 AG Grid 는 테마·폭·색을 **런타임에 인라인
스타일로** 넣는데, 명시하지 않은 `style-src` 가 `default-src` 로 폴백하면 **그 전부가
차단된다.**

**개발에서는 보이지 않는다.** Vite 가 `index.html` 을 주고 `/api` 만 프록시하므로 이 헤더를
만나지 않는다([25](../../build-deploy.md) §4) — **단일 JAR 배포에서만** 나타나고, 그래서
프론트를 임베드해 띄우기 전까지 아무도 모른다. 고친 뒤의 확인도 **반드시 단일 JAR 로**
한다.

#### 같은 폴백에 아이콘도 걸려 있었다 (2026-08-30 — `CODE_MGMT` 확인 중)

AG Grid 는 자기 아이콘을 파일이 아니라 CSS 안의
`background-image: url("data:image/svg+xml,…")` 로 넣는다. 명시하지 않은 `img-src` 가
`default-src 'self'` 로 폴백하면 **`data:` 는 `'self'` 가 아니므로 차단**되고, 판의 정렬
화살표·스피너 자리가 **조용히 빈다.**

**드러나기 어려운 모양이었다.** 우리 아이콘(`@ant-design/icons`)은 DOM 의 `<svg>`
엘리먼트라 애초에 이미지가 아니어서 멀쩡했다 — 그래서 *전부 안 보이는* 것이 아니라
*일부만 안 보이는* 상태였고, 그것은 **판의 스타일로 읽힌다.** 콘솔을 봐야 걸린다.

| 지시자 | 여는 것 | 내주는 것 |
|---|---|---|
| `style-src` | `'unsafe-inline'` | 주입된 마크업의 **시각적 변조**(가짜 오버레이). 스크립트 실행은 아니다 |
| `img-src` | `data:` | **없다시피 하다** — SVG 안의 스크립트는 `<img>`·`background-image` 문맥에서 돌지 않는다 |
| `script-src` | **열지 않는다** | `default-src` 를 따라 <b>인라인 스크립트가 막힌다</b> — XSS 의 주된 경로가 그쪽이다 |
| `connect-src`·`frame-src` | 〃 | 〃 |

**`data:` 를 `default-src` 에 넣지 않는 것이 요점이다.** 거기 넣으면 `script-src` 까지 함께
열려 **`data:text/javascript` 가 실행 가능해진다** — 고치려던 것은 아이콘 하나인데 여는 것은
XSS 의 주된 경로가 된다. **지시자마다 최소로 연다.**

**nonce 를 고르지 않았다.** AntD 의 `ConfigProvider csp={{nonce}}` 와 AG Grid 의 nonce 를
함께 쓰면 `'unsafe-inline'` 없이 닫을 수 있지만, 대가는 **요청마다 nonce 를 만들어
`index.html` 에 심는 것**이다 — 지금 정적 리소스로 나가는 그 파일을 서버가 렌더해야 하고
캐시 정책과 서빙 경로가 함께 바뀐다([ADR-0001](../../../records/adr/0001-repository-layout.md) 의
단일 JAR 배포가 전제한 모양이 아니다). **`img-src` 에는 해당하지 않는다** — nonce 는
인라인 스크립트·스타일의 장치이고 `data:` 이미지에는 걸 자리가 없다.

> **무엇을 내주는지 분명히 해 둔다.** 인라인 스타일이 허용되면 주입된 마크업이 화면을
> **시각적으로 변조**할 수 있다(가짜 오버레이·클릭재킹 유사 효과). XSS 의 주된 경로인
> 스크립트 실행은 여전히 막히며, `X-Frame-Options: DENY` 도 그대로다. nonce 로 닫는 것은
> **정적 서빙을 바꿀 때** 함께 본다.

### 8.1 `X-Forwarded-For` 를 손으로 읽지 않는다

**그 헤더는 클라이언트가 아무 값이나 넣을 수 있다**(2026-08-30 — 손으로 읽던 코드를 걷어냈다).
첫 값을 그대로 쓰면 아무나 `X-Forwarded-For: 1.2.3.4` 를 보내 **로그인 이력의 IP 를 위조**할
수 있다. 그 이력은 *누가 어디서 들어왔나* 에 답하려고 남기는 것이라, 위조되면 남길 이유가
없어진다.

**AUTH-08 이 서는 날에는 인증 우회가 된다.** 접속 IP 허용([41](../../../knowledge/sys/user-role.md) §7)이 같은 값을 보게 되면
헤더 한 줄로 허용 목록을 통과한다 — 지금은 그 검사가 없어 **감사 기록의 문제로만** 남아
있지만, 그때 고치는 것은 늦다.

**판이 이미 그 일을 안전하게 한다.**

| 설정 | 무엇을 하나 |
|---|---|
| `server.forward-headers-strategy: none` (**기본**) | 헤더를 무시한다. 직접 노출·로컬 |
| `server.forward-headers-strategy: native` | 톰캣 `RemoteIpValve` — **바로 앞 홉이 신뢰하는 프록시일 때만** 헤더를 반영해 `getRemoteAddr()` 를 바꾼다 |
| `server.tomcat.remoteip.internal-proxies` | 그 신뢰 목록. 배포지의 LB·프록시 대역을 적는다 |

애플리케이션은 `getRemoteAddr()` **하나만** 본다. 프록시 뒤에 두면서 설정을 켜지 않으면
**프록시의 IP 가 남는데**, 그것은 거짓이 아니라 *덜 쓸모 있는 사실* 이며 위조된 클라이언트
IP 보다 낫다.

> **로컬에서 `0:0:0:0:0:0:0:1` 로 보이는 것은 IPv6 루프백(`::1`)이다** — 톰캣이 축약하지 않고
> 편 형태로 준다. 정상이다.

#### 8.1.1 헤더 목록을 순회하는 옛 방식을 쓰지 않는다

자바 진영에 오래 돌아다닌 유틸이 있다 — `X-Forwarded-For` · `Proxy-Client-IP` ·
`WL-Proxy-Client-IP` · `HTTP_X_FORWARDED_FOR` … 를 차례로 훑어 처음 값이 있는 것을 쓰는
방식이다. **그것을 되살리지 않는다.**

| 왜 | |
|---|---|
| **전부 클라이언트가 넣을 수 있다** | 열넷을 뒤지든 하나를 읽든 같다. 늘어나는 것은 **위조 경로의 수**뿐이다 |
| **`HTTP_*` 는 헤더 이름이 아니다** | CGI·PHP 의 `$_SERVER` 키다. `getHeader("HTTP_X_FORWARDED_FOR")` 는 **그런 이름의 헤더**를 찾는 것이라 어떤 프록시도 보내지 않는다 — 보내는 것은 공격자뿐이다 |
| **`REMOTE_ADDR` 도 헤더가 아니다** | 같은 이유. 진짜 값은 `getRemoteAddr()` 이며 헤더로 오지 않는다 |
| **`Via` 는 IP 가 아니다** | 프록시의 신원(`1.1 proxy.example.com`)이다. 걸리면 IP 자리에 그것이 남는다 |
| **`split(",")[0]` 이 가장 위험한 값이다** | 프록시는 뒤에 덧붙인다 — 맨 앞은 **최초 발신자가 적어 넣은 것**이다 |

**물음이 "어느 헤더인가" 가 아니라 "보낸 쪽을 믿는가" 다.** 헤더 목록으로는 후자에 답할 수
없다. 답하는 것은 **바로 앞 홉의 IP** 하나뿐이고, 그것은 클라이언트가 바꿀 수 없다 —
`internalProxies` 가 보는 값이 그것이다.

> **프록시가 `X-Real-IP` 만 붙인다면** 목록에 한 줄 더하는 대신 설정을 바꾼다 —
> `server.tomcat.remoteip.remote-ip-header: x-real-ip`. 신뢰 검사는 그대로 걸린 채다.
