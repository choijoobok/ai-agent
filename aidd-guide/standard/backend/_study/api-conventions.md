## 2. API 규약 — [21](./architecture.md) §6-1 의 상세

### 2.1 경로 — 계층 · 도메인 · 동작

```
/api/{계층}/{도메인}/{동작}
     public         user       getList
     common         batchSchedule   runNow
     service
```

| 마디 | 무엇 | 원본 |
|---|---|---|
| **계층** | `public` · `common` · `service` **셋뿐** — 그 밖의 `/api/**` 는 **무조건 403** | [23](./security-design.md) §4 |
| **도메인** | 애그리거트 하나 — [21](./architecture.md) §2 의 패키지와 같은 이름 | 소스 |
| **동작** | **접두가 액션을 정한다** — `get`·`search`·`find`·`retrieve`→`READ`, `save`·`insert`·`update`·`delete`→`SAVE`, `export`→`EXPORT`, 그 외 `EXECUTE` | [ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md) · [21](./architecture.md) §6-1.1 |

> **`export` 접두를 쓰는 API 는 아직 하나도 없다.** 엑셀의 두 갈래가 프론트 생성이라
> 서버 경로가 없기 때문이며([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md)), 그래서 그 화면들의 `EXPORT` 는 **메뉴가
> 선언한다**([ADR-0027](../../../records/adr/0027-menu-declared-export-action.md) · [42](../../../knowledge/sys/menu.md) §4). **접두 규칙은 그대로 살아 있다** — 세 번째 갈래
> (임의 API · 서버 POI)를 만들면 그때 발동한다.

- **버전 프리픽스가 없다** — 단일 배포라 구버전 클라이언트가 없다(설계 개요 §3-19)
- **`service` 계층은 고정 경로**다. 경로 변수·와일드카드 금지 — **식별자와 조건은 body** 다.
  인가 판정이 **경로 완전 일치**로 `SYS_API` 를 찾기 때문이다([23](./security-design.md) §4)
- **`service` 는 `POST` 하나로 통일한다** — 조회도 `POST` 다. 조건이 body 에 들어가고([54](../../frontend/_study/grid-column-contract.md) §4.1 의
  검색 폼 조건 전부), **쿼리스트링에 담으면 길이 상한과 인코딩에 걸린다.**
  REST 의 동사 매핑을 쓰지 않는 것은 **액션이 넷으로 닫혀 있기 때문**이다([23](./security-design.md) §4)

#### 2.1.1 `common` · `public` 도 같은 접두를 쓴다 (2026-09-02)

**인가 시드가 읽는 것은 `/api/service/**` 뿐이다**([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)) — 그래서 나머지 두 계층의 접두는
**기계가 아니라 사람을 위한 것**이다. 그렇다고 규칙 밖에 두면 실제로 이렇게 된다
(2026-09-02 실측): 즐겨찾기는 `add`·`remove`, 저장된 조건은 `save`·`delete`, 메뉴 통계는
`select`·`frequent`, 번들은 키가 `bundle` 인데 경로는 `getBundle` 이었다. **같은 일이 네 가지
이름으로 불렸다.**

| 무엇 | 접두 |
|---|---|
| 조회 | **`get*`** |
| 우리 테이블에 쓰는 것 | **`save*`** · **`delete*`** — 버튼 이름이 아니라 **컬럼을 쓰는가**가 기준이다([61](../../../../documents/screen/user/requirements.md) §3.4.1) |
| 그 밖의 동작 | **동작 이름 그대로** — `login` · `logout` · `heartbeat` · `changePassword`. `service` 라면 `EXECUTE` 로 떨어지는 자리다 |

**HTTP 메서드는 계층이 정한다.** `service` 는 전부 `POST`(위 §2.1), `common`·`public` 은
**조회에 `GET`** 을 쓴다 — 조건이 없거나 한둘이고 브라우저 캐시가 성립하는 자리다.
예외 둘을 명시한다:

| 예외 | 왜 |
|---|---|
| `POST /api/common/code/getList` | **본문으로 그룹 코드 목록을 보낸다.** 쿼리스트링에 담으면 길이 상한에 걸린다 — `service` 가 전부 `POST` 인 것과 같은 이유다 |
| `GET /api/common/progress/{jobId}` | **경로 변수형 조회.** 진행률은 초 단위로 폴링되며 `jobId` 가 곧 자원이다. `service` 의 *경로 변수 금지* 는 인가 판정이 경로 완전 일치이기 때문인데, 이 계층은 그 판정을 하지 않는다 |

### 2.2 표기는 **camelCase 단수**다 — [21](./architecture.md) §6-1.1 을 닫는다

그 절이 *"동작 마디의 표기(`getList` / `get-list`)는 미결이다"* 로 남겼고,
[21](./architecture.md) §6-1 은 도메인 마디를 *"케밥케이스 **복수형**"* 이라고 적었다.
**`60`~`65` 가 쓴 경로 열다섯이 전부 그것과 다르다.**

```
/api/service/accessLog/getList        /api/service/batchSchedule/runNow
/api/service/apiCatalog/getMenuList   /api/service/roleAuth/getAffectedUsers
/api/service/batchHistory/cancel      /api/service/user/exportExcel
```

**케밥·복수형이 하나도 없다.** 여섯 문서가 같은 방향으로 벗어났으면 규약이 틀린 것이다.

| | 채택 | 왜 |
|---|---|---|
| 도메인 | **camelCase 단수** — `batchSchedule` | **애그리거트 이름 그대로**다([21](./architecture.md) §2). 복수형은 *리소스 컬렉션*을 뜻하는 REST 관례인데 **여기는 리소스가 아니라 동작**이다 |
| 동작 | **camelCase** — `getList` | **접두 매칭이 한 겹 단순해진다.** `get-list` 면 접두가 `get` 인지 `get-` 인지 규칙이 늘고, `getList`·`get-list` 를 둘 다 받으면 시드가 갈린다 |
| 원본 | **소스의 메서드명** | 시드가 **생성물**이라([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)) 자바 메서드명이 그대로 경로가 되는 것이 **표기를 하나로 유지하는 유일한 방법**이다 |

> **[21](./architecture.md) §6-1 의 *케밥케이스 복수형* 을 고친다**(§6). 규약이 먼저 있었지만
> **화면 여섯이 실물을 냈고 실물이 일관됐다.**

### 2.3 봉투 — 성공도 실패도 감싼다

```jsonc
// 성공
{ "success": true,  "data": { … },  "traceId": "7f2a1c9e-…" }
// 실패
{ "success": false, "code": "err.duplicate-code",
  "message": "이미 등록된 코드입니다: USE_YN / Y", "traceId": "7f2a1c9e-…" }
```

| 키 | 언제 | 비고 |
|---|---|---|
| `success` | 언제나 | 프론트의 첫 분기 |
| `data` | 성공 | 목록이면 `PageResponse`(§3.9) |
| `code` | 실패 | **문자열 상수.** `SYS_LO_EXCEPTION.ERR_CD` 에 그대로 남는다([45](../../../knowledge/sys/logs.md) §4.2) |
| `message` | 실패 | **서버가 번역을 완성한다** — [21](./architecture.md) §6-1.2 |
| **`traceId`** | **언제나** | 성공에도 담는다 — 아래 |

**성공 응답에도 `traceId` 를 담는 이유** — 5xx 토스트만 그것을 쓰는 것이 아니다([24](../../frontend/_study/frontend-stack.md) §9).
*"저장은 됐다는데 값이 이상하다"* 는 문의에서 **성공한 요청을 사용 이력에서 찾아야 하고**,
그 열쇠가 `traceId` 다([64](../../../../documents/screen/log/access/requirements.md) §2.5). 담지 않으면 사용자가 **시각과 화면 이름으로만**
찾아온다.

| 상태 코드 | 언제 | 프론트 |
|---|---|---|
| 200 | 성공 | — |
| **400** | 검증 실패 · **조회조건 위반**(§4) | 폼이 필드별 오류를 표시([56](../../frontend/_study/grid-edit-validation.md) §3.3) |
| **401** | 세션 만료 | **재인증 모달** — 로그아웃하지 않는다(화면 흐름 §7.1) |
| **403** | 인가 거부 | 권한 없음 화면 또는 토스트. **`code` 가 세 갈래를 나른다**([23](./security-design.md) §4) |
| 500 | 그 밖 | 공통 에러 토스트 + `traceId` |

**400 의 본문에는 필드별 배열이 더 붙는다.**

```jsonc
{ "success": false, "code": "err.validation",
  "message": "입력값을 확인하세요",
  "fields": [ { "field": "cron", "message": "쿨다운(300초)이 크론 최소 간격(60초)보다 깁니다" },
              { "field": "lockMinIntervalSec", "message": "〃" } ],
  "traceId": "…" }
```

**같은 문구가 두 필드에 실린다** — [65](../../../../documents/screen/batch/schedule/requirements.md) §3.4 가 *"어느 쪽이 틀렸는지 서버가 말할 수
없다. 관계가 틀린 것"* 이라고 한 경우다. **`fields` 는 배열이므로 그것이 표현된다.**

### 2.4 헤더 넷

| 헤더 | 언제 | 원본 |
|---|---|---|
| **`X-Request-Id`** | **매 요청** — 쿼리 `_rid` 와 **이중 채널** | [29](../crosscutting.md) §3 · [24](../../frontend/_study/frontend-stack.md) §9 |
| **`X-Menu-Code`** | 매 요청. **메뉴 문맥 없으면 생략**하고 서버는 `NULL` 로 저장 | [21](./architecture.md) §6.3 · [64](../../../../documents/screen/log/access/requirements.md) §3.2.1 |
| `X-XSRF-TOKEN` | 매 요청 (axios 기본) | [24](../../frontend/_study/frontend-stack.md) §9 |
| `Accept-Language` | 매 요청 | 세션 언어가 우선이며 이것은 폴백 |

- **중복 방어는 쓰기만 받는다.** `X-Request-Id` 는 전 요청에 붙지만 `SYS_REQ_DEDUP` 선점은
  **`SAVE`·`EXECUTE` 에만** 건다 — 조회는 멱등이라 막을 것이 없고, 막으면 **새로고침이
  중복으로 걸린다**([29](../crosscutting.md))
- **`traceId` 와 `X-Request-Id` 는 같은 값이다**(설계 개요 §3-13). 응답의 `traceId` 를
  들고 온 사용자가 곧 그 요청을 특정한다

### 2.5 시간은 **오프셋 포함 ISO-8601** 이다 — 요청도 응답도

```
2026-08-28T09:14:02+09:00
```

- **서버가 현재시각을 SQL 로 구하지 않는다**([22](./db-portability.md) §4.5 — `SYSDATE`·`NOW()`·`GETDATE()` 금지).
  애플리케이션이 값을 주입하므로 **경계 판단이 한 곳**이다
- **조회조건의 날짜도 오프셋을 붙인다.** 화면은 로컬로 그리지만([64](../../../../documents/screen/log/access/requirements.md) §2.2 의 기간
  조건) 와이어에서 오프셋이 빠지면 **서버 타임존에 따라 하루가 밀린다**
- **날짜만 다루는 필드**(`date` · `precision: 'month'` — [54](../../frontend/_study/grid-column-contract.md) §4.5)는 `2026-08-28` ·
  `2026-08` 로 보낸다. **오프셋을 붙이지 않는다** — 시점이 아니라 달력 값이다

## 3. 조회 요청 (QRY-01)

### 3.0 조회는 **둘**이다 — 이 장은 그중 하나다

| | **고정형** | **동적형** — 이 장 |
|---|---|---|
| 사용자가 연산자를 바꾸나 | **아니다** | 그렇다 |
| 어디 | **디테일 그리드**([53](../../frontend/_study/grid-standard.md) §6.1) · 코드·콤보·트리 · 단건 조회 | **검색 폼([57](../../frontend/_study/search-form-contract.md))이 있는 마스터 그리드** |
| 요청 | **전용 `record`** — `{ "userId": "kim.jb" }` | 아래 봉투 |
| 화이트리스트 | **없다** | **필요하다**(§4) |
| 개수 | **대부분** | 화면당 **최대 하나** |

**화면에 검색 폼이 있으면 동적형, 없으면 고정형.** [53](../../frontend/_study/grid-standard.md) §1.1 이 조회조건 폼을
*화면에 하나*로 못 박았으므로 **동적형은 화면당 하나를 넘지 않는다** — 디테일 탭이
다섯이면 **고정형이 다섯, 동적형이 하나**다.

> **고정형이 기본인 이유는 편의가 아니라 보안이다.** 디테일을 동적 봉투로 태우면
> 부모 키 제약이 **클라이언트가 보낸 조건 하나**로 표현된다 — `conditions` 를 빈 배열로
> 보내면 **조건 없는 전체 조회**가 되어 남의 자식 행이 전부 나오고, `op` 를 `contains` 로
> 바꾸면 다른 사용자까지 걸린다. **`@NotBlank String userId` 는 그것을 표현할 수 없다.**
> [23](./security-design.md) §4 의 *deny by default* 와 같은 방향이며 — **표현할 수 없는 것은 공격할 수
> 없다.** 구현은 [34](../search.md) §2·§3.

### 3.1 봉투 — **동적형의**

```jsonc
{
  "conditions": [ { "field": "creDtm", "op": "between", "value": ["2026-08-27T00:00:00+09:00",
                                                                  "2026-08-28T23:59:59+09:00"] },
                  { "field": "userId",  "op": "eq",      "value": "kim.jb" },
                  { "field": "menuCd",  "op": "in",      "value": ["USER_MGMT", null] } ],
  "sorts":  [ { "field": "creDtm", "dir": "desc" } ],
  "page":   { "mode": "cursor", "size": 100, "cursor": "eyJ…" },
  "params": { "roleCd": "ROLE_X", "roleAsOf": "2026-08-28" }   // 화면 전용 — §3.1.1
}
```

**넷이다.** `conditions` · `sorts` · `page` · `params`.
**앞의 셋이 공통**이고 **`params` 만 화면마다 다르다** — 없는 화면이 대부분이다.

- **`conditions` 는 배열이고 전부 `AND` 다.** **`OR` 는 지금 열지 않는다** — 근거는
  *사례가 없다* 가 아니라 **비용**이다: 열면 **중첩 그룹**이 따라오고 그것은 와이어 ·
  화이트리스트 · 폼 UI · 저장된 조건([57](../../frontend/_study/search-form-contract.md) §5)을 **넷 다** 바꾼다.
  **흔한 형태는 파생이 덮는다** — *"거래처명 또는 사업자번호로"* 는 [63](../../../../documents/screen/code/requirements.md) §4.6 의
  *키·설명 한 칸* 과 같은 모양이며 **한 필드가 두 컬럼을 건다**(§3.5).
  **진짜 임의 `OR`(고급 검색)는 §7 미결**이다
- **같은 필드가 두 번 오지 않는다.** 오면 400 이다 — 범위는 `between` 이 받고, 다중은 `in` 이 받는다
- **빈 조건은 보내지 않는다.** 화면이 비운 칸은 배열에서 빠진다 — `value: null` 을 보내
  *"NULL 인 것을 찾아라"* 와 섞이지 않게 한다(§3.6). **예외는 `isNull` · `isNotNull` 뿐**이며
  그 둘은 **값이 없는 것이 정상**이다(§3.3)

#### 3.1.1 `params` — 봉투를 빠져나가는 문

**폼의 모든 칸이 `conditions` 로 가지는 않는다.** 조건 하나가 술어 하나가 되지 않는
필드가 있다.

| 폼 필드가 | 어디로 |
|---|---|
| 컬럼 하나에 연산자 하나 | **`conditions`** |
| 화면 값 **하나** → SQL 조각 **하나** (컬럼 조합 · `IN` 묶음 · `EXISTS`) | **`conditions`** + 스펙의 `.derived()`(§3.5) |
| **여러 칸이 합쳐져 조각 하나** | **`params`** |
| 다른 조건을 **수식**한다 (기준일 · 포함 플래그) | **`params`** |
| **술어가 아니다** (조인 전환 · `SELECT` 식 · 상관 서브쿼리의 인자) | **`params`** |

**경계는 하나다 — 파생은 값 하나가 들어가고 조각 하나가 나온다. 그 관계가 깨지면 `params`.**
`.derived()` 는 **자기 필드의 값만** 보므로 형제 칸을 읽을 수 없다(§3.5). *보유 역할* 이
`roleCd` 하나면 파생으로 족하고, 거기에 **기준일과 만료 포함 여부가 붙어 `EXISTS` 하나를
만들면** 그때부터 `params` 다.

**`params` 는 화이트리스트를 우회하는 문이 아니다.** 규칙 다섯이 막는다.

| | |
|---|---|
| **타입이 있다** | 화면 전용 `record` 이며 `@Valid` 다 — **열린 맵이 아니다** |
| **빌더에 들어가지 않는다** | 서비스 코드가 **이름으로 직접 읽는다.** §3.0 고정형과 같은 성질이라 화이트리스트도 인젝션 표면도 없다 |
| **컬럼을 지명할 수 없다** | `params` 의 값이 SQL 식별자가 되는 일은 없다 — 되면 그것이 곧 §4 우회다 |
| **정렬 대상이 아니다** | `sorts` 는 `conditions` 의 이름 공간만 본다(§3.7) |
| **함께 저장된다** | UX-07 이 저장하는 것은 **넷 전부**다. `params` 만 빠지면 복원이 반쪽이 된다 |

> **`conditions` 에 섞지 않는 이유가 [55](../../frontend/_study/grid-api-contract.md) §8 과 같다.** 그 절이 *"대상 행과 `params` 를
> 섞지 않는다 — 섞으면 서버가 **이 필드가 행의 것인가 파라미터인가를 이름으로 추측**하게
> 된다"* 고 적었다. 여기도 같다 — 섞으면 **빌더가 *이 조건을 `WHERE` 에 넣어야 하나* 를
> 이름으로 추측**하게 된다.

**어느 칸이 어디로 가는지는 [57](../../frontend/_study/search-form-contract.md) 이 필드마다 선언한다.** 기본은 `conditions` 이며,
`params` 로 뺄 때는 **키를 함께 적는다**(폼 필드명과 다를 수 있다). 서버 형태는
[34](../search.md) §4.6.

### 3.2 조건 하나 — `field` · `op` · `value`

| 키 | 무엇 |
|---|---|
| `field` | **논리 이름.** 화이트리스트가 이것으로 판정한다(§4). **컬럼명도 별칭도 아니다** — 아래 |
| `op` | **연산자 열셋 중 하나**(§3.3) |
| `value` | 스칼라 또는 배열. **타입은 `op` 와 필드 타입이 함께 정한다**(§3.4) |

#### `field` 를 컬럼·별칭으로 올리지 않는 이유 **넷**

조인이 있으면 **서버는** 별칭까지 알아야 한다 — `"D.DEPT_CD"` 같은 것이 필요하다(§5.2).
**그것을 와이어까지 올리면 넷을 잃는다.**

| | |
|---|---|
| **파생을 표현할 수 없다** | §3.5 의 계정 상태 · 결과 묶음 · `5xx` · `EXISTS` 는 **컬럼이 없다** |
| **별칭은 쿼리 하나의 사정** | 같은 필드가 목록 · 엑셀 · 카운트에서 다른 별칭을 가질 수 있고, **조인 순서를 바꾸면 바뀐다** |
| **저장된 조건이 무효화된다** | UX-07 은 조회조건을 **DB 에 남긴다.** 조인을 손보면 **사용자 데이터가 깨진다** |
| **스키마가 노출된다** | devtools 로 테이블 · 컬럼 · 조인 구조가 그대로 보인다 |

### 3.3 연산자 **열셋** — [60](../../../../documents/screen/_standalone/README.md) §11 을 닫는다

[60](../../../../documents/screen/_standalone/README.md) §2.2 가 후보 여덟(`=` `LIKE` `>` `>=` `<` `<=` `BETWEEN` `IN`)을 적고
*"화면별 필요를 모아 [72](./api-conventions.md) 가 확정한다"* 고 넘겼다.

> **2026-08-28 개정.** 처음에 **아홉**으로 닫으며 `endsWith` · `ne` · `isNull` 을
> *"사례 0"* 을 근거로 뺐다. **그 근거가 틀렸다** — 모수로 삼은 `60`~`65` 는 **시스템
> 관리 화면**이고 이 저장소는 **업무 도메인을 가리지 않는 베이스**다(설계 원칙).
> 지금 화면에 요구가 없다는 것은 **템플릿을 쓰는 업무 화면에 없다는 뜻이 아니다**
> ([57](../../frontend/_study/search-form-contract.md) §1.1). 넷을 되돌려 **열셋**로 연다.

| `op` | SQL | `value` | 타입 |
|---|---|---|---|
| **`eq`** | `= ?` | 스칼라 | 전부 |
| **`ne`** | `<> ?` — **`NULL` 처리는 아래** | 스칼라 | 전부 |
| **`in`** | `IN (…)` | 배열. **`null` 포함 가능**(§3.6) | 전부 |
| **`startsWith`** | `LIKE ? \|\| '%'` | 문자열 | 문자열 |
| **`contains`** | `LIKE '%' \|\| ? \|\| '%'` | 문자열 | 문자열 |
| **`endsWith`** | `LIKE '%' \|\| ?` | 문자열 | 문자열 |
| **`between`** | `>= ? AND <= ?` | **2원소 배열. 한쪽이 `null` 이면 단측** | 숫자 · 날짜 |
| **`gt`** · **`gte`** · **`lt`** · **`lte`** | `> ?` · `>= ?` · `< ?` · `<= ?` | 스칼라 | 숫자 · 날짜 |
| **`isNull`** | `IS NULL` | **없다** | 전부 |
| **`isNotNull`** | `IS NOT NULL` | **없다** | 전부 |

#### 부등호는 **넷 다** 둔다 — 사례가 없어도

둘만 두면 *"초과"* 를 표현할 방법이 없고, 화면이 **`gte` 에 값을 하나 더해 흉내 낸다.**
정수라면 맞지만 **날짜와 소수에서는 틀린다** — `ELAPSED_MS`([65](../../../../documents/screen/batch/schedule/requirements.md) §4.7)나 타임스탬프에
epsilon 을 더하는 것은 오답이며, **그 우회가 화면마다 다르게 구현된다.**
넷은 같은 SQL 모양이라 빌더에 분기가 늘지 않는다.

#### `endsWith` — **비용이 `contains` 와 같다**

처음에 *"인덱스를 못 탄다"* 를 근거로 뺐는데 **`contains` 도 못 탄다.** 둘 다
`LIKE '%…'` 라 **선행 와일드카드가 인덱스를 무력화하는 정도가 동일**하므로,
`contains` 를 열어 두고 `endsWith` 만 막는 것은 **비용이 아니라 취향**이었다.

**업무 화면에서는 흔하다** — 전화번호 뒷자리 · 계좌 끝자리 · 파일 확장자 · 사업자번호
끝 다섯. `contains` 가 **더 넓게 찾아 주긴 하지만**, 사용자는 그 여분을 눈으로 걸러야 한다.

#### `ne` — **`in` 이 덮지 못한다**

처음 근거는 *"`in` 으로 맞는 것을 고르게 하는 편이 낫다"* 였다. **정의역이 작고 열거
가능할 때만 맞는 말**이다 — 코드 필드는 그렇지만 **`text` 필드는 아니다.**
*"`system` 계정 제외"* · *"본사 제외"* 를 `in` 으로 쓰려면 **나머지 전부를 열거**해야 한다.

*"부정 조건 UI 가 혼란스럽다"* 는 근거도 **연산자 셀렉터가 생기며 사라졌다**([57](../../frontend/_study/search-form-contract.md) §3.4) —
목록의 한 항목이 *같지 않음* 일 뿐이다.

##### `ne` 는 **`NULL` 을 포함한다**

```sql
-- 표준 SQL: NULL 인 행이 빠진다. 4벤더 전부 같다
WHERE DEPT_CD <> 'HQ'
-- 이 프로토콜: nullable 필드면 서버가 이렇게 편다
WHERE (DEPT_CD <> 'HQ' OR DEPT_CD IS NULL)
```

**사용자가 *"HQ 가 아닌 것"* 이라 말할 때 부서 없는 행을 빼겠다는 뜻이 아니다.**
표준 그대로 두면 **행이 조용히 사라지고** 그 이유를 화면에서 알 수 없다 —
[22](./db-portability.md) §4.5 의 `NULL` 취급이 벤더 문제가 아니라 **의미 문제**로 나타나는 자리다.
`nullable` 이 아닌 필드에서는 `OR` 를 붙이지 않는다(화이트리스트가 안다 — §4.1).

#### `isNull` · `isNotNull` — **값을 받지 않는 연산자 둘**

처음에 *"실제 사례가 `메뉴 목록 + 없음` 이라 `in` 과 함께 쓰였다"* 를 근거로 뺐다.
**그 사례는 여전히 `in` + `null` 이 맞다**(§3.6) — 목록에서 고르는 중에 *(없음)* 도
고르는 것이라 조건이 하나다. **그러나 그것이 덮지 못하는 것이 있다.**

| | |
|---|---|
| `in` + `null` 이 덮는 것 | *"이 목록 중 하나 **또는** 없음"* — 정의역이 열거 가능할 때 |
| **덮지 못하는 것** | *"**값이 있는 것만**"* — `isNotNull` 은 `in` 으로 표현할 방법이 아예 없다. *"미처리 건"* · *"종료일이 빈 계약"* 이 그것이다 |

- **`value` 를 보내지 않는다.** 있으면 400 이다 — 무시하면 *"값을 넣었는데 안 걸린다"* 가 된다
- **§3.1 의 *빈 조건은 보내지 않는다* 에 대한 유일한 예외**다. 값이 없는 것이 정상이므로
  **`op` 만으로 조건이 성립한다**
- **빈 문자열을 저장하지 않는 것이 전제다**([22](./db-portability.md) §4.5 — *Oracle 은 `''` = NULL*).
  전제가 깨지면 같은 데이터가 벤더마다 다르게 걸린다

#### 뺀 것은 하나 — **`LIKE` 를 한 연산자로 두는 것**

| 뺀 것 | 왜 |
|---|---|
| **`LIKE`(와일드카드를 값에 담는 것)** | **셋으로 갈랐다.** 하나로 두면 **화면마다 와일드카드를 어디 붙일지 정하게 되고**, 값에 `%` 를 넣게 되어 **이스케이프가 화면의 일**이 된다. `startsWith` 는 인덱스를 타고 나머지 둘은 못 타므로 **프로토콜이 구분해야 화면이 그것을 알 수 있다** |

**이것은 *사례가 없어서* 가 아니라 *틀린 결과와 이스케이프 책임* 이 근거다** — [57](../../frontend/_study/search-form-contract.md) §1.1 의 셋 중 첫째다.

- **`%` 와 `_` 는 서버가 이스케이프한다.** 값에 그것이 들어오면 리터럴로 취급하며
  `ESCAPE` 절을 붙인다 — **4벤더 전부 지원**한다. 화면이 와일드카드를 아는 일이 없다
- **`LIKE` 셋은 대소문자를 가리지 않는다**(2026-08-30 — 구현이 뒤집었다). 아래 참조
- **`eq` · `ne` · `in` 은 가린다** — 코드값·ID 를 맞추는 자리이며, 무시하면 **서로 다른
  두 키가 같아진다**

> **처음에는 *정규화하지 않는다* 였다.** [22](./db-portability.md) §4.5 의 *"MySQL 기본 콜레이션은 대소문자
> 무시"* 를 근거로 *"벤더마다 다르며 프로토콜이 정할 일이 아니다"* 라고 적었는데,
> **그 문장이 스스로 문제를 말하고 있었다** — 벤더마다 다르면 **같은 조건이 MySQL 에서는
> 걸리고 PostgreSQL 에서는 안 걸린다.** [22](./db-portability.md) §1 이 내건 *무수정 기동* 은 기동이 되는
> 것이 아니라 **같은 답이 나오는 것**이다.
>
> **그래서 애플리케이션이 정규화한다** — 원래 문장의 뒷부분이 그것이었고, 지금 그 주체가
> 화면이 아니라 **서버의 `FieldSpec.like`** 한 곳이다.
>
> | | |
> |---|---|
> | 어디까지 | `startsWith` · `contains` · `endsWith` **셋뿐** — 사람이 *기억나는 대로 치는* 검색이다 |
> | 어떻게 | `LOWER(col) LIKE LOWER(?)`. QueryDSL 의 `likeIgnoreCase` 이며 **4벤더 전부 지원**한다 |
> | **대가** | **`startsWith` 가 인덱스를 못 탄다.** 컬럼에 함수가 걸리기 때문이며, 이 절이 셋을 가른 이유([위](#))가 절반 무너진다 |
> | 그 대가를 받는 이유 | 페이징이 결과를 자르므로 느려도 끝나지만, **틀린 결과는 끝나지 않는다.** 필요한 테이블에는 함수 기반 인덱스를 만든다 — 문법이 벤더마다 다르므로 [22](./db-portability.md) §4 의 대상이다 |
- **화면이 열셋을 다 열 의무는 없다** — [57](../../frontend/_study/search-form-contract.md) §3.4 의 `ops` 가 좁히며 **근거는 성능뿐**이다

### 3.4 **연산자가 타입을 제한한다** — 필드마다 선언하지 않는다

[10](../../../knowledge/features.md) §J 가 QRY-01 의 비고에 *"연산자가 허용 타입을 선언"* 이라고 적었다.
**그 방향이 맞다** — 반대로 하면 필드마다 허용 연산자를 적어야 하고 그것이 곧 미러링이다(§4.1).

| `op` | 받는 타입 | `value` |
|---|---|---|
| `eq` · `ne` · `in` | **전부** | 있다 |
| `startsWith` · `contains` · `endsWith` | **문자열만** | 있다 |
| `between` · `gt` · `gte` · `lt` · `lte` | **숫자 · 날짜 계열만** | 있다 |
| **`isNull` · `isNotNull`** | **전부** | **없다** — 있으면 400 |

- **위반은 400 이다.** `startsWith` 를 `number` 필드에 걸면 조회가 일어나지 않는다
- **필드의 타입은 DTO 가 안다**(§4.1). 그래서 **필드별 선언이 없어도 판정이 된다** —
  화이트리스트가 *"이 필드가 존재하는가"* 만 보면 나머지는 타입에서 나온다
- **`boolean` 에 `eq` 만 쓰이는 것은 규칙이 아니라 결과**다. `ynFlag` 는 문자열 `Y`/`N` 이라
  ([22](./db-portability.md) §4.3) `in` 도 성립한다

> **문자열에 부등호를 여는 문이 하나 있다**(2026-09-02 — [68](../../../playbook/INDEX.md) §3.3 이 요구했다). 스펙이
> 컬럼에 **`ordered()`** 를 붙이면 그 칸은 `between`·`gt`·`gte`·`lt`·`lte` 를 받는다.
>
> **타입이 아니라 선언이 근거다.** 자바 타입만 보면 `ORD_NM` 과 `DLVR_YM` 이 같은
> `String` 이고, 앞의 것에 범위를 열면 *가로 이상 나중* 같은 조건이 성립해 **말이 되지
> 않는 결과가 조용히 나온다**. *"이 문자열의 사전순이 이 값의 시간순이다"* 는 컬럼을 아는
> 자리에서만 할 수 있는 말이며([48](../../../playbook/INDEX.md) §4.2 의 `202608`), 그래서 스펙이 한다.
>
> **이 절의 첫 판은 그 자리를 파생 필드로 미뤘다** — *"그런 컬럼이 실제로 생기면
> `.derived()` 가 받는 자리"*. **파생의 자바 타입도 `String`** 이라 거기서도 똑같이
> 막혔고, 열어 준 적 없는 문을 가리키고 있었다.

### 3.5 파생 조건 — **와이어의 문제가 아니었다**

화면 값과 SQL 컬럼이 1:1 이 아닌 사례가 넷 나왔다.

| 화면 | 조건 | 실제 SQL |
|---|---|---|
| [61](../../../../documents/screen/user/requirements.md) §3.3 | 계정 상태 `IN (정상, 잠김)` | `USE_YN` · 기간 · `LOCK_YN` · `DORMANT_YN` **네 컬럼의 조합** |
| [64](../../../../documents/screen/log/access/requirements.md) §4.6 | 결과 묶음 `= 실패만` | `LOGIN_RSLT_CD IN (FAIL_* 아홉)` |
| [64](../../../../documents/screen/log/access/requirements.md) §5.6 | 상태 `= 5xx 만` | `HTTP_STAT BETWEEN 500 AND 599` |
| [65](../../../../documents/screen/batch/schedule/requirements.md) §4.7 | 결과 묶음 `= 실패만` | `RSLT_CD IN (FAIL, CANCELED)` |
| [61](../../../../documents/screen/user/requirements.md) §3.3 | 보유 역할 `= ROLE_X` | **`EXISTS` 서브쿼리** — `SYS_USER_ROLE` |

**프로토콜에 새 것이 필요 없다.** 화면은 평범하게 보낸다.

```jsonc
{ "field": "status", "op": "in", "value": ["NORMAL", "LOCKED"] }
```

**번역은 화이트리스트가 갖는다** — `status` 는 DTO 필드이되 **컬럼이 아니고**, 빌더가 그것을
네 컬럼의 조건으로 편다(§5.1). 즉 **파생 조건은 와이어의 문제가 아니라 화이트리스트의
문제**였다.

| 그래서 규칙 둘 | |
|---|---|
| **`field` 는 컬럼명이 아니다** | **논리 이름**이며, 컬럼과 1:1 일 의무가 없다(§3.2) |
| **파생 필드는 정렬 대상이 아니다** | [54](../../frontend/_study/grid-column-contract.md) §3 이 *"파생 컬럼은 SQL `ORDER BY` 대상이 아니다"* 라고 이미 적었다. **화이트리스트가 그것을 안다**(§4.1) — `sorts` 에 오면 400 |

> **`OR` 를 열지 않은 이유가 여기 있다**(§3.1). 위 넷은 전부 내부적으로 `OR` 이거나
> 컬럼 조합인데, **그것을 클라이언트가 조립하게 하면** 화면이 테이블 구조를 알게 된다.
> 서버가 이름 하나를 받아 펴는 편이 **화면과 스키마를 떼어 놓는다.**

### 3.6 `null` · 단위 · 조건부 — 셋을 가른다

| 무엇 | 어디서 | 프로토콜은 |
|---|---|---|
| **`IS NULL`** | [64](../../../../documents/screen/log/access/requirements.md) §3.2.1 *메뉴 없음* 체크박스 | **`in` 의 배열에 `null` 을 넣는다** → `IN (…) OR col IS NULL`. **필드 전체에 존재만 물으면 `isNull`**(§3.3) |
| **단위 변환** | [65](../../../../documents/screen/batch/schedule/requirements.md) §4.7 입력은 초, 저장은 ms | **와이어는 언제나 저장 단위.** 변환은 화면이 한다 |
| **조건부 필수** | [64](../../../../documents/screen/log/access/requirements.md) §2.2 추적 ID 를 넣으면 기간이 선택 | **와이어에 나타나지 않는다** — 조건이 안 올 뿐이다 |

- **`isNull` 과 `in` + `null` 은 다른 물건이다**(§3.3). *"메뉴 목록 중 하나 **또는** 없음"* 은
  **조건 하나**라 `in` 이 맞고, *"메뉴가 없는 것만"* · *"있는 것만"* 은 **`isNull` · `isNotNull`**
  이다. 둘을 한 필드에 함께 쓰면 §3.1 의 *"같은 필드는 한 번"* 에 걸린다 — **셋 중 하나만 고른다**
- **단위를 와이어가 알면 규칙이 두 곳에 생긴다.** 서버가 *"이 필드는 초로 온다"* 를 알아야
  하면 [57](../../frontend/_study/search-form-contract.md) 의 선언과 서버가 어긋날 수 있다 — **저장 단위 하나**로 닫는다
- **조건부 필수는 [57](../../frontend/_study/search-form-contract.md) 과 서버 검증 둘 다**가 본다([56](../../frontend/_study/grid-edit-validation.md) §3.4 와 같은 규칙).
  프로토콜은 그것을 표현하지 않는다 — **표현할 것이 없다**

### 3.7 정렬 — 배열이고, **tie-breaker 는 서버가 붙인다**

```jsonc
"sorts": [ { "field": "elapsedMs", "dir": "desc" } ]
```

[54](../../frontend/_study/grid-column-contract.md) §3 이 정한 것을 그대로 받는다.

| | |
|---|---|
| **처음부터 배열** | 기본이 원소 하나일 뿐이다. 다중 정렬은 화면이 `multiSort` 로 켠다([54](../../frontend/_study/grid-column-contract.md) §3) |
| **비어 있으면** | 서버의 **기본 정렬**을 쓴다 — 화면이 선언한 것이 아니라 **API 가 가진 것**이다 |
| **`dir`** | `asc` · `desc` 둘뿐 |
| **tie-breaker** | **클라이언트가 보내지 않는다.** 서버가 `ORDER BY {요청} , {PK}` 로 **언제나 붙인다** |

**tie-breaker 를 서버가 붙이는 것이 규칙인 이유** — [22](./db-portability.md) §4.5 가 *"NULL 정렬 순서가
벤더별로 다름. `ORDER BY` 에 **항상** 명시적 tie-breaker(PK) 추가"* 라고 정했다.
클라이언트에 맡기면 **빠뜨린 화면에서만 페이징이 흔들리고**, 그 증상은
*"2페이지에 1페이지 행이 또 있다"* 라 원인을 짐작하기 어렵다. **커서형에서는 곧바로 깨진다**(§3.8).

- **파생 필드는 `sorts` 에 올 수 없다**(§3.5) — 400
- **`params` 의 키도 올 수 없다**(§3.1.1) — 이름 공간이 다르다. 400
- **`nclob` 컬럼도 올 수 없다.** Oracle 이 `CLOB` 을 `ORDER BY` 에 쓰지 못한다([54](../../frontend/_study/grid-column-contract.md) §5.5) —
  **화이트리스트가 막는다**(§4.1)

### 3.8 페이징 — 모드 **셋**. **화면이 선언하지 않는다** ([64](../../../../documents/screen/log/access/requirements.md) §7 을 닫는다)

**모드는 엔드포인트가 정하고 응답이 나른다.** 요청에도 화면 선언에도 없다.

```jsonc
// 요청 — 모드가 없다. 첫 장은 언제나 이 모양이다
"page": { "page": 0, "size": 20 }
"page": { "size": 100, "cursor": "eyJ…" }    // 다음 장 — 커서는 앞 응답이 준 것

// 응답이 모드를 말한다 (§3.9)
"data": { "mode": "offset", … }
```

| 모드 | 언제 | 총 건수 | 정렬 |
|---|---|---|---|
| **`offset`**(기본) | 대부분 | **센다** — `COUNT` 가 한 번 더 나간다 | **서버** |
| **`cursor`** | **대용량 이력** — [64](../../../../documents/screen/log/access/requirements.md) §2.3 | **세지 않는다** | **서버** · 한 컬럼 |
| **`all`** | **전량이 작고 페이징이 무의미한 화면** | **`COUNT` 없이** 배열 길이 | **클라이언트** |

> **`cursor` 가 섰다**(2026-08-30 — 이력 슬라이스). 첫 사용처가 `ACCESS_LOG` 이며
> ([64](../../../../documents/screen/log/access/requirements.md) §2.3) 셋이 다 돈다. 토큰은 `CursorToken`, `WHERE` 조립은 `CursorSupport`,
> 응답은 `Built.respondCursor` 다.
>
> **토큰이 다섯 마디다** — `field | dir | backward | value | pk`. 앞의 둘이 *정렬이 바뀌면
> 무효* 를 집행하고(값만 담으면 바뀐 정렬에 옛 기준점이 먹혀 **결과가 조용히 틀린다**),
> `backward` 가 `‹ 이전` 을 같은 형식으로 나른다 — 화면은 두 방향을 구분하지 않고 받은 것을
> 되돌려준다.
>
> **실측에서 잡은 것 하나**(2026-08-30). 튜플 비교를 `path.lt(value)` 로 쓰려면
> `ComparableExpression` 캐스팅이 필요한데 **숫자 경로가 그 타입이 아니다** —
> `NumberExpression` 은 `ComparableExpressionBase` 를 직접 상속한다. 정렬 키(시각)는
> 통과하고 **PK 만 걸려 커서가 전부 400** 이었다. 지금은 `Ops.LT`·`Ops.GT`·`Ops.EQ` 로
> 조립한다 — 연산자는 경로의 자바 타입을 묻지 않는다.

#### 화면이 선언하지 않는 이유 — **미러링이기 때문이다**

**페이징 여부는 이미 서버 소스가 정한다.** 리포지터리가 `Pageable` 을 받는지, 커서
조건을 붙이는지, 전량을 뽑는지가 **곧 모드**다. 그것을 화면이 한 번 더 적으면
**같은 사실이 두 곳에 생기고, 어긋날 때 어느 쪽이 맞는지 알 수 없다** —
§4.1 이 `PARAM_TYPE_CD`([46](../../../knowledge/sys/batch.md) §5.2) · `MIN_VAL`/`MAX_VAL`([43](../../../knowledge/sys/code.md) §6.2) ·
DTO 리플렉션에 대해 내린 것과 **같은 판단**이다.

**[53](../../frontend/_study/grid-standard.md) §2.3 의 `countMode` 도, 이 문서가 한때 제안한 `pageMode` 도 폐기한다**(§6).
푸터가 무엇을 그릴지는 **응답을 보고 정한다.**

| 응답의 `mode` | 푸터([53](../../frontend/_study/grid-standard.md) §2.3) | 헤더 클릭 |
|---|---|---|
| `offset` | 총 건수 · **번호 네비** · 사이즈 콤보 | **재조회** |
| `cursor` | `N건 조회됨` · **`‹ 이전 · 다음 ›`** | **재조회** · 단일 정렬만 |
| `all` | **건수만** — 네비도 사이즈 콤보도 없다 | **즉시 정렬** |

#### `all` — 전량을 한 번에 주고, 정렬과 필터를 **둘 다 클라이언트가** 한다

**페이징이 없으면 정렬을 서버가 할 이유도 없다.** [54](../../frontend/_study/grid-column-contract.md) §3 이 정렬을 서버로 보낸
근거는 *"현재 페이지만 정렬하면 전체에서 가장 큰 값을 못 준다"* 인데, **페이지가 없으면
그 근거가 성립하지 않는다.** 헤더 클릭에 재조회가 붙지 않으므로 **편집 중에도 정렬할 수
있다**([53](../../frontend/_study/grid-standard.md) §3.1).

- **첫 사례가 이미 있다** — [62](../../../../documents/screen/menu/requirements.md) §4.2.2 의 메뉴 트리가 *"페이징이 없으므로 푸터가
  한 칸"* 이라고 적었다. **그것이 이 모드다**
- 엑셀 드롭다운이 **한 항목**이 된다 — *현재 페이지* 와 *전체* 가 같다(〃)
- `sorts` 를 **보내지 않는다.** 서버는 자기 기본 정렬로 준다
- **상한을 건다.** 서버가 `상한 + 1` 건을 읽어 넘치면 **에러다** — 조용히 자르면 *전량* 이
  거짓말이 된다([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) 가 엑셀 상한에서 쓴 것과 같은 수법). 값과 대상은 §7

#### 판정은 **총 페이지 수가 1인가** 가 아니라 **모드가 무엇인가** 다

*"결과가 한 페이지로 끝났으면 클라이언트가 정렬하자"* 는 **거의 맞지만 한 곳에서 틀린다.**

| | |
|---|---|
| **맞는 부분** | 판정을 화면 선언이 아니라 **응답에서** 읽는다. 소스가 이미 아는 것을 화면이 적을 이유가 없다 |
| **틀리는 부분** | **`totalPages == 1`** 로 판정하면 **`offset` 그리드가 데이터 양에 따라 다르게 동작한다** |

18건이면 즉시 정렬되고 22건이면 재조회 + *"편집을 버릴까요"* 다. **같은 화면이 어제와
오늘 다르게 동작하고**, 사용자는 *"정렬해도 편집이 안 날아간다"* 를 배운 뒤 **데이터가
늘어난 날 작업을 잃는다.** 순서도 바뀐다 — 클라이언트 비교와 서버 `ORDER BY` 는
tie-breaker · 콜레이션([22](./db-portability.md) §4.5) · `NULL` 위치 · 표시값에서 어긋나므로
([54](../../frontend/_study/grid-column-contract.md) §3) **임계값을 넘는 순간 정렬 결과가 달라진다.**

**`mode` 로 판정하면 사라진다.** `all` 은 건수와 무관하게 언제나 클라이언트,
`offset` 은 1페이지여도 언제나 서버다 — **한 페이지를 다시 읽는 비용은 이미 인덱스를
탄 조건의 재실행일 뿐**이고, 그 대가로 **동작이 데이터 양에 흔들리지 않는다.**

#### 커서 토큰 — 불투명하고, 유효기간이 없다

| | |
|---|---|
| 무엇이 들어 있나 | **정렬 키의 마지막 행 값 + PK** 를 묶어 base64 |
| **불투명한 이유** | 클라이언트가 해석하면 **정렬 키가 노출**되고, 형태를 바꿀 때 프론트가 깨진다 |
| **유효기간이 없는 이유** | **서버가 상태를 갖지 않는다.** 토큰이 곧 `WHERE (creDtm, seq) < (?, ?)` 이며 다중화에서도 안전하다 |
| 정렬이 바뀌면 | **무효다.** 화면이 커서를 버리고 첫 장으로 간다 — [54](../../frontend/_study/grid-column-contract.md) §3 의 *"정렬이 바뀌면 페이지를 1로"* 가 커서형에서는 **선택이 아니라 필수**다 |
| 다음 장 판정 | **`size + 1` 건을 읽는다.** [ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) 가 엑셀 상한을 *"상한 + 1 건까지만 조회"* 로 판정한 것과 같은 수법 |

- **커서형은 정렬을 한 컬럼으로 좁힌다**([64](../../../../documents/screen/log/access/requirements.md) §2.3) — 기준점이 성립하려면 정렬 키가
  고정이어야 한다. **`sorts` 원소가 둘 이상이면 400**
- **뒤로 가기도 커서다.** `‹ 이전` 은 방향을 뒤집어 읽고 결과를 되집는다 — 화면은 두 토큰
  (`prev` · `next`)을 응답에서 받는다(§3.9)
- **페이지 번호를 만들 수 없다.** 그래서 푸터가 `‹ 이전 · 다음 ›` 이 된다([53](../../frontend/_study/grid-standard.md) §2.3)

#### 벤더 중립

| | |
|---|---|
| JPA · QueryDSL | `Pageable` — **Hibernate 방언이 처리한다**([22](./db-portability.md) §4.4) |
| **MyBatis** | **`OFFSET n ROWS FETCH NEXT m ROWS ONLY`** — 표준 SQL. **MySQL 만 미지원**이라 `databaseId="mysql"` 분기(〃) |
| 커서형 | **`WHERE` 절이므로 벤더 차이가 없다** — 페이징 문법을 쓰지 않고 `FETCH FIRST n ROWS ONLY` 만 붙인다([22](./db-portability.md) §4.5) |

> **커서형이 오히려 벤더 중립적이다.** 오프셋 페이징이 벤더 분기를 요구하는 유일한 자리인데
> ([22](./db-portability.md) §4.4) 커서형은 **보통의 `WHERE` + 상위 N** 이다.

### 3.9 응답 — `PageResponse<T>`. **`mode` 가 첫 키다**

```jsonc
{ "success": true, "traceId": "…",
  "data": { "mode": "offset",        // offset · cursor · all — §3.8
            "content": [ … ],
            "size": 100,
            "hasNext": true,
            "totalElements": 3418,   // cursor 면 null
            "totalPages": 35,        // 〃
            "nextCursor": null,      // offset · all 이면 null
            "prevCursor": null } }
```

| 키 | `offset` | `cursor` | `all` |
|---|---|---|---|
| **`mode`** | ✓ | ✓ | ✓ |
| `content` · **`hasNext`** | ✓ | ✓ | ✓ (`hasNext` 는 언제나 `false`) |
| `size` | ✓ | ✓ | **`null`** |
| `totalElements` | ✓ | **`null`** | ✓ (배열 길이) |
| `totalPages` | ✓ | **`null`** | **`null`** |
| `nextCursor` · `prevCursor` | **`null`** | ✓ | **`null`** |

- **`mode` 를 명시하는 이유** — 필드가 `null` 인지로 추론하면 **`cursor` 의 마지막 장과
  `all` 이 구별되지 않는다**(둘 다 `totalPages`·`nextCursor` 가 `null` 이고 `hasNext` 가
  `false` 다). 모양을 훑어 알아내게 하는 대신 **서버가 한 마디로 말한다**
- **`hasNext` 를 셋 다 채우는 것이 요점이다.** 그리드 푸터가 **한 컴포넌트**이므로
  ([53](../../frontend/_study/grid-standard.md) §2.3) *"다음이 있나"* 는 모드와 무관하게 답이 있어야 한다
- **타입을 셋으로 가르지 않는다.** 가르면 `<DataGrid>` 가 셋을 받아야 한다 —
  **한 타입에 `mode` 한 키**가 화면의 분기를 한 곳에 모은다

## 4. 화이트리스트 (QRY-02 · QRY-05)

### 4.1 **스펙 객체**가 화이트리스트다 — 미러링하지 않는다

[10](../../../knowledge/features.md) §J 의 QRY-05 가 *"화이트리스트 **DTO 리플렉션 도출** — 프론트 선언과
미러링하지 않음"* 이라고 적었다. **원칙은 맞고 물건이 틀렸다**(아래).

```java
public final class AccessLogSpec {

    static final QSysLoAccess AL = QSysLoAccess.sysLoAccess;
    static final QSysUser     U  = QSysUser.sysUser;

    public static final QuerySpec SPEC = QuerySpec.of("accessLog")
        .from(AL)
        .leftJoin(U).on(U.userId.eq(AL.userId))    // 조인도 여기 있다 (§5.1)
        .col("creDtm",     AL.creDtm).sortable()   // 정렬 가능
        .col("userId",     AL.userId)
        .col("userNm",     U.userNm)               // 조인 컬럼 — 별칭을 Q타입이 안다
        .col("menuCd",     AL.menuCd).nullable()   // in 배열에 null 허용
        .col("requestUri", AL.requestUri)
        .derived("status", AccessLogSpec::status)  // 컬럼이 아니다 — 정렬 불가
        .defaultSort("creDtm", DESC)
        .pk(AL.seq)                                // tie-breaker
        .build();
}
```

**이 스펙이 곧 화이트리스트다.** `.col(…)` 로 열지 않은 이름이 오면 400 이고,
**대상이 `Path` 객체라 타입이 곧 허용 연산자다**(§3.4).

#### 레코드 리플렉션이 아닌 이유 — **둘**

| | |
|---|---|
| **① 그 레코드는 바인딩되지 않는다** | `creDtm` 에 `between` 이 오면 값이 **2원소 배열**이고 `menuCd` 에 `in` 이 오면 **리스트**다. `OffsetDateTime`·`String` 필드에 담기지 않는다 — **`@RequestBody` DTO 가 아니라 선언용 스펙**이었다 |
| **② 리플렉션은 절반만 준다** | 필드 **이름 집합**은 나오지만 **어느 컬럼·별칭인지**는 안 나온다. 조인이 있으면 그것이 필요하고(§5.2) **없이는 SQL 을 못 만든다** |

#### 원칙은 그대로다 — **원본이 되는 물건만 바뀐다**

| 왜 소스에서 뽑나 | |
|---|---|
| **원본이 하나** | 프론트 선언([57](../../frontend/_study/search-form-contract.md))과 서버 목록이 둘이면 **어긋날 때 어느 쪽이 맞는지 알 수 없다** — [46](../../../knowledge/sys/batch.md) §5.2 가 `PARAM_TYPE_CD` 를, [43](../../../knowledge/sys/code.md) §6.2 가 `MIN_VAL`/`MAX_VAL` 을 거부한 것과 **같은 판단** |
| **빠뜨릴 수 없다** | 조건을 열려면 `.col(…)` 한 줄을 적어야 하고, **안 적으면 400 이라 조용히 새지 않는다** |
| **같은 계열이 이미 셋** | 시드 생성([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)) · 설정 키([63](../../../../documents/screen/code/requirements.md) §4.2) · 메시지 키([ADR-0023](../../../records/adr/0023-message-key-sync-from-source.md)) — **소스에서 뽑는다**가 이 저장소의 반복 패턴이다. **[57](../../frontend/_study/search-form-contract.md) 의 프론트 타입도 이 스펙에서 생성한다** |

**컨트롤러에 목록을 손으로 적지 않는다** — 스펙과 목록이 둘이 되어 위 첫 줄이 **그대로
자기에게 돌아온다.** 필드를 늘리고 목록에 안 적으면 조용히 400, 컬럼을 바꾸고 목록만
고치면 **조용히 엉뚱한 컬럼**이다.

#### 선언 셋이 타입으로 표현되지 않는 것을 담는다

| | 무엇 | 없으면 |
|---|---|---|
| `.sortable()` | `sorts` 에 올 수 있다 | **기본은 정렬 불가** — [54](../../frontend/_study/grid-column-contract.md) §3 이 끄는 대상을 셋 적었고, **닫힌 쪽이 기본**이어야 `nclob` 정렬 같은 사고가 안 난다 |
| `.nullable()` | `in` 배열에 `null` 허용(§3.6) | `null` 이 오면 400 |
| `.derived(name, fn)` | 컬럼이 아니다(§3.5) — **번역 함수를 함께 준다** | — |

> **`.sortable()` 의 기본이 *불가* 인 것이 [54](../../frontend/_study/grid-column-contract.md) §2 의 `editable` 과 같은 방향이다** —
> *"편집은 명시해야 열린다"*. **닫힌 것을 여는 것은 의식적 행위**여야 한다.

> **`.derived()` 는 특별한 것이 아니다.** §5.1 이 파생에만 두려 했던 *번역 함수 등록* 이
> **전 필드의 공통 형태**이고, 파생은 *식이 컬럼 하나가 아닌 필드* 일 뿐이다 —
> **개념이 하나 준다.**

### 4.2 검증 없이 빌더에 들어갈 수 없다 — **자료형으로 막는다**

QRY-02 가 *"미검증 요청은 **빌더 진입 차단**"* 이라고 적었다.

| | |
|---|---|
| 무엇이 문제인가 | 서비스가 **검증 호출을 빠뜨릴 수 있다.** 그러면 임의 필드로 조건이 만들어진다 |
| **어떻게 막나** | **빌더의 산출물(`Built` · `SqlFragment`)만 쿼리에 들어간다.** 그 생성자를 패키지 전용으로 닫으면 **빌더 말고는 아무도 만들 수 없다** |
| 왜 문서가 아니라 장치인가 | **원칙 P1** — 규칙이 아니라 메커니즘으로 강제한다. [23](./security-design.md) §4 의 *deny by default* 와 같은 방향이다 |

**AOP 통과 표식보다 자료형이 낫다.**

| | AOP 표식 | **자료형** |
|---|---|---|
| 검증을 건너뛰면 | **런타임 500** | **컴파일 실패** |
| 매퍼·리포지터리 시그니처 | 무엇이든 받는다 | **`SqlFragment` 만 받는다** |

표식은 *"검증을 부르는 것을 잊었다"* 를 **배포 후에** 알려 주고, 자료형은 **빌드에서 막는다.**
구현은 [34](../search.md) §6.2.

**그래도 런타임에 뚫리면 400 이 아니라 500 이다.** 사용자 입력의 문제가 아니라 **우리 코드의
버그**이므로, 조용히 400 으로 돌려주면 *"조회가 안 된다"* 로 묻힌다 —
[45](../../../knowledge/sys/logs.md) §4.2 의 에러 로그에 스택과 함께 남아야 한다.

## 5. 빌더 (QRY-03 · QRY-04)

**구현은 Phase 7 이 만든다.** 여기는 **계약**만 적는다 — 무엇을 받고 무엇을 보장하나.

### 5.1 QueryDSL — 기본

| | |
|---|---|
| 입력 | 검증을 통과한 조건 배열 + 정렬 + 페이징 |
| 출력 | `Predicate` · `OrderSpecifier[]` · `Pageable` |
| **FROM · JOIN** | **스펙이 갖는다**(§4.1) — 서비스에 두지 않는다. 아래 |
| **파생 필드** | `.derived(name, fn)` 이 **번역 함수를 함께 등록한다** — `status → (USE_YN, 기간, LOCK_YN, DORMANT_YN)`(§3.5) |
| tie-breaker | **빌더가 붙인다**(§3.7) — 서비스가 잊을 수 없다 |

**조인을 스펙이 갖는 이유** — 서비스에 두면 스펙과 어긋날 수 있고 **아무도 안 본다.**
스펙에 조인 컬럼을 열어 놓고 서비스가 조인을 안 붙이면 **묵시적 크로스 조인**이 되어
**결과가 조용히 틀린다.** 한 곳에 있으면 어긋날 수가 없다 — §4.1 의 *원본이 하나* 가
조인에도 적용된다([34](../search.md) §4.4).

> **프로젝션은 서비스에 남겨도 된다.** *조건* 이 아니라 *표시* 라 어긋나도 SQL 이 틀리지 않는다.

### 5.2 MyBatis — 통계·리포트만. **`${}` 를 여기서만 연다**

[21](./architecture.md) §3 이 *"통계/집계, 다중 조인 리포트, 벤더별 튜닝"* 으로 용도를 좁혔다.

| | |
|---|---|
| 동적 조건 | **공통 조각 하나**(`common-search.xml`)를 `<include>` 한다 — **화면 XML 은 조건절을 쓰지 않는다** |
| **`${}`** | **식별자(컬럼 · 정렬 방향)에만.** 넣는 값은 언제나 **스펙이 돌려준 소스 상수**이며 요청 문자열은 SQL 에 들어가지 않는다 — 아래 |
| 대상 컬럼 | **문자열 상수**다 — `"D.DEPT_CD"` 처럼 **조인 별칭을 포함**한다(§4.1 의 QueryDSL 판과 다른 점) |
| 페이징 | `OFFSET … FETCH NEXT` + **`databaseId="mysql"` 분기**([22](./db-portability.md) §4.4) |
| **쓰기 금지** | 원칙적으로 읽기 전용([21](./architecture.md) §3 규칙 1) |

#### `${}` 를 피할 수 없다 — MyBatis 가 아니라 **JDBC** 의 사정이다

`PreparedStatement` 의 `?` 는 **값 자리**이며 컬럼명 자리에 놓을 수 없다. MyBatis 의 `#{}`
가 그 위에 있으니 **동적 컬럼명은 `${}` 외에 방법이 없다.**
[21](./architecture.md) §3 규칙 3 의 *전면 금지* 를 그렇게 고친다(§6).

**안전한 이유는 검증이 아니라 자료형이다.** 요청의 `field` 는 **맵의 키로만** 쓰이고,
SQL 에 들어가는 것은 **맵이 돌려준 컴파일 타임 상수**다 — `' OR 1=1--` 는 키로 존재하지
않아 **400** 이 되며 **SQL 문자열이 만들어지는 경로 자체가 없다**([34](../search.md) §6.1).

**컬럼을 XML 에 나열하는 대안은 채택하지 않는다** — 그 나열이 곧 **두 번째 화이트리스트**이고
§4.1 이 *미러링* 이라며 거부한 형태다. 공통 조각의 `<choose>` 는 **연산자 열셋**을 나열할
뿐이라 **화면이 늘어도 안 는다.**

#### MyBatis 를 좁힌 것은 **안전 장치이기도 하다**

`"D.DEPT_CD"` 의 `D` 는 **XML 의 `JOIN … D` 에만 존재**한다. 스펙은 자바이고 조인은 XML 이라
**둘을 기계로 묶을 수 없다** — 별칭을 개명하면 컴파일도 기동도 통과하고 **그 조건을 쓰는
화면에서만 런타임에 깨진다.** QueryDSL 은 조인이 스펙 안에 있어(§5.1) 이 문제가 없다.

| 그래서 방어가 둘이다 | |
|---|---|
| **적게 쓴다** | [21](./architecture.md) §3 의 *통계·리포트만* 이 **성능 취향이 아니다** |
| **전 조건을 태우는 통합 테스트** | 스펙의 컬럼 수만큼 케이스가 나온다 → §7 |

### 5.3 벤더 중립이 프로토콜에 남긴 것 — 넷

| [22](./db-portability.md) 의 제약 | 프로토콜에서 |
|---|---|
| `ORDER BY` 에 항상 PK tie-breaker | **서버가 붙인다**(§3.7) — 클라이언트가 보내지 않는다 |
| Oracle 은 `'' = NULL` | **빈 조건을 보내지 않는다**(§3.1). `null` 은 `in` 안에서만 뜻을 갖는다(§3.6) |
| MySQL 콜레이션은 대소문자 무시 | **`LIKE` 셋을 서버가 정규화한다**(§3.3 — 2026-08-30). 콜레이션에 맡기면 같은 조건이 벤더마다 다른 답을 낸다 |
| 오프셋 페이징 문법이 갈린다 | **커서형이 그 분기를 피한다**(§3.8) |

## 6. 이 문서가 규약에 되돌려 주는 것

| # | 무엇 | 어디로 | 무엇이 바뀌나 |
|---|---|---|---|
| 1 | **경로 표기는 camelCase 단수다** | [21](./architecture.md) §6-1 | *"리소스는 케밥케이스 복수형"* 이 틀렸다 — **`60`~`65` 의 경로 열다섯이 전부 다르다**(§2.2) |
| 2 | **동작 마디 표기 미결이 닫힌다** | [21](./architecture.md) §6-1.1 | `getList` — 소스의 메서드명이 그대로 경로다 |
| 3 | **`countMode` 를 폐기한다 — 대체 선언도 두지 않는다** | [53](../../frontend/_study/grid-standard.md) §2.3 · §9 | 페이징 여부는 **서버 소스가 이미 정한다.** 화면이 적으면 미러링이고, 푸터는 **응답의 `mode`** 를 보고 그린다(§3.8) |
| 4 | **연산자 열셋** | [60](../../../../documents/screen/_standalone/README.md) §11 | 후보 여덟에서 **`LIKE` 가 셋으로 갈리고**(앞·부분·뒤), **부등호 넷**과 **`isNull` · `isNotNull`** 이 더해진다. 뺀 것은 **`LIKE` 를 하나로 두는 것** 하나뿐이다(§3.3) |
| 5 | **성공 응답에도 `traceId`** | [21](./architecture.md) §6-1 | 그 표는 **에러에만** 적었다 — *"저장은 됐는데 값이 이상하다"* 가 사용 이력을 못 찾는다(§2.3) |
| 6 | **`sorts` 배열과 tie-breaker 의 주체** | [54](../../frontend/_study/grid-column-contract.md) §3 | 그 절이 *"프로토콜은 처음부터 배열로 받아 두고"* 라고 예고한 것의 확정. **tie-breaker 는 서버**다(§3.7) |
| 7 | **`.sortable()` 의 기본이 *불가*** | [54](../../frontend/_study/grid-column-contract.md) §3 | 그 절은 *"정렬할 수 없는 컬럼이 있다"* 로 끄는 쪽을 열거했다. **켜는 쪽을 명시**로 뒤집는다(§4.1) |
| 8 | **`${}` 는 식별자에만** | [21](./architecture.md) §3 규칙 3 | 그 규칙은 **전면 금지 + 빌드 검사**였다. **JDBC 가 식별자를 바인딩하지 못해** 동적 조건에서 성립하지 않는다 — 화이트리스트 상수만, 공통 XML 한 곳(§5.2) |
| 9 | **MyBatis 를 좁힌 것은 안전 장치이기도 하다** | [21](./architecture.md) §3 | 조인 별칭이 **XML 에만 존재**해 자바 화이트리스트와 기계로 묶을 수 없다(§5.2) |
| 10 | **디테일 그리드의 요청 모양** | [55](../../frontend/_study/grid-api-contract.md) §5 | 그 절은 *"조건은 폼이 검증해서 준다"* 인데 **디테일에는 폼이 없다.** 고정형 전용 요청이다(§3.0) |

## 7. 미결 사항

| 항목 | 성격 | 범위 | 게이트 |
|---|---|---|---|
| **`ne` 의 `NULL` 포함을 화면이 알아야 하나**(§3.3) — 서버가 `OR col IS NULL` 을 붙이는 것이 사용자 의도에 맞지만, *표준 SQL 과 다르다* 를 어디서 말할지. 연산자 라벨에 담을지 도움말로 뺄지 | 결정 | 템플릿 | Phase 6 |
| **`SearchRequest<P>` 의 바인딩 형태**(§3.1.1) — 화면 전용 `params` 를 제네릭으로 받을 때 Jackson·Bean Validation 이 **타입 변수까지 따라오는지**. `params` 없는 화면의 표기(`Void`?)도 함께 | 검증 | 템플릿 | Phase 7 |
| **`mode: 'all'` 의 상한과 대상 화면**(§3.8) — 몇 건까지 전량으로 볼지(`SYS_CONFIG` 키), 어느 엔드포인트가 전량인지. 후보는 **코드 상세 · 역할 목록 · 디테일 탭 대부분 · 메뉴 트리**([62](../../../../documents/screen/menu/requirements.md) §4.2.2 이 이미 그렇다) | 결정 | 템플릿 | **Phase 5 완료 시점** |
| **임의 `OR` — 고급 검색 · 조건 빌더**(§3.1) — 사용자가 **조건 행을 추가**하고 `AND`/`OR` 로 묶는 UI. 업무 화면에서 요구가 나온다. 와이어는 **중첩 노드**가 되고 [57](../../frontend/_study/search-form-contract.md) 의 폼·저장이 함께 바뀐다 — **템플릿이 낼지 프로젝트가 얹을지** | 결정 | 템플릿 | Phase 6 |
| **`in` 배열의 길이 상한**(§3.2) — Oracle 은 `IN` 원소가 1000개를 넘지 못한다. 화면이 그만큼 보낼 일이 있는지, 넘으면 **임시 테이블 조인**으로 갈지 | 실측 | 템플릿 | Phase 7 |
| **`contains` 의 비용**(§3.3) — 인덱스를 못 탄다. **기간 조건과 함께일 때만 허용**할지, 화면 판단에 맡길지 | 결정 | 템플릿 | Phase 6 |
| **커서형 `‹ 이전` 의 구현**(§3.8) — 방향을 뒤집어 읽고 되집는다. **첫 장 판정**과 경계가 맞는지 | 검증 | 템플릿 | Phase 7 |
| **스펙의 공통 조각을 어떻게 재사용하나**(§4.1) — 기간·페이징처럼 여러 화면이 같은 조건을 갖는다. `QuerySpec` 빌더에 **부분 적용**을 둘지 | 결정 | 템플릿 | Phase 7 |
| **MyBatis 별칭 통합 테스트의 형태**(§5.2) — 스펙의 컬럼을 순회해 조건을 하나씩 태우는 것을 **자동 생성**할 수 있는지 | 검증 | 템플릿 | Phase 7 |
| **MyBatis MySQL 분기의 실동작**(§5.2) — `databaseId` 분기가 4벤더에서 도는지 | 검증 | 템플릿 | **스파이크 2차**([22](./db-portability.md) §6.1 · Docker) |
| **요청 본문 크기 상한** — 조건이 많은 화면에서. [21](./architecture.md) §6.2 의 캐시 상한 1MB 와 같은 값이어야 하는지 | 결정 | 템플릿 | Phase 7 |

|---|---|---|
| **조회 연산자 집합**([60](../../../../documents/screen/_standalone/README.md) §11) — 후보 여덟 | **열셋.** `eq`·`ne`·`in` · `startsWith`·`contains`·`endsWith` · `between`·`gt`·`gte`·`lt`·`lte` · `isNull`·`isNotNull`. **`LIKE` 를 셋으로 가른다**(인덱스가 갈린다). **뺀 것은 `LIKE` 를 한 연산자로 두는 것 하나** — 나머지는 *사례 0* 이 근거였고 **그 근거가 시스템 화면 표본이라 틀렸다**(2026-08-28 개정) → §3.3 | 2026-08-28 |
| **동작 마디의 표기**([21](./architecture.md) §6-1.1) | **camelCase.** 소스의 메서드명이 그대로 경로이며, 케밥이면 접두 매칭 규칙이 한 겹 는다. **도메인 마디도 camelCase 단수** — [21](./architecture.md) §6-1 의 *케밥 복수형* 을 고친다 → §2.2 | 2026-08-28 |
| **총 건수 없는 페이징의 와이어**([64](../../../../documents/screen/log/access/requirements.md) §7) | **모드 셋**(`offset` · `cursor` · `all`)이며 **응답의 `mode` 가 나른다 — 화면은 선언하지 않는다.** 커서는 **불투명 토큰**이고 **유효기간이 없다** → §3.8 · §3.9 | 2026-08-28 |
| **파생 조건을 어떻게 싣나**([61](../../../../documents/screen/user/requirements.md) §3.3 외 넷) | **와이어의 문제가 아니었다.** 화면은 평범한 조건 하나를 보내고 **번역은 화이트리스트가 갖는다** — `field` 는 **논리 이름**이지 컬럼명이 아니다 → §3.5 · §3.2 | 2026-08-28 |
| **조회를 한 봉투로 다루나**([34](../search.md) §8) | **둘로 가른다.** 고정형(전용 `record`)이 기본이고 동적형은 **검색 폼이 있는 그리드만**. 디테일을 봉투로 태우면 **부모 키 제약이 클라이언트의 조건 하나**가 되어 빈 배열로 전체 조회가 된다 → §3.0 | 2026-08-28 |
| **화이트리스트를 무엇에서 뽑나**(§4.1) | **레코드가 아니라 스펙 객체.** 그 레코드는 **바인딩되지 않고**, 리플렉션은 **컬럼·별칭을 주지 못한다.** *소스에서 뽑는다* 는 원칙과 근거 셋은 그대로 → §4.1 | 2026-08-28 |
| **`@Derived` 번역 함수의 등록 위치**(§5.1) | **스펙 안이다.** `.derived(name, fn)` 이 이름과 함께 받으므로 등록 위치가 따로 없고, **파생이 특별한 것이 아니게 된다** → §4.1 | 2026-08-28 |
| **MyBatis 에서 `${}` 를 쓸 수 있나**([21](./architecture.md) §3 규칙 3) | **식별자에만.** JDBC 가 컬럼명을 바인딩하지 못해 **피할 수 없고**, 요청 문자열은 **맵의 키로만** 쓰인다. 공통 XML 한 곳만 빌드 검사에서 예외 → §5.2 | 2026-08-28 |
| **빌더 진입 차단의 수단**(§4.2) | **AOP 표식이 아니라 자료형.** 산출물의 생성자를 닫으면 검증 누락이 **런타임 500 이 아니라 컴파일 실패**가 된다 → §4.2 | 2026-08-28 |
