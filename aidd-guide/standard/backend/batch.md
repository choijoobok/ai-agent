# 배치 — **등록이 곧 스케줄이다**

> **`@Scheduled` 를 쓰지 않는다.** 그것은 *크론이 소스에 있을 때* 의 것이고 여기서는 크론이
> `SYS_SCHEDULE_BATCH.CRON` 이다 — **데이터로 등록이 늘어야** 같은 구현을 파라미터만 바꿔
> 열 벌 돌릴 수 있다.
>
> 표는 [knowledge/sys/batch.md](../../knowledge/sys/batch.md) · 진행률과의 차이는
> [progress.md](./progress.md).

## 1. `BatchJob` — 계약 넷

> 실물은 `domain/batch/`(계약·코드) · `domain/batch/run/`(스케줄러·러너·풀·하트비트·유령
> 청소·이력 쓰기) · `support/lock/NodeId`(락·이력·유령 판정이 **함께 쓰는** 식별자).

```java
BatchJobResult run(BatchJobContext context);
```

| 계약 | 어기면 |
|---|---|
| **빈 이름이 곧 `BEAN_ID`** | 별도 이름 규칙을 만들면 **두 이름 사이에 매핑이 하나 생긴다** |
| **`paramJson` 을 그대로 받는다** | `Map` 으로 풀어 주면 **스펙의 절반을 프레임워크가 갖는다** — 타입도 필수 여부도 모른 채로 |
| **취소를 물어야 한다** | 안 읽으면 끝까지 돌고 `SUCCESS` 로 끝난다 — **화면은 그것을 거짓말하지 않는다** |
| **예외를 삼키지 않는다** | `try/catch` 로 정상 종료를 만들면 **이력이 성공으로 남고** 실패 알림도 안 나간다 |

- **템플릿에 업무 배치는 하나도 없다.** 지어내면 아무도 안 쓰는 배치가 시드에 남는다 —
  시스템 배치 둘(`RetentionPurgeJob` · `ExpiryNoticeJob`)만 있고 그것들은 **이미 정책으로
  정해진** 기능이다.
- **셀렉트 목록은 시드가 아니라 스프링 컨텍스트에서 모은다**(`BatchJobRegistry`) — 시드면
  배포마다 어긋나 *고를 수 있는데 실행되지 않는* 빈이 보인다. **비어 있는 것이 정상이다.**
  컨텍스트 순서는 스캔 순서라 **정렬해서 준다.**

## 2. 취소는 **협조적**이다

배치는 **다른 노드에서 돌 수 있으므로 스레드를 직접 끊을 수 없다.**

```java
for (Order order : targets) {
    if (context.isCancelRequested()) {
        return BatchJobResult.canceled("중단 요청으로 " + done + "건에서 멈췄다");
    }
    ...
}
```

- **DB 를 매번 읽는다.** 요청은 **다른 노드의 화면**이 세우므로 메모리 플래그로는 보이지
  않는다 — 캐시하면 *중단이 안 먹는다* 가 되고 운영자는 버튼을 다시 누른다. 체크포인트를
  **너무 잘게 두지 않는 것**은 구현의 몫이다.
- **멈췄으면 `canceled(...)` 로 말한다.** `of(...)` 면 러너는 *확인하지 않고 끝까지 돈 배치*
  와 구분할 수 없다.
- **확인하지 않는 구현을 빌드가 막지 못한다** — *물어볼 수단을 준다* 까지가 인터페이스의
  한계다. **계약을 문서로 못박고 화면이 결과를 정직하게 그리는 쪽**을 택했다.

## 3. 결과 — 요약과 상세가 **따로**다

| | 어디 | 왜 |
|---|---|---|
| `summary()` | `RSLT_MSG` — **목록 컬럼** | 합치면 *어느 배치가 몇 건을 처리했나* 를 목록에서 훑을 수 없다 |
| `detail()` | `RSLT_DTL_MSG` — `nclob`, 모달 탭 | `VARCHAR(1000)` 에 대상 목록을 담으면 넘친다 |
| `canceled()` | `RSLT_CD` 를 가른다 | **`CANCELED` 와 `SUCCESS` 를 가르는 유일한 값** |

**`summary` 는 1000자에서 잘린다**(넘겼다면 상세가 잘못 들어온 것이다). **상세를 습관적으로
채우지 않는다** — 보존이 1년이라 모든 실행이 채우면 비대화가 빠르다.

## 4. `BatchResultCode` — `SKIP` 이 둘로 갈린 것이 요점이다

| 코드 | 뜻 | 얼마나 나나 |
|---|---|---|
| `SKIP_LOCK` | **정상** — 다중화에서 한 노드만 실행한다 | 노드 수 − 1 만큼 **매 주기** |
| `SKIP_COOLDOWN` | **결함** — 막으려던 사고다 | **나면 안 된다** |

**한 코드에 정상과 결함이 함께 있으면 화면이 색을 정할 수 없다.**
**`RSLT_MSG` 로 분기하지 않는다** — 문자열을 화면이 읽어 색을 정하면 **문구를 고치는 순간
화면이 틀린다.** 사유는 계속 적되 **판정은 코드가 갖는다.**

> **`USE_YN='N'` 은 어느 코드도 아니다** — 스케줄러가 등록조차 하지 않으므로 **행이 없다.**
> *행이 없다* = 꺼져 있다, *`SKIP_*` 이 있다* = 켜져 있는데 건너뛰었다.

## 5. 스케줄러 — 전건을 다시 건다

| 다시 읽는 시점 | |
|---|---|
| 기동 직후 | `ApplicationReadyEvent` — DB 가 뜨고 나서다 |
| **저장 커밋 뒤** | `BatchScheduleChanged` — **롤백된 저장으로 걸지 않는다** |

**부분 갱신을 하지 않는다** — 삭제·활성화·크론 변경이 전부 다른 갱신이 되고 **하나를
빠뜨리면 바뀐 크론이 다음 재기동까지 반영되지 않는다.** 등록이 수십 건이라 전건이 싸다.

**모든 노드가 걸고 락이 하나만 실행시킨다.** 노드 3대의 한 주기에 `SUCCESS` 1 +
`SKIP_LOCK` 2 가 나오면 **락이 제대로 동작한 것**이고, 안 보이면 오히려 이상하다.

### 기동 시 전건 재검증 — 어긋남마다 결과가 다르다

| 어긋남 | 결과 | 왜 |
|---|---|---|
| **크론을 못 읽는다** | **걸지 않는다** | `CronTrigger` 가 생성자에서 던진다 — 걸려고 하면 **그 뒤의 등록이 하나도 안 걸린다** |
| **쿨다운 ≥ 크론 최소 간격** | **걸되 경고한다** | 돌기는 돈다 — 안 걸면 **성능 저하를 정지로 바꾸는** 셈이다 |

**저장 화면이 검증하지만 시드와 직접 UPDATE 는 그 검증을 지나지 않는다** — 이 템플릿은
파기 배치를 시드로 넣으므로 **지나지 않는 경로가 실제로 있다.**

## 6. 러너 — 입구 둘이 **쿨다운에서만** 갈린다

| | `runNow`(화면) | `runScheduled`(크론) |
|---|---|---|
| `EXEC_TYPE_CD` | `MANUAL` | `SCHEDULE` |
| 쿨다운 | **우회한다** | 지킨다 — 막히면 `SKIP_COOLDOWN` |
| 락에 막히면 | **거절** — 사람이 보고 있다 | `SKIP_LOCK` 행 하나 |

> **거절과 `SKIP` 이 다른 것이 요점이다.** 사람이 누른 실행은 *안 됐다* 를 **그 자리에서
> 말해야** 하고, 크론이 깨운 실행은 **이력에 적는 것이 유일한 말하기**다.

- **진행률을 쓰지 않는다.** `ProgressHelper` 는 *요청 스레드가 시작하는 작업* 을 전제하는데
  배치는 **락을 잡은 노드**에서 돌고 그것이 다른 노드일 수 있다 — 보여줄 자리는 실행 이력의
  `RUNNING` 행이다. `runNow` 는 **시작만 확인하고 돌아온다.**
- **락 해제가 `finally` 에 있다.** 없으면 프로세스가 살아 있는 채 락이 남아 **만료까지 다시
  못 돈다** — 만료 안전망은 *프로세스가 죽었을 때* 의 것이다.

## 7. 전용 풀 — 진행률 풀과도 다르다

```
core 2 · max 4 · queue 100 · 종료 시 대기(상한 있음)
```

- **`@EnableAsync` 를 켜지 않는다** — 켜면 전 애플리케이션의 `@Async` 기본 실행기가 정해진다.
- **풀이 작다** — 전부 DB 를 쓰므로 **커넥션 풀이 진짜 상한**이다.
- **무한 큐를 쓰지 않는다** — 넘치면 `FAIL` 로 남는 편이 **조용히 쌓이다 메모리로 죽는
  것**보다 낫다.
- **종료 때 기다리되 상한을 둔다.** 안 기다리면 정상 재기동마다 유령이 생겨 **그 신호의
  값이 떨어지고**, 무한이면 배치 하나가 **배포를 막는다.**

## 8. 하트비트 — `LOCK_EXPIRY_SEC` 의 뜻을 바꾼다

**없으면 오래 도는 배치가 자기 락을 잃는다** — 살아 있는데 만료되고, 다음 주기에 깨어난
다른 노드가 **선점에 성공한다.** 락으로 막으려던 사고가 정확히 그 자리에서 일어난다.

| | |
|---|---|
| **기간을 늘려도 안 풀린다** | 짧으면 **중복 실행**, 길면 진짜 죽었을 때 **그만큼 아무도 못 돈다** |
| **미는 쪽의 결과** | `LOCK_EXPIRY_SEC` 이 *이만큼 걸릴 것이다*(예측)에서 **이만큼 소식이 없으면 죽은 것이다**(관측)로 바뀐다 |
| **주기는 만료의 1/3** | **한 번 놓쳐도 만료되지 않아야** 한다 — 1/2 이면 한 번에 만료다 |
| **뺏겼으면 멈춘다** | 배치를 **죽이지는 않는다**(체크포인트 밖에서 죽으면 **정확히 유령을 만든다**). 대신 *중복 실행이 일어났을 수 있다* 를 크게 남긴다 |

## 9. 유령 — 판정은 **락이 한다**

**유령은 보기 싫은 것이 아니라 막는 것이다** — `RUNNING` 행이 남으면 `runNow` 가 *이미
실행 중* 으로 읽어 **사람이 눌러도 다시 안 돈다.**

| 그 노드의 살아 있는 락 | 판정 |
|---|---|
| 있다 | 프로세스가 있다 — **얼마나 오래 돌든 정상** |
| 없다 | 프로세스가 없다 — 밀어 줄 것이 없어 만료됐다 |

- **시각으로 재지 않는다** — `START_DTM + LOCK_EXPIRY_SEC` 는 **오래 도는 정상 배치를
  죽었다고 부른다**(기본 300초).
- **`NODE_ID` 까지 맞춰 묻는다.** 키만 물으면 *지금 다시 돌고 있는 경우* 새 실행의 락을
  보고 **옛 유령을 살아 있다고 판정한다.**
- **노드마다 돌고 락을 잡지 않는다** — `markLost` 가 `RUNNING` 일 때만 먹는다. 락을 씌우면
  **청소가 청소를 필요로 한다.**
- **기동 직후에도 훑는다.** 노드가 죽는 가장 흔한 경로가 **재배포**다.

## 10. 이력 쓰기 — 트랜잭션 경계가 **실행과 반대**다

| | 언제 | 왜 |
|---|---|---|
| `start` | **실행 전에 커밋** | 안 하면 도는 동안 화면에 아무것도 안 보인다 — `RUNNING` 을 미리 넣는 이유 전부가 무효다 |
| `finish` | **실행 후 새 트랜잭션** | 배치가 자기 업무 트랜잭션을 롤백해도 **실패했다는 기록은 남아야** 한다 |

**`REQUIRES_NEW` 가 그 둘을 함께 표현한다.** 락 저장소가 같은 이유로 같은 전파를 쓴다.
**`NODE_ID` 는 `NodeId` 하나가 만든다** — 러너가 문자열을 직접 만들면 **락 표와 대조가
깨진다.**

## 11. 체크리스트

- [ ] `BatchJob` 구현이 **취소를 묻고 `canceled()` 로 답하는가**
- [ ] 예외를 삼키지 않는가
- [ ] 상세를 **습관적으로** 채우고 있지 않은가
- [ ] 오래 도는 배치인데 `LOCK_EXPIRY_SEC` 만 키우려 하고 있지 않은가(하트비트가 이미 민다)
- [ ] 새 결과 코드가 필요하면 **열거형**에 더했는가(공통코드가 아니다)
