# 개인정보 분리보관 — **아직 없다.** 지금 지켜야 할 제약만 있다

> **구현이 없고 스키마는 재설계 대상이다**([ADR-0008](../../records/adr/0008-pii-vault-pattern.md) —
> 2026-08-26 개정으로 **적용을 미루고 테이블 설계를 처음부터 다시 하기로** 했다).
>
> 그래서 이 파일은 **설계서가 아니다.** 지금 만드는 화면과 로그가 **나중에 vault 를
> 붙일 수 있게** 남겨 둬야 하는 것 둘만 적는다 — 그 둘을 지금 어기면 **나중에 못 붙인다.**

> **`13-safety/pii.md` 와 다른 주제다.** 그쪽은 *AI 가 로그·요약에 개인정보를 쓰지 않는
> 작업 규칙* 이고, 여기는 *애플리케이션이 개인정보를 어떻게 담는가* 다. 낱말이 같을 뿐이다.

## 1. 방향 — 컬럼 암호화가 아니라 분리보관

원본 테이블에는 **참조키(UUID)만** 두고 값은 별도 저장소에 모은다. 방향은 유지되며
**스키마만 재설계 대상**이다.

## 2. 제약 하나 — **부분 검색이 성립하지 않는다**

원본 테이블에 UUID 만 있으므로 일반적인 조건 검색이 안 된다.

| 요구 | 가능 | 방법 |
|---|---|---|
| 완전 일치(전화번호 · 이메일) | ✅ | 검색어 → 해시 → vault 에서 UUID 목록 → 원본 테이블 `IN` |
| **부분 일치**(*"김" 포함*) | ❌ | **지원하지 않는다** |
| 정렬(이름 가나다순) | ❌ | 〃 |
| 그룹핑 · 집계 | ❌ | 〃 |

> **이 제약이 화면 요건을 바꾼다.** *이름에 '김' 이 포함된 사용자 검색* 은 **불가능**하다.
> 요건서를 쓸 때 **컬럼별로 PII 지정 여부를 검색 조건과 함께** 정해야 하며,
> **부분 검색이 반드시 필요한 컬럼은 PII 대상에서 빼는 판단**이 필요하다.
>
> **지금 이것을 놓치면 나중에 화면을 다시 만들어야 한다** — vault 를 붙이는 날
> 조회조건 하나가 성립하지 않는 것을 알게 된다.

## 3. 제약 둘 — **요청 전문 로그가 vault 를 무의미하게 만들 수 있다**

사용 이력과 에러 로그는 **Ajax 요청 전문을 통째로 저장한다**([logging.md](./logging.md)).
그런데 **등록·수정 요청 body 에는 개인정보가 평문으로 들어온다.**

```
원본 테이블: 참조키만          ← vault 가 지킨다
요청 전문 로그: 평문 그대로     ← 여기가 구멍이다
```

**마스킹 키를 손으로 관리하면 반드시 어긋난다.** PII 정의에서 **자동으로 파생**해야 한다.

| 항목 | 규칙 |
|---|---|
| 파생 | PII 컬럼명 → camelCase 변환 → 마스킹 키 목록에 **자동 추가** |
| 반영 시점 | PII 정의 캐시를 갱신할 때 마스킹 키도 **함께** |
| 매칭 | 대소문자 무시. 컬럼명(`PHONE_NO`)과 JSON 키(`phoneNo`) **양쪽** 등록 |
| 응답 | 응답 body 는 저장하지 않으므로 대상이 아니다 |

> **파기 의무와 직결된다.** 파기 요구로 vault 행을 지웠는데 **로그 테이블에 평문이 남아
> 있으면 파기가 완료되지 않은 것**이다.

## 4. 붙이는 날 다시 정할 것

- 테이블 설계 전부(ADR-0008 이 재설계 대상으로 남겼다)
- 마스킹 규칙의 코드 구현과 규칙 코드 체계
- 마스킹 해제 보기의 권한과 **접근 이력**
