# 목록 처리의 트랜잭션 경계 — 한 덩이냐 건별이냐

> **저장이냐 실행이냐가 가르지 않는다.** 가르는 것은 하나다 —
> **실패했을 때 무엇이 남아야 하는가.**
>
> 저장에도 건별이 필요할 때가 있고, 실행에도 전부 아니면 전무가 맞을 때가 있다.
> 그래서 이 선택은 **액션의 성질이 아니라 그 목록의 성질**에서 나온다.

## 1. 두 모양

| | `RowTx.oneTxForAll` | `RowTx.oneTxPerRow` |
|---|---|---|
| 트랜잭션 | **전체에 하나** | **행마다 하나** |
| 실패하면 | 전부 되돌아간다 | **그 행만** 되돌아간다 |
| 끝맺음 | `BusinessException` 을 **던진다** | `RowReport` 를 **돌려준다** |
| 응답 | **400** + `rows` | **200** + `{total, done, failed, rows}` |
| 부르는 메서드 | `@Transactional` **이어야** 한다 | `@Transactional` **이면 안 된다** |

**둘 다 끝까지 돌고 실패를 모은다.** 루프 안에서 던지면 사용자가 N 번 눌러 오류를 하나씩
발견하고 *고칠 것이 몇 개인지* 를 끝까지 모른다 → [exception.md](./exception.md) §3.

**순번은 언제나 요청 배열의 것이다.** 화면이 그 순번으로 셀을 붉히므로, 행을 갈라 담은 뒤
그 목록을 돌리면 **남의 행이 붉어진다** — 예외도 경고도 나지 않는다.

## 2. 어느 쪽인가 — 순서대로 묻는다

1. **절반만 반영된 상태를 화면이 알아볼 수 있나?** 없으면 **한 덩이**다. `recalcItems` 가
   그 자리다 — 진행률은 사라지고 남는 것은 금액뿐이라, 어디까지 됐는지 아무도 모른다.
2. **재시도할 입력을 누가 소유하나?** **사용자가 소유하면 건별을 쓰지 않는다.** 엑셀
   업로드가 그 자리다: 500행 중 488행이 들어가면 그 파일은 **그대로 다시 못 올린다**
   (성공분이 중복으로 걸린다). 사용자가 힘들게 만든 파일을 **지우는 편집부터 하게 만드는**
   것이 부분 커밋의 대가라면 값이 맞지 않는다. **`ExcelUploadTab` 의 `save` 는 `perRow` 를
   받지 않는다** — 규칙이 아니라 타입이 막는다. 화면 그리드는 반대다: 배열을 화면이 들고
   있어 실패 행만 남길 수 있다(§7).
3. **한 건이 다른 건에 기대나?** 기대면 한 덩이다(합계·번호 채번·상호 검증).
4. **다시 돌려도 같은 결과인가(멱등).** 멱등하면 한 덩이가 싸다 — 답이 *전부 다시* 이므로.
5. **한 덩이로 묶기에 목록이 너무 긴가?** 길면 건별이 아니라 **청크 커밋**이 답이다.
   아직 만들지 않았다 — 필요해지면 여기에 절을 더한다(실패분 내려받기는 있다, §7).

> **1~4 가 전부 건별을 가리켜도, 2 가 아니라고 하면 건별을 쓰지 않는다.** 부분 커밋은
> 서버의 편의가 아니라 **사용자가 다시 낼 수 있을 때**만 이득이다.

## 3. 한 덩이 — `oneTxForAll`

```java
@Transactional
public void saveOrders(List<SmplOrderSaveRow> rows) {
    RowTx.oneTxForAll(rows, row -> {
        switch (row.rowState()) { case C -> create(row); … }
    });
}
```

맨 앞 실패의 코드와 문구가 봉투의 것이 된다 — 봉투의 `code` 는 하나뿐이고, 하나를 골라야
한다면 **사용자가 처음 만나는 것**이 맞다. 낱낱의 사유는 `rows` 가 나른다.

## 4. 건별 — `oneTxPerRow`

```java
// 바깥에 @Transactional 이 없다
public RowReport shipEach(List<Long> ordIds) {
    return RowTx.oneTxPerRow(ordIds, runner::shipOne);
}

@Service
class SampleShipRunner {
    @Transactional                      // ← 경계는 여기다
    void shipOne(long ordId) { … }
}
```

- **바깥에 트랜잭션을 걸지 않는다.** 걸면 행마다 커밋되지 않고, 게다가 실패를 잡고 계속
  돌기 때문에 커밋 시점에 `UnexpectedRollbackException` 이 나서 **499행이 성공한 실행이
  통째로 사라진다**.
- **`REQUIRES_NEW` 가 필요 없다.** 바깥에 트랜잭션이 없으므로 기본 전파(`REQUIRED`)가
  행마다 새 트랜잭션을 연다. `REQUIRES_NEW` 는 **바깥이 반드시 트랜잭션이어야 할 때**의
  것이고(실행 이력 헤더처럼 — `BatchHistoryWriter`), 그때는 행마다 **커넥션을 둘** 잡는다:
  멈춰 있는 바깥 트랜잭션도 자기 커넥션은 쥐고 있다. 500행이면 풀이 마른다.
- **다른 빈이어야 한다.** 같은 빈의 메서드를 부르면 프록시를 지나지 않아 애너테이션이
  무시되고, **예외도 경고도 없이** 전건이 한 덩이로 묶인다.
- **업무 예외가 아닌 것은 잡지 않는다.** 그것은 그 행이 틀린 것이 아니라 **시스템이 고장 난
  것**이고, 고장 난 채로 남은 499행을 계속 미는 것은 손해를 키운다. 이미 커밋된 앞 행은
  남으며 `traceId` 로 어디까지 갔는지 찾는다.
- **전건이 실패해도 200 이다.** 부분 성공이든 전건 실패든 **사용자가 할 일이 같다**(표를
  보고 고쳐 다시 낸다). 상태 코드를 가르면 화면에 분기가 하나 늘고 그 분기가 하는 일이
  없다. 그리고 요청이 거부된 것이 아니다 — 500건을 시도했고 0건이 됐다.

## 5. 헤더를 고르고 디테일을 건별로 돌 때

화면이 고른 것은 헤더 5행인데 실제 일은 그 아래 디테일 수백 건인 경우다.

- **안쪽의 경계는 백엔드가 정한다.** 한 헤더의 디테일 일부만 커밋할지 그 헤더를 통째로
  되돌릴지는 업무가 정할 문제이며, 두 모양 다 이 문서의 규칙을 그대로 쓴다(안쪽에서 다시
  `oneTxForAll` 이거나 `oneTxPerRow` 다).
- **바깥으로 나가는 순번은 헤더 배열의 것이다.** 화면이 붉힐 수 있는 것은 자기가 보낸
  배열의 행뿐이라, 디테일 순번을 실어 보내면 **엉뚱한 헤더가 붉어진다**. 디테일의 실패는
  **그 헤더 행의 사유로 접어 올린다** — `RowError.fields` 가 배열인 것이 그 통로다.

## 6. 빌드가 지킨다

`RowTx` 는 트랜잭션을 **열지도 닫지도 못한다** — 경계는 `@Transactional` 이 어디 붙어
있느냐가 정한다. 이름이 거짓이 되지 않게 `RowTxConventionTest` 가 두 가지를 센다:

| 규칙 | 어긋나면 |
|---|---|
| `oneTxForAll` 은 **쓰기 트랜잭션 안**에서 돈다 | 끝에 던져도 되돌릴 것이 없다 |
| `oneTxPerRow` 는 **어떤 트랜잭션 안에서도** 돌지 않는다 | 행마다 커밋되지 않는다. `readOnly` 여도 마찬가지다 |

**호출 사슬을 거슬러 올라간다** — 트랜잭션은 진입 메서드에 걸리고 사적 헬퍼는 그 안에서
돌기 때문이다. 부르는 이가 하나도 없는 메서드는 **사슬이 끊긴 것**이라 위반으로 센다.

## 7. 화면은 결과를 어떻게 다루나 — **둘 중 하나를 반드시 고른다**

건별을 선언한 화면은 **실패가 남았을 때** 그리드를 어떻게 할지 함께 적는다.
**기본값이 없다** — 정답이 하나가 아니고, 기본값을 두면 아무도 고르지 않는다.

```ts
perRow: { after: 'reload' | 'keepFailed' }   // 저장·실행이 같은 칸을 쓴다
```

| | `reload` | `keepFailed` |
|---|---|---|
| 그리드 | 보던 자리를 다시 읽는다 | **실패한 행만 남기고 비운다** |
| 화면의 편집 | 사라진다 — **실패한 행의 것도** | 실패 행의 것만 남는다 |
| 쓰는 자리 | 서버가 정한 값(채번·상태·계산 금액)을 보여 줘야 할 때 | 고쳐서 다시 낼 것이 화면에 있을 때 |

**고르는 법은 한 가지 물음이다** — *실패한 행을 사용자가 이 화면에서 고쳐 다시 내나?*
그렇다면 `keepFailed` 다. 재조회는 그 입력을 지우고, 지워지면 재시도가 불가능해진다.

배관이 함께 하는 것 넷 —

- **전건 성공은 이 선언과 무관하다.** 남길 실패가 없으므로 평소의 `reloadAfter` 규칙대로
  **보던 자리**를 다시 읽는다 — 커서형은 쪽수가 없으므로 커서로 간다(`gridReloadHere` 가 잠근다).
- **표 아래 첫 줄은 뒤처리마다 다르고 함께 뜨지 않는다** — 함께 뜨면 *비웠다* 와 *새로
  읽는다* 가 서로를 부정한다. 둘 다 **배관만 아는 사실**이라 배관이 말한다.
  - `keepFailed` → 비웠다(`grid.partial.kept`). **비운 것이 있을 때만** — 전건 실패면 지울 것이 없다
  - `reload` → 곧 다시 읽는다(`grid.partial.gone`). **조건 없이**, 그리고 **닫기 전에**:
    닫는 순간 재조회가 *어느 넷이 왜 안 됐나* 를 지운다. 사후 통보는 알림이 아니라 부고다
- **순번을 못 이으면 비우지 않는다** — 배열을 **화면이 직접 만드는** 저장은 걸렀는지
  정렬했는지 배관이 알 수 없다. 표만 내고 콘솔에 남긴다.

### 전건 롤백에는 고를 것이 없다

`oneTxForAll` 이 실패하면 **그리드를 건드리지 않는다.** 커밋된 것이 없어 지울 성공 행이
없고, 화면에 있는 편집이 곧 **다시 낼 입력**이다. 배관은 둘만 한다 — 셀을 칠하고 표를 낸다.

| | 성공 | 실패 |
|---|---|---|
| `oneTxForAll` | 성공 모달 → 재조회 | 표 + 붉은 셀 · **그리드 그대로** |
| `oneTxPerRow` | 성공 모달 → 재조회 | 결과 표 → `after` 대로 |

### 진행률과는 함께 켜지 못한다

`progress` 인 실행의 응답은 `jobId` 라 **돌려줄 결과가 없다** — *접수했다* 이지 *끝났고
이러이러하다* 가 아니다. 둘을 켜면 진행률이 이기고 `perRow` 는 무시되며, 배관이 개발자
콘솔에 남긴다(조용히 지나가면 오지 않을 모달을 기다린다).

@defer P4 긴 작업의 실패분은 아직 답이 없다 — 3천 건은 표에 담기지 않고, 실패분 파일도
  브라우저가 만들 수 없다(그 파일은 *보낸 행* 으로 만드는데 대상이 화면에 없다).
  서버가 만들어 두고 창이 링크를 주는 모양이며, **만들면 지우는 사람도 필요하다**.

### 실패분 엑셀 — 두 모달 다

표는 **읽을** 수는 있어도 고쳐서 다시 낼 수는 없다. 오백 행에서 열둘이 걸린 자리에 남는
일은 원본 파일로 **옮겨 적는 것**이고, 그 옮겨 적기가 새 오타를 만든다. **전건 롤백에 더
필요하다** — 오백 행 전부가 다시 낼 것이라, 알아야 하는 것은 *어느 열둘인가* 하나다.

**시트가 둘인 것이 규약이다.** 첫 시트는 **양식 그대로**여서 고쳐 그대로 다시 올릴 수 있고,
사유는 **둘째 시트**로 간다 — 첫 시트에 열로 붙이면 업로드 파서가 *양식이 다르다* 며
거절한다. → [../../playbook/excel-upload.md](../../playbook/excel-upload.md) §5

표시(표 · 붉은 셀 · 건수)는 저장 실패와 **같은 자리**를 쓴다 →
[../frontend/save-errors.md](../frontend/save-errors.md).
