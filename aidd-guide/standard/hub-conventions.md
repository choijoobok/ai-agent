# Agentic AI Hub 개발 규약

> **백오피스 템플릿의 표준([standard/INDEX.md](INDEX.md))이 먼저다.** 여기는 그 위에
> **Hub 를 얹을 때만 추가되는 규약**이며, 템플릿 표준과 충돌하는 것은 없다 — 겹치는 자리는
> 링크만 둔다.
>
> **결정의 근거는 `documents/spec/` 이 갖는다** — 여기는 *그래서 코드를 어떻게 쓰나* 다.
> 원칙 ID(`PRN-`)와 제약 ID(`CON-`)는 [`spec/02-constraints.yaml`](../../documents/spec/02-constraints.yaml),
> 구조 ID(`ARCH-`)는 [`spec/20-architecture.yaml`](../../documents/spec/20-architecture.yaml).

## 1. 결정 트리

```
Hub 코드를 쓴다
  ├─ "테이블 이름을 정한다"                  → §2
  ├─ "yml 을 어디에 두나 · 비밀값"            → §3
  ├─ "패키지를 어디에 만드나 · 모듈 간 참조"  → §4
  ├─ "외부 모델을 부른다"                     → §5
  ├─ "트랜잭션을 어디서 여나"                 → §6
  ├─ "로그에 무엇을 남기나"                   → §7
  ├─ "일시 컬럼·입력 형식"                    → §8
  └─ "테스트·평가"                            → §9
```

## 2. DB 테이블 네이밍

- **모든 테이블에 접두어 `ai_`** 를 붙인다. 형식은 `ai_<서브모듈>_<상세>`.
- 서브모듈 키는 모듈명 또는 기능 영역 — `ai_admin_*` · `ai_portal_*` · `ai_agent_*`.
- **서브모듈 키는 명명 구분용이다.** 테이블의 **소유·접근 권한을 뜻하지 않는다**(ARCH-010).
- PK 는 **서로게이트 키**를 쓰고, 자연키(예: 카탈로그의 `(데이터소스, DB 스키마, 테이블명)`)에는
  **유니크 제약**을 둔다. 참조는 서로게이트 키로 하여 **이름 변경이 참조를 깨지 않게** 한다.
- 명명의 어휘는 [`spec/03-glossary.yaml`](../../documents/spec/03-glossary.yaml) 의 `key` 다 — §8 도 참조.

## 3. 설정 파일

- 모듈별 yml 은 **파일을 분리**하고 `application-<프로파일>.yml` 에서 import 한다.
- 프로파일은 **로컬 / 개발 / 운영**.
- LLM Provider 선택(개발기 CLI ↔ 운영 API)은 **프로파일 설정으로 전환**한다(CON-033).
- **비밀 값은 평문으로 두지 않는다.** 기본 전략은 **yml + Jasypt 암호화**이며 복호화 키는
  환경 변수 또는 배포 도구에서 주입한다(CON-011).
- **업무 DB·DW 데이터소스는 yml 에만 정의한다.** 데이터소스 ID 와 접속 정보·풀 설정을 포함하며,
  이 ID 는 admin 데이터소스 관리(FEAT-002)가 연결 대상으로 선택하는 값이다.
  다중 데이터소스를 전제하므로 **프로파일별로 파일을 분리한다.**
- **API 연동 계정의 자격증명(키·비번·토큰)도 yml 에만 둔다.** 화면은 **인증 방식과 자격증명
  참조 키만** 관리한다 — 데이터소스 접속 정보와 같은 2계층 원칙이다(ARCH-030).

## 4. 모듈 패키지와 계층

```
common/                Entity · QueryDSL Q타입 · Repository · 권한 판정 컴포넌트(FEAT-303) · 공용 유틸
modules/admin/         controller · service · dto(record) · 화면
modules/portal/        controller · service · dto(record) · 화면
modules/agent/         controller · service · dto(record)
```

- **공통 계층은 어떤 모듈에도 의존하지 않는다.** 역방향 의존이 생기면 **agent 분리가
  불가능해진다**(CON-009).
- **모듈 간 서비스 참조를 금지한다.** 예외는 **portal → agent(채팅 처리) 하나**이며, 이 호출은
  인터페이스를 경유하고 **트랜잭션을 공유하지 않는다**(ARCH-011 · ARCH-015).
- DTO·Record 는 모듈 안에 둔다. **모듈 간에 DTO 를 공유하지 않으며 Entity 를 컨트롤러 응답으로
  직접 반환하지 않는다.**
- 모듈 간 서비스 참조를 금지한 결과 같은 규칙이 여러 모듈 서비스에 중복 구현될 수 있다.
  **중복 구현이 발견되면 공통 컴포넌트로 승격한다** — 그룹 판정(FEAT-303)이 그 선례다.
  이것은 템플릿 표준의 "두 번째 사용에 올린다"([frontend/packages.md](frontend/packages.md))와
  같은 규칙이다.
- **프레임워크의 추상 클래스를 상속한 빈에는 Spring AOP 어노테이션(`@Transactional` 등)을
  붙이지 않는다.** 프록시가 생성자를 거치지 않고 만들어져 **상위 클래스의 필드가 초기화되지
  않은 채 남는다.** 트랜잭션 경계가 필요하면 **별도 빈으로 분리해 위임한다.**
- **대화 이력의 논리 삭제 조회에 Repository 전역 필터를 걸지 않는다.** 전역 필터를 걸면
  admin 이 삭제 표시분을 볼 수 없어 **감사가 불가능해진다**(REQ-109). 대신 조회 메서드를
  표시 대상용과 전량용으로 나누고 **이름으로 구분한다** — `findVisible…` / `findAllIncludingDeleted…`.

## 5. 외부 모델 호출 규칙

- 공급사 SDK·엔드포인트 의존성은 **공통 계층(FEAT-304) 안에만** 둔다. `modules/` 아래 어떤
  코드도 공급사 SDK 를 import 하지 않고 **HTTP 클라이언트로 모델 API 를 직접 호출하지 않는다**(PRN-01).
- 개발 기간의 CLI Provider 도 **공통 컴포넌트 내부 구현체로만** 존재한다.
- **프레임워크의 모델 추상화(예: Spring AI 의 `ChatModel`)도 공통 컴포넌트 내부에만 둔다.**
  공급사 SDK 는 아니지만 **같은 층의 경쟁 추상화**이므로, 도메인에 노출하면 공급사 교체
  가능성을 얻는 대신 **프레임워크 자체가 교체 불가능한 종속**이 된다(CON-005).
  호출 기록 강제·용도별 인터페이스 분리·테스트용 구현체 자리도 우리 인터페이스를 유지해야
  성립한다.
- **오케스트레이션 프레임워크의 타입은 `modules/agent` 안에서만 참조한다.** portal·admin 이
  참조하면 **빌드가 실패해야 한다.**
- 공통 컴포넌트는 **호출 성공·실패와 무관하게 호출 기록을 남긴다.** 기록 없이 성공한 호출이
  있으면 안 된다(PRN-07).
- **용도별로 인터페이스를 분리해 노출한다** — 대화·추론용과 임베딩용을 하나로 합치지 않는다.
  그래야 "portal·admin 은 대화·추론 LLM 을 호출하지 않는다"(ARCH-013)를 **참조 관계로 검사할 수
  있다.** 호출 기록에 **호출 용도**를 함께 남겨 사후 감사에서 조회로 검증한다.
- **위반 여부는 의존성 규칙 검사(아키텍처 테스트)로 확인한다. 리뷰에만 의존하지 않는다** —
  템플릿의 `LayerDependencyTest` 와 같은 자리에 규칙을 더한다(CLAUDE.md §8).

## 6. 트랜잭션 경계

- **이력·사용량 기록은 호출자 트랜잭션에 참여시키지 않는다.** 별도 트랜잭션 또는 오토커밋
  커넥션으로 즉시 커밋해 **호출자의 롤백에 영향받지 않게** 한다(REQ-108).
- **LLM 응답을 기다리는 구간에는 트랜잭션과 DB 커넥션을 열어두지 않는다.** 한 턴은 수 초에서
  수 분이 걸리므로 턴 전체를 한 트랜잭션으로 감싸면 **커넥션 풀이 고갈된다.**
  턴 처리는 **단계마다 짧게 커밋한다.**
- 그래도 트랜잭션이 필요한 곳은 남는다 — 여러 테이블에 걸친 상태 전이:
  신청 승인(신청 상태 + 쿼터 조정) · 워크플로우 정의 저장(마스터·상세) ·
  지식 등록·수정(본문 + 임베딩 벡터) · 세션과 첫 턴 생성.
  **본문과 벡터가 어긋나거나 승인과 쿼터가 어긋나면 복구가 어렵다.**
- **실패한 액션은 롤백 대상이 아니라 실패 이력으로 남긴다.** 업무 API 를 연속 실행하다 중간에
  실패하면 앞선 실행은 자동 복구되지 않는다 — 부분 실행 상태를 사용자에게 알리고 이력으로
  추적한다(REQ-026).
- **별도 트랜잭션을 쓰면 한 요청이 커넥션을 둘 점유할 수 있다.** 커넥션 풀 크기를 이 전제로
  산정한다.
- **리스 연산의 모든 진입점에 트랜잭션 경계를 직접 붙인다** — 자기 호출은 프록시를 거치지
  않아 `@Transactional` 이 적용되지 않는다([turn-execution.md](../../documents/design/turn-execution.md) §8.2).

## 7. 로그와 오류 식별

**감사 이력은 무엇이 일어났는지에 답하지만 왜 실패했는지에는 답하지 못한다.** 장애 진단 경로를
별도로 갖춘다.

- 세션·턴·**회차**·스텝 식별자를 **애플리케이션 로그에도 일관되게 남긴다.** 이력과 로그를
  같은 키로 대조할 수 있어야 한다. **회차가 빠지면 되돌림이 있었던 턴에서 로그와 이력이 1:1 로
  대조되지 않는다.**
- 사용자에게 표시되는 오류에는 **참조 코드**를 함께 노출한다. 문의가 들어왔을 때 해당 턴을 즉시
  특정하기 위한 것이며 **내부 구조나 스키마 정보를 담지 않는다.**
- **애플리케이션 로그에 업무 데이터 원문을 남기지 않는다.** 조회 결과와 API 응답 본문, 그 일부를
  담은 예외 메시지·HTTP 클라이언트 요청·응답 로깅이 대상이다. **감사 이력에서 마스킹한 값이
  로그에 평문으로 남으면 REQ-111 의 통제가 통째로 무효가 된다.** 로그에는 식별자(세션·턴·회차·스텝 ·
  API · 경로 이름)와 **건수만** 남긴다.
- **품질 신고와 시스템 오류를 섞지 않는다** — 신고(REQ-110)는 응답 품질의 경로이고 시스템
  오류는 참조 코드로 추적한다.
- 서버 문구의 언어 규칙은 템플릿과 같다 — 로그와 예외의 기본 메시지는 **한국어**
  ([`CLAUDE.md`](../../CLAUDE.md)).

## 8. 시각과 타임존

- AI 전용 DB 의 **모든 일시 컬럼은 `timestamptz`** 로 관리한다.
- 사용자가 입력하는 일시(워크플로우 시작·종료 등)는 **브라우저 타임존이 적용된 ISO 8601** 로 받는다.
- 업무 DB·DW 의 시각 체계는 고객사마다 다르므로, 조회 결과의 기준 시각(REQ-012)에는
  **그 데이터소스의 시각 체계를 함께 명시한다.**
- **모든 점유·만료 판정은 DB 서버 시각(`now()`)으로 한다** — 인스턴스의 시스템 시각을 쓰면
  시각 오차가 그대로 판정의 오차가 된다.

## 9. 테스트와 검증

- 개발 환경과 운영 환경을 분리하고 개발에서 검증한 뒤 운영으로 이관한다.
- **다만 프롬프트 규칙과 지식은 이 경로를 거치지 않는다.** PRN-06 에 따라 운영 관리자가 운영
  화면에서 직접 바꾸고 즉시 반영되므로 **환경 분리로는 잘못된 변경을 막을 수 없다.**
  이 경로의 안전장치는 **변경 이력과 되돌리기**(FEAT-033)다.
- LLM 호출은 비결정적이고 비용이 발생하므로, 자동화된 회귀 테스트를 위해 **공통 컴포넌트에
  테스트용 구현체(고정 응답 또는 녹화·재생)를 둘 자리를 인터페이스 설계 시점에 확보한다.**
  구현 시점은 미룰 수 있으나 **인터페이스가 이를 수용하지 못하면 나중에 추가할 수 없다.**
- **평가셋 없이 프롬프트 규칙·지식·카탈로그를 바꾸지 않는다**(FEAT-034). 이 세 자산은 배포 없이
  즉시 반영되므로 회귀를 감지할 수단이 없으면 **품질이 조용히 나빠진다.**
- 평가는 **단계별과 전체를 함께 측정**하고, **앞 단계에 정답을 주입한 상태에서 뒤 단계만 격리
  측정**하는 경로를 함께 둔다. 전체 정확도만 보면 어느 단계가 무너졌는지 알 수 없다.
- **외부 공개 벤치마크 점수를 목표로 삼지 않는다** — 평가셋은 고객사의 실제 스키마·용어·질의로
  구성한다.
- 평가는 LLM 호출을 발생시키므로 비용이 든다. 실행 주기와 평가셋 크기는 운영 설정으로 관리하고
  사용량은 개인 쿼터가 아닌 **시스템 비용**으로 집계한다(NFR-015).
- **다중 DBMS 지원은 검증 대상 목록을 정하고 그 범위 안에서만 지원을 선언한다.** 목록은
  연동 대상 데이터소스의 DBMS 종류·버전을 기준으로 한다(CON-023).
- 스키마 불일치 감지와 인라인 값 샘플링의 방식·한계는 REQ-304 가 갖는다 — **여기에 다시 적지 않는다.**
- **훅 순서 회귀 테스트를 CI 에 편입한다** — 오케스트레이션 프레임워크의 훅 순서에 의존하는
  결합이 있어, 버전 업 시 조용히 깨지는 것을 막아야 한다.
