# 진행률 — 화면은 **폴링 코드를 쓰지 않는다**

> 실행 선언에 **`progress: true` 한 줄**이면 그리드가 응답의 `jobId` 를 훅에 넘긴다.
> 화면마다 주기·중단 조건·실패 처리가 갈리면 **같은 기능이 화면 수만큼** 생긴다.
>
> 서버 쪽은 [../backend/progress.md](../backend/progress.md).

## 1. 화면이 적는 것은 이만큼이다

```ts
{
  key: 'recalc', url: E.recalculateOrders, target: 'none',
  progress: true,                    // ← 이것뿐
  params: () => openParams({ ... }),
}
```

**폴링·창·경과 시간·재시도는 전부 `shared/progress/` 의 것이다.**

## 2. 호스트 하나 — **폴링은 창이 아니라 호스트가 든다**

`ProgressHost` 가 `AppProviders` 안에 한 번 서고, 여는 통로는 컨텍스트다.

| 두는 곳 | 왜 |
|---|---|
| **폴링을 호스트에** | 창에 두면 **닫는 순간 폴링이 죽어 `onDone` 이 오지 않고** 목록이 갱신되지 않은 채 남는다 |
| **접힌 표시를 셸에** | **작업이 화면보다 오래 산다** — 사용자는 재계산을 걸어 두고 다른 메뉴로 간다. 화면에 두면 그 순간 표시가 사라진다 |
| **`jobId` 하나만** | 둘 겹치면 창 하나에 무엇을 그릴지가 문제가 된다. 그리드가 이미 실행 중복을 막으며, 겹쳐 오면 앞의 것을 **보는 것만** 그만둔다 |

## 3. 닫기는 **접는 것**이다

```
도는 중에 닫기  →  접는다   (폴링은 그대로 · 표시가 남아 다시 열린다)
끝나고 닫기     →  버린다   (볼 것이 남아 있지 않다)
```

**모달을 닫아도 약속은 계속 산다.** 닫는 것은 *보는 것* 을 그만두는 일이지 **작업을 멈추는
일이 아니며**, 그래서 `onDone` 은 창이 닫힌 뒤에도 온다.

> **여기가 한 번 어긋나 있었다.** 닫기가 폴링의 세대를 올려 루프를 취소했다 — 닫으면
> `onDone` 이 오지 않아 **목록이 갱신되지 않았다.** 그 고장에는 오류도, 실패한 작업도
> 없다: 사용자가 보는 것은 *재계산을 눌렀는데 금액이 그대로* 뿐이라 **화면을 의심할
> 근거가 하나도 없다.** `ProgressHost.test.tsx` 가 그 자리를 지킨다.

## 4. 폴링 규칙 셋 — `poll.ts` 가 따로 있는 이유

**검사할 수 있게 하려고** 떼어 두었다. 이 셋은 화면을 몰아서는 재기 어렵고, **흔들리는
검사는 없는 것보다 나쁘다.** 시각과 통신을 주입으로 받으므로 **진짜 시간을 기다리지 않는다.**

| 규칙 | 값 | 근거 |
|---|---|---|
| **주기** | **1초** | 서버가 *1% 또는 1초 중 늦은 쪽* 으로 쓴다 — **쓰는 쪽에 맞춘다.** 더 자주 물으면 같은 값을 다시 받고, 더 뜸하면 써 둔 것을 놓친다 |
| **401 은 실패가 아니다** | 예산을 쓰지 않는다 | 재인증 모달이 뜨고 사람이 비밀번호를 치는 동안 **수십 초**가 지난다. 실패로 세면 그 사이 예산이 바닥나 **멀쩡히 도는 작업을 놓친다** |
| **연속 실패 예산** | **5** | 일시적 끊김은 넘기고 **영영 두드리지는 않는** 선. 무한이면 서버가 내려간 사이 창 하나가 초당 한 번씩 계속 나간다 |

### 못 보는 것과 실패한 것을 **가른다**

예산을 넘으면 **던진다 — `FAILED` 를 지어내지 않는다.**

> 둘은 사용자에게 다른 사실이다: 작업이 실패한 것과 **우리가 진행률을 못 보는 것**이며,
> 후자에서 작업은 **여전히 돌고 있을 수 있다.** 지어내면 사용자는 다시 실행하고,
> **그때 같은 작업이 두 번 돈다.**

`pollJob` 의 반환이 `null` 이면 **중간에 그만둔 것**이며 작업의 결과가 아니다.

## 5. 경과 시간 — **서버 시각을 쓰지 않는다**

기준은 **창을 연 순간**(`openedAt`)이다.

- **퍼센트만으로는 기다릴 수 없다.** 24% 는 *얼마나 더* 를 말하지 않는데, 사용자가 그 창
  앞에서 하는 결정은 **기다릴까 접을까** 하나다 — **3초 지난 24% 와 5분 지난 24% 는 그
  결정이 정반대다.**
- **`CRE_DTM` 을 쓰면** 브라우저와 서버의 시계가 어긋난 만큼 틀리고(음수까지 나온다),
  더 나쁜 것은 **폴링이 실패하는 동안 멈춘다**는 점이다 — 진행률을 못 보는 그 구간이
  **경과 시간이 가장 필요한 때**다.
- **분과 초뿐이다.** 그렇게 오래 열려 있으면 *접어 두는 것* 이 답이며, `90분 12초` 로
  읽히는 편이 **단위가 하나 늘어 눈이 다시 읽는 것**보다 낫다.
- **음수를 0 으로 접는다.** 시계가 뒤로 갈 수 있다(NTP 보정) — `-1분 -3초` 는 진행률의
  신뢰를 통째로 깎는다.
- **초는 두 자리로 채운다** — 폭이 흔들리면 **1초마다 그 줄이 움직인다.**

## 6. 응답이 그리는 것

```ts
{ jobId, jobStatCd, curCnt, totCnt, subTitle, stepMsg, errMsg, modDtm }
```

| 필드 | 규칙 |
|---|---|
| `totCnt` | **`null` 일 수 있다** → **불확정 막대**. `0` 으로 치환하면 `0/0` 이라 **완료로 보인다** |
| **`subTitle`** | *어느 구간* — 구간이 갈리지 않으면 `null` 이고 **그 줄을 그리지 않는다** |
| **`stepMsg`** | *지금 무엇을 하는 중* — 퍼센트만 있으면 **멈춘 것과 느린 것이 같다** |
| `errMsg` | `FAILED` 에서만. 모달은 **사유를 표시한 채 남는다** — 닫는 것은 사용자다 |

**`subTitle` 과 `stepMsg` 를 한 줄에 쓰지 않는다.** `stepMsg` 는 구간 안에서 계속 바뀌므로
합치면 **어느 행을 보고 있는지가 1초마다 사라진다.**

## 7. `onDone` 은 **`DONE` 뒤에** 부른다

도는 중에 재조회하면 **절반만 반영된 목록**을 본다.

## 8. 컨텍스트 — 훅은 조건부로 부를 수 없다

| | 언제 |
|---|---|
| `useProgress()` | 진행률을 **반드시 쓰는** 자리 — 없으면 던진다 |
| **`useOptionalProgress()`** | **그리드 컨트롤러** — 모든 그리드에서 도는데 진행률을 쓰는 실행은 드물다. 여기서 던지면 **진행률과 상관없는 그리드가 호스트를 요구한다** |
| `requireProgress(open)` | **실제로 쓰는 순간** 던진다 — 빠뜨렸을 때 조용히 지나가지 않는 성질은 그대로다 |

## 9. 엔드포인트 — `/api` 를 두 번 적지 않는다

```ts
getOne: (jobId) => `/common/progress/${encodeURIComponent(jobId)}`
```

> 클라이언트의 `baseURL` 이 이미 `/api` 다. 또 적으면 `/api/api/...` 로 나가 **403** 이 오고
> 화면은 *진행률을 확인할 수 없습니다* 를 보인다 — 그 문구는 **서버가 내려갔을 때를 위한
> 것**이므로 원인과 정반대의 사실을 말하며, **작업 자체는 멀쩡히 끝나므로 아무도 그것을
> 고장으로 읽지 않는다.**

## 10. 체크리스트

- [ ] 화면에 폴링 코드가 **없는가**
- [ ] `onDone` 에서 재조회하는가(도는 중이 아니라)
- [ ] `totCnt` 가 `null` 인 작업을 **불확정 막대**로 그리는가
- [ ] 컨트롤러 계열에서 **`useOptionalProgress`** 를 쓰는가
