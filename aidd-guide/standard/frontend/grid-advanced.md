# 그리드 심화 — 컬럼 계약 · 편집 · 검증 · 마스터-디테일

> **어휘는 우리 것이고 판은 어댑터가 고른다.** 컬럼 선언에 AG Grid 의 이름이 나오지
> 않는다 — Community 와 Enterprise 를 오가도 화면이 바뀌지 않아야 한다.
>
> 뼈대와 `api` 선언은 [grid.md](./grid.md).

## 1. 컬럼 하나

```ts
{
  field:    'productId',
  header:   'col.product.id',      // 메시지 키 — 문자열이 아니다
  type:     'popupRef',
  width:    120,
  pinned:   'left',

  visible:  true,                  // 초기 표시. 꺼도 설정 창에서 켤 수 있다
  hidden:   false,                 // true 면 설정 창에도 없다 — 켤 수 없다

  pk:       true,                  // 신규만 · 필수 · 헤더 `*`
  sortable: true,                  // 기본 false — 정렬도 명시해야 열린다
  filter:   'set',                 // 생략하면 타입이 정한다

  renderer: 'badge',               // 표시만 바꾼다. 값은 원본
  editor:   'popupRef',            // 생략하면 타입이 정한다
  editable: (row) => …,            // 기본 false — 편집은 명시해야 열린다
  required: true,
  afterEdit: (row) => ({ … }),
  validate:  (v, row, ctx) => msg | null,
}
```

> **위 예시는 자주 쓰는 열둘이고 컬럼 키는 서른여섯이다.**
> **쓸 수 있는 이름과 기본값의 정본은 [declarations.md](./declarations.md) §1 이다** —
> 여기서 다시 적지 않는다(2026-09-04: 이 자리에 있던 표가 `sortable` 의 기본값을
> `true` 로 적고 있었고 소스는 `?? false` 였다. 같은 사실을 두 곳에 두면 한 곳이 낡는다).

**명시해야 열리는 것 둘**: `editable` 과 `sortable` 은 **없으면 꺼진다.**

**숨김이 두 층인 이유**: `visible` 은 *지금 안 보인다*(사용자가 켤 수 있다)이고
`hidden` 은 *이 사용자에게 없는 컬럼이다*(설정 창에도 없다).

## 2. 컬럼 유형 — 13종

**AG Grid 내장 9종을 전부 쓰고 커스텀 넷을 더한다.**

| 타입 | 기본 에디터 | 비고 |
|---|---|---|
| `text` | `text` | **긴 텍스트는 에디터로 가른다** — `largeText` · `textModal` |
| `number` | `number` | |
| `bigint` | `text` | **API 가 문자열로 내려야 의미가 있다** |
| `boolean` | — | **직접 쓰지 않는다.** `ynFlag` 로 감싼다 |
| `date` · `dateTime`(+`String`) | `date` | **AntD 달력** — 필터와 같은 것 |
| `object` | — | **쓰지 않는다** |
| **`ynFlag`** | **`switch`** | DB 가 `CHAR(1) 'Y'/'N'` 이다. **체크박스가 아니다** |
| **`code`** | `select` · `richSelect` | 표시는 코드명, 저장은 코드값 |
| **`popupRef`** | `popupRef` | 한 번 골라 여러 칸을 채운다 |
| **`list`** | `listModal` | **배열을 담는다** |

> **닫힌 집합이 아니라 *늘리는 조건이 있는* 집합이다.** 여기는 업무 도메인을 가리지 않는
> 베이스이므로 *"지금 화면에 사례가 없다"* 는 막는 근거가 아니다. **늘릴 때 지킬 것은 둘** —
> ① **Enterprise 기능에 기대지 않는다** ② **표시 형식은 타입이 아니라 `renderer` 다**
> (통화·퍼센트·전화번호는 새 타입이 아니다).

> **타입 목록에 미구현을 넣지 않는다.** 선언할 수 있는데 어댑터가 모르는 값이 있으면
> **조용히 무시**되고, 화면 개발자는 **자기가 오타를 냈는지 미구현인지 알 수 없다.**
> 늘리는 자리는 **그것을 처음 요구하는 화면**이다.

**날짜 에디터는 타입이 고른다.** 판의 기본은 텍스트 칸이라 그대로 두면 사람이
`2026-08-31` 을 손으로 치는데 **형식이 틀리면 조용히 값이 되지 않는다.**

## 3. 정렬과 필터 — 역할이 다르다

| | 검색 폼 | **컬럼 필터** |
|---|---|---|
| 무엇을 하나 | **서버에서 좁힌다** | **조회 결과 안에서 거른다** |
| 서버로 가나 | 간다 | **가지 않는다** |
| 저장에 영향 | — | **없다 — 숨겨진 행도 저장된다** |

**그래서 무엇을 거르고 있는지 화면이 말해야 한다.** 말하지 않으면 사용자가 필터를
검색으로 오해하고 *"데이터가 없어졌다"* 고 읽는다.

- **정렬은 헤더 클릭 3단계**(오름 → 내림 → 없음)이고 **판정은 서버**다.
- `set` 필터의 목록은 **로드된 행에서 모은다** — 서버에 묻지 않는다.

## 4. 편집

- **편집 전에 되는지 미리 답하고, 안 되면 이유를 말한다.** 열리지 않는 셀을 눌렀을 때
  아무 일도 일어나지 않으면 사용자는 **고장으로 읽는다.**
- **후작업(`afterEdit`)은 계산 컬럼을 위한 것**이다 — 수량을 고치면 금액이 따라온다.

## 5. 검증 — 두 시점, 세 층

| 시점 | 무엇이 도나 | 결과 |
|---|---|---|
| **입력 시** | **컬럼 공통(1층)만** — 그 셀 + 그 행 | 즉시 표시. **편집을 막지는 않는다** |
| **API 호출 전** | **세 층 전부** | 통과해야 서버로 간다 |

> **입력 시점에 컬럼 공통만 도는 이유** — 그때는 **사용자가 어느 버튼을 누를지 모른다.**
> 저장 규칙으로 검사했는데 승인 버튼을 누르면 검사가 어긋난다.

> **API 호출 전 검증을 생략하지 않는다.** 입력 시에만 하면 **붙여넣기 · 후작업 · 팝업**
> 으로 들어온 값이 검사를 건너뛴다 — **사람이 타이핑한 값만 검사하게 된다.**

> **저장뿐 아니라 모든 `actions` 가 같다.** 저장만 검증하면 실행 버튼이 **검증 안 된
> 화면 상태로 절차를 발동한다.**

### 세 층

| 층 | 어디에 | 언제 | 예 |
|---|---|---|---|
| **1. 컬럼 공통** | 컬럼의 `required` · `validate` | **입력 시 + 모든 API** | 필수 · 형식 · 범위 · 다른 컬럼에 따른 분기 |
| **2. API 별 컬럼** | `api.{save\|actions[]}.validate.columns` | **그 API 호출 전에만** | 승인할 때만 필요한 필수 |
| **3. API 별 그리드** | 〃 `.validate.grid` | 〃 | **행을 종합**해야 아는 것 — 합계 · 중복 키 · 최소 1건 |

```ts
validate: (value, row, ctx) => null | message                    // 1·2층
validate: (rows, ctx) => [] | [{ rowId, field?, message }]       // 3층
```

**왜 API 별로 가르나** — 같은 컬럼이 **저장할 때는 선택이고 승인할 때는 필수**일 수 있다.

| 대안 | 왜 기각하나 |
|---|---|
| 컬럼의 `validate` 안에서 API 를 분기 | **컬럼 선언이 화면의 버튼 구성을 알게 된다.** 방향이 거꾸로다 |
| 전부 그리드 단위로 올린다 | **어느 셀의 문제인지 붙일 자리가 없어진다** |
| API 마다 컬럼 배열을 따로 선언 | 컬럼이 API 수만큼 복제된다 |

**컬럼 검증이 값이 아니라 행 전체를 받는 이유** — *"출고 유형이 A 면 창고가 필수"* 같은
분기가 흔하다. 값만 받으면 검증이 전부 **그리드 단위로 밀려나고**, 그러면 어느 셀의
문제인지 붙일 자리가 없어진다.

**3층을 따로 두는 이유** — 합계·중복은 **행 하나만 봐서는 알 수 없다.** 그리드 검증의
`field` 가 **선택**인 것도 같은 이유다 — 합계 오류는 특정 셀에 귀속되지 않는다.

> **2층의 필수는 헤더 `*` 에 나오지 않는다.** 헤더는 **컬럼 선언**을 말하는데 API 별
> 필수는 *"그 버튼을 누를 때만"* 이라 상시 표시할 수 없다. 상시 필수는 1층의 `required` 로
> 선언하고, 그렇지 않은 것은 **확인 문구와 오류 메시지가 설명한다.**

> **3층의 생산자가 하나 더 있다** — `GridController.setIssues`. 엑셀 업로드가 그 자리이며,
> 파일에서 읽은 값이 컬럼의 어휘로 풀리지 않는 경우는 **저장 직전이 아니라 파일을 읽은
> 그 자리에서** 보여야 한다. 저장까지 미루면 사용자는 **412행을 다 훑고 나서** 처음 듣는다.
> **층이 하나 더 생긴 것이 아니다** — 나오는 것은 같은 `GridIssue[]` 이고, 갈리는 것은
> **누가 만드는가**뿐이다.

> **`params`(파라미터 모달)는 이 세 층의 대상이 아니다.** 그것은 그리드 행이 아니라
> **API 호출의 인자**이며 **모달이 자기 검증을 한다.**

**서버 검증이 없어지는 것은 아니다.** 프론트 검증은 UX 이고 방어는 서버다.

## 6. 마스터-디테일

- **디테일은 마스터의 선택에 종속된다.** 상태가 셋이다 — 선택 없음 · 선택됨 · 미저장.
- **마스터의 삭제는 디테일이 비어야 열린다.**
- **디테일의 부모 키는 `searchParams` 로 준다** — 조건 목록에 두면 **선택적**이 되어
  부모를 빠뜨린 요청이 전 그룹의 자식을 쏟는다([grid.md §7](./grid.md)).
- **저장 단위가 아닌 디테일에는 상태 컬럼을 두지 않는다.**
