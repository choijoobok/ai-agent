# 56. 그리드 편집과 검증 — 진입 · 훅 · 두 시점 세 층

- 상태: **초안** (Phase 4~5 경계. [54](./grid-column-contract.md) 에서 갈라져 나왔다 — §1.1)
- 최종수정일: 2026-08-28
- 관련: [53-grid-standard](./grid-standard.md) · [54-grid-column-contract](./grid-column-contract.md) · [55-grid-api-contract](./grid-api-contract.md) · [21-backend-architecture](../../backend/_study/architecture.md) §6-1 · [10-feature-inventory](../../../knowledge/features.md) §K(UX-10 · UX-14)
- **읽어야 할 때**: **편집 가능한 그리드를 만들 때** · 행마다 편집 가능 여부가 갈릴 때 · 계산 컬럼을 붙일 때 · **검증 규칙을 붙일 때**(컬럼 공통인지 API 별인지 — §3.2) · 그리드 공통 컴포넌트를 구현할 때(Phase 6)

## 1. 범위 — 값이 들어오고 검사받기까지

| 여기 있는 것 | 여기 없는 것 |
|---|---|
| 편집 진입 · 이동 · 취소(§2.2) | **컬럼 선언의 키 전체** → [54](./grid-column-contract.md) §2 |
| **편집 전 판단과 거부 메시지**(§2.1) | 어떤 타입이 어떤 **에디터**를 쓰나 → [54](./grid-column-contract.md) §5 |
| 편집 후 후작업 — 계산 컬럼(§2.3) | 팝업 참조(`popupRef`)의 **선언** → [54](./grid-column-contract.md) §6 |
| **검증**(§3) — 두 시점 · 세 층 · 실패 표시 | 일괄 저장 · 행 상태 · 삭제 상태 → [53](./grid-standard.md) §3 |
| — | **검증이 도는 시점**(호출 흐름) → **[55](./grid-api-contract.md)** §5~§8 |
| — | 서버 DTO 검증 → [21](../../backend/_study/architecture.md) §6-1 |

### 1.1 `54` 와의 분담 — 한 줄로

**[54](./grid-column-contract.md) 는 *"이 컬럼이 무엇인가"*, 여기는 *"그 값이 어떻게 들어오고 어떻게 검사받는가"* 다.**

| | [53](./grid-standard.md) | [54](./grid-column-contract.md) | 여기 |
|---|---|---|---|
| 단위 | 그리드 하나 | 컬럼 하나 | **한 번의 편집 · 한 번의 검증** |
| 답하는 질문 | 버튼이 어디 있나 · 저장은 언제 나가나 | 이 컬럼은 어떻게 정렬·필터·표시되나 | **이 셀을 고칠 수 있나 · 고치면 무엇이 따라오나 · 무엇이 통과를 막나** |
| 에디터 | — | **어느 것을 쓰나**(타입이 정한다) | **어떻게 도나**(진입 · 이동 · 훅) |

> **조회 전용 그리드만 만든다면 이 문서는 읽지 않아도 된다.** 그것이 [54](./grid-column-contract.md) 에서
> 이만큼을 갈라낸 이유다 — 컬럼을 선언하는 일과 편집을 설계하는 일은 **같은 순간에 하지
> 않는다**(설계 문서 모음 의 분할 기준).

### 1.2 여기서도 어휘는 우리 것이다

[ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md) 이 정한 대로 **화면은 `ag-grid` 를 import 하지 않는다.** 아래 `editable` ·
`afterEdit` · `validate` 는 전부 우리 어휘이며, **편집 전 판단 메시지와 검증 프레임워크는
AG Grid 에 대응이 없어 자체 구현**이다([54](./grid-column-contract.md) §7.2 의 7·8번).

## 2. 편집 — 진입 · 이동 · 전후 훅

### 2.1 편집 전 판단 — 되는지 미리 답하고, 안 되면 이유를 말한다

```ts
editable: true | false | (row, ctx) => true | { ok: false, message: '...' }
```

| 형태 | 언제 |
|---|---|
| `true` · `false` | 컬럼 전체가 **항상** 되거나 안 되거나 |
| **함수** | **행마다 다르다** — 다른 컬럼 값에 달렸다 |

함수 형태의 실물 둘 —

- *"이미 출고 마감된 주문은 수정 불가"* — 같은 행의 마감 상태가 결정한다
- *"자기 계정은 사용 여부를 못 바꾼다"* — [61](../../../../documents/screen/user/requirements.md) §3.7.1. **컬럼 전체가 아니라 특정 행의
  특정 컬럼**만 막는 경우다

**거부에는 메시지가 필수다.** 함수는 `false` 가 아니라 **`{ ok:false, message }`** 를
반환한다 — 메시지가 없으면 사용자는 **클릭이 먹지 않는 이유를 모르고**, 화면이 고장난 줄
안다. 메시지는 토스트(UX-10)로 낸다(편집 모드가 아니라 셀에 붙일 자리가 없다).

> **판정 시점은 편집 진입 직전이다.** 렌더 시점에 한 번만 하면 **같은 행의 다른 셀을 고쳐
> 조건이 바뀌었을 때 낡은 판정이 남는다** — 마감 상태를 바꿨는데 옆 셀이 여전히 잠겨 있다.

### 2.2 편집 모드 진입과 이동

| 동작 | 결과 |
|---|---|
| **더블 클릭** | 편집 모드 진입 — **`switch` 는 예외**([54](./grid-column-contract.md) §5.2), 클릭 한 번이 곧 확정 |
| `Enter` | 진입 · 편집 중이면 **확정** |
| **`Tab`** | 다음 **편집 가능** 셀로 — **읽기 전용 셀은 건너뛴다** |
| `Shift`+`Tab` | 이전 편집 가능 셀로 |
| `Esc` | **취소** — 값 원복 |
| **행 추가** | **편집 가능한 가장 왼쪽 셀**이 자동으로 편집 모드가 되고 **포커스가 들어간다**([55](./grid-api-contract.md) §3.6) |

- **행 끝에서 `Tab`** 은 **다음 행의 첫 편집 가능 셀**로 넘어간다. **마지막 행의 끝에서는
  멈춘다** — 새 행을 만들지 않는다. 만들면 `Tab` 을 한 번 더 눌렀을 뿐인데 빈 행이 쌓이고,
  그 행은 저장 시 검증에 걸린다
- 읽기 전용 셀을 더블 클릭하면 §2.1 의 메시지가 있을 때만 낸다. 없으면 아무 일도 하지 않는다
- **`switch` 는 `Tab` 으로 닿은 뒤 `Space` 로 토글**한다([54](./grid-column-contract.md) §5.2) — 마우스 없이도
  닿아야 한다
- **행 추가에서 자동 진입하는 이유** — 추가 직후 사용자가 할 일은 값 입력 하나뿐이다.
  더블 클릭을 한 번 더 요구할 이유가 없다

> **긴 텍스트는 읽기 전용이어도 열린다**([54](./grid-column-contract.md) §5.5) — 셀에서 볼 수 없으므로 에디터를
> **읽기 모드**로 연다. §2.1 의 거부 메시지가 나오지 않는 유일한 읽기 전용 컬럼이다.

### 2.3 편집 후 후작업 — 계산 컬럼

```ts
afterEdit: (row, ctx) => ({ amount: row.qty * row.unitPrice })
```

부분 객체를 반환하면 행에 머지한다. `null` 을 반환하면 아무 일도 없다.

| 규칙 | 왜 |
|---|---|
| **연쇄는 한 단계에서 멈춘다** | `afterEdit` 가 바꾼 값이 다른 컬럼의 `afterEdit` 를 **다시 부르지 않는다.** 서로를 부르면 무한 루프가 되고, 루프가 아니어도 **어느 컬럼이 먼저 도느냐로 결과가 갈린다** |
| 계산이 이어지면 **한 곳에서 전부** | 수량 → 금액 → 부가세라면 수량의 `afterEdit` 가 셋을 다 계산한다 |
| 후작업이 바꾼 값도 **행 상태를 만든다** | 이미 추가·수정이므로 새로 생기는 상태는 없다([53](./grid-standard.md) §3.2) |

**한 번의 편집이 도는 순서**

```
셀 값 확정 → popupRef.apply([54] §6) → afterEdit(§2.3) → 입력 시 검증(§3.1)
```

> **셀 편집기 밖에서 들어온 값도 같은 순서를 탄다.** 팝업이 채운 칸([54](./grid-column-contract.md) §6),
> 화면이 넣은 배열([54](./grid-column-contract.md) §5.6), 스캐너 입력이 전부 그렇다 — **경로가 달라도 규약을
> 비껴가지 않는다.**

## 3. 검증 — 두 시점, 세 층

### 3.1 두 시점에서 한다

| 시점 | 무엇이 도나 | 결과 |
|---|---|---|
| **입력 시** | **컬럼 공통 검증만**(§3.2 1층) — 그 셀 + 그 행 | 즉시 표시. 편집을 막지는 않는다 |
| **API 호출 전** | **세 층 전부** — 전체 행 + 그리드 단위 | 통과해야 서버로 간다([55](./grid-api-contract.md) §6 · §7) |

- **입력 시점에 컬럼 공통만 도는 이유** — 그때는 **사용자가 어느 버튼을 누를지 모른다.**
  저장 규칙으로 검사했는데 승인 버튼을 누르면 검사가 어긋난다
- **API 호출 전 검증을 생략하지 않는다.** 입력 시에만 하면 **붙여넣기 · 후작업(§2.3) ·
  팝업([54](./grid-column-contract.md) §6)** 으로 들어온 값이 검사를 건너뛴다 — 사람이 타이핑한 값만
  검사하게 된다
- 실패하면 **서버를 부르지 않는다**
- **저장뿐 아니라 모든 `actions` 가 같다**([55](./grid-api-contract.md) §2) — 저장만 검증하면 실행 버튼이
  검증 안 된 화면 상태로 절차를 발동한다

### 3.2 세 층으로 선언한다 — 컬럼 공통과 API 별

| 층 | 어디에 선언 | 언제 도나 | 예 |
|---|---|---|---|
| **1. 컬럼 공통** | 컬럼의 `required`([54](./grid-column-contract.md) §5.1) · `validate` | **입력 시 + 모든 API** | 필수 · 형식 · 범위 · **다른 컬럼에 따른 분기** |
| **2. API 별 컬럼** | `api.save.validate.columns`<br>`api.actions[].validate.columns` | **그 API 호출 전에만** | 승인할 때만 필요한 필수 |
| **3. API 별 그리드** | 〃 `.validate.grid` | 〃 | **행을 종합**해야 아는 것 — 합계 · 중복 키 · 최소 1건 |

시그니처는 층이 달라도 같다.

```ts
// 컬럼 단위 (1층 · 2층)
validate: (value, row, ctx) => null | message

// 그리드 단위 (3층)
validate: (rows, ctx) => [] | [{ rowId, field?, message }]
```

#### 왜 API 별로 가르나

**같은 컬럼이 저장할 때는 선택이고 승인할 때는 필수일 수 있다.** 사유 컬럼이 그렇다 —
임시 저장에는 없어도 되지만 승인에는 있어야 한다.

| 대안 | 왜 기각하나 |
|---|---|
| 컬럼의 `validate` 안에서 API 를 분기한다 | **컬럼 선언이 화면의 버튼 구성을 알게 된다.** 방향이 거꾸로다 — 컬럼은 자기 값만 알아야 한다 |
| 전부 그리드 단위로 올린다 | **어느 셀의 문제인지 붙일 자리가 없어진다**(§3.3) |
| API 마다 컬럼 배열을 따로 선언한다 | 컬럼이 API 수만큼 복제된다 |

**API 선언 옆에 두면** *"이 API 를 부르려면 무엇이 참이어야 하는가"* 가 **한곳에 모인다**
— [55](./grid-api-contract.md) §2 가 URL · 확인 문구 · 재조회 여부를 한 선언에 모은 것과 같은 이유다.

#### 컬럼 검증이 값이 아니라 행 전체를 받는 이유

> *"출고 유형이 `A` 면 창고가 필수"* 같은 분기가 흔하다. 값만 받으면 그 분기를 쓸 수 없어
> 검증이 전부 **그리드 단위로 밀려나고**, 그러면 **어느 셀의 문제인지 붙일 자리가 없어진다.**
> 행을 함께 받으면 셀에 귀속된 채로 분기할 수 있다.

#### 그리드 단위를 따로 두는 이유

합계·중복은 **행 하나만 봐서는 알 수 없다.** 컬럼 검증에 억지로 넣으면 매 셀 편집마다
전체 행을 훑게 되고, 그래도 *"어느 행이 잘못인가"* 에 답하지 못한다. 그리드 검증의
`field` 가 **선택**인 것도 같은 이유다 — 합계 오류는 특정 셀에 귀속되지 않는다.

#### 여기가 `list` 의 유일성 · 형식 · 개수를 받는 자리다

[54](./grid-column-contract.md) §5.6 이 `unique` · `pattern` · `max` 를 컬럼 키로 두지 않은 것은 **그것이 전부
검증이기 때문**이다. 배열은 `validate` 에 **통째로** 들어오므로 개수도 중복도 여기서 본다 —
그리고 *"창고가 A 면 최대 50개"* 같은 조합이 **처음부터 표현된다.**

| 컬럼 키로 남은 것 | 왜 |
|---|---|
| `required`([54](./grid-column-contract.md) §5.1) | **헤더가 `*` 를 그리려면 알아야 한다** — 표시에 나타난다 |
| 유일성 · 형식 · 개수 | **표시에 나타나지 않는다** → 여기 |

> **어느 층인지는 편집 어휘가 정한다**(2026-09-02 — 샘플의 태그 · [48](../../../playbook/INDEX.md) §8).
>
> | 화면 | 층 | 세는 것 |
> |---|---|---|
> | ①(`list` 컬럼) | **1층 — 컬럼** | 셀 값인 **배열의 길이**. 다른 행을 볼 필요가 없고, 3층으로 올리면 *어느 셀인가* 를 잃는다 |
> | ⑤(같은 데이터를 행으로) | **3층 — 그리드** | **판의 행 수**. 삭제 행이 빠진 뒤라 그 수가 곧 *저장 뒤의 개수* 다(§3.3) |
>
> **문구는 하나다.** 사용자가 아는 사실이 *이 주문에 태그가 몇 개까지* 하나이므로 두 층이
> 같은 메시지 키를 쓴다 — 갈라 쓰면 같은 규칙이 두 문장으로 설명된다.
>
> **서버는 값을 하나만 갖는다**(도메인의 상수). 화면마다 갈라 두면 ⑤에서 스물한 개를
> 만들 수 있고, 그러면 배열을 통째로 보내는 ①이 **자기가 만들지도 않은 개수에 걸려**
> 그 주문을 저장하지 못한다 — 사용자에게는 *고친 것도 없는데 저장이 거부된다* 로 보인다.

> **`params` 는 이 세 층의 대상이 아니다.** 파라미터 모달이 받는 값은 그리드 행이 아니라
> **API 호출의 인자**이며 **모달이 자기 검증을 한다**([55](./grid-api-contract.md) §8) — 조회조건 폼이 자기
> 검증을 하는 것과 같은 자리다. 여기 세 층은 **그리드가 가진 데이터**만 본다.

> **2층의 필수는 헤더 `*` 에 나오지 않는다.** 헤더는 **컬럼 선언**을 말하는데([53](./grid-standard.md) §8.3)
> API 별 필수는 *"그 버튼을 누를 때만"* 이라 상시 표시할 수 없다. 상시 필수는 1층의
> `required` 로 선언하고, 그렇지 않은 것은 **확인 문구와 오류 메시지가 설명한다.**

> **3층의 생산자가 하나 더 생겼다**(2026-09-02 — `GridController.setIssues`). 엑셀 업로드가
> 그 자리다([68](../../../playbook/INDEX.md) §9.2): 파일에서 읽은 값이 컬럼의 어휘로 풀리지 않는 경우(코드명이 두
> 코드에 걸린다 · 숫자가 아니다 · 파일 안에서 키가 겹친다)가 있고, 그것은 **저장 직전이
> 아니라 파일을 읽은 그 자리에서** 보여야 한다 — [68](../../../playbook/INDEX.md) §8.6 이 *미리보기가 곧 행 상태* 라고
> 적은 화면이며, 저장까지 미루면 사용자는 **412행을 다 훑고 나서** 처음 듣는다.
>
> **층이 하나 더 생긴 것이 아니다.** 나오는 것은 같은 `GridIssue[]` 이고 표시도 §3.3
> 그대로다 — 갈리는 것은 **누가 만드는가**뿐이다. 조회·저장이 이 값을 자기 결과로 덮는다.

### 3.3 실패를 어떻게 보여주나

1. **건수를 먼저 알려준다** — *"3건의 오류가 있습니다"*. 없으면 사용자는 하나 고치고
   저장하기를 반복한다
2. **첫 실패 행으로 스크롤**하고 그 셀에 **포커스**를 준다
3. 실패한 셀을 표시한다(테두리 · 배경)
4. 메시지를 낸다 — 한 건이면 셀 툴팁, 여러 건이면 **목록**
5. **목록의 항목을 클릭하면 그 셀로 이동한다**

> **툴팁 하나로는 아무 말도 하지 않는 것과 같았다**(2026-08-31 실물). 넷째 줄(*메시지를
> 낸다*)이 구현에서 **셀 툴팁 하나**로만 서 있었고, 그 툴팁은 판의 기본 지연이 **2초**라
> 붉은 셀에 마우스를 올려도 2초를 버텨야 나왔다 — IP 형식이 아닌 값을 넣으면 **테두리만
> 빨개지고 이유가 어디에도 없었다.**
>
> 셋을 함께 고쳤다.
>
> | | |
> |---|---|
> | **입력 시점** | 칸을 고쳐 규칙을 어기면 **그 자리에서 토스트**로 말한다. §2.1 의 편집 거부와 **같은 통로**다 — 뜻은 다르지만(*고칠 수 없다* 대 *고쳤는데 그대로 저장되지 않는다*) 사용자가 알아야 하는 것은 같다: **지금 한 입력이 그대로 남지 않는다**. §3.1 의 *편집을 막지 않는다* 는 그대로다 |
> | **툴팁** | 지연을 **300ms** 로 줄인다. 0 으로 두면 셀 사이로 마우스가 지나갈 때마다 툴팁이 **따라다닌다** — 겨냥해서 멈춘 것과 지나간 것을 가르는 만큼만 기다린다 |
> | **저장 시점** | 건수 아래에 **어긋난 규칙을 줄로** 낸다. 컬럼 이름을 앞에 붙이고(같은 문구가 여러 컬럼에서 난다), **같은 줄은 한 번만** 내며(열 행이 같은 규칙을 어기면 고칠 일이 하나다), **열 줄에서 끊고 남은 수를 말한다** |
>
> **행 번호를 적지 않는다.** 화면의 번호는 *보이는 자리*(판의 `rowIndex`)에서 나오므로
> 클라이언트 정렬이 걸린 판에서는 우리가 센 배열 순서와 **어긋난다** — 틀린 번호는 없는
> 번호보다 나쁘다. 어느 셀인지는 위 ②가 이미 데려간다.
>
> **⑤(목록의 항목을 클릭하면 그 셀로 이동)는 아직 없다.** 목록이 컬럼 단위로 접혀 있어
> 클릭 하나가 가리키는 셀이 여럿이며, 그것을 열려면 목록의 단위를 *행마다* 로 되돌려야
> 한다 — 그때 위의 *행 번호* 문제를 함께 풀어야 하므로 요구가 올 때 같이 본다.

| 예외 | |
|---|---|
| **필터로 숨겨진 행** | **필터를 풀고** 그 행으로 이동한다([54](./grid-column-contract.md) §4.1) — 포커스를 줄 수 없는 곳에 오류를 남기지 않는다 |
| **꺼져 있는 컬럼**(`visible: false`) | **그 컬럼을 켜고** 셀로 이동한다([54](./grid-column-contract.md) §2.1) — 필터를 푸는 것과 같은 이유다 |
| **`hidden` 컬럼** | **검증 대상이 아니다** — 편집할 수 없으므로 실패가 날 자리가 없다([54](./grid-column-contract.md) §2.1) |
| **삭제 상태 행** | **검증에서 뺀다**([53](./grid-standard.md) §3.2) — 지울 행의 값은 저장되지 않는다 |
| 〃 (그리드 검증) | **삭제 행을 뺀 결과로 계산한다** — 합계·최소 1건은 저장 후의 모습을 물어야 한다 |
| 무변경 행 | 검증한다 — 그리드 검증(합계·중복)의 대상이기 때문이다 |

### 3.4 서버 검증이 없어지는 것은 아니다

프론트 검증은 **UX** 다. 최종 판정은 **서버 DTO 검증**이며([21](../../backend/_study/architecture.md) §6-1) 프론트가
통과시킨 값도 서버가 거부할 수 있다. [60](../../../../documents/screen/_standalone/README.md) §4.2 가 비밀번호 규칙에서 같은 판단을 했다 —
**규칙의 원본은 서버 한 곳**이고 화면은 그것을 미리 보여주는 것이다.
