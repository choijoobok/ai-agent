# 53. 그리드 표준 — 크롬 · 편집 · 마스터-디테일

- 상태: **초안** (Phase 4~5 경계. [61](../../../../documents/screen/user/requirements.md) §2 에서 분리 — §1.2)
- 최종수정일: 2026-08-29
- 관련: **[54-grid-column-contract](./grid-column-contract.md)**(컬럼 계약 — 짝 문서) · [55-grid-api-contract](./grid-api-contract.md) · [56-grid-edit-validation](./grid-edit-validation.md) · [24-frontend-stack](./frontend-stack.md) §6·§7 · [ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md) · [ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) · [51-main-shell](./main-shell.md) §9.6 · [10-feature-inventory](../../../knowledge/features.md) §K(UX-06 · UX-13 · UX-14)
- **읽어야 할 때**: **그리드가 있는 화면을 설계할 때**(`61`~`67` · 샘플) · **그리드 공통 컴포넌트를 만들 때**(Phase 6) · 목업에 그리드를 그릴 때 · 마스터-디테일 화면의 버튼이 언제 열리는지 확인할 때

## 1. 범위 — 화면마다 다시 정하지 않는다

한 줄 요약 — **자리와 동작을 고정하고 내용만 화면이 채운다.**

| 여기 있는 것 | 여기 없는 것 |
|---|---|
| 크롬 — 제목 · 버튼 · 페이징의 자리(§2) | 컬럼 **타입 어휘** → [24](./frontend-stack.md) §6.1 |
| 편집 상태와 **일괄 저장**(UX-14 — §3) | **필터 · 에디터 어휘** → [ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md) |
| 컬럼 고정 구조(§4) | 전역 표시 속성(행 높이 · 폰트) → [51](./main-shell.md) §9 |
| 그리드 설정 창(UX-06 — §5) | 컴포넌트 **시그니처** → Phase 6 |
| **마스터-디테일 연동**(§6) | 화면별 컬럼 · 조회조건 → `60`~`79` |
| **셀·행의 색과 우선순위**(§8) | **테마 토큰 생성** → [51](./main-shell.md) §9.7 |
| — | **API 계약 · 버튼 자동 렌더링 · 실행 흐름** → **[55](./grid-api-contract.md)** |
| 목업 어휘(§7) | 목업 문서군의 절 양식 → [60](../../../../documents/screen/_standalone/README.md) §2 |
| — | **컬럼 하나의 계약** — 정렬 · 필터 · 유형 · 에디터 → **[54](./grid-column-contract.md)** |
| — | **편집 동작 · 전후 훅 · 검증** → **[56](./grid-edit-validation.md)** |

> **이 문서는 Phase 6 공통 컴포넌트의 요구사항이다.** 컴포넌트가 이 규약을 만족하면 화면은
> **컬럼만 선언**하며, **그 컬럼을 어떻게 선언하는지는 [54](./grid-column-contract.md) 가 갖는다.** 반대로 여기 없는 동작을 화면이 직접 구현하기 시작하면 화면마다
> 그리드가 갈라지고 [ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md) 의 판 교체 경계도 함께 무너진다.

### 1.1 편집 폼을 두지 않는다 — 이것이 나머지의 전제다

**화면에 남는 폼은 조회조건(`<SearchForm>`) 하나다.** 상세 편집 폼도, 등록 모달도 두지
않는다. 등록은 **그리드의 새 행**이고 수정은 **셀 편집**이며 저장은 §3 의 일괄 처리다.

| 왜 | |
|---|---|
| 저장 경로가 하나가 된다 | [23](../../backend/_study/security-design.md) §4 가 이미 *"그리드 저장 표준이 리스트 CUD 일괄 처리"* 로 정했다. 폼을 함께 두면 **같은 테이블에 저장 경로가 둘**이 되고 액션 판정도 두 API 를 따라간다 |
| 컴포넌트가 하나로 닫힌다 | 폼 상세는 화면마다 레이아웃이 갈린다. 그리드는 §2 의 크롬 하나로 전 화면이 같다 |
| 화면 전환이 없다 | 목록에서 보고 그 자리에서 고친다 — 상세 폼이 접혔다 펴지는 왕복이 사라진다 |

**상태 플래그가 섞인 테이블도 폼으로 도망가지 않는다.** 지켜야 할 규칙은 폼이 아니라
**컬럼별 편집 가능 여부**로 지킨다 — [61](../../../../documents/screen/user/requirements.md) §2.3 이 계정 상태 넷으로 그 사례를 보인다.

> **여기서 없앤 것은 *행을 편집하는 폼*이다.** 실행 버튼이 임의의 인자를 받는
> **파라미터 모달**은 그리드 행이 아니라 **API 호출의 인자**를 받으므로 이 규칙 밖이다 —
> [55](./grid-api-contract.md) §8.
>
> **엑셀 업로드 탭도 이 규칙 밖이다**([ADR-0024](../../../records/adr/0024-excel-upload-dedicated-tab.md)). 같은 테이블의 행을 편집하지만
> **저장 API 를 새로 만들지 않고 업무 탭의 `save` 를 그대로 부른다** — 판별 기준은
> *"같은 테이블에 저장 경로가 둘이 되는가"* 이고, 여기서는 **하나**다. 다른 것은
> **행이 어디서 왔는가**(파일 vs 손입력)뿐이다.

### 1.2 `61` 에서 분리한 이유 (2026-08-27)

이 규약은 [61](../../../../documents/screen/user/requirements.md) §2 에서 시작했다. 그런데 편집 상태·컬럼 고정·마스터-디테일 연동이
더해지면서 **문서 하나 분량**이 됐고, `62`~`67` 이 *사용자 화면 문서*를 참조해야 하는
모양이 됐다. 설계 문서 모음 문서 크기 규약(*"읽는 순간이 갈리면 분할한다"*)의 대상이다 —
**화면을 설계하는 순간**과 **그리드 규약을 확인하는 순간**은 다르다.

번호는 `50~59`(프론트 레이아웃 · 디자인 시스템)에 든다 — [51](./main-shell.md) 이 셸의 자리를 정했듯
여기는 **콘텐츠 안 그리드의 자리**를 정한다.

## 2. 크롬 — 모든 그리드가 같은 자리에 같은 것을 둔다

화면마다 다르면 사용자가 화면마다 다시 배운다.

```
┌ 사용자 목록   [Ⓐ]  [조회] [저장] [잠금 해제]   [Ⓑ]   [⤓▾] [⚙] ┐
│  ↑ 제목       임의   ↑ api 선언이 채운다        임의   ↑ 도구   │
├──────────────────────────────────────────────────────────────────┤
│  그리드 본문                                                      │
├──────────────────────────────────────────────────────────────────┤
│ 총 128건 · 7페이지      ‹ 1 2 3 … 7 ›              20건씩 ▾       │
└──────────────────────────────────────────────────────────────────┘
```

> **그리드는 남는 높이를 채운다 — 셸이 그것을 줘야 한다**(2026-08-29 — 구현). 크롬이
> 헤더·본문·푸터 셋이고 늘어나는 것은 본문뿐이므로, 콘텐츠 영역의 높이가 `auto` 면
> 화면의 `height: 100%` 가 **0 으로 풀려 그리드가 줄 하나 없이 접힌다.** 실제로 그렇게
> 렌더됐고, 셸의 콘텐츠 영역을 뷰포트에 고정하는 것으로 고쳤다 — [51](./main-shell.md) §5.
>
> **② 엑셀과 ③ 그리드 설정은 아직 없다.** ③은 개인화 테이블 스키마가 §9 의 미결이라
> **저장할 곳이 정해지기 전에는 켰다 꺼도 남지 않고**, ②는 첫 실물이 서버 POI 경로라
> ([63](../../../../documents/screen/code/requirements.md) §3.6) 다운로드 이력과 함께 온다. 같은 이유로 **판(AG Grid)의 컬럼 메뉴도 꺼 둔다** —
> 열어 두면 저장되지 않는 컬럼 설정을 만지게 된다.

### 2.1 상단 — 왼쪽은 제목, 오른쪽은 버튼

| 자리 | 내용 | 액션 |
|---|---|---|
| 왼쪽 | **그리드 제목** | — |
| **Ⓐ** | **임의 컨트롤** — 조회 앞. 업무성([55](./grid-api-contract.md) §3.2) | **`actionCd` 가 선언한 것**([55](./grid-api-contract.md) §3.3) |
| 오른쪽 ① | 조회 · 저장 · **화면 고유 버튼** — **`api` 선언이 채운다**([55](./grid-api-contract.md) §3) | `R` · `S` · **버튼마다 다르다** |
| **Ⓑ** | **임의 컨트롤** — 도구 앞. 도구성(〃) | 〃 — 인쇄는 `EXPORT` 다 |
| 오른쪽 ② | **엑셀 다운로드** — 아이콘 + 드롭다운 + **툴팁** | `E` |
| 오른쪽 ③ | **그리드 설정** — 아이콘. `settings={false}` 로 끌 수 있다 | **없음** |

**자동으로 나오는 것은 다섯**(조회 · 저장 · 각종 실행 · 엑셀 · 설정)이고, **임의 컨트롤이
들어갈 자리는 Ⓐ · Ⓑ 둘뿐**이다 — ① 사이에는 끼울 수 없다([55](./grid-api-contract.md) §3.2).

- **①은 손으로 놓지 않는다.** `api` 선언([55](./grid-api-contract.md) §2)에서 자동으로 렌더링되며 **권한
  없는 것은 감춘다**([55](./grid-api-contract.md) §3)
- **Ⓐ Ⓑ 도 손으로 놓지 않는다.** `controls` **선언**으로 받으며 렌더 함수(JSX)를 열지
  않는다 — 열면 그리드의 잠금 상태를 모르는 버튼이 섞인다([55](./grid-api-contract.md) §3.7)
- **도구 둘(②③)은 항상 맨 오른쪽 고정이다.** 화면마다 ①의 개수가 달라도 도구의 위치가
  흔들리지 않는다 — 사용자가 매번 찾지 않게 하는 것이 자리를 고정하는 이유다
> **크롬을 두르지 않는다**(2026-08-30 — 실물). ①의 줄과 푸터에 <b>배경도 테두리도</b>
> 두지 않는다 — AG Grid 가 이미 자기 테두리를 그리므로 위아래를 또 감싸면 **선이 두 겹**이고,
> 배경을 깔면 그 둘이 **본문과 다른 판**처럼 떠 보인다.
>
> **높이는 버튼이 없어도 같다.** 버튼이 하나도 없는 그리드([63](../../../../documents/screen/code/requirements.md) §3.2 의 하단)는 제목
> 줄만큼만 높아져 **같은 화면의 그리드 둘이 다른 크롬**을 갖게 됐다. 버튼 한 줄의 높이가
> 바닥값이다.
>
> **버튼에는 아이콘이 붙는다** — 조회 `🔍` · 행 추가 `＋` · 저장 `💾`. 글자만 있으면
> 비슷한 길이의 버튼 셋이 나란히 서서 **훑을 때 자리로 구분**하게 된다.
>
> **아이콘만 있는 버튼에는 툴팁을 단다**(2026-08-30 실물 — 엑셀에서 한 번 뺐다 되돌렸다).
> 뺐던 이유는 *"누르면 항목 이름이 바로 나온다"* 였는데, 그 항목이 **현재 페이지 · 전체**
> 라 **무엇의** 현재 페이지인지 말하지 않는다 — 열어 봐도 이것이 엑셀이라는 말은 어디에도
> 없다.
>
> 반대로 **글자가 이미 보이는 것에는 달지 않는다.** 판(antd)이 세그먼트·셀렉트·페이지
> 번호에 브라우저 기본 툴팁을 달아 두는데, 그것은 **보이는 글자를 그대로 한 번 더** 띄우고
> 모양도 셸의 툴팁과 다르다(OS 의 노란 상자다). `title: ''` · `showTitle={false}` 로 끈다.
>
> **③을 끄는 자리가 있다**(2026-08-30 실물 — `settings={false}`). 개인화할 것이 없는
> 그리드가 있기 때문이다: 컬럼이 몇 개 안 되고 **전부 봐야 하는** 디테일 그리드가
> 그렇다([63](../../../../documents/screen/code/requirements.md) §3.2의 하단). 버튼만 감추는 것이 아니라 **저장된 설정을 읽지도 않는다** —
> 바꿀 길이 없는 설정을 화면마다 한 번씩 물어보는 것은 왕복 하나를 그냥 버리는 일이고,
> 화면에 그리드가 둘이면 왕복도 둘이다.
>
> **위아래 여백은 8px 이다**(2026-08-30 실물 — 4 에서 올렸다). 크롬을 두르지 않기로 한
> 대가로 ①의 줄과 푸터가 **판의 테두리에 붙어** 보였다 — 배경이 없으니 여백이 유일한
> 경계다. 줄과 푸터가 같은 값을 쓴다: 위아래가 다르면 그리드가 한쪽으로 눌린다.

- **권한 없는 버튼은 감춘다**([51](./main-shell.md) §6). `E` 가 없으면 ②도 감추고, **Ⓐ Ⓑ 의 컨트롤도
  `actionCd` 를 선언했으면 같은 판정을 받는다**([55](./grid-api-contract.md) §3.3) — 엑셀을 막고 인쇄를
  열어 두면 막은 것이 옆문으로 나간다
- **그리드 설정은 권한 대상이 아니다.** 개인화이며 `(MENU_CD, ACTION_CD)` 쌍에 대응이
  없다 — 액션 4종은 **데이터에 대한 것**이다([23](../../backend/_study/security-design.md) §4)
- **제목은 화면 제목이 아니라 그리드 제목이다.** 한 화면에 그리드가 여럿이므로(마스터 +
  탭 N) 화면 단위 제목 줄은 자리를 둘 곳이 없고, 화면 이름은 **탭바와 브레드크럼이 이미
  낸다**([51](./main-shell.md) §5). [24](./frontend-stack.md) §7 의 `<PageContainer>`(제목 + 액션버튼)가 하던 일이
  `<DataGrid>` 헤더로 옮겨온다 — Phase 6 컴포넌트 목록의 입력이다

> **①을 "실행 버튼" 이라고 부르지 않는다.** `EXECUTE`(액션 `X`)와 섞인다. 잠금 해제는
> ①의 버튼이지만 액션은 **`SAVE`** 다([61](../../../../documents/screen/user/requirements.md) §3.4.1). **자리 이름과 액션 이름을 같게 쓰면
> 시드가 틀린다** — ①은 *화면 고유 버튼*이고 액션은 버튼마다 경로 접두가 정한다([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)).

### 2.2 엑셀 다운로드는 항목 둘짜리 드롭다운이다

| 항목 | 경로 |
|---|---|
| **현재 페이지** | 프론트 생성(`exceljs`) — **지금 화면에 보이는 행.** 컬럼 필터가 걸려 있으면 **걸러진 결과**다([54](./grid-column-contract.md) §4.1) |
| **전체** | 프론트 생성 — 조회 조건으로 전량 재조회 후 생성. `ui.excel.max-rows` 상한([43](../../../knowledge/sys/code.md) §6.4) |

**두 항목 모두 컬럼은 지금 보이는 것만 나간다** — 사용자가 끈 컬럼은 빠지고 `hidden`
컬럼은 언제나 없다([54](./grid-column-contract.md) §2.1). *"화면에 없던 컬럼이 파일에 있다"* 는 그 자체로 문의가 된다.

~~[ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) 의 세 갈래 중 프론트 둘이 여기다. 세 번째(서버 POI · 임의 API)는 이
버튼이 아니다~~ → **세 번째도 이 버튼이다**(2026-09-02 — 아래).
**이력은 어느 경로든 남는다**([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md)).

#### 세 번째 갈래를 ①로 미루지 않는다 (2026-09-02)

[ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) 는 이미 *"사용자에게는 셋이 같은 버튼 묶음으로 보일 수 있다 — 임의 API
경로도 **현재 페이지**·**전체** 라는 이름을 그대로 쓸 수 있다"* 고 적었다. 이 절이 그것을
①로 미룬 것이 **ADR 과 어긋나 있었다.**

미루면 상단-하단 그리드 화면에서 사용자는 **같은 뜻의 버튼을 두 자리에서** 만난다 — ②의
아이콘과 ①의 *엑셀 다운로드*. 어느 쪽이 무엇을 주는지는 눌러 봐야 알고, 그 차이는
**파일을 열고 나서** 드러난다.

**`<DataGrid excel={...}>` 하나가 셋을 가른다.**

| 선언 | 경로 |
|---|---|
| 없음 | 프론트 생성 둘 — 지금까지와 같다 |
| `page` · `all` | **이름은 그대로, 경로만 서버.** 상단-하단을 조인해 한 장으로 내리는 화면이 이 자리다 |
| `extra[]` | 구분선 아래에 **화면 고유 항목**. 권한은 항목마다(`actionCd`, 기본 `EXPORT`) |

**서버 경로는 프론트 이력을 부르지 않는다.** `POST /api/common/excel/saveLog` 는 *호출이 없는
경로* 의 구멍을 메우는 것이고([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md)), 서버 생성은 **요청이 도착하는 것 자체가
기록**이다 — 또 부르면 한 번 내려받은 것이 **두 행**이 된다.

**파일 이름은 서버가 정한다**(`Content-Disposition`). 이 갈래의 파일은 그리드의 표가
아니므로(헤더 블록 + 상품 표, 다중 시트) 그리드 제목으로 이름을 지으면 **내용과 이름이
어긋난다**. 서버가 말하지 않을 때만 우리 규칙(`제목_20260902_1432.xlsx`)으로 떨어진다.

**판을 바꿔도 이 선언은 그대로다**([ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md)) — 담긴 것이 URL 과 메시지 키뿐이라
AG Grid 의 판본과 접점이 없다. 실물은 [68](../../../playbook/INDEX.md) §5.4.

**아이콘만 두는 이유** — 항목이 둘이라 어느 라벨도 대표하지 못하고, ①이 길어지면 도구가
밀린다. 라벨은 드롭다운을 열면 나온다.

> **아이콘도 비활성으로 보여야 한다**(2026-08-31 실물). 하단 탭이 잠겼을 때(§6.1 의
> `disabled`) 이 버튼만 **활성 상태의 색**으로 남아 있었다 — 눌리지는 않는데 아이콘이 켜져
> 보이면 *왜 안 눌리나* 가 된다.
>
> 원인이 **툴팁과 드롭다운 사이**였다. antd 의 드롭다운은 `disabled` 를 자식에게 전해
> 주는데(`child.props.disabled ?? disabled`) **그 자식이 툴팁**이라 버튼에는 닿지 않았다.
> 잠금은 **버튼이 직접 받아야** 한다 — 감싼 것이 하나 늘 때마다 조용히 새는 자리다.

> **이 버튼이 서는 화면은 메뉴가 정한다**(2026-08-30 · [ADR-0027](../../../records/adr/0027-menu-declared-export-action.md)). 조회 API 를 가진
> 그리드면 컴포넌트는 언제나 그릴 준비가 돼 있고, 실제로 보이는가는 `EXPORT` 권한이
> 가른다([51](./main-shell.md) §6 — 권한이 없으면 아예 없다). **그런데 그 권한을 줄 수 있는 메뉴가
> `SYS_MENU.EXPORT_YN` 으로 한정된다** — [52](../../../knowledge/sys/menu.md) §4.2 의 액션 열에 `E` 가 없는 화면은
> 부여 자체가 거부되므로 버튼이 설 수 없다. **화면 쪽에 끄는 스위치를 두지 않는 이유**가
> 그것이다: 감추는 것이 아니라 **줄 수 없게** 해서 닫는다.

> **섰다**(2026-08-30 — 구현). 두 항목 모두 `exceljs` 로 브라우저에서 만든다.
>
> | | |
> |---|---|
> | **컬럼** | 판에게 묻는다(`getAllDisplayedColumns`) — 사용자가 끈 컬럼과 옮긴 순서가 <b>판의 상태</b>다. 시스템 컬럼(번호·상태·삭제)은 우리 선언에 없어 자연히 빠진다 |
> | **값** | <b>화면의 어휘</b>로 만든다([54](./grid-column-contract.md) §5) — 코드는 이름으로, `list` 는 나열로, `ynFlag` 는 `Y`·`N`. 판의 렌더러를 쓰지 않는 이유는 <b>*전체* 경로에 판이 없기</b> 때문이다: 거기서만 다른 규칙을 쓰면 같은 컬럼이 두 파일에서 다르게 나온다 |
> | **전체의 왕복** | 안에서 <b>페이징한다</b>. `PageSpec.MAX_SIZE` 가 1000 이라 한 번에 못 받으며, 서버에 전용 경로를 내면 <b>같은 화이트리스트를 두 곳에서</b> 유지하게 된다 |
> | **상한 판정** | <b>첫 응답의 총 건수</b>로 한다. 5만 건을 다 받아 놓고 거절하면 상한이 지키려던 것을 이미 다 치른 뒤다 |
> | **0건** | 파일을 만들지 않는다 — 열어 보고 나서야 아는 것이 가장 나쁘다 |
>
> **다운로드 이력도 섰다**(2026-08-30 — 구현). 파일을 저장한 <b>직후</b>에
> `POST /api/common/excel/saveLog` 를 부른다([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md)).
>
> | | |
> |---|---|
> | **부르는 자리** | `workbook.ts` — **파일이 나가는 자리가 곧 기록이 나가는 자리**다. 버튼마다 부르면 새 버튼이 잊을 수 있고, 잊어도 **아무 증상이 없어** 드러나지 않는다 |
> | **보내는 것** | `scope`(현재 페이지 · 전체) · `rowCount` · `columnKeys`. **`menuCd` 는 보내지 않는다** — `X-Menu-Code` 헤더가 이미 나르고 그것이 `SYS_LO_ACCESS.MENU_CD` **컬럼**이다. body 에도 담으면 같은 사실이 한 행에 두 벌이다 |
> | **받는 곳** | 전용 테이블이 없다([47](../../../knowledge/sys/notification.md) §4.2). **컨트롤러도 저장하지 않는다** — 사용 이력 인터셉터가 모든 `/api/**` 를 남기므로 **요청이 도착하는 것 자체가 기록**이다 |
> | **실패** | 삼킨다. 파일은 이미 사용자의 디스크에 있고 *"이력을 남기지 못했습니다"* 는 **할 수 있는 일이 없는 문구**다 |
> | **0건** | 부르지 않는다 — 파일을 만들지 않으므로 내려받은 것이 없다 |
>
> **`EXPORT` 권한이 값을 내는 것이 이 기록과 짝을 이룰 때다**([ADR-0027](../../../records/adr/0027-menu-declared-export-action.md)). 프론트 생성
> 엑셀에는 서버가 막을 요청이 없어 그 권한은 **집행되는 통제가 아니라 운영 사실**이며
> ([23](../../backend/_study/security-design.md) §4), 부여만 있고 기록이 없으면 *누가 내려받았나* 에 답할 수 없다.

> **업로드 버튼은 여기 없다.** 엑셀 업로드는 **전용 탭**이고 그 탭의 저장은 ①의 저장
> 버튼이다([ADR-0024](../../../records/adr/0024-excel-upload-dedicated-tab.md)) — ②는 **내보내기 전용**이다. 그리고 **전체 다운로드가 곧
> 업로드 양식**이다. 컬럼이 화면과 같으므로 양식이 갈릴 수 없고, 양식 파일을 따로
> 배포·관리할 것이 없다.

### 2.3 하단 — 셋으로 나눈다

| 자리 | 내용 |
|---|---|
| 왼쪽 | **총 건수 · 총 페이지 수**. 컬럼 필터가 걸리면 **이 페이지 N건 중 M건**을 덧붙인다 |
| 중앙 | **페이지 네비게이션** |
| 오른쪽 | **페이지 사이즈 콤보** |

**컬럼 필터는 서버로 가지 않는다**([54](./grid-column-contract.md) §4.1) — 총 건수·페이지 수는 필터와 무관하게
서버 기준이며, 필터가 거른 결과는 **덧붙인 문구**로만 나타난다. 그 표기가 *"필터가
현재 페이지에만 걸린다"* 를 사용자에게 알리는 유일한 자리다.

> **셀 하나를 `Ctrl+C` 로 복사한다**(2026-08-30). **복사하는 것은 데이터가 아니라
> 화면에 보이는 글자다** — 값이 `Y` 인 칸을 사람은 *사용* 으로 보고 있고 붙여 넣으려는
> 것도 그것이다([54](./grid-column-contract.md) §5.4). 그래서 값을 다시 포맷하지 않고 **그려진 셀을 읽는다.**
>
> **다만 셀의 글자가 전부 값인 것은 아니다**(2026-08-30 — 실물에서 잡음). 처음에는
> *배지든 태그든 렌더러가 무엇을 하든 결과가 같다* 고 적고 셀을 통째로 읽었는데, 값 뒤에
> 배지를 덧붙이는 셀에서 `CODE_REF_KEY시스템` 이 복사됐다 — **붙여 넣을 수 없는 문자열**이다.
>
> | | 배지가 무엇인가 | 복사 |
> |---|---|---|
> | `renderer: 'badge'` | **값 대신** 그린다 | **된다** — 그것 말고 복사할 것이 없다 |
> | `badge` ([54](./grid-column-contract.md)) | 값 **뒤에** 덧붙는 **내력** | **빠진다** — 값은 따로 있다 |
>
> **판정은 그린 쪽이 한다.** 어댑터가 곁들인 조각에 표시를 남기고 복사는 그것을 뺄 뿐이다 —
> 복사 쪽에서 태그 모양이나 색으로 짐작하면 **새 렌더러가 생길 때마다 조용히 틀린다.**
> 조용한 것이 이 결함의 성질이었다: 복사는 성공한 것처럼 보이고 **붙여 넣은 곳에서야**
> 드러난다.
>
> 판의 클립보드 기능은 Enterprise 라([ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md)) 우리가 직접 한다. **가로채지 않는 자리
> 둘**이 있다 — 글자를 골라 둔 사용자(그가 원하는 것은 고른 그것이다)와 편집 중(입력 칸
> 안의 복사는 브라우저의 일이다). 글자가 없는 셀(스위치)만 예외로 `Y`·`N` 을 만든다.

> **쪽수 후보는 100 · 500 · 1000 이다**(2026-08-30 실물). 백오피스는 한 화면에 많이 놓고
> **훑는다** — 스무 줄씩 넘기는 것은 *찾는* 일에 맞는 크기이고, 여기서 흔한 일은 죽 훑어
> 내리다 하나를 집는 것이다. 맨 위가 1000 인 것은 **서버의 상한**이며(`PageSpec.MAX_SIZE`)
> 후보에 상한을 넘는 값을 두면 고르는 순간 400 이 난다. 화면이 `pageSizes` 로 바꿀 수
> 있다 — 행 하나가 무거운 화면은 100 도 버겁고, 코드표는 1000 이 편하다.
>
> **첫 조회의 크기도 함께 옮겼다**(20 → 100). 둘이 다르면 **콤보에 없는 값이 골라진 채로**
> 화면이 뜬다.
>
> **페이지 이동 넷에만 툴팁을 단다** — 이전 · 다음 · 다섯 쪽 앞뒤. 숫자 항목은 빼는데,
> 그 위에 같은 숫자를 띄우는 것은 말을 더하는 것이 아니라 가리는 것이다. 가운데 둘이
> **다섯 쪽**인 것은 판의 기본값이며 점 셋으로만 그려져 몇 쪽인지 알 길이 없다.

> **푸터의 모양은 화면이 선언하지 않는다 — 응답의 `mode` 가 정한다**([72](../../backend/_study/api-conventions.md) §3.8).
>
> | `mode` | 왼쪽 | 중앙 | 오른쪽 |
> |---|---|---|---|
> | `offset` | 총 건수 · 총 페이지 | 번호 네비 | 사이즈 콤보 |
> | `cursor` | `N건 조회됨` | `‹ 이전 · 다음 ›` | 사이즈 콤보 |
> | **`all`** | **건수만** | **없다** | **없다** |
>
> **페이징 여부는 서버 소스가 이미 정한다** — 화면이 한 번 더 적으면 미러링이다.
> `all` 의 첫 사례가 [62](../../../../documents/screen/menu/requirements.md) §4.2.2 의 메뉴 트리이며 **디테일 탭과 코드 상세가 같은
> 모양**이다. 그 그리드는 **정렬도 필터도 클라이언트**라 서버를 다시 부르는 것이
> 조회 버튼뿐이다(§3.1).

**페이지 사이즈는 3층이다** — [43](../../../knowledge/sys/code.md) §6.1 의 폴백과 **같은 방향**이며 아래가 위를 덮는다
(그쪽은 층이 둘이다).

| 층 | 어디 | 누가 정하나 |
|---|---|---|
| 시스템 기본값 | `ui.grid.page-size` (`SYS_CONFIG` — [43](../../../knowledge/sys/code.md) §6.4) | 관리자 |
| **화면 기본값** | **화면 코드의 그리드 선언** | 개발자 — 화면이 자기 데이터 양을 안다(로그는 100, 사용자는 20) |
| 개인 설정 | 그리드 개인화(DB — §5) | 사용자 — 콤보를 바꾸면 **그 화면에** 기억된다 |

**화면 기본값을 코드에 두는 이유** — DB 에 두면 화면을 추가할 때마다 시드가 필요하고,
시드를 빠뜨린 화면은 시스템 기본값으로 **조용히** 떨어진다. 코드에 두면 화면 선언과 함께
리뷰된다.

> **총 건수는 공짜가 아니다.** `COUNT` 쿼리가 한 번 더 나가며 대용량 이력 테이블에서
> 비싸다. **[64](../../../../documents/screen/log/access/requirements.md) §2.3 이 로그 3종에 대해 *생략* 을 골랐다**(2026-08-28) — 그 화면들은
> 이 표의 왼쪽·중앙이 **`N건 조회됨`** 과 **`‹ 이전 · 다음 ›`** 으로 바뀐다. **예외는 화면이
> **엔드포인트가 정하고 응답의 `mode` 가 나른다** — [72](../../backend/_study/api-conventions.md) §3.8. **화면은 선언하지 않는다.**
>
> **생략을 고르면 정렬이 딸려 온다.** 번호 없는 이동은 정렬 키가 고정이어야 성립하므로
> **헤더 정렬이 한 컬럼으로 좁혀진다** — 둘은 한 결정이며 따로 되돌릴 수 없다([64](../../../../documents/screen/log/access/requirements.md) §2.3).

### 2.4 검색 폼의 버튼은 **초기화 하나**다 — 조회는 그리드가 갖는다

`<SearchForm>`(UX-15)은 **화면에 남는 유일한 폼**이고(§1.1) 그 아래에 마스터 그리드가 있다.
**그리드 ①이 이미 조회 버튼을 갖는다**(§2.1 · [55](./grid-api-contract.md) §3.1) — 폼에도 두면 **같은 조회를
부르는 버튼이 둘**이 된다.

| | |
|---|---|
| 조회 · 검색 버튼 | **없다** — 그리드 ①의 조회가 그것이다 |
| **초기화** | **있다** — 조건과 **컬럼 필터를 함께** 지운다([54](./grid-column-contract.md) §4.2) |
| 접기 · 펼치기 · 개인화 | **브레드크럼 줄**([51](./main-shell.md) §5.1) — 폼 밖이다 |

- **`Enter` 는 남는다.** 버튼을 없앤 것이지 제스처를 없앤 것이 아니다 — 폼 안에서 `Enter`
  를 치면 마스터 그리드의 조회가 돈다. 폼을 채우고 손을 옮기지 않는 것이 **가장 흔한
  동선**이다
- **검색 폼은 마스터 그리드의 것이다.** 디테일은 마스터의 선택에 종속되므로(§6.1) 자기
  조회조건을 갖지 않는다 — 폼이 하나인 것과 그리드가 여럿인 것이 어긋나지 않는 이유다
- **초기화를 폼에 남기는 이유** — 지우는 대상이 **폼의 내용**이다. 그리드 ①에 두면
  *"무엇을 초기화하나"* 가 헤더에서는 보이지 않는다

> **버튼을 없애도 조회 시점은 바뀌지 않는다.** 조건을 고치는 즉시 조회하지 **않는다** —
> 서버 왕복이며, 세 칸을 채우는 동안 세 번 나간다. 컬럼 필터가 즉시 걸리는 것과 다르며
> 그 비대칭이 [54](./grid-column-contract.md) §4.1 이 정한 둘의 역할 차이 그대로다.

> **화면에 들어오는 것도 조회 시점이 아니다** (2026-09-02 — 적혀 있지 않아 한 번 어긋났다).
> **첫 조회는 사용자가 누른다.** 전 화면이 그렇게 돌고 있었는데 그 사실이 어디에도 적혀
> 있지 않아, [68](../../../playbook/INDEX.md) §11.1 이 *"샘플은 자동으로 한다"* 로 닫아 두는 일이 생겼다 — 규약이
> 글로 없으면 **각자 다른 것을 규약이라고 믿는다.**
>
> 자동으로 하지 않는 근거는 조건 즉시 조회를 막은 것과 같다: 들어오자마자 나가는 왕복은
> **사용자가 조건을 고르기 전의 결과**를 가져오고, 멀티탭(UX-02)에서 탭을 여섯 복원하면
> **여섯이 한꺼번에** 나간다. 빈 그리드가 *아직 아무것도 묻지 않았다* 를 말하는 자리다.

## 3. 편집과 저장 — 기본은 일괄이다 (UX-14)

### 3.1 저장은 버튼을 누를 때 한 번 일어난다

셀을 고치면 **행에 상태가 붙을 뿐** 서버로 나가지 않는다. ①의 저장 버튼을 누르면
**추가 · 수정 · 삭제 상태의 행을 한 번에** 보낸다.

- API 는 **하나**다 — `save` 하나이며 등록/수정/삭제로 쪼개지 않는다. 행 상태는 URL 이
  아니라 **페이로드 안**에 있다([23](../../backend/_study/security-design.md) §4 — 액션을 4종에서 닫는 이유)
- 그래서 액션도 `SAVE` 하나다. 행 상태별로 권한을 가르는 것은 **API 경계에서 집행할 수
  없으므로** 권한 화면의 장식이 된다(〃)
- **컬럼 필터로 숨겨진 행도 함께 저장된다.** 필터는 **표시만** 거른다([54](./grid-column-contract.md) §4.1) —
  행 상태는 그대로 남아 있다. 그래서 저장 전 확인에서 **보이지 않는 변경 행이 몇 건인지**
  알린다. 알리지 않으면 *"내가 안 고친 것이 저장됐다"* 가 된다

#### 미저장 변경이 있으면 **재조회를 확인한다**

**서버 재조회는 그리드의 행을 통째로 갈아 끼운다** — 상태가 붙은 행이 사라진다.
재조회를 유발하는 행위는 **넷**이고 **넷 다 같은 규칙**을 따른다.

| 행위 | |
|---|---|
| **조회** 버튼(§2.1) | 확인 다이얼로그 |
| **페이지 이동** | 〃 — [55](./grid-api-contract.md) §3.6 이 이미 적었다 |
| **페이지 사이즈 변경**(§2.3) | 〃 |
| **정렬**(헤더 클릭) | 〃 — **서버 정렬이므로 재조회다**([54](./grid-column-contract.md) §3) |

**하나만 적으면 나머지 셋에서 사고가 난다.** [55](./grid-api-contract.md) §3.6 은 *페이지 이동* 에만
적었는데 **정렬이 더 자주 눌린다.**

- 다이얼로그는 **미저장 변경이 있을 때만** 뜬다 — 훑는 동안에는 아무 일도 없다
- **신규 행만이 아니다.** 수정·삭제 상태의 행도 같이 사라진다(§3.2)
- **컬럼 필터와 접기는 여기 없다** — 서버를 부르지 않는다([54](./grid-column-contract.md) §4.1 · §4.3)
- 문구와 선택지는 **UX-10 과 같다**(§6.1 의 마스터 행 전환) — **규칙이 하나여야 학습이 하나다**

#### 그런데 대부분의 편집 그리드에는 이 상황이 오지 않는다

[72](../../backend/_study/api-conventions.md) §3.0 이 조회를 둘로 갈랐다. **그 선이 여기서도 쓰인다.**

| | 검색 폼이 **있다** (마스터) | 검색 폼이 **없다** (디테일 탭 · 코드 상세 · 트리) |
|---|---|---|
| 조회 | 동적형 | 고정형 |
| 응답의 `mode` | `offset` · `cursor` | **`all`**([72](../../backend/_study/api-conventions.md) §3.8) |
| 정렬 | **서버** — 재조회 | **클라이언트** — 재조회 아님 |
| 위 넷 중 남는 것 | **넷 다** | **조회 버튼 하나** |

**`all` 응답을 받은 그리드에서는 정렬해도 편집이 살아 있다.** 페이지가 없고 정렬이
클라이언트라 **갈아 끼울 일이 없기 때문**이다.

> **`offset` 인데 결과가 1페이지뿐이어도 다이얼로그가 뜬다.** 건수로 판정하면
> *"정렬해도 편집이 안 날아간다"* 를 배운 사용자가 **데이터가 늘어난 날 작업을 잃는다**
> ([72](../../backend/_study/api-conventions.md) §3.8).

> **그래도 규칙이 필요한 이유** — **검색 폼이 있으면서 편집도 되는 그리드가 있다.**
> 사용자 목록이 그렇다([52](../../../knowledge/sys/menu.md) §4.3 — *기본정보 탭을 두지 않으므로 마스터 그리드의
> 컬럼이다*). 그 화면은 `offset` 이고 **넷 다 다이얼로그를 받는다.**

### 3.2 행 상태 넷 — 왼쪽 끝 컬럼이 보여준다

**편집 가능한 그리드는 맨 왼쪽에 상태 컬럼을 갖는다.**

| 상태 | 아이콘 | 언제 | 행 표시 |
|---|---|---|---|
| 무변경 | (빈칸) | 조회된 그대로 | — |
| **추가** | `PlusOutlined` | 행 추가 버튼([55](./grid-api-contract.md) §3.6 — **선언해야 나온다**) | 강조 배경 |
| **수정** | `EditOutlined` `UndoOutlined` | 저장된 행의 셀을 고쳤을 때. **되돌리기가 편집 취소다**(§3.3) | 강조 배경 |
| **삭제** | `DeleteOutlined` | 삭제 아이콘을 눌렀을 때 | **취소선 + 회색 · 셀 편집 불가** |

> **글리프가 아니라 아이콘이다**(2026-08-30 실물). `＋`·`✕`·`✎` 는 **글꼴이 주는 글자**라
> 사용자가 고른 글꼴마다 굵기와 크기가 달라지고([51](./main-shell.md) §9.3), 셸의 다른 아이콘과 나란히
> 놓이면 혼자 다른 계열로 보인다. 삭제 컬럼의 토글도 같다 — 표시 전 `DeleteOutlined`,
> 표시 후 `UndoOutlined`.

> ~~**상태 컬럼은 *편집 가능* 이 아니라 *저장 단위* 에 붙는다**(2026-08-29 — 구현).~~
> **되돌렸다**(2026-08-30 — 실물). [63](../../../../documents/screen/code/requirements.md) §3.2 의 하단에 상태 컬럼을 두면 *영영 빈 칸* 이라고
> 적었는데, **비어 있던 것은 컬럼이 아니라 구현이었다** — 하단이 값만 갈아 끼우고
> `rows.ts` 의 전이를 타지 않아 상태가 서지 않았을 뿐이다.
>
> **상태 컬럼은 편집이 열리는 그리드에 붙는다.** 마스터의 *수정* 표시는 *"이 키를 고쳤다"* 까지만
> 말하고 **어느 언어를 고쳤는지는 말하지 않는다** — 언어가 다섯이면 하단을 훑어야 한다.
>
> **삭제 컬럼은 여전히 저장 단위의 것이다.** 남의 저장에 실리는 그리드는 행을 지우지
> 않는다(그 하단의 행 집합은 마스터 행의 `list` 이므로 지울 대상이 아니다).
>
> **편집 가능 여부는 저장 권한에서 곧바로 끌어내지 않는다** — 그랬다면 그 하단이 영영
> 읽기 전용이었을 것이고, 그것이 화면의 절반이다. 저장 단위가 다른 그리드는 **마스터의
> 저장 권한을 넘겨받는다**([63](../../../../documents/screen/code/requirements.md) §3.7).

> **저장 단위인데 조회가 없는 그리드가 나왔다**(2026-08-30 — [61](../../../../documents/screen/user/requirements.md) §4.4). 개인 예외 목록은
> **행 상태도 삭제 컬럼도 저장 버튼도 갖는데** 자기 조회 경로가 없다 — 그 그리드를 먹이는
> 것은 **권한 트리의 조회 하나**이고, 둘이 *같은 데이터의 두 표시* 라 원본이 하나여야 하기
> 때문이다.
>
> | | 63 §3.2 의 하단 | **여기** |
> |---|---|---|
> | 조회 | 자기 것이 있다 | **없다** — 남의 응답이 먹인다 |
> | 저장 | **남의 저장에 실린다** | **자기 저장이다** |
> | 크롬 | 조회 버튼 있음 | **조회 버튼이 없다** — 선언이 없으면 버튼도 없다(§2.1) |
>
> **엑셀은 그래도 있다.** *전체* 가 부르는 전량 조회는 그 경우 **화면이 든 행 전부**를
> 돌려준다 — 서버 페이징이 없으므로 그것이 실제로 전량이다([55](./grid-api-contract.md) §2).

- 상태 컬럼은 **읽기 전용 표시**다. 사용자가 상태를 직접 고르지 않는다
- **한 행은 상태 하나만 갖는다.** 수정한 행을 삭제하면 삭제이며, 되돌리면 수정으로
  돌아가는 것이 아니라 **무변경**으로 돌아간다 — 셀 값도 함께 되돌린다. 부분적으로
  되돌리면 *"무엇이 남았는지"* 를 화면이 설명할 수 없다

### 3.3 신규 행은 끝까지 신규다

| 행위 | 결과 |
|---|---|
| 신규 행의 셀을 고친다 | **추가 상태 유지** — 수정으로 바뀌지 않는다 |
| 신규 행의 삭제 아이콘을 누른다 | **그리드에서 즉시 제거** — 삭제 상태로 두지 않는다 |

**서버에 없는 행이기 때문**이다. 수정으로 바뀌면 저장 시 `UPDATE` 가 나가 0건이 갱신되고,
삭제 상태로 남으면 **존재한 적 없는 행을 지우라고** 보내게 된다. 둘 다 서버가 판단할
문제가 아니라 화면이 만들지 말아야 할 상태다.

#### 값이 원본과 같아지면 **상태도 무변경으로 돌아간다** (2026-08-31)

되돌리기 아이콘은 *한 번에 전부* 되돌리고, 이것은 **한 칸씩 되돌린 결과가 마침 전부인
경우**다. 두 길의 끝이 같아야 상태 컬럼이 값과 어긋나지 않는다.

| | |
|---|---|
| 판정 | **조회 직후 스냅샷(`original`)과 내용 비교** — 고쳤다는 사실을 따로 기억하지 않는다 |
| 어디서 | `editRow` — **셀 편집이 지나는 유일한 문**이다(스위치도 여기로 온다) |
| 신규 행 | **그대로 추가**다(위 표) — 원본이 없으므로 비교할 것도 없다 |
| 부분 되돌림 | **수정이 남는다** — 나머지 칸이 아직 다르다 |

**그대로 두면 넷이 함께 틀린다.** 그 행이 저장 대상에 들고, 확인 모달의 *수정 N건* 이
실제보다 많으며, 서버는 **같은 값을 쓰는 `UPDATE`** 를 한 번 낸다 — 그리고 사용자에게는
*"되돌렸는데 표시가 안 사라진다"* 로 보인다.

**참조가 아니라 내용으로 비교한다.** 동적 컬럼은 값을 맵의 한 칸으로 들고 있어
([54](./grid-column-contract.md) §2.2 의 `refs`) 편집이 **맵을 새로 만들어** 쓴다 — 참조로 비교하면 그 칸은 영영
*바뀐 것* 이 된다. 판정은 `sameData` 하나이며 [63](../../../../documents/screen/code/requirements.md) §3.2 의 마스터-디테일도 같은 것을 쓴다.

#### 편집 취소 — **수정한 행에만 있다** (2026-08-30)

상태 컬럼의 *수정* 아이콘 옆 되돌리기다. 누르면 그 행이 **원본 값 · 무변경 상태**로 돌아간다.

| 상태 | `UndoOutlined` | 되돌리는 수단 |
|---|---|---|
| **수정** | **있다** | 여기 |
| 추가 | 없다 | **삭제 아이콘** — 되돌리는 것이 곧 없애는 것이다(위 표) |
| 삭제 | 없다 | **삭제 아이콘을 다시** — §3.4 |

**셋을 한 아이콘에 두지 않는다.** 그러면 같은 자리의 같은 그림이 *상태마다 다른 일* 을
하게 되고, 사용자는 누르기 전에 자기 행의 상태를 먼저 읽어야 한다.

- **값도 함께 되돌린다.** 상태만 지우면 화면에는 고친 값이 남은 채 *무변경* 이 되고,
  그 행은 **저장되지 않으면서 저장된 것처럼** 보인다
- **검증 실패 표시도 함께 지운다** — 원본은 저장에 실리지 않으므로 잴 것이 없다
- **마스터-디테일에서는 마스터까지 내려갈 수 있다**([63](../../../../documents/screen/code/requirements.md) §3.2) — 고친 것이 그 값
  하나뿐이었다면 마스터는 이제 원본과 같다. 그대로 두면 저장할 것이 없는데 *수정* 표시가 남아
  *"저장이 안 된다"* 로 읽힌다

### 3.4 삭제는 상태이지 실행이 아니다

**그리드의 맨 오른쪽에 삭제 컬럼을 둔다.** 아이콘을 누르면 그 행이 **삭제 상태가 될
뿐**이며 서버로 나가지 않는다 — 저장 버튼을 눌러야 지워진다.

- **되돌릴 수 있다.** 삭제 상태의 행에서 아이콘을 다시 누르면 무변경으로 돌아간다.
  되돌릴 수 없으면 실수했을 때 **다시 조회하는 수밖에 없고, 그러면 다른 편집이 함께
  날아간다**
- 삭제 상태의 행은 **셀 편집이 막힌다** — 지울 행을 고치는 것은 의미가 없다
- 확인 다이얼로그는 **저장 시점에 한 번**이다(UX-10). 아이콘마다 물으면 여러 행을 지울 때
  같은 질문을 반복하게 된다

### 3.5 삭제 컬럼이 없는 그리드가 있다

**물리 삭제를 하는 테이블에만 삭제 컬럼이 나온다.** 삭제 대신 상태 컬럼이나 종료일로
끝내는 테이블이 이미 여럿이다.

| 테이블 | 못 쓰게 하는 수단 | 삭제 컬럼 |
|---|---|---|
| `SYS_USER` | `USE_YN='N'` — 물리 삭제 없음([41](../../../knowledge/sys/user-role.md) §4.5 · USER-02) | **없다** |
| `SYS_ROLE` | `USE_YN='N'` — 부여 행이 살아나야 한다([42](../../../knowledge/sys/menu.md) §3.1) | **있다** — 한 번도 쓰이지 않은 역할은 지운다([62](../../../../documents/screen/menu/requirements.md) §3.5) |
| **`SYS_MENU`** | `USE_YN='N'` — 유효 권한의 최종 게이트([23](../../backend/_study/security-design.md) §4) | **없다** — **즉시 저장 그리드**다(§3.6). 삭제는 ①의 버튼이며 게이트가 넓다([62](../../../../documents/screen/menu/requirements.md) §4.8) |
| `SYS_USER_ROLE` | 회수는 `VALID_TO_DT`. 삭제는 **오등록 정정**용 | 있다 |
| `SYS_USER_MENU_AUTH` | 〃([61](../../../../documents/screen/user/requirements.md) §4.7) | 있다 |
| `SYS_USER_IP_ALLOW` | 삭제 | 있다 |

> **삭제 컬럼이 없다고 상태 컬럼까지 없는 것은 아니다.** 추가·수정은 여전히 일어난다.
> 둘은 독립이다 — 편집 가능하면 상태 컬럼, 물리 삭제 가능하면 삭제 컬럼이다.

### 3.6 즉시 저장은 예외이며 화면이 선언한다

| 즉시 저장이 맞는 경우 | 예 |
|---|---|
| **행 상태로 표현할 수 없는 편집** | 순서 변경 — 형제 전체가 다시 쓰인다([42](../../../knowledge/sys/menu.md) §4). 트리 부모 이동 |
| **누적할 자리가 없는 편집** | 즐겨찾기 순서([42](../../../knowledge/sys/menu.md) §7) |
| **락이 필요한 편집** | 메뉴 트리 저장 — `@CustomLock(WAIT)` 로 직렬화한다([42](../../../knowledge/sys/menu.md) §4) |

**한 그리드 안에서 일괄과 즉시를 섞지 않는다.** 즉시 저장 그리드에는 **상태 컬럼도 저장
버튼도 두지 않는다** — 섞으면 저장 버튼이 무엇을 저장하는지 사용자가 알 수 없고, 이미
저장된 편집과 아직 아닌 편집이 같은 화면에 있게 된다.

## 4. 컬럼 고정 — 양끝은 시스템, 안쪽은 사용자

```
┌──────┬──────┬────────┬──────────┬ ─ ─ ─ ─ ─ ─ ┬──────────┬────────┐
│ [No] │ [☑] │ [상태] │ 좌 고정   │ 스크롤 영역  │  우 고정  │ [삭제] │
│ 시스템│ 시스템│ 시스템 │ 사용자    │   사용자     │  사용자   │ 시스템 │
└──────┴──────┴────────┴──────────┴ ─ ─ ─ ─ ─ ─ ┴──────────┴────────┘
                                ←── 가로 스크롤은 가운데만 ──→
```

| 영역 | 누가 정하나 | 숨김 | 이동 |
|---|---|---|---|
| **행 번호** | 시스템 — **모든 그리드에 항상** | 불가 | 불가 |
| **선택 체크박스** | 시스템 — **다중 선택 그리드에만** | 불가 | 불가 |
| **상태 컬럼** | 시스템 — 편집 가능 그리드에 **항상** | 불가 | 불가 |
| 좌 고정 | 사용자(§5) | 가능 | 가능 |
| 스크롤 영역 | 〃 | 가능 | 가능 |
| 우 고정 | 사용자(§5) | 가능 | 가능 |
| **삭제 컬럼** | 시스템 — 물리 삭제 가능한 그리드에 **항상**(§3.5) | 불가 | 불가 |

**양끝을 사용자가 건드릴 수 없는 이유** — 상태 컬럼을 숨기면 **무엇이 바뀌었는지 알 수
없고**, 삭제 컬럼이 스크롤 밖으로 밀리면 가로 스크롤이 있는 화면에서 **삭제할 수단이
사라진다.** 사용자가 스스로 화면을 망가뜨릴 수 있는 설정은 두지 않는다.

#### 행 번호와 체크박스의 순서 (2026-08-30 — 구현)

| | |
|---|---|
| **번호가 맨 왼쪽** | 번호는 **행을 부르는 이름**이다 — 옆 사람에게 *"3번 행"* 이라고 말할 수 있어야 한다. 체크박스를 앞에 두면 *행을 부르는 이름* 앞에 *행에 하는 일* 이 놓인다 |
| **페이지를 넘어 이어진다** | `page × size + 보이는 자리 + 1` 이다. 페이지마다 1부터 다시 세면 <i>"몇 번째 데이터인가"</i> 를 사용자가 손으로 계산한다 |
| **컬럼 필터가 걸리면 다시 매긴다** | 걸러진 행은 자리를 비우는 것이 아니라 목록에서 빠진다. 필터가 현재 페이지 안에서만 걸린다는 사실은 푸터가 말한다(§2.3 · [54](./grid-column-contract.md) §4.2) |
| **정렬 대상이 아니다** | 번호는 **값이 아니라 자리**다 |
| **판의 선택 컬럼을 쓰지 않는다** | AG Grid 가 붙이는 것은 `lockPosition: 'left'` 라 **언제나 맨 앞**이고, 번호를 그보다 왼쪽에 두는 **내장 행번호 컬럼(`rowNumbers`)은 Enterprise** 다([ADR-0004](../../../records/adr/0004-antd-with-ag-grid.md)) — Community 에서 내장 체크박스를 켜면 순서가 **체크박스 → 번호** 가 된다. 그래서 체크박스도 시스템 컬럼으로 직접 만든다. **판의 의도도 `번호 → 체크박스` 다**(판이 컬럼을 조립하는 순서가 그렇다) — 갈리는 것은 설계가 아니라 **유료 경계**다 |
| **`Shift` 로 범위를 고른다**(2026-09-02) | 위 결정의 대가다 — 판은 **내장 선택 컬럼에만** 수식키를 붙이므로(`inferNodeSelections`) 우리가 직접 한다(`shared/grid/selectRange`). 수식키 없는 클릭이 **앵커**를 옮기고, `Shift` 가 거기부터 칠하고, 칠한 범위 안을 다시 누르면 **줄어들고**, `Ctrl`(`⌘`)+`Shift` 는 **푼다** |
| **범위가 고른 것을 비우지는 않는다** | 여기서 판과 **일부러 갈린다.** 판은 앵커가 선택돼 있지 않으면 선택 전체를 리셋하지만, 이 체크박스가 가리키는 것은 **실행의 대상**이고(§7 · 55 §7) 사용자가 여러 번에 걸쳐 모은다 — 범위 하나 칠했다고 앞서 고른 행이 사라지면 **무엇이 사라졌는지 화면이 말하지 않는다.** 푸는 것은 **직전 `Shift` 가 칠한 구간**뿐이며, 그것은 *방금 한 일을 고치는 것* 이라 잃는 것을 사용자가 안다 |
| **자리가 갈아 끼워졌으면 범위를 잡지 않는다** | 범위는 **보이는 순서**의 구간이라 인덱스로 세는데, 조회·정렬·필터·페이지 이동이 그 자리를 통째로 바꾼다. 앵커는 행 ID 를 함께 들고 있다가 어긋나면 **한 행 토글로 떨어진다** — 남의 자리를 칠하는 것보다 아무것도 안 하는 편이 낫다 |
| **다중일 때 행 클릭으로 선택되지 않는다** | 체크박스만이 선택 수단이다. 클릭 선택을 함께 열면 스크롤하다 흘린 클릭 하나가 **고른 것을 통째로 갈아 치운다** |
| **전체 선택은 *보이는 행*** | `forEachNodeAfterFilter` 다 — 걸러진 행까지 고르면 **보이지 않는 것을 고른 줄 모른 채** 저장하게 된다 |

- **`hidden` 컬럼은 이 표의 어느 칸도 아니다**([54](./grid-column-contract.md) §2.1) — 화면에 나오지 않으므로 고정할
  자리가 없고 설정 창에 줄도 없다. `visible: false` 로 꺼 둔 컬럼은 **사용자 영역 그대로**이며
  켜면 자기 고정 상태로 돌아온다
- **틀고정은 좌 · 우 두 방향이다.** 사용자는 안쪽에서 좌/우 고정을 각각 지정한다
- **고정 폭 합에 상한**을 컴포넌트가 건다 — 시스템 두 컬럼을 포함한 좌우 고정 폭의 합이
  뷰포트의 일정 비율을 넘으면 스크롤 영역이 사라져 그리드가 못 쓰게 된다
- 조회 전용 그리드는 양끝 컬럼이 없으므로 **전체가 스크롤 영역 + 사용자 고정**이다

> | 〃 이름은 **툴팁** | 선 둘의 생김새가 같다. 늘 글자를 붙이면 컬럼 목록 사이에 글자 줄이 끼어 읽는 흐름이 끊긴다 — 대신 압정을 **고정되는 쪽 끝**에 둔다 |
> | 〃 여는 순간 **양끝으로 모은다** | 선언이 가운데 컬럼에 `pinned` 를 적어 두었을 수 있다(판은 알아서 끝으로 옮겨 그린다). 그대로 그리면 **선 위에 고정 아닌 컬럼**이 섞여 경계선의 뜻이 무너진다 |
> | **목록이 스크롤한다** | 컬럼 수는 화면이 정하므로 상한이 없다. 창이 화면보다 길어지면 **저장 버튼이 아래로 밀려 보이지 않는다.** 끌다가 목록 밖으로 나가면 판이 스스로 밀어 준다(`@dnd-kit` 의 자동 스크롤) — **한 번에 끝까지** 옮길 수 있다 |
> | **제목에 그리드 이름** | 마스터-디테일이면 창이 둘이고 생김새가 같다 — 어느 것을 건드리고 있는지 **창이 말하지 않으면 알 수 없다** |
> | **페이지 사이즈는 아직 없다** | 켜면 화면에 들어오는 순간 저장된 크기로 <b>조회가 한 번 돌아야</b> 하는데, 지금 그리드는 사용자가 눌러야 읽는다 — 그 규칙을 먼저 정해야 하는 일이다 |
> | **초기화는 행을 지운다** | 지금의 기본값을 계산해 저장하지 않는다. 기본값은 <b>화면 선언</b>이고 배포마다 바뀔 수 있다 — 굳혀 두면 *초기화했는데 옛 기본값* 이 된다 |
> | **버튼이 넷이다 — `취소 적용 ⋯ 저장 초기화`**(2026-08-31 개정) | <b>가르는 선은 DB 다.</b> 왼쪽 둘은 <b>DB 를 건드리지 않고</b> 오른쪽 둘은 <b>행을 넣거나 지운다</b> — <i>되돌릴 수 있는가</i> 가 그 선에서 갈리므로, 잘못 눌렀을 때의 값도 거기서 갈린다 |
> | 〃 **적용은 화면에만 두고, 되감을 자리를 여기로 옮긴다** | 고친 것은 이미 화면에 들어가 있으므로(아래 <i>적용과 저장</i>) 이 버튼이 하는 일은 <b>여기까지를 남기겠다</b> 를 말하는 것이다. <b>강조하지 않는다</b> — 이 창에서 대개 하려는 것은 저장이고, 같은 무게로 두면 <i>어느 쪽이 남는 것인가</i> 를 매번 읽어야 한다 |
> | 〃 **취소는 언제나 켜져 있다** | <b>마지막으로 남기기로 한 자리</b>로 되감고 닫는다 — 저장했거나 적용한 것, 둘 다 없으면 선언으로. 헤더를 끌어 바꾼 순서와 창에서 고치는 중인 것은 <b>아직 남기기로 한 것이 아니므로</b> 함께 물린다 |
> | 〃 **초기화는 저장된 설정이 있을 때만 켜진다** | 판정이 <i>화면이 선언과 다른가</i> 가 아니라 <b>지울 행이 있는가</b> 다. 그래서 이 버튼의 상태가 곧 <b>*이 그리드가 개인화됐는가*</b> 의 답이며, 꺼졌을 때는 <b>툴팁이 이유를 말한다</b> — 눌러 봐야 아무 일이 없는 회색 버튼은 스스로 아무것도 설명하지 못한다 |
> | 〃 **왜 하나로는 안 됐나** | 잠깐 <i>되돌릴 것이 있는가</i> 하나로 켜고 껐더니, 창에서 컬럼을 켜고 끄기만 해도 초기화가 켜졌고 사용자가 그것을 <b>저장됨</b> 으로 읽었다(2026-08-30 실물 — <i>"저장을 안 눌렀는데 자동 저장인가"</i>). <b>버튼 하나가 두 일을 겸하면 그 두 상태를 사람이 구분할 수 없다</b> |
> | **전부 끈 채로 남길 수 없다** | 빈 그리드가 되면 <b>되돌릴 컨트롤이 그 그리드 안에</b> 있다. <b>저장과 적용이 함께 막는다</b> — 적용도 되감을 자리를 옮기므로, 저장에서만 막으면 <b>취소를 눌러도 빈 판으로 돌아온다</b>. 고치는 <i>도중</i> 에는 막지 않는다: 마지막 체크를 끄는 순간이 이미 빈 판이라 <b>지우고 다시 고르는</b> 흔한 순서마다 창이 말을 걸게 된다 |
> | **권한이 없다** | 내 화면을 내가 어떻게 보는가는 업무 권한과 무관하다. 액션을 붙이면 <b>메뉴마다 하나씩</b> 더 만들어야 한다 |
>
> **적용과 저장은 다른 일이다**(2026-08-30 — 실물). 컬럼을 옮기거나 끄면 **그 자리에서
> 그리드에 반영**되고, 저장 버튼은 **DB 에 남기는 일**만 한다 — *껐다 켜보며 맞춘다* 는
> 것이 창을 닫아야 보인다면 **맞춰 볼 수가 없다.** 저장 버튼이 남아 있는 이유는
> 저장처가 DB 라 토글마다 API 를 부르면 요청이 폭증하기 때문이다.
>
> **닫는 것이 곧 취소다**(2026-08-30 — 두 번 고쳤다). 처음에는 *취소* 가 연 시점으로
> 되돌렸고, 다음에는 그것을 없애며 **적용이 즉시라면 되돌릴 것이 없다** 고 적었다 —
> 이미 화면이 그 상태이고 사용자는 그것을 보고 닫는다는 것이었다. **그 판단이 틀렸다.**
> 저장하지 않은 상태가 화면에 그대로 남으면 사용자는 *저장된 것* 과 구분하지 못하고,
> 실제로 *"저장을 안 눌렀는데 자동 저장인가"* 가 나왔다.
>
> 지금은 **취소가 되돌리고 `X` 도 같다** — 되돌리는 버튼과 `X` 가 다르게 굴면 *어떻게
> 닫았느냐* 로 결과가 갈리는데 그 구분을 사용자가 알 방법이 없다는 지적은 그대로 유효하며,
> **둘을 같게 만드는 것**으로 그것을 지킨다.

> **적용 — 저장하지 않고 들고 나가는 길**(2026-08-31 — 지시). 위의 *남는 것은 저장한
> 것뿐* 이 한 가지를 막고 있었다: **지금만 이렇게 보고 저장은 하지 않겠다.** 고친 것은
> 이미 화면에 들어가 있는데 닫는 길이 **저장하거나 되감거나** 둘뿐이라, 그 상태를 보려면
> **창을 열어 둔 채여야** 했다 — 창이 그리드를 가리므로 그것은 보는 것이 아니다.
>
> **셋이 남기는 것이 다 다르고 이름이 그 차이를 진다** — 저장은 **DB**, 적용은 **화면**,
> 취소는 **되감기**. 그래서 이 버튼은 `닫기` 가 아니다: `닫기` 로 두면 취소와 무엇이
> 다른지 말하지 못한다.
>
> **DB 에는 아무것도 가지 않으므로 *초기화* 는 여전히 꺼져 있다.** 적용한 것을 버리는
> 길은 **새로 고침**이다 — 다음 진입에서 저장된 것(없으면 선언)이 다시 읽힌다.

> **적용이 *되감을 자리* 도 옮긴다**(2026-08-31 — 지시). 처음에는 화면에만 두고 닫게 했는데,
> 그러면 **취소가 여전히 DB 를 기준으로** 되감았다 — *적용* 으로 맞춰 둔 화면이 **그 뒤에
> 창을 열어 무엇 하나만 고치고 취소해도 통째로 날아갔다.**
>
> **남기기로 한 것과 해 보는 중인 것을 가르는 선이 저장 하나뿐이면 안 된다.** 지금은 셋이
> 각자의 자리를 갖는다.
>
> | 무엇 | DB | 화면 | 취소가 돌아올 자리 |
> |---|---|---|---|
> | **저장** | ● | ● | 여기로 |
> | **적용** | — | ● | **여기로** |
> | 창에서 고치는 중 · 헤더 드래그 | — | ● | 아니다 |
>
> **`saved` 는 그대로 DB 만 본다.** 초기화가 켜지는 조건은 *지울 행이 있는가* 이고, 적용은
> 지울 행을 만들지 않는다 — 그 둘을 겹치면 예전의 *"저장을 안 눌렀는데 자동 저장인가"* 가
> 그대로 돌아온다.
>
> **소스에서 컬럼 순서를 바꿨는데 화면이 그대로면 저장된 설정을 의심한다**(2026-08-30 —
> 실물). 시그니처는 필드 이름을 **정렬해서** 해시하므로 컬럼이 **늘거나 줄 때만** 설정을
> 폐기한다 — 순서를 넣으면 사용자가 순서를 바꿀 때마다 **자기 설정이 자기를 폐기**하기
> 때문이다(UX-13). 그 대가로 **순서만 바뀐 배포는 저장한 사람의 화면에서 조용히 묻힌다.**
>
> 확인하는 자리가 곧 **설정 창의 초기화 버튼**이다 — 켜져 있으면 저장된(또는 적용된)
> 설정이 이기고 있는 것이고, 눌러 지우면 선언이 나온다. 개발 중에 특히 잘 밟는다:
> 실측하며 한 번 저장해 두면 그 뒤로 컬럼 선언을 아무리 고쳐도 자기 화면만 그대로다.

> **헤더 드래그는 *순서만* 바꾼다**(2026-08-31 — 실물). 판이 알려 주는 컬럼 목록에는
> **꺼 둔 컬럼도 함께** 들어 있는데(`getAllGridColumns`), 그것을 받아 적으면서 **모르는
> 칸을 *보임 · 고정 없음* 으로** 채우고 있었다. 저장된 설정이 없는 그리드에서는 그 *모르는
> 칸* 이 **전부**라, **헤더를 한 번 끌면 숨겨 둔 컬럼이 쏟아지고 틀고정도 함께 풀렸다.**
>
> 바닥값은 **지금 화면에 입혀진 것**이다 — 선언의 `visible` · `pinned` 가 거기 들어 있고,
> 창에서 껐다 켠 것(아직 확정 전)도 **지금 화면의 상태**이므로 함께 살아남는다.

> **새 `columnDefs` 를 넘기는 것만으로는 모자랐다.** 판은 사용자가 UI 로 만든 상태
> (순서·표시·고정)를 **선언보다 우선**해 들고 있다 — 선언을 바꾼 뒤 `applyColumnState`
> 로 한 번 맞춰야 화면이 따라온다. 폭과 정렬은 담지 않는다: 담지 않은 속성은 판이 그대로
> 두며, 폭은 `localStorage` 의 것이고 정렬은 헤더가 가진 상태다.

> **시그니처는 *순서를 보지 않는다*** — 이름을 정렬해 해시한다. 사용자가 바꾼 순서가
> 섞이면 순서를 바꿀 때마다 **자기 설정이 자기를 폐기하고**, 사용자가 겪는 것은
> *"설정이 저장되지 않는다"* 인데 원인을 짐작할 수 없다. **부르는 쪽의 규약으로 두지
> 않고 함수가 보장한다** — 한 번의 실수로 깨지는 자리다.
>
> **어긋난 행은 읽을 때 지운다.** 살려 두면 다음 저장 때까지 맞지 않는 설정이 DB 에 남고
> **다른 기기에서 다시 읽힌다.**

> **트리 그리드는 이 창을 갖지 않는다.** [61](../../../../documents/screen/user/requirements.md) §4.4 의 권한 트리와 [62](../../../../documents/screen/menu/requirements.md) §4.2 의 메뉴 트리
> 둘 다 없다 — **계층 컬럼이 맨 왼쪽 고정**이라 순서도 고정도 대상이 아니고, 페이지가
> 없어 페이지 사이즈도 없다. 남는 것이 컬럼 서너 개의 표시 여부뿐이면 **창을 열 값이 없다.**
> ③ 아이콘 자체를 두지 않는다 — 눌러서 빈 창을 보는 것이 가장 나쁘다.

> **틀고정을 DB 에 두는 이유** — [41](../../../knowledge/sys/user-role.md) §4.3 의 경계는 *기기·화면의 속성* 과 *사람의
> 속성* 이다. 틀고정은 *"이 컬럼을 붙잡고 나머지를 스크롤한다"* 는 **읽는 방식**이므로
> 순서·표시여부와 같은 쪽이다.

**시그니처 무효화(UX-13)가 여기 걸린다.** 화면의 컬럼 목록이 바뀌면 저장된 설정은
폐기한다 — 서버 저장이므로 검증도 서버 한 곳이다([10](../../../knowledge/features.md) UX-13).

**시그니처는 이 창의 목록으로 계산한다.**

```
시그니처 = 전체 컬럼 − 시스템 컬럼 − hidden − 동적 컬럼
```

저장된 설정에 들어 있지 않은 컬럼이 늘거나 줄었다고 사용자의 표시·순서·고정을 버릴
이유가 없다. **`hidden` 을 껐다 켜는 것은 목록을 바꾸므로 시그니처가 바뀐다.**

> **동적 컬럼을 빼는 이유가 이 규약의 생존 조건이다**([ADR-0025](../../../records/adr/0025-reference-code-definition-and-dynamic-columns.md)). 컬럼 목록이 **데이터에서
> 오는 그리드**([54](./grid-column-contract.md) §2.2)에서는 마스터 행을 클릭할 때마다 목록이 바뀐다 — 넣어 두면
> **클릭마다 저장된 설정이 폐기되고**, 사용자가 겪는 것은 *"설정이 저장되지 않는다"* 이며
> **원인을 짐작할 수 없다.** 안전장치가 연발되는 오작동이 되는 자리다.

## 6. 마스터-디테일 연동 — 디테일은 마스터의 선택에 종속된다

관리 화면의 표준 형태가 **상단 마스터 그리드 + 하단 디테일 탭**이다([52](../../../knowledge/sys/menu.md) §3.5).
디테일이 언제 열리고 닫히는지를 화면마다 정하면 **이전 행의 데이터를 보면서 편집하는**
사고가 난다.

### 6.1 상태가 셋이다

| 상태 | 언제 | 디테일 그리드 |
|---|---|---|
| **빈 상태** | 화면 진입 · **마스터 조회 직후** · **마스터 신규 행 추가 직후** | 데이터 **리셋** · 버튼 **전부 비활성** · *"마스터에서 행을 선택하세요"* |
| **잠긴 상태** | **미저장 신규 행**을 선택 | 〃 · **조회하지 않는다** · *"저장 후 편집할 수 있습니다"* — **예외는 아래** |
| **활성** | **저장된** 마스터 행을 선택 | 전부 조회 · 버튼 활성 |

- **조회 직후에 리셋하는 이유** — 조회는 마스터 목록을 통째로 바꾼다. 이전에 보던 행이
  결과에 없을 수도 있는데 디테일이 남아 있으면 **다른 사람의 데이터를 그 사람 것으로
  보게 된다.** 가장 위험한 오작동이라 자동 선택도 하지 않는다
- **미저장 신규 행이 잠기는 이유** — 부모 키가 아직 DB 에 없어 자식을 붙일 수 없다.
  붙이려 하면 FK 위반이다([41](../../../knowledge/sys/user-role.md) §8)
- 그래서 **신규 등록은 2단계**다 — *마스터 행 추가 → 저장 → 그 행 선택 → 디테일 편집*.
  한 번에 끝나지 않는 것이 이 규칙의 대가이며, 대신 **부모 없는 자식이 화면에 존재할 수
  없다**

> **예외 하나 — 디테일이 마스터의 `list` 컬럼이면 잠그지 않는다.** 위 두 이유가 둘 다
> 성립하지 않는 화면이 있다: 디테일이 **DB 에 붙지 않아**(마스터 행의 `list` 값을 편집할
> 뿐이며 FK 는 저장 시점에 서버가 순서대로 만든다) 위반할 것이 없고, 디테일의 행 집합이
> **서버 조회가 아니라 캐시에서** 온다. 그러면 마스터 신규 행 추가 직후에도 디테일이
> **리셋되지 않고 빈 항목으로 채워지며 2단계 등록을 치르지 않는다.** 실물은
> [63](../../../../documents/screen/code/requirements.md) §3.2(다국어 메시지)이며 [54](./grid-column-contract.md) §5.6 의 *"화면의 다른 그리드"* 경로다.
> **조회 직후 리셋은 그대로**다.
>
> **그런 디테일에는 버튼을 하나도 두지 않는다** — `api` 를 선언하지 않는다. 조회 버튼이
> 있으면 **`list` 의 미저장 편집이 날아가고**, 저장 버튼이 있으면 저장 단위가 둘이 된다
> ([63](../../../../documents/screen/code/requirements.md) §3.2). §2.1 의 ①은 `api` 선언이 채우므로 **선언이 없으면 자리째로 비는 것**이다.

> **디테일에 미저장 편집이 있는 채로 다른 마스터 행을 클릭하면 확인 다이얼로그를 띄운다**
> (UX-10). 리셋은 되돌릴 수 없고, 사용자는 클릭이 편집을 버린다는 것을 모른다.

> **"버튼 전부 비활성" 은 `<DataGrid disabled>` 하나로 건다**(2026-08-31 — [61](../../../../documents/screen/user/requirements.md) §3.9 가
> 요구했다). ①뿐 아니라 **②③도 함께 잠근다** — 대상이 없는데 엑셀을 내려받을 수는 없고,
> 빈 판의 컬럼 설정을 여는 것도 할 일이 아니다. `collapsed` 와 축이 다르다: 저것은
> *안 보인다* 이고 이것은 **보이는데 누를 수 없다** 이며, **비활성되는 것은 버튼이지 탭이
> 아니다**(탭을 잠그면 *"이 사용자에게 그 탭이 없나"* 로 읽힌다).
> **`list` 디테일(위 예외)에서는 묻지 않는다** — 편집이 마스터 행에 남아 잃을 것이 없다.
> 마스터 자신의 미저장 행 상태는 **유지된다** — 리셋되는 것은 디테일뿐이다.

#### 6.1.1 디테일도 ①에 **조회**를 갖는다 (2026-09-01)

**자동 조회와 수동 재조회는 다른 일이다.** 디테일은 마스터의 선택이 바뀔 때 스스로
읽지만(위 표의 *활성*), 그것만으로 닫히지 않는 자리가 있다.

| 언제 눌리나 | |
|---|---|
| **남이 고쳤다** | 마스터를 건드리지 않고 **이쪽만** 다시 읽는다 |
| **저장이 실패했다** | 서버가 실제로 어떤 상태인지 확인한다 — 화면의 편집을 버리고 원본으로 되돌리는 길이기도 하다 |
| **실행이 서버에서 값을 바꿨다** | `reloadAfter` 가 없는 실행이거나, 실행 대상이 마스터인데 결과가 디테일에 남는 경우 |

**마스터의 조회로 대신할 수 없다.** 마스터 조회는 목록을 통째로 바꾸고 **디테일을
리셋한다**(위 표) — 보던 행이 결과에 없을 수도 있으므로 자동 선택도 하지 않는다. 즉
*"디테일만 새로고침"* 을 하려고 마스터를 조회하면 **고른 행을 잃는다.**

| 규칙 | |
|---|---|
| **버튼은 `api.read` 선언이 낸다** | 화면이 손으로 놓지 않는다(§2.1 · [55](./grid-api-contract.md) §3.1). 디테일이 그것을 선언하므로 자리가 채워진다 |
| **선언할 수 없으면 `onRead`** | 행이 **다른 조회에서** 오는 그리드가 있다 — 응답이 `PageResponse` 가 아니라 컨트롤러가 파싱하지 못한다. 그때만 화면이 함수를 건다(`DataGrid.onRead` · `TreeGrid.onRead` 와 같은 모양). **미저장 확인도 화면이 한다** — 컨트롤러를 거치지 않으므로 §3.1 이 자동으로 돌지 않는다 |
| **대상은 여전히 마스터의 선택**이다 | 부모 키는 `searchParams` 로 간다 — 조회 버튼이 그 값을 바꾸지 않는다 |
| **미저장이면 묻는다** | §3.1 의 재조회 규약 그대로다. 잃는 것이 디테일의 편집뿐이라도 묻는다 |
| **비어 있으면 비활성** | 대상이 없으면 `<DataGrid disabled>` 가 ①을 통째로 잠근다(위) |
| **하단 탭이면 탭마다** | 지연 로딩이라 **안 연 탭은 읽지도 않았고**, 연 탭을 다시 읽는 것도 그 탭만의 일이다 |

> **선언하지 않는 자리가 하나 있다 — `list` 디테일**(위 예외). 행 집합이 서버 조회가
> 아니라 **캐시에서** 오므로 조회 버튼이 부를 곳이 없고, 눌리면 **`list` 의 미저장 편집이
> 날아간다.** 그 화면은 `api` 를 통째로 선언하지 않아 ①이 **자리째로 빈다**.

> **실물** — `CODE_MGMT` 의 상세 코드 그리드가 이것이다([63](../../../../documents/screen/code/requirements.md) §2). 반대쪽 실물은
> `MESSAGE_MGMT` 의 하단(`list` 디테일 — [63](../../../../documents/screen/code/requirements.md) §3.2)이며 **버튼이 하나도 없다.**
> 둘을 나란히 보면 *조회 버튼이 있고 없고* 가 **화면의 취향이 아니라 데이터가 어디서
> 오는가**의 결과라는 것이 보인다.

#### 디테일 그리드의 제목이 **누구의 것인지** 말한다 (2026-08-31 — 구현)

디테일 그리드는 자기가 **누구의 것인지 말하지 못한다.** 마스터의 선택 행이 스크롤 밖으로
나가거나 조회조건이 펼쳐지면 지금 보고 있는 것이 누구의 것인지가 **화면 어디에도 없고**,
그 상태의 저장은 *다른 사람의 것을 고친 것* 이 될 수 있다.

```ts
<DataGrid titleSuffix={{ parent: master, fields: ['userId', 'userNm'] }} … />
// 제목 줄 —  보유 역할   admin / 관리자
```

| | |
|---|---|
| 무엇을 붙이나 | **부모 행의 컬럼 값을 슬래시로 이은 것.** 선언 순서가 곧 표시 순서다 |
| 왜 컨트롤러를 넘기나 | 선택은 사용자가 바꾸는 **흐르는 값**이다 — 행을 뽑아 넘기면 그 순간의 값이 굳고, **마스터의 선택을 디테일이 또 들게** 된다 |
| 빈 값 | **조용히 빠진다.** 미저장 신규 행처럼 아직 값이 없는 경우가 있고, 그때 `/` 만 남으면 그것이 값처럼 보인다. 고른 행이 없으면 **아무것도 붙지 않는다** — *(없음)* 같은 자리표를 만들지 않는다 |
| 굵기 | 제목과 **갈린다**(보조 색) — 이것은 제목이 아니라 *지금 무엇을 보고 있나* 이고, 같은 굵기면 **그리드 이름이 행마다 바뀌는 것**처럼 보인다 |

> **화면이 문자열을 만들지 않는다.** 화면마다 조립하면 구분자·순서·빈 값 처리가 화면 수만큼
> 생기고, 부모의 선택을 **디테일이 또 들어야** 한다 — 컨트롤러가 이미 갖고 있는 사실이다.

#### 하단 탭의 기본값 셋 — 화면이 적지 않는다 (2026-08-31 — 구현)

탭 안이 그리드인 화면이 여러 개 서면서 같은 값 셋을 매번 적게 됐다. **적는 자리가 화면이면
새 화면이 빠뜨려도 조용하다** — 그 화면만 탭바가 좁다. 그래서 공용 컴포넌트가 갖는다.

| | |
|---|---|
| **본문 높이** | 탭 본문이 **남는 높이를 다 쓴다.** 그리드는 자기 몫을 채우는 컴포넌트인데 antd 의 탭 본문 래퍼 셋이 기본 높이가 auto 라 그 사이에서 높이가 **끊긴다**(헤더와 푸터만 보이고 판이 0px 이 된다) |
| **탭 최소 폭 100px** | 이름이 두 글자인 탭(*세션*)과 다섯 글자인 탭(*개인 예외*)이 나란히 있으면 폭이 제각각이라 **손이 자리를 기억하지 못한다.** 다국어에서 더 벌어진다 — 같은 탭이 언어마다 다른 폭이 된다. 글자가 아니라 **탭 자체**에 걸고 가운데 정렬을 함께 건다(안쪽에 걸면 antd 의 여백이 그 위에 더해져 선언한 값보다 넓어지고, 정렬이 없으면 짧은 이름이 왼쪽에 몰려 **탭 사이 간격이 제각각으로** 보인다) |
| **탭바 높이 = 그리드 버튼 줄** | `controlHeight + 16` — §2.1 의 버튼 줄과 같은 값이다. 위아래로 나란히 놓이는 두 줄이라 높이가 갈리면 **탭바만 눌린 것처럼** 보인다 |
| **접힘** | 스플리터가 이 pane 을 접으면 **탭바가 사라지고** 활성 탭의 그리드 제목 한 줄만 남는다(§6.3) — 그리드 하나짜리 하단과 같은 모양이다. 언마운트하지 않으므로 조회한 행과 미저장 편집이 살아 있다 |

> **antd 의 크기 프리셋(`size`)을 열지 않는다.** 탭바 높이를 우리가 정하므로 겹치고, 둘이
> 다투면 *화면마다 다른 높이* 라는 원래 문제로 돌아온다.

### 6.2 마스터의 삭제는 디테일이 비어야 열린다

| 조건 | 마스터 행의 삭제 |
|---|---|
| 디테일 그리드가 **없는** 화면 | 항상 가능 |
| 디테일이 있고 **행 미선택** | **비활성** — 자식 유무를 모른다 |
| 디테일이 있고 선택 + **하나라도 1건 이상** | **비활성** |
| 디테일이 있고 선택 + **전부 0건** | **활성** |
| **미저장 신규 행** | **항상 가능** — 즉시 제거(§3.3) |

**근거는 FK 다.** 자식이 있으면 `DELETE` 가 DB 에서 거부된다([41](../../../knowledge/sys/user-role.md) §8 — 걸되 이력에는
걸지 않는다). 화면이 미리 막는 것은 **저장 시점에 나는 실패를 조회 시점에 알리는** 일이다.

- **판정은 디테일이 전부 도착한 뒤**에 한다. N 개를 병렬 조회하고 하나라도 실패하면
  **닫아 둔다** — `deny by default` 와 같은 방향이다([23](../../backend/_study/security-design.md) §4)
- **디테일이 자식 전부를 보여주지 않는 화면이 있다.** 다른 화면에서 편집하는 자식은
  이 화면에 그리드가 없지만 **FK 는 그대로 막는다.** 그때는 **마스터의 건수 컬럼**이
  디테일의 자리를 대신한다 — 조회 응답이 이미 갖고 있어 왕복이 늘지 않는다.
  실물은 [62](../../../../documents/screen/menu/requirements.md) §3.5(역할 ↔ 역할 권한)다
- **다중 선택 삭제가 불가능해진다.** 디테일은 선택된 한 행에 대해서만 조회되므로 나머지
  행은 자식 유무를 모른다. 디테일이 있는 마스터에서 **삭제 후보는 선택된 행 하나**다
- 디테일이 없는 화면(단일 그리드)은 이 제약을 받지 않는다 — 여러 행을 삭제 상태로 만들고
  한 번에 저장한다

> **`USER_MGMT` 에는 이 규칙이 적용되지 않는다.** `SYS_USER` 는 물리 삭제를 하지 않아
> 삭제 컬럼 자체가 없다(§3.5). **디테일 경로**의 첫 실물은 **코드 그룹 ↔ 코드**
> ([63](../../../../documents/screen/code/requirements.md) §2.5), **건수 컬럼 경로**는 **역할 화면**([62](../../../../documents/screen/menu/requirements.md) §3.5)이다.
>
> **게이트와 확인을 가르는 기준은 *DB 가 거부하는가* 다.** 자식이 **다른 화면에서 관리되는
> 남의 데이터**면 게이트이고, **그 행의 파생**이면 서비스가 자식부터 지우므로 거부되지 않아
> **확인**이다 — [63](../../../../documents/screen/code/requirements.md) §2.5 가 한 화면 안에서 그 둘을 나란히 보인다
> ([ADR-0025](../../../records/adr/0025-reference-code-definition-and-dynamic-columns.md) · [ADR-0023](../../../records/adr/0023-message-key-sync-from-source.md) §3 이 메시지 키에서 같은 판단을 했다).

### 6.3 배치는 축이 둘이고, 사이에 스플리터가 있다

**상하가 기본이고 좌우도 된다.** 축은 **화면이 선언**하며, 축이 정해지면 스플리터의
방향과 접기 방향이 함께 정해진다 — 따로 고르지 않는다.

| 축 | 언제 쓰나 | 스플리터 | 접기 |
|---|---|---|---|
| **상하**(기본) | 마스터가 **넓다** — 컬럼이 많은 목록 | **가로 막대** — 위아래로 끈다 | `▲` · `▼` |
| **좌우** | 마스터가 **좁다** — 트리처럼 컬럼이 한둘 | **세로 막대** — 좌우로 끈다 | `◀` · `▶` |

**좌우의 실물은 `62`(역할 ↔ 권한 트리)와 [61](../../../../documents/screen/user/requirements.md) §4**(권한 트리 ↔ 개인 예외)다.
트리는 컬럼이 하나라 위아래로 두면 **가로 공간의 대부분이 빈다.**

#### 화살표는 스플리터가 갈 자리를 가리킨다

여기가 유일하게 헷갈리는 자리라 못 박는다.

| 상태 | 보이는 화살표 | 누르면 | 결과 |
|---|---|---|---|
| **둘 다 열림** | `▲` · `▼` | 막대가 그쪽 끝으로 간다 | `▲` → **마스터가 접힌다** · `▼` → **디테일이 접힌다** |
| **마스터가 접힘**(막대가 위) | **`▼` 하나** | 막대가 제자리로 | **되돌린다** |
| **디테일이 접힘**(막대가 아래) | **`▲` 하나** | 〃 | 〃 |

***"무엇을 접는가"* 가 아니라 *"막대가 어디로 가는가"* 다.** 반대로 읽으면 누를 때마다
틀린 쪽이 접힌다. 좌우 축의 `◀` `▶` 도 같은 규칙이며, 그래서 **축이 바뀌어도 배울 것이
새로 없다.**

> **접히면 화살표가 하나로 준다**(2026-08-30 — 구현). 처음에는 둘을 늘 그려 두고 갈 수
> 없는 쪽을 **비활성**으로 두었는데, 그러면 접은 뒤에 <b>눌리는 화살표가 이미 있는 상태를
> 가리켜</b> 아무 일도 일어나지 않는다 — **화살표로 접으면 화살표로 돌아올 수 없었다.**
> 접힌 상태에서 뜻이 있는 동작은 *되돌리기* 하나뿐이므로 화살표도 하나다. **비활성
> 상태가 아예 없어진다.**
>
> **접근성 이름이 방향에서 오지 않는다** — 같은 `▼` 가 접기이기도 되돌리기이기도 하다.

#### 막대의 모양 (2026-08-30 — 실물에서 다듬음)

| | |
|---|---|
| 막대 | 높이 **14px** · 옅은 채움 · **위아래 테두리** — 두 그리드 <b>사이의 띠</b>이므로 양쪽에 경계가 있어야 한다. 한쪽만 두면 막대가 어느 한쪽에 <b>붙은 것</b>처럼 보인다 |
| 화살표 | **폭 100px** — 12px 짜리 띠에서 <b>겨냥해 누를 수 있는 여유는 폭뿐</b>이다 |
| 〃 | **위아래 테두리 없음 · 각진 모서리 · 둘이 맞붙음**(맞닿는 선은 겹친다) — 막대에서 <b>도려낸 조각</b>처럼 보여야 한다 |

**화살표가 자기 위아래 선을 또 그으면 띠 안에 선이 넉 줄**이 되고, 그것이 *두 줄짜리
테두리* 로 읽힌다. 지우는 것은 막대의 선이 아니라 **화살표의 선**이다.

#### 접힌 쪽은 사라지지 않는다 — 제목 줄만 남는다

| | |
|---|---|
| 접힌 쪽 | **그리드 헤더(§2.1)의 제목 줄만** 남고 본문·푸터가 접힌다 |
| 버튼 | **함께 접힌다** — 보이지 않는 그리드의 저장 버튼을 누를 이유가 없다 |
| 되돌리기 | **제목 줄 클릭** 또는 스플리터의 반대 화살표 |
| 디테일 탭 | **탭 줄도 접힌다** — 남는 것은 **활성 탭의 그리드 제목 한 줄**이다(2026-08-31 — 아래) |

**제목 줄을 남기는 이유** — 완전히 없애면 *"디테일이 원래 없는 화면"* 과 구분되지 않는다.
**접힌 것과 없는 것은 다르다.**

> **탭 줄을 남기지 않는다**(2026-08-31 실물 — 위 표를 뒤집었다). 근거는 *"어느 탭이 열려
> 있었는지가 정보다"* 였는데, **그 정보가 이미 제목 줄에 있다** — 남는 제목이 활성 탭의
> 그리드 제목이다(*보유 역할* · *접속 IP* …). 탭 줄은 같은 사실을 한 줄 더 쓰는 셈이었다.
>
> 그리고 남겨 둔 결과가 접힘으로 읽히지 않았다. **탭바 · 버튼 줄 · 페이징이 그대로 남고
> 판만 0px** 이 되어, 접은 것이 아니라 *판이 깨진 것* 처럼 보였다 — 그리드 하나짜리 하단은
> 제목 한 줄로 접히는데 **탭이 있는 하단만 다른 모양**이었다.
>
> **탭바만 감추면 나머지는 따라온다.** 남은 본문(활성 탭 하나)의 그리드가 스스로 제목 한
> 줄로 접히므로 결과가 그리드 하나짜리 하단과 **같은 모양**이 된다 — 접힘의 규칙이 하나여야
> 배울 것도 하나다. 구현은 §6.1 의 하단 탭 공용 컴포넌트가 갖는다(`collapsed`).

#### 둘 다 접히지는 않는다

한쪽이 접히면 **반대쪽 접기 화살표는 비활성**이다. 둘 다 접으면 콘텐츠 영역이 비고 그
화면은 아무 것도 하지 못한다 — 되돌릴 수는 있지만 **갈 이유가 없는 상태를 만들지 않는다**
(§6.1 이 조회 후 자동 선택을 두지 않은 것과 같은 방향이다).

#### 끝까지 끌면 접힘으로 스냅한다

각 쪽에 **최소 크기**가 있다 — 그리드 헤더 한 줄 + 컬럼 헤더 + 본문 한 행 + 푸터.
그보다 작게 끌면 **접힘에 붙는다.**

**손으로 끌어 접은 것과 화살표로 접은 것이 같은 상태여야 한다.** 두 경로가 다른 상태를
만들면 되돌리는 방법도 갈린다 — *"끌어서 없앴는데 화살표로는 안 돌아온다"* 가 생긴다.

> **미저장 편집이 있어도 접힌다.** 접기는 **표시**이지 데이터가 아니다 — 컬럼 필터가
> 표시만 거르는 것과 같다([54](./grid-column-contract.md) §4.1). 다만 **검증 실패가 접힌 쪽에 있으면
> 펼치고 그 셀로 이동한다** — [56](./grid-edit-validation.md) §3.3 이 필터에 대해 정한 것과 같은 규칙이다.

#### 비율과 접힘 상태는 `localStorage` 다 — 컬럼 너비와 같은 자리(§5)

| | 왜 |
|---|---|
| **DB 가 아니다** | **뷰포트에 종속된다** — 27인치에서 맞춘 비율이 노트북에서는 틀리다. 사람의 속성이 아니라 **기기·화면의 속성**이다([41](../../../knowledge/sys/user-role.md) §4.3 의 경계) |
| **그리드 설정 창에 없다** | **직접 조작으로 정해진다** — 헤더를 끌어 너비를 바꾸는 것과 같다(§5) |
| 초기화 | 그리드 설정 창의 **초기화가 함께 되돌린다** — 너비와 같다 |

**축(상하·좌우)은 화면 코드의 선언이므로 사용자가 바꾸지 않는다.** 바꾸게 하면 같은
화면이 사람마다 다르게 생기고, **스크린샷으로 하는 문의 응대가 어긋난다.**

## 7. 목업 어휘

목업 규약(자체 완결 · 프레임워크 없음 · 픽셀 충실도 아님)은 [60](../../../../documents/screen/_standalone/README.md) §2.3 이 갖는다.
그리드가 쓰는 클래스만 여기 적는다.

| 클래스 | 무엇 | 대응하는 공통 컴포넌트([24](./frontend-stack.md) §7) |
|---|---|---|
| **`.bc`** | **브레드크럼 줄** — 왼쪽 경로는 셸, **오른쪽 슬롯은 화면**([51](./main-shell.md) §5.1) | 셸 + `<SearchForm>` 컨트롤 |
| `.sf` | 검색 폼 — **화면에 남는 유일한 폼**(§1.1) | `<SearchForm>` (UX-15) |
| `.tb` | **그리드 헤더** — 왼쪽 제목(`.ttl`) · 오른쪽 버튼(아이콘은 `.ico`) | `<DataGrid>` 헤더 (§2.1) |
| `.grid` | 그리드 본문 — 상태 열 `.st` · 삭제 열 `.del` · 읽기 전용 셀 `.ro` | `<DataGrid>` |
| `.pg` | **그리드 푸터** — 건수 · 네비게이션 · 페이지 사이즈 3분할 | 〃 (서버 페이징) |
| `.split` | **마스터-디테일 스플리터** — 손잡이(`.hnd`) · 접기 화살표(§6.3) | `<SplitPane>` ([24](./frontend-stack.md) §7) |
| `.swt` | **스위치** — 값이 둘인 데이터 칸. `ynFlag` 와 권한 트리가 함께 쓴다([54](./grid-column-contract.md) §5.2) | AntD `Switch` (자체 에디터) |

그리드 설정 창은 **`.modal` 을 재사용**한다 — 새 클래스를 두지 않는다.

> **`.bc` 가 리프 목업의 유일한 예외다.** 셸 크롬을 그리지 않는 규약([60](../../../../documents/screen/_standalone/README.md) §2.3)에서 이 줄만
> 그린다 — **오른쪽 슬롯이 화면의 것**이라 그리지 않으면 조회조건 컨트롤을 보일 자리가 없다.
> 왼쪽 경로는 **어디에 있는지 알려주는 배경**으로만 둔다.

- **리프 화면 목업은 셸 크롬을 그리지 않는다**(`.screen.leaf`) — 셸은 [51](./main-shell.md) 이 소유하며
  17장에 복제하면 51 이 바뀔 때 17장이 함께 틀린다
- **행 상태와 고정 영역은 그린다.** 자리가 이 문서의 결정이므로 목업이 보여야 한다
- [ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md) 의 어휘(`filter` · `editor`)는 **문서 표에만** 적고 HTML 로 흉내 내지 않는다

## 8. 셀과 행의 색 — 무엇을 칠하고, 무엇이 이기나

**색은 그리드가 스스로 정하지 않는다.** [51](./main-shell.md) §9.7 의 테마 축 셋(모드 · Primary Color ·
색 톤)에서 만든 토큰을 받아 쓴다 — 그리드만 따로 색을 가지면 셸의 회색과 어긋나고,
사용자가 톤을 바꿨을 때 화면의 절반만 따라온다.

### 8.1 무엇을 색으로 말하나

| 무엇 | 색 | 짝이 되는 표시 |
|---|---|---|
| **컬럼 상태** — 필수 · 편집 가능 · 읽기 전용 | 셀 배경 — **편집 가능은 칠하지 않는다** | **헤더 표시**([54](./grid-column-contract.md) §5.1) |
| **행 상태** — 추가 · 수정 · 삭제 | 행 배경 | **상태 컬럼 아이콘**(§3.2) |
| **현재 선택 행 · 선택 셀** | Primary 옅은 단계 | 셀 테두리 |
| **편집 중인 셀** | Primary 테두리 | 커서 |
| **검증 실패** | 오류색 배경 + 테두리 | 메시지 · 오류 목록([56](./grid-edit-validation.md) §3.3) |

> **색만으로 말하지 않는다.** 위 다섯 모두 **아이콘·테두리·헤더 표시와 짝**을 이룬다 —
> 색각 이상이 있는 사용자에게 색은 정보가 아니다. 특히 **필수 컬럼은 헤더의 `*` 가
> 원본**이고 배경색은 그것을 거드는 것이다([54](./grid-column-contract.md) §5.1).

#### 컬럼 상태 셋 중 **편집 가능은 바탕이다**

셋 모두 칠하면 **편집 가능 셀이 대다수라 그리드 전체가 칠해진다** — 그러면 아무것도
구분되지 않는다. [사용자 관리 목업](../../../../documents/screen/user/mockup.html)을 그리면서 확인한 것이며 규약으로 굳힌다.

| 컬럼 상태 | 셀 배경 |
|---|---|
| **필수 입력** | 옅은 강조색 |
| **편집 가능** | **바탕 그대로 — 칠하지 않는다** |
| **읽기 전용** | 회색 |

**가장 흔한 것이 바탕이어야 한다.** 잉크는 예외에 쓴다 — *"이 칸은 반드시 채워야 한다"*
와 *"이 칸은 못 고친다"* 가 예외이고, 고칠 수 있는 것은 그리드의 기본값이다.

### 8.2 겹치면 무엇이 이기나 — 우선순위 여섯

한 셀에 여러 상태가 겹친다. **선택한 행의 필수 컬럼 셀이 검증에 실패한 채 편집 중**일 수
있다. 순서를 정하지 않으면 화면마다 다르게 보인다.

| 순위 | 상태 | 왜 이 자리인가 |
|---|---|---|
| **1** | **검증 실패** | 저장을 막는다. 다른 무엇보다 먼저 보여야 한다 |
| **2** | **편집 중인 셀** | 지금 타이핑하는 자리다 |
| **3** | **현재 선택 셀** | |
| **4** | **현재 선택 행** | |
| **5** | **행 상태**(추가 · 수정 · 삭제) | |
| **6** | **컬럼 상태**(필수 · 편집 가능 · 읽기 전용) | 정적이므로 **다른 것이 없을 때의 바탕**이다 |

**선택(3·4)이 행 상태(5)를 이기는 이유** — 선택은 *"지금 무엇을 하고 있는가"* 이고 행
상태는 *"무엇을 했는가"* 다. 지금이 이긴다. 행 상태는 **상태 컬럼 아이콘이 계속 말하고
있으므로**(§3.2) 배경을 잠시 양보해도 정보가 사라지지 않는다.

> **삭제 상태 행은 예외처럼 보이지만 아니다.** 취소선과 흐림은 배경이 아니라 **글자**에
> 걸리므로 선택 배경과 겹쳐도 둘 다 보인다.

### 8.3 헤더가 컬럼을 말하고, 셀이 그 셀을 말한다

[56](./grid-edit-validation.md) §2.1 이 `editable` 에 **함수 형태**를 뒀다 — 행마다 편집 가능 여부가 다르다.
그러면 헤더는 *"편집 가능"* 인데 어떤 셀은 잠겨 있다.

| | 말하는 것 |
|---|---|
| **헤더** | **컬럼 선언** — 이 컬럼은 원래 무엇인가 |
| **셀 배경** | **그 셀의 실제 상태** — 지금 이 행에서 편집할 수 있는가 |

**둘이 어긋나는 것이 정상이다.** 헤더가 행마다 바뀔 수는 없고, 셀이 선언만 따르면
*"편집 가능해 보이는데 클릭이 안 되는"* 셀이 생긴다 — 그때 [56](./grid-edit-validation.md) §2.1 의 거부
메시지가 나온다.

### 8.4 Primary 에서 파생하고, 직접 색을 정하지 않는다

선택·편집 표시는 [51](./main-shell.md) §9.4 의 **Primary Color 팔레트에서 단계를 골라** 쓴다.

| 쓰임 | 단계 |
|---|---|
| 현재 선택 행 | **가장 옅은 단계** |
| 현재 선택 셀 | 한 단계 진한 것 + 테두리 |
| 편집 중인 셀 | **테두리는 Primary 원색**, 배경은 바탕색 — 입력 글자가 읽혀야 한다 |

- **옅은 단계로 고정하는 것이 대비 문제를 구조적으로 피한다.** 그리드는 글자가 촘촘해
  배경이 진해지면 전부 읽기 어려워진다 — [51](./main-shell.md) §9.4 가 커스텀 Primary 에 대비 경고를
  두기로 한 것과 같은 걱정이며, 여기서는 **애초에 진한 단계를 쓰지 않아** 막는다
- **다크와 라이트에서 같은 단계를 쓰지 않는다.** 같은 알파를 얹으면 다크에서는 보이지
  않거나 반대로 튄다 — 단계는 모드별로 고른다
- **검증 실패색만 Primary 와 무관하다.** 오류는 Primary 가 무엇이든 오류색이어야 한다 —
  Primary 를 빨강으로 고른 조직에서 오류가 선택과 같은 색이 되면 안 된다

| **총 건수 · 총 페이지의 `COUNT` 비용**(§2.3) — 상한 · 근사 · 생략 | **생략.** 상한은 *"1000+"* 라 어차피 번호를 못 만들고, 근사는 벤더별 통계 뷰가 달라 [22](../../backend/_study/db-portability.md) 의 무수정 기동이 깨진다. 다음 페이지는 `size+1` 건을 읽어 판정하고, **그 대가로 정렬이 한 컬럼으로 좁혀진다** → [64](../../../../documents/screen/log/access/requirements.md) §2.3 | 2026-08-28 |
| **엑셀 다운로드 이력의 호출**(§2.2) — [ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) 의 `POST /api/common/excel/saveLog` 가 없었다. 막고 있던 것은 `SYS_LO_ACCESS` 의 부재였다 | **섰다.** 부르는 자리는 **버튼이 아니라 `workbook.ts`** 다 — 내려받고 지날 수 없는 자리가 거기다. `menuCd` 는 보내지 않고 `scope` 를 더했다(→ §2.2 · [ADR-0019](../../../records/adr/0019-excel-download-three-paths.md)) | 2026-08-30 |
| **선언의 이름과 와이어 형태**(§2.3) | **선언을 두지 않는다.** 페이징 여부는 서버 소스가 정하고 **응답의 `mode`**(`offset`·`cursor`·`all`)가 나른다 — 화면이 적으면 미러링이다. 커서는 **불투명 토큰**이며 유효기간이 없다 → [72](../../backend/_study/api-conventions.md) §3.8 · §3.9 | 2026-08-28 |
