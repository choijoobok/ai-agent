# 55. 그리드 API 계약 — 선언 · 버튼 · 실행 흐름

- 상태: **초안** (Phase 4~5 경계. [53](./grid-standard.md) §9 에서 분리 — §1.2)
- 최종수정일: 2026-08-29
- 관련: [53-grid-standard](./grid-standard.md) · [54-grid-column-contract](./grid-column-contract.md) · [56-grid-edit-validation](./grid-edit-validation.md) · [29-request-dedup](../../backend/crosscutting.md) · [ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md) · [21-backend-architecture](../../backend/_study/architecture.md) §6-1 · [10-feature-inventory](../../../knowledge/features.md) §K(UX-10)
- **읽어야 할 때**: **그리드에 API 를 붙일 때** · 상단 버튼이 어떻게 만들어지는지 확인할 때 · **조회·저장·실행이 도는 순서**를 볼 때 · 실행 버튼이 **임의의 인자를 받아야** 할 때(§8) · 무엇을 모달로 낼지 정할 때(§9)

## 1. 범위 — 그리드가 서버와 주고받는 전부

| 여기 있는 것 | 여기 없는 것 |
|---|---|
| `api` 선언의 키 전체(§2) | 크롬의 **자리** · 행 상태 · 컬럼 고정 · 색 → [53](./grid-standard.md) |
| **버튼 자동 렌더링**과 권한 필터(§3) | **컬럼 하나**의 계약 → [54](./grid-column-contract.md) |
| 중복 실행 방지(§4) | **서버 측** 중복 요청 방어 → [29](../../backend/crosscutting.md) |
| 조회 · 저장 · 실행 흐름(§5~§7) | 검증 규칙의 **선언 방식** → [56](./grid-edit-validation.md) §3.2 |
| **행 추가**(§3.6) — 버튼 · 사전 판단 · 기본값 · 콜백 | 편집 진입 · 이동 → [56](./grid-edit-validation.md) §2.2 |
| **`params`** — 폼·모달에서 값 받기(§8) | 액션 4종과 경로 접두 → [ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md) |
| 모달 · 토스트의 가름(§9) | 조회 **와이어 프로토콜** → `72` |

### 1.1 셋의 분담

| | [53](./grid-standard.md) | [54](./grid-column-contract.md) | 여기 |
|---|---|---|---|
| 관점 | 화면을 **배치**하는 사람 | **컬럼**을 선언하는 사람 | **API** 를 붙이는 사람 |
| 답하는 질문 | 버튼이 어디 있나 · 무엇이 무슨 색인가 | 이 컬럼은 어떻게 정렬·필터·표시되나 | **버튼을 누르면 무슨 일이 어떤 순서로 일어나나** |
| 단위 | 그리드 하나 | 컬럼 하나 | 호출 하나 |

**셋 다 Phase 6 공통 컴포넌트의 요구사항이다.**

### 1.2 `53` 에서 분리한 이유 (2026-08-27)

이 규약은 [53](./grid-standard.md) §9 에서 시작했다. 그런데 `params`(§8)가 더해지면서 절 하나가
**문서의 40%** 를 차지하게 됐고, 설계 문서 모음 문서 크기 규약(*"읽는 순간이 갈리면 분할한다"*)의
대상이 됐다 — **그리드를 배치하는 순간**과 **API 를 붙이는 순간**은 다르다.

**버튼의 자리는 [53](./grid-standard.md) §2.1 이, 버튼의 내용은 여기 §3 이 갖는다.** 자리와 내용이
갈리는 것이 어색해 보이지만, 자리는 **모든 그리드가 같고** 내용은 **화면마다 다르다.**

## 2. 그리드가 하는 일은 전부 `api` 에 있다

```ts
api: {
  read:    { url, params, emptyNotice },                            // 하나
  save:    { url, params, confirm, reloadAfter,
             validate, onSuccess, onError },                        // 하나
  actions: [ { key, url, label, target, params, confirm, reloadAfter,
               validate, onSuccess, onError }, … ],                 // 여럿
}
```

| 키 | 개수 | 무엇 |
|---|---|---|
| `read` | **하나** | 조회 — §5 |
| `save` | **하나** | 일괄 저장 — §6. 등록/수정/삭제로 쪼개지 않는다([53](./grid-standard.md) §3.1) |
| **`actions`** | **여럿** | 그 밖의 모든 버튼 — §7 |

**`params` 는 셋 다 갖는다** — 규칙이 하나면 기억할 것이 없다. 어디서 오는지만 다르다(§8).

**API 를 부르지 않는 버튼은 `api` 가 아니라 `controls` 에 선언한다** — §3.2.

> **`actions` 를 `execute` 라고 부르지 않는다.** [53](./grid-standard.md) §2.1 이 이미 경고한 자리다 — `EXECUTE`
> (액션 `X`)와 섞인다. **잠금 해제는 `actions` 의 하나이지만 액션은 `SAVE`** 다
> ([61](../../../../documents/screen/user/requirements.md) §3.4.1). **선언에 액션을 적지 않는다** — 액션은 경로 접두가 정하며([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)),
> 선언에 또 적으면 같은 사실이 두 곳에 표현되어 시드와 어긋난다.

**②③은 `api` 에 없다.** 엑셀은 그리드가 가진 데이터로 프론트가 만들고([53](./grid-standard.md) §2.2), 그리드 설정은
개인화라 데이터 API 가 아니다. **서버가 만드는 엑셀**([ADR-0019](../../../records/adr/0019-excel-download-three-paths.md) 세 번째 갈래)만
`actions` 의 하나가 된다.

## 3. 버튼은 자동으로 렌더링된다

**①의 버튼은 화면이 손으로 놓지 않는다.** `api` 선언을 읽어 그리드 헤더가 만든다.

| 규칙 | |
|---|---|
| 순서 | **조회 → 행 추가 → 저장 → `actions` 선언 순서**. 선언 순서가 곧 화면 순서다 |
| 라벨 | `label` 메시지 키. 없으면 `read`·`save` 는 표준 라벨 |
| **권한** | 각 URL 의 액션을 유효 권한과 대조해 **없으면 감춘다**([51](./main-shell.md) §6) |
| 비활성 | §4 의 잠금 · 마스터-디테일 상태([53](./grid-standard.md) §6.1) · 대상 없음(§7) |

> **화면이 `<Permission>` 을 손으로 두르지 않는다.** 버튼과 URL 이 한 선언에 있으므로
> 권한 판정에 필요한 것이 이미 다 있다. 손으로 두르면 **버튼을 추가하고 권한을 빠뜨리는**
> 경로가 열린다 — [ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md) 이 시드를 생성으로 돌린 것과 같은 이유다.

> **`api.actions[]` 가 섰다**(2026-08-30 — 구현). 첫 실물은 [61](../../../../documents/screen/user/requirements.md) §3.4 의 **잠금 해제 ·
> 휴면 해제 · 비밀번호 초기화** 셋이며, 예고한 대로 *첫 실행 버튼이 생기는 화면* 이 가져왔다.
> `params` 모달(§8)은 **아직 없다** — 그 셋이 받을 인자가 없어서다(선택 행이 전부다).
> 그것도 같은 규칙으로 미룬다: **처음 인자를 요구하는 실행**이 가져온다.
>
> **`controls` 의 첫 실물은 [63](../../../../documents/screen/code/requirements.md) §2.4 의 *참조 코드 관리*** 이고, 지금은 권한 트리 둘의
> *모두 접기 · 펼치기* 도 그것이다(62 §4.5.1).

### 3.1 자동으로 나오는 것 여섯

| 무엇 | 어디서 | 자리 |
|---|---|---|
| 조회 | `api.read` — **또는 `onRead`**([53](./grid-standard.md) §6.1.1) | ① |
| **행 추가** | **`addRow`** — 선언하지 않으면 **나오지 않는다**(§3.6) | ① |
| 저장 | `api.save` | ① |
| **각종 실행** | `api.actions[]` — 선언 순서 | ① |
| 엑셀 다운로드 | **선언이 없다** — 그리드가 자기 데이터로 만든다([53](./grid-standard.md) §2.2) | ② |
| 그리드 설정 | 〃 — 개인화다([53](./grid-standard.md) §5) | ③ |

> **조회만 원천이 둘이다**(2026-09-01). 행이 **자기 경로가 아니라 다른 조회에서** 오는
> 그리드가 있어서다 — `USER_AUTH_MGMT` 의 하단이 그것이며([61](../../../../documents/screen/user/requirements.md) §4.4) 응답이 트리라
> `api.read` 를 선언할 수가 없다. **버튼은 하나이고 자리도 하나다**: 화면이 `onRead` 를
> 주면 그것이, 없으면 `api.read` 가 낸다. **둘 다 주지 않는다** — 그러면 선언 하나가
> 죽어 있다는 뜻이다. 셋째 자리인 *아무것도 없음* 도 결정이며 `list` 디테일이 그 자리다
> ([53](./grid-standard.md) §6.1).

**순서는 조회 → 행 추가 → 저장 → `actions`** 다. 행 추가가 저장 앞인 것은 **일의 순서**이며
([53](./grid-standard.md) §3.1 — 추가하고 저장한다) 목업이 그렇게 그려져 있다.

### 3.2 임의 컨트롤은 `controls` 로 선언한다 — 자리는 둘

API 를 부르지 않는 버튼이 필요하다 — 도움말, 인쇄, 다른 화면 열기. `actions` 는 `url` 이
전제이므로 여기 넣을 수 없다.

```ts
controls: [
  { key:'scope',  slot:'beforeRead',  type:'select',
    options:[…], value, onChange },
  { key:'print',  slot:'beforeTools', type:'button', actionCd:'EXPORT',
    label:'btn.print', icon:'🖨', onClick, disabled },
]
```

**`slot` 은 둘뿐이다.**

| `slot` | 어디 | 성격 | 예 |
|---|---|---|---|
| **`beforeRead`** | 조회 버튼 **앞** | **업무** — 이 화면의 일 | 다른 화면 열기 · 표시 범위 전환 |
| **`beforeTools`** | 도구(②③) **앞** | **도구** — 보기 · 출력 | 인쇄(UX-12) · 도움말 |

> **중간에 끼울 수 없다.** ①의 순서는 `조회 → 저장 → actions 선언순`으로 고정이다(§3).
> 사이에 임의 버튼이 들어가면 **화면마다 조회 버튼의 위치가 달라진다** — 자리를 고정하는
> 이유가 사라진다([53](./grid-standard.md) §2.1). 자리를 둘로 닫으면 사용자는 *"조회는 왼쪽 묶음의 첫째"*
> 하나만 배우면 된다.

**`type` 은 셋뿐이다** — `button` · `select` · `toggle`. 그 이상이 필요하면 그것은 그리드
헤더가 아니라 **검색 폼**의 일이다(UX-15).

> **실물이 이미 있다.** [61](../../../../documents/screen/user/requirements.md) §3.8.1 의 유효 권한 탭이 헤더에 *"전체 메뉴 / 가진 것만"*
> 셀렉트를 둔다 — `slot: 'beforeRead'` 의 `select` 다. 그래서 이름이 `buttons` 가 아니라
> **`controls`** 다.

> **`select` 가 섰다**(2026-08-31 — 그 탭이 가져왔다). `GridControl` 이 유니언이 됐고
> (`GridButtonControl | GridSelectControl`) `toggle` 은 **그것을 처음 요구하는 화면이
> 가져온다** — `api.actions[]` 가 그랬던 것과 같은 규칙이다.
>
> **컨트롤이 스스로 재조회하지 않는다.** `onChange` 를 받은 화면이 상태를 바꾸고 그것이
> `searchParams` 로 흘러 들어간 뒤 화면이 `read()` 를 부른다 — 컨트롤이 컨트롤러를 직접
> 부르면 셀렉트 하나가 **그리드의 미저장 편집을 말없이 버릴** 수 있게 된다([53](./grid-standard.md) §3.1 의
> 재조회 규약은 컨트롤러의 것이다).

### 3.3 권한은 `actionCd` 로 선언한다

**API 버튼은 URL 에서 액션이 도출되지만**([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)) **`controls` 에는 도출할 URL 이
없다.** 그래서 필요한 액션을 직접 적는다.

```ts
{ key:'print', slot:'beforeTools', type:'button',
  actionCd: 'EXPORT',                  // 이 화면의 액션 — 대부분
  label:'btn.print', onClick }

{ key:'openCode', slot:'beforeRead', type:'button',
  menuCd: 'CODE_MGMT', actionCd: 'READ',   // 다른 화면 — 드물다
  label:'btn.openCode', onClick }
```

| 키 | 없으면 | 뜻 |
|---|---|---|
| **`actionCd`** | **항상 보인다** | 필요한 액션 — `READ` · `SAVE` · `EXPORT` · `EXECUTE`([23](../../backend/_study/security-design.md) §4) |
| **`menuCd`** | **이 그리드가 속한 화면** | 다른 화면의 권한이 필요할 때만 — *"코드 관리 열기"* 같은 이동 버튼 |

**이름이 권한 단위와 1:1 이다.** 권한은 `(MENU_CD, ACTION_CD)` 쌍이고([23](../../backend/_study/security-design.md) §4 ·
[42](../../../knowledge/sys/menu.md) §6) 두 키가 그 쌍을 그대로 적는다 — **`MENU_CD` 는 화면이 이미 알므로 대부분
`actionCd` 하나면 끝난다.**

> **선언한 쌍이 그 메뉴에 *정의되어 있어야* 한다**(2026-08-30 · [ADR-0027](../../../records/adr/0027-menu-declared-export-action.md)). 정의되지
> 않은 액션은 **부여할 수 없으므로** 그 버튼은 누구에게도 보이지 않는다 — 감춰진 것이
> 아니라 **켤 방법이 없는 것**이고, 증상은 *"권한을 줬는데 버튼이 없다"* 가 아니라
> *"줄 칸이 없다"* 로 나타난다.
>
> **`actionCd:'EXPORT'` 가 걸리기 쉽다.** 위의 인쇄 버튼처럼 출력 계열을 선언하는데, 그
> 화면의 엑셀이 프론트 생성이면 `SYS_API` 에 `EXPORT` 행이 없어 **메뉴가 `EXPORT_YN` 으로
> 선언하지 않는 한 정의되지 않는다**([42](../../../knowledge/sys/menu.md) §4). 나머지 셋은 그 액션의 API 를 이 화면이
> 하나라도 쓰고 있으면 자동으로 정의된다.

> **`requires` 같은 이름을 쓰지 않는다.** *"필수 입력 요건"* 으로 읽혀 컬럼의
> `required`([54](./grid-column-contract.md) §5.1)와 섞인다. **테이블 컬럼명을 그대로 쓰면 무엇을 가리키는지
> 물을 필요가 없다** — 설계 문서 모음 의 `AUTH` 용어 규약이 같은 방향이다.

판정과 감춤은 API 버튼과 **같다** — 유효 권한에 없으면 감춘다([51](./main-shell.md) §6).

#### 선언을 여는 것이 순수하게 나은 이유

*"손으로 적으면 빠뜨린다"* 는 걱정은 **자동 도출을 수동 선언으로 바꿀 때** 성립한다.
여기는 다르다 — **도출할 근거가 애초에 없다.**

| | 선언을 막으면 | **`actionCd` 를 열면** |
|---|---|---|
| 적지 않으면 | 항상 보인다 | **항상 보인다** — 같다 |
| 적으면 | **적을 수 없다** | 권한대로 감춘다 |

**빠뜨렸을 때의 결과가 양쪽이 같으므로** 선언을 여는 것은 잃는 것이 없다.

> **막지 않았다면 구멍이 생겼다.** 인쇄(UX-12)는 엑셀과 **같은 데이터를 내보낸다.**
> 엑셀은 `E` 로 감추면서 인쇄를 열어 두면 **막은 것을 옆문으로 내보내게 된다.**

#### `actionCd` 는 표시 규칙이지 보안 경계가 아니다

| | 무엇이 집행하나 |
|---|---|
| `api.actions[]` 의 권한 | **서버** — 인가 인터셉터가 URL 로 판정한다([23](../../backend/_study/security-design.md) §4). 버튼을 감추는 것은 편의다 |
| **`controls.actionCd`** | **화면뿐** — 서버가 볼 요청이 아예 없다 |

**인쇄를 감췄다고 데이터가 못 나가는 것은 아니다** — 이미 화면에 있는 것을 사용자가 캡처할
수 있다. 진짜 방어는 **애초에 조회 권한을 주지 않는 것**이다. `actionCd` 는 *"엑셀은 막고
인쇄는 여는"* **일관성의 붕괴를 막는 것**이지 통제 수단이 아니다.

#### 그래도 서버를 부르면 `actions` 다

| 이 버튼은 | 어디에 | 받는 것 |
|---|---|---|
| 서버를 부른다 | **`api.actions[]`** | 권한 · 잠금 · **검증 · 확인 · 재조회 · 콜백** |
| 서버를 부르지 않는다 | **`controls`** | 권한 · 잠금 |

> **`controls` 의 `onClick` 에서 서버를 부르지 않는다.** 권한을 걸 수 있게 됐다고 달라지지
> 않는다 — 여기 두면 **검증도 확인도 재조회도 없이** 호출되고, **서버 인가가 집행할 URL 을
> 선언에서 잃는다.** 규약으로 막고 리뷰에서 본다.

### 3.6 행 추가는 `addRow` 가 정한다 — **선언하지 않으면 버튼이 없다**

**저장 권한이 있어도 행을 추가하면 안 되는 그리드가 많다.** 조회 전용 디테일 탭,
서버가 만드는 행(로그·세션), 부모를 먼저 저장해야 하는 자식 그리드가 그렇다.
**`api.save` 가 있다고 행 추가 버튼을 자동으로 내지 않는다.**

```ts
addRow: true                      // 기본값만 쓸 때
addRow: {
  label,                          // 메시지 키. 기본 '행 추가'
  canAdd:   (rows, ctx) => true | { ok:false, message },   // 누른 순간 판단
  defaults: (rows, ctx) => ({ … }),                        // 새 행의 초기값
  onAdd:    (row, rows, ctx) => void,                      // 추가 후
}
```

| 키 | 기본값 | 무엇 |
|---|---|---|
| **`addRow` 자체** | **없음 — 버튼이 나오지 않는다** | 선언이 곧 허용이다 |
| `label` | `행 추가` | |
| **`canAdd`** | 없음(항상 가능) | **지금 추가해도 되나** + 안 되면 이유 |
| **`defaults`** | 없음(빈 행) | 새 행의 초기값 |
| **`onAdd`** | 없음 | 추가 후 화면이 더 할 일 |

#### 추가하면 **첫 입력 칸이 열린다** (2026-08-31 — 구현)

행을 더한 다음에 사람이 하는 일은 **언제나 첫 칸을 채우는 것**이다. 그것을 클릭 두 번
(행 선택 · 셀 더블클릭)으로 두면 *행 추가* 가 **세 동작**이 되고, 새 행이 판 위쪽에 붙으므로
([53](./grid-standard.md) §3.3) 스크롤이 아래에 있으면 **추가된 행이 보이지도 않는다.**

| | |
|---|---|
| 어느 칸인가 | **화면에 보이는 순서로 첫 편집 가능 칸.** 판에게 묻는다 — 사용자가 끈 컬럼과 옮긴 순서가 판의 상태이므로([53](./grid-standard.md) §5) **선언의 첫 컬럼이 화면의 첫 컬럼이 아닐 수 있다** |
| 편집기를 여는 조건 | **일반 텍스트 칸일 때만.** 나머지는 **포커스만** 준다 |
| 자리를 어떻게 찾나 | **행 id 로** 찾는다(`getRowNode`) — 번호로 두면 정렬·필터가 행을 옮겼을 때 **엉뚱한 행의 셀**이 열린다 |

> **텍스트 말고는 열지 않는 이유.** 스위치는 편집 모드가 없고([54](./grid-column-contract.md) §5.2 — 한 번 누르면
> 그것이 값이다), 달력·콤보는 열린 채로 시작하면 **판을 덮는 판**이 사람이 요청하지도 않은
> 상태로 떠 있게 된다. 텍스트는 열려 있어도 그냥 빈 칸이라 그 부담이 없고, **바로 타이핑할
> 수 있다는 이득만** 남는다.

#### 왜 기본값이 *"버튼 없음"* 인가

[54](./grid-column-contract.md) §2 가 `editable` 기본값을 **`false`** 로 둔 것과 같은 방향이다 — **편집은
명시해야 열린다.** 반대로 두면 조회 전용 그리드마다 `addRow: false` 를 적어야 하고,
**빠뜨린 화면에 버튼이 생긴다.** 빠뜨렸을 때 **덜 열리는 쪽**으로 실패해야 한다.

#### 권한은 저장에 붙는다

**행 추가에는 URL 이 없어 액션을 유추할 수 없다**([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)). `api.save` 의 `SAVE`
권한을 따른다 — **추가한 행은 저장으로만 서버에 가므로**, 저장할 수 없는 사람에게
추가를 허용하면 **버릴 것을 만들게 한다.**

| 조건 | 버튼 |
|---|---|
| `addRow` 선언 없음 | **없다** |
| 선언했으나 `api.save` 가 없다 | **없다** — 나갈 곳이 없다 |
| 선언 + `SAVE` 권한 없음 | **감춘다**(§3) |
| 마스터-디테일 빈·잠긴 상태 | **비활성**([53](./grid-standard.md) §6.1) |
| `canAdd` 가 거부 | **비활성 아님 — 눌리고 메시지를 낸다**(아래) |

#### `canAdd` 는 누른 순간에 판단하고, 안 되면 이유를 말한다

**비활성으로 막지 않는다.** 회색 버튼은 *"왜 안 되는지"* 를 말하지 못하고, 사용자는
**화면이 고장난 줄 안다** — [56](./grid-edit-validation.md) §2.1 이 `editable` 에서 같은 판단을 했다.

```ts
canAdd: (rows) => rows.length < 100
  ? true
  : { ok:false, message: '한 번에 100건까지 등록할 수 있습니다' }
```

| 실물 | |
|---|---|
| 건수 상한 | *"한 번에 100건까지"* |
| **미저장 행이 있으면 막는다** | *"먼저 저장하세요"* — 순번을 서버가 매기는 그리드 |
| 상태 의존 | *"마감된 전표에는 행을 추가할 수 없습니다"* |

**반환 형태가 [56](./grid-edit-validation.md) §2.1 의 `editable` 과 같다** — `true | { ok:false, message }`.
규약이 하나면 기억할 것이 없다. 메시지는 **토스트**로 낸다(§9).

> **`canAdd` 는 검증이 아니다.** [56](./grid-edit-validation.md) §3 의 세 층은 **이미 있는 행의 값**을 본다.
> `canAdd` 는 *"행을 만들어도 되나"* 이며 값이 아직 없다.

#### `defaults` — 빈 행으로 시작하지 않는다

```ts
defaults: (rows, ctx) => ({
  useYn:    'Y',                  // 켜 두는 것이 정상이다
  validFrom: ctx.today,           // 거의 항상 오늘
  whCd:     ctx.master.whCd,      // 부모에서 물려받는다
  sortSeq:  rows.length + 1,      // 직전 행에서 잇는다
})
```

| 규칙 | 왜 |
|---|---|
| **사람이 정해야 하는 값은 채우지 않는다** | 기본값을 넣으면 *"그대로 저장"* 이 된다 — [61](../../../../documents/screen/user/requirements.md) §4.4 가 재부여에서 사유를 비운 것과 같다 |
| **`afterEdit` 를 부르지 않는다** | 행 생성은 편집이 아니다. 계산이 필요하면 **`defaults` 안에서 전부 한다** — [56](./grid-edit-validation.md) §2.3 의 *"연쇄는 한 단계에서 멈춘다"* 와 같은 이유 |
| **읽기 전용 컬럼에도 넣을 수 있다** | 서버가 채울 값을 미리 보여주는 것이다. 편집 가능 여부와 다른 축이다 |

#### 새 행은 맨 위에 붙고, 정렬·필터를 타지 않는다

| | |
|---|---|
| 자리 | **맨 위** — 방금 만든 것이 바로 보인다. 아래에 붙이면 스크롤해야 한다 |
| 정렬([54](./grid-column-contract.md) §3) | **대상이 아니다** — 정렬은 서버가 하고 이 행은 서버에 없다 |
| 필터([54](./grid-column-contract.md) §4) | **대상이 아니다** — 값이 비어 있어 **거의 항상 걸러진다.** 방금 만든 행이 사라지면 사고다 |
| 페이지 이동 | **확인 다이얼로그** — 미저장 행이 버려진다. **정렬 · 조회 · 페이지 사이즈도 같다**([53](./grid-standard.md) §3.1 이 넷을 한 규칙으로 묶었다) |

#### `onAdd` 와 편집 진입

**편집 진입은 컴포넌트가 한다** — 편집 가능한 가장 왼쪽 셀이 자동으로 편집 모드가 되고
포커스가 들어간다([56](./grid-edit-validation.md) §2.2). `onAdd` 는 **그 위에 화면이 더 하는 것**이다.

- 포커스를 다른 컬럼으로 옮긴다 — `defaults` 가 앞 컬럼을 이미 채웠을 때
- 팝업을 연다 — 상품을 먼저 골라야 하는 그리드([54](./grid-column-contract.md) §6)
- 화면의 다른 자리를 갱신한다 — 건수 표시 등

**행 상태는 `onAdd` 가 바꿀 수 없다.** 추가 행은 끝까지 추가다([53](./grid-standard.md) §3.3).

### 3.7 `controls` 가 받지 못하는 것

| | |
|---|---|
| 검증 · 확인 · 재조회 · 콜백 | §5~§7 의 흐름은 `api` 선언에만 붙는다 |
| `params` 모달(§8) | 〃 |

### 3.8 렌더 함수(JSX)를 받지 않는 이유

*"헤더에 `children` 을 열어 화면이 아무거나 넣게 하면 되지 않나"* — 그렇게 하지 않는다.

| 열면 | |
|---|---|
| **잠금이 안 걸린다** | 화면이 만든 버튼은 그리드의 in-flight 상태를 모른다(§4) |
| **모양이 갈린다** | 크기 · 간격 · 아이콘 규격이 화면마다 달라진다 |
| **권한 없는 버튼이 섞인다** | 자동 렌더링이 거른 것 옆에 거르지 않은 것이 놓인다 — `actionCd`(§3.3)도 지나지 않는다 |
| **경계가 무너진다** | 화면이 그리드 내부를 알게 된다 — [ADR-0018](../../../records/adr/0018-grid-edition-agnostic-vocabulary.md) 이 어댑터 경계를 둔 것과 같은 논리 |

**컴포넌트는 헤더를 통째로 렌더한다.** 화면이 주는 것은 `api` 와 `controls` **선언 둘**이고,
헤더는 그것을 한 배열로 합쳐 순서대로 그린다.

```
[ controls(beforeRead) ] [ 조회 · 저장 · actions ] [ controls(beforeTools) ] [ ⤓▾ ] [ ⚙ ]
        Ⓐ                    ① — 권한으로 거른다             Ⓑ                ②      ③
```

**모든 컨트롤이 같은 상태를 본다** — `{ inFlight, 마스터-디테일 상태, 선택 행 수 }`. 이것이
선언형으로 닫는 값어치다. 손으로 놓은 버튼은 이 상태를 볼 수 없다.

## 4. 응답을 받기 전에는 다시 실행하지 않는다

**두 층에서 막는다.**

| 층 | 막는 것 |
|---|---|
| **버튼** | 요청이 나가는 순간 **①②를 전부 비활성**한다. 응답이 오면 푼다 |
| **API 호출** | 같은 그리드의 호출이 **진행 중이면 새 호출을 거부**한다 |

- **버튼만 막지 않는다.** 키보드·단축키·프로그램 경로가 남는다
- **잠금은 그리드 단위**다. 조회 중에 저장하거나 저장 중에 조회하면 **화면의 데이터와
  서버의 데이터가 어긋난 채 섞인다** — 버튼 하나씩 잠그면 그 조합이 열린다
- **③(그리드 설정)은 잠그지 않는다.** 개인화라 데이터와 무관하다
- 실패해도 **반드시 푼다.** 에러 모달을 띄우고 잠금을 그대로 두면 화면이 죽는다

> **[29](../../backend/crosscutting.md) 의 중복 요청 방어와 다른 층이다.** 29 는 **서버 측** at-most-once(`X-Request-Id`,
> 기본 OFF)이고 여기는 **클라이언트 측 in-flight 잠금**이다. 클라이언트 잠금은 **네트워크
> 지연 중의 더블클릭**을 막고, 서버 방어는 **재시도·새로고침·프록시 재전송**을 막는다 —
> 하나가 다른 하나를 대신하지 못한다.

## 5. 조회 — 조건은 폼이 검증해서 준다

```
① 그리드가 조회조건 폼에 파라미터를 요청
② 폼이 자기 검증을 수행         ── 실패 → 조회하지 않는다. 폼이 오류를 표시
③ 폼이 최종 값을 넘긴다
④ 그리드가 호출                 ── 실패 → 에러 모달(§9)
⑤ 성공 → 데이터 로드
⑥ 0건이면 옵션에 따라 알린다
```

- **조회 조건의 검증은 폼이 한다.** 그 규칙은 폼이 갖고 있고(UX-15) 그리드가 알면
  **같은 규칙이 두 곳에 생긴다.** 그리드는 *"값을 달라"* 고 요청할 뿐이다 — `params` 의
  계약은 §8 이며 **조회조건 폼도 파라미터 모달도 같은 모양**이다
- 검증 실패면 **조회 자체가 일어나지 않는다** — 오류 표시는 폼의 몫이다
- **컬럼 필터는 유지된다**([54](./grid-column-contract.md) §4.2) — 새로 받은 결과에 다시 걸린다

**디테일 그리드에는 폼이 없다** — §1.1 의 조회조건 폼은 **마스터의 것**이다(§2.4 · [53](./grid-standard.md) §1.1).
디테일은 **마스터의 PK 를 그대로 넘기는 고정형 조회**이며 **연산자가 없는 전용 요청**을 쓴다.

```jsonc
{ "userId": "kim.jb", "page": { "page": 0, "size": 20 } }
```

**동적 조회 봉투([72](../../backend/_study/api-conventions.md) §3.1)를 쓰지 않는다.** 쓰면 부모 키 제약이 **클라이언트가 보낸
조건 하나**가 되어, `conditions` 를 빈 배열로 보내면 **남의 자식 행이 전부 나온다** —
[72](../../backend/_study/api-conventions.md) §3.0 이 조회를 둘로 가른 이유이며, 구현은 [34](../../backend/search.md) §2·§3 이다.

**0건 알림(`emptyNotice`)의 기본값이 자리마다 다르다.**

| 그리드 | 기본 | 왜 |
|---|---|---|
| **마스터** | **알린다** | 사용자가 조건을 넣고 기다린 결과다. 빈 그리드만 보여주면 *"조회가 된 건가 안 된 건가"* 를 알 수 없다 |
| **디테일** | **알리지 않는다** | 마스터 행을 고를 때마다 **자동으로** 도는 조회다. 역할이 없는 사용자를 고를 때마다 모달이 뜨면 클릭을 방해한다 |

**빈 상태 표시(`<EmptyState>`)는 알림과 별개로 항상 나온다** — 알림은 흐름을 멈추는 것이고
빈 상태는 그리드가 비어 있다는 표시다.

## 6. 저장 — 검증 → 확인 → 저장 → 재조회

```
① 검증        ── 실패 → 오류 목록 · 첫 실패 셀로 이동(54 §8.3). 서버를 부르지 않는다
② 확인        ── "추가 N · 수정 M · 삭제 K건을 저장하시겠습니까?"   (confirm: false 면 건너뛴다)
③ 저장        ── 실패 → 에러 모달 → onError
④ 성공 모달   ── 확인을 누르면
⑤ 재조회      ── 현재 페이지를 다시 조회               (reloadAfter: false 면 건너뛴다)
⑥ onSuccess
```

| 옵션 | 기본 | |
|---|---|---|
| `confirm` | **`true`** | **건수를 알리고 묻는다.** 일괄 저장은 화면에 안 보이는 행까지 나가므로([53](./grid-standard.md) §3.1) 건수가 유일한 요약이다 |
| `reloadAfter` | **`true`** | 서버가 채운 값(감사 컬럼 · 생성 키 · 트리거 결과)이 화면에 없다 |
| `onSuccess` · `onError` | 없다 | 재조회 **말고** 다른 일이 필요할 때 |

- **확인 문구에 숨겨진 행을 포함한다** — 컬럼 필터로 안 보이는 변경 행이 있으면 그 건수도
  함께 알린다([53](./grid-standard.md) §3.1)
- **재조회는 성공 모달의 확인 이후**다. 모달과 동시에 돌면 사용자가 결과를 읽는 동안
  화면이 바뀐다
- **`onSuccess` 는 재조회를 대신하지 않는다.** 둘 다 설정하면 재조회 후에 돈다 — 콜백이
  최신 데이터를 보게 해야 한다

## 7. 실행 — 선택 행이 대상이다

```
① 대상 확인   ── 선택 0건이면 버튼이 비활성이다
② 검증        ── 그 action 의 검증(54 §8.2). 실패 → 중단
③ params()    ── 파라미터 모달이 있으면 열고 기다린다(§8). 취소 → 중단
④ 확인        ── "선택한 N건을 실행하시겠습니까?"   (③ 이 있으면 모달이 겸한다)
⑤ 호출 → 성공/실패 모달 → 재조회 → 콜백      (§6 와 같은 꼬리)
```

| 키 | 값 | |
|---|---|---|
| `target` | **`selected`**(기본) · `all` · `none` | 어느 **묶음**을 보나 |
| **`eligible`** | 없음(기본) · `(row) => boolean` | 그 묶음 안에서 **무엇이 대상인가** — 아래 |
| `toTargets` | 없음(기본) · 함수 | 대상 행 → 요청의 `targets`. **모양만 바꾸는 자리**다 |
| **`params`** | 없음(기본) · 함수 | **모달로 임의의 인자를 받는다** — §8 |
| **`hint`** | 없음(기본) · 메시지 키 | **왜 눌리지 않는가** — 비활성 버튼의 툴팁. 아래 |
| 나머지 | `confirm` · `reloadAfter` · `validate` · `onSuccess` | §6 와 같다 |

#### `hint` — 비활성 사유가 *선택 0건* 이 아닐 때 (2026-08-31)

[61](../../../../documents/screen/user/requirements.md) §3.7.1 이 요구했다. 자기 계정의 세션은 끊을 수 없는데(그 자리에서 화면 밖으로
밀려난다) 그것은 **권한이 아니라 대상 제약**이라 감추면 *"왜 이 사람만 안 되나"* 가 된다 —
**보이되 막고 사유를 붙인다.** `GridControl.hint` 와 같은 자리이며 문구도 같은 방식이다.

> **선택 0건뿐인 실행에는 두지 않는다.** 무엇이 모자란지가 화면에 이미 보이므로 툴팁은
> 같은 말을 한 번 더 하는 것이다.

#### `eligible` — 대상 여부를 **행의 값**이 정할 때 (2026-08-30)

*실행 중인 배치만 중단할 수 있다*([65](../../../../documents/screen/batch/schedule/requirements.md) §4.5)처럼 **고른 것 전부가 대상은 아닌** 실행이 있다.
`target` 이 *어느 묶음을 보나* 라면 이것은 **그 안에서 무엇이 대상인가**다.

**`toTargets` 안에서 거르면 안 된다** — 거기서 줄이면 **확인 문구의 건수가 실제 실행 건수와
어긋난다**: *"3건을 실행합니다"* 라고 묻고 1건만 나간다. 그래서 `eligible` 은 **①(대상 확인)
에서** 걸리며, 걸러진 결과가 비면 **버튼이 아예 비활성**이고 확인 문구의 `{count}` 도
`params` 모달의 기본값도 그 결과를 본다.

> **서버는 거르지 않고 거절한다.** 화면이 고른 사이에 그 행의 상태가 바뀔 수 있고, 그때
> 조용히 건너뛰면 *"눌렀는데 아무 일도 없다"* 가 된다([56](./grid-edit-validation.md) §3.4 — 최종 판정은 서버다).

> **버튼의 활성 판정과 실행이 같은 함수를 부른다**(`actionTargets`). 두 곳에서 따로 세면
> **켜져 있는데 눌러도 아무 일 없는** 버튼이 생기고, 그 버튼은 이유도 말하지 못한다.

#### 액션 코드는 **`url` 이 말한다** — 선언하지 않는다

`controls` 는 `actionCd` 를 손으로 적지만(§3.3 — 도출할 URL 이 없다) 여기는 **URL 이 있다.**
경로 접두가 액션을 정하고([ADR-0020](../../../records/adr/0020-path-prefix-action-and-seed-generation.md)) 그 규칙이 곧 시드를 만들므로, 선언에 또 적으면
**같은 사실이 두 곳**이 되어 시드와 어긋난다.

> **프론트에 규칙의 사본이 하나 생긴다**(`shared/authz/apiAction.ts`). **원본은 시드
> 생성기**이며(`bootstrap/build.gradle.kts` 의 `actionOfPath`), 사본이 틀려도 데이터는 새지
> 않는다 — 여기서 하는 판정은 *버튼을 그릴까* 이고 최종 판정은 인가 인터셉터다([23](../../backend/_study/security-design.md) §4).
> 틀리면 드러나는 증상은 **눌러도 403 인 버튼**이거나 **보이지 않는 버튼**이며, 둘 다
> `API_CATALOG`([62](../../../../documents/screen/menu/requirements.md) §5)와 대조하면 곧 보인다.

- **`target: 'selected'` 이면 선택 0건일 때 버튼이 비활성**이다. 눌렀는데 *"선택하세요"*
  가 뜨는 것보다 **누를 수 없는 것이 먼저 보이는 편**이 낫다
- `target: 'none'` 은 행과 무관한 실행이다(예: 전체 재계산). 확인 문구에 건수를 넣지 않는다
- **미저장 변경이 있을 때 실행을 막을지는 `validate` 로 표현한다** — 대부분의 실행은
  저장된 데이터를 대상으로 하므로, 그 조건이 필요하면 그리드 단위 검증에 적는다

## 8. `params` — 값을 만드는 것은 그리드가 아니다

**그리드는 값을 요청할 뿐이고, 값을 만들고 검증하는 것은 그것을 가진 쪽이다.**

```ts
params: (rows?) => Promise<값 | null>
```

| 어디서 오나 | 누가 검증하나 | 취소 |
|---|---|---|
| **조회조건 폼**(`read`) | 폼 — UX-15 | 검증 실패 → 조회하지 않는다 |
| **파라미터 모달**(`actions` · `save`) | **모달** | 취소 · 검증 실패 → **`null` 반환, 실행하지 않는다** |
| 없음 | — | `params` 를 선언하지 않으면 이 단계가 없다 |

- **`Promise` 로 통일한다.** 폼은 이미 화면에 있어 즉시 값을 낼 수 있지만 모달은 열고
  기다려야 한다. 둘을 다르게 두면 그리드가 **두 경로를 알아야** 하고, 조회 조건을 모달로
  받는 화면이 생기는 순간 규칙이 또 갈린다
- **`null` 이 취소다.** 예외를 던지게 하면 취소와 오류가 같은 통로로 오고, 취소마다 에러
  모달이 뜬다
- `rows` 는 **`target` 이 고른 대상**이다(§7) — 선택 행의 값으로 모달의 기본값을 채울 수 있다

#### 파라미터 모달이 있으면 확인(`confirm`)을 겸한다

모달에 **건수를 표시하고 실행/취소 버튼**을 두면 확인이 이미 거기 있다. `params` 와
`confirm` 을 둘 다 켜면 **같은 것을 두 번 묻는다.**

| `params` | `confirm` | 사용자가 보는 것 |
|---|---|---|
| 없음 | `true`(기본) | 확인 다이얼로그 — *"선택한 N건을 실행하시겠습니까?"* |
| **있음** | — | **파라미터 모달 하나** — 건수 표시 + 입력 + 실행/취소 |

#### 순서 — 검증이 먼저, 파라미터가 나중

```
① 대상 확인 → ② 검증 → ③ params() → ④ 호출
```

**데이터가 틀렸는데 파라미터를 입력하게 하면 헛수고다.** 사유를 다 쓰고 나서
*"3건의 오류가 있습니다"* 를 보는 것이 가장 나쁜 순서다.

> **파라미터에 따라 검증이 갈리는 경우는 이 순서로 담을 수 없다.** 그때는 **모달이 자기
> 검증에서 처리하거나 서버가 판정한다** — 프론트 검증은 UX 이고 최종 판정은 서버다
> ([56](./grid-edit-validation.md) §3.4). 순서를 옵션으로 뒤집게 하면 화면마다 흐름이 갈린다. §10 미결.

#### 요청 페이로드는 둘로 나뉜다

| 자리 | 무엇 |
|---|---|
| 대상 행 | `target` 이 고른 것(§7) — `save` 는 상태가 붙은 변경 행([53](./grid-standard.md) §3.1) |
| **`params`** | 모달·폼이 만든 값 |

**둘을 섞지 않는다.** 섞으면 서버가 *"이 필드가 행의 것인가 파라미터인가"* 를 이름으로
추측하게 된다.

> **봉투의 이름은 고정이다** — 몸통은 `{ targets, params }` 이며 `toTargets` 는 **`targets`
> 안쪽의 모양만** 바꾼다. 2026-09-02 에 [68](../../../playbook/INDEX.md) §3.4 의 실행 둘이 이것을
> 어겨(`ordIds` · 두 칸을 맨 위에) **한 번도 서버에 닿지 않은 채** 서 있었다. 서버 쪽은
> **읽는 칸만 선언한다**(`UserTargetRequest` 는 `params` 가 없고 `SampleRecalcRequest` 는
> `targets` 가 없다) — 읽지 않는 칸을 선언하면 *그것을 쓴다* 고 말하는 셈이 된다.
>
> **`params` 를 서버가 실제로 받는 첫 자리가 저 재계산이다.** 그전까지는 이 절의 오른쪽
> 칸이 **선언만 있고 받는 쪽이 없었다** — 그래서 어긋남이 드러날 자리도 없었다.

#### 이 모달은 §1.1 의 예외가 아니다

[53](./grid-standard.md) §1.1 이 없앤 것은 **그리드 행을 편집하는 폼**이다. 파라미터 모달은 그리드 행이 아니라
**API 호출의 인자**를 받으므로 *"같은 테이블에 저장 경로가 둘"* 이 되지 않는다.

| | 편집 폼(두지 않는다) | **파라미터 모달**(둔다) |
|---|---|---|
| 무엇을 받나 | **행의 컬럼 값** | **호출의 인자** |
| 저장되는 곳 | 그리드가 이미 담당하는 테이블 | 그 API 가 정한다 |
| 없으면 | 셀 편집으로 대신할 수 있다 | **대신할 자리가 없다** |

`<FormModal>`([24](./frontend-stack.md) §7)의 쓰임이 여기다 — 등록/수정 모달이 아니라 **실행 파라미터 모달**이다.

> **2026-09-02 — 섰다**(`shared/formmodal`). 위 표가 *취소* 와 *검증 실패* 를 같은 칸에
> 넣었지만 **동작은 갈린다**: 결과는 둘 다 *실행하지 않는다* 이되, 취소는 창이 닫히고
> **검증 실패는 열린 채로 이유가 붙는다.** 닫아 버리면 사용자는 무엇이 틀렸는지 보지
> 못한 채 처음부터 다시 연다.
>
> **`progress: true` 인 실행에는 성공 모달이 뜨지 않는다**([68](../../../playbook/INDEX.md) §9.1). 여기서 성공은
> *접수됐다* 이지 *끝났다* 가 아니며, §9 의 *실행이 완료되었습니다* 를 그대로 내면
> **화면이 거짓말한 것**이 된다 — 사용자는 목록을 보러 갔다가 아무것도 안 바뀐 것을 본다.

## 9. 무엇을 모달로, 무엇을 토스트로 내나

| 알림 | 수단 | 왜 |
|---|---|---|
| 조회 · 저장 · 실행 **실패** | **모달** | 읽고 조치해야 한다. **놓치면 안 된다** |
| 저장 · 실행 **성공** | **모달** | **확인이 다음 단계(재조회)를 트리거한다** |
| 조회 **0건** | **모달**(옵션 — §5) | 위와 같은 흐름에 있다 |
| 저장 · 실행 **전 확인** | **확인 다이얼로그** | UX-10. **`params` 모달이 있으면 그것이 겸한다**(§8) |
| 실행 **파라미터 입력** | **모달** | 값을 받아야 진행한다 — §8 |
| 편집 거부([56](./grid-edit-validation.md) §2.1) · 사소한 안내 | **토스트** | 흐름을 멈출 이유가 없다 |

**가르는 기준은 "흐름을 멈춰야 하는가" 하나다.** 토스트는 사라지므로 **놓쳐도 되는 것**에만
쓴다 — 저장 결과를 놓치면 사용자는 저장이 됐는지 모른 채 다시 누른다.

> **에러 모달의 문구는 서버가 완성해 내려준다**([21](../../backend/_study/architecture.md) §6-1.2). 화면은 `code` 로
> 분기하지 않고 받은 `message` 를 그대로 넣는다 — [60](../../../../documents/screen/_standalone/README.md) §3.6 이 로그인 화면에서 같은
> 판단을 했다.

| **`onSuccess` 와 재조회의 순서**(§6) — 재조회 후에 도는 것으로 뒀다. 재조회를 기다리지 않아야 하는 콜백이 있는지 | 결정 | 템플릿 | Phase 6 |
| **잠금의 범위를 넓힐지**(§4) — 지금은 그리드 단위다. 마스터가 저장 중일 때 디테일도 잠글지(마스터-디테일은 [53](./grid-standard.md) §6.1 이 이미 리셋한다) | 결정 | 템플릿 | Phase 6 |

| **`target: 'all'` 이 보내는 것**(§7) — 현재 페이지인지 조회 조건 전량인지. 후자면 서버가 조건으로 다시 뽑는다. **아직 쓰는 화면이 없다** — 첫 실물 셋이 전부 `selected` 다 | 결정 | 템플릿 | Phase 6 |
| **`onSuccess` 가 모달을 열면 모달이 둘이 된다**(§7 · §9) — *"실행했습니다"* 다음에 화면의 모달이 뜬다([61](../../../../documents/screen/user/requirements.md) §3.4 의 임시 비밀번호 · [65](../../../../documents/screen/batch/schedule/requirements.md) §3.7). **선언에서 알 수 없다**: 같은 `onSuccess` 를 조용한 재조회에만 쓰는 화면도 있고(61 §4.4 의 트리 재조회) 거기서 일반 모달을 지우면 **성공했다는 말이 사라진다**. 추론하지 말고 선언을 하나 열지, 그냥 둘지 | 결정 | 템플릿 | Phase 6 |
| **실행의 꼬리를 다른 그리드로 돌릴지**(§7) — `reloadAfter` 는 **자기 그리드**를 다시 읽는다. 하단 pane 을 읽어야 하는 실행이 있고([65](../../../../documents/screen/batch/schedule/requirements.md) §3.7 의 즉시 실행) 지금은 `reloadAfter: false` + `onSuccess` 로 화면이 직접 부른다. 옵션으로 열면 **그리드가 남의 그리드를 알게 된다** | 결정 | 템플릿 | Phase 6 |

### 해소된 미결

| 항목 | 결론 | 해소일 |
|---|---|---|
| **`api.actions[]` 를 언제 만들 것인가**(§3) — *"첫 실행 버튼이 생기는 화면이 가져온다 — 지금 만들면 눌러 본 적 없는 흐름이 남는다"* | **[61](../../../../documents/screen/user/requirements.md) §3.4 가 가져왔다.** 미룬 값이 그대로 나타났다 — 실제 화면 하나로는 안 보였을 것 둘이 붙어 왔다: **`eligible`**(고른 것 전부가 대상은 아닌 실행 — [65](../../../../documents/screen/batch/schedule/requirements.md) §4.5 가 요구했다)과 **응답을 화면에 주는 `onSuccess`**(임시 비밀번호처럼 재조회로 얻을 수 없는 값 — 61 §3.4). 둘 다 *언젠가 필요할 것* 으로는 설계되지 않았을 모양이다 | 2026-08-30 |
| **`menuCd` 를 쓸 일이 실제로 있나**(§3.3) — *사례가 없으면 키를 없앤다* 로 남겼던 것 | **남긴다.** 모수로 삼은 `62`~`65` 가 **시스템 관리 화면**이라 요구가 안 나왔을 뿐이며, 여기는 **업무 도메인을 가리지 않는 베이스**다([57](./search-form-contract.md) §1.1). 업무 화면의 *"주문에서 재고 조정 열기"* 같은 이동 버튼이 **다른 화면의 권한**을 요구한다 — 키가 없으면 **권한 없는 사용자에게 보이는 버튼**이 생긴다 | 2026-08-28 |
