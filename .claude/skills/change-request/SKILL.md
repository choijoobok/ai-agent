# 변경 요청 처리

## 먼저 확인: CR이 필요한가
`gates.P3_design.status != approved` 면 CR 불필요. 그냥 spec을 고친다.
G3 승인 이후에만 CR 절차를 탄다. → `aidd-guide/process/change-control.md`

## 절차

### ① 접수 및 분류
`Add` (추가) / `Modify` (변경) / `Remove` (삭제) / `Fix` (오류정정)

### ② 영향 분석
`/trace --impact <ID>` 로 체인을 타고 영향을 전부 나열한다.
- 직접 영향: 반드시 수정할 산출물 ID
- 간접 영향: 검토 필요한 것 (관련 ADR, 인접 화면, 이미 구현된 슬라이스)
- **재작업 규모**: 슬라이스 몇 개 분량인지

### ③ 3옵션 제시 (반드시 3개)
```
(A) 지금 반영 — 영향/일정
(B) 나중에 (2차 / P5 이후) — 리스크
(C) 안 함 — 대안(수기 운영 등), 예상 불만
```
**옵션 C를 항상 포함한다.** AI는 요청을 거절할 줄 모르므로 거절을 선택지로 만들어 준다.
권장안을 표시하되 결정은 사용자가 한다.

### ④ 반영
사용자 판정 후: spec 수정 → `/doc-gen` 재생성 → 영향 슬라이스 상태를 `todo` 로 되돌림
→ 관련 TC 갱신 → 필요 시 ADR 추가

### ⑤ 기록
`documents/decisions/CHANGES.md` 에 CR-### 등록. `documents/project.state.yaml` counters 갱신.

## 범위 증가 감지
CR 처리할 때마다 누적을 계산해 보고한다.
```
G3 대비: FEAT 62 → 71 (+14.5%)  누적 CR: Add 7 / Modify 3 / Remove 1
⚠️ 베이스라인 대비 15%에 근접. 범위 재조정을 검토하시겠습니까?
```
**AI가 할 수 있는 유일한 범위 통제는 누적 증가를 보여 주는 것이다.**

## 배포 후 변경이면 추가로 요구
마이그레이션 계획 / 하위 호환성 / 롤백 시나리오 / 사용자 공지 — 4개 없으면 접수하지 않는다.
